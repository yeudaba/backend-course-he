1. ESLint

אחרי ההתקנה בקופסת 🧰, VS Code מסמן בעיות בזמן הקלדה. אפשר גם להריץ על קובץ או תיקייה:

```term % npx eslint 01-values-variables/starter/P01-E23-old-code.js .. /Users/yeuda/dev/backend-course/01-values-variables/starter/P01-E23-old-code.js 2:1 error Unexpected var, use let or const instead no-var 3:1 error Unexpected var, use let or const instead no-var 4:1 error Unexpected var, use let or const instead no-var 5:1 error Unexpected var, use let or const instead no-var ✖ 4 problems (4 errors, 0 warnings) 4 errors and 0 warnings potentially fixable with the `--fix` option. ```

כל שורה: מיקום (שורה:עמודה), חומרה, הסבר, ושם הכלל. הכללים שהפעלנו בקורס:

(npx מריץ כלי שהותקן בפרויקט — נסביר בפרק 13. ו־`npm run lint` הוא קיצור שהגדרנו ב־`package.json`.)

2. השיטה: חמישה שלבים לכל באג

  1. שחזר. מצא קלט מדויק שגורם לבאג, כל פעם. "לפעמים זה קורה" — עוד לא שחזור. רשום אותו.
  2. בודד. צמצם: הקלט הכי קטן שעדיין שובר; החלק הכי קטן של הקוד שמעורב. stack trace, breakpoint, או "חיפוש בינארי" — כבה חצי מהקוד (הערות) ובדוק אם הבאג עוד קיים.
  3. השערה. נסח במשפט: "אני חושב ש־X קורה כי Y". אם אתה לא יכול לנסח — חזור לשלב 2.
  4. תקן — שינוי אחד. רק את מה שההשערה אומרת. אם התיקון לא עבד, בטל אותו לפני שמנסים אחר (אחרת מצטברים שינויים שאף אחד לא מבין).
  5. הוכח והגן. הרץ את הקלט מהשלב הראשון — ועוד כמה. ובעולם המקצועי: כתוב בדיקה אוטומטית שנכשלת לפני התיקון ועוברת אחריו, כדי שהבאג לא יחזור לעולם (פרק 22).
💡 שיטת הברווז

תקוע? הסבר את הקוד, שורה אחר שורה, בקול, למישהו — או לברווז גומי על השולחן (באמת — זו טכניקה מוכרת: "rubber duck debugging"). ברגע שאתה צריך להגיד "וכאן `total` הוא 0, כי..." — לעתים קרובות אתה שומע את הבאג בעצמך.

⚠️ כששולחים לי (או לכל אחד) שאלה

כדי לקבל עזרה מהר: (1) מה ניסית לעשות; (2) הקוד (לא צילום מסך — טקסט); (3) הודעת השגיאה המלאה, כולל ה־stack; (4) מה ציפית ומה קיבלת; (5) מה כבר ניסית. זה גם בדיוק המבנה של דיווח באג טוב בעבודה.
