1. הדרישות

  • קליטה: לקוחות שולחים אירועים ב־batches (עד 500), מזוהים ב־API key. בשיא — אלפי אירועים בשנייה. הקליטה חייבת להיות מהירה וזמינה גם כשהמסד איטי.
  • נכונות: לקוחות שולחים שוב אחרי timeout (retry) — אירוע עם אותו eventId נספר פעם אחת. ושום אירוע שקיבל 202 לא הולך לאיבוד.
  • אנליטיקה: אירועים ומשתמשים פעילים לכל יום (שעון ישראל), ומשפכי המרה ("מכל מי שצפה, כמה הוסיפו לעגלה, וכמה קנו").
  • הפרדה: לקוח רואה רק את הנתונים שלו — גם דרך ה־cache.

key: acme:u42. tenantId בא מה־API key — לעולם לא מגוף הבקשה.

הסכמה ב־MySQL

השמות והטיפוסים — חוזה (הבודקים של שלב 3 כותבים ישירות לטבלאות). אינדקסים ואילוצים נוספים — שלך.

```sql CREATE TABLE events ( id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY, tenant_id VARCHAR(40) NOT NULL, event_id CHAR(36) NOT NULL, name VARCHAR(40) NOT NULL, user_id VARCHAR(64) NOT NULL, ts DATETIME(3) NOT NULL, -- UTC day DATE NOT NULL, -- היום בשעון ישראל props JSON NULL, received_at DATETIME(3) NOT NULL, UNIQUE KEY (tenant_id, event_id) ); CREATE TABLE daily_counts (tenant_id VARCHAR(40), day DATE, name VARCHAR(40), events INT UNSIGNED NOT NULL, PRIMARY KEY (tenant_id, day, name)); CREATE TABLE user_days (tenant_id VARCHAR(40), day DATE, user_id VARCHAR(64), PRIMARY KEY (tenant_id, day, user_id)); ```
