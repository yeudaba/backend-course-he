🎯 בשלב הזה
  • שירות HTTP קטן ומהיר: אימות לפי API key, ולידציה לכל אירוע, ו־Kafka.
  • 202 — ומתי בדיוק מותר להחזיר אותו.
  • batch שחלקו תקין: מקבלים את התקינים, ומדווחים על השאר.

1. הדרישות

  • POST /v1/events, header x-api-key ← tenant (מילון apiKeys). בלי key או key לא מוכר: 401 INVALID_API_KEY.
  • גוף: { events: [...] }. לא JSON ← 400 INVALID_JSON; מערך ריק או חסר ← 400 INVALID_BATCH; יותר מ־maxBatch ← 400 BATCH_TOO_LARGE; גוף מעל 1MB ← 413 — בלי לקרוא את כולו לזיכרון.
  • לכל אירוע: eventId (UUID), name ([a-z][a-z0-9_]{0,39}), userId (1–64), ts (ISO, לא יותר מ־5 דקות בעתיד, לא ישן מ־7 ימים), props (אובייקט, עד 2KB ב־JSON, לא חובה). אירוע לא תקין — נכנס ל־rejected עם index ו־reason; השאר — ממשיכים.
  • התקינים ← send אחד ל־Kafka (לא אחד לכל אירוע), key tenant:userId, ערך לפי החוזה. ורק אחרי שה־send הצליח — 202 { accepted, rejected }.
  • Kafka לא זמין ← 503. GET /health ← 200 (בלי key).

2. החלטות

  • למה 202 ולא 201? 202 = "התקבל לעיבוד". האירוע עוד לא במסד, ואולי לא יהיה שם עוד שנייה — וזה בסדר, כל עוד הוא ב־Kafka.
  • למה לחכות ל־send? כי 202 הוא הבטחה. החזרת 202 ואז Kafka נפל — אירוע "שהתקבל" אבד, והלקוח לא ישלח אותו שוב. ה־producer — idempotent (יחידה 26.5).
  • ו־503 בכישלון: הלקוח ישלח שוב את כל ה־batch. חלק כבר אולי הגיע ל־Kafka? בגלל זה eventId — שלב 2 יזרוק כפילויות.
  • זמן מהשרת: receivedAt הוא שלך; ts של הלקוח — אולי שעון לא מכוון, לכן גבולות. ו־now מוזרק — לבדיקות.

אין כאן framework: http.createServer מספיק לשני נתיבים, וכל מילישנייה בשירות קליטה נחשבת. (Express או Fastify — גם בסדר, אם הבודק עובר.)
