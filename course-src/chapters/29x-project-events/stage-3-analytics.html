🎯 בשלב הזה
  • ייצוא מצטבר מ־MySQL ל־lake של Parquet.
  • API שאילתות: סטטיסטיקה יומית מ־MySQL, משפכים מ־DuckDB.
  • הפרדה בין לקוחות — גם ב־cache.

1. הייצוא

  • exportToLake({ pool, conn, lakeDir, pageSize }): כל האירועים עם id גדול מה־watermark (ב־lakeDir/_state.json), בעמודים, לקובץ חדש part-00001.parquet, part-00002…. בלי חדשים — בלי קובץ ({ exported: 0, file: null }).
  • עמודות ב־Parquet (לפחות): tenant_id, event_id, name, user_id, ts (UTC) , day. ה־watermark נכתב רק אחרי שהקובץ קיים.

כאן, בניגוד ל־E25 ביחידה 28.5, אירועים לא משתנים — אז id עולה מספיק כ־watermark, ואין "גרסה אחרונה" לחשב. (עם CronJob ו־concurrencyPolicy: Forbid — שלב 4 — אין שני ייצואים במקביל.)

2. ה־API

  • GET /v1/stats/daily?from&to[&name] ← לכל יום שיש בו נתונים: events (סכום מ־daily_counts, אולי רק של name) ו־users (מ־user_days).
  • GET /v1/funnel?steps=view,add_to_cart,purchase&from&to ← לכל שלב, כמה משתמשים עשו אותו אחרי הפעם הראשונה שעשו את השלב הקודם (בטווח). 2 עד 5 שלבים. אין lake ← אפסים.
  • API key ← tenant (אחרת 401). from/to — תאריכים תקינים, טווח 0–92 ימים; שמות אירועים — כמו בקליטה; אחרת 400.
  • cache עם TTL, header X-Cache: HIT|MISS, ו־now מוזרק.

למה שתי מערכות? סטטיסטיקה יומית היא כמה שורות מטבלה מסוכמת — MySQL עונה במילי־שניות, ועדכני מיד. משפך סורק את כל האירועים של כל המשתמשים בטווח — זה בדיוק מה ש־OLAP עמודתי טוב בו, והמסד של הקליטה לא צריך לשאת את זה (יחידה 28.5). המחיר: המשפך עדכני רק עד הייצוא האחרון (עד 15 דקות). כתוב את זה ב־README — זו החלטה, לא באג.
