🎯 בשלב הזה

`service.list(query)` ו־`service.stats()`. בסוף: PR2-SCHEMA, PR2-SERVICE, PR2-API ו־PR2-LIST עוברים. (קובץ חמישי, PR2-WEB, שייך ליחידה 15.5 — הוא ייכשל עד שתגיע לשם, וזה בסדר.)

1. `list(query)`

`query` כבר עבר את `listQuerySchema` — הכול מוקלד ועם ברירות מחדל. שלושה שלבים, לפי הסדר:

  1. סינון: `status`, `priority` — שוויון. `q` — מופיע ב־title או ב־description, בלי תלות באותיות.
  2. מיון לפי `sort`:
    • `createdAt` / `dueDate` — השוואת מחרוזות (ISO ממוין נכון כמחרוזת).
    • `priority` — לפי דרגה: low < medium < high (לא לפי א״ב!).
    • משימות בלי `dueDate` — תמיד בסוף, גם במיון עולה וגם ביורד.
    • שוויון ← לפי `id` עולה. בלי זה, הסדר של משימות שוות עלול להשתנות בין בקשות — והלקוח יראה משימה פעמיים, בשני עמודים.
  3. pagination: `{ data, meta: { page, limit, total, totalPages } }` — `total` הוא אחרי הסינון.
💡 רמז: מיון לפי עדיפות ```ts const PRIORITY_RANK = { low: 1, medium: 2, high: 3 }; const diff = PRIORITY_RANK[a.priority] - PRIORITY_RANK[b.priority]; ```
💡 רמז: "בלי dueDate בסוף, בשני הכיוונים"

טפל במקרה הזה לפני שהופכים את הכיוון: אם לאחת מהן אין dueDate — מחזירים תוצאה שלא תלויה ב־desc. רק כשלשתיהן יש — משווים, ואז הופכים אם צריך.

2. `stats()`

```json { "total": 5, "byStatus": { "todo": 3, "in_progress": 1, "done": 1 }, "overdue": 1 } ```

`overdue` — משימות שאינן `done`, יש להן `dueDate`, והוא לפני היום (לפי `this.now()`). כל הסטטוסים מופיעים ב־`byStatus`, גם עם 0.

(השנייה מריצה את כל קובצי PR2 — כולם צריכים לעבור חוץ מ־PR2-WEB.)

💡 מה יקרה בפרק 19

עכשיו אתה שולף את כל המשימות לזיכרון ואז מסנן וחותך. עם 100 משימות — מצוין. עם 10 מיליון — השרת יקרוס. בפרק 19 הסינון, המיון וה־pagination יעברו למסד הנתונים (`WHERE`, `ORDER BY`, `LIMIT/OFFSET`) — ולכן אז `list` תעבור מה־service ל־repository. שים לב לזה כשתגיע לשם.
