🎯 בשיעור הזה
  • ETL ו־ELT: איך נתונים עוברים מהאפליקציה למקום שבו מנתחים אותם.
  • data lake: Parquet על S3, מחולק, append-only.
  • סנכרון מצטבר: watermark, keyset, ו"הגרסה האחרונה" בקריאה.
  • ובחזרה לאפליקציה: API אנליטי עם cache, שעומד ב־SLO.

1. מהמסד לאנליטיקה

השיעור הקודם אמר "הדוחות רצים במחסן, לא על המסד של האפליקציה". אבל הנתונים נוצרים במסד של האפליקציה. מה שמחבר — צינור נתונים:

ETL (Extract, Transform, Load) מעבד את הנתונים בדרך; ELT — הגישה הנפוצה היום — מעתיק אותם כמו שהם, ומעבד בתוך המחסן עם SQL (dbt הוא הכלי הנפוץ לזה). בשני המקרים, השאלה הקשה היא לא "איך מעתיקים", אלא "איך מעתיקים רק את מה שהשתנה, בלי לאבד ובלי לספור פעמיים".

2. סנכרון מצטבר

להעתיק את כל טבלת ההזמנות כל שעה — עובד עד שיש 50 מיליון הזמנות. במקום: watermark — "עד איפה הגעתי" — ובכל ריצה רק השורות שהשתנו אחריו:

```sql SELECT … FROM orders WHERE (updated_at, id) > ($1, $2) -- ה־watermark מהריצה הקודמת ORDER BY updated_at, id LIMIT 1000 ```

שלושה פרטים שעושים את ההבדל (E25):

  • (updated_at, id) ולא רק updated_at: UPDATE אחד על 20 שורות נותן לכולן אותו updated_at. אם העמוד נחתך באמצע, WHERE updated_at > $1 מדלג על השאר. זו בדיוק pagination עם cursor מפרק 18 — עם מפתח מורכב.
  • ה־watermark נשמר אחרי שהנתונים נכתבו — ובכתיבה אטומית (קובץ זמני ← rename). נפילה באמצע ← הריצה הבאה מעתיקה שוב את אותן שורות. כפילות — לא אובדן.
  • מחיקות לא מופיעות ב־updated_at. לכן מבטלים ולא מוחקים (soft delete, status = 'cancelled'), או משתמשים ב־CDC שקורא את ה־WAL ורואה גם מחיקות.

3. append-only, והגרסה האחרונה

הזמנה 5 בוטלה אחרי שכבר יוצאה. לא משנים את הקובץ הישן — מוסיפים קובץ חדש עם הגרסה המעודכנת. ה־lake הוא append-only: קל, בטוח, ואפשר תמיד לבנות מחדש. את "המצב הנוכחי" מחשבים בקריאה:

```sql SELECT * FROM read_parquet('lake/part-*.parquet') QUALIFY row_number() OVER (PARTITION BY id ORDER BY updated_at DESC) = 1 ```

זה הרעיון שמאחורי Delta Lake (Databricks) ו־Apache Iceberg: קבצי Parquet שלא משתנים, ושכבת metadata שאומרת מה הגרסה העדכנית — עם טרנזקציות, ו"time travel" לכל נקודה בעבר.

4. ובחזרה ל־API

הדשבורד צריך תשובות מהירות. E24 בונה API אנליטי מעל Parquet, עם שלוש החלטות ביצועים:

  1. לחשב מראש מה שאפשר: בעלייה, טוענים את הנתונים לזיכרון של DuckDB עם עמודת "יום בשעון ישראל" מחושבת — במקום לחשב אזור זמן ל־60,000 שורות בכל בקשה.
  2. cache עם TTL: דשבורד שמתרענן כל דקה אצל 50 אנשים שואל את אותן שאלות. LRU עם TTL, ו־X-Cache כדי לראות מה קורה. (ובמערכת עם כמה instances — Redis, פרק 26.)
  3. למדוד: הבודק של E24 מריץ 300 בקשות, 10 במקביל, ודורש p95 מתחת ל־50ms — SLO אמיתי, ובדיקת עומס אמיתית (שיעור 1).
💼 בעולם העבודה

"ספר על פעם ששיפרת ביצועים" — שאלה כמעט קבועה. התשובה הטובה מתחילה במדידה ("ה־p95 היה 800ms; בדיקת עומס הראתה שהוא קופץ ב־30 משתמשים"), ממשיכה בממצא ("פרופיל הראה שה־event loop חסום ב־X" / "השאילתה סרקה את כל הטבלה"), ונגמרת במספר ("p95 של 40ms, ובדיקת עומס ב־CI כדי שזה לא יחזור"). היחידה הזו נותנת לך את כל החלקים.
