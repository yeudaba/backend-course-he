לפרויקט: Render מריץ את ה־Docker image שלך (אותו Dockerfile מפרק 23), עם HTTPS ודומיין ….onrender.com מוכנים; ו־Neon — PostgreSQL מנוהל. בשניהם יש תוכנית חינמית שמספיקה לתיק עבודות. המגבלות, נכון לנובמבר 2026: ב־Render השרת החינמי "נרדם" אחרי 15 דקות בלי בקשות ומתעורר תוך כדקה, והמסד החינמי שלהם נמחק אחרי 30 יום — ולכן המסד ב־Neon, שבתוכנית החינמית שלו המסד לא פג. ו־Render מריצה "פקודה לפני deploy" (למשל migrations) רק בתוכניות בתשלום — לכן אצלנו ה־CI מריץ אותן. תנאים של תוכניות חינמיות משתנים: לפני שבונים עליהם — דף התמחור.

והעיקר: הכלים מתחלפים, העקרונות לא. image אחד שעובר בדיקות, הגדרות מה־env, migrations לפני הקוד, health check, ודרך חזרה — אותו דבר ב־Render, ב־VPS וב־Kubernetes.

2. ה־pipeline

```yaml file=.github/workflows/ci.yml deploy: if: github.event_name == 'push' && github.ref == 'refs/heads/main' needs: [test, docker] runs-on: ubuntu-latest timeout-minutes: 15 environment: production steps: - uses: actions/checkout@v5 - uses: actions/setup-node@v5 with: node-version: 24 cache: npm - run: npm ci - name: migrations on the production database run: npx prisma migrate deploy env: DATABASE_URL: ${{ secrets.DATABASE_URL }} - name: trigger deploy on Render run: curl -fsS -X POST "$RENDER_DEPLOY_HOOK_URL" > /dev/null env: RENDER_DEPLOY_HOOK_URL: ${{ secrets.RENDER_DEPLOY_HOOK_URL }} - name: smoke test of the live URL run: node scripts/smoke.mjs env: BASE_URL: ${{ vars.PRODUCTION_URL }} EXPECT_COMMIT: ${{ github.sha }} ```
  • migrations לפני הקוד. הקוד החדש מניח שהעמודה החדשה קיימת. ולכן — כל migration חייב לעבוד גם עם הקוד הישן (סעיף 3).
  • deploy hook — כתובת סודית שקריאה אליה אומרת ל־Render "בנה והרץ את ה־commit האחרון". ב־Render מכבים את ה־auto-deploy: אחרת Render היה מתחיל לבנות מיד ב־push, לפני שהבדיקות וה־migrations עברו.
  • בדיקת עשן — ה־deploy hook רק מתחיל deploy. האם הוא הצליח? scripts/smoke.mjs שואל את /version עד שה־commit הוא ה־github.sha הנוכחי, ואז את /ready.

3. /version ובדיקת העשן

Render מגדירה לשרת RENDER_GIT_COMMIT, ו־/version מחזיר אותו. כך הרצנו את smoke.mjs מול השרת מקומית — פעם כש"ה־deploy לא הגיע" (commit אחר רץ), ופעם כשכן (פלטים אמיתיים):

```term % BASE_URL=http://localhost:3925 EXPECT_COMMIT=9f0e1d2c… TIMEOUT_SECONDS=3 INTERVAL_SECONDS=1 node scripts/smoke.mjs .. #1: /version ← 200, commit 2cb197c (מחכים ל־9f0e1d2) .. #2: /version ← 200, commit 2cb197c (מחכים ל־9f0e1d2) .. #3: /version ← 200, commit 2cb197c (מחכים ל־9f0e1d2) !! ✖ הגרסה 9f0e1d2 לא עלתה תוך 3 שניות % BASE_URL=http://localhost:3925 EXPECT_COMMIT=2cb197caebad857cf5eed6c8d1ddd582085d5dca node scripts/smoke.mjs .. ✔ http://localhost:3925 — commit 2cb197c, ready (0s) ```

שים לב לריצה הראשונה: /version ענה 200 כל הזמן. בדיקת עשן שבודקת רק "השרת עונה" הייתה מכריזה על הצלחה — כשבפועל רצה הגרסה הקודמת (E22). ב־Render החינמי: build של כמה דקות, ושרת שישן מתעורר תוך כדקה — לכן ברירת המחדל של הסקריפט היא 15 דקות.

4. migrations בלי downtime: expand/contract

deploy הוא לא רגע — הוא חלון. ה־migration רץ, ובמשך דקה או שתיים הקוד הישן עדיין מקבל בקשות מול המסד החדש. ואם יהיה rollback — הקוד הישן יחזור לרוץ מול המסד החדש לזמן ארוך. לכן migration בטוח הוא כזה ששתי הגרסאות עובדות איתו:

שינוי שם / מחיקה של עמודה✖expand/contract: (1) מוסיפים חדשה, הקוד כותב לשתיהן; (2) מעבירים נתונים, הקוד קורא מהחדשה; (3) deploy נפרד — מוחקים את הישנה

ב־E16 תכתוב בודק שמזהה את המקרים האלה בקובץ migration — סוג הבדיקה שרצה ב־CI בצוותים גדולים.

5. rollback

הגרסה החדשה עלתה ומשהו לא בסדר. קודם — חוזרים לגרסה שעבדה, ורק אחר כך מתקנים בשקט. ב־Render: בדף ה־service, ברשימת ה־deploys, ליד deploy קודם — "Rollback". או ב־Git: git revert ו־push, וה־pipeline מעלה את הגרסה המתוקנת. ה־migration לא חוזר — עוד סיבה ל־expand/contract.

ופלטפורמות עושות לבד חצי מהעבודה: גרסה חדשה מקבלת תנועה רק אחרי שה־health check שלה עובר (ב־Render: Health Check Path ← /ready). גרסה שלא עולה בכלל — לא מחליפה את הקודמת. זה blue/green (E25): החדשה עולה ליד הישנה, נבדקת, ורק אז מקבלת תנועה.
