🎯 בשיעור הזה
  • למה console.log("משהו נכשל") לא מספיק בשרת אמיתי.
  • לוגים מובנים: שורת JSON לכל אירוע, ורמות.
  • מה אסור לכתוב ללוג.
  • request ID — לעקוב אחרי בקשה אחת, מהלקוח ועד השורה בלוג.
  • AsyncLocalStorage — "משתנה של הבקשה", שעובר דרך await.

1. "משהו נכשל"

לקוחה כותבת לתמיכה: "ניסיתי לשמור משימה ויצאה שגיאה". בשרת רצות מאות בקשות בדקה, והלוג נראה ככה:

```text Server started error! Error: connect ECONNREFUSED 127.0.0.1:5432 user logged in error! ```

איזו מהשגיאות שלה? מתי? איזה נתיב? כמה זמן לקח? אין לדעת. לוג טוב עונה על השאלות האלה בלי לפתוח את הקוד — ובשביל זה כל שורה צריכה שדות, לא משפט.

2. לוג מובנה: שורת JSON לכל אירוע

```text {"time":"2026-11-07T15:30:24.134Z","level":"warn","msg":"request","requestId":"support-ticket-4512","userId":1,"method":"GET","path":"/tasks/999","status":404,"durationMs":6} ```

(שורה אמיתית מהפרויקט, שלב ז׳.) כל שורה היא אובייקט: אפשר לסנן status >= 500, לספור בקשות לפי path, לחשב ממוצע של durationMs, ולמצוא את כל מה שקרה למשתמש 1. כלים כמו CloudWatch, Datadog או Grafana Loki (פרק 25) קוראים JSON בלי הגדרות. ובטרמינל — grep, או jq שמבין JSON.

שלושה כללים: שורה אחת לאירוע (JSON.stringify בלי רווחים — ירידת שורה באמצע שוברת את האיסוף); אותם שמות שדות בכל המערכת (userId, לא פעם user_id ופעם uid); וזמן ב־ISO, ב־UTC.

רמהמתידוגמה
errorמשהו נשבר אצלנו, ומישהו צריך לטפל500, המסד לא זמין, חריגה לא צפויה
warnלא תקין, אבל צפוי — בדרך כלל אשמת הלקוח4xx, ניסיון כניסה שנכשל, 429
infoאירועים רגילים שרוצים לספור ולמצואבקשה שהצליחה, השרת עלה
debugפרטים לחיפוש באג — כבוי בפרודקשןSQL, ערכי ביניים, healthcheck מוצלח

הרמה נקבעת ב־LOG_LEVEL: בפרודקשן info, וכשמחפשים באג — debug לכמה דקות. (ההשוואה — לפי מספר, לא לפי מחרוזת: "error" < "info" הוא true ב־JavaScript, ו־logger שמשווה מחרוזות זורק בדיוק את השגיאות. E20.)

3. מה אסור לכתוב ללוג

לוגים נשמרים חודשים, מגובים, נשלחים לשירות חיצוני, וכל המפתחים (ולפעמים התמיכה) קוראים אותם. ערך שנכתב ללוג — דלף. לכן אף פעם: סיסמאות, טוקנים (access, refresh, איפוס סיסמה), header של Authorization, cookies, מספרי כרטיס אשראי. ובזהירות: מידע אישי (אימייל, טלפון, כתובת) — userId מספיק כדי למצוא.

שתי הגנות: (1) לא לכתוב req.body או אובייקט שלם "בשביל הדיבוג"; (2) redact ב־logger עצמו — רשת ביטחון שמחליפה כל שדה בשם password/token/... ב־"[REDACTED]", בכל עומק (E07). ועוד מקום שבו סודות מסתתרים: ה־query string. /reset-password?token=… — לכן ב־path כותבים בלי query.

4. request ID

השרת קובע מזהה לכל בקשה: אם הלקוח (או שירות אחר במערכת) שלח X-Request-Id תקין — משתמשים בו; אחרת randomUUID(). המזהה חוזר ב־header של התשובה, וה־frontend יכול להציג אותו בהודעת שגיאה ("קוד לתמיכה: …"). מהפרויקט (פלט אמיתי, מקוצר):

```term % curl -si localhost:3000/tasks/999 -H "Authorization: Bearer $TOKEN" -H "X-Request-Id: support-ticket-4512" .. HTTP/1.1 404 Not Found .. X-Request-Id: support-ticket-4512 .. {"error":{"code":"TASK_NOT_FOUND","message":"משימה 999 לא נמצאה"}} ```

"תקין" — חשוב: המזהה נכתב לכל שורת לוג, אז לא מקבלים מבחוץ מחרוזת באורך מגה־בייט או עם מרכאות וסוגריים. /^[A-Za-z0-9._-]{1,64}$/, ואם לא — מזהה חדש (E08). והשורה עצמה נכתבת ב־res.on("finish") — כשכבר ידועים ה־status והמשך (E09).

5. AsyncLocalStorage: "המשתנה של הבקשה"

ה־middleware יודע את ה־requestId. אבל שורת לוג מתוך ה־repository — שלא מקבל req — איך תדע? להעביר requestId כפרמטר לכל פונקציה? ומשתנה גלובלי לא עובד, כי Node מטפל בהרבה בקשות במקביל: בזמן ש־א׳ מחכה למסד, ב׳ רצה.

```ts run import { AsyncLocalStorage } from "node:async_hooks"; import { setTimeout as sleep } from "node:timers/promises"; const als = new AsyncLocalStorage<{ requestId: string }>(); let current = ""; // הגרסה הנאיבית: משתנה גלובלי async function handle(id: string, ms: number) { current = id; await als.run({ requestId: id }, async () => { await sleep(ms); // "שאילתה למסד" console.log(`expected=${id} global=${current} als=${als.getStore()?.requestId}`); }); } await Promise.all([handle("r-1", 20), handle("r-2", 10)]); ``` ```out expected=r-2 global=r-2 als=r-2 expected=r-1 global=r-2 als=r-1 ```

הגלובלי "נדרס" על ידי הבקשה השנייה, ו־r-1 כותבת ללוג את המזהה של r-2. AsyncLocalStorage (מובנה ב־Node) שומר ערך לכל "שרשרת" אסינכרונית: מה שהתחיל בתוך als.run(store, fn) — כל await, setTimeout ו־Promise שנוצרו ממנו — רואה את אותו store. ה־middleware עוטף את next() ב־run, וה־logger קורא getStore(). כך כל שורה, מכל מקום בקוד, כוללת requestId ו־userId (E10).

6. לאן הלוגים הולכים

לא לקובץ. אפליקציה כותבת ל־stdout, שורה אחרי שורה — וזהו. Docker אוסף (docker compose logs api), ופלטפורמת הענן (פרק 25) שולחת לכלי חיפוש. ככה האפליקציה לא מתעסקת בסיבוב קבצים, בדיסק מלא ובהרשאות. (זה אחד מעקרונות The Twelve-Factor App — "logs as event streams".)

💡 ספריות

בעבודה כמעט תמיד יש ספרייה: pino (מהירה מאוד, JSON כברירת מחדל, עם child ו־redact) או winston. ב־Nest — nestjs-pino. הן עושות את מה שכתבת בתרגילים, ועוד: כתיבה אסינכרונית, פורמט קריא בפיתוח (pino-pretty). בפרויקט כתבנו logger קטן בעצמנו כדי לראות את כל החלקים — ובראיון "מה pino עושה בשבילך" היא שאלה שתדע לענות עליה.
