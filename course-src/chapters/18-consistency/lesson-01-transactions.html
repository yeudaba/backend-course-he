🎯 בשיעור הזה
  • `BEGIN` / `COMMIT` / `ROLLBACK`.
  • מה קורה כשפקודה נכשלת באמצע.
  • transactions מ־Node עם `pg` — הדפוס הנכון.

1. הבעיה

העברה של 300 ש״ח מ־Yossi ל־Noa היא שתי פקודות: להוסיף ל־Noa, להוריד מ־Yossi. מה אם השרת נופל בין השתיים? או שהשנייה נכשלת? הכסף "נוצר יש מאין". transaction אומר למסד: כל הפקודות האלה — יחד, או אף אחת.

```sql run db=18-consistency/files/bank.sql stderr continue BEGIN; UPDATE accounts SET balance = balance + 300 WHERE id = 3; -- Noa מקבלת UPDATE accounts SET balance = balance - 300 WHERE id = 2; -- ל־Yossi יש רק 250! COMMIT; SELECT id, owner, balance FROM accounts ORDER BY id; ``` ```out BEGIN UPDATE 1 ERROR: new row for relation "accounts" violates check constraint "accounts_balance_check" DETAIL: Failing row contains (2, Yossi, -50.00). ROLLBACK id | owner | balance ----+-------+--------- 1 | Dana | 1000.00 2 | Yossi | 250.00 3 | Noa | 0.00 4 | Avi | 5000.00 (4 rows) ```

קרא את הפלט לאט: העדכון הראשון הצליח (`UPDATE 1`), השני הפר את ה־CHECK — ומהרגע הזה ה־transaction "מת". ה־`COMMIT` בסוף הפך ל־`ROLLBACK`, וגם העדכון הראשון בוטל: Noa עדיין עם 0. בלי `BEGIN`, הייתה ל־Noa עכשיו 300 ש״ח שלא באו מאף אחד.

2. הפקודות

פקודהמה עושה
`BEGIN`פותח transaction. מעכשיו שום שינוי לא "סופי"
`COMMIT`הכול נשמר — ונראה לכל שאר החיבורים בבת אחת
`ROLLBACK`הכול מבוטל, כאילו לא קרה

בלי `BEGIN`, כל פקודה היא transaction קטן משלה (autocommit). אחרי שגיאה בתוך transaction, כל פקודה נוספת נדחית עם `current transaction is aborted, commands ignored until end of transaction block` — עד ROLLBACK.

💡 ACID במשפט לכל אות

Atomicity — הכול או כלום. Consistency — אחרי ה־commit כל האילוצים מתקיימים. Isolation — transactions במקביל לא "רואים" חצאי עבודה אחד של השני (שיעור 2). Durability — אחרי ש־COMMIT חזר, הנתונים שרדו גם אם החשמל ייפול עכשיו. שאלת ראיון קלאסית.

וגם בטעויות שלך: לפני `UPDATE`/`DELETE` מסוכן ב־psql, `BEGIN;` — מריצים, בודקים עם SELECT, ואם משהו לא נראה טוב — `ROLLBACK;`.

3. מ־Node: הספרייה pg

בפרק 19 Prisma תעשה את זה בשבילך, אבל כדאי לראות מה קורה מתחת. `pg` היא הספרייה הבסיסית של PostgreSQL ל־Node (מותקנת בתיקיית הקורס):

```js file=playground/transfer.mjs import pg from "pg"; const pool = new pg.Pool({ connectionString: process.env.COURSE_DATABASE_URL }); export async function transfer(fromId, toId, amount) { const client = await pool.connect(); // חיבור אחד — כל ה־transaction עליו try { await client.query("BEGIN"); await client.query("UPDATE accounts SET balance = balance - $1 WHERE id = $2", [amount, fromId]); await client.query("UPDATE accounts SET balance = balance + $1 WHERE id = $2", [amount, toId]); await client.query("INSERT INTO transfers (from_id, to_id, amount) VALUES ($1, $2, $3)", [fromId, toId, amount]); await client.query("COMMIT"); } catch (err) { await client.query("ROLLBACK"); throw err; // מי שקרא יחליט מה להחזיר (400? 500?) } finally { client.release(); // תמיד! אחרת ה־pool מתרוקן ו־השרת נתקע } } ```
חלקלמה
`pg.Pool`מאגר חיבורים פתוחים. פתיחת חיבור למסד יקרה (עשרות ms) — ה־pool ממחזר אותם בין בקשות
`pool.connect()`"השאל" חיבור אחד. חובה ל־transaction: `pool.query()` יכול לשלוח כל פקודה בחיבור אחר, ו־BEGIN בחיבור אחד לא משפיע על חיבור אחר
`$1, $2`פרמטרים. לעולם לא `` `... WHERE id = ${id}` `` — זו SQL injection (פרק 21). pg שולח את הערכים בנפרד מהשאילתה
`finally { release() }`חיבור שלא שוחרר "דולף". אחרי 10 דליפות (ברירת המחדל של ה־pool) — כל בקשה חדשה מחכה לנצח
⚠️ SQL injection — בקצרה

`client.query("SELECT * FROM users WHERE email = '" + email + "'")` עם email שהוא `' OR '1'='1` — מחזיר את כל המשתמשים. עם `'; DROP TABLE users; --` — גרוע יותר. פרמטרים (`$1`) פותרים את זה לגמרי, כי הערך אף פעם לא הופך לחלק מהקוד של השאילתה.
