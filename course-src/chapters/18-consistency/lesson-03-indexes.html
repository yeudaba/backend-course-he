🎯 בשיעור הזה
  • מה זה index, ואיך הוא עובד (בערך).
  • `EXPLAIN`: Seq Scan מול Index Scan.
  • index על כמה עמודות, index חלקי, ומתי index לא עוזר.

1. בלי index

```sql run db=18-consistency/files/bank.sql EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF, BUFFERS OFF) SELECT * FROM big_orders WHERE customer_id = 42; ``` ```out QUERY PLAN ----------------------------------------------------- Seq Scan on big_orders (actual rows=100.00 loops=1) Filter: (customer_id = 42) Rows Removed by Filter: 199900 (3 rows) ```

`Seq Scan` — המסד עבר על כל 200,000 השורות כדי למצוא 100 ("Rows Removed by Filter: 199900"). כמו לחפש שם בספר טלפונים לא ממוין: דף אחרי דף. (`EXPLAIN ANALYZE` מריץ את השאילתה באמת ומראה מה קרה; האפשרויות בסוגריים רק מסתירות מספרים שמשתנים מהרצה להרצה.)

ב־psql אפשר למדוד זמן: `\timing on`, ואז להריץ את השאילתה. אצלך זה יהיה בסביבות כמה מילישניות — עם 200 מיליון שורות, דקות.

2. עם index

```sql run db=18-consistency/files/bank.sql CREATE INDEX big_orders_customer_id_idx ON big_orders (customer_id); EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF, BUFFERS OFF) SELECT * FROM big_orders WHERE customer_id = 42; ``` ```out CREATE INDEX QUERY PLAN ------------------------------------------------------------------------------------ Bitmap Heap Scan on big_orders (actual rows=100.00 loops=1) Recheck Cond: (customer_id = 42) Heap Blocks: exact=100 -> Bitmap Index Scan on big_orders_customer_id_idx (actual rows=100.00 loops=1) Index Cond: (customer_id = 42) Index Searches: 1 (6 rows) ```

`Bitmap Index Scan` — המסד מצא דרך ה־index את מיקומי 100 השורות ("Heap Blocks: exact=100"), וקרא רק אותן. index הוא עותק ממוין של עמודה (או כמה), עם "כתובת" של כל שורה. כמו אינדקס בסוף ספר.

3. המחיר

  • כל כתיבה מעדכנת את כל ה־indexes של הטבלה. 10 indexes ← כל INSERT עושה 11 כתיבות.
  • מקום בדיסק ובזיכרון.
  • לכן: index לשאילתות שבאמת רצות הרבה ושצריכות אותו — לא "ליתר ביטחון" על כל עמודה.
כן — שקול index עללא יעזור
עמודות ב־WHERE / JOIN של שאילתות נפוצותטבלאות קטנות (מאות שורות) — סריקה מהירה ממילא
Foreign keys (`orders.customer_id`) — PostgreSQL לא יוצר להם index אוטומטית!עמודה עם מעט ערכים שונים (`is_active`) כשרוב השורות מתאימות
עמודות ב־ORDER BY עם LIMIT ("20 האחרונות")`WHERE lower(email) = ...` כשה־index על `email` (פונקציה על העמודה)
(מפתח ראשי ו־UNIQUE — מקבלים index אוטומטית)`LIKE '%abc'` — אחוז בהתחלה, אי אפשר "לקפוץ" בעץ ממוין

4. index על כמה עמודות

```sql run db=18-consistency/files/bank.sql CREATE INDEX big_orders_status_created_idx ON big_orders (status, created_at); EXPLAIN (COSTS OFF) SELECT id, total FROM big_orders WHERE status = 'pending' AND created_at >= '2025-12-01' ORDER BY created_at LIMIT 20; ``` ```out CREATE INDEX QUERY PLAN ------------------------------------------------------------------------------------------------------------------------- Limit -> Index Scan using big_orders_status_created_idx on big_orders Index Cond: ((status = 'pending'::text) AND (created_at >= '2025-12-01 00:00:00+02'::timestamp with time zone)) (3 rows) ```

index על `(status, created_at)` ממוין קודם לפי status ובתוכו לפי תאריך — כמו ספר טלפונים לפי שם משפחה ואז שם פרטי. הוא עוזר ל־`WHERE status = ...` ול־`WHERE status = ... AND created_at ...`, אבל לא ל־`WHERE created_at ...` לבד (כמו שספר טלפונים לא עוזר למצוא את כל מי ששמו "דנה"). כלל: עמודת השוויון ראשונה, עמודת הטווח/מיון אחריה.

index חלקי ו־UNIQUE

```sql -- רק ההזמנות הפתוחות (קטן יותר, ורוב השאילתות של המחסן עליהן) CREATE INDEX big_orders_open_idx ON big_orders (created_at) WHERE status IN ('paid', 'pending'); -- אימייל ייחודי בלי תלות באותיות CREATE UNIQUE INDEX customers_email_lower_key ON customers (lower(email)); ```
💡 ומה עם הסקריפט שרץ על ייצור?

`CREATE INDEX` רגיל נועל את הטבלה לכתיבה עד שהוא מסתיים — בטבלה גדולה זה דקות שבהן אי אפשר ליצור הזמנות. בייצור: `CREATE INDEX CONCURRENTLY` (איטי יותר, לא חוסם).
