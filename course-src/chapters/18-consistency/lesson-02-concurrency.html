🎯 בשיעור הזה
  • race condition: "קרא ← חשב ← כתוב" במקביל.
  • ארבעה פתרונות: עדכון אטומי, אילוץ, `FOR UPDATE`, ניסיון חוזר.
  • נעילות, deadlock ורמות בידוד — מה שצריך לדעת.

1. הבאג

נשאר Hand Grinder אחד במלאי. קוד "נאיבי" של קנייה:

```js const { rows } = await db.query("SELECT stock FROM inventory WHERE product_id = 1"); if (rows[0].stock < 1) throw new HttpError(409, "OUT_OF_STOCK", "אזל"); await db.query("UPDATE inventory SET stock = $1 WHERE product_id = 1", [rows[0].stock - 1]); // ... יצירת הזמנה, חיוב ... ```

הבאג הזה לא יופיע בפיתוח (אתה לבד), וגם לא בבדיקות רגילות. הוא יופיע במבצע של Black Friday.

2. פתרון 1: עדכון אטומי עם תנאי

```sql run db=18-consistency/files/bank.sql UPDATE inventory SET stock = stock - 1 WHERE product_id = 1 AND stock >= 1; UPDATE inventory SET stock = stock - 1 WHERE product_id = 1 AND stock >= 1; SELECT stock FROM inventory WHERE product_id = 1; ``` ```out UPDATE 1 UPDATE 0 stock ------- 0 (1 row) ```

במקום "קרא ואז כתוב" — פקודה אחת שבודקת וכותבת. `stock - 1` מחושב במסד מהערך העדכני, ו־`AND stock >= 1` מוודא שיש. הראשון: `UPDATE 1` (נמכר). השני: `UPDATE 0` — אף שורה לא עודכנה, כלומר אזל. בקוד: `if (result.rowCount === 0) throw new HttpError(409, ...)`. גם כששתי הפקודות מגיעות באותה מילישנייה — המסד נועל את השורה לרגע העדכון, והשנייה רואה כבר את 0. זה הפתרון הפשוט והמהיר ביותר — כשמתאים, תמיד אותו.

3. פתרון 2: אילוץ כרשת ביטחון

`stock integer NOT NULL CHECK (stock >= 0)` — גם אם יש באג בקוד, המסד לא יסכים למלאי שלילי. העדכון השני ייכשל עם `violates check constraint`, וה־transaction שלו יבוטל. אילוצים הם לא "במקום" לוגיקה נכונה — הם מה שתופס את מה שהלוגיקה פספסה.

4. פתרון 3: SELECT ... FOR UPDATE

לפעמים צריך לקרוא, לחשוב בקוד (הנחות, מבצעים, בדיקות מסובכות) ורק אז לכתוב. אז נועלים את השורה בזמן הקריאה. בשני חלונות psql:

```term .. ── חלון A ────────────────────────────────────────── % BEGIN; % SELECT stock FROM inventory WHERE product_id = 2 FOR UPDATE; stock ------- 40 .. ── חלון B ────────────────────────────────────────── % BEGIN; % SELECT stock FROM inventory WHERE product_id = 2 FOR UPDATE; .. (B נתקע ומחכה — השורה נעולה על ידי A) .. ── חלון A ────────────────────────────────────────── % UPDATE inventory SET stock = stock - 5 WHERE product_id = 2; % COMMIT; .. ── חלון B ────────────────────────────────────────── stock ------- 35 .. (B ממשיך — ורואה את הערך אחרי השינוי של A) % COMMIT; ```

`FOR UPDATE` אומר: "אני עומד לשנות את השורות האלה — אף אחד אחר לא נוגע בהן עד שאסיים". הנעילה משתחררת ב־COMMIT או ROLLBACK. המחיר: בקשות מחכות בתור. לכן — transactions קצרים, ובלי לחכות בתוכם לדברים חיצוניים (קריאה ל־API של תשלומים בתוך transaction פתוח = כל הקונים של אותו מוצר מחכים לספק התשלומים).

💡 גם UPDATE נועל

כל `UPDATE` נועל את השורות שהוא משנה עד סוף ה־transaction. אם A עשה `UPDATE accounts ... WHERE id = 1` בתוך BEGIN, ו־B מנסה לעדכן את אותה שורה — B מחכה עד ש־A יסיים, ואז מחשב מהערך החדש. בגלל זה פתרון 1 עובד.

5. Deadlock

```term .. ── A ── העברה מ־Dana (1) ל־Avi (4) ── B ── העברה מ־Avi (4) ל־Dana (1) .. A: UPDATE ... WHERE id = 1 (נועל את 1) .. B: UPDATE ... WHERE id = 4 (נועל את 4) .. A: UPDATE ... WHERE id = 4 (מחכה ל־B) .. B: UPDATE ... WHERE id = 1 (מחכה ל־A) !! ERROR: deadlock detected ```

כל אחד מחכה לשני — לנצח. PostgreSQL מזהה את זה תוך שנייה, מבטל אחד מהם (קוד שגיאה `40P01`), והשני ממשיך. מניעה: לנעול תמיד באותו סדר — למשל קודם את ה־id הקטן. בהעברה: `ORDER BY id` ב־`SELECT ... FOR UPDATE` של שני החשבונות.

6. רמות בידוד וניסיון חוזר

רמהמה רואיםמתי
Read Committed (ברירת מחדל)כל פקודה רואה את מה ש־commit עד אליהכמעט תמיד — עם עדכונים אטומיים ו־FOR UPDATE
Repeatable Readכל ה־transaction רואה "צילום" מהתחלתודוחות שצריכים תמונה עקבית
Serializableכאילו כל ה־transactions רצו אחד אחרי השניחוקים מסובכים בין שורות שונות

ברמות הגבוהות, כשיש התנגשות המסד לא מחכה — הוא זורק: `could not serialize access due to concurrent update` (קוד `40001`). הקוד שלך צריך לתפוס את הקוד הזה ולנסות שוב את כל ה־transaction מההתחלה (תרגיל E19). שגיאות `40001` ו־`40P01` הן "זמניות" — כמו 503 בפרק 14.
