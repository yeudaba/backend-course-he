🎯 בשיעור הזה
  • hash, הצפנה ו־encoding — שלושה דברים שונים.
  • למה hash מהיר (SHA-256) לא מתאים לסיסמאות, ומה bcrypt עושה אחרת.
  • הרשמה וכניסה: הקוד, והפרטים הקטנים שמונעים דליפת מידע.

1. מה קורה כשמסד נתונים דולף

זה קורה לחברות גדולות כל הזמן: גיבוי שנשכח בשרת פתוח, עובד שהמחשב שלו נפרץ, SQL injection. התוקף מקבל עותק של טבלת users. השאלה היא לא אם, אלא מה הוא ימצא שם. ואנשים משתמשים באותה סיסמה בהרבה אתרים — כלומר דליפה אצלך פותחת להם גם את המייל ואת הבנק.

לכן הכלל הראשון: השרת אף פעם לא שומר סיסמה. הוא שומר משהו שמאפשר לבדוק אם סיסמה נכונה — ולא לשחזר אותה.

אפשר לחזור למקור?דוגמהלסיסמאות?
Encodingכן, לכל אחד, בלי מפתחBase64, URL encoding❌ זו לא הגנה בכלל
הצפנה (encryption)כן, למי שיש לו את המפתחAES❌ המפתח יושב באותו שרת — ידלוף יחד
Hashלא — חד־כיווניSHA-256, bcrypt✔ אבל רק hash איטי עם salt

2. למה לא SHA-256?

SHA-256 נבנה להיות מהיר — זו התכונה הנכונה לבדיקת קבצים, והגרועה ביותר לסיסמאות. תוקף עם טבלה שדלפה לא "פורץ" את ה־hash; הוא פשוט מנחש: לוקח מיליוני סיסמאות נפוצות, מחשב לכל אחת hash ומשווה. כרטיס מסך מחשב מיליארדי SHA-256 בשנייה. ובלי salt — שתי סיסמאות זהות נותנות אותו hash, אז מספיק לחשב פעם אחת לכל המשתמשים (ויש טבלאות מוכנות מראש).

bcrypt פותר את שתי הבעיות:

  • salt — 16 בתים אקראיים, חדשים לכל hash. אותה סיסמה ← hash שונה בכל פעם, וכל ניחוש צריך להיות מחושב בנפרד לכל משתמש.
  • cost — כמה איטי לחשב. כל +1 מכפיל את הזמן. בשרת זה עניין של עשירית שנייה בכניסה; לתוקף זה הופך מיליארד ניחושים בשנייה לכמה אלפים.

3. bcrypt בקוד

```ts run import bcrypt from "bcryptjs"; const a = await bcrypt.hash("correct horse battery", 10); const b = await bcrypt.hash("correct horse battery", 10); console.log(a.length, a.slice(0, 7)); console.log("אותה סיסמה, אותו hash?", a === b); console.log("נכונה:", await bcrypt.compare("correct horse battery", a)); console.log("שגויה:", await bcrypt.compare("correct horse batter", a)); console.log("cost מתוך המחרוזת:", bcrypt.getRounds(a)); ``` ```out 60 $2b$10$ אותה סיסמה, אותו hash? false נכונה: true שגויה: false cost מתוך המחרוזת: 10 ```

שתי הקריאות ל־hash נותנות מחרוזות שונות (salt שונה), ובכל זאת compare מצליח עם שתיהן: הוא קורא את ה־salt ואת ה־cost מתוך המחרוזת, מחשב שוב, ומשווה. לכן גם אי אפשר "לחפש משתמש לפי hash" — בודקים תמיד compare(password, user.passwordHash).

💡 איזה cost?

OWASP ממליץ על 10 לפחות. בפרויקט שלנו ברירת המחדל היא 12, מתוך BCRYPT_ROUNDS ב־.env — ובבדיקות 4, כדי שירוצו מהר. מדוד אצלך: console.time("h"); await bcrypt.hash("x", 12); console.timeEnd("h"). המטרה: מספיק איטי לתוקף, מספיק מהיר למשתמש. (חלופה מודרנית: Argon2id — מה ש־OWASP ממליץ עליו ראשון. bcrypt עדיין בחירה טובה ונפוצה מאוד.)

4. 72 בתים

ל־bcrypt יש מגבלה שכדאי להכיר: הוא משתמש רק ב־72 הבתים הראשונים של הסיסמה. כל מה שאחריהם — נחתך בשקט:

```ts run import bcrypt from "bcryptjs"; const hash = await bcrypt.hash("a".repeat(72) + "-my-secret-ending", 4); console.log(await bcrypt.compare("a".repeat(72) + "-something-else", hash)); console.log(Buffer.byteLength("שלום", "utf8")); ``` ```out true 8 ```

סיסמה אחרת לגמרי — ו־compare מחזיר true. ושים לב לשורה השנייה: אות עברית היא 2 בתים ב־UTF-8. כלומר 72 בתים זה בערך 36 אותיות בעברית. לכן בהרשמה בודקים את הבתים, לא את התווים, ומסרבים לסיסמה ארוכה מדי — עדיף הודעה ברורה מאשר חיתוך שקט.

5. הרשמה

```ts file=src/auth/auth.service.ts async register({ email, password }: RegisterInput) { const user = await this.users.insert({ email, // כבר trim + toLowerCase מה־schema passwordHash: await this.passwords.hash(password), role: "user", // תמיד. לא מגוף הבקשה (שיעור 4) createdAt: this.clock.now().toISOString(), }); if (!user) throw new HttpError(409, "EMAIL_TAKEN", "האימייל כבר רשום"); return toPublicUser(user); // בלי passwordHash } ```
  • אימייל מנורמל: Dana@Example.com ו־dana@example.com הם אותו אדם. בלי זה — שני חשבונות, ובלבול בכניסה.
  • unique במסד, לא רק "בדקתי קודם": שתי הרשמות באותה מילישנייה יעברו שתיהן את הבדיקה (פרק 18). ה־repository תופס את השגיאה P2002 של Prisma ומחזיר undefined.
  • toPublicUser — פונקציה אחת שמסירה את passwordHash. כל תשובה שמחזירה משתמש עוברת דרכה. גם hash לא יוצא החוצה: הוא מאפשר ניחושים offline.

6. כניסה — בלי לגלות מי רשום

```ts file=src/auth/auth.service.ts async login({ email, password }: LoginInput) { const user = await this.users.findByEmail(email); if (!user) { await this.passwords.verifyAgainstDummy(password); // אותו זמן בערך throw invalidCredentials(); // אותה הודעה } if (!(await this.passwords.verify(password, user.passwordHash))) throw invalidCredentials(); return this.issueTokens(user); } ```

"אימייל לא רשום" ו"סיסמה שגויה" מחזירים אותה תשובה: 401 INVALID_CREDENTIALS, "אימייל או סיסמה שגויים". אחרת תוקף בודק רשימה של מיליון אימיילים ולומד מי הלקוחות שלך (user enumeration) — ואז מתמקד בהם. וגם הזמן מסגיר: bcrypt לוקח זמן, אז תשובה מהירה פירושה "לא בדקנו סיסמה — אין משתמש כזה". לכן גם כשאין משתמש, מריצים compare מול hash "דמה".

⚠️ אף פעם בלוג

לא סיסמה, לא hash, לא טוקן. גם לא "רק לדיבאג". לוגים נשמרים, נשלחים לשירותים חיצוניים, ונקראים ע"י אנשים שאין להם גישה למסד. אם אתה רושם את גוף הבקשה (פרק 24) — הסתר שדות כמו password.

7. מדיניות סיסמאות

ההמלצות העדכניות (NIST, OWASP) הפוכות ממה שרוב האתרים עדיין עושים: אורך חשוב יותר מ"אות גדולה, מספר וסימן". מינימום 8 (עדיף 12+ למערכות רגישות), לאפשר סיסמאות ארוכות ורווחים, לא לחייב החלפה כל 90 יום — ולחסום סיסמאות נפוצות או כאלה שכבר דלפו. בפרויקט: 8 תווים לפחות ו־72 בתים לכל היותר. ובכניסה לא בודקים מדיניות בכלל — רק שנשלחה סיסמה.
