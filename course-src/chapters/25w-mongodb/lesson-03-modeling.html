1. מתכננים לפי השאילתות

ב־PostgreSQL תכננת לפי הישויות: טבלה לכל דבר, בלי כפילויות (נרמול, פרק 17), ו־JOIN בזמן הקריאה. ב־Mongo השאלה הפוכה: מה המסך/ה־endpoint צריך, ואיך הוא מקבל את זה בקריאה אחת? בחנות הקפה:

  • דף הזמנה — ההזמנה וכל הפריטים שלה, תמיד ביחד.
  • "ההזמנות שלי" — רשימה של הזמנות של לקוח, מהחדשה.
  • דף מוצר — המוצר, המאפיינים שלו ותקציר הדירוגים.
  • ניהול — מכירות לפי מוצר (aggregation, שיעור 4).

3. שכפול מכוון

בכל פריט בהזמנה שמרנו name ו־price — עותק ממסמך המוצר. ב־Postgres זה "לא מנורמל". כאן זה נכון, משתי סיבות:

  • זו האמת ההיסטורית. המחיר במוצר יעלה בחודש הבא; ההזמנה מינואר צריכה להראות כמה שילמו. (גם ב־Postgres שמרנו unit_price ב־order_items מאותה סיבה.)
  • הקריאה זולה. דף ההזמנה לא צריך $lookup למוצרים כדי להציג שמות.

המחיר של שכפול: אם השדה המשוכפל צריך להתעדכן (שם הלקוח מופיע ב־1,000 פוסטים שלו, והוא שינה שם) — צריך לעדכן 1,000 מסמכים. לכן משכפלים רק מה שלא משתנה, או שמותר לו להיות היסטורי.

4. מערכים שגדלים לנצח

מסמך מוגבל ל־16MB. זה המון — אבל מערך שגדל בלי הגבלה יגיע לשם, ולפני כן כל קריאה וכתיבה של המסמך תהיה איטית. דוגמה: לשמור את כל ההזמנות בתוך מסמך הלקוח. ללקוחה פעילה יש 3,000 הזמנות, ודף הפרופיל שלה טוען את כולן. הכלל: מערך מוטמע — רק כשיש לו גבול טבעי. אחרת: collection נפרד עם הפניה, ואינדקס ({ customerId: 1, createdAt: -1 }, שיעור 4).

ומה עם הדירוגים במוצר? בנתוני הדוגמה הם מוטמעים, כי יש מעט. בחנות אמיתית עם אלפי דירוגים: collection reviews נפרד, ובמוצר רק תקציר — ratingCount ו־ratingSum, שמתעדכנים באותה פקודה שמוסיפה דירוג (E16). זה דפוס נפוץ: "computed pattern".

5. $lookup — כשבכל זאת צריך join

הצגת "ההזמנה ושם הלקוח" בממשק ניהול: $lookup הוא LEFT JOIN, בתוך aggregation (שיעור 4). הוא עובד, אבל אם כמעט כל שאילתה צריכה $lookup — סימן שהמבנה לא מתאים לדפוסי הגישה, או ש־Postgres היה בחירה טובה יותר לחלק הזה.

6. schema validation בשרת

"בלי schema" לא חייב להיות "בלי כללים". $jsonSchema על collection — והשרת דוחה כל insert או update שלא עומד בהם (קוד שגיאה 121):

```ts run import { MongoClient, MongoServerError } from "mongodb"; const client = new MongoClient(process.env.MONGO_URL ?? "mongodb://localhost:27017/?directConnection=true"); const db = client.db("lesson3"); await db.createCollection("products", { validator: { $jsonSchema: { bsonType: "object", required: ["name", "price"], properties: { name: { bsonType: "string", minLength: 1 }, price: { bsonType: ["int", "double"], minimum: 0 }, }, }, }, }); const products = db.collection("products"); await products.insertOne({ name: "Ceramic Mug", price: 35 }); for (const bad of [{ name: "Mug" }, { name: "Mug", price: "35" }, { name: "Mug", price: -1 }]) { try { await products.insertOne({ ...bad }); // עותק: insertOne מוסיף _id לאובייקט שקיבל } catch (err) { if (err instanceof MongoServerError) console.log(err.code, JSON.stringify(bad)); } } console.log(await products.countDocuments()); await db.dropDatabase(); await client.close(); ``` ```out 121 {"name":"Mug"} 121 {"name":"Mug","price":"35"} 121 {"name":"Mug","price":-1} 1 ```

זה רשת ביטחון ברמת המסד — כמו NOT NULL ו־CHECK ב־Postgres. הולידציה הראשית נשארת בקוד (Zod), כדי להחזיר ללקוח 400 עם הודעה ברורה; ה־validator תופס את מה שעבר בטעות (סקריפט migration, שירות אחר שכותב לאותו collection). E18 בונה אחד מלא, כולל enum ו־additionalProperties: false.
