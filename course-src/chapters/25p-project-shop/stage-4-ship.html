1. בדיקות

  • unit (npm test, בלי מסד): מכונת המצבים, Luhn, חישוב סכומים, הגדרות.
  • e2e (npm run test:e2e, מול PostgreSQL אמיתי — schema חדש לכל ריצה, כמו בפרק 22): זרימה מלאה, מרוץ (Promise.all של 10 לקוחות על 3 יחידות), ושה־CHECK באמת קיים.

מבחן לבדיקת המרוץ שלך: שבור את הקוד בכוונה — החזר את "SELECT ואז UPDATE" — וודא שהבדיקה נכשלת. בדיקה שעוברת גם על קוד שבור לא בודקת כלום (פרק 22).

2. Docker, CI ופריסה

הכול כבר עשית בפרויקט 2 — כאן מרכיבים לבד:

  • Dockerfile multi-stage, לא root (פרק 23). compose.yaml: db (postgres:18-alpine, healthcheck, volume ב־/var/lib/postgresql), migrate שמריץ migrations ו־seed ונגמר, api שמחכה לו, ו־web.
  • CI (פרק 25): שירות postgres, npm ci, generate, typecheck, unit, migrate deploy, e2e, build — ו־deploy ל־Render אחרי ש־main ירוק.
  • פריסה: Neon + Render, כמו בפרק 25. ב־Render הוסף ADMIN_EMAIL ו־ADMIN_PASSWORD (סיסמה חזקה, חדשה).

3. דף ההדגמה

HTML ו־JavaScript פשוטים (יחידה 15.5): קטלוג עם חיפוש, כניסה, עגלה, "הזמן" עם Idempotency-Key (מפתח אחד ללחיצה, שנשמר עד שהיא מצליחה), תשלום, וההזמנות שלי עם ביטול. מה שמראיין יכול ללחוץ עליו תוך 30 שניות — שווה יותר מכל Swagger. הצילום בתחילת הפרויקט הוא הדף של הפתרון לדוגמה.

4. README

ה־README הוא הדבר הראשון (ולפעמים היחיד) שמראיין רואה. מה חייב להיות בו:

  1. משפט אחד: מה המערכת עושה.
  2. קישור חי, קישור ל־Swagger (/docs), תג CI.
  3. הרצה מקומית — עד 3 פקודות (cp .env.example .env, docker compose up --build, open …).
  4. תרשים ארכיטקטורה ותרשים מסד נתונים — Mermaid (GitHub מצייר אותו) או תמונה.
  5. "החלטות טכניות" — החלק שמראיינים קוראים. לא "השתמשתי ב־NestJS", אלא "למה": למה עדכון מותנה ולא בדיקה בקוד (ומה ראית כשניסית את השני), למה המחיר נשמר בהזמנה, למה אגורות, למה 404 ולא 403. כל החלטה — שורה או שתיים.
  6. "מה הייתי משפר עם עוד זמן" — מראה שאתה יודע מה חסר: ביטול אוטומטי של הזמנות שלא שולמו, cache, תור למיילים, refresh tokens.
