1. cache-aside

הדפוס הנפוץ ביותר: הקוד שלך מנהל את ה־cache. Redis לא יודע כלום על המסד.

```ts async function getOrSet(key: string, ttlSeconds: number, load: () => Promise): Promise { const hit = await redis.get(key); if (hit !== null) return JSON.parse(hit) as T; // HIT const value = await load(); // MISS — הולכים למסד await redis.set(key, JSON.stringify(value), "EX", ttlSeconds); return value; } const page = await getOrSet(`products:${JSON.stringify(query)}`, 60, () => prisma.product.findMany(…)); ```

שלוש החלטות בכל cache:

  • המפתח — חייב לכלול כל מה שמשפיע על התשובה. ?q=latte&page=2 ו־?q=latte&page=1 — שני מפתחות. שכחת את page? עמוד 2 מחזיר את עמוד 1 (E20). וסדר: {page, q} ו־{q, page} הם אותה בקשה — בפרויקט בונים את המפתח מה־DTO אחרי ולידציה, בסדר קבוע.
  • ה־TTL — כמה זמן מותר לתשובה להיות ישנה. גם אם יש ביטול מסודר, תמיד שמים TTL: הוא רשת הביטחון לכל מקום ששכחת לבטל.
  • hit !== null, לא if (hit) — 0, "" ו־[] הם תשובות. ו־JSON.stringify: ioredis שומר אובייקט כ־"[object Object]".

2. כמה זה שווה? מדידה

הרצתי את חנות הקפה (שלב 5) ב־docker compose עם 20,000 מוצרים, וחיפוש GET /products?q=… — ILIKE שלא יכול להשתמש באינדקס, כך שהמסד סורק. כל בקשה פעמיים: הראשונה MISS, השנייה HIT (זמן כולל מ־curl):

עמודMISS (מסד)HIT (Redis)
2177.4ms2.6ms
2293.2ms2.8ms
2390.6ms2.7ms
2478.7ms2.3ms
2568.2ms2.6ms

פי 30. אבל שים לב מה המספרים לא אומרים: עם 30 מוצרים (כמו ב־seed) המסד עונה ב־2–3ms בעצמו, ו־cache רק מוסיף מורכבות. ולפני cache — אינדקס נכון (פרק 18) הוא בדרך כלל התיקון הנכון. cache שווה כשהשאילתה יקרה וגם חוזרת הרבה וגם מותר לתשובה להיות קצת ישנה.

בפרויקט, התשובה מסמנת את עצמה — header שמאוד עוזר בדיבאג:

```term % curl -si "localhost:3000/products?q=V60" | grep -i "^x-cache" .. X-Cache: MISS % curl -si "localhost:3000/products?q=V60" | grep -i "^x-cache" .. X-Cache: HIT ```

3. ביטול: למחוק, או להעלות גרסה

מנהל שינה מחיר. מה עם ה־cache? הדרך הפשוטה: DEL למפתח. אבל לרשימת המוצרים יש מפתח לכל צירוף של q, sort, page, limit — אלפים. למצוא אותם צריך KEYS (אסור) או SCAN (איטי). הפתרון בפרויקט: גרסה לקבוצה.

```ts file=src/redis/cache.service.ts const version = (await this.redis.get(`v:${group}`)) ?? "0"; const fullKey = `cache:${group}:${version}:${key}`; // cache:products:3:{"q":"V60",…} … async invalidate(group: string) { await this.redis?.incr(`v:${group}`); // מעכשיו כולם קוראים מ־:4: } ```

פקודה אחת, אטומית, בלי לחפש כלום. המפתחות של גרסה 3 לא נמחקים — אף אחד לא קורא אותם, וה־TTL מנקה. המחיר: עוד GET בכל בקשה. מתי מבטלים? בכל שינוי שמשפיע על הרשימה — יצירה, עדכון, מחיקה, וגם הזמנה: המלאי (stock) מופיע ברשימה.

ובכל זאת, בין ה־UPDATE במסד ל־INCR יש רגע שבו בקשה יכולה לקרוא את הישן — ואפילו לשמור אותו מחדש תחת הגרסה החדשה, אם התחילה לטעון לפני העדכון וסיימה אחריו. זה מקור הקושי ב־cache: "There are only two hard things in Computer Science: cache invalidation and naming things". לכן ה־TTL נשאר תמיד, ולכן מה שחייב להיות מדויק — לא קוראים מ־cache.

⚠️ מה לא שמים ב־cache
  • החלטות. הקטלוג יכול להראות מחיר ישן לדקה; ההזמנה לוקחת את המחיר והמלאי מהמסד, בתוך הטרנזקציה (פרויקט 3, שלב 2). cache לתצוגה — כן; ל"מותר למכור?" — אף פעם.
  • מידע של משתמש במפתח משותף. GET /orders ב־cache לפי URL בלבד — והלקוח הבא רואה את ההזמנות של הקודם. מידע אישי: המפתח כולל את המשתמש, או — עדיף — לא שומרים.
  • שגיאות. המסד נפל, load() זרק — לא שומרים כלום (E07).

4. stampede

מפתח פופולרי פג. באותה מילישנייה מגיעות 200 בקשות, כולן רואות miss, וכולן מריצות את השאילתה היקרה — המסד מקבל פי 200 עומס בדיוק ברגע הכי גרוע. בתוך תהליך אחד זה קל לראות:

```ts run const db = { calls: 0 }; const loadProducts = async () => { db.calls++; await new Promise((r) => setTimeout(r, 50)); return ["latte", "mocha"]; }; // cache-aside נאיבי (Map במקום Redis — אותה בעיה) const cache = new Map(); async function naive(key: string) { if (cache.has(key)) return cache.get(key)!; const value = await loadProducts(); cache.set(key, value); return value; } await Promise.all(Array.from({ length: 200 }, () => naive("products"))); console.log("נאיבי:", db.calls, "שאילתות"); // single-flight: מי שמגיע בזמן שהטעינה רצה — מחכה לאותו Promise db.calls = 0; cache.clear(); const inFlight = new Map>(); async function singleFlight(key: string) { if (cache.has(key)) return cache.get(key)!; let p = inFlight.get(key); if (!p) { p = loadProducts().then((v) => { cache.set(key, v); return v; }).finally(() => inFlight.delete(key)); inFlight.set(key, p); } return p; } await Promise.all(Array.from({ length: 200 }, () => singleFlight("products"))); console.log("single-flight:", db.calls, "שאילתות"); ``` ```out נאיבי: 200 שאילתות single-flight: 1 שאילתות ```

זה פותר בתוך תהליך. עם חמישה שרתים — עדיין 5 שאילתות; כדי להוריד ל־1 צריך מנעול ב־Redis: מי שתפס טוען, השאר מחכים שהערך יופיע (E13). דרכים נוספות: TTL עם רעש אקראי (60 + random(0..10)) כדי שמפתחות לא יפוגו יחד, ו"רענון מוקדם" — טוענים מחדש ברקע קצת לפני שהתוקף נגמר.

💡 ועוד שכבה: cache בזיכרון התהליך

הכי מהיר — בלי רשת בכלל: Map בתוך התהליך (L1), ו־Redis מאחוריו (L2). הבעיה: חמישה שרתים = חמישה עותקים, וביטול צריך להגיע לכולם. pub/sub של Redis עושה את זה (E19) — ועם TTL קצר ל־L1, כי pub/sub לא מבטיח הגעה.
