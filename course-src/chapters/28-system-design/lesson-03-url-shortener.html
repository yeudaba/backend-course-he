🎯 בשיעור הזה
  • שאלת התכנון הקלאסית, מקצה לקצה, בשבעת השלבים.
  • איך מייצרים קוד קצר: מונה, אקראי, או hash — ומה כל אחד עולה.
  • 301 או 302, cache לקישורים חמים, וספירת קליקים בלי להאט את ה־redirect.

1. דרישות ומספרים

מ־E01 ו־E02: יצירה (אנונימית, עם הגבלת קצב), alias אופציונלי, תפוגה, ספירת קליקים; redirect מהיר וזמין. 100 מיליון redirects ביום (3,000/s בשיא), מיליון קישורים חדשים ביום (~10/s), 1TB ב־5 שנים. מערכת קריאה, יחס 100:1.

2. API ונתונים

```text POST /links { url, alias?, ttlSeconds? } → 201 { code, shortUrl, expiresAt } GET /:code → 302 Location: · 404 אם לא קיים · 410 אם פג GET /links/:code/stats → { clicks, createdAt } (ליוצר בלבד) ``` ```sql CREATE TABLE links ( code text PRIMARY KEY, -- החיפוש היחיד ב־redirect: לפי code url text NOT NULL, owner_id bigint REFERENCES users(id), created_at timestamptz NOT NULL DEFAULT now(), expires_at timestamptz, clicks bigint NOT NULL DEFAULT 0 ); ```

ה־redirect הוא SELECT url, expires_at FROM links WHERE code = $1 — חיפוש לפי PRIMARY KEY, מילישנייה. 1TB בטבלה אחת זה הרבה לגיבוי, אבל לא בעיה לאינדקס.

hash של ה־URL7 התווים הראשונים של sha256(url)אותו URL ← אותו קודהתנגשויות בין URLs שונים; ושני אנשים שמקצרים אותו URL חולקים סטטיסטיקות
```ts run const ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"; const encode = (n: number) => { let s = ""; do { s = ALPHABET[n % 62] + s; n = Math.floor(n / 62); } while (n > 0); return s; }; console.log("מונה:", [1, 2, 3, 61, 62, 1_000_000, 1_000_001].map(encode).join(" ")); console.log("קודים אפשריים:", [6, 7, 8].map((len) => `${len} תווים = ${(62 ** len).toExponential(1)}`).join(" · ")); // סיכוי שקוד אקראי חדש יתנגש, כשכבר יש 2 מיליארד קודים (7 תווים) console.log("התנגשות לקוד חדש:", (2e9 / 62 ** 7).toFixed(5)); ``` ```out מונה: 1 2 3 Z 10 4c92 4c93 קודים אפשריים: 6 תווים = 5.7e+10 · 7 תווים = 3.5e+12 · 8 תווים = 2.2e+14 התנגשות לקוד חדש: 0.00057 ```

שני מיליארד קישורים, והסיכוי שקוד אקראי חדש כבר תפוס — כחצי פרומיל. ניסיון שני כמעט תמיד מצליח. לכן בחרנו באקראי (E17), עם code כ־PRIMARY KEY: INSERT שנכשל על ייחודיות ← קוד חדש. המסד הוא שמבטיח, לא "בדקתי קודם" (אותו לקח כמו המלאי בפרויקט 3).

4. ה־redirect: 301 או 302?

301 Moved Permanently — הדפדפן שומר את ההפניה ולא שואל אותנו שוב. מהיר יותר, פחות עומס — אבל לא נדע על הקליקים הבאים, ואי אפשר לשנות יעד או לחסום קישור שהתגלה כפישינג. 302 Found — כל קליק עובר דרכנו. רוב השירותים בוחרים 302 (או 307) — הסטטיסטיקות והשליטה הן המוצר.

5. עומס: cache וקליקים

3,000 redirects בשנייה, ורובם — על מעט קישורים (קמפיין שפורסם עכשיו). cache: code ← url ב־Redis עם TTL של שעה (פרק 26). קישור חם — מ־Redis תמיד; המסד מקבל רק miss. ביטול: אם מותר לשנות יעד או למחוק — DEL לקוד ביחד עם העדכון.

קליקים: UPDATE links SET clicks = clicks + 1 בכל redirect = 3,000 כתיבות בשנייה על אותן שורות חמות — נעילות, ובדיוק במקום שהיה אמור להיות קריאה בלבד. במקום זה: INCR clicks:<code> ב־Redis, ו־job שכל דקה מעביר למסד באצווה (E18 בכיוון ההפוך). אם נאבד דקה של קליקים כש־Redis נופל — זה מחיר סביר, וכדאי להגיד אותו בקול.

התרשים הסופי: לקוח ← load balancer ← 2–3 שרתי API (stateless) ← Redis (cache + מונים) ← PostgreSQL (primary + replica), ו־worker שמעביר קליקים. אין sharding, אין Kafka — המספרים לא מצדיקים.

⚠️ מה ששוכחים בשאלה הזו
