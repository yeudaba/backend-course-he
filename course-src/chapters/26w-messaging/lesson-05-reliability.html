🎯 בשיעור הזה
  • consumer אידמפוטנטי: "כבר טיפלתי" באותה טרנזקציה.
  • dual write, ו־transactional outbox שפותר אותו.
  • retries: מתי לנסות שוב, כמה לחכות, ומתי לוותר.
  • אירועים לאורך זמן: מעטפת, גרסאות, ו־seq לסדר.

1. consumer אידמפוטנטי

at-least-once אומר שכל consumer יקבל, מתישהו, הודעה שכבר טיפל בה. התשובה היא לא "לוודא שזה לא יקרה" — אלא שזה לא יזיק. שלוש דרכים, מהפשוטה:

  • פעולה אידמפוטנטית מטבעה: UPDATE orders SET status = 'shipped' — פעמיים זה כמו פעם. UPDATE … SET stock = stock - 1 — לא.
  • upsert לפי מפתח טבעי: INSERT … ON CONFLICT (order_id) DO NOTHING — "רשומת משלוח להזמנה 42" יכולה להיות רק אחת.
  • טבלת אירועים שטופלו: processed_events (consumer, event_id) PRIMARY KEY — ה־INSERT אליה באותה טרנזקציה עם הפעולה. אם ה־INSERT לא הכניס (כבר קיים) ← דילוג (E15).

ה"באותה טרנזקציה" הוא כל הסיפור. "בדוק אם טופל ← טפל ← סמן" בשלושה צעדים נפרדים נשבר בשני מקרים: שני consumers בודקים יחד (שניהם "לא טופל"), או נפילה בין הטיפול לסימון (טופל, לא סומן ← יטופל שוב).

2. dual write ו־outbox

הקוד הכי נפוץ — ושבור:

```ts await db.orders.create(order); // 1. מסד await broker.publish("order.placed", order); // 2. broker ← נפילה כאן = הזמנה בלי אירוע ```

שתי מערכות, בלי טרנזקציה משותפת. נפילה בין 1 ל־2 — ההזמנה קיימת, ואף שירות לא יודע. להפוך את הסדר — אירוע על הזמנה שאולי תיכשל. זו בעיית ה־dual write, ואין לה פתרון בתוך הקוד הזה. הפתרון המקובל — transactional outbox:

שני הדפוסים — outbox ו־consumer אידמפוטנטי — הם זוג. outbox מבטיח שאף אירוע לא יאבד; אידמפוטנטיות מבטיחה שכפילות לא תזיק. יחד: "בדיוק פעם אחת" בהשפעה, גם בלי שה־broker מבטיח את זה.

3. retries

הטיפול נכשל. לפני "לנסות שוב" — שתי שאלות:

  1. האם ניסיון נוסף יעזור? timeout, 503, חיבור שנפל — כנראה. 400 (נתונים לא תקינים), 404 (ההזמנה לא קיימת), JSON פגום — לעולם לא. שגיאה קבועה ← dead letter מיד, בלי לבזבז ניסיונות.
  2. כמה לחכות? exponential backoff — 0.5, 1, 2, 4 שניות… עם תקרה — ועם jitter: השהיה אקראית עד התקרה. בלי jitter, אלף consumers שנכשלו יחד חוזרים יחד, ומפילים שוב את השירות שבדיוק התאושש. ואם השירות אמר כמה לחכות (Retry-After ב־429) — מכבדים (E16).

ואחרי N ניסיונות — dead letter queue, עם alarm. DLQ שאף אחד לא מסתכל עליו הוא פח אשפה עם שם יפה.

4. אירועים לאורך זמן

אירוע שנכתב היום ייקרא מחר ע״י consumer שעוד לא נכתב. לכן כל אירוע עטוף במעטפת קבועה:

```json { "id": "4f1c2a9e-…", "type": "order.placed", "version": 2, "occurredAt": "2026-11-08T10:00:00.000Z", "source": "coffee-api", "data": { "orderId": 42, "email": "dana@example.com", "total": { "amountCents": 8990, "currency": "ILS" } } } ```
  • id — לאידמפוטנטיות. type ו־version — כדי שה־consumer יידע איך לקרוא את data.
  • שינוי שובר (שדה שהשתנה) ← גרסה חדשה. consumers מתעדכנים קודם לקבל את שתיהן, ורק אז ה־producer עובר (E08). שדה נוסף — לא שובר, אם consumers מתעלמים משדות שהם לא מכירים.
  • סדר: גם עם key ו־partition, retries ו־DLQ יכולים לשבש סדר. מספר רץ לכל ישות (seq, מגרסת השורה במסד) נותן ל־consumer לזהות אירוע ישן ולהתעלם ממנו (E13).
💼 בעולם העבודה

"ספר על מערכת event-driven שבנית" — הנה התשובה, משלושת הפרויקטים של הקורס ומהיחידה הזו: outbox כדי שאירוע לא יאבד, consumer אידמפוטנטי כדי שכפילות לא תזיק, key לסדר, DLQ עם alarm, backoff עם jitter, ו־exactly-once מול מסד עם offsets באותה טרנזקציה. מעט מועמדים לג׳וניור יודעים להסביר את כל השרשרת — ופרויקט 4 בונה אותה מקצה לקצה.
