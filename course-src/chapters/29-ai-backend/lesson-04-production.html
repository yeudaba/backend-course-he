1. streaming

תשובה ארוכה לוקחת שניות. במקום ספינר — מציגים אותה כשהיא נכתבת. בצד ה־API:

```ts const stream = client.messages.stream({ model: "claude-opus-5-5", max_tokens: 16000, system, messages }); for await (const event of stream) { if (event.type === "content_block_delta" && event.delta.type === "text_delta") send(event.delta.text); } const final = await stream.finalMessage(); // ההודעה המלאה — stop_reason ו־usage ללוג ```

ובצד שלך, לדפדפן — Server-Sent Events: תשובת HTTP אחת שנשארת פתוחה, עם שורות data: … (E15). שלושה פרטים: כל שורה — JSON (ירידת שורה בטקסט אחרת שוברת את הפורמט); רק טקסט יוצא, לא thinking; ושגיאה באמצע — כבר אי אפשר להחזיר 500, אז שולחים event: error בתוך הזרם. ואם יש nginx לפני השרת (פרק 25) — proxy_buffering off לנתיב הזה, אחרת הוא אוסף הכול ושולח בסוף.

מה שלא מתאים ל־streaming: עבודות שאף אחד לא מחכה להן בזמן אמת — סיכום לילי של ביקורות, תיוג אלף מוצרים. אלה הולכות לתור (פרק 26), ול־Message Batches API של Anthropic — בקשות אסינכרוניות בחצי מחיר.

2. שגיאות

מה ה־SDK עושה בעצמו? מדדתי עם fetch מדומה (E05): על 429 הוא שולח את הבקשה שלוש פעמים (ניסיון ועוד שניים, עם backoff — כ־1.5 שניות בסך הכול) ורק אז זורק RateLimitError. על 400 — פעם אחת וזורק BadRequestError. כלומר:

  • לא עוטפים ב־retry נוסף — זה ה"retry בכמה שכבות" מפרק 28. אם צריך יותר: maxRetries בבנאי.
  • timeout: ברירת המחדל של ה־SDK ארוכה (דקות). בבקשת HTTP של משתמש — קובעים משהו סביר לנתיב: client.messages.create(params, { timeout: 30_000 }).
  • אחרי שהכול נכשל — מה המשתמש רואה? הודעה מנומסת, תשובה קבועה, מודל חלופי בעומס (E12), או "נציג יחזור אליך". ובשגיאות מתמשכות — circuit breaker (פרק 28).
  • סוגי שגיאות — לפי class, לא לפי טקסט: Anthropic.RateLimitError, BadRequestError, AuthenticationError, InternalServerError, כולם APIError עם status.

(ויש גם סוג "כישלון" שאינו שגיאה: stop_reason: "refusal". ב־Opus 5.5 אפשר לבקש מה־API לנסות מודל חלופי לבד במקרה של סירוב — פרמטר fallbacks בבטא. זה מנגנון אחר מ־E12, שמטפל בעומס.)

3. עלות

prompt caching. ה־system של עוזר החנות — מדיניות משלוחים, החזרות ואחריות — הוא אלפי טוקנים, זהים בכל בקשה. עם cache_control, ה־API שומר את תחילת הבקשה לכמה דקות, וקריאה ממנו עולה חלק קטן ממחיר קלט רגיל (ב־Opus 5.5: $0.20 למיליון במקום $4; הכתיבה הראשונה — קצת יותר מקלט רגיל):

```ts file=P29-E23.ts system: [ { type: "text", text: `${POLICY}\n\n\n${policyDocument}\n`, cache_control: { type: "ephemeral" } }, ], messages: [{ role: "user", content: `(today is ${today})\n\n${question}` }], ```

החוק: ה־cache הוא התאמה של תחילת הבקשה, בית אחרי בית (בסדר: tools ← system ← messages). כל מה שמשתנה — תאריך, שם משתמש, מזהה בקשה — אחרי החלק הקבוע. תאריך בתוך ה־system = prefix חדש בכל בקשה = cache שלא נקרא אף פעם, ותשלום על כתיבה בכל פעם (E23). איך יודעים? usage.cache_read_input_tokens בבקשה השנייה — אפס ← משהו משתנה.

cache לתשובות (E16) — אחר לגמרי: לשאלה שחוזרת בדיוק ("מה שעות המשלוח?") לא קוראים ל־API בכלל. cache-aside מפרק 26, עם מפתח שכולל מודל ו־system — ורק לתשובות שאינן אישיות.

תקציב. משתמש אחד, או סקריפט, יכול לשרוף בלילה את התקציב החודשי. מגבלה יומית למשתמש (E17), הגבלת קצב על הנתיב (פרקים 24, 26), max_tokens סביר, היסטוריה מקוצרת (E07, E18), ומגבלה כוללת בקונסולה של הספק כרשת ביטחון אחרונה. ולוג של usage בכל קריאה — כדי שתדע מה עולה לך כסף לפני שהחשבון מגיע (E08).

4. פרטיות ולוגים

  • שולחים את המינימום. כדי לענות "איפה ההזמנה" המודל צריך סטטוס ותאריכים — לא כתובת, טלפון ופרטי תשלום (E04). כל מה שנשלח עובר לספק חיצוני; בדוק את מדיניות השמירה שלו, ומה החוק אומר על המידע שלך.
  • לוג של כל קריאה: request ID, משתמש, מודל, usage, זמן, stop_reason, שגיאה. לא את הטקסט המלא כברירת מחדל — redact (פרק 24), ואם שומרים לדיבאג, עם תוקף קצר.
  • להגיד למשתמש שהוא מדבר עם מערכת אוטומטית, ושתשובות יכולות לטעות. זה גם הוגן, וגם — במקומות רבים — חובה.
