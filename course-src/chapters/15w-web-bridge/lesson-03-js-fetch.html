`addEventListener` — callback שרץ כשמשהו קורה (פרק 5 ופרק 10: אירועים). הנפוצים: `click`, `submit` (טופס נשלח), `input` (הקלדה), `change`.

2. טופס ← שרת ← דף

```js file=playground/app.js const API = "http://localhost:3000"; document.querySelector("#new-task").addEventListener("submit", async (event) => { event.preventDefault(); // ← בלי זה הדפדפן מרענן את הדף const fields = new FormData(event.target); // הערכים לפי name const res = await fetch(`${API}/tasks`, { method: "POST", headers: { "Content-Type": "application/json" }, body: JSON.stringify({ title: fields.get("title"), priority: fields.get("priority") }), }); const data = await res.json(); if (!res.ok) { document.querySelector("#error").textContent = data.error.message; return; } const li = document.createElement("li"); li.textContent = data.title; document.querySelector("#tasks").append(li); }); ```

זה אותו `fetch` מפרק 14 — עם אותה מלכודת: צריך לבדוק `res.ok`. וההודעה שמוצגת היא `error.message` מה־API — עכשיו רואים למה כדאי שה־API יחזיר הודעות ברורות במבנה קבוע.

⚠️ textContent, לא innerHTML

`li.innerHTML = task.title` נראה אותו דבר — עד שמישהו יוצר משימה בשם ``. הדפדפן מפרש את זה כ־HTML ומריץ את הקוד אצל כל מי שצופה ברשימה. זו XSS — אחת הפרצות הנפוצות בעולם (OWASP, פרק 21). `textContent` תמיד מציג טקסט כמו שהוא. אם חייבים לבנות HTML ממחרוזות — מקודדים כל ערך (תרגיל E06).

3. CORS

הפעל את פרויקט 2 (פורט 3000), ודף שמריץ את הקוד למעלה מכתובת אחרת (פורט 5500 — בשיעור 4). לחיצה על "הוספה" — ובקונסול:

```term !! Access to fetch at 'http://localhost:3000/tasks' from origin 'http://localhost:5500' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource. !! Failed to load resource: net::ERR_FAILED ```

ו־`fetch` זורק `TypeError: Failed to fetch`. אבל עם curl — אותה בקשה עובדת. מה קורה?

  • Origin = פרוטוקול + host + port. `http://localhost:5500` ו־`http://localhost:3000` הם origins שונים (פורט שונה).
  • Same-Origin Policy: כברירת מחדל, קוד בדף רשאי לקרוא תשובות רק מה־origin שלו. למה? בלי זה, כל אתר שתיכנס אליו היה יכול לשלוח בקשה לבנק שלך (הדפדפן מצרף את העוגיות שלך!) ולקרוא את היתרה.
  • CORS = הדרך של השרת לומר "ל־origin הזה מותר": header `Access-Control-Allow-Origin: http://localhost:5500` בתשובה.

Preflight

בקשה "לא פשוטה" — למשל POST עם `Content-Type: application/json`, או PATCH/DELETE — הדפדפן לא שולח מיד. קודם הוא שואל, בבקשת `OPTIONS`:

```term % curl -i -X OPTIONS localhost:3000/tasks -H "Origin: http://localhost:5500" -H "Access-Control-Request-Method: POST" -H "Access-Control-Request-Headers: content-type" HTTP/1.1 204 No Content Access-Control-Allow-Origin: http://localhost:5500 Vary: Origin, Access-Control-Request-Headers Access-Control-Allow-Methods: GET,HEAD,PUT,PATCH,POST,DELETE Access-Control-Allow-Headers: content-type .. ... ```

(זה הפלט אחרי התיקון למטה.) רק אם התשובה מתירה — נשלחת הבקשה האמיתית. ב־DevTools ← Network תראה שתי שורות: `OPTIONS` ואחריה `POST`.

התיקון — בשרת

```ts file=src/app.ts import cors from "cors"; app.use(cors({ origin: ["http://localhost:5500"] })); // לפני ה־routes ```
⚠️ לא `origin: "*"` "כדי שזה יעבוד"

`*` מתיר לכל אתר באינטרנט לקרוא את ה־API מדפדפן של משתמש. ל־API ציבורי לגמרי (מזג אוויר) זה בסדר. ל־API עם נתוני משתמשים — רשימה מפורשת של ה־origins שלך, מתוך משתנה סביבה (בייצור: הדומיין האמיתי).

💡 CORS הוא לא אבטחה של השרת

שים לב לאיור: השרת הריץ את הבקשה. CORS מגן על המשתמש (שאתר זר לא יקרא את הנתונים שלו דרך הדפדפן שלו) — לא על השרת. מי שרוצה לתקוף את השרת ישתמש ב־curl. להגנה על השרת: הזדהות והרשאות (פרק 21).
