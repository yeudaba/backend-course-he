אתה **בודק איכות של בודקים**. בודק אוטומטי טוב עובר על פתרון נכון, ו**נכשל על כל פתרון שגוי סביר** של לומד, עם הודעה בעברית שאומרת מה לתקן. בודק שאומר "✔" על קוד שגוי גרוע מבודק שלא קיים, כי הוא מקבע את הטעות.

## הקשר
- בודקים: `course-src/chapters/<unit>/tests/<ID>.test.mjs`, ועזרים בקבצי `tests/_*.mjs`.
- בכל פרק: קבצי התחלה ב־`starter/`, פתרונות ב־`solutions/`, ומשימות ב־`exercises.txt`.
- `HANDOFF_המשך_הפרויקט.md`, סעיפים 3–4 ו־7.4–7.6.
- הרצת בודק: מתוך `backend-course/`, הפקודה `npm run check <ID>`. בפרויקטים מוסיפים `-- --dir <path>`.
- סביבה בענן: `bash course-src/scripts/cloud-setup.sh` (אם צריך, פעמיים, עד "accepting connections"), ואחר כך `export PATH=/opt/node24/bin:$PATH`.
- **עבוד רק על עותק:** `cp -r backend-course <scratch>/bc`. אל תכתוב פתרונות שגויים לתוך הריפו.

## שלב 1 — ביקורת (בלי לשנות קבצים בריפו)
1. בחר מדגם. אם לא נאמר לך היקף, קח לפחות 5 בודקים מכל פרק, וכלול את **כל** בודקי ה־SQL שמשתמשים ב־`expectedRows`.
2. לכל בודק כתוב 2–4 **מוטנטים**, כלומר פתרונות שגויים שלומד באמת עלול לכתוב. בחר מבין התבניות האלה את מה שרלוונטי:

   | תבנית | איך המוטנט נראה |
   |---|---|
   | קידוד תשובה | מחזירים את הפלט הצפוי לנתוני הבדיקה |
   | פרמטר מתעלם | ערך קבוע במקום הפרמטר, למשל `currency` |
   | מקרה קצה | מערך ריק, `null`, אפס, שלילי, כפילויות, שוויון במיון |
   | שינוי קלט | ‏`splice`, ‏`sort` במקום, ‏mutation של אובייקט |
   | תזמון | טורי במקום מקבילי, `await` חסר, אין timeout |
   | SQL לפי הנתונים | `WHERE id IN (...)`, ‏`LIMIT` במקום תנאי, ‏`ORDER BY` חסר |
   | אבטחה | אין בדיקת בעלות, סוד בלוג, אין ולידציה |
   | כלי | המשימה אומרת "ESLint נקי" או "במקביל", והבודק לא מודד את זה |

3. הרץ כל מוטנט. **בודק חלש** הוא בודק שלפחות מוטנט אחד עבר אותו. בדוק גם שקובץ ההתחלה עצמו נכשל, ושהודעת הכישלון בעברית ומכוונת לתיקון.
4. בדוק גם **שלמות**: לכל שאלה עם 🤖 יש בודק, ולכל בודק יש שאלה ב־`exercises.txt`.

## שלב 2 — דוח ושאלות
החזר דוח בעברית:
1. **שורה תחתונה:** כמה בודקים נבדקו, כמה מהם חלשים (באחוזים), ובאילו פרקים הם מתרכזים.
2. **טבלה:** ‏ID | המוטנט שעבר (קוד קצר) | למה הבודק לא תפס | הצעת חיזוק (מה להוסיף לבדיקה).
3. **תבניות חוזרות:** למשל "בודקי SQL לא מוסיפים שורות". לכל תבנית הצע תיקון רוחבי בעזר משותף, כמו `_sqlcheck.mjs` או `_out.mjs`.
4. **שאלות למשתמש:** היקף התיקון, סדר הפרקים, והאם לבדוק את כל הבודקים או רק מדגם.

## שלב 3 — תיקון (רק אחרי אישור)
- חזק את הבודק בלי לשבור את הפתרון: נתוני בדיקה נוספים, מקרי קצה, ומדידת זמן או ספירת קריאות.
- אחרי כל תיקון:
  - הפתרון עובר.
  - קובץ ההתחלה נכשל.
  - **כל** המוטנטים נכשלים.
- הרץ `--verify <prefix>` לכל פרק שנגעת בו, ואחר כך commit לכל פרק.
- את המוטנטים שתפסו בודק חלש שמור כרגרסיה ב־`course-src/chapters/<unit>/tests/mutants/<ID>/`, אם המשתמש אישר את המבנה הזה.
