שיעור 5 — Node.js, טרנזקציות — ו־Mongo או Postgres?

⏱ ~50 דקות

🎯 בשיעור הזה
  • MongoClient באפליקציה: אחד לתהליך, נסגר בכיבוי.
  • collections עם טיפוסים ב־TypeScript.
  • ObjectId ב־API: 400 על מזהה לא תקין, ומחרוזת בתשובה.
  • NoSQL injection — הגרסה של Mongo ל־SQL injection.
  • טרנזקציות: מתי צריך, ואיך עם session.
  • Mongo או Postgres — השיקולים, ומה עונים בראיון.

1. MongoClient באפליקציה

כמו pg.Pool (פרק 18) ו־PrismaClient (פרק 19): לקוח אחד לכל התהליך, שנוצר בעלייה ונסגר בכיבוי מסודר (פרק 24). הוא מחזיק pool של חיבורים בעצמו (maxPoolSize, ברירת מחדל 100). new MongoClient לכל בקשה פותח חיבורים חדשים כל הזמן — הטעות הנפוצה ביותר.

src/db.ts 
import { MongoClient, type Collection } from "mongodb";

export interface Product {
  _id: string;
  name: string;
  price: number;
  stock: number;
  tags: string[];
}

export const client = new MongoClient(process.env.MONGO_URL!);
export const db = client.db("shop");
export const products: Collection<Product> = db.collection<Product>("products");

עם הטיפוס, TypeScript בודק גם שאילתות ועדכונים: products.updateOne({ _id: "p1" }, { $inc: { stok: 1 } }) — שגיאת קומפילציה על stok, ו־$push: { tags: 5 } — שגיאה כי tags הוא מערך מחרוזות. בלי טיפוס (db.collection("products")) כל שדה הוא any, ואלה נשמרים בשקט.

2. ObjectId ב־API

ה־_id בכתובת (GET /notes/6af1a8c0…) מגיע כמחרוזת. שלושה מקרים: לא תקין ← 400 (לא 500 — new ObjectId("abc") זורק); תקין ולא קיים ← 404; קיים ← 200, וב־JSON מחזירים id כמחרוזת hex. שימו לב ש־ObjectId.isValid מחזיר true גם על כל מחרוזת של 12 תווים (12 בתים) — לכן בודקים גם אורך 24 (E19).

3. NoSQL injection

אין כאן מחרוזת SQL לשבור — אבל יש משהו דומה. ב־Express, ?category[$ne]=x מגיע כ־req.query.category = { $ne: "x" }, ו־JSON body יכול להכיל כל אובייקט. ואז:

import { MongoClient } from "mongodb";

const client = new MongoClient(process.env.MONGO_URL ?? "mongodb://localhost:27017/?directConnection=true");
const db = client.db("lesson5");
const users = db.collection("users");
await users.insertMany([{ email: "dana@example.com", role: "admin" }, { email: "yossi@example.com", role: "user" }]);

// מה ש־login נאיבי עושה עם req.body.email
const body = JSON.parse('{ "email": { "$ne": "nobody" } }');
console.log(await users.findOne({ email: body.email }, { projection: { _id: 0 } }));

await db.dropDatabase();
await client.close();
{ email: 'dana@example.com', role: 'admin' }

"משתמש שהאימייל שלו לא שווה ל־nobody" — הראשון שנמצא, והוא admin. ההגנה: לוודא שכל ערך מהמשתמש הוא מהטיפוס שציפית (Zod עם z.string(), או typeof), לפני שהוא נכנס ל־filter (E20). ובאותה משפחה: לא להעביר את ה־body כמו שהוא ל־$set — רק שדות מותרים (mass assignment, E21).

4. טרנזקציות

שינוי של מסמך אחד הוא אטומי תמיד — ובזכות embedding, רוב הפעולות הן כאלה (שיעור 2). אבל לפעמים צריך כמה מסמכים ביחד: הזמנה מורידה מלאי מכמה מוצרים ויוצרת מסמך הזמנה. אם המוצר השלישי אזל — שני הראשונים צריכים לחזור. בשביל זה יש טרנזקציות (דורשות replica set — לכן ה־--replSet בקופסת ה־🧰):

import { MongoClient } from "mongodb";

const client = new MongoClient(process.env.MONGO_URL ?? "mongodb://localhost:27017/?directConnection=true");
const db = client.db("lesson5b");
const products = db.collection<{ _id: string; stock: number }>("products");
await products.insertMany([{ _id: "p1", stock: 5 }, { _id: "p7", stock: 0 }]);

const session = client.startSession();
try {
  await session.withTransaction(async () => {
    for (const [id, qty] of [["p1", 2], ["p7", 1]] as const) {
      const r = await products.updateOne({ _id: id, stock: { $gte: qty } }, { $inc: { stock: -qty } }, { session });
      if (r.modifiedCount === 0) throw new Error(`out of stock: ${id}`);
    }
  });
} catch (err) {
  console.log("aborted:", (err as Error).message);
} finally {
  await session.endSession();
}
console.log(await products.find().toArray()); // p1 חזר ל־5

await db.dropDatabase();
await client.close();
aborted: out of stock: p7
[ { _id: 'p1', stock: 5 }, { _id: 'p7', stock: 0 } ]
  • כל פעולה בתוך הטרנזקציה מקבלת { session }. פעולה בלי session רצה מחוץ לטרנזקציה — ולא מתבטלת כשהטרנזקציה נכשלת. זה הבאג הנפוץ ביותר (E23).
  • withTransaction מבצע commit בסוף, abort כשנזרקת שגיאה, ומנסה שוב כשיש התנגשות זמנית עם טרנזקציה אחרת (TransientTransactionError). לכן הקוד בפנים צריך להיות בטוח להרצה חוזרת.
  • טרנזקציות ב־Mongo עובדות, אבל הן לא "הדרך הרגילה" כמו ב־Postgres. אם כמעט כל פעולה צריכה טרנזקציה של כמה collections — שווה לשאול שוב אם המבנה (או המסד) נכון.

5. Mongo או Postgres?

MongoDB מתאים כש…PostgreSQL מתאים כש…
הנתונים הם "אובייקטים" שנקראים ונכתבים בשלמותם (הזמנה עם פריטים, פרופיל, קטלוג עם מאפיינים משתנים)יש הרבה קשרים בין ישויות, ושאילתות שמחברות אותן בדרכים שלא ידועות מראש (דוחות, אנליטיקה)
המבנה משתנה הרבה, או שונה בין מסמכים (מוצרים מסוגים שונים)שלמות חשובה מאוד: מפתחות זרים, CHECK, טרנזקציות על פני הרבה טבלאות (כסף, מלאי מורכב)
צריך לפצל את הנתונים בין הרבה שרתים (sharding מובנה)הצוות יודע SQL, ויש כלים (ORM, BI) שמניחים SQL

ובפועל: Postgres עם jsonb (פרק 16) מכסה הרבה מהמקרים "של Mongo", ו־Mongo עם $lookup וטרנזקציות מכסה הרבה מהמקרים "של Postgres". בראיון, התשובה הטובה היא לא "Mongo מהיר יותר" ולא "SQL תמיד עדיף" — אלא: "תלוי בדפוסי הגישה. בפרויקט שלי בחרתי ב־Postgres כי יש הזמנות, מלאי ותשלומים שחייבים להיות עקביים ביחד; קטלוג עם מאפיינים שונים לכל סוג מוצר היה מתאים למסמכים, ושם השתמשתי ב־jsonb."

💡 Mongoose

בהרבה פרויקטים קיימים תפגוש Mongoose — ספרייה מעל ה־driver עם schemas, ולידציה, populate (מעין $lookup) ו־middleware. היא עושה בשבילך חלק ממה שעשית ביחידה ביד; הבנה של ה־driver ושל מה שקורה מתחת היא מה שיעזור כשמשהו לא עובד. ב־NestJS יש @nestjs/mongoose.

💼 בעולם העבודה

במודעות של חברות Node בארץ MongoDB מופיע לצד PostgreSQL ו־MySQL, ולפעמים במקומם. מה שמבדיל ג׳וניור שעבד עם Mongo באמת: עדכון אטומי עם תנאי במקום "קרא ואז כתוב", אינדקס מורכב לפי השאילתה, הגנה מ־NoSQL injection, ותשובה מנומקת ל"למה Mongo כאן?". ואם במשרה עובדים רק עם Postgres — השאלה "מתי היית בוחר במסד של מסמכים?" עדיין תגיע, ועכשיו יש לך תשובה מניסיון.
