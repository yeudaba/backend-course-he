שיעור 3 — InnoDB: טרנזקציות, נעילות ו־deadlocks

⏱ ~50 דקות

🎯 בשיעור הזה
  • REPEATABLE READ: למה SELECT בתוך טרנזקציה יכול להחזיר ערך ישן — הרצה אמיתית.
  • קריאות נועלות: FOR UPDATE, FOR SHARE, SKIP LOCKED.
  • deadlock: איך הוא נוצר, מה InnoDB עושה, ומה עושים אנחנו.

1. REPEATABLE READ

בפרק 18 למדנו רמות בידוד. ב־PostgreSQL ברירת המחדל היא READ COMMITTED: כל פקודה רואה את מה שמחויב באותו רגע. ב־InnoDB ברירת המחדל היא REPEATABLE READ: SELECT רגיל רואה "תמונה" שנלקחה בקריאה הראשונה של הטרנזקציה — גם אם בינתיים מישהו אחר שינה ושמר. הרצתי את זה עם שני חיבורים:

import mysql from "mysql2/promise";

const url = process.env.MYSQL_URL ?? "mysql://root:course@localhost:3306";
const admin = await mysql.createConnection(url);
await admin.query("CREATE DATABASE IF NOT EXISTS rr_demo");
const a = await mysql.createConnection({ uri: url, database: "rr_demo" });
const b = await mysql.createConnection({ uri: url, database: "rr_demo" });
await a.query("CREATE TABLE IF NOT EXISTS products (id INT PRIMARY KEY, stock INT NOT NULL)");
await a.query("REPLACE INTO products VALUES (1, 10)");

const stock = async (c: mysql.Connection, sql = "SELECT stock FROM products WHERE id = 1") => ((await c.query<any[]>(sql))[0][0].stock);

await a.query("START TRANSACTION");
console.log("A reads:", await stock(a));
await b.query("UPDATE products SET stock = 7 WHERE id = 1"); // B: autocommit
console.log("B committed 7");
console.log("A reads again:", await stock(a));
console.log("A FOR UPDATE:", await stock(a, "SELECT stock FROM products WHERE id = 1 FOR UPDATE"));
await a.query("UPDATE products SET stock = stock - 1 WHERE id = 1");
console.log("A after its UPDATE:", await stock(a));
await a.query("COMMIT");

await a.end(); await b.end();
await admin.query("DROP DATABASE rr_demo"); await admin.end();
A reads: 10
B committed 7
A reads again: 10
A FOR UPDATE: 7
A after its UPDATE: 6

המסקנה המעשית — חזקה עוד יותר מבפרק 18: אל תחליט לפי SELECT רגיל בתוך טרנזקציה. או שההחלטה בתוך ה־UPDATE (WHERE stock >= ?, ובודקים affectedRows — E13), או שקוראים עם FOR UPDATE ומחליטים אחרי הנעילה (E09).

2. קריאות נועלות

קריאהרואהנועלתמתי
SELECTהתמונה של הטרנזקציהלאתצוגה, דוחות
SELECT … FOR SHAREהאחרון שמחויבנעילה משותפת — אחרים יכולים לקרוא, לא לשנות"תוודא שזה קיים ולא משתנה עד שאסיים"
SELECT … FOR UPDATEהאחרון שמחויבנעילה בלעדית"אני הולך לשנות את זה"
… FOR UPDATE SKIP LOCKEDרק שורות שלא נעולותבלעדית, ומדלג על נעולותתור עבודות: כל worker לוקח אחרות (E14)
… FOR UPDATE NOWAIT—נכשל מיד אם נעול"אם מישהו כבר מטפל — וותר"

ועוד הבדל מ־PostgreSQL: InnoDB נועל גם "פערים" (gap locks) — טווחים בין ערכים באינדקס — כדי למנוע שורות "רפאים" ב־REPEATABLE READ. לכן FOR UPDATE על WHERE status = 'queued' בלי אינדקס מתאים יכול לנעול הרבה יותר שורות ממה שחשבת. אינדקס על העמודות ב־WHERE מצמצם את הנעילה.

3. deadlock

טרנזקציה A נועלת את מוצר 1 ומחכה למוצר 3; B נועלת את 3 ומחכה ל־1. אף אחת לא תתקדם. InnoDB מזהה את המעגל מיד ומבטל אחת מהן (rollback מלא) עם שגיאה 1213:

Error: Deadlock found when trying to get lock; try restarting transaction
errno: 1213, code: 'ER_LOCK_DEADLOCK', sqlState: '40001'

(הפלט מהרצה אמיתית של התרחיש מול MySQL 8.4 — וזה גם מה שהבודק של E15 מייצר.) שלושה דברים עושים:

  1. לנעול באותו סדר. SELECT … WHERE id IN (…) ORDER BY id FOR UPDATE — אם כולם נועלים מהקטן לגדול, אין מעגל (E09, E24).
  2. טרנזקציות קצרות, בלי קריאות רשת באמצע, ועם אינדקסים שמצמצמים מה ננעל.
  3. retry של כל הטרנזקציה, על 1213 (וגם 1205 — Lock wait timeout exceeded, אחרי 50 שניות כברירת מחדל). הטרנזקציה בוטלה כולה, אז בטוח לנסות שוב (E15).
⚠️ autocommit

בלי START TRANSACTION, כל פקודה היא טרנזקציה משלה — ונעילה של SELECT … FOR UPDATE משתחררת מיד בסוף אותה פקודה. "שמתי FOR UPDATE ועדיין יש כפילויות" — כמעט תמיד זה (E22).
