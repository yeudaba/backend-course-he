P28-E26 · quorum: כמה העתקים צריכים להסכים 🤖

✍️ מאפסרמה 3⏱ 25 דק׳ידע נדרש: שיעור 4

במסדים מבוזרים (Cassandra, ‏DynamoDB) יש N העתקים של כל רשומה. כתיבה מחכה ל־W אישורים, וקריאה שואלת R העתקים. אם R + W > N, כל קבוצת קריאה חופפת לכל קבוצת כתיבה בהעתק אחד לפחות, ולכן הקריאה תמיד רואה את הכתיבה האחרונה. כתוב מקובץ ריק סימולציה קטנה, וייצא:

  • type Replica = { up: boolean; version: number; value: string | null }.
  • isStrong(n, r, w): boolean — ‏r + w > n.
  • quorumWrite(replicas, w, value, version): boolean — כותבת value ו־version לכל העתק עם up: true, ומחזירה האם לפחות w אישרו. גם כשהכתיבה "נכשלה", העתקים שאישרו נשארים מעודכנים.
  • quorumRead(replicas, r) ← { value, version, repaired }. קוראת את r ההעתקים הזמינים הראשונים (לפי הסדר במערך), ומחזירה את הערך עם ה־version הגבוה מביניהם. ‏read repair: כל העתק שנקרא ויש לו גרסה ישנה מתעדכן לחדשה, ו־repaired הוא כמה עודכנו. פחות מ־r העתקים זמינים ← Error.

P28-E28 · hedged request: בקשה שנייה אם הראשונה מתעכבת 🤖

🔁 חזרהרמה 3⏱ 25 דק׳ידע נדרש: שיעור 2

🔁 חזרה על new Promise עם resolve/reject, ‏setTimeout/clearTimeout ו־then עם שתי פונקציות (פרק 10), ‏closures (פרק 5) ו־generics (פרק 11). ב־p99 (שיעור 1) אחת ממאה בקשות איטית בלי סיבה: GC, דיסק עמוס, שכן רועש. "hedged request" (מהמאמר של Google, ‏The Tail at Scale) עוזר: אם אין תשובה תוך זמן קצר, שולחים את אותה בקשה שוב, ולוקחים את מי שעונה ראשון. כתוב וייצא hedged<T>(fn: (attempt: number) => Promise<T>, delayMs: number): Promise<T>:

  • מתחילה fn(1). אם אחרי delayMs עוד אין תשובה, מתחילה גם fn(2). התשובה המוצלחת הראשונה מנצחת.
  • אם fn(1) נכשלה לפני ש־fn(2) התחילה, ‏fn(2) מתחילה מיד, בלי לחכות ל־delayMs.
  • שתיהן נכשלו ← reject עם השגיאה של האחרונה שנכשלה. לכל היותר שתי קריאות ל־fn.
  • תשובה שמגיעה אחרי שכבר הוחלט (הצלחה מאוחרת, או כישלון מאוחר) — לא משנה כלום.
