שיעור 1 — איך ניגשים: דרישות ואומדנים

⏱ ~40 דקות

🎯 בשיעור הזה
  • מה זו שאלת תכנון, ומה מצפים מ־Junior.
  • שבעה שלבים — ומה אומרים בכל אחד.
  • אומדן "על גב מעטפה": בקשות בשנייה, אחסון, ומספרים שכדאי לזכור.

1. מה מצפים ממך

בשאלת תכנון אין תשובה נכונה אחת. המראיין בודק איך אתה חושב: שואל לפני שמתכנן? יודע להגיד "זה מספיק" ולא מסבך? מבין מה כל רכיב עולה? מ־Junior לא מצפים לתכנן את יוטיוב. מצפים לתכנן משהו קטן היטב, ולדעת מה ישתנה כשהוא יגדל. ובעבודה — אותה חשיבה בכל משימה של "להוסיף פיצ׳ר": איפה הנתונים, מי קורא, מה קורה כשמשהו נופל.

2. שבעה שלבים

שלבמה עושיםדוגמה (קיצור קישורים)
1. דרישותפונקציונליות (מה עושים) ולא־פונקציונליות (כמה, כמה מהר, כמה אמין). לכתוב אותןיצירה, redirect, alias, תפוגה, סטטיסטיקות; redirect מהיר; זמינות גבוהה

3. APIendpoints, מה נכנס ומה יוצאPOST /links, GET /:code ← 302
4. מודל נתוניםטבלאות, מפתחות, אינדקסיםlinks(code PK, url, expires_at, …)
5. תרשיםהגרסה הפשוטה שעובדת: לקוח ← שרת ← מסדואז מוסיפים רק מה שהאומדן מצדיק
6. העמקההחלק המעניין: איך מייצרים קוד? איפה צוואר הבקבוק?קוד אקראי מול מונה; cache לקישורים חמים

הטעות הנפוצה ביותר: לדלג לשלב 5 ולצייר עשר קופסות. התרשים בא אחרי המספרים — הם אלה שאומרים אם צריך cache, כמה שרתים, ואם בכלל צריך sharding (כמעט אף פעם לא).

3. אומדנים

הכלים: יום ≈ 100,000 שניות (86,400). מיליון ביום ≈ 12 בשנייה. השיא — פי 2 עד 10 מהממוצע, תלוי במערכת (אתר קניות בבלאק פריידיי — הרבה יותר). ומשם — חשבון:

const day = 86_400;
const scenarios = [
  { name: "חנות הקפה (היום)", users: 2_000, perUser: 30, writes: 0.1, bytes: 2_000, peak: 5, days: 365 },
  { name: "קיצור קישורים", users: 10_000_000, perUser: 10, writes: 0.01, bytes: 500, peak: 3, days: 365 * 5 },
  { name: "רשת חברתית בינונית", users: 5_000_000, perUser: 200, writes: 0.05, bytes: 1_000, peak: 3, days: 365 },
];
for (const s of scenarios) {
  const perDay = s.users * s.perUser;
  const avg = perDay / day;
  const storageGB = (perDay * s.writes * s.bytes * s.days) / 1e9;
  console.log(`${s.name}: ממוצע ${Math.round(avg)}/s · שיא ${Math.round(avg * s.peak)}/s · אחסון ${Math.round(storageGB)}GB`);
}
חנות הקפה (היום): ממוצע 1/s · שיא 3/s · אחסון 4GB
קיצור קישורים: ממוצע 1157/s · שיא 3472/s · אחסון 913GB
רשת חברתית בינונית: ממוצע 11574/s · שיא 34722/s · אחסון 18250GB

מה המספרים אומרים? חנות הקפה: בקשה בשנייה — שרת אחד ישן רוב הזמן. קיצור קישורים: 3,500 בשנייה בשיא — הרבה לשרת Node אחד אם כל בקשה הולכת למסד, קל עם cache ו־2–3 שרתים. רשת חברתית: 35,000 בשנייה ו־18TB בשנה — כאן מתחילים לדבר על replicas, cache רציני, ואולי חלוקה של הנתונים. האומדן אומר לך גם ממה לא לפחד.

4. מספרים שכדאי לזכור

לא בעל פה במדויק — מסדרי גודל. אלה מספרים מקובלים (מהרשימה המפורסמת "Latency numbers every programmer should know", מעודכנים בערך לחומרה של היום), לא מדידה שלי:

פעולהבערך
גישה לזיכרון100 ננו־שניות
קריאה אקראית מ־SSD100 מיקרו־שניות
הלוך־חזור בתוך אותו data center (שרת ← Redis)0.5 מילישנייה
שאילתה פשוטה עם אינדקס1 מילישנייה
הלוך־חזור ישראל ← אירופה50–70 מילישניות
הלוך־חזור ישראל ← ארה״ב (מערב)150–200 מילישניות

והמספרים שמדדנו בעצמנו בקורס: GET מ־Redis מול שאילתת חיפוש על 20,000 מוצרים — 2.5ms מול 70–90ms (פרק 26); OFFSET 500000 מול cursor — 83ms מול 0.06ms (שיעור 4). המסקנה: רשת ודיסק הם היקרים; לולאה בזיכרון כמעט תמיד זניחה לידם. ושאילתה בתוך לולאה (N+1) — הכי יקרה מכולן.

💡 "מה אם…?" — המשפט שהופך תכנון לטוב

אחרי כל קופסה בתרשים: מה אם היא נופלת? מה אם היא איטית? מה אם הבקשה מגיעה פעמיים? מה אם שני משתמשים עושים את זה באותו רגע? רוב הבאגים בפרודקשן הם תשובה שלא נשאלה לאחת מארבע השאלות האלה — וכבר פגשת את כולן בקורס (פרקים 18, 24, 26).
