P28-E26 · quorum: כמה העתקים צריכים להסכים 🤖 ✍️ מאפס רמה 3

💡 רמז 1

‏quorumWrite: לולאה, ‏continue על העתק שלא זמין, ומונה acks. ‏quorumRead: ‏replicas.filter((x) => x.up).slice(0, r) ← ההעתקים שנקראו. אם יש פחות מ־r, זורקים.

💡 רמז 2

החדש ביותר: answered.reduce((best, x) => (x.version > best.version ? x : best)) (פרק 6). אחר כך עוד לולאה על answered: מי שהגרסה שלו נמוכה מקבל את הערך והגרסה של החדש. אלה אובייקטים, ולכן השינוי נשמר במערך המקורי.

✅ פתרון
// P28-E26 — quorum: כמה העתקים צריכים להסכים
export type Replica = { up: boolean; version: number; value: string | null };

export function isStrong(n: number, r: number, w: number): boolean {
  return r + w > n;
}

export function quorumWrite(replicas: Replica[], w: number, value: string, version: number): boolean {
  let acks = 0;
  for (const replica of replicas) {
    if (!replica.up) continue;
    replica.version = version;
    replica.value = value;
    acks++;
  }
  return acks >= w;
}

export function quorumRead(replicas: Replica[], r: number): { value: string | null; version: number; repaired: number } {
  const answered = replicas.filter((rep) => rep.up).slice(0, r);
  if (answered.length < r) throw new Error(`רק ${answered.length} העתקים זמינים, צריך ${r}`);
  const newest = answered.reduce((best, rep) => (rep.version > best.version ? rep : best));
  let repaired = 0;
  for (const rep of answered) {
    if (rep.version < newest.version) {
      rep.version = newest.version;
      rep.value = newest.value;
      repaired++;
    }
  }
  return { value: newest.value, version: newest.version, repaired };
}

];

התרחיש: הכתיבה הגיעה רק להעתקים 0 ו־1, כי 2 היה למטה. אחר כך 2 חזר, ו־0 נפל. הקריאה עם R=2 שאלה את 1 ואת 2. ל־1 יש את הגרסה החדשה, ולכן היא מנצחת. זו החפיפה ש־R + W > N מבטיחה. בדרך, העתק 2 קיבל את הגרסה (repaired: 1), כך שההעתקים מתכנסים בלי תהליך נפרד.

הבדיקה האחרונה בבודק עוברת על כל הצירופים: כתיבה בלי העתק אחד, וקריאה בלי העתק אחר. הקריאה תמיד מוצאת את v1. עם R = W = 1 זה לא נכון: הכתיבה יכולה להגיע רק להעתק 0, והקריאה רק להעתק 1. זה ה־trade-off של שיעור 4. ‏R=1, W=1 מהיר וזמין מאוד, אבל eventually consistent.

מה הסימולציה מפשטת? ‏version כאן הוא מספר שהכותב בוחר. במערכת אמיתית שני כותבים יכולים לבחור אותה גרסה, ואז צריך חותמת זמן עם מזהה צומת, או vector clock. וכתיבה "שנכשלה" (פחות מ־W) שנשארה בחלק מההעתקים יכולה להופיע בקריאה מאוחרת. זו הסיבה ש־Cassandra ממליצה לנסות שוב כתיבה שנכשלה עם אותו ערך.

⚠️ טעויות נפוצות
  • לקרוא מכל ההעתקים ולבחור את החדש — "עובד", אבל זה R=N: כל העתק שנופל מפיל את הקריאה.
  • לבחור את הערך הנפוץ ביותר במקום את הגרסה הגבוהה — שני העתקים ישנים "מנצחים" העתק אחד חדש.
  • read repair גם להעתקים שלא נקראו — הקורא לא יודע מה יש בהם.
  • quorumWrite שעוצרת אחרי w אישורים — שאר ההעתקים נשארים ישנים, והחפיפה נשענת על מזל.

P28-E27 · בדיקות ל־GET /health 🤖 🔁 חזרה רמה 3

💡 רמז 1

פונקציית עזר חוסכת הרבה רעש: const check = (name, over = {}) => ({ name, ok: true, critical: false, latencyMs: 10, ...over }). כל בדיקה מציינת רק את מה שמעניין אותה: check("db", { critical: true, ok: false }). ב־TypeScript: ‏over: Partial<Check>, ו־import { overallHealth, type Check }.

💡 רמז 2

חפש את המקרים שבהם שני כללים מתנגשים: בדיקה קריטית שנכשלה וגם לא קריטית שנכשלה, בדיקה קריטית איטית שעברה, ובדיקה קריטית שנכשלה וגם איטית. לגבול: בדיוק 1000 ← לא איטי, ‏1001 ← איטי. ולפרמטר: קריאה עם slowMs אחר.

  • לבדוק כל כלל לבד — באגים בסדר העדיפויות עוברים.

P28-E28 · hedged request: בקשה שנייה אם הראשונה מתעכבת 🤖 🔁 חזרה רמה 3

💡 רמז 1

‏return new Promise((resolve, reject) => { ... }), ובתוכו משתנים משותפים: settled, ‏started, ‏failures, ‏timer. פונקציה פנימית start() מעלה את started וקוראת ל־fn(started).then(onValue, onError). בכל אחת מהן, השורה הראשונה היא if (settled) return;.

💡 רמז 2

ב־onError: אם started === 1, זו הראשונה, והשנייה עוד לא יצאה ← clearTimeout(timer); start();. אחרת, אם failures === 2 ← settled = true; reject(err). הטיימר: ‏setTimeout(() => { if (!settled && started === 1) start(); }, delayMs).

✅ פתרון
// P28-E28 — hedged request: בקשה שנייה אם הראשונה מתעכבת
export function hedged<T>(fn: (attempt: number) => Promise<T>, delayMs: number): Promise<T> {
  return new Promise<T>((resolve, reject) => {
    let settled = false;
    let failures = 0;
    let started = 0;
    let timer: ReturnType<typeof setTimeout> | undefined;

    const start = () => {
      started++;
      fn(started).then(
        (value) => {
          if (settled) return;
          settled = true;
          clearTimeout(timer);
          resolve(value);
        },
        (err) => {
          if (settled) return;
          failures++;
          if (started === 1) {
            clearTimeout(timer);
            start(); // הראשונה נכשלה לפני שהשנייה התחילה — מתחילים אותה מיד
          } else if (failures === 2) {
            settled = true;
            reject(err);
          }
        },
      );
    };

    start();
    timer = setTimeout(() => {
      if (!settled && started === 1) start();
    }, delayMs);
  });
}

async function demo() {
  const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));
  const t0 = Date.now();
  const slowFirst = await hedged(async (attempt) => {
    await sleep(attempt === 1 ? 300 : 40);
    return `תשובה מניסיון ${attempt}`;
  }, 50);
  console.log(slowFirst, "· לפני שהראשונה סיימה?", Date.now() - t0 < 300);
  const fastFirst = await hedged(async (attempt) => `תשובה מניסיון ${attempt}`, 50);
  console.log(fastFirst);
  try {
    await hedged(async (attempt) => {
      throw new Error(`נכשל ${attempt}`);
    }, 50);
  } catch (err) {
    console.log((err as Error).message);
  }
}

שורה 1: הניסיון הראשון "תקוע" ל־300ms, השני יצא אחרי 50ms וענה תוך 40ms. התשובה חזרה בערך אחרי 90ms. שורה 2: הראשון מהיר, ולכן השני לא יצא בכלל. שורה 3: שניהם נכשלו. השני נכשל אחרון, כי הוא התחיל מיד אחרי הכישלון של הראשון.

‏settled הוא הלב: ‏resolve ו־reject של Promise מתעלמים ממילא מקריאה שנייה, אבל בלי הדגל, כישלון מאוחר היה מתחיל ניסיון שלישי, או סופר כישלונות לא נכון. ‏.then(onValue, onError) עם שתי פונקציות, ולא .then().catch(): כך שגיאה בתוך onValue לא נתפסת כ"כישלון של fn".

מתי לא להשתמש בזה? רק על פעולות שבטוח לשלוח פעמיים: קריאות (GET), או פעולות idempotent עם מפתח (פרק 24). והמחיר: עוד עומס על השרתים. לכן delayMs נבחר לפי p95. כך רק 5% מהבקשות שולחות עותק שני.

⚠️ טעויות נפוצות
  • Promise.race([fn(1), delay.then(() => fn(2))]) — ‏race מחזיר גם את הכישלון הראשון. ‏fn(1) שנכשלה מהר מפילה הכול, למרות ש־fn(2) הייתה מצליחה.
  • לא לבטל את הטיימר — אחרי הצלחה מהירה, ‏fn(2) יוצאת בכל זאת (עומס כפול על כל בקשה).
  • ‏reject בכישלון הראשון כש־fn(2) עוד רצה.
  • לחכות ל־delayMs גם אחרי שהראשונה נכשלה — זמן המתנה מיותר בדיוק כשמשהו לא בסדר.

// P28-E06
// base62: ספרות 0-9, a-z, A-Z. כמו בסיס 10 או 16 — רק עם 62 "ספרות". 7 תווים = 62⁷ ≈ 3.5 טריליון קודים
const ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";

export function encode(n: number): string {
  if (!Number.isSafeInteger(n) || n < 0) throw new Error("רק מספר שלם אי־שלילי");
  if (n === 0) return "0";
  let out = "";
  while (n > 0) {
    out = ALPHABET[n % 62] + out;
    n = Math.floor(n / 62);
  }
  return out;
}

export function decode(code: string): number {
  if (!/^[0-9a-zA-Z]+$/.test(code)) throw new Error("קוד לא תקין");
  let n = 0;
  for (const ch of code) n = n * 62 + ALPHABET.indexOf(ch);
  if (!Number.isSafeInteger(n)) throw new Error("קוד ארוך מדי");
  return n;
}
⚠️ טעויות נפוצות
  • לשכוח את 0 — הלולאה לא רצה, ומתקבלת מחרוזת ריקה (E20).

export interface Inputs {
  dailyActiveUsers: number;
  requestsPerUserPerDay: number;
  writeRatio: number; // חלק הבקשות שכותבות (0..1)
  bytesPerWrite: number;
  peakFactor: number; // השיא פי כמה מהממוצע

    peakRps: Math.round(avgRps * i.peakFactor),
    writesPerSecond: Math.round(writesPerDay / 86_400),
    storageGB: Math.round(storageBytes / 1e9),

}

💡 רמז 2

✅ פתרון
// P28-E08
// שני אלגוריתמים של load balancer: round robin (בתורות) ו־least connections (למי שהכי פנוי)
export function roundRobin(servers: readonly string[]) {
  if (servers.length === 0) throw new Error("אין שרתים");
  let next = 0;
  return () => servers[next++ % servers.length];
}

export function leastConnections(servers: readonly string[]) {
  if (servers.length === 0) throw new Error("אין שרתים");
  const active = new Map(servers.map((s) => [s, 0]));
  return {
    // בתיקו — הראשון ברשימה (סדר קבוע)
    acquire(): string {
      let best = servers[0];
      for (const s of servers) if (active.get(s)! < active.get(best)!) best = s;
      active.set(best, active.get(best)! + 1);
      return best;
    },
    release(server: string) {
      const n = active.get(server);
      if (n === undefined) throw new Error(`שרת לא מוכר: ${server}`);
      if (n > 0) active.set(server, n - 1);
    },
    active: (server: string) => active.get(server) ?? 0,
  };
}

מתי מה? round robin — כשכל הבקשות דומות. least connections — כשיש בקשות ארוכות (העלאת קבצים, WebSocket), ושרת אחד "נתקע" עם הכבדות. ב־nginx: least_conn;. ב־load balancers של הענן — הגדרה.

⚠️ טעויות נפוצות
  • מונה גלובלי משותף לכמה load balancers — עם הרבה מופעים, round robin "מושלם" הוא לא המטרה; פיזור סביר כן.

💡 רמז 1

💡 רמז 2

"כישלון אחד נוסף מוציא שוב": כשמחזירים שרת, קבע את מונה הכישלונות שלו ל־failThreshold − 1.

✅ פתרון
// P28-E09
// load balancer עם health checks: אחרי failThreshold כישלונות ברצף — השרת יוצא מהסבב; אחרי recoverAfterMs — מקבל הזדמנות
export function createBalancer(servers: readonly string[], { failThreshold = 3, recoverAfterMs = 10_000, now = () => Date.now() } = {}) {
  const fails = new Map(servers.map((s) => [s, 0]));
  const downSince = new Map<string, number>();
  let next = 0;

  const isUp = (s: string) => {
    const since = downSince.get(s);
    if (since === undefined) return true;
    if (now() - since >= recoverAfterMs) {
      downSince.delete(s); // הזדמנות שנייה; כישלון אחד נוסף יוריד שוב
      fails.set(s, failThreshold - 1);
      return true;
    }
    return false;
  };

  return {
    pick(): string | null {
      for (let i = 0; i < servers.length; i++) {
        const s = servers[next++ % servers.length];
        if (isUp(s)) return s;
      }
      return null; // כולם למטה — 503 ללקוח
    },
    report(server: string, ok: boolean) {
      if (ok) {
        fails.set(server, 0);
        return;
      }
      const n = (fails.get(server) ?? 0) + 1;
      fails.set(server, n);
      if (n >= failThreshold && !downSince.has(server)) downSince.set(server, now());
    },
    healthy: () => servers.filter((s) => !downSince.has(s) || now() - downSince.get(s)! >= recoverAfterMs),
  };
}

זה מה שה־HEALTHCHECK ב־Dockerfile (פרק 23) ו־/ready (פרק 25) מזינים: ה־load balancer שואל, ושרת שלא עונה — לא מקבל תנועה. ולכן /ready מחזיר 503 כשהמסד לא זמין: "אל תשלחו אליי".

⚠️ טעויות נפוצות
  • להוציא שרת אחרי כישלון בודד — בעומס, שגיאה אחת "מזיזה" תנועה לשרת השני, שגם הוא נכשל פעם, וכולם יוצאים.

💡 רמז 2

✅ פתרון
// P28-E11
// cursor "אטום": הלקוח לא יודע (ולא צריך לדעת) מה בפנים. base64url של JSON — ובדיקה כשהוא חוזר
export interface Cursor {
  createdAt: string; // ISO
  id: number;
}

export function encodeCursor(c: Cursor): string {
  return Buffer.from(JSON.stringify([c.createdAt, c.id])).toString("base64url");
}

export function decodeCursor(raw: string): Cursor {
  try {
    const [createdAt, id] = JSON.parse(Buffer.from(raw, "base64url").toString("utf8"));
    if (typeof createdAt !== "string" || Number.isNaN(Date.parse(createdAt)) || !Number.isSafeInteger(id) || id < 1) throw new Error();
    return { createdAt, id };
  } catch {
    throw new Error("cursor לא תקין");
  }
}

// keyset: "אחרי השורה הזו" במיון (createdAt DESC, id DESC). בלי OFFSET — מהיר בכל עמוד, ולא מדלג/מכפיל כשנוספות שורות
export function nextPage<T extends Cursor>(rows: readonly T[], limit: number, after?: string) {
  const sorted = [...rows].sort((a, b) => (a.createdAt < b.createdAt ? 1 : a.createdAt > b.createdAt ? -1 : b.id - a.id));
  const c = after ? decodeCursor(after) : null;
  const start = c ? sorted.findIndex((r) => r.createdAt < c.createdAt || (r.createdAt === c.createdAt && r.id < c.id)) : 0;
  const page = start === -1 ? [] : sorted.slice(start, start + limit);
  const last = page[page.length - 1];
  const hasMore = start !== -1 && start + limit < sorted.length;
  return { data: page, nextCursor: hasMore && last ? encodeCursor(last) : null };
}

ב־SQL זה WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 20 — ובשיעור 4 מדדנו: 0.06ms בכל עמוד, מול 83ms ל־OFFSET 500000.

⚠️ טעויות נפוצות

💡 רמז 2

✅ פתרון
// P28-E12
// retry עם exponential backoff ו־jitter: לא כל הלקוחות חוזרים באותה שנייה (thundering herd)
export class HttpError extends Error {
  status: number;
  constructor(status: number, message = `HTTP ${status}`) {
    super(message);
    this.status = status;
  }
}

// מה שווה לנסות שוב: רשת, 5xx, 429. 4xx אחר — הבקשה שגויה, ניסיון נוסף ייכשל באותה דרך
export const isRetryable = (err: unknown) => !(err instanceof HttpError) || err.status >= 500 || err.status === 429;

export async function retry<T>(
  fn: (attempt: number) => Promise<T>,
  {
    retries = 3,
    baseMs = 100,
    maxMs = 5000,
    random = Math.random,
    sleep = (ms: number) => new Promise<void>((r) => setTimeout(r, ms)),
  }: { retries?: number; baseMs?: number; maxMs?: number; random?: () => number; sleep?: (ms: number) => Promise<void> } = {},
): Promise<T> {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fn(attempt);
    } catch (err) {
      if (attempt >= retries || !isRetryable(err)) throw err; // לא ישנים אחרי הניסיון האחרון
      const cap = Math.min(maxMs, baseMs * 2 ** attempt);
      await sleep(Math.floor(random() * cap)); // "full jitter": בין 0 לתקרה
    }
  }
}

ולמה jitter? אם אלף לקוחות נכשלו באותו רגע (השירות נפל), בלי jitter כולם חוזרים יחד אחרי 100ms, ושוב יחד אחרי 200ms — "עדר" שמפיל את השירות בכל פעם שהוא מנסה לקום. ועוד כלל: מנסים שוב רק פעולות idempotent — או עם Idempotency-Key (פרק 24).

  • retry בכמה שכבות — הלקוח 3, ה־API 3, ה־worker 3 ← 27 קריאות לשירות שנפל. מנסים שוב בשכבה אחת.

💡 רמז 2

✅ פתרון
// P28-E13
// consistent hashing: השרתים והמפתחות על אותו "מעגל" של מספרים; מפתח שייך לשרת הראשון אחריו (עם עטיפה).
// הוספה/הסרה של שרת מזיזה רק את המפתחות שלידו — כ־1/n, לא כמעט הכול כמו ב־hash % n
import { createHash } from "node:crypto";

export function hash32(s: string): number {
  return createHash("md5").update(s).digest().readUInt32BE(0);
}

export function createRing({ vnodes = 100 }: { vnodes?: number } = {}) {
  let points: { at: number; node: string }[] = []; // ממוין לפי at
  const nodes = new Set<string>();

  return {
    add(node: string) {
      if (nodes.has(node)) return;
      nodes.add(node);
      for (let i = 0; i < vnodes; i++) points.push({ at: hash32(`${node}#${i}`), node });
      points.sort((a, b) => a.at - b.at || (a.node < b.node ? -1 : 1));
    },
    remove(node: string) {
      if (!nodes.delete(node)) return;
      points = points.filter((p) => p.node !== node);
    },
    get(key: string): string | null {
      if (points.length === 0) return null;
      const h = hash32(key);
      // חיפוש בינארי: הנקודה הראשונה שה־at שלה >= h; אין כזו — עוטפים להתחלה
      let lo = 0;
      let hi = points.length;
      while (lo < hi) {
        const mid = (lo + hi) >>> 1;
        if (points[mid].at < h) lo = mid + 1;
        else hi = mid;
      }
      return points[lo === points.length ? 0 : lo].node;
    },
    nodes: () => [...nodes],
  };
}

למה virtual nodes? עם נקודה אחת לשרת, ארבע נקודות "אקראיות" על מעגל יוצרות קטעים בגדלים שונים מאוד — שרת אחד מקבל 40% והשני 10%. 100 נקודות לשרת ממצעות את זה. וזה גם מאפשר משקלים: שרת חזק — יותר נקודות.

⚠️ טעויות נפוצות
  • לא למיין אחרי add — החיפוש הבינארי "עובד" ומחזיר שרת, רק לא הנכון (E22).

P28-E14 · replicas וקריאה אחרי כתיבה 🤖 רמה 3

💡 רמז 1

Map של userId ← זמן הכתיבה האחרונה.

💡 רמז 2

now() - at < stickyMs — ב־2999 עוד primary, ב־3000 כבר replica.

✅ פתרון
// P28-E14
// primary + replicas: כתיבות ל־primary, קריאות ל־replicas — חוץ מ"קריאה אחרי כתיבה":
// משתמש שכתב עכשיו קורא מה־primary לזמן קצר, כי ה־replica עוד לא קיבלה את השינוי (replication lag)
export function createDbRouter({ primary, replicas, stickyMs = 2000, now = () => Date.now() }: { primary: string; replicas: readonly string[]; stickyMs?: number; now?: () => number }) {
  const lastWrite = new Map<string, number>();
  let next = 0;
  return {
    forWrite(userId: string): string {
      lastWrite.set(userId, now());
      return primary;
    },
    forRead(userId: string): string {
      const at = lastWrite.get(userId);
      if (at !== undefined && now() - at < stickyMs) return primary;
      if (replicas.length === 0) return primary;
      return replicas[next++ % replicas.length];
    },
  };
}

// P28-E15
// circuit breaker: שירות שנופל שוב ושוב — מפסיקים לקרוא לו לזמן מה (נכשלים מיד), ואז מנסים בזהירות
export type BreakerState = "closed" | "open" | "half-open";

export function createBreaker<T>(call: () => Promise<T>, { failureThreshold = 5, openMs = 30_000, now = () => Date.now() } = {}) {
  let state: BreakerState = "closed";
  let failures = 0;
  let openedAt = 0;
  let trialRunning = false;

  return {
    get state(): BreakerState {
      if (state === "open" && now() - openedAt >= openMs) state = "half-open";
      return state;
    },
    async exec(): Promise<T> {
      const s = this.state;
      if (s === "open" || (s === "half-open" && trialRunning)) throw new Error("circuit open");
      if (s === "half-open") trialRunning = true; // רק בקשת ניסיון אחת עוברת
      try {
        const result = await call();
        state = "closed";
        failures = 0;
        return result;
      } catch (err) {
        failures++;
        if (s === "half-open" || failures >= failureThreshold) {
          state = "open";
          openedAt = now();
        }
        throw err;
      } finally {
        if (s === "half-open") trialRunning = false;
      }
    },
  };
}

הבעיה שזה פותר: ספק משלוחים נופל ועונה אחרי 30 שניות (timeout). כל בקשה שלנו מחזיקה חיבור 30 שניות ← אחרי דקה נגמרים החיבורים, והשרת שלנו נופל — גם לבקשות שלא קשורות למשלוחים. עם breaker: אחרי 5 כישלונות, נכשלים מיד ("המשלוח יחושב מאוחר יותר"), והשרת חי. ובשילוב: timeout קצר, retry עם jitter, breaker.

✅ פתרון
// P28-E18
// batching: הרבה בקשות "תביא את X" באותו רגע ← שאילתה אחת עם כולם (כמו DataLoader מול N+1)
export function createBatcher<K, V>(
  loadMany: (keys: K[]) => Promise<Map<K, V>>,
  { maxBatch = 100, waitMs = 0 }: { maxBatch?: number; waitMs?: number } = {},
) {
  let queue: { key: K; resolve: (v: V | undefined) => void; reject: (e: unknown) => void }[] = [];
  let timer: ReturnType<typeof setTimeout> | null = null;

  const flush = () => {
    if (timer) clearTimeout(timer);
    timer = null;
    const batch = queue;
    queue = [];
    const keys = [...new Set(batch.map((b) => b.key))];
    loadMany(keys).then(
      (result) => batch.forEach((b) => b.resolve(result.get(b.key))),
      (err) => batch.forEach((b) => b.reject(err)),
    );
  };

  return (key: K) =>
    new Promise<V | undefined>((resolve, reject) => {
      queue.push({ key, resolve, reject });
      if (new Set(queue.map((q) => q.key)).size >= maxBatch) flush();
      else if (!timer) timer = setTimeout(flush, waitMs);
    });
}

זה DataLoader (הספרייה של GraphQL) בגרסה קטנה, והתשובה הכללית ל־N+1 (פרק 19): עשרים resolvers שכל אחד מבקש "משתמש X" ← שאילתה אחת WHERE id IN (…). אותו רעיון בכתיבה: במקום INSERT לכל קליק — אצווה כל שנייה.

export function createFeed({ celebrityThreshold = 1000, timelineCap = 500 }: { celebrityThreshold?: number; timelineCap?: number } = {}) {
  const followers = new Map<string, Set<string>>();
  const following = new Map<string, Set<string>>();
  const timelines = new Map<string, Post[]>(); // החדש ראשון
  const postsBy = new Map<string, Post[]>(); // החדש ראשון
  const stats = { timelineWrites: 0 };
  let nextId = 1;

  const set = (m: Map<string, Set<string>>, k: string) => m.get(k) ?? m.set(k, new Set()).get(k)!;
  const isCelebrity = (u: string) => (followers.get(u)?.size ?? 0) >= celebrityThreshold;
  const newestFirst = (a: Post, b: Post) => b.at - a.at || b.id - a.id;

  return {
    stats,
    follow(user: string, target: string) {
      set(followers, target).add(user);
      set(following, user).add(target);
    },
    post(author: string, at: number): Post {
      const p = { id: nextId++, author, at };
      (postsBy.get(author) ?? postsBy.set(author, []).get(author)!).unshift(p);
      if (!isCelebrity(author)) {
        for (const f of followers.get(author) ?? []) {
          const tl = timelines.get(f) ?? timelines.set(f, []).get(f)!;
          tl.unshift(p);
          if (tl.length > timelineCap) tl.length = timelineCap;
          stats.timelineWrites++;
        }
      }
      return p;
    },
    timeline(user: string, limit = 20): Post[] {
      // Map לפי id: פוסט של מי שהפך לסלבריטי אחרי שפרסם — כבר בפיד, וגם נמשך עכשיו. לא להציג פעמיים
      const merged = new Map((timelines.get(user) ?? []).map((p) => [p.id, p]));
      for (const t of following.get(user) ?? []) {
        if (isCelebrity(t)) for (const p of (postsBy.get(t) ?? []).slice(0, limit)) merged.set(p.id, p);
      }
      return [...merged.values()].sort(newestFirst).slice(0, limit);
    },
  };
}

const ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";

export function encode(n: number): string {
  if (!Number.isSafeInteger(n) || n < 0) throw new Error("רק מספר שלם אי־שלילי");
  if (n === 0) return "0"; // תקלה 1: בלי זה, 0 ← "" (הלולאה לא רצה), וקוד ריק לא מתפענח
  let out = "";
  while (n > 0) {
    out = ALPHABET[n % 62] + out; // תקלה 2: היה out += … ← הספרות יוצאות הפוך (הקטנה ראשונה)
    n = Math.floor(n / 62); // תקלה 3: היה n / 62 ← שבר, והלולאה ממשיכה עם 0.0something עד שמתקבל אפס
  }
  return out;
}

export function decode(code: string): number {
  if (!/^[0-9a-zA-Z]+$/.test(code)) throw new Error("קוד לא תקין");
  let n = 0;
  for (const ch of code) n = n * 62 + ALPHABET.indexOf(ch);
  return n;
}

  return {
    add(node: string) {
      for (let i = 0; i < vnodes; i++) points.push({ at: hash32(`${node}#${i}`), node });

export function createBreaker<T>(call: () => Promise<T>, { failureThreshold = 3, openMs = 10_000, now = () => Date.now() } = {}) {
  let state: "closed" | "open" | "half-open" = "closed";
  let failures = 0;
  let openedAt = 0;
  return {
    get state() {
      if (state === "open" && now() - openedAt >= openMs) state = "half-open";
      return state;
    },
    async exec(): Promise<T> {
      const s = this.state;
      // תקלה 2: הבדיקה הייתה רק אחרי שהקריאה נכשלה ← כשהמעגל פתוח, כל בקשה עדיין פנתה לשירות המת (וחיכתה ל־timeout שלו)
      if (s === "open") throw new Error("circuit open");
      try {
        const result = await call();
        failures = 0; // תקלה 1: הצלחה לא איפסה את המונה ← 3 כישלונות "מפוזרים" לאורך יום פותחים את המעגל
        state = "closed";
        return result;
      } catch (err) {
        failures++;
        // תקלה 3: התנאי היה רק s === "closed" ← כישלון של בקשת הניסיון ב־half-open השאיר אותו half-open, וכל הבקשות עברו לשירות

          state = "open";
          openedAt = now();
        }
        throw err;
      }
    },
  };
}

P28-E24 · אתגר: מזהי Snowflake 🤖 רמה 5

💡 רמז 1

((ms − EPOCH) << 22n) | (worker << 12n) | seq — הכול BigInt (BigInt(x)).

💡 רמז 2

פירוק: id >> 22n, (id >> 12n) & 1023n, id & 4095n.

✅ פתרון
// P28-E24
// מזהה בסגנון Snowflake (טוויטר): 64 ביט = 41 זמן (מילישניות מ־epoch משלנו) | 10 worker | 12 מונה.
// כל שרת מייצר לבד, בלי לתאם, והמזהים ממוינים בערך לפי זמן. BigInt — כי Number שומר רק 53 ביט
const EPOCH = 1_767_225_600_000n; // 2026-01-01T00:00:00Z

export function createIdGenerator(workerId: number, { now = () => Date.now() }: { now?: () => number } = {}) {
  if (!Number.isInteger(workerId) || workerId < 0 || workerId > 1023) throw new Error("workerId בין 0 ל־1023");
  let lastMs = -1;
  let seq = 0;
  return {
    next(): bigint {
      let ms = now();
      if (ms < lastMs) throw new Error(`השעון חזר אחורה ב־${lastMs - ms}ms — מסרבים לייצר מזהים כפולים`);
      if (ms === lastMs) {
        seq = (seq + 1) & 4095;
        if (seq === 0) {
          while (ms <= lastMs) ms = now(); // 4096 מזהים באותה מילישנייה — מחכים לבאה
        }
      } else {
        seq = 0;
      }
      lastMs = ms;
      return ((BigInt(ms) - EPOCH) << 22n) | (BigInt(workerId) << 12n) | BigInt(seq);
    },
  };
}

export function parseId(id: bigint) {
  return {
    time: new Date(Number((id >> 22n) + EPOCH)).toISOString(),
    workerId: Number((id >> 12n) & 1023n),
    seq: Number(id & 4095n),
  };
}

למה לא מספר אוטומטי מהמסד? כי אז כל יצירה צריכה את המסד — ועם כמה מסדים (sharding) כל אחד סופר לבד. למה לא UUID אקראי? 128 ביט, ולא ממוין — אינדקס B-tree שמקבל ערכים אקראיים מתפצל בכל מקום. Snowflake: 64 ביט, ממוין בערך לפי זמן, בלי תיאום. היום יש גם UUIDv7 — UUID שמתחיל בזמן — שנותן את רוב היתרונות עם תקן מוכר. ובצד הלקוח: מזהה של 64 ביט הוא מעבר ל־Number.MAX_SAFE_INTEGER — ב־JSON שולחים אותו כמחרוזת.

⚠️ טעויות נפוצות
  • Number במקום BigInt — מעבר ל־53 ביט מספרים "נעגלים" בשקט, ושני מזהים שונים הופכים לאותו מספר.

P28-E25 · אתגר: Bloom filter 🤖 רמה 5

💡 רמז 1

ביט p: בית p >> 3, ביט p & 7 בתוכו. הדלקה: |= 1 << (p & 7).

💡 רמז 2

d.readUInt32BE(4) | 1 — מה הסימן של התוצאה, כשהביט העליון דלוק?

✅ פתרון
// P28-E25
// Bloom filter: "בטוח לא קיים" או "אולי קיים" — במעט זיכרון. אין false negatives; false positives בשיעור שבוחרים.
// m ביטים ו־k פונקציות hash, מחושבים מגודל צפוי n ושיעור טעות p
import { createHash } from "node:crypto";

export function createBloom(expected: number, falsePositiveRate: number) {
  const m = Math.ceil((-expected * Math.log(falsePositiveRate)) / Math.LN2 ** 2);
  const k = Math.max(1, Math.round((m / expected) * Math.LN2));
  const bits = new Uint8Array(Math.ceil(m / 8));

  // double hashing: שני hashים מ־sha256, ומהם k מיקומים (h1 + i·h2)
  const positions = (item: string) => {
    const d = createHash("sha256").update(item).digest();
    const h1 = d.readUInt32BE(0);
    const h2 = (d.readUInt32BE(4) | 1) >>> 0; // ">>> 0": בלי זה, | הופך מספר גדול לשלילי — ומיקום שלילי ב־Uint8Array פשוט לא נכתב
    return Array.from({ length: k }, (_, i) => (h1 + i * h2) % m);
  };

  return {
    m,
    k,
    bytes: bits.length,
    add(item: string) {
      for (const p of positions(item)) bits[p >> 3] |= 1 << (p & 7);
    },
    mightContain(item: string): boolean {
      return positions(item).every((p) => (bits[p >> 3] & (1 << (p & 7))) !== 0);
    },
  };
}

על מיליון שמות עם 1% טעות: 1.2MB ו־7 hashים. מדדתי: 1.002% false positives. Set עם אותם מיליון שמות תפס כ־35MB. "לא קיים" — בטוח, ואפשר לענות מיד; "אולי" — שואלים את המסד. כך עושים Cassandra ו־RocksDB (לדלג על קבצים שבטוח אין בהם את המפתח), וכך דפדפנים בדקו פעם אתרים זדוניים.

⚠️ טעויות נפוצות
  • זה הבאג שהיה לי בפתרון הראשון: x | 1 ב־JavaScript מחזיר מספר עם סימן של 32 ביט. כשהביט העליון דלוק — שלילי, המיקום שלילי, ו־bits[-5] |= … לא זורק — פשוט לא כותב. התוצאה: false negatives, הדבר היחיד שאסור ל־Bloom filter. הבודק תפס את זה; >>> 0 מחזיר ל־unsigned.
