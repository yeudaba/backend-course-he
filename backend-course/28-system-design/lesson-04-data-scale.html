שיעור 4 — נתונים בקנה מידה

⏱ ~50 דקות

🎯 בשיעור הזה
  • עימוד: למה OFFSET איטי בעמוד 25,000 — מדידה — ו־cursor.
  • כשמסד אחד לא מספיק: sharding, ולמה hash % n מסוכן.
  • מזהים בלי מסד מרכזי: Snowflake ו־UUIDv7.
  • batching ו־Bloom filter: לחסוך הלוך־חזור.
  • עקביות: מה מותר להיות ישן.

1. עימוד: OFFSET מול cursor

בכל הפרויקטים עימדנו עם ?page= — כלומר OFFSET (page − 1) × limit. זה פשוט ומאפשר "קפוץ לעמוד 7". אבל כדי לדלג על חצי מיליון שורות, המסד צריך לעבור עליהן. מדדתי על טבלה של מיליון פוסטים, עם אינדקס על (created_at DESC, id DESC), שלוש שאילתות של 20 שורות: עמוד ראשון, OFFSET 500000, ו־cursor מאותה נקודה (פלט EXPLAIN ANALYZE, מקוצר):

---- offset 0
Limit (actual time=0.035..0.039 rows=20.00 loops=1)
  ->  Index Only Scan using posts_created_id on posts (actual time=0.033..0.035 rows=20.00 loops=1)
Execution Time: 0.053 ms
---- offset 500000
Limit (actual time=82.980..82.985 rows=20.00 loops=1)
  ->  Index Only Scan using posts_created_id on posts (actual time=0.011..70.149 rows=500020.00 loops=1)
Execution Time: 83.000 ms
---- keyset
Limit (actual time=0.026..0.029 rows=20.00 loops=1)
  ->  Index Only Scan using posts_created_id on posts (actual time=0.024..0.027 rows=20.00 loops=1)
        Index Cond: (ROW(created_at, id) < ROW('2026-01-06 20:53:20+02'::timestamp with time zone, 500000))
Execution Time: 0.057 ms

שימו לב ל־rows=500020: כדי להחזיר 20, ה־OFFSET קרא חצי מיליון. ה־cursor (keyset pagination) אומר "תן לי 20 אחרי השורה הזו" — המסד יורד באינדקס ישר לשם, בכל עמוד באותה מהירות. בונוס: אם נוספות שורות בזמן הגלילה, OFFSET מחזיר כפילויות (הכול "זז" למטה); cursor — לא (E11).

המחיר: אין "קפוץ לעמוד 7", רק "הבא". לפיד, לגלילה אינסופית ול־API ציבורי — cursor. לטבלת ניהול עם 30 עמודים — OFFSET בסדר גמור. ה־cursor הוא מחרוזת אטומה (base64url) — הלקוח לא בונה אותה, ואתה יכול לשנות את מה שבתוכה.

2. sharding

replicas מחלקות קריאות. כשהכתיבות או הנפח גדולים ממסד אחד — מחלקים את הנתונים: sharding. כל משתמש (וכל מה ששלו) במסד אחד מתוך כמה, לפי מפתח. המחיר כבד: שאילתה על כמה משתמשים — לכמה מסדים; טרנזקציה בין shards — כמעט בלתי אפשרית; JOIN — בקוד. לכן זה הצעד האחרון, אחרי אינדקסים, cache, replicas ושרת גדול יותר. (PostgreSQL אחד על חומרה טובה מחזיק טרה־בייטים ואלפי כתיבות בשנייה.)

ואיך מחליטים איזה shard? הרעיון הראשון — hash(userId) % n. עובד, עד שמוסיפים מסד. מדדתי על 100,000 מפתחות (E16):

שינויhash % n — זזוconsistent hashing — זזו
4 ← 5 שרתים80.3%19.2%
10 ← 11 שרתים90.9%7.9%
10 ← 9 (שרת נפל)89.9%11.5%

consistent hashing (E13): השרתים והמפתחות על "מעגל" של מספרים; מפתח שייך לשרת הבא אחריו. שרת חדש "לוקח" רק את המפתחות שבקטע שלו — כ־1/n. ב־sharding זה ההבדל בין להעביר עשירית מהנתונים לבין כמעט הכול; ב־cache מבוזר — בין 8% פספוסים לבין cache ריק ומסד שקורס. וירטואל נודס (100 נקודות לשרת) מיישרים את הפיזור.

3. מזהים

id SERIAL דורש מסד אחד שסופר. עם כמה shards, או כשרוצים לייצר מזהה לפני שמגיעים למסד — צריך מזהים שכל שרת מייצר לבד:

גודלממוין לפי זמןהערה
UUIDv4 (אקראי)128 ביטלאאינדקס B-tree מקבל ערכים בכל מקום — יותר פיצולי דפים ו־cache misses
UUIDv7128 ביטכן (מתחיל בזמן)תקן מ־2024 (RFC 9562); הבחירה הנוחה היום
Snowflake (E24)64 ביטכןזמן | מכונה | מונה; קטן — אבל צריך לחלק מספרי מכונות, ובלקוח JavaScript — לשלוח כמחרוזת

4. פחות הלוך־חזור

הלוך־חזור למסד או ל־Redis הוא חצי מילישנייה ומעלה (שיעור 1). מאה כאלה בבקשה — 50ms. שני כלים:

  • batching (E18): אוספים בקשות "תביא משתמש X" שמגיעות יחד, ושולחים שאילתה אחת עם IN (…). זה DataLoader, והפתרון הכללי ל־N+1 (פרק 19). בכתיבה — אותו דבר: קליקים, צפיות ולוגים נכתבים באצוות.
  • Bloom filter (E25): לענות "בטוח לא קיים" בלי לשאול בכלל. מיליון שמות משתמש עם 1% טעות — 1.2MB (מדדתי 1.002% false positives), מול כ־35MB ל־Set עם אותם שמות. "לא" — עונים מיד; "אולי" — שואלים את המסד.

5. עקביות: מה מותר להיות ישן

ברגע שיש עותקים — replica, cache, CDN, אינדקס חיפוש — יש רגעים שבהם הם לא מסכימים עם המקור. CAP אומר שכשהרשת בין שרתים נקטעת, צריך לבחור: לענות (אולי עם מידע ישן) או לסרב. וגם בלי תקלות — כל עותק עולה בעדכניות. התשובה המעשית היא לא לבחור "עקבי" או "זמין" לכל המערכת, אלא לכל נתון (E04): קטלוג — דקה ישן זה בסדר; מלאי ברגע ההזמנה ונקודות לפני מימוש — רק מהמקור, בטרנזקציה; סטטוס אחרי תשלום — מהמקור למשתמש ששילם. כך בנית את חנות הקפה, גם אם לא קראנו לזה בשם.
