P26.5-E94 · מ־version 1 ל־version 2, בלי לשבור 🧠 הבנה רמה 2

P26.5-E95 · ‏seq: איזה אירוע ישן? 🧠 הבנה רמה 2

💡 רמז 1

‏seq קטן או שווה למה שכבר נשמר ← לזרוק.

💡 רמז 2

גרסה של השורה — version = version + 1 בכל עדכון.

✅ פתרון
  1. placed (1) ← shipped (3) ← paid (2) נזרק ← shipped (3) נזרק (כפילות) ← delivered (5) ← out-for-delivery (4) נזרק.
  2. delivered.
  3. עמודת version בשורת ההזמנה, שעולה בכל עדכון — באותה טרנזקציה שכותבת את שורת ה־outbox. כך ה־seq תמיד משקף את הסדר האמיתי במסד.
  4. את המעבר — אם צרכן אחר צריך לשלוח "התשלום התקבל" על כל paid, הוא חייב לראות אותו גם אם הגיע מאוחר. ‏projection של מצב — מותר לדלג; תגובה לאירוע — אסור.
⚠️ טעויות נפוצות
  • להשתמש ב־occurredAt במקום seq — שני שרתים עם שעונים שונים במילישניות, ואותה שנייה לשני אירועים.

P26.5-E96 · שני relays על אותה טבלת outbox 🧠 הבנה רמה 2

💡 רמז 1

שניהם קוראים את אותן 100 שורות.

💡 רמז 2

NOWAIT זורק; בלי כלום — מחכה; SKIP — מדלג.

✅ פתרון
  1. שניהם מפרסמים את אותן הודעות — כל אירוע פעמיים (בטוח עם consumer אידמפוטנטי, אבל בזבוז).
  2. כל relay נועל את השורות שבחר, ושורות נעולות מדולגות ע״י האחר — הם מתחלקים בעבודה בלי לחכות זה לזה. בלי SKIP — B מחכה ל־A, ואין מקביליות.
  3. B עלול לפרסם את paid לפני ש־A פרסם את placed. ‏E28: ה־relay לוקח רק את האירוע הבא של כל key (הקטן ביותר שלא פורסם) — כך שני relays לעולם לא מחזיקים שני אירועים של אותו key במקביל.
⚠️ טעויות נפוצות
  • לסמן published_at לפני ה־publish "כדי שהשני לא ייקח" — ונפילה ביניהם מאבדת את האירוע.

P26.5-E08 · מעטפת לאירועים 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

קודם המעטפת (data: z.unknown()), ואז סכמה לפי version.

💡 רמז 2

z.iso.datetime() ל־occurredAt, z.email() לכתובת.

✅ פתרון
// P26.5-E08: מעטפת לאירועים — id, סוג, גרסה, זמן — ואימות בצד שמקבל
import { randomUUID } from "node:crypto";
import { z } from "zod";

export interface EventEnvelope<T = unknown> {
  id: string;
  type: string;
  version: number;
  occurredAt: string;
  source: string;
  data: T;
}

export function makeEvent<T>(type: string, version: number, data: T, { id = randomUUID(), now = new Date(), source = "coffee-api" } = {}): EventEnvelope<T> {
  return { id, type, version, occurredAt: now.toISOString(), source, data };
}

const envelope = z.object({
  id: z.string().min(1),
  type: z.string().min(1),
  version: z.number().int().positive(),
  occurredAt: z.iso.datetime(),
  source: z.string().min(1),
  data: z.unknown(),
});

const placedV1 = z.object({ orderId: z.number().int().positive(), email: z.email(), totalCents: z.number().int().positive() });
const placedV2 = z.object({
  orderId: z.number().int().positive(),
  email: z.email(),
  total: z.object({ amountCents: z.number().int().positive(), currency: z.string().length(3) }),
});
export type OrderPlaced = z.infer<typeof placedV2>;

// מקבל כל גרסה שאנחנו מכירים, ומחזיר תמיד את הצורה העדכנית (v2)
export function parseOrderPlaced(raw: string): EventEnvelope<OrderPlaced> {
  let json: unknown;
  try {
    json = JSON.parse(raw);
  } catch {
    throw new Error("לא JSON");
  }
  const env = envelope.parse(json);
  if (env.type !== "order.placed") throw new Error(`סוג לא צפוי: ${env.type}`);
  if (env.version === 1) {
    const d = placedV1.parse(env.data);
    return { ...env, version: 2, data: { orderId: d.orderId, email: d.email, total: { amountCents: d.totalCents, currency: "ILS" } } };
  }
  if (env.version === 2) return { ...env, data: placedV2.parse(env.data) };
  throw new Error(`גרסה לא מוכרת: ${env.version}`);
}

למה שתי גרסאות? כי אי אפשר לעדכן את כל ה־producers וה־consumers באותה שנייה. הכלל: consumer מתעדכן קודם (מקבל גם v1 וגם v2), ורק אחר כך ה־producer מתחיל לשלוח v2. ובחברות עם הרבה צוותים — Schema Registry שאוכף את זה.

P26.5-E13 · projection מזרם לא מסודר 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

ההשוואה היא ל־seq השמור — לא לסדר ההגעה.

💡 רמז 2

status = הסוג בלי order..

✅ פתרון
// P26.5-E13: projection — מצב ההזמנות מתוך זרם אירועים (עם כפילויות ואי־סדר)
export interface OrderEvent {
  orderId: number;
  seq: number; // מספר רץ לכל הזמנה: 1, 2, 3…
  type: "order.placed" | "order.paid" | "order.shipped" | "order.cancelled";
}

export interface OrderView {
  status: "placed" | "paid" | "shipped" | "cancelled";
  seq: number;
}

const STATUS = { "order.placed": "placed", "order.paid": "paid", "order.shipped": "shipped", "order.cancelled": "cancelled" } as const;

export function applyEvent(state: Map<number, OrderView>, e: OrderEvent): boolean {
  const cur = state.get(e.orderId);
  if (cur && e.seq <= cur.seq) return false; // כפילות, או אירוע ישן שהגיע מאוחר
  if (cur?.status === "cancelled") return false; // סופי
  state.set(e.orderId, { status: STATUS[e.type], seq: e.seq });
  return true;
}

export function project(events: OrderEvent[]) {
  const state = new Map<number, OrderView>();
  let applied = 0;
  for (const e of events) if (applyEvent(state, e)) applied++;
  return { state, applied, ignored: events.length - applied };
}

ה־seq מגיע מה־producer — מהמסד שלו (מספר גרסה בשורת ההזמנה, שעולה בכל עדכון). בלעדיו, consumer לא יכול לדעת ש־"paid" שהגיע עכשיו ישן מ־"shipped" שכבר ראה.

P26.5-E15 · consumer אידמפוטנטי 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

INSERT … ON CONFLICT DO NOTHING, ו־rowCount.

💡 רמז 2

שני consumers עם אותו eventId במקביל: ה־INSERT של השני מחכה לטרנזקציה של הראשון, ואז רואה שהשורה קיימת.

✅ פתרון
// P26.5-E15: consumer אידמפוטנטי — "טופל" נרשם באותה טרנזקציה עם הפעולה
import type { Pool } from "pg";

export interface PaymentEvent {
  eventId: string;
  orderId: number;
  amountCents: number;
}

export async function handlePaymentEvent(pool: Pool, e: PaymentEvent): Promise<"processed" | "duplicate"> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const mark = await client.query(
      "INSERT INTO processed_events (consumer, event_id) VALUES ('payments', $1) ON CONFLICT DO NOTHING",
      [e.eventId],
    );
    if (mark.rowCount === 0) {
      await client.query("ROLLBACK");
      return "duplicate"; // כבר טופל (או מטופל ממש עכשיו בטרנזקציה אחרת — ה־INSERT חיכה לה)
    }
    await client.query("INSERT INTO payments (order_id, amount_cents, event_id) VALUES ($1, $2, $3)", [e.orderId, e.amountCents, e.eventId]);
    const upd = await client.query("UPDATE orders SET status = 'paid' WHERE id = $1", [e.orderId]);
    if (upd.rowCount !== 1) throw new Error(`הזמנה ${e.orderId} לא קיימת`);
    await client.query("COMMIT");
    return "processed";
  } catch (err) {
    await client.query("ROLLBACK").catch(() => {});
    throw err; // נכשל ← גם הסימון בוטל, ואפשר לנסות שוב
  } finally {
    client.release();
  }
}
⚠️ טעויות נפוצות
  • "קודם בודקים SELECT … WHERE event_id = ?, ואם אין — מטפלים" — שני consumers בודקים יחד, שניהם לא מוצאים, שניהם מחייבים. הסימון חייב להיות הפעולה הנועלת עצמה.
  • לסמן ב־Redis ולשמור במסד — שתי מערכות, אין טרנזקציה משותפת. קריסה ביניהן ← או כפול או חסר.

P26.5-E16 · retry עם backoff ו־jitter 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

attempt 1 ← תקרה 500; 2 ← 1000; 3 ← 2000…

💡 רמז 2

"full jitter" — לא תקרה ± קצת, אלא כל הטווח מ־0.

✅ פתרון
// P26.5-E16: מתי לנסות שוב, ומתי לוותר — exponential backoff עם jitter
export type RetryDecision = { action: "retry"; delayMs: number } | { action: "dead-letter"; reason: string };

export interface RetryOptions {
  baseMs?: number;
  maxMs?: number;
  maxAttempts?: number;
  random?: () => number;
}

export function isPermanent(err: any): boolean {
  if (err?.permanent === true) return true;
  const s = err?.status;
  return typeof s === "number" && s >= 400 && s < 500 && s !== 408 && s !== 429; // 4xx — לא ישתנה בניסיון חוזר
}

// attempt = כמה ניסיונות כבר נכשלו (1 אחרי הכישלון הראשון)
export function nextRetry(attempt: number, err: unknown, { baseMs = 500, maxMs = 30_000, maxAttempts = 5, random = Math.random }: RetryOptions = {}): RetryDecision {
  if (isPermanent(err)) return { action: "dead-letter", reason: "permanent" };
  if (attempt >= maxAttempts) return { action: "dead-letter", reason: "max-attempts" };
  const cap = Math.min(maxMs, baseMs * 2 ** (attempt - 1));
  let delayMs = Math.floor(random() * cap); // "full jitter": אקראי בין 0 לתקרה — כדי שאלף consumers לא יחזרו באותה שנייה
  const retryAfter = (err as any)?.retryAfterMs;
  if (typeof retryAfter === "number" && retryAfter > delayMs) delayMs = Math.min(retryAfter, maxMs);
  return { action: "retry", delayMs };
}

למה jitter? שירות התשלומים נפל לדקה, ואלף consumers נכשלו יחד. בלי jitter — כולם חוזרים יחד אחרי 500ms, ושוב אחרי 1000ms: גלים שמפילים את השירות בדיוק כשהוא מנסה לקום ("thundering herd"). עם jitter — הניסיונות מתפזרים.

P26.5-E17 · transactional outbox 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

SELECT … WHERE published_at IS NULL ORDER BY id LIMIT $1 FOR UPDATE SKIP LOCKED.

💡 רמז 2

בתוך טרנזקציה: הנעילה מחזיקה עד ה־COMMIT.

✅ פתרון
// P26.5-E17: transactional outbox — ההזמנה והאירוע נשמרים יחד; relay שולח אחר כך
import type { Pool } from "pg";

export interface OutboxRow {
  id: number;
  topic: string;
  key: string;
  payload: any;
}

export async function placeOrder(pool: Pool, order: { email: string; totalCents: number }): Promise<number> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const { rows } = await client.query("INSERT INTO orders (email, total_cents) VALUES ($1, $2) RETURNING id", [order.email, order.totalCents]);
    const id = rows[0].id as number;
    await client.query("INSERT INTO outbox (topic, key, payload) VALUES ('orders', $1, $2)", [
      String(id),
      { type: "order.placed", orderId: id, email: order.email, totalCents: order.totalCents },
    ]);
    await client.query("COMMIT");
    return id;
  } catch (err) {
    await client.query("ROLLBACK").catch(() => {});
    throw err;
  } finally {
    client.release();
  }
}

export async function relayOutbox(pool: Pool, publish: (row: OutboxRow) => Promise<void>, { batch = 100 } = {}): Promise<number> {
  const client = await pool.connect();
  const sent: number[] = [];
  try {
    await client.query("BEGIN");
    const { rows } = await client.query(
      "SELECT id, topic, key, payload FROM outbox WHERE published_at IS NULL ORDER BY id LIMIT $1 FOR UPDATE SKIP LOCKED",
      [batch],
    );
    let failure: unknown = null;
    for (const r of rows) {
      try {
        await publish({ id: Number(r.id), topic: r.topic, key: r.key, payload: r.payload });
        sent.push(Number(r.id));
      } catch (err) {
        failure = err; // עוצרים: לשמור על הסדר. מה שנשלח — מסמנים
        break;
      }
    }
    if (sent.length) await client.query("UPDATE outbox SET published_at = now() WHERE id = ANY($1::bigint[])", [sent]);
    await client.query("COMMIT");
    if (failure) throw failure;
    return sent.length;
  } catch (err) {
    await client.query("ROLLBACK").catch(() => {});
    throw err;
  } finally {
    client.release();
  }
}

outbox נותן at-least-once: אם ה־relay שלח ונפל לפני ה־COMMIT — השורה תישלח שוב. לכן ה־consumer אידמפוטנטי (E15) — שני הדפוסים באים יחד. ובקנה מידה גדול, במקום relay שסורק — CDC (Debezium) שקורא את ה־WAL של PostgreSQL ושולח ל־Kafka.

  }
}

export async function relayOutbox(pool: Pool, publish: (row: any) => Promise<void>): Promise<number> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const { rows } = await client.query(
      // תיקון 3: FOR UPDATE SKIP LOCKED — שני relays במקביל לא לוקחים את אותן שורות
      "SELECT id, topic, key, payload FROM outbox WHERE published_at IS NULL ORDER BY id LIMIT 50 FOR UPDATE SKIP LOCKED",
    );
    for (const r of rows) {
      await publish(r);
      // תיקון 2: מסמנים אחרי ש־publish הצליח, לא לפני
      await client.query("UPDATE outbox SET published_at = now() WHERE id = $1", [r.id]);
    }
    await client.query("COMMIT");
    return rows.length;
  } catch (err) {
    await client.query("ROLLBACK").catch(() => {});
    throw err;
  } finally {
    client.release();
  }
}

בתיקון הזה, publish שנכשל באמצע מבטל (ROLLBACK) גם את הסימון של מה שכבר נשלח באותה ריצה — אז אלה יישלחו שוב. זה at-least-once, ובסדר — ה־consumers אידמפוטנטיים. E17 מראה גרסה שמסמנת את מה שהצליח.

// P26.5-E24: צינור ההזמנות של חנות הקפה ב־RabbitMQ
import type { Channel, ConfirmChannel } from "amqplib";

export interface PipelineNames {
  exchange: string;
  emailQueue: string;
  inventoryQueue: string;
  deadLetterExchange: string;
  deadLetterQueue: string;

export interface OrderPlaced {
  eventId: string;
  orderId: number;
  email: string;

export async function setupOrderPipeline(ch: Channel, n: PipelineNames): Promise<void> {
  await ch.assertExchange(n.exchange, "topic", { durable: true });
  await ch.assertExchange(n.deadLetterExchange, "fanout", { durable: true });

// publisher confirms: מחכים שה־broker אישר שקיבל (ושמר) — רק אז "נשלח"
export async function publishOrderPlaced(ch: ConfirmChannel, exchange: string, e: OrderPlaced): Promise<void> {
  ch.publish(exchange, "order.placed", Buffer.from(JSON.stringify(e)), {
    persistent: true,
    contentType: "application/json",
    messageId: e.eventId,
  });

}

export interface ProcessedStore {
  // true אם זו הפעם הראשונה (ונרשם), false אם כבר טופל
  markIfNew(consumer: string, eventId: string): Promise<boolean>;
  unmark(consumer: string, eventId: string): Promise<void>;
}

export function memoryStore(): ProcessedStore {
  const seen = new Set<string>();
  return {
    async markIfNew(c, id) {
      const k = `${c}:${id}`;
      if (seen.has(k)) return false;
      seen.add(k);
      return true;
    },
    async unmark(c, id) {
      seen.delete(`${c}:${id}`);
    },
  };
}

function isOrderPlaced(x: any): x is OrderPlaced {
  return (
    x && typeof x.eventId === "string" && Number.isInteger(x.orderId) && typeof x.email === "string" &&
    Array.isArray(x.items) && x.items.every((i: any) => Number.isInteger(i.productId) && Number.isInteger(i.quantity) && i.quantity > 0)
  );
}

// consumer אידמפוטנטי: אותו eventId פעמיים ← פעולה אחת. הודעה פגומה ← dead letter מיד
export async function startConsumer(
  ch: Channel,
  queue: string,
  name: string,
  store: ProcessedStore,
  handle: (e: OrderPlaced) => Promise<void>,
): Promise<string> {
  await ch.prefetch(10);
  const { consumerTag } = await ch.consume(queue, async (msg) => {
    if (!msg) return;
    let e: unknown;
    try {
      e = JSON.parse(msg.content.toString());
    } catch {
      return ch.nack(msg, false, false);
    }
    if (!isOrderPlaced(e)) return ch.nack(msg, false, false);
    if (!(await store.markIfNew(name, e.eventId))) return ch.ack(msg); // כפילות — כבר טופל
    try {
      await handle(e);
      ch.ack(msg);
    } catch {
      await store.unmark(name, e.eventId); // לא הצליח — שיוכל לנסות שוב
      ch.nack(msg, false, false);
    }
  });
  return consumerTag;
}

בלי confirms, publish חוזר כשההודעה נכנסה ל־buffer של הספרייה — לא כשהגיעה ל־broker. נפילה של הרשת באותו רגע ← ההזמנה נשמרה, האירוע לא. עם confirms — יודעים, ואפשר לנסות שוב (או: outbox, E17).

// P26.5-E25: אנליטיקה מ־Kafka ל־PostgreSQL — ה־offset נשמר באותה טרנזקציה עם התוצאה
import { Admin, Consumer, MessagesStreamModes, stringDeserializers } from "@platformatic/kafka";
import type { Pool } from "pg";
import { randomUUID } from "node:crypto";

export interface AggregatorOptions {
  brokers: string[];
  topic: string;
  pool: Pool;
  max: number;
}

async function partitionsOf(brokers: string[], topic: string): Promise<number[]> {
  const admin = new Admin({ clientId: "revenue-meta", bootstrapBrokers: brokers });
  try {
    const md = await admin.metadata({ topics: [topic] });
    return Array.from({ length: md.topics.get(topic)!.partitionsCount }, (_, i) => i);
  } finally {
    await admin.close();
  }
}

export async function runRevenueAggregator({ brokers, topic, pool, max }: AggregatorOptions): Promise<number> {
  const { rows } = await pool.query("SELECT partition, next_offset FROM consumer_offsets WHERE topic = $1", [topic]);
  const stored = new Map(rows.map((r: any) => [Number(r.partition), BigInt(r.next_offset)]));
  const offsets = (await partitionsOf(brokers, topic)).map((partition) => ({ topic, partition, offset: stored.get(partition) ?? 0n }));

  // group חד־פעמי לכל ריצה: ה־offsets של Kafka לא נקראים ולא נכתבים — האמת במסד
  const consumer = new Consumer({ groupId: `revenue-${topic}-${randomUUID()}`, clientId: "revenue", bootstrapBrokers: brokers, deserializers: stringDeserializers });
  const stream = await consumer.consume({ topics: [topic], mode: MessagesStreamModes.MANUAL, offsets, autocommit: false });
  let n = 0;
  try {
    for await (const m of stream) {
      const e = JSON.parse(m.value) as { orderId: number; totalCents: number; at: string };
      const client = await pool.connect();
      try {
        await client.query("BEGIN");
        await client.query(
          `INSERT INTO revenue_by_minute (minute, orders, revenue_cents) VALUES (date_trunc('minute', $1::timestamptz), 1, $2)
           ON CONFLICT (minute) DO UPDATE SET orders = revenue_by_minute.orders + 1, revenue_cents = revenue_by_minute.revenue_cents + EXCLUDED.revenue_cents`,
          [e.at, e.totalCents],
        );
        await client.query(
          `INSERT INTO consumer_offsets (topic, partition, next_offset) VALUES ($1, $2, $3)
           ON CONFLICT (topic, partition) DO UPDATE SET next_offset = EXCLUDED.next_offset`,
          [topic, m.partition, String(m.offset + 1n)],
        );
        await client.query("COMMIT"); // התוצאה וה־offset — יחד, או אף אחד
      } catch (err) {
        await client.query("ROLLBACK").catch(() => {});
        throw err;
      } finally {
        client.release();
      }
      if (++n >= max) break;
    }
  } finally {
    await stream.close().catch(() => {});
    await consumer.close();
  }
  return n;
}

זה הדפוס שמאחורי "exactly-once" אמיתי מול מסד: התוצאה וה"איפה עצרתי" נכתבים אטומית, אז אין מצב ביניים. הבודק מפיל את התהליך בשני מקומות שונים — ומימוש עם שתי טרנזקציות (קודם התוצאה, אחר כך ה־offset) נכשל באחד מהם: אירוע נספר פעמיים.

P26.5-E27 · בדיקות ל־decide: לנסות שוב או dead letter? 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

שלוש השהיות ראשונות מראות את הנוסחה (וגם שהחזקה מתחילה מ־0). לתקרה צריך שני צדדים: ניסיון שבו הנוסחה עוד מתחת ל־60,000 (6 ← 32,000), וניסיון שבו היא כבר מעל (7 ← 64,000, ולכן 60,000).

💡 רמז 2

לגבול של maxAttempts: ‏decide(4, 5) ← retry, ‏decide(5, 5) ← dead-letter. ל־reason: בדוק שמכיל את הודעת השגיאה (includes), ולא שהוא שווה למחרוזת מדויקת. ‏TypeScript ידרוש לבדוק קודם ש־action === "dead-letter" לפני שניגשים ל־reason.

✅ פתרון
// P26.5-E27 — הבדיקות
import { test } from "node:test";
import assert from "node:assert/strict";
import { decide } from "./P26.5-E27.ts";

const temporary = { retryable: true, message: "connection reset" };
const permanent = { retryable: false, message: "product 99 not found" };

test("השהיה שמכפילה את עצמה: 1000, 2000, 4000", () => {
  assert.deepEqual(decide(1, 10, temporary), { action: "retry", delayMs: 1000 });
  assert.deepEqual(decide(2, 10, temporary), { action: "retry", delayMs: 2000 });
  assert.deepEqual(decide(3, 10, temporary), { action: "retry", delayMs: 4000 });
});

test("תקרה של 60 שניות", () => {
  assert.deepEqual(decide(6, 20, temporary), { action: "retry", delayMs: 32_000 });
  assert.deepEqual(decide(7, 20, temporary), { action: "retry", delayMs: 60_000 });
  assert.deepEqual(decide(19, 20, temporary), { action: "retry", delayMs: 60_000 });
});

test("maxAttempts: הניסיון האחרון ← dead-letter, זה שלפניו ← retry", () => {
  assert.equal(decide(4, 5, temporary).action, "retry");
  const last = decide(5, 5, temporary);
  assert.equal(last.action, "dead-letter");
  assert.ok(last.action === "dead-letter" && last.reason.includes("connection reset"), "ה־reason כולל את הודעת השגיאה");
  assert.equal(decide(1, 1, temporary).action, "dead-letter", "maxAttempts של 1 — בלי ניסיון חוזר");
});

test("שגיאה קבועה ← dead-letter מיד", () => {
  const d = decide(1, 5, permanent);
  assert.equal(d.action, "dead-letter");
  assert.ok(d.action === "dead-letter" && d.reason.includes("product 99 not found"));
});

test("attempt לא תקין ← RangeError", () => {
  for (const bad of [0, -1, 1.5, NaN]) assert.throws(() => decide(bad, 5, temporary), RangeError, String(bad));
});

שלושה דברים כאן שקל לפספס. הגבול של maxAttempts: מימוש עם > במקום >= נותן ניסיון נוסף, ורק decide(5, 5) תופס אותו. התקרה משני הצדדים: בדיקה רק על 19 לא מבדילה בין תקרה של 30 שניות ל־60 בניסיון הנכון, ובדיקה רק על 6 לא תופסת מימוש בלי תקרה. ה־reason: מי שמסתכל על ה־DLQ בשלוש בלילה צריך לראות למה ההודעה שם.

includes ולא equal על ה־reason: הניסוח המדויק הוא פרט מימוש. מה שחשוב הוא שהמידע שם. בדיקה שמשווה מחרוזת שלמה נשברת בכל שינוי ניסוח, ומלמדת את הצוות להתעלם מבדיקות אדומות.

⚠️ טעויות נפוצות
  • לבדוק רק את 1, 2, 3 — שלושה מוטנטים (בלי תקרה, תקרה של 30 שניות, ו־>) עוברים.
  • assert.equal(d.reason, "נכשל 5 פעמים: connection reset") — עובד על הקוד הזה, אבל קושר את הבדיקה לניסוח.
  • לבדוק RangeError רק על 0 — שבר (1.5) עובר במימוש שבודק רק attempt < 1.

P26.5-E28 · האירוע הבא לכל מפתח ב־outbox 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

ב־CTE: כל השורות שלא פורסמו, ועליהן שני חלונות על אותה חלוקה: ROW_NUMBER() OVER (PARTITION BY topic, key ORDER BY id) AS rn ו־COUNT(*) OVER (PARTITION BY topic, key) AS pending. בשאילתה החיצונית: WHERE rn = 1.

💡 רמז 2

אי אפשר לכתוב WHERE rn = 1 באותה שאילתה שבה מחשבים את rn: ‏WHERE רץ לפני החלונות. לכן ה־CTE. ‏WHERE published_at IS NULL שייך ל־CTE, כדי שהחלונות יספרו רק ממתינים.

✅ פתרון
WITH pending AS (
  SELECT
    id, topic, key, event_type,
    ROW_NUMBER() OVER (PARTITION BY topic, key ORDER BY id) AS rn,
    COUNT(*) OVER (PARTITION BY topic, key) AS pending
  FROM outbox
  WHERE published_at IS NULL
)
SELECT topic, key, id AS next_id, event_type, pending
FROM pending
WHERE rn = 1
ORDER BY next_id;
  topic   |   key   | next_id |   event_type    | pending
----------+---------+---------+-----------------+---------
 orders   | order-2 |       4 | OrderPaid       |       2
 payments | pay-9   |       5 | PaymentCaptured |       2
 orders   | order-1 |       6 | OrderShipped    |       2
 orders   | order-3 |       8 | OrderPlaced     |       1
 audit    | order-1 |      11 | OrderViewed     |       1
(5 rows)

order-1 ב־orders: אירועים 1 ו־3 כבר פורסמו, ולכן הבא בתור הוא 6, ואחריו עוד אחד (10). ב־audit יש גם order-1, אבל זה רצף אחר, עם סדר משלו. ‏PARTITION BY key לבד היה מערבב ביניהם: ‏pending של 3, ו־OrderViewed היה נעלם.

למה לא GROUP BY topic, key עם MIN(id)? ‏MIN(id) נותן את next_id, אבל לא את event_type שלו. בשביל זה צריך JOIN חזרה לטבלה. ‏ROW_NUMBER נותן את כל השורה הראשונה בכל קבוצה בשלב אחד. זה הדפוס של "top-N לכל קבוצה" מ־P18-E28.

ב־relay אמיתי השאילתה נגמרת ב־FOR UPDATE SKIP LOCKED (שיעור 5), כדי ששני relays לא יפרסמו את אותו אירוע. אבל עם פונקציות חלון אי אפשר לנעול. לכן בפועל נועלים קודם את השורות (SELECT ... FOR UPDATE SKIP LOCKED), ובוחרים מהן.

⚠️ טעויות נפוצות
  • לסנן published_at IS NULL בשאילתה החיצונית, אחרי החלון — ‏rn = 1 הוא האירוע הראשון שאי פעם נכתב, והוא כבר פורסם.
  • PARTITION BY key בלי topic — רצפים של topics שונים מתערבבים.
  • ORDER BY created_at בחלון — שני אירועים באותה מילישנייה מקבלים סדר מקרי. ‏id (‏bigserial) מגדיר סדר כתיבה חד־משמעי.

// P26.5-E100: upcaster — מ־v1 ל־v2 בקריאה
type V2Data = { orderId: number; email: string; total: { amountCents: number; currency: string } };
type V2 = { type: "order.placed"; version: 2; data: V2Data };

export function upcast(e: { type: string; version: number; data: unknown }): V2 {
  if (e.type !== "order.placed") throw new Error(`סוג לא נתמך: ${e.type}`);
  switch (e.version) {
    case 2:
      return structuredClone(e) as V2;
    case 1: {
      const d = e.data as { orderId: number; email: string; total: number };
      return { ...structuredClone(e), type: "order.placed", version: 2, data: { ...d, total: { amountCents: Math.round(d.total * 100), currency: "ILS" } } };
    }
    default:
      throw new Error(`גרסה לא נתמכת: ${e.version}`);
  }
}

כשתגיע v3, מוסיפים case 2 שמעלה ל־3, ו־v1 עובר דרך שניהם — כל שלב קטן ונבדק לבד. הלוגיקה העסקית מכירה רק את הגרסה האחרונה, וזה מה שמחזיק את הקוד פשוט שנים.

⚠️ טעויות נפוצות
  • Math.floor(total * 100) — ‏0.29 * 100 הוא 28.999999999999996, ויוצא 28.
  • להעלות גרסה "לא מוכרת" כאילו היא האחרונה — v3 מהעתיד נקרא לא נכון בשקט.
