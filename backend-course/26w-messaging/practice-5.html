אירוע עובר בין שירותים שנכתבים ומתעדכנים בנפרד — לכן כל אירוע עטוף ב"מעטפת" קבועה. ב־P26.5-E08.ts:

P26.5-E16 · retry עם backoff ו־jitter 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 20 דק׳ידע נדרש: שיעור 5

ב־P26.5-E16.ts:

  • isPermanent(err) — err.permanent === true, או status 4xx — חוץ מ־408 ו־429.
  • nextRetry(attempt, err, { baseMs, maxMs, maxAttempts, random }) — שגיאה קבועה ← { action: "dead-letter", reason: "permanent" }; attempt ≥ maxAttempts ← reason: "max-attempts"; אחרת { action: "retry", delayMs }: תקרה = min(maxMs, baseMs × 2^(attempt−1)), השהיה = floor(random() × תקרה); ואם יש err.retryAfterMs גדול יותר — הוא (עד maxMs).

P26.5-E17 · transactional outbox 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 30 דק׳ידע נדרש: שיעור 5

הבעיה: "שומרים הזמנה במסד ושולחים אירוע ל־broker" — שתי מערכות. אם שומרים ונופלים לפני השליחה — אין אירוע. אם שולחים ואז השמירה נכשלת — אירוע על הזמנה שלא קיימת. הפתרון: האירוע נכתב לטבלת outbox באותה טרנזקציה, ותהליך נפרד (relay) שולח. ב־P26.5-E17.ts:

  • placeOrder(pool, { email, totalCents }) — הזמנה + שורת outbox (topic 'orders', key = id, payload { type: "order.placed", orderId, email, totalCents }) בטרנזקציה אחת; מחזירה id.
  • relayOutbox(pool, publish, { batch }) — לוקח עד batch שורות שלא נשלחו, לפי הסדר, נועל אותן כך ש־relay מקביל ידלג עליהן, שולח אחת־אחת, ומסמן published_at. publish נכשל ← עוצר, מסמן את מה שכבר נשלח, וזורק.

P26.5-E24 · אתגר: צינור ההזמנות ב־RabbitMQ 🤖

💻 כתיבת קוד 🤖רמה 5⏱ 60 דק׳ידע נדרש: שיעור 5

הזמנה בחנות הקפה מפעילה שני שירותים — מייל ומלאי — דרך RabbitMQ. ב־P26.5-E24.ts:

  • setupOrderPipeline(ch, names) — topic exchange, תור למייל ותור למלאי (שניהם מקבלים order.placed), ו־dead letter exchange + תור לשניהם.
  • publishOrderPlaced(confirmCh, exchange, event) — persistent, JSON, messageId = eventId, וחוזרת רק אחרי שה־broker אישר (publisher confirms).
  • memoryStore() — markIfNew(consumer, eventId) ו־unmark, בזיכרון (בפרודקשן — טבלה כמו ב־E15).
  • startConsumer(ch, queue, name, store, handle) — הודעה פגומה (JSON, או חסרים שדות, או כמות ≤ 0) ← dead letter בלי handle; eventId שכבר טופל ע״י אותו consumer ← ack בלי handle; handle נכשל ← unmark ו־dead letter.

P26.5-E27 · בדיקות ל־decide: לנסות שוב או dead letter? 🤖

💻 כתיבת קוד 🤖🔁 חזרהרמה 3⏱ 25 דק׳ידע נדרש: שיעור 5

🔁 חזרה על כתיבת בדיקות (פרק 22): גבולות, union של תוצאות, וטבלת קלטים לא תקינים. ב־26w-messaging/starter/P26.5-E27.ts יש decide(attempt, maxAttempts, error), שמחליטה מה לעשות בהודעה שהטיפול בה נכשל:

  • attempt — מספר הניסיון שנכשל עכשיו (1 = הראשון). לא שלם או קטן מ־1 ← RangeError.
  • שגיאה שאינה retryable ← { action: "dead-letter", reason } מיד. ה־reason כולל את הודעת השגיאה.
  • הגענו ל־maxAttempts ניסיונות ← dead-letter, גם כאן עם הודעת השגיאה ב־reason.
  • אחרת ← { action: "retry", delayMs }: ‏1000ms × 2attempt−1 (1000, 2000, 4000...), ולכל היותר 60,000.

כתוב בדיקות ב־P26.5-E27.spec.ts, מקובץ ריק. הבודק מריץ אותן על הקוד התקין, על שני מימושים תקינים אחרים, ועל 11 גרסאות עם באג. את P26.5-E27.ts לא משנים.

P26.5-E28 · האירוע הבא לכל מפתח ב־outbox 🤖

💻 כתיבת קוד 🤖🔁 חזרהרמה 2⏱ 20 דק׳ידע נדרש: שיעור 5

🔁 חזרה על CTE ופונקציות חלון: ‏ROW_NUMBER ו־COUNT עם PARTITION BY (‏P17-E27, ‏P18-E28). ה־relay של ה־outbox (שיעור 5) חייב לשמור סדר לכל מפתח: אסור לפרסם OrderShipped לפני OrderPaid של אותה הזמנה. לכן הוא שואל: "מה האירוע הבא לכל מפתח, וכמה ממתינים אחריו?". בטבלה outbox(id, topic, key, event_type, created_at, published_at) כתוב שאילתה עם העמודות:

  • topic, ‏key — שורה אחת לכל צירוף שיש לו אירועים שלא פורסמו (published_at IS NULL). אותו key ב־topic אחר הוא רצף נפרד.
  • next_id — ה־id הקטן ביותר מבין הממתינים, ו־event_type שלו.
  • pending — כמה אירועים ממתינים לאותו topic ו־key.

מיון: next_id.
