P26.5-E01 · איזה כלי? 🧠 הבנה רמה 1

💡 רמז 1

שתי שאלות מכריעות: האם ההודעה "נמחקת" אחרי שטופלה (תור), או נשארת כדי שאחרים יקראו גם, ושוב (log)? ומי מנהל את התשתית?

💡 רמז 2

Kafka שומר את האירועים לפי זמן (retention) — לא לפי "מישהו קרא".

✅ פתרון
  1. BullMQ — כבר יש Redis, ו־BullMQ נותן delayed jobs ו־retries מובנים. להוסיף RabbitMQ או Kafka בשביל זה — תשתית בלי סיבה.
  2. RabbitMQ (fanout/topic exchange — תור לכל שירות) או Kafka (topic אחד, consumer group לכל שירות). ב־AWS: SNS ← SQS (תור SQS לכל שירות שמנוי ל־topic של SNS).
  3. Kafka. נפח גבוה, כמה צרכנים עצמאיים, ו־replay: מזיזים את ה־offset של ה־group אחורה ומעבדים שוב. בתור רגיל ההודעות כבר נמחקו.
  4. SQS — מנוהל לגמרי, משלמים לפי בקשות, DLQ מובנה.
  5. RabbitMQ עם topic exchange: ישראל — order.*.il; ביטולים — order.cancelled.* (E03, E06). "מחו״ל" קשה יותר: binding לא יודע להגיד "הכול חוץ מ־il" — אז מכניסים את זה למפתח (order.created.abroad), או משתמשים ב־headers exchange. ניתוב גמיש הוא החוזקה של RabbitMQ.
⚠️ טעויות נפוצות
  • "Kafka כי זה מה שחברות גדולות משתמשות" — Kafka דורש תפעול (או שירות מנוהל יקר), ותור עבודות פשוט לא צריך אותו.

P26.5-E02 · מה קורה כשה־consumer נופל? 🧠 הבנה רמה 1

💡 רמז 1

הודעה שלא אושרה — חוזרת (לתור, או אחרי visibility timeout, או מה־offset האחרון).

💡 רמז 2

החיוב קורה בעולם החיצוני — ה־broker לא יודע עליו.

✅ פתרון
  1. ההודעה אושרה ונמחקה, החיוב לא קרה ← הלקוח לא חויב, לתמיד. זה at-most-once: כל הודעה מטופלת לכל היותר פעם אחת — לפעמים אפס.
  2. החיוב קרה, ה־ack לא ← ההודעה חוזרת ← חיוב כפול. זה at-least-once: לפחות פעם אחת — לפעמים יותר.
  3. הכול בסדר.

at-least-once הוא ברירת המחדל הנכונה כמעט תמיד (עדיף כפול מחסר), בתנאי שה־consumer אידמפוטנטי: אותה הודעה פעמיים ← אותה תוצאה כמו פעם אחת. איך: מזהה ייחודי לכל אירוע, ו"כבר טיפלתי ב־X" שנשמר באותה טרנזקציה עם הפעולה (E15) — ולספק התשלומים שולחים idempotency key (פרק 21). "exactly-once" של Kafka חל רק בתוך Kafka (קריאה ← כתיבה ל־topic אחר); ברגע שיש צד שלישי — מסד, API, מייל — חוזרים לאידמפוטנטיות.

P26.5-E33 · ‏ack לפני או אחרי — לכל נקודת נפילה 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

תרחיש: crashAfter = ‏0, 1, 2 (כמה צעדים בוצעו לפני הנפילה), או "בלי נפילה".

💡 רמז 2

אם ה־ack לא בוצע לפני הנפילה ← מוסיפים ריצה מלאה אחת (‏handle עוד פעם).

✅ פתרון
// P26.5-E33: ack לפני או אחרי — לכל נקודת נפילה
type Step = "ack" | "handle";

export function crashOutcomes(order: Step[]) {
  if (order.length !== 2 || !order.includes("ack") || !order.includes("handle")) throw new RangeError("צריך בדיוק ack ו־handle");
  const counts: number[] = [];
  for (const crashAfter of [0, 1, 2, null]) {
    const done = crashAfter === null ? order : order.slice(0, crashAfter);
    let handled = done.filter((s) => s === "handle").length;
    if (crashAfter !== null && !done.includes("ack")) handled += 1; // נמסרת שוב, והפעם הכול עובר
    counts.push(handled);
  }
  const minHandled = Math.min(...counts);
  const maxHandled = Math.max(...counts);
  const guarantee = minHandled === 0 ? "at-most-once" : maxHandled > 1 ? "at-least-once" : "exactly-once";
  return { minHandled, maxHandled, guarantee } as const;
}

שני סדרים, שתי הבטחות, ואף פעם לא exactly-once: ack קודם — יש תרחיש של 0; handle קודם — יש תרחיש של 2. זו הטבלה מהשיעור כקוד. "בדיוק פעם אחת" מגיע רק מבחוץ — מ־consumer אידמפוטנטי.

⚠️ טעויות נפוצות
  • לשכוח את התרחיש "נפל אחרי שני הצעדים" — הוא לא משנה כאן, אבל בלעדיו קל לפספס את המקרה ההפוך.

P26.5-E34 · תור בזיכרון: ‏ack, ‏nack ונפילה 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

מערך לתור, ו־Map<tag, { consumer, msg }> ל־unacked.

💡 רמז 2

"לראש בסדר המקורי": ‏queue.unshift(...msgs) — עם מערך בסדר הקבלה.

✅ פתרון
// P26.5-E34: תור בזיכרון — ack, nack ונפילה
export class MemoryQueue<T> {
  #queue: T[] = [];
  #unacked = new Map<number, { consumer: string; msg: T }>();
  #nextTag = 1;

  push(msg: T) {
    this.#queue.push(msg);
  }
  size() {
    return this.#queue.length;
  }
  receive(consumer: string) {
    if (this.#queue.length === 0) return null;
    const msg = this.#queue.shift() as T;
    const tag = this.#nextTag++;
    this.#unacked.set(tag, { consumer, msg });
    return { tag, msg };
  }
  #take(tag: number) {
    const e = this.#unacked.get(tag);
    if (!e) throw new Error(`tag לא מוכר: ${tag}`);
    this.#unacked.delete(tag);
    return e;
  }
  ack(tag: number) {
    this.#take(tag);
  }
  nack(tag: number, requeue: boolean) {
    const e = this.#take(tag);
    if (requeue) this.#queue.unshift(e.msg);
  }
  crash(consumer: string) {
    const mine = [...this.#unacked].filter(([, e]) => e.consumer === consumer).sort(([a], [b]) => a - b);
    for (const [tag] of mine) this.#unacked.delete(tag);
    this.#queue.unshift(...mine.map(([, e]) => e.msg));
    return mine.length;
  }
  unacked(consumer: string) {
    return [...this.#unacked.values()].filter((e) => e.consumer === consumer).length;
  }
}

זה בדיוק מה ש־RabbitMQ עושה עם חיבור שנסגר: ה־unacked חוזרות, ו־consumer אחר מקבל אותן. ו־nack עם requeue לראש התור הוא הסיבה שהודעה פגומה יכולה "לתקוע" worker בלולאה (‏E20).

⚠️ טעויות נפוצות
  • להעביר הודעה ל־unacked רק אחרי שה־consumer "סיים" — אז אין מה להחזיר בנפילה.

P26.5-E35 · ‏log בזיכרון: ‏partitions, ‏offsets ו־groups 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

💡 רמז 2

‏slice(from, from + max), ו־offset של כל אחת: from + i.

✅ פתרון
// P26.5-E35: log בזיכרון — partitions, offsets ו־groups
type Entry = { key: string; value: string };

export class MemoryLog {
  #parts: Entry[][];
  #committed = new Map<string, number>();

  constructor(partitions: number) {
    this.#parts = Array.from({ length: partitions }, () => []);
  }
  #partitionOf(key: string) {
    let h = 0;
    for (let i = 0; i < key.length; i++) h += key.charCodeAt(i);
    return h % this.#parts.length;
  }
  append(key: string, value: string) {
    const partition = this.#partitionOf(key);
    const offset = this.#parts[partition].push({ key, value }) - 1;
    return { partition, offset };
  }
  read(group: string, partition: number, max: number) {
    const from = this.#committed.get(`${group}:${partition}`) ?? 0;
    return this.#parts[partition].slice(from, from + max).map((e, i) => ({ offset: from + i, ...e }));
  }
  commit(group: string, partition: number, nextOffset: number) {
    this.#committed.set(`${group}:${partition}`, nextOffset);
  }
  lag(group: string) {
    return this.#parts.reduce((sum, p, i) => sum + p.length - (this.#committed.get(`${group}:${i}`) ?? 0), 0);
  }
}

ההבדל מהתור (E34) נראה בקוד: אין delete. קריאה לא משנה את ה־log, ולכל group יש רק מספר — איפה הוא עצר. "replay" הוא commit למספר קטן יותר.

⚠️ טעויות נפוצות
  • ש־read יזיז את ה־offset — אז קריסה בין הקריאה לטיפול מאבדת הודעות (at-most-once).

P26.5-E36 · ‏handler אידמפוטנטי — גם במקביל 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

‏done = new Set<string>(), ו־running = new Map<string, Promise<void>>().

💡 רמז 2

מי שמחכה ל־Promise של אחר ונכשל — כאן: אם הראשון נכשל, השני ינסה בעצמו.

✅ פתרון
// P26.5-E36: handler אידמפוטנטי — גם במקביל
type Msg<T> = { id: string } & T;

export function idempotent<T>(handler: (msg: Msg<T>) => Promise<void>) {
  const done = new Set<string>();
  const running = new Map<string, Promise<void>>();
  return async function handle(msg: Msg<T>): Promise<"handled" | "duplicate"> {
    if (done.has(msg.id)) return "duplicate";
    const inFlight = running.get(msg.id);
    if (inFlight) {
      try {
        await inFlight;
        return "duplicate";
      } catch {
        return handle(msg); // הראשון נכשל — ננסה בעצמנו
      }
    }
    const p = handler(msg);
    running.set(msg.id, p);
    try {
      await p;
      done.add(msg.id);
      return "handled";
    } finally {
      running.delete(msg.id);
    }
  };
}

זה עובד בתוך תהליך אחד. עם שני workers ההגנה חייבת להיות במקום משותף — טבלה עם מפתח ראשי, באותה טרנזקציה של הפעולה (שיעור 5). ו־Set שגדל לנצח — בפועל שומרים חלון (‏E84).

⚠️ טעויות נפוצות
  • לסמן את ה־id לפני ההרצה — handler שנכשל לא ינוסה שוב לעולם.

P26.5-E37 · הודעה פגומה לא חוסמת את התור 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

תור של { msg, attempts }, ולולאה while (queue.length).

💡 רמז 2

‏queue.push(item) אחרי כישלון — לסוף.

✅ פתרון
// P26.5-E37: הודעה פגומה לא חוסמת את התור
export async function processAll<T extends { id: string }>(messages: T[], handler: (m: T) => Promise<void>, maxAttempts: number) {
  const queue = messages.map((msg) => ({ msg, attempts: 0 }));
  const done: string[] = [];
  const dead: { id: string; attempts: number; error: string }[] = [];
  while (queue.length) {
    const item = queue.shift()!;
    try {
      await handler(item.msg);
      done.push(item.msg.id);
    } catch (e) {
      item.attempts++;
      if (item.attempts >= maxAttempts) dead.push({ id: item.msg.id, attempts: item.attempts, error: (e as Error).message });
      else queue.push(item);
    }
  }
  return { done, dead };
}

שני הרעיונות של "הודעה רעלה" (poison message): לא לנסות אותה בלולאה הדוקה בראש התור, ולא לנצח — אחרי N ניסיונות היא הולכת הצידה (DLQ), עם הסיבה, כדי שאדם יסתכל.

⚠️ טעויות נפוצות
  • להחזיר לראש התור — הודעה פגומה אחת מעסיקה את ה־worker maxAttempts פעמים ברצף, וכל השאר מחכים.

P26.5-E38 · איפה הסדר נשבר? 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

💡 רמז 2

✅ פתרון
// P26.5-E38: איפה הסדר נשבר?
export function outOfOrderKeys(delivered: { key: string; seq: number }[]) {
  const max = new Map<string, number>();
  const bad = new Set<string>();
  for (const { key, seq } of delivered) {
    const m = max.get(key);
    if (m !== undefined && seq <= m) bad.add(key);
    else max.set(key, seq);
  }
  return [...bad].sort();
}

‏"סדר מובטח רק בגבולות" — וזה הכלי לבדוק אם הגבולות שבחרת מספיקים: מריצים את הזרם האמיתי, ורואים אילו ישויות קיבלו אירועים לא בסדר.

⚠️ טעויות נפוצות

P26.5-E39 · מה עולה שרשרת סינכרונית? 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

‏reduce לסכום ולמכפלה.

💡 רמז 2

‏Math.round(x * 1e6) / 1e6.

✅ פתרון
// P26.5-E39: מה עולה שרשרת סינכרונית?
type Call = { ms: number; availability: number };
const r6 = (x: number) => Math.round(x * 1e6) / 1e6;

export function syncChain(calls: Call[]) {
  return {
    latencyMs: calls.reduce((s, c) => s + c.ms, 0),
    availability: r6(calls.reduce((p, c) => p * c.availability, 1)),
  };
}

export function withBroker(publish: Call) {
  return { latencyMs: publish.ms, availability: r6(publish.availability) };

✅ פתרון
// P26.5-E40: מי מקבל מה — תור מול log
export function deliver(model: "queue" | "log", groups: Record<string, string[]>, messages: string[]) {
  const out: Record<string, string[]> = {};
  for (const c of Object.values(groups).flat()) out[c] = [];
  const spread = (consumers: string[]) => messages.forEach((m, i) => consumers.length && out[consumers[i % consumers.length]].push(m));
  if (model === "queue") spread(Object.values(groups).flat());
  else for (const consumers of Object.values(groups)) spread(consumers);
  return out;
}

בתור — שני שירותים שקוראים מאותו תור "גונבים" הודעות זה מזה: המיילים מקבלים חצי, האנליטיקה חצי. ב־log — כל שירות מקבל הכול, ובתוך שירות העבודה מתחלקת. (ב־RabbitMQ פותרים את זה עם תור לכל שירות ו־exchange שמעתיק — שיעור 2.)

⚠️ טעויות נפוצות

import express from "express";
import { z } from "zod";

type Event = { id: string; type: string; data: unknown };
const schema = z.object({
  email: z.string().includes("@"),
  items: z.array(z.object({ productId: z.number().int().positive(), qty: z.number().int().positive() })).min(1),
});

export function ordersApp({ publish, newId }: { publish: (e: Event) => Promise<void>; newId: () => string }) {
  const app = express();
  app.use(express.json());
  app.post("/orders", async (req, res) => {
    const r = schema.safeParse(req.body);
    if (!r.success) return res.status(400).json({ error: "הזמנה לא תקינה" });
    const id = newId();
    try {
      await publish({ id, type: "order.placed", data: { email: r.data.email, items: r.data.items } });
    } catch {
      return res.status(503).json({ error: "לא הצלחנו לקבל את ההזמנה, נסה שוב" });
    }
    res.status(202).json({ orderId: id });
  });
  return app;
}

💡 רמז 2

✅ פתרון
// P26.5-E45: להודיע לכולם ב־HTTP — ולמה זה כואב
type Service = { name: string; call: (event: unknown) => Promise<void> };

export async function notifyAll(services: Service[], event: unknown, timeoutMs: number) {
  const timers: NodeJS.Timeout[] = [];
  const withTimeout = (p: Promise<void>) =>
    Promise.race([p, new Promise<never>((_, reject) => timers.push(setTimeout(() => reject(new Error("timeout")), timeoutMs)))]);
  const results = await Promise.allSettled(services.map((s) => withTimeout(Promise.resolve().then(() => s.call(event)))));
  timers.forEach(clearTimeout);
  return results.map((r, i) =>
    r.status === "fulfilled" ? { name: services[i].name, ok: true } : { name: services[i].name, ok: false, error: (r.reason as Error).message },
  );
}

גם בגרסה הטובה ביותר — במקביל, עם timeout, בלי להפיל — נשארות שאלות שאין להן תשובה טובה כאן: מה עושים עם שירות שנכשל? מי ינסה שוב, ומתי? מה עם שירות חדש? broker עונה על כולן: הוא שומר, הצרכנים מנסים שוב בקצב שלהם, ושירות חדש פשוט מאזין.

⚠️ טעויות נפוצות
  • Promise.all — שירות אחד שנכשל מפיל את כל ההודעה, ולא יודעים מי כן קיבל.
  • for … await — הזמן הכולל הוא סכום של כולם.

-- P26.5-E46: log ב־SQL — מה ה־group קורא עכשיו?
SELECT g.group_name,
       MIN(e.id) AS next_id,
       COUNT(e.id) AS lag
FROM group_offsets g
LEFT JOIN events e ON e.id > g.last_id
GROUP BY g.group_name
ORDER BY lag DESC, g.group_name;

זה Kafka בקטן: הטבלה היא ה־partition, ה־id הוא ה־offset, ו־group_offsets הוא ה־committed offset. ואכן, outbox עם relay (שיעור 5) הוא log כזה בדיוק.
