שיעור 4 — Kafka: partitions, keys ו־consumer groups

⏱ ~55 דקות

🎯 בשיעור הזה
  • Kafka כ־log: topic, partition, offset, retention.
  • keys: מה קובע partition, ולמה סדר מובטח רק בתוכו.
  • consumer groups: חלוקת partitions, rebalance, ו־offsets לכל group.
  • commit אחרי טיפול, replay, ו־consumer lag.

1. log מחולק

Kafka שומר topics. כל topic מחולק ל־partitions, וכל partition הוא קובץ שרק מוסיפים לסופו: כל הודעה מקבלת offset — מספר רץ בתוך ה־partition. הודעות לא נמחקות כשקוראים אותן; הן נמחקות לפי retention (למשל 7 ימים, או לפי גודל). קריאה לא משנה כלום ב־topic — consumer רק זוכר "עד איפה הגעתי".

2. keys וסדר

producer שולח הודעה עם key (לא חובה, אבל כמעט תמיד). ה־partition נקבע מ־hash של ה־key, אז כל ההודעות עם אותו key נכנסות לאותו partition — לפי הסדר. בלי key — ההודעות מתפזרות (round-robin), וסדר אין (E04, E22).

מה בוחרים כ־key? את הישות שהסדר שלה חשוב: מספר הזמנה, מזהה משתמש, מזהה חשבון. "paid" חייב להיקרא לפני "shipped" של אותה הזמנה; בין הזמנות שונות — לא אכפת לנו, וזה מה שמאפשר מקביליות.

⚠️ hash של מי?

הלקוח (לא ה־broker) מחשב את ה־partition. ל־Java client יש partitioner ידוע (murmur2), ולקוחות בשפות אחרות לא תמיד מחשבים בדיוק כמוהו — @platformatic/kafka, למשל, מספק compatibilityPartitioner בדיוק בשביל זה. אם producers בשתי שפות כותבים לאותו topic עם אותם keys — ודאו שהם מחשבים partition באותה דרך, אחרת "אותו key ← אותו partition" נשבר.

ועוד אמת לא נעימה: גם producer יכול לכתוב כפול. אם ה־broker קיבל את ההודעה אבל האישור לא חזר (timeout), ה־producer שולח שוב. בפיתוח היחידה הזו ראינו את זה קורה מול topic שזה עתה נוצר — אותן הודעות פעמיים ב־partition. הפתרון בצד ה־producer: idempotent: true — ה־broker מזהה ניסיון חוזר לפי מספר רץ, ולא כותב פעמיים.

3. consumer groups ו־offsets

consumers מתאגדים ב־group (לפי groupId). בתוך group, כל partition שייך ל־consumer אחד בדיוק — כך העבודה מתחלקת. consumer מצטרף או נופל ← rebalance: ה־partitions מחולקים מחדש. ו־group שונה = קורא עצמאי: שירות המיילים ושירות האנליטיקה קוראים את אותו topic, כל אחד מהמקום שלו.

"המקום" הוא ה־committed offset — לכל group ולכל partition, ה־offset הבא שצריך לקרוא. Kafka שומר אותו בשבילך (בתוך topic פנימי). והנה כל זה בהרצה אמיתית: שני groups קוראים את אותן ארבע הודעות, ואז "מחזירים אחורה" את אחד מהם:

import { Admin, Consumer, Producer, MessagesStreamModes, MessagesStreamFallbackModes, stringSerializers, stringDeserializers } from "@platformatic/kafka";

const brokers = [process.env.KAFKA_BROKERS ?? "localhost:9092"];
const topic = `lesson4-${Date.now()}`;
const admin = new Admin({ clientId: "lesson4", bootstrapBrokers: brokers });
await admin.createTopics({ topics: [topic], partitions: 1, replicas: 1 });
const producer = new Producer({ clientId: "lesson4", bootstrapBrokers: brokers, serializers: stringSerializers, idempotent: true });
await producer.send({ messages: ["placed", "paid", "shipped", "delivered"].map((value) => ({ topic, key: "order-42", value })) });

async function read(groupId: string, max: number) {
  const consumer = new Consumer({ groupId, clientId: groupId, bootstrapBrokers: brokers, deserializers: stringDeserializers });
  const stream = await consumer.consume({
    topics: [topic],
    mode: MessagesStreamModes.COMMITTED,               // מאיפה שה־group עצר
    fallbackMode: MessagesStreamFallbackModes.EARLIEST, // group חדש ← מההתחלה
    autocommit: false,
  });
  const got: string[] = [];
  for await (const m of stream) {
    got.push(`${m.offset}:${m.value}`);
    await m.commit(); // אחרי הטיפול
    if (got.length >= max) break;
  }
  await stream.close();
  await consumer.close();
  return got.join(" ");
}

console.log("emails   :", await read(`${topic}-emails`, 4));
console.log("analytics:", await read(`${topic}-analytics`, 4));
// replay: מחזירים את ה־offset של group אחד אחורה (כשאין בו consumers פעילים)
await admin.alterConsumerGroupOffsets({ groupId: `${topic}-emails`, topics: [{ name: topic, partitionOffsets: [{ partition: 0, offset: 1n }] }] });
console.log("emails, after reset to offset 1:", await read(`${topic}-emails`, 3));

await producer.close();
await admin.deleteTopics({ topics: [topic] });
await admin.close();
emails   : 0:placed 1:paid 2:shipped 3:delivered
analytics: 0:placed 1:paid 2:shipped 3:delivered
emails, after reset to offset 1: 1:paid 2:shipped 3:delivered

שלושה דברים מהפלט: (1) שני ה־groups קיבלו את כל ההודעות — זה לא "תור" שבו הודעה הולכת לאחד. (2) ההודעות לא נמחקו אחרי שנקראו. (3) replay: הזזנו offset, וקראנו שוב — כך מתקנים באג ב־consumer ומעבדים מחדש את היום האחרון. בתור רגיל, ההודעות האלה כבר היו מזמן בפח.

4. מתי לעשות commit

אותה שאלה כמו ack: commit לפני הטיפול ← at-most-once; אחרי ← at-least-once (E14). autocommit: true עושה commit לפי זמן, בלי קשר לשאלה אם סיימת — נוח, ומסוכן כשהטיפול נכשל. ויש דרך שלישית, למי שכותב למסד: לא לעשות commit ב־Kafka בכלל, אלא לשמור את ה־offset במסד, באותה טרנזקציה עם התוצאה, ובעלייה להתחיל ממנו — כך כל הודעה משפיעה בדיוק פעם אחת (E25).

5. consumer lag

lag = הסוף של ה־partition פחות ה־committed offset של ה־group: כמה הודעות מחכות. זה המדד הראשון בכל דשבורד של Kafka. lag שעולה בהתמדה אומר שהצרכנים איטיים מהקצב — מוסיפים consumers (עד מספר ה־partitions, שהוא תקרת המקביליות), או מאיצים את הטיפול (E19).

💼 בעולם העבודה

שאלות שחוזרות בראיונות על Kafka: "איך מבטיחים סדר?" (key, ובתוך partition); "מה קורה כשמוסיפים consumer?" (rebalance; מעבר למספר ה־partitions — לא עוזר); "consumer נפל באמצע — מה קורה להודעה?" (חוזרת מה־committed offset — לכן אידמפוטנטיות); "מה ההבדל מ־RabbitMQ?" (log מול תור; replay; כמה groups עצמאיים). אחרי היחידה הזו יש לך תשובות — עם קוד שרץ.
