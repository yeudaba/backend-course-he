P26.5-E47 · ‏direct, ‏topic או fanout — לאן זה מגיע? 🧠 הבנה רמה 2

💡 רמז 1

direct — שוויון מדויק, ו־*/# הם סתם תווים. fanout — מתעלם מה־key.

💡 רמז 2

topic: ‏* — מילה אחת בדיוק; ‏# — אפס מילים או יותר.

✅ פתרון
  • direct: 1 ← ‏q1. ‏2, 3, 4 ← אף אחד (אין binding שהוא בדיוק order.created.il, order או ריק).
  • topic: 1 ← ‏q1, ‏q2, ‏q3. ‏2 ← ‏q3 (‏* לא תופס שתי מילים). ‏3 ← ‏q3 (‏order.* צריך מילה אחרי הנקודה). ‏4 ← ‏q3 (‏# תופס גם אפס מילים).
  • fanout: כל הארבע ← כל שלושת התורים.

הודעה בלי תור מתאים — נזרקת בשקט. ‏mandatory: true ב־publish גורם ל־RabbitMQ להחזיר אותה ל־producer (אירוע return).

⚠️ טעויות נפוצות
  • לחשוב ש־order.* תופס order.created.il — לזה צריך order.#.

P26.5-E48 · ‏prefetch: מה קורה בלעדיו? 🧠 הבנה רמה 2

💡 רמז 1

בלי prefetch, RabbitMQ דוחף לכל consumer כמה שיש.

💡 רמז 2

prefetch = ‏unacked לכל היותר.

✅ פתרון
  1. א׳ מקבל את כל ה־10,000 לזיכרון (unacked), ו־ב׳ — כלום. א׳ עלול להיגמר לו הזיכרון, ועבודה מתעכבת למרות שיש worker פנוי.
  2. א׳ מחזיק 10 בכל רגע; ב׳ מקבל מיד את הבאות — העבודה מתחלקת.
  3. חוזרות לתור, ו־ב׳ מקבל אותן (at-least-once — אולי חלקן כבר טופלו).
  4. גבוה מדי — חזרה לבעיה 1, ונפילה מחזירה הרבה הודעות. ‏1 — בין כל הודעה לבאה יש הלוך־חזור ברשת, וה־worker מחכה. ערך טיפוסי: כמספר העבודות שה־worker באמת יכול להריץ במקביל.
⚠️ טעויות נפוצות
  • להגדיר prefetch אחרי consume — הוא חל רק על consumers שנוצרים אחריו.

P26.5-E49 · ‏nack עם requeue — הלולאה 🧠 הבנה רמה 2

💡 רמז 1

requeue מחזיר לראש התור, ו־מיד.

💡 רמז 2

prefetch 1 — אותה הודעה, שוב ושוב.

✅ פתרון
  1. ההודעה חוזרת לראש התור ונמסרת שוב מיד — אלפי פעמים בשנייה. המעבד ב־100%, הלוג מתמלא באותה שגיאה.
  2. עם prefetch 1 — תקועות מאחוריה. עם prefetch גבוה — חלקן מטופלות, אבל ההודעה הפגומה תופסת חלק מה־worker לתמיד.
  3. קבועה (JSON פגום, נתונים לא תקינים) ← nack(msg, false, false) ל־dead letter מיד (‏E07). זמנית (שירות לא זמין) ← retry עם השהיה (תור המתנה עם TTL, ‏E18), ואחרי N ניסיונות — dead letter.
⚠️ טעויות נפוצות
  • "נוסיף setTimeout לפני ה־nack" — ההודעה תפוסה (unacked) כל הזמן הזה, ו־worker שנופל באמצע מחזיר אותה.

P26.5-E50 · ‏durable, ‏persistent, ו־RabbitMQ שעלה מחדש 🧠 הבנה רמה 1

💡 רמז 1

durable — ההגדרה של התור שורדת. persistent — ההודעה נכתבת לדיסק.

💡 רמז 2

צריך את שניהם.

✅ פתרון
  1. התור נעלם — ואיתו ההודעות, גם אם הן persistent.
  2. התור נשאר, ריק — ההודעות היו רק בזיכרון.
  3. הכול נשאר (מה שהגיע לדיסק — לכן publisher confirms כשחשוב).
  4. נמחק כבר כשהחיבור נסגר — זה כל העניין שלו (מתאים ל־"תור לכל instance", ‏E53).
  5. ה־exchange נשאר, התור וה־binding — לא. הודעות שמגיעות עכשיו — לאף אחד.
⚠️ טעויות נפוצות
  • "הגדרנו persistent, אז שום הודעה לא תאבד" — לא עם תור שאינו durable, ולא בלי volume לקונטיינר (‏E58).

P26.5-E51 · לקרוא את x-death 🧠 הבנה רמה 2

💡 רמז 1

‏rejected = ‏nack ב־work. ‏expired = יצאה מתור ההמתנה.

💡 רמז 2

הסדר במערך: האחרון שקרה ראשון — אבל אל תסמוך על זה.

✅ פתרון
  1. פעמיים — count: 2 ברשומה של work עם rejected.
  2. שלישי.
  3. זה היה הניסיון השלישי, ו־3 הוא המקסימום ← לא לשלוח ל־retry, אלא ל־dead queue (‏E18).
  4. ב־x-death יש רשומה לכל (תור, סיבה), וגם תורים אחרים בדרך (dead letter, העברה ידנית). הספירה הנכונה היא הרשומה של התור שלך, עם הסיבה שלך — זה בדיוק E55.
⚠️ טעויות נפוצות
  • לספור את אורך המערך — הוא לא גדל עם כל ניסיון; ה־count גדל.

P26.5-E06 · topic exchange 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

assertExchange(name, "topic", { durable: true }), assertQueue, bindQueue(queue, exchange, pattern) — פעמיים ל־emailQueue.

💡 רמז 2

ch.publish(exchange, routingKey, Buffer, { persistent, contentType, messageId }).

✅ פתרון
// P26.5-E06: topic exchange — מי מקבל איזה אירוע
import type { Channel } from "amqplib";

export interface Topology {
  exchange: string;
  emailQueue: string;
  analyticsQueue: string;
}

export interface OrderEvent {
  id: string;
  type: "created" | "paid" | "shipped" | "cancelled";
  orderId: number;
  country: string;
}

export async function setupTopology(ch: Channel, t: Topology): Promise<void> {
  await ch.assertExchange(t.exchange, "topic", { durable: true });
  await ch.assertQueue(t.emailQueue, { durable: true });
  await ch.assertQueue(t.analyticsQueue, { durable: true });
  // routing key: order.<type>.<country>  —  * = מילה אחת, # = אפס מילים או יותר
  await ch.bindQueue(t.emailQueue, t.exchange, "order.created.*");
  await ch.bindQueue(t.emailQueue, t.exchange, "order.shipped.*");
  await ch.bindQueue(t.analyticsQueue, t.exchange, "order.#");
}

export const routingKey = (e: OrderEvent) => `order.${e.type}.${e.country.toLowerCase()}`;

export function publishOrderEvent(ch: Channel, exchange: string, e: OrderEvent): boolean {
  return ch.publish(exchange, routingKey(e), Buffer.from(JSON.stringify(e)), {
    persistent: true, // נשמר בדיסק — שורד restart של RabbitMQ (בתור durable)
    contentType: "application/json",
    messageId: e.id,
  });
}

durable (התור שורד restart של ה־broker) ו־persistent (ההודעה נכתבת לדיסק) — צריך את שניהם. ובפרודקשן ב־RabbitMQ 4: quorum queues (arguments: { "x-queue-type": "quorum" }) — משוכפלים על כמה nodes, ובלי זה נפילה של node אחד מאבדת את התור.

⚠️ טעויות נפוצות
  • Buffer.from(event) בלי JSON.stringify — זורק (אובייקט הוא לא מחרוזת).

P26.5-E07 · worker עם dead letter 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

ch.prefetch(n) לפני consume.

💡 רמז 2

ch.nack(msg, false, false) — הפרמטר השלישי הוא requeue.

✅ פתרון
// P26.5-E07: worker עם prefetch, ack אחרי הצלחה, ו־dead letter לכישלונות
import type { Channel, ConsumeMessage } from "amqplib";

export interface WorkQueue {
  queue: string;
  deadLetterExchange: string;
  deadLetterQueue: string;
}

export async function setupWorkQueue(ch: Channel, w: WorkQueue): Promise<void> {
  await ch.assertExchange(w.deadLetterExchange, "fanout", { durable: true });
  await ch.assertQueue(w.deadLetterQueue, { durable: true });
  await ch.bindQueue(w.deadLetterQueue, w.deadLetterExchange, "");
  await ch.assertQueue(w.queue, { durable: true, deadLetterExchange: w.deadLetterExchange });
}

export async function startWorker(
  ch: Channel,
  queue: string,
  handler: (job: unknown) => Promise<void>,
  { prefetch = 5 } = {},
): Promise<string> {
  await ch.prefetch(prefetch); // לכל היותר prefetch הודעות שלא אושרו — בזמן נתון
  const { consumerTag } = await ch.consume(queue, async (msg: ConsumeMessage | null) => {
    if (!msg) return; // התור נמחק / ה־consumer בוטל
    try {
      const job = JSON.parse(msg.content.toString());
      await handler(job);
      ch.ack(msg); // רק אחרי שהעבודה הצליחה
    } catch {
      ch.nack(msg, false, false); // requeue=false ← ל־dead letter exchange, לא חזרה לראש התור
    }
  });
  return consumerTag;
}
⚠️ טעויות נפוצות
  • nack(msg) עם ברירת המחדל (requeue=true) — ההודעה חוזרת לראש התור מיד ונכשלת שוב, אלפי פעמים בשנייה ("poison message"). E20.

P26.5-E18 · retry עם השהיה ב־RabbitMQ 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

dead letter אל ה־default exchange ("") עם deadLetterRoutingKey = שם התור — מגיע ישר לתור. messageTtl בתור ההמתנה.

💡 רמז 2

כמה ניסיונות היו? RabbitMQ מוסיף header בשם x-death עם count לכל תור וסיבה.

✅ פתרון
// P26.5-E18: retry עם השהיה — תור המתנה עם TTL, ו־dead letter חזרה
import type { Channel, ConsumeMessage } from "amqplib";

export interface RetryNames {
  queue: string; // העבודה
  retryQueue: string; // ממתינים delayMs, ואז חוזרים ל־queue
  deadQueue: string; // נכשלו maxAttempts פעמים
}

export async function setupRetry(ch: Channel, n: RetryNames, delayMs: number): Promise<void> {
  // nack ב־queue ← default exchange ("") עם routing key = retryQueue
  await ch.assertQueue(n.queue, { durable: true, deadLetterExchange: "", deadLetterRoutingKey: n.retryQueue });
  // TTL פג ב־retryQueue ← default exchange עם routing key = queue
  await ch.assertQueue(n.retryQueue, { durable: true, messageTtl: delayMs, deadLetterExchange: "", deadLetterRoutingKey: n.queue });
  await ch.assertQueue(n.deadQueue, { durable: true });
}

// כמה פעמים ההודעה כבר נדחתה מ־queue (RabbitMQ סופר ב־x-death)
export function attemptsSoFar(msg: ConsumeMessage, queue: string): number {
  const deaths = (msg.properties.headers?.["x-death"] ?? []) as { queue: string; reason: string; count: number }[];
  return deaths.find((d) => d.queue === queue && d.reason === "rejected")?.count ?? 0;
}

export async function startRetryingWorker(
  ch: Channel,
  n: RetryNames,
  handler: (job: any) => Promise<void>,
  { maxAttempts = 3 } = {},
): Promise<string> {
  await ch.prefetch(10);
  const { consumerTag } = await ch.consume(n.queue, async (msg) => {
    if (!msg) return;
    const attempt = attemptsSoFar(msg, n.queue) + 1;
    try {
      await handler(JSON.parse(msg.content.toString()));
      ch.ack(msg);
    } catch (err) {
      if (attempt >= maxAttempts) {
        ch.sendToQueue(n.deadQueue, msg.content, {
          persistent: true,
          contentType: msg.properties.contentType,
          headers: { "x-attempts": attempt, "x-error": String((err as Error)?.message ?? err) },
        });
        ch.ack(msg);
      } else {
        ch.nack(msg, false, false); // ← retryQueue, ואחרי delayMs חזרה
      }
    }
  });
  return consumerTag;
}

(ל־RabbitMQ יש גם plugin של delayed messages, ו־quorum queues סופרות ניסיונות בעצמן — x-delivery-limit. הטריק עם TTL עובד בכל התקנה.)

import type { Channel } from "amqplib";

export async function startEmailWorker(ch: Channel, queue: string, sendEmail: (to: string, subject: string) => Promise<void>) {

P26.5-E52 · התאמה של topic binding 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

‏match(p, k): אם p ריק ← ‏k ריק. אם p[0] === "#" ← לנסות לדלג על 0, 1, 2… מילים מ־k.

💡 רמז 2

key ריק — "".split(".") הוא [""]. כדאי להפוך אותו ל־[].

✅ פתרון
// P26.5-E52: התאמה של topic binding
const words = (s: string) => (s === "" ? [] : s.split("."));

function match(p: string[], k: string[]): boolean {
  if (p.length === 0) return k.length === 0;
  const [head, ...rest] = p;
  if (head === "#") {
    for (let skip = 0; skip <= k.length; skip++) if (match(rest, k.slice(skip))) return true;
    return false;
  }
  if (k.length === 0) return false;
  return (head === "*" || head === k[0]) && match(rest, k.slice(1));
}

export function bindingMatches(pattern: string, routingKey: string) {
  return match(words(pattern), words(routingKey));
}

זה מה שה־topic exchange מריץ על כל binding לכל הודעה (בגרסה יעילה יותר — עץ של מילים). כדאי לבדוק כך תבניות לפני שמקשרים תורים בפרודקשן.

⚠️ טעויות נפוצות
  • להמיר ל־regex עם # ← .* — ‏order.# הופך ל־order\..*, שלא תופס order לבד.

P26.5-E53 · ‏fanout: הודעה לכל ה־instances 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

💡 רמז 2
const { consumerTag } = await ch.consume(queue, cb, { noAck: true });

✅ פתרון
// P26.5-E53: fanout — הודעה לכל ה־instances
import type { Channel } from "amqplib";

export async function subscribeInstance(ch: Channel, exchange: string, onMessage: (data: unknown) => void) {
  await ch.assertExchange(exchange, "fanout", { durable: false });
  const { queue } = await ch.assertQueue("", { exclusive: true });
  await ch.bindQueue(queue, exchange, "");
  const { consumerTag } = await ch.consume(queue, (msg) => {
    if (msg) onMessage(JSON.parse(msg.content.toString()));
  }, { noAck: true });
  return {
    queue,
    async cancel() {
      await ch.cancel(consumerTag);
    },
  };
}

export function broadcast(ch: Channel, exchange: string, data: unknown) {
  return ch.publish(exchange, "", Buffer.from(JSON.stringify(data)), { contentType: "application/json" });
}

זה pub/sub של Redis (פרק 26) — ב־RabbitMQ. תור exclusive לכל instance: instance שמת — התור שלו נמחק לבד, ואין הודעות שנערמות לאף אחד. ‏noAck מתאים כאן: "נקה cache" שאבד אינו אסון (ה־TTL מכסה).

⚠️ טעויות נפוצות
  • תור עם שם קבוע לכל ה־instances — אז הם מתחלקים בהודעות (E40), וכל instance מקבל רק חלק.

P26.5-E54 · ‏worker שנותן הזדמנות שנייה אחת 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

‏msg.fields.redelivered — ‏true אם RabbitMQ כבר מסר את ההודעה הזו (ל־consumer כלשהו) ולא קיבל ack.

💡 רמז 2

שני try: אחד ל־JSON.parse, ואחד ל־handler.

✅ פתרון
// P26.5-E54: worker שנותן הזדמנות שנייה אחת
import type { Channel } from "amqplib";

export async function startSecondChanceWorker(ch: Channel, queue: string, handler: (job: unknown) => Promise<void>) {
  await ch.prefetch(1);
  const { consumerTag } = await ch.consume(queue, async (msg) => {
    if (!msg) return;
    let job: unknown;
    try {
      job = JSON.parse(msg.content.toString());
    } catch {
      return ch.nack(msg, false, false); // קבוע — אין טעם לנסות שוב
    }
    try {
      await handler(job);
      ch.ack(msg);
    } catch {
      ch.nack(msg, false, !msg.fields.redelivered); // ראשון ← עוד ניסיון; שני ← dead letter
    }
  });
  return consumerTag;
}

‏redelivered הוא דגל, לא מונה — "לפחות פעם אחת קודם". לכן זה נותן בדיוק הזדמנות שנייה אחת, וזה גם תופס הודעה שחזרה בגלל worker שנפל (גם אז היא redelivered). לספירה אמיתית — x-death (‏E55) או ה־x-delivery-limit של quorum queues.

⚠️ טעויות נפוצות
  • requeue תמיד — הלולאה של E49.

// P26.5-E55: כמה פעמים כבר נכשלה? (x-death)
type Death = { queue?: string; reason?: string; count?: number };

export function deathCount(headers: Record<string, unknown> | undefined, queue: string, reason?: string) {
  const deaths = headers?.["x-death"];
  if (!Array.isArray(deaths)) return 0;
  return (deaths as Death[])
    .filter((d) => d.queue === queue && (reason === undefined || d.reason === reason))
    .reduce((s, d) => s + (typeof d.count === "number" ? d.count : 1), 0);
}

זה החלק "באיזה ניסיון אני" של E18: ‏deathCount(msg.properties.headers, queue, "rejected") + 1.

⚠️ טעויות נפוצות
  • ‏headers["x-death"][0].count — הרשומה הראשונה יכולה להיות של תור ההמתנה (‏expired), לא של התור שלך.

P26.5-E56 · ‏retry ב־BullMQ מול RabbitMQ 🧠 הבנה רמה 2

💡 רמז 1

BullMQ שומר את העבודה ב־Redis, עם attemptsMade, ו־sorted set של עבודות מתוזמנות.

💡 רמז 2

✅ פתרון
  1. BullMQ הוא תור עבודות: לכל עבודה יש מצב (מונה ניסיונות, שגיאה אחרונה), וזמן ריצה עתידי ב־sorted set — "תחזיר בעוד X" הוא פעולה בסיסית. ‏RabbitMQ הוא broker של הודעות: הודעה לא "מחכה עד", היא בתור או לא.
  2. כמה תורי המתנה — work.retry.1s, ‏work.retry.4s, ‏work.retry.16s — וה־worker בוחר לאיזה לשלוח לפי x-death (או תור לכל השהיה, ‏E60). או plugin של delayed messages.
  3. כשההודעות כבר זורמות ב־RabbitMQ בין שירותים (ניתוב, כמה צרכנים, שפות שונות), ואין Redis משותף. BullMQ מצוין בתוך אפליקציית Node אחת.
⚠️ טעויות נפוצות
  • להעביר "בשביל ה־retry" אירועים בין שירותים ל־BullMQ — הוא לא נועד לניתוב ול־fan-out.

// P26.5-E59: POST /events ל־topic exchange
import express from "express";
import type { Channel } from "amqplib";
import { z } from "zod";

const schema = z.object({
  id: z.string().min(1),
  type: z.enum(["created", "paid", "shipped", "cancelled"]),
  orderId: z.number().int().positive(),
  country: z.string().regex(/^[A-Za-z]{2}$/),
});

export function eventsApp(ch: Channel, exchange: string) {
  const app = express();
  app.use(express.json());
  app.post("/events", (req, res) => {
    const r = schema.safeParse(req.body);
    if (!r.success) return res.status(400).json({ error: "אירוע לא תקין" });
    const e = r.data;
    const routingKey = `order.${e.type}.${e.country.toLowerCase()}`;
    ch.publish(exchange, routingKey, Buffer.from(JSON.stringify(e)), { persistent: true, contentType: "application/json", messageId: e.id });
    res.status(202).json({ routingKey });
  });
  return app;
}

ה־routing key נבנה מהנתונים אחרי ולידציה — כך country: "IL" ו־"il" מגיעים לאותו binding, ו־type: "order.#" לא יכול "לנתב" את עצמו לכל התורים.

⚠️ טעויות נפוצות
  • לבנות את ה־key מ־req.body.type לפני ולידציה — לקוח יכול לשלוח "*.#" ולקבל ניתוב שלא התכוונת.

💡 רמז 1

💡 רמז 2

אותו delay ← אותו תור, עם אותן הגדרות — ‏assertQueue חוזר שוב בלי שגיאה.

✅ פתרון
// P26.5-E60: השהיה לכל הודעה — בלי head-of-line
import type { Channel } from "amqplib";

export async function scheduleIn(ch: Channel, { waitPrefix, target }: { waitPrefix: string; target: string }, payload: unknown, delayMs: number) {
  const wait = `${waitPrefix}.${delayMs}`;
  await ch.assertQueue(wait, {
    durable: true,
    messageTtl: delayMs,
    deadLetterExchange: "",
    deadLetterRoutingKey: target,
    expires: delayMs + 60_000,
  });
  ch.sendToQueue(wait, Buffer.from(JSON.stringify(payload)), { persistent: true, contentType: "application/json" });
  return wait;
}

בתור עם TTL קבוע כל ההודעות פגות באותו קצב, אז הסדר בתור הוא גם סדר הפקיעה — אין head-of-line. המחיר: תור לכל השהיה, ולכן בפועל מעגלים להשהיות קבועות (1s, ‏5s, ‏30s, ‏5m). השהיות של שעות וימים — זה כבר תפקיד של מסד או BullMQ, לא של broker.

⚠️ טעויות נפוצות
  • תור המתנה אחד ו־expiration לכל הודעה — עובד בבדיקה עם הודעה אחת, ונשבר בפרודקשן.
  • לשכוח deadLetterRoutingKey — ההודעה "מתה" ל־default exchange עם השם של תור ההמתנה, וחוזרת אליו.

P26.5-E61 · עצירה מסודרת של consumer 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

‏const inFlight = new Set<Promise<void>>(): כל טיפול נכנס כשמתחיל ויוצא כשמסתיים.

💡 רמז 2

‏await Promise.allSettled([...inFlight]), ואז await ch.close() — ה־close מחזיר ל־תור את מה שעוד unacked.

✅ פתרון
// P26.5-E61: עצירה מסודרת של consumer
import type { Channel, ConsumeMessage } from "amqplib";

export async function startConsumer(ch: Channel, queue: string, handler: (job: unknown) => Promise<void>, prefetch: number) {
  await ch.prefetch(prefetch);
  const inFlight = new Set<Promise<void>>();
  const handle = async (msg: ConsumeMessage) => {
    try {
      await handler(JSON.parse(msg.content.toString()));
      ch.ack(msg);
    } catch {
      ch.nack(msg, false, false);
    }
  };
  const { consumerTag } = await ch.consume(queue, (msg) => {
    if (!msg) return;
    const p = handle(msg).finally(() => inFlight.delete(p));
    inFlight.add(p);
  });
  return {
    async stop() {
      await ch.cancel(consumerTag);
      await Promise.allSettled([...inFlight]);
      await ch.close();
    },
  };
}

שלושת השלבים הם אותו כיבוי מסודר של שרת HTTP (פרק 24): לסגור את הדלת, לחכות למי שבפנים, לכבות את האור. בלי שלב 2 — ‏close מחזיר לתור הודעות שבאמצע טיפול, ו־worker אחר יטפל בהן שוב (at-least-once — לא נורא אם אידמפוטנטי, אבל מיותר).

⚠️ טעויות נפוצות
  • ch.close() מיד — עבודות באמצע נקטעות, וה־ack שלהן נכשל ("channel closed").
  • לשכוח cancel — בזמן ההמתנה ממשיכות להגיע הודעות חדשות, וה־stop לא נגמר.
