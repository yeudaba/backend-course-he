יחידה 26.5 — תורים ואירועים: RabbitMQ, Kafka ו־SQS

⏱ 4 מפגשים

🧰 לפני שמתחילים — יחידה 26.5

מה צריך שכבר יהיה מותקן: Docker Desktop, PostgreSQL מפרק 16, ו־LocalStack מיחידה 26.3 (לתרגילי SQS).

מה מתקינים / מריצים עכשיו (פעם אחת; אחר כך docker start rabbitmq kafka):

  • RabbitMQ 4: 
    docker run -d --name rabbitmq -p 5672:5672 rabbitmq:4-alpine
  • Kafka 4.1 — broker אחד במצב KRaft (בלי ZooKeeper). ה־image הרשמי עולה עם הגדרות ברירת מחדל שמתאימות בדיוק לזה: 
    docker run -d --name kafka -p 9092:9092 apache/kafka:4.1.0
  • בדיקה: docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list ← בלי שגיאה (רשימה ריקה). ו־docker logs rabbitmq | grep "Server startup complete".
  • ב־~/dev/backend-course/.env: COURSE_RABBIT_URL=amqp://localhost:5672 ו־COURSE_KAFKA_BROKERS=localhost:9092.
  • npm install בתיקיית הקורס — מוסיף את amqplib (RabbitMQ) ואת @platformatic/kafka (לקוח Kafka מודרני, ב־TypeScript, בלי רכיבים native).

📂 העתקת חומרי הפרק: ב־Finder, העתק את התיקייה 26w-messaging מתוך ~/Desktop/Backend/backend-course אל ~/dev/backend-course (גרירה עם ⌥ Option). אם התיקייה כבר שם מהעתקה קודמת ואתה רוצה לשמור את מה שכתבת — בחר Keep Both / Stop ולא Replace.

✔ בדיקה: cd ~/dev/backend-course && npm install && npm run check P26.5-E06 ← הבודק מתחבר ל־RabbitMQ ונכשל על הקובץ הריק. ECONNREFUSED 127.0.0.1:5672 — הקונטיינר לא רץ.

🎯 בסוף הפרק תדע
  • להבין מתי תור ומתי log, at-most-once מול at-least-once — ולמה consumer חייב להיות אידמפוטנטי.
  • RabbitMQ: exchanges, bindings, ack/nack, prefetch, dead letters ו־retry עם השהיה.
  • SQS: Standard מול FIFO, visibility timeout, long polling, batches ו־DLQ — מול LocalStack.
  • Kafka: topics, partitions, keys, consumer groups, offsets ו־commit אחרי טיפול; lag.
  • דפוסי אמינות: outbox, idempotent consumer, backoff עם jitter, מעטפת וגרסאות לאירועים — ו־exactly-once מול מסד.

🤔 למה צריך את זה?

בפרק 26 שלחת מייל אישור ברקע עם BullMQ: שרת אחד, Redis אחד, תור אחד. כשהמערכת גדלה לעשרות שירותים — הזמנות, תשלומים, מלאי, מיילים, אנליטיקה — הם מדברים ביניהם בהודעות, לא בקריאות HTTP ישירות: שירות ההזמנות לא מחכה לשירות המיילים, ולא נופל כשהוא נופל. המודעה שראית ביקשה "SQS/Kafka/RabbitMQ" — שלושת הכלים הנפוצים לזה, כל אחד עם מודל אחר. ביחידה הזו תריץ את שלושתם, תבין מתי כל אחד, ובעיקר — את מה שמשותף להם: הודעות מגיעות פעמיים, לא בסדר, או בכלל לא, אם לא בונים נכון. מי שיודע לענות בראיון "איך תמנע חיוב כפול כש־consumer נופל?" — עבר את החלק הקשה.

🏁 מבחן מעבר

  • לבחור בין BullMQ, RabbitMQ, SQS ו־Kafka לתרחיש, ולהסביר למה.
  • להסביר at-most-once מול at-least-once, ולכתוב consumer אידמפוטנטי.
  • להגדיר ב־RabbitMQ topic exchange, prefetch ו־dead letter — ולהסביר למה nack עם requeue הוא מלכודת.
  • להסביר visibility timeout ו־DLQ ב־SQS, ולכתוב consumer עם long polling.
  • להסביר partitions, keys ו־consumer groups ב־Kafka, ולמה commit אחרי טיפול.
  • להסביר transactional outbox ולמה "שמור ושלח" בלי outbox שבור.
  • npm run check P26.5: 80% מ־E06–E19, ולפחות שני תרגילי תיקון.
