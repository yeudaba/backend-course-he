שיעור 2 — RabbitMQ: exchanges, ack ו־dead letters

⏱ ~50 דקות

🎯 בשיעור הזה
  • המודל של RabbitMQ: producer ← exchange ← binding ← queue ← consumer.
  • ארבעה סוגי exchanges, ו־routing keys עם * ו־#.
  • ack, nack, prefetch — ומה קורה כש־consumer נופל.
  • dead letters, ו־retry עם השהיה.

1. המודל

ב־RabbitMQ, producer לא שולח לתור. הוא שולח ל־exchange, עם routing key; ה־exchange מעתיק את ההודעה לכל תור שיש לו binding מתאים; consumers קוראים מתורים. ההפרדה הזו היא מה שנותן ניתוב גמיש: ה־producer לא יודע כמה תורים יש ומי מאזין.

exchangeמנתב לפישימוש
directrouting key זהה בדיוק ל־binding"עבודות של סוג X לתור X"
topicתבנית: * = מילה אחת, # = אפס או יותראירועים — הכי נפוץ
fanoutמתעלם מה־key — לכל התורים המקושריםbroadcast, dead letters
headersheaders של ההודעהנדיר

ויש גם default exchange (שמו מחרוזת ריקה): כל תור מקושר אליו אוטומטית בשמו. ch.sendToQueue("emails", …) הוא בעצם publish ל־default exchange עם key emails.

2. ack, prefetch ו־nack

RabbitMQ שולח הודעה ל־consumer ומסמן אותה "unacked". שלוש אפשרויות:

  • ack — טופלה, למחוק.
  • nack(msg, false, true) — לא טופלה, להחזיר לתור (requeue). זהירות: לראש התור, ומיד.
  • nack(msg, false, false) — לא טופלה, לא להחזיר: אם לתור יש dead letter exchange — לשם; אחרת נזרקת.

ואם ה־consumer נופל (החיבור נסגר) עם הודעות unacked — RabbitMQ מחזיר אותן לתור, ו־consumer אחר יקבל אותן. זה at-least-once — בתנאי שה־ack בא אחרי הטיפול (E20).

prefetch — כמה הודעות unacked consumer מחזיק לכל היותר. בלעדיו, RabbitMQ דוחף לו את כל התור — אלפי הודעות לזיכרון, ו־consumer שני שעולה לא מקבל כלום. הרצה אמיתית: worker עם prefetch 2, ש"מטפל" בכל הודעה 100ms ונכשל על עבודה 3:

import amqp from "amqplib";

const conn = await amqp.connect(process.env.RABBIT_URL ?? "amqp://localhost:5672");
const ch = await conn.createChannel();
const dlx = `lesson2-dlx-${Date.now()}`;
await ch.assertExchange(dlx, "fanout", { autoDelete: true });
const dead = (await ch.assertQueue("", { exclusive: true })).queue;
await ch.bindQueue(dead, dlx, "");
const work = (await ch.assertQueue("", { exclusive: true, deadLetterExchange: dlx })).queue;

for (let id = 1; id <= 5; id++) ch.sendToQueue(work, Buffer.from(JSON.stringify({ id })));

await ch.prefetch(2);
let inFlight = 0;
let maxInFlight = 0;
let done = 0;
await ch.consume(work, async (msg) => {
  const { id } = JSON.parse(msg!.content.toString());
  maxInFlight = Math.max(maxInFlight, ++inFlight);
  console.log(`start ${id}`);
  await new Promise((r) => setTimeout(r, 100));
  inFlight--;
  if (id === 3) ch.nack(msg!, false, false); // נכשל ← dead letter
  else ch.ack(msg!);
  done++;
});
while (done < 5) await new Promise((r) => setTimeout(r, 20));
console.log("max in flight:", maxInFlight);
console.log("dead letters:", (await ch.checkQueue(dead)).messageCount);
await conn.close();

לעולם לא יותר משתיים בטיפול. ועבודה 3 לא חזרה לתור — היא ב־dead letter, מחכה שמישהו יסתכל.

3. retry עם השהיה

כשל זמני (שירות התשלומים לא עונה) מצדיק ניסיון נוסף — אבל לא מיד, ולא לראש התור. ל־RabbitMQ אין "החזר בעוד 5 שניות", אבל יש שני כלים שמרכיבים את זה: dead letter, ו־TTL של תור:

💡 quorum queues

הדוגמאות כאן משתמשות בתורים "classic" — פשוטים ומתאימים לפיתוח. בפרודקשן עם RabbitMQ 4 משתמשים ב־quorum queues (arguments: { "x-queue-type": "quorum" }): משוכפלים על כמה שרתים, ושורדים נפילה של אחד. הם גם סופרים ניסיונות מסירה בעצמם (x-delivery-limit) — הגנה מובנית מ־poison messages.
