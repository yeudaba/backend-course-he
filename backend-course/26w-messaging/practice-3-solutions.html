P26.5-E05 · visibility timeout 🧠 הבנה רמה 1

💡 רמז 1

receive לא מוחק — הוא "מסתיר" את ההודעה לזמן מוגבל.

💡 רמז 2

ההודעה נמחקת רק ב־DeleteMessage.

✅ פתרון
import { SQSClient, CreateQueueCommand, SendMessageCommand, ReceiveMessageCommand, DeleteQueueCommand } from "@aws-sdk/client-sqs";

const sqs = new SQSClient({
  region: "us-east-1",
  endpoint: process.env.AWS_ENDPOINT_URL ?? "http://localhost:4566",
  credentials: { accessKeyId: "test", secretAccessKey: "test" },
});
const { QueueUrl } = await sqs.send(new CreateQueueCommand({ QueueName: `e05-${Date.now()}`, Attributes: { VisibilityTimeout: "2" } }));
await sqs.send(new SendMessageCommand({ QueueUrl, MessageBody: "resize image 42" }));

const receive = async (label: string) => {
  const r = await sqs.send(new ReceiveMessageCommand({ QueueUrl, WaitTimeSeconds: 1, MessageSystemAttributeNames: ["ApproximateReceiveCount"] }));
  const m = r.Messages?.[0];
  console.log(label, m ? `"${m.Body}" (receive #${m.Attributes?.ApproximateReceiveCount})` : "— nothing");
};
await receive("1.");
await receive("2.");
await new Promise((r) => setTimeout(r, 2500));
await receive("3.");

2. — nothing

(WaitTimeSeconds: 1 — long polling קצר. בלי זה, receive "סוקר" רק חלק מהשרתים של SQS, ויכול לחזור ריק גם כשיש הודעה — שיעור 3.) בזמן ה־visibility timeout ההודעה "בטיפול" — consumers אחרים לא רואים אותה. לא נמחקה עד הסוף ← חוזרת, והמונה עולה. כלל: ה־timeout ארוך מהזמן שלוקח לטפל (אחרת ההודעה חוזרת בזמן שעוד מטפלים בה, ומטופלת פעמיים); ועבודה ארוכה מאריכה אותו תוך כדי (ChangeMessageVisibility). ואחרי maxReceiveCount קבלות — ל־DLQ (E11).

P26.5-E62 · ‏visibility timeout קצר מדי 🧠 הבנה רמה 2

💡 רמז 1

בשנייה 30 ההודעה חוזרת להיות גלויה.

💡 רמז 2

ReceiptHandle שייך לקבלה מסוימת.

✅ פתרון
  1. בשנייה 30 ההודעה גלויה שוב, consumer אחר מקבל אותה ומתחיל להפיק את אותה חשבונית. שתי חשבוניות.
  2. ה־handle ישן (הייתה קבלה חדשה). ב־SQS המחיקה בדרך כלל עדיין מצליחה, אבל ה־consumer השני כבר עובד — ואולי ימחק "שוב" או יחזיר אותה. כפילות בכל מקרה.
  3. הגדרה: timeout ארוך מהזמן הארוך הסביר (60–90 שניות). קוד: heartbeat — ChangeMessageVisibility כל כמה שניות בזמן העבודה (‏E67). ובכל מקרה — consumer אידמפוטנטי.
  4. consumer שנפל באמת משאיר את ההודעה מוסתרת 12 שעות — עיכוב ענק לכל כשל.
⚠️ טעויות נפוצות
  • להגדיל את ה־timeout בלי consumer אידמפוטנטי — הכפילות נדירה יותר, לא נעלמת.

P26.5-E63 · כמה עולה short polling? 🧠 הבנה רמה 2

💡 רמז 1

‏50 קריאות בשנייה ל־worker.

💡 רמז 2

שנייה × 60 × 60 × 24 × 30 = 2,592,000 שניות.

✅ פתרון
  1. ‏4 × 50 = 200 בשנייה × 2,592,000 ≈ ‏518 מיליון בקשות ← ‏~$207 בחודש, על כלום.
  2. כל worker — קריאה כל 20 שניות כשריק: ‏4 × 129,600 ≈ ‏518,400 בקשות ← ‏~$0.21.

⚠️ טעויות נפוצות

P26.5-E64 · מה ה־MessageGroupId? 🧠 הבנה רמה 2

💡 רמז 1

group = יחידת הסדר, וגם יחידת החסימה.

💡 רמז 2

בתוך group — הודעה אחת בכל רגע.

✅ פתרון
  1. סדר גלובלי — ואפס מקביליות: worker אחד עובד, השאר מחכים. הודעה תקועה עוצרת את כל התור.
  2. הנכון: סדר לכל הזמנה, מקביליות בין הזמנות. הודעה תקועה עוצרת רק את ההזמנה שלה.
  3. אין סדר בכלל (כל הודעה group משלה) — כמו Standard, אבל עם מגבלות של FIFO.
  4. עובד, אבל הלקוח הגדול הוא "group חם": כל ה־500 שלו בטור, ואם אחת נתקעת — כולן. עדיף ישות קטנה יותר (הזמנה), אם הסדר בין הזמנות של אותו לקוח לא חשוב.
⚠️ טעויות נפוצות
  • לבחור FIFO "ליתר ביטחון" עם group אחד — מקבלים תור איטי, ושום הגנה מכפילות שלא היה אפשר לקבל מ־consumer אידמפוטנטי.

P26.5-E09 · SQS FIFO 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

SendMessageBatchCommand עם Entries. ה־Id של כל entry — ייחודי רק בתוך ה־batch.

💡 רמז 2

batch לא זורק כשחלק נכשל — מחזיר Failed.

✅ פתרון
// P26.5-E09: שליחה לתור FIFO — סדר לכל הזמנה, בלי כפילויות, ב־batches
import { SQSClient, SendMessageBatchCommand } from "@aws-sdk/client-sqs";

export interface OrderEvent {
  eventId: string;
  orderId: number;
  type: string;
  data?: unknown;
}

export async function sendOrderEvents(sqs: SQSClient, queueUrl: string, events: OrderEvent[]): Promise<number> {
  let sent = 0;
  for (let i = 0; i < events.length; i += 10) {
    const chunk = events.slice(i, i + 10); // SQS: עד 10 הודעות ב־batch
    const res = await sqs.send(
      new SendMessageBatchCommand({
        QueueUrl: queueUrl,
        Entries: chunk.map((e, j) => ({
          Id: String(j), // ייחודי בתוך ה־batch בלבד
          MessageBody: JSON.stringify(e),
          MessageGroupId: String(e.orderId), // סדר נשמר בתוך קבוצה
          MessageDeduplicationId: e.eventId, // אותו id תוך 5 דקות ← נשלח פעם אחת
          MessageAttributes: { type: { DataType: "String", StringValue: e.type } },
        })),
      }),
    );
    if (res.Failed?.length) {
      const ids = res.Failed.map((f) => chunk[Number(f.Id)].eventId);
      throw new Error(`שליחה נכשלה עבור: ${ids.join(", ")} (${res.Failed[0].Code})`);
    }
    sent += res.Successful?.length ?? 0;
  }
  return sent;
}

FIFO מול Standard: Standard — כמעט בלי הגבלת קצב, אבל סדר "בערך" ולפעמים כפילויות; FIFO — סדר מדויק בתוך group ו־dedup של 5 דקות, עם תקרת קצב. ושימו לב: סדר בתוך group אומר שהודעה תקועה בהזמנה 7 עוצרת רק את הזמנה 7 — לא את כל התור.

P26.5-E10 · consumer של SQS 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

WaitTimeSeconds — עד 20.

💡 רמז 2

למחיקה צריך את ה־ReceiptHandle של הקבלה הזו (לא את ה־MessageId).

✅ פתרון
// P26.5-E10: consumer של SQS — long polling, ומחיקה רק אחרי הצלחה
import { SQSClient, ReceiveMessageCommand, DeleteMessageBatchCommand } from "@aws-sdk/client-sqs";

export async function pollOnce(
  sqs: SQSClient,
  queueUrl: string,
  handler: (body: unknown) => Promise<void>,
  { waitSeconds = 20 } = {},
): Promise<{ handled: number; failed: number }> {
  const res = await sqs.send(
    new ReceiveMessageCommand({
      QueueUrl: queueUrl,
      MaxNumberOfMessages: 10,
      WaitTimeSeconds: waitSeconds, // long polling: מחכה עד שיש הודעה, במקום לחזור ריק מיד
    }),
  );
  const done: { Id: string; ReceiptHandle: string }[] = [];
  let failed = 0;
  for (const [i, m] of (res.Messages ?? []).entries()) {
    try {
      await handler(JSON.parse(m.Body!));
      done.push({ Id: String(i), ReceiptHandle: m.ReceiptHandle! });
    } catch {
      failed++; // לא מוחקים: אחרי ה־visibility timeout ההודעה תחזור (ובסוף — ל־DLQ)
    }
  }
  if (done.length) {
    const del = await sqs.send(new DeleteMessageBatchCommand({ QueueUrl: queueUrl, Entries: done }));
    if (del.Failed?.length) throw new Error(`מחיקה נכשלה: ${del.Failed[0].Message}`);
  }
  return { handled: done.length, failed };
}

ובפועל — לולאה: while (!stopping) await pollOnce(…), ו־SIGTERM (פרק 24) מסמן stopping, כך שהקבלה הנוכחית מסתיימת לפני היציאה.

💡 רמז 1

RedrivePolicy הוא מחרוזת JSON עם deadLetterTargetArn ו־maxReceiveCount.

💡 רמז 2

✅ פתרון
// P26.5-E11: תור עם dead-letter queue
import { SQSClient, CreateQueueCommand, GetQueueAttributesCommand } from "@aws-sdk/client-sqs";

export async function createQueueWithDlq(
  sqs: SQSClient,
  name: string,
  { maxReceiveCount = 5, visibilityTimeout = 30 } = {},
): Promise<{ queueUrl: string; dlqUrl: string }> {
  const dlq = await sqs.send(
    new CreateQueueCommand({ QueueName: `${name}-dlq`, Attributes: { MessageRetentionPeriod: String(14 * 24 * 3600) } }),
  );
  const { Attributes } = await sqs.send(new GetQueueAttributesCommand({ QueueUrl: dlq.QueueUrl!, AttributeNames: ["QueueArn"] }));
  const main = await sqs.send(
    new CreateQueueCommand({
      QueueName: name,
      Attributes: {
        VisibilityTimeout: String(visibilityTimeout),
        RedrivePolicy: JSON.stringify({ deadLetterTargetArn: Attributes!.QueueArn, maxReceiveCount }),
      },
    }),
  );
  return { queueUrl: main.QueueUrl!, dlqUrl: dlq.QueueUrl! };
}

ה־DLQ שומר 14 יום כי מישהו צריך להסתכל: alarm על "יש הודעות ב־DLQ", בדיקה, תיקון — ואז redrive חזרה לתור הראשי (יש לזה כפתור בקונסולה ו־API).

💡 רמז 2

✅ פתרון
// P26.5-E21: ה־consumer אחרי התיקון
import { SQSClient, ReceiveMessageCommand, DeleteMessageCommand } from "@aws-sdk/client-sqs";

export async function processInvoices(sqs: SQSClient, queueUrl: string, issue: (invoice: any) => Promise<void>) {
  const res = await sqs.send(
    new ReceiveMessageCommand({ QueueUrl: queueUrl, MaxNumberOfMessages: 10, WaitTimeSeconds: 20 }), // תיקון 3: long polling
  );
  let issued = 0;
  for (const m of res.Messages ?? []) {
    try {
      await issue(JSON.parse(m.Body!));
    } catch {
      continue; // תיקון 1: לא מוחקים לפני שהצליח — ההודעה תחזור
    }
    await sqs.send(new DeleteMessageCommand({ QueueUrl: queueUrl, ReceiptHandle: m.ReceiptHandle! })); // תיקון 2: ה־ReceiptHandle של ההודעה הזו
    issued++;
  }
  return issued;
}

הכפילויות היו מתקלה 2: כל ההודעות "נמחקו" עם ה־ReceiptHandle של הראשונה — כלומר רק היא נמחקה (כמה פעמים), והשאר חזרו אחרי ה־visibility timeout ועובדו שוב.

P26.5-E67 · ‏heartbeat ל־visibility בזמן עבודה ארוכה 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

💡 רמז 2

✅ פתרון
// P26.5-E67: heartbeat ל־visibility בזמן עבודה ארוכה
import { ChangeMessageVisibilityCommand, type SQSClient } from "@aws-sdk/client-sqs";

export async function withVisibilityHeartbeat<T>(
  sqs: SQSClient,
  queueUrl: string,
  receiptHandle: string,
  work: () => Promise<T>,
  { visibilitySeconds, everyMs }: { visibilitySeconds: number; everyMs: number },
): Promise<T> {
  const timer = setInterval(() => {
    sqs.send(new ChangeMessageVisibilityCommand({ QueueUrl: queueUrl, ReceiptHandle: receiptHandle, VisibilityTimeout: visibilitySeconds })).catch(() => {});
  }, everyMs);
  try {
    return await work();
  } finally {
    clearInterval(timer);
  }
}

‏VisibilityTimeout ב־ChangeMessageVisibility נספר מעכשיו, לא מתחילת הקבלה — לכן heartbeat של "עוד 30 שניות" כל 10 שניות שומר על ההודעה כמה שצריך. ואם ה־worker מת — ה־heartbeat מת איתו, וההודעה חוזרת תוך 30 שניות.

⚠️ טעויות נפוצות
  • להפעיל את ה־heartbeat רק פעם אחת בהתחלה עם ערך גדול — זה סתם timeout ארוך (‏E62).
  • בלי finally — עבודה שזרקה משאירה interval שממשיך להאריך הודעה שאף אחד לא מטפל בה.

// P26.5-E68: שליחה ב־batches — וגם מה שנכשל
import { SendMessageBatchCommand, type SQSClient } from "@aws-sdk/client-sqs";

export async function sendAll(sqs: SQSClient, queueUrl: string, messages: { id: string; body: unknown }[]) {
  const ok = new Set<string>();
  const bad = new Map<string, string>();
  for (let i = 0; i < messages.length; i += 10) {
    const chunk = messages.slice(i, i + 10);
    const res = await sqs.send(
      new SendMessageBatchCommand({ QueueUrl: queueUrl, Entries: chunk.map((m) => ({ Id: m.id, MessageBody: JSON.stringify(m.body) })) }),
    );
    for (const s of res.Successful ?? []) ok.add(s.Id!);
    for (const f of res.Failed ?? []) bad.set(f.Id!, f.Code ?? "Unknown");
  }
  return {
    sent: messages.filter((m) => ok.has(m.id)).map((m) => m.id),
    failed: messages.filter((m) => bad.has(m.id)).map((m) => ({ id: m.id, code: bad.get(m.id)! })),
  };
}

P26.5-E69 · ‏redrive: מה־DLQ חזרה לתור 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

💡 רמז 2

‏Id ב־batch — מספר הסידור (String(i)). מיפוי בחזרה: Successful.map((s) => msgs[Number(s.Id)]).

✅ פתרון
// P26.5-E69: redrive — מה־DLQ חזרה לתור
import { DeleteMessageBatchCommand, ReceiveMessageCommand, SendMessageBatchCommand, type SQSClient } from "@aws-sdk/client-sqs";

export async function redrive(sqs: SQSClient, fromUrl: string, toUrl: string, max = Infinity) {
  let moved = 0;
  while (moved < max) {
    const { Messages: msgs = [] } = await sqs.send(
      new ReceiveMessageCommand({ QueueUrl: fromUrl, MaxNumberOfMessages: Math.min(10, max - moved), WaitTimeSeconds: 0 }),
    );
    if (msgs.length === 0) break;
    const sent = await sqs.send(new SendMessageBatchCommand({ QueueUrl: toUrl, Entries: msgs.map((m, i) => ({ Id: String(i), MessageBody: m.Body! })) }));
    const ok = (sent.Successful ?? []).map((s) => msgs[Number(s.Id)]);
    if (ok.length) {
      await sqs.send(new DeleteMessageBatchCommand({ QueueUrl: fromUrl, Entries: ok.map((m, i) => ({ Id: String(i), ReceiptHandle: m.ReceiptHandle! })) }));
    }
    moved += ok.length;
  }
  return moved;
}

ל־SQS יש היום redrive מובנה בקונסולה (StartMessageMoveTask), אבל זה בדיוק מה שהוא עושה. ה־max חשוב: מחזירים קודם 10, רואים שהן עוברות, ורק אז את השאר.

⚠️ טעויות נפוצות
  • למחוק לפני ששולחים — נפילה ביניהם מוחקת את ההודעה לגמרי.
  • לבקש תמיד 10 — עם max: 12 מעבירים 20.

// P26.5-E70: עומק התור, וכמה workers צריך
import { GetQueueAttributesCommand, type SQSClient } from "@aws-sdk/client-sqs";

export async function queueDepth(sqs: SQSClient, queueUrl: string) {
  const { Attributes: a = {} } = await sqs.send(
    new GetQueueAttributesCommand({
      QueueUrl: queueUrl,
      AttributeNames: ["ApproximateNumberOfMessages", "ApproximateNumberOfMessagesNotVisible", "ApproximateNumberOfMessagesDelayed"],
    }),
  );
  return {
    visible: Number(a.ApproximateNumberOfMessages ?? 0),
    inFlight: Number(a.ApproximateNumberOfMessagesNotVisible ?? 0),
    delayed: Number(a.ApproximateNumberOfMessagesDelayed ?? 0),
  };
}

export function workersNeeded(depth: { visible: number; inFlight: number }, { perWorker, min, max }: { perWorker: number; min: number; max: number }) {
  return Math.min(max, Math.max(min, Math.ceil((depth.visible + depth.inFlight) / perWorker)));
}

זה המדד שמחברים ל־autoscaling של workers (‏KEDA ב־Kubernetes, או ECS לפי מדד של CloudWatch): ה־CPU של worker שמחכה להודעות הוא אפס, אז HPA לפי CPU לא רואה שיש 50,000 בתור. "Approximate" — כי SQS מבוזר, והמספר הוא הערכה.

⚠️ טעויות נפוצות
  • לא לספור in-flight — workers שעובדים עכשיו נעלמים מהחישוב, והמערכת "מקטינה" באמצע עבודה.

✅ פתרון
// P26.5-E74: claim check — הודעה גדולה דרך S3
import { randomUUID } from "node:crypto";
import { GetObjectCommand, PutObjectCommand, type S3Client } from "@aws-sdk/client-s3";
import { SendMessageCommand, type SQSClient } from "@aws-sdk/client-sqs";

export async function sendClaimCheck(
  { s3, sqs }: { s3: S3Client; sqs: SQSClient },
  { bucket, queueUrl }: { bucket: string; queueUrl: string },
  payload: unknown,
  limitBytes = 200_000,
): Promise<"inline" | "s3"> {
  const json = JSON.stringify(payload);
  if (Buffer.byteLength(json) <= limitBytes) {
    await sqs.send(new SendMessageCommand({ QueueUrl: queueUrl, MessageBody: JSON.stringify({ inline: payload }) }));
    return "inline";
  }
  const s3Key = `claims/${randomUUID()}.json`;
  await s3.send(new PutObjectCommand({ Bucket: bucket, Key: s3Key, Body: json, ContentType: "application/json" }));
  await sqs.send(new SendMessageCommand({ QueueUrl: queueUrl, MessageBody: JSON.stringify({ s3Key }) }));
  return "s3";
}

export async function readClaimCheck(s3: S3Client, bucket: string, body: string) {
  const msg = JSON.parse(body) as { inline?: unknown; s3Key?: string };
  if (msg.s3Key) {
    const obj = await s3.send(new GetObjectCommand({ Bucket: bucket, Key: msg.s3Key }));
    return JSON.parse(await obj.Body!.transformToString());
  }
  return msg.inline;
}

הסדר: קודם S3, אחר כך התור — ככה לעולם אין כרטיס לקובץ שלא קיים. ומי מוחק את הקבצים? בדרך כלל lifecycle rule על ה־prefix claims/ (למשל אחרי 14 יום, כמו ה־DLQ) — לא ה־consumer, שאולי עוד יצטרך לקרוא שוב.

⚠️ טעויות נפוצות
  • לבדוק json.length — עם עברית, הודעה "קטנה" עוברת את המגבלה.
  • לשלוח את ההודעה לפני ש־PutObject הסתיים — consumer מהיר מקבל NoSuchKey.

P26.5-E75 · ‏poller שנעצר יפה 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

‏let running = true, ו־const loop = (async () => { while (running) { … } })(). ‏stop: ‏running = false; await loop.

💡 רמז 2

receive שכבר בדרך יחזור אחרי עד waitSeconds — ההודעות שהגיעו בו מטופלות לפני שהלולאה בודקת את running.

✅ פתרון
// P26.5-E75: poller שנעצר יפה
import { DeleteMessageCommand, ReceiveMessageCommand, type SQSClient } from "@aws-sdk/client-sqs";

export function startPoller(sqs: SQSClient, queueUrl: string, handler: (body: unknown) => Promise<void>, { waitSeconds }: { waitSeconds: number }) {
  let running = true;
  const counts = { handled: 0, failed: 0 };
  const loop = (async () => {
    while (running) {
      let msgs;
      try {
        ({ Messages: msgs = [] } = await sqs.send(new ReceiveMessageCommand({ QueueUrl: queueUrl, MaxNumberOfMessages: 10, WaitTimeSeconds: waitSeconds })));
      } catch {
        await new Promise((r) => setTimeout(r, 200));
        continue;
      }
      for (const m of msgs) {
        try {
          await handler(JSON.parse(m.Body!));
          await sqs.send(new DeleteMessageCommand({ QueueUrl: queueUrl, ReceiptHandle: m.ReceiptHandle! }));
          counts.handled++;
        } catch {
          counts.failed++;
        }
      }
    }
  })();
  return {
    async stop() {
      running = false;
      await loop;
    },
    stats: () => ({ ...counts }),
  };
}

ב־SIGTERM (פרק 24): ‏await poller.stop(), ואז לסגור את המסד. במקרה הגרוע ה־stop מחכה waitSeconds — לכן 20 שניות של long polling הם עדיין בתוך 30 השניות של Kubernetes, אבל כדאי לדעת שהן שם.

⚠️ טעויות נפוצות
  • ‏process.exit ב־SIGTERM — הודעות באמצע טיפול לא נמחקות, ויטופלו שוב.

P26.5-E76 · ‏batch של 10, במקביל של 3 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

‏concurrency "עובדים", וכל אחד לוקח את האינדקס הבא מתוך מונה משותף: while (next < messages.length) { const i = next++; … }.

💡 רמז 2

תוצאה לכל אינדקס במערך (results[i] = true/false), ובסוף מסננים לפי הסדר.

✅ פתרון
// P26.5-E76: batch של 10, במקביל של 3
export async function processBatch<M extends { MessageId: string }>(messages: M[], handler: (m: M) => Promise<void>, concurrency: number) {
  const results: boolean[] = [];
  let next = 0;
  async function worker() {
    while (next < messages.length) {
      const i = next++;
      try {
        await handler(messages[i]);
        results[i] = true;
      } catch {
        results[i] = false;
      }
    }
  }
  await Promise.all(Array.from({ length: Math.min(concurrency, messages.length) }, worker));
  return {
    ok: messages.filter((_, i) => results[i]).map((m) => m.MessageId),
    failed: messages.filter((_, i) => !results[i]).map((m) => m.MessageId),
  };
}

‏next++ בטוח כאן כי JavaScript רץ ב־thread אחד: בין await ל־await אף "עובד" אחר לא נכנס באמצע. אז ה־failed הולך ל־DeleteMessageBatch (רק ה־ok) — כמו ב־E10.

⚠️ טעויות נפוצות
  • לחלק לגלים של 3 עם Promise.all — הודעה איטית אחת עוצרת את כל הגל.
