P25.5-E03 · REPEATABLE READ

🧠 הבנהרמה 1⏱ 15 דק׳ידע נדרש: שיעור 3

ב־MySQL ברירת המחדל היא REPEATABLE READ (ב־PostgreSQL: READ COMMITTED). מלאי = 10. טרנזקציה A: START TRANSACTION; SELECT stock … ← 10. עכשיו B (בחיבור אחר) מוריד ל־7 ועושה COMMIT. מה יראה A ב: (1) SELECT stock שוב? (2) SELECT stock … FOR UPDATE? (3) UPDATE products SET stock = stock - 1 ואז SELECT? ומה המסקנה לגבי "קרא ואז החלט"?

P25.5-E56 · ‏REPEATABLE READ — מה A רואה?

🧠 הבנהרמה 2⏱ 10 דק׳ידע נדרש: שיעור 3

מלאי של מוצר 1: ‏10. שתי טרנזקציות, בסדר הזה:

A: START TRANSACTION;
A: SELECT stock FROM products WHERE id = 1;                     -- (1)
B: UPDATE products SET stock = 4 WHERE id = 1;  (autocommit)
A: SELECT stock FROM products WHERE id = 1;                     -- (2)
A: UPDATE products SET stock = stock - 1 WHERE id = 1;
A: SELECT stock FROM products WHERE id = 1;                     -- (3)
A: COMMIT;

מה ייקרא ב־(1), (2), ו־(3), ובסוף במסד? ומה היה ב־(2) עם READ COMMITTED (ברירת המחדל של PostgreSQL)? ומה הלקח לקוד "בדוק שיש מלאי, ואז הורד"?

P25.5-E57 · ‏FOR SHARE או FOR UPDATE?

🧠 הבנהרמה 2⏱ 10 דק׳ידע נדרש: שיעור 3

לכל מצב — SELECT רגיל, FOR SHARE, או FOR UPDATE? ולמה?

  1. מסך "ההזמנות שלי" — רשימה להצגה.
  2. לפני שמוסיפים ביקורת: לוודא שהמוצר קיים ופעיל, ושאף אחד לא ימחק אותו עד שה־INSERT נגמר.
  3. להעביר כסף: לקרוא את היתרה, להחליט, ולעדכן.
  4. דוח חודשי שרץ 40 שניות.
  5. שני workers מעבדים תור, כל אחד צריך עבודה שאף אחד אחר לא לקח.

P25.5-E58 · ‏gap lock — למה INSERT מחכה?

🧠 הבנהרמה 3⏱ 10 דק׳ידע נדרש: שיעור 3

worker מריץ בטרנזקציה: SELECT * FROM jobs WHERE status = 'queued' FOR UPDATE. אין אינדקס על status. בזמן שהוא עובד, ה־API מנסה INSERT INTO jobs (status) VALUES ('queued') — וה־INSERT מחכה עד שה־worker מסיים (או נכשל אחרי 50 שניות עם 1205). (1) למה INSERT של שורה חדשה מחכה? (2) למה זה קורה ב־InnoDB ולא ב־PostgreSQL? (3) מה משנה אינדקס על status? (4) ומה עוד אפשר לשנות?

P25.5-E59 · ‏NOWAIT מול SKIP LOCKED

🧠 הבנהרמה 2⏱ 10 דק׳ידע נדרש: שיעור 3

לכל מצב — FOR UPDATE (לחכות), NOWAIT, או SKIP LOCKED?

  1. משתמש לוחץ על מושב באולם. אם מישהו אחר באמצע להזמין אותו — להגיד מיד "המושב בתהליך הזמנה", לא לחכות.
  2. 5 workers שולחים מיילים מתור משותף.
  3. העברה בין שני ארנקים.
  4. job לילי שמעדכן מחירים, ולא אכפת לו לחכות כמה שניות.
  5. "תן לי מושב פנוי כלשהו בשורה A".

P25.5-E60 · ‏FOR UPDATE בלי טרנזקציה

🧠 הבנהרמה 2⏱ 10 דק׳ידע נדרש: שיעור 3

הקוד הזה אמור למנוע מכירת יותר ממה שיש במלאי, ובכל זאת נמכרו 12 יחידות מתוך 10:

const [[p]] = await pool.query("SELECT stock FROM products WHERE id = ? FOR UPDATE", [id]);
if (p.stock < qty) throw new OutOfStock();
await pool.query("UPDATE products SET stock = stock - ? WHERE id = ?", [qty, id]);

(1) למה ה־FOR UPDATE לא עזר? (2) תקן בשתי דרכים: אחת עם טרנזקציה, ואחת בלי. (3) למה בדרך עם הטרנזקציה חייבים getConnection?

P25.5-E15 · deadlock, ואיך חיים איתו 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 25 דק׳ידע נדרש: שיעור 3

בקובץ P25.5-E15.ts: withDeadlockRetry(fn, { retries = 3, sleep, random }) — מריץ את fn(attempt); אם נזרקה שגיאה עם errno 1213 (deadlock) או 1205 (lock wait timeout) — מחכה קצת (אקראי, גדל) ומנסה שוב, עד retries פעמים. כל שגיאה אחרת — מיד. הבודק גם מייצר deadlock אמיתי: שתי טרנזקציות שנועלות שני מוצרים בסדר הפוך.

P25.5-E61 · העברה בין ארנקים — בלי deadlock 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 25 דק׳ידע נדרש: שיעור 3

בקובץ 25v-mysql/files/locks.sql יש wallets(customer_id PK, balance). בקובץ 25v-mysql/starter/P25.5-E61.ts (יש בו רק הערה) כתוב וייצא:

export async function transfer(pool: Pool, fromId: number, toId: number, amount: number): Promise<{ from: number; to: number }>
  • amount שלם חיובי, אחרת RangeError. ‏fromId === toId ← Error("SAME_WALLET").
  • בטרנזקציה על חיבור אחד: נועלים את שני הארנקים בשאילתה אחת, לפי סדר המזהים (לא לפי מי שולח). אחד חסר ← Error("WALLET_NOT_FOUND"). אין מספיק ← Error("INSUFFICIENT_FUNDS").
  • מחזיר את היתרות החדשות. החיבור חוזר ל־pool תמיד.

הבודק מריץ 40 העברות במקביל, חצי מ־1 ל־4 וחצי מ־4 ל־1 — בלי אף deadlock.

P25.5-E64 · ‏READ COMMITTED מפרק 18 מול REPEATABLE READ

🧠 הבנהרמה 2⏱ 10 דק׳ידע נדרש: פרק 18, שיעור 3

קוד שעבד נכון ב־PostgreSQL (פרק 18) עובר ל־MySQL בלי שינוי. לכל קטע — האם ההתנהגות משתנה, ואיך?

  1. ‏UPDATE עם תנאי — SET balance = balance - 100 רק WHERE … AND balance >= 100 — ובדיקת מספר השורות.
  2. בטרנזקציה: SELECT balance … WHERE id = 1 (בלי FOR UPDATE), החלטה בקוד, ואז UPDATE … SET balance = $new.
  3. דוח בטרנזקציה: SELECT COUNT(*) ואז SELECT SUM(…) — כשבינתיים נכנסות הזמנות.
  4. ‏SELECT … FOR UPDATE ואז UPDATE, בטרנזקציה.
