P25.5-E86 · ‏UUID כמפתח ראשי ב־InnoDB 🧠 הבנה רמה 2

💡 רמז 1

כל אינדקס משני מחזיק, ליד כל ערך, את המפתח הראשי (איור 1).

💡 רמז 2

‏UUID v4 הוא אקראי — איפה בעץ הוא נכנס?

✅ פתרון
  1. כל רשומה בכל אינדקס משני גדלה: 36 בתים (‏CHAR(36) ב־utf8mb4 — עד 144 בתים לפי הגדרה!) במקום 4. יותר דיסק, פחות אינדקס בזיכרון.
  2. כל UUID אקראי נכנס במקום אקראי ב־clustered index: דפים מתפצלים, נכתבים מחדש, ו־buffer pool מתמלא בדפים חצי ריקים. עם AUTO_INCREMENT כל הכנסה בסוף העץ.
  3. (א) ‏BINARY(16) במקום טקסט (‏UUID_TO_BIN). (ב) UUID ממוין בזמן — ‏v7, או UUID_TO_BIN(uuid, 1) שמסדר מחדש את החלקים של v1 (E93). ‏(ג) מפתח ראשי AUTO_INCREMENT פנימי, ו־UUID כעמודה ייחודית "ציבורית" — מה שה־API חושף.
⚠️ טעויות נפוצות
  • להחליט לפי בדיקה על 1,000 שורות — ההבדל מופיע כשהטבלה כבר לא נכנסת לזיכרון.

P25.5-E87 · לקרוא EXPLAIN: האם יש קפיצה לטבלה? 🧠 הבנה רמה 2

💡 רמז 1

מה בדיוק יש בכל רשומה של האינדקס המשני? (העמודות שלו + המפתח הראשי.)

💡 רמז 2

3 — האינדקס ממוין לפי customer_id, ‏status, ‏created_at. האם created_at ממוין בתוך customer_id לבד?

✅ פתרון
  1. covering — id הוא המפתח הראשי, והוא בכל רשומה של האינדקס.
  2. לא — total לא באינדקס; קפיצה לכל שורה. (אם זו שאילתה חמה — להוסיף total לסוף האינדקס.)
  3. covering (‏created_at באינדקס) — אבל המיון לא "בחינם": בתוך לקוח 3, הרשומות ממוינות קודם לפי status, אז צריך מיון נוסף (filesort) על מה שנמצא.
  4. covering — סופרים רשומות באינדקס.

ב־TREE: ‏Covering index lookup on orders using … במקום Index lookup; וב־FORMAT=TRADITIONAL — ‏Using index בעמודה Extra.

⚠️ טעויות נפוצות
  • להוסיף את כל העמודות לאינדקס "כדי שיהיה covering" — האינדקס הופך לעותק של הטבלה, וכל INSERT מעדכן אותו.

P25.5-E88 · סדר העמודות באינדקס 🧠 הבנה רמה 2

💡 רמז 1

כלל: קודם עמודות עם =, ואחריהן העמודה של המיון/הטווח.

💡 רמז 2

אינדקס הוא "ממוין לפי הראשונה, ובתוכה לפי השנייה…" — כמו ספר טלפונים.

✅ פתרון
  • (customer_id, created_at) — א מצוין. ב — מוצא את הלקוח וממוין, אבל מסנן status תוך כדי (כמו "לפני" בשיעור).
  • (customer_id, status, created_at) — ב מצוין. א — מוצא את הלקוח, אבל created_at לא ממוין על פני כל הסטטוסים ← מיון.
  • (status, created_at) — ג מצוין.
  • (created_at, customer_id) — כמעט לא עוזר לאף אחת: עמודה ראשונה בלי =.

שלושה אינדקסים: ‏(customer_id, created_at), ‏(customer_id, status, created_at), ‏(status, created_at). אם א פחות חשובה — אפשר לוותר על הראשון, ולשלם במיון. (ושימו לב: (customer_id) לבד מיותר כשיש אינדקס שמתחיל בו — E92.)

⚠️ טעויות נפוצות
  • אינדקס לכל עמודה בנפרד — MySQL משתמש בדרך כלל באחד, והשאר רק מאטים כתיבה.

P25.5-E89 · ‏migration שנכשל באמצע 🧠 הבנה רמה 2

💡 רמז 1

כל ALTER עושה COMMIT מרומז — לפניו ואחריו.

💡 רמז 2

ה־CHECK השלישי — על אילו שורות הוא נכשל?

✅ פתרון
  1. העמודה נוספה (ה־ALTER הראשון כבר מחויב), ה־UPDATE בוצע (‏autocommit), וה־CHECK נכשל — כי יש שורות USD. המסד "חצי מעודכן".
  2. ה־ALTER הראשון נכשל: ‏Duplicate column name 'currency'. ואם הכלי של ה־migrations לא רשם את הקובץ כרץ — הוא תקוע, ומישהו צריך לתקן ביד.
  3. הכול בטרנזקציה אחת — הכישלון ב־CHECK מבטל גם את העמודה וגם את ה־UPDATE, והמסד בדיוק כמו לפני.
  4. migration לכל פקודת DDL; פקודות שמותר להריץ שוב (‏ADD COLUMN IF NOT EXISTS לא קיים ב־MySQL — בודקים ב־information_schema, או כלי שעושה זאת); ובדיקת הנתונים לפני CHECK (כאן — ה־CHECK בכלל שגוי: צריך גם USD).
⚠️ טעויות נפוצות
  • לכתוב migrations ל־MySQL "כמו ל־PostgreSQL" עם הרבה פקודות בקובץ, ולסמוך על rollback שלא קיים.

P25.5-E90 · למה GET_LOCK? 🧠 הבנה רמה 2

💡 רמז 1

שני עותקים בודקים "migration 7 רץ?" באותו רגע.

💡 רמז 2

‏GET_LOCK משתחרר לבד כשהחיבור נסגר.

✅ פתרון
  1. (א) שניים מריצים את אותו ALTER … ADD COLUMN — אחד מצליח, השני נכשל ("Duplicate column") והשרת שלו לא עולה. (ב) שניים מריצים UPDATE … SET x = x * 100 — הנתונים מוכפלים פעמיים.
  2. הבדיקה ("לא רץ") והרישום ("רץ") הן שתי פעולות, עם migration ארוך באמצע — וב־MySQL ה־DDL לא בטרנזקציה, אז אי אפשר לנעול שורה בטבלה הזו "סביב" ה־ALTER.
  3. נעילה בשם, ברמת השרת: רק חיבור אחד מחזיק 'schema_migrations'; האחרים מחכים (עד timeout), ואחרי שהראשון סיים — רואים שהכול רץ, ולא עושים כלום. היא של החיבור — ולכן שרת שקרס באמצע משחרר אותה אוטומטית (‏P25.5-E19).
  4. מה־CI — רק תהליך אחד מריץ, לפני ה־deploy, בלי מרוץ בכלל. GET_LOCK הוא רשת ביטחון למי שמריץ migrations בעלייה (נפוץ בפלטפורמות בלי שלב CI).
⚠️ טעויות נפוצות
  • GET_LOCK על חיבור מה־pool ואז ה־migrations על חיבורים אחרים — הנעילה "מוחזקת" על ידי חיבור שלא עושה כלום, וחוזרת ל־pool נעולה.

P25.5-E91 · איך יודעים שההעברה הצליחה? 🧠 הבנה רמה 2

💡 רמז 1

סכומים, תאריכים, טקסט — כל אחד נשבר בדרך אחרת.

💡 רמז 2

שורות שנוספו או השתנו אחרי שהעתקת אותן.

✅ פתרון
  1. (א) ספירה לכל טבלה. (ב) סכומים: SUM(total) עד האגורה (המרה דרך float תתפוס כאן), ‏SUM(LENGTH(name)) או hash של עמודות טקסט (קידוד, ‏utf8mb3). (ג) מינימום/מקסימום של תאריכים (המרת אזור זמן — שעתיים "זזו") ובדיקה מדגמית של שורות ספציפיות בשני הצדדים.
  2. מספר זהה לא תופס: סכומים שעוגלו (89.90 ← 89.9000001), טקסט שנחתך או ש־🔥 הפך ל־?, תאריכים שזזו בשעתיים, ‏boolean ש"הפך" ('f' ← 1).
  3. הרצה חוזרת (idempotent, ‏ON DUPLICATE KEY UPDATE) שמעבירה גם שינויים — כמה סבבים, ואז חלון קצר של "קריאה בלבד" במערכת הישנה, סבב אחרון, השוואה, והעברה.
⚠️ טעויות נפוצות
  • לבדוק "נראה בסדר" על 10 שורות ראשונות — הבאגים בשורות עם ערכים קיצוניים.

P25.5-E16 · חיפוש FULLTEXT 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

ALTER TABLE products ADD FULLTEXT INDEX … (name).

💡 רמז 2

MATCH(name) AGAINST ('+grinder* -electric' IN BOOLEAN MODE).

✅ פתרון
-- P25.5-E16
-- חיפוש מלא (FULLTEXT) ב־InnoDB: אינדקס על name, ו־MATCH … AGAINST. במצב BOOLEAN: + חובה, - אסור, * prefix
ALTER TABLE products ADD FULLTEXT INDEX ft_products_name (name);
SELECT name
FROM products
WHERE MATCH(name) AGAINST ('+grinder* -electric' IN BOOLEAN MODE)
ORDER BY name;

ומה עם קלט של משתמש? בתווים כמו + - * " ( ) יש משמעות ב־BOOLEAN MODE — מנקים אותם (או משתמשים ב־NATURAL LANGUAGE MODE). ומעל כמה מיליוני מסמכים, או כשצריך דירוג חכם, פונים למנוע חיפוש (Elasticsearch/OpenSearch, Meilisearch).

⚠️ טעויות נפוצות
  • LIKE '%grinder%' על טבלה גדולה — סורק הכול; אינדקס רגיל לא עוזר כשהתבנית מתחילה ב־%.

P25.5-E18 · אינדקס נכון, לפי EXPLAIN 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

סדר העמודות באינדקס: קודם מה שמשווים ב־=, אחר כך מה שממיינים.

💡 רמז 2

האינדקס הקיים (customer_id, created_at) ממוין נכון — אבל עובר על כל ההזמנות המבוטלות עד שמוצא 10 ששולמו.

✅ פתרון
-- P25.5-E18
-- השאילתה: WHERE customer_id = ? AND status = 'paid' ORDER BY created_at DESC LIMIT 10.
-- אינדקס מורכב בסדר: שוויון קודם (customer_id, status), ואז המיון (created_at) — בלי filesort, ובלי לסרוק הזמנות בסטטוס אחר
CREATE INDEX idx_orders_customer_status_created ON orders (customer_id, status, created_at);

ב־InnoDB כל אינדקס משני מכיל גם את המפתח הראשי — לכן id כבר "באינדקס". הוסף גם total ← covering index: המסד לא צריך לקרוא את השורה בכלל. ולכן גם: מפתח ראשי קצר וממוין (AUTO_INCREMENT), לא UUID אקראי — הוא מוכפל בכל אינדקס.

⚠️ טעויות נפוצות

P25.5-E19 · migrations עם GET_LOCK 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

SELECT GET_LOCK('schema_migrations', ?) AS ok ← 1 אם קיבלת.

💡 רמז 2

הנעילה שייכת לחיבור — לכן pool.getConnection(), לא pool.query.

✅ פתרון
// P25.5-E19
import type { Pool } from "mysql2/promise";

// כלי migrations בקטן. שני דברים שמיוחדים ל־MySQL:
// (1) DDL עושה COMMIT מרומז — אי אפשר לעטוף CREATE/ALTER בטרנזקציה ולבטל. migration שנכשל באמצע — נשאר באמצע.
// (2) GET_LOCK: נעילה בשם, לכל השרתים — כך שני שרתים שעולים יחד לא מריצים את אותו migration פעמיים
export async function migrate(pool: Pool, migrations: readonly { id: string; sql: string }[], { lockTimeoutSeconds = 10 } = {}): Promise<string[]> {
  const conn = await pool.getConnection();
  try {
    const [[lock]] = await conn.query<any[]>("SELECT GET_LOCK('schema_migrations', ?) AS ok", [lockTimeoutSeconds]);
    if (lock.ok !== 1) throw new Error("לא התקבלה נעילה ל־migrations");
    try {
      await conn.query("CREATE TABLE IF NOT EXISTS schema_migrations (id VARCHAR(100) PRIMARY KEY, applied_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3))");
      const [done] = await conn.query<any[]>("SELECT id FROM schema_migrations");
      const applied = new Set(done.map((r) => r.id));
      const ran: string[] = [];
      for (const m of [...migrations].sort((a, b) => (a.id < b.id ? -1 : 1))) {
        if (applied.has(m.id)) continue;
        await conn.query(m.sql);
        await conn.execute("INSERT INTO schema_migrations (id) VALUES (?)", [m.id]);
        ran.push(m.id);
      }
      return ran;
    } finally {
      await conn.query("SELECT RELEASE_LOCK('schema_migrations')");
    }
  } finally {
    conn.release();
  }
}

ההבדל הגדול מ־PostgreSQL: שם, CREATE TABLE בתוך טרנזקציה אפשר לבטל. ב־MySQL כל DDL עושה COMMIT מרומז — migration עם שלוש פקודות שנכשל בשלישית משאיר את שתי הראשונות. לכן: migration קטן, פקודה אחת אם אפשר, ו־"expand/contract" (פרק 25).

⚠️ טעויות נפוצות
  • GET_LOCK על pool.query — הנעילה נלקחת בחיבור אחד, ה־migrations רצים באחרים, וה־RELEASE משחרר (או לא) בשלישי.

P25.5-E24 · אתגר: "הזמן" של חנות הקפה ב־MySQL 🤖 💻 כתיבת קוד 🤖 רמה 5

💡 רמז 1

שני פתרונות קודמים בפרק הם רוב הדרך: E09 (הזמנה), E17 (idempotency).

💡 רמז 2

אחרי INSERT IGNORE שהחזיר 0 — קרא את השורה עם FOR SHARE: ב־REPEATABLE READ קריאה רגילה יכולה להחזיר את התמונה הישנה.

✅ פתרון
// P25.5-E24
import type { Pool } from "mysql2/promise";

export class EmptyCart extends Error {}
export class OutOfStock extends Error {
  productId: number;
  constructor(productId: number) {
    super(`אין מספיק מלאי למוצר ${productId}`);
    this.productId = productId;
  }
}

// "הזמן" של חנות הקפה — ב־MySQL. טרנזקציה אחת: מפתח idempotency, עגלה, נעילת המוצרים (FOR UPDATE, לפי id —
// סדר קבוע מונע deadlocks), בדיקת מלאי, הזמנה ופריטים עם המחיר של עכשיו, הורדת מלאי, ריקון העגלה
export async function createOrderFromCart(pool: Pool, customerId: number, idemKey: string): Promise<{ orderId: number; totalCents: number; replayed: boolean }> {
  const conn = await pool.getConnection();
  try {
    await conn.beginTransaction();
    // אותו מפתח בבקשה מקבילה: ה־INSERT מחכה לנעילה על המפתח, וממשיך כשהראשונה מסתיימת
    const [ins] = await conn.execute<any>("INSERT IGNORE INTO order_requests (idem_key, customer_id) VALUES (?, ?)", [idemKey, customerId]);
    if (ins.affectedRows === 0) {
      // FOR SHARE — קריאה "נועלת" רואה את הגרסה המחויבת האחרונה (לא את ה־snapshot של REPEATABLE READ)
      const [[prev]] = await conn.execute<any[]>("SELECT r.customer_id, r.order_id, o.total FROM order_requests r LEFT JOIN orders o ON o.id = r.order_id WHERE r.idem_key = ? FOR SHARE", [idemKey]);
      await conn.commit();
      if (!prev || prev.customer_id !== customerId || prev.order_id === null) throw new Error("Idempotency-Key בשימוש");
      return { orderId: prev.order_id, totalCents: Math.round(Number(prev.total) * 100), replayed: true };
    }
    const [cart] = await conn.execute<any[]>("SELECT product_id, quantity FROM cart_items WHERE customer_id = ? ORDER BY product_id", [customerId]);
    if (cart.length === 0) throw new EmptyCart("העגלה ריקה");
    const [products] = await conn.query<any[]>("SELECT id, price, stock FROM products WHERE id IN (?) ORDER BY id FOR UPDATE", [cart.map((c) => c.product_id)]);
    const byId = new Map(products.map((p) => [p.id, p]));
    let totalCents = 0;
    for (const c of cart) {
      const p = byId.get(c.product_id);
      if (!p || p.stock < c.quantity) throw new OutOfStock(c.product_id);
      totalCents += Math.round(Number(p.price) * 100) * c.quantity;
    }
    const [order] = await conn.execute<any>("INSERT INTO orders (customer_id, status, total) VALUES (?, 'pending_payment', ?)", [customerId, (totalCents / 100).toFixed(2)]);
    const orderId: number = order.insertId;
    await conn.query("INSERT INTO order_items (order_id, product_id, quantity, unit_price) VALUES ?", [cart.map((c) => [orderId, c.product_id, c.quantity, byId.get(c.product_id).price])]);
    for (const c of cart) await conn.execute("UPDATE products SET stock = stock - ? WHERE id = ?", [c.quantity, c.product_id]);
    await conn.execute("DELETE FROM cart_items WHERE customer_id = ?", [customerId]);
    await conn.execute("UPDATE order_requests SET order_id = ? WHERE idem_key = ?", [orderId, idemKey]);
    await conn.commit();
    return { orderId, totalCents, replayed: false };
  } catch (err) {
    await conn.rollback(); // גם שורת ה־idempotency מתבטלת — אפשר לנסות שוב עם אותו מפתח
    throw err;
  } finally {
    conn.release();
  }
}
⚠️ טעויות נפוצות
  • לשמור את ה־idempotency בטרנזקציה נפרדת מההזמנה — קריסה ביניהן משאירה מפתח "בטיפול" לנצח, או הזמנה בלי מפתח.

💡 רמז 1

💡 רמז 2

✅ פתרון
// P25.5-E25
import type pg from "pg";
import type { Pool } from "mysql2/promise";

// העברת טבלה מ־PostgreSQL ל־MySQL — משימה אמיתית כשמחליפים מסד או מאחדים מערכות.
// בקבוצות (keyset לפי id, לא OFFSET), עם המרת טיפוסים, ו־idempotent: הרצה שנייה לא מכפילה (ON DUPLICATE KEY UPDATE)
export async function copyCustomers(source: pg.Client | pg.Pool, target: Pool, { batchSize = 500 } = {}): Promise<{ copied: number; batches: number }> {
  let lastId = 0;
  let copied = 0;
  let batches = 0;
  for (;;) {
    const { rows } = await source.query(
      "SELECT id, name, email, is_vip, balance::text AS balance, created_at FROM customers WHERE id > $1 ORDER BY id LIMIT $2",
      [lastId, batchSize],
    );
    if (rows.length === 0) break;
    const values = rows.map((r: any) => [
      r.id,
      r.name,
      r.email,
      r.is_vip ? 1 : 0, // boolean ← TINYINT(1)
      r.balance, // numeric כמחרוזת ← DECIMAL — בלי לעבור דרך float
      // timestamptz ← DATETIME(3) ב־UTC (MySQL DATETIME לא שומר אזור זמן — מחליטים ומתעדים: UTC)
      (r.created_at as Date).toISOString().slice(0, 23).replace("T", " "),
    ]);
    await target.query(
      "INSERT INTO customers (id, name, email, is_vip, balance, created_at) VALUES ? AS new " +
        "ON DUPLICATE KEY UPDATE name = new.name, email = new.email, is_vip = new.is_vip, balance = new.balance, created_at = new.created_at",
      [values],
    );
    copied += rows.length;
    batches++;
    lastId = rows[rows.length - 1].id;
  }
  return { copied, batches };
}

במעבר אמיתי: קודם להעתיק (כמו כאן), אחר כך לכתוב לשני המסדים במקביל, להשוות, ורק אז להעביר קריאות — וכל הזמן עם דרך חזרה (expand/contract בגדול).

⚠️ טעויות נפוצות

         MAX(NON_UNIQUE) = 0 AS is_unique,
         GROUP_CONCAT(COLUMN_NAME ORDER BY SEQ_IN_INDEX SEPARATOR ',') AS cols

}

// P25.5-E94: העברה בקבוצות — עם המשך
export async function copyInBatches<R extends { id: number }>({ readBatch, writeBatch, size, startAfter = 0 }: {
  readBatch: (afterId: number, size: number) => Promise<R[]>;
  writeBatch: (rows: R[]) => Promise<void>;
  size: number;
  startAfter?: number;
}) {
  if (!Number.isInteger(size) || size <= 0) throw new RangeError(`size לא תקין: ${size}`);
  let after = startAfter;
  let batches = 0;
  let rows = 0;
  for (;;) {
    const batch = await readBatch(after, size);
    if (batch.length === 0) break;
    if (!batch.every((r, i) => r.id > (i === 0 ? after : batch[i - 1].id))) throw new Error("NOT_SORTED");
    await writeBatch(batch);
    batches++;
    rows += batch.length;
    after = batch[batch.length - 1].id;
    if (batch.length < size) break;
  }
  return { batches, rows, lastId: after };
}
⚠️ טעויות נפוצות
  • להמשיך לפי מספר הקבוצה (OFFSET batches * size) — שורה שנמחקה במקור באמצע ההעברה מזיזה את כל השאר, ושורה אחת לא מועתקת.

// P25.5-E98: שורה מ־PostgreSQL לשורה של MySQL
export function toMysqlValue(v: unknown): string | number | null {
  if (v === null || v === undefined) return null;
  if (typeof v === "boolean") return v ? 1 : 0;
  if (v instanceof Date) return v.toISOString().replace("T", " ").replace("Z", "");
  if (typeof v === "bigint") return v.toString();
  if (typeof v === "object") return JSON.stringify(v);
  return v as string | number;
}

export function pgRowToMysql(row: Record<string, unknown>) {
  return Object.fromEntries(Object.entries(row).map(([k, v]) => [k, toMysqlValue(v)]));
}

// P25.5-E99: slow query log — מה הכי איטי?
export function normalizeSql(sql: string): string {
  return sql
    .replace(/'(?:[^']|'')*'/g, "?")
    .replace(/\b\d+(?:\.\d+)?\b/g, "?")
    .replace(/\s+/g, " ")
    .trim()
    .replace(/\s*;$/, "");
}

export function slowLogReport(text: string) {
  const groups = new Map<string, { query: string; count: number; total: number; maxRowsExamined: number }>();
  for (const entry of text.split(/^# Time:/m).slice(1)) {
    const lines = entry.split("\n");
    const qi = lines.findIndex((l) => l.startsWith("# Query_time"));
    if (qi === -1) continue;
    const m = /Query_time:\s*([\d.]+).*Rows_examined:\s*(\d+)/.exec(lines[qi]);
    if (!m) continue;
    const sql = lines
      .slice(qi + 1)
      .filter((l) => !/^\s*(SET timestamp=\d+;|use \S+;)\s*$/i.test(l))
      .join("\n");
    const query = normalizeSql(sql);
    if (!query) continue;
    const g = groups.get(query) ?? { query, count: 0, total: 0, maxRowsExamined: 0 };
    g.count++;
    g.total += Number(m[1]);
    g.maxRowsExamined = Math.max(g.maxRowsExamined, Number(m[2]));
    groups.set(query, g);
  }
  return [...groups.values()]
    .map(({ query, count, total, maxRowsExamined }) => ({ query, count, totalSeconds: Math.round(total * 1000) / 1000, maxRowsExamined }))
    .sort((a, b) => b.totalSeconds - a.totalSeconds);
}

// P25.5-E100: full table scan — מ־Node
import type { Pool, RowDataPacket } from "mysql2/promise";

export async function fullScans(pool: Pool, sql: string, params: unknown[] = []) {
  const [rows] = await pool.query<RowDataPacket[]>(`EXPLAIN FORMAT=JSON ${sql}`, params);
  const raw = rows[0].EXPLAIN;
  const plan = typeof raw === "string" ? JSON.parse(raw) : raw;
  const found: { table: string; rows: number }[] = [];
  const seen = new Set<string>();
  const walk = (node: unknown): void => {
    if (Array.isArray(node)) return node.forEach(walk);
    if (node === null || typeof node !== "object") return;
    const o = node as Record<string, unknown>;
    if (typeof o.table_name === "string" && o.access_type === "ALL" && !seen.has(o.table_name)) {
      seen.add(o.table_name);
      found.push({ table: o.table_name, rows: Number(o.rows_examined_per_scan) });
    }
    Object.values(o).forEach(walk);
  };
  walk(plan);
  return found;
}

בבדיקות integration: לעטוף את ה־pool כך שכל שאילתה עוברת גם דרך fullScans, ולהיכשל אם יש סריקה של טבלה שאמורה להיות גדולה. כך אינדקס חסר מתגלה ב־PR — לא בפרודקשן.

⚠️ טעויות נפוצות
  • לחפש "ALL" כמחרוזת בכל ה־JSON — תופס גם טבלה בשם ALL_ORDERS, או ערכים אחרים.
