P25.5-E03 · REPEATABLE READ 🧠 הבנה רמה 1

💡 רמז 1

ב־REPEATABLE READ, SELECT רגיל קורא מ"תמונה" שנלקחה בקריאה הראשונה של הטרנזקציה.

💡 רמז 2

UPDATE ו־FOR UPDATE קוראים את הגרסה המחויבת האחרונה ("locking read").

✅ פתרון
  1. 10 — אותה תמונה. (ב־PostgreSQL, READ COMMITTED: 7.)
  2. 7 — קריאה נועלת רואה את האחרון.
  3. 6 — ה־UPDATE עובד על 7, ואחריו A רואה את השינוי שלו עצמו.

המסקנה: ב־MySQL, "SELECT ואז החלטה ואז UPDATE" גרוע עוד יותר מב־PostgreSQL — ה־SELECT יכול להחזיר ערך ישן בתוך הטרנזקציה. ההחלטה צריכה להיות בתוך ה־UPDATE (WHERE stock >= ?, E13) או אחרי FOR UPDATE (E09). בשיעור 3 — ההרצה האמיתית של התרחיש.

⚠️ טעויות נפוצות
  • "אני בטרנזקציה, אז אני מוגן" — טרנזקציה לא נועלת שורות שרק קראת.

P25.5-E56 · ‏REPEATABLE READ — מה A רואה? 🧠 הבנה רמה 2

💡 רמז 1

‏SELECT רגיל ב־REPEATABLE READ — מהתמונה שנלקחה בקריאה הראשונה של הטרנזקציה. ‏UPDATE — תמיד על הגרסה האחרונה.

💡 רמז 2

אחרי ש־A עדכן את השורה בעצמו, היא "שלו" — הוא רואה את השינוי של עצמו.

✅ פתרון
  1. (1) ‏10.
  2. (2) ‏10 — אותה תמונה. (ב־READ COMMITTED: ‏4.)
  3. (3) ‏3 — ה־UPDATE עבד על הגרסה האחרונה (4), ו־A רואה את השינוי של עצמו.
  4. במסד: 3.

הלקח: "קרא 10, יש מספיק, הורד 8" — ב־REPEATABLE READ ההחלטה מבוססת על 10, כשבפועל יש 4. מחליטים בתוך ה־UPDATE (WHERE stock >= ?, ‏affectedRows), או קוראים עם FOR UPDATE (השיעור, סעיף 1).

⚠️ טעויות נפוצות
  • להסיק מ־(2) שה־UPDATE של B "לא קרה" — הוא קרה ונשמר; A פשוט לא רואה אותו ב־SELECT רגיל.

P25.5-E57 · ‏FOR SHARE או FOR UPDATE? 🧠 הבנה רמה 2

💡 רמז 1

‏FOR SHARE: אחרים יכולים לקרוא (וגם לנעול ב־SHARE), לא לשנות. ‏FOR UPDATE: אף אחד לא נועל אחריך.

💡 רמז 2

נעילה = מישהו אחר מחכה. מה המחיר של לנעול שורות ל־40 שניות?

✅ פתרון
  1. רגיל — רק קוראים.
  2. FOR SHARE על המוצר — אחרים יכולים גם הם להוסיף ביקורות (נעילה משותפת), אבל אף אחד לא מוחק/משנה אותו עד ה־COMMIT. (המפתח הזר גם נועל את שורת ההורה ב־SHARE בזמן ה־INSERT.)
  3. FOR UPDATE — מחליטים לפי מה שקראנו, ואסור שמישהו ישנה בינתיים.
  4. רגיל — ועדיף על replica. נעילה הייתה עוצרת את כל העדכונים ל־40 שניות. וב־REPEATABLE READ הדוח עקבי בלי נעילות (E63).
  5. FOR UPDATE SKIP LOCKED (‏P25.5-E14).
⚠️ טעויות נפוצות
  • FOR UPDATE "ליתר ביטחון" בכל מקום — כל הבקשות מחכות זו לזו, והשרת נהיה איטי בלי שום שגיאה.

P25.5-E58 · ‏gap lock — למה INSERT מחכה? 🧠 הבנה רמה 3

💡 רמז 1

ב־REPEATABLE READ, ‏FOR UPDATE מבטיח שגם שורות חדשות שמתאימות לתנאי לא יופיעו עד הסוף (‏"phantoms").

💡 רמז 2

בלי אינדקס — כדי למצוא את השורות שמתאימות, InnoDB סורק את הכול. מה הוא נועל בדרך?

✅ פתרון
  1. כדי ש־FOR UPDATE באמת "יחזיק" את כל מה שמתאים ל־status = 'queued', ‏InnoDB נועל גם את הפערים (gaps) באינדקס — שם שורות חדשות היו נכנסות. בלי אינדקס על status — הוא סרק את המפתח הראשי כולו, ונעל את כל השורות ואת כל הפערים: כל INSERT מחכה.
  2. PostgreSQL לא מונע phantoms בנעילות (ב־READ COMMITTED אין צורך; ב־SERIALIZABLE הוא מזהה התנגשות אחרת). ל־InnoDB ב־REPEATABLE READ יש gap locks.
  3. עם אינדקס, הסריקה (והנעילה) רק על הטווח של 'queued' — INSERT עם status אחר לא מחכה. (‏INSERT של 'queued' — אולי, תלוי איפה בפער.)
  4. LIMIT 1 … FOR UPDATE SKIP LOCKED — לוקחים עבודה אחת, לא את כולן; טרנזקציות קצרות; ואם מתאים — רמת בידוד READ COMMITTED לחיבור של ה־worker (בה אין gap locks בחיפושים רגילים).
⚠️ טעויות נפוצות
  • להגדיל את innodb_lock_wait_timeout "כי ה־INSERT נכשל" — הבעיה היא היקף הנעילה, לא הזמן.

P25.5-E59 · ‏NOWAIT מול SKIP LOCKED 🧠 הבנה רמה 2

💡 רמז 1

‏NOWAIT — שגיאה מיד אם נעול. ‏SKIP LOCKED — מתעלם מהנעולות ומחזיר את השאר.

💡 רמז 2

האם התשובה הנכונה היא "השורה הזו בדיוק", או "שורה כלשהי שמתאימה"?

✅ פתרון
  1. NOWAIT — המושב הזה בדיוק; נעול ← הודעה מיידית (E62).
  2. SKIP LOCKED — כל worker לוקח עבודה אחרת, אף אחד לא מחכה.
  3. FOR UPDATE רגיל (בסדר קבוע, E61) — חייבים את שני הארנקים האלה, ושווה לחכות כמה מילישניות.
  4. FOR UPDATE רגיל.
  5. SKIP LOCKED עם LIMIT 1 — מושב שאף אחד לא באמצע להזמין.
⚠️ טעויות נפוצות
  • SKIP LOCKED כשרוצים שורה מסוימת — "המושב שלך" פשוט לא חוזר, ונראה כאילו הוא לא קיים.

P25.5-E60 · ‏FOR UPDATE בלי טרנזקציה 🧠 הבנה רמה 2

💡 רמז 1

בלי START TRANSACTION, כל פקודה היא טרנזקציה משלה (autocommit).

💡 רמז 2

‏pool.query — כל קריאה, חיבור אחר אולי.

✅ פתרון
  1. ב־autocommit, ה־SELECT … FOR UPDATE הוא טרנזקציה של פקודה אחת: הנעילה משתחררת ברגע שהוא מסתיים — לפני ה־UPDATE. שתי בקשות קוראות 10, ושתיהן מורידות.
  2. (א) getConnection ← ‏beginTransaction ← SELECT … FOR UPDATE ← בדיקה ← UPDATE ← ‏commit (ו־rollback/‏release). (ב) בלי טרנזקציה: UPDATE … SET stock = stock - ? WHERE id = ? AND stock >= ?, ו־affectedRows === 0 ← אין מלאי (‏P25.5-E13).
  3. טרנזקציה שייכת לחיבור. ‏BEGIN על חיבור אחד ו־UPDATE על אחר — ה־UPDATE בכלל לא בתוך הטרנזקציה, והחיבור הראשון נשאר עם טרנזקציה פתוחה ונעילות.
⚠️ טעויות נפוצות
  • pool.query("START TRANSACTION") — נראה נכון, ובפועל פותח טרנזקציה על חיבור אקראי ששאר הקוד לא משתמש בו.

P25.5-E13 · מלאי תחת עומס 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

UPDATE … SET stock = stock - ? WHERE id = ? AND stock >= ?.

💡 רמז 2

affectedRows — לא changedRows.

✅ פתרון
// P25.5-E13
import type { Pool } from "mysql2/promise";

// הורדת מלאי בפקודה אחת, מותנית. ב־MySQL: affectedRows = כמה שורות *התאימו* ל־WHERE ושונו.
// (changedRows — רק שורות שהערך בהן באמת השתנה. כאן זה אותו דבר, אבל ב־UPDATE שקובע ערך זהה — changedRows הוא 0)
export async function reserveStock(pool: Pool, productId: number, quantity: number): Promise<boolean> {
  if (!Number.isInteger(quantity) || quantity <= 0) throw new Error("כמות לא תקינה");
  const [res] = await pool.execute<any>("UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?", [quantity, productId, quantity]);
  return res.affectedRows === 1;
}
⚠️ טעויות נפוצות
  • SELECT stock ואז UPDATE — ב־REPEATABLE READ ה־SELECT יכול אפילו להחזיר ערך ישן מתוך הטרנזקציה שלך (E03).

P25.5-E14 · תור עבודות: SKIP LOCKED 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

טרנזקציה: SELECT id … ORDER BY id LIMIT ? FOR UPDATE SKIP LOCKED, ואז UPDATE על ה־ids, ו־COMMIT.

💡 רמז 2

בלי SKIP LOCKED — worker שני מחכה לראשון (ואז מוצא את אותן שורות כבר running). עם — מדלג ולוקח את הבאות.

✅ פתרון
// P25.5-E14
import type { Pool } from "mysql2/promise";

// תור עבודות על טבלה: כמה workers לוקחים עבודות במקביל, בלי שאותה עבודה תילקח פעמיים.
// FOR UPDATE נועל את השורות שנבחרו; SKIP LOCKED (MySQL 8.0+) מדלג על נעולות במקום לחכות להן
export async function claimJobs(pool: Pool, workerId: string, limit: number): Promise<number[]> {
  const conn = await pool.getConnection();
  try {
    await conn.beginTransaction();
    const [rows] = await conn.query<any[]>("SELECT id FROM jobs WHERE status = 'queued' ORDER BY id LIMIT ? FOR UPDATE SKIP LOCKED", [limit]);
    const ids = rows.map((r) => r.id as number);
    if (ids.length) await conn.query("UPDATE jobs SET status = 'running', locked_by = ? WHERE id IN (?)", [workerId, ids]);
    await conn.commit();
    return ids;
  } catch (err) {
    await conn.rollback();
    throw err;
  } finally {
    conn.release();
  }
}

זה דפוס שמאפשר תור בלי Redis ובלי broker — כשהעומס צנוע. ביחידה 26.5 נראה מתי עוברים ל־RabbitMQ, Kafka או SQS.

⚠️ טעויות נפוצות
  • לשכוח שהנעילה חיה רק עד ה־COMMIT — אם הסימון (UPDATE) לא באותה טרנזקציה, אחרים יראו את העבודות כ־queued.

P25.5-E15 · deadlock, ואיך חיים איתו 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

(err as { errno?: number }).errno.

💡 רמז 2

ה־fn הוא כל הטרנזקציה — InnoDB ביטל את כולה, אז מנסים את כולה.

✅ פתרון
// P25.5-E15
// InnoDB מזהה deadlock ומבטל את אחת הטרנזקציות (errno 1213, ER_LOCK_DEADLOCK); המתנה ארוכה לנעילה — 1205.
// שתיהן "בטוחות לנסות שוב": הטרנזקציה בוטלה כולה. מנסים שוב את *כל* הטרנזקציה, עם המתנה קצרה ואקראית
export const RETRYABLE = new Set([1213, 1205]);

export async function withDeadlockRetry<T>(
  fn: (attempt: number) => Promise<T>,
  { retries = 3, sleep = (ms: number) => new Promise<void>((r) => setTimeout(r, ms)), random = Math.random } = {},
): Promise<T> {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fn(attempt);
    } catch (err) {
      const errno = (err as { errno?: number }).errno;
      if (attempt >= retries || errno === undefined || !RETRYABLE.has(errno)) throw err;
      await sleep(Math.floor(random() * 20 * 2 ** attempt));
    }
  }
}

מה עדיף על retry: שה־deadlock לא יקרה — לנעול תמיד באותו סדר (ORDER BY id FOR UPDATE, כמו ב־E09 ו־E24), טרנזקציות קצרות, ואינדקסים שמונעים נעילה של יותר שורות מהנדרש. אבל במערכת עמוסה deadlock יקרה בסוף — ו־retry הוא חלק מהתשובה.

⚠️ טעויות נפוצות
  • retry על פקודה בודדת מתוך הטרנזקציה — אחרי deadlock כל הטרנזקציה בוטלה, והפקודות שלפני כבר לא קיימות.

P25.5-E17 · idempotency ב־MySQL 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

INSERT IGNORE ואז affectedRows: 1 = אני הראשון.

💡 רמז 2

mysql2 מחזיר JSON כאובייקט — אבל אם בעתיד תשנה טיפוס עמודה, בדוק גם מחרוזת.

✅ פתרון
// P25.5-E17
import type { Pool } from "mysql2/promise";

export class InProgress extends Error {}

// Idempotency ב־MySQL: INSERT IGNORE על מפתח ראשי — affectedRows 1 = "אני הראשון", 0 = כבר קיים.
// (ב־PostgreSQL: ON CONFLICT DO NOTHING RETURNING.) התוצאה נשמרת כ־JSON, והבקשה החוזרת מקבלת אותה
export async function once<T>(pool: Pool, key: string, fn: () => Promise<T>): Promise<{ result: T; replayed: boolean }> {
  const [ins] = await pool.execute<any>("INSERT IGNORE INTO idempotency (idem_key, status) VALUES (?, 'pending')", [key]);
  if (ins.affectedRows === 1) {
    try {
      const result = await fn();
      await pool.execute("UPDATE idempotency SET status = 'done', result = ? WHERE idem_key = ?", [JSON.stringify(result), key]);
      return { result, replayed: false };
    } catch (err) {
      await pool.execute("DELETE FROM idempotency WHERE idem_key = ?", [key]); // נכשל ← אפשר לנסות שוב עם אותו מפתח
      throw err;
    }
  }
  const [rows] = await pool.execute<any[]>("SELECT status, result FROM idempotency WHERE idem_key = ?", [key]);
  if (!rows[0] || rows[0].status !== "done") throw new InProgress(`בקשה ${key} עדיין בטיפול`);
  const stored = rows[0].result;
  return { result: (typeof stored === "string" ? JSON.parse(stored) : stored) as T, replayed: true };
}
⚠️ טעויות נפוצות
  • INSERT IGNORE מתעלם לא רק מכפילות — גם משגיאות אחרות (ערך ארוך מדי נחתך, ועוד). כאן זה בטוח (מפתח קצר), אבל בכל מקום אחר — ON DUPLICATE KEY UPDATE idem_key = idem_key מדויק יותר.

P25.5-E22 · תור עבודות — שלוש תקלות 🤖 💻 כתיבת קוד 🤖 רמה 4

💡 רמז 1

איפה הטרנזקציה? ובאיזה חיבור רצה כל פקודה?

💡 רמז 2

כמה שורות ה־SELECT מחזיר?

✅ פתרון
// P25.5-E22
import type { Pool } from "mysql2/promise";

export async function claimJobs(pool: Pool, workerId: string, limit: number): Promise<number[]> {
  const conn = await pool.getConnection(); // תקלה 1: היה pool.query ישירות ← כל פקודה בחיבור אחר, בלי טרנזקציה — הנעילה משתחררת מיד אחרי ה־SELECT
  try {
    await conn.beginTransaction();
    // תקלה 2: בלי FOR UPDATE SKIP LOCKED ← שני workers קוראים אותן שורות ושניהם "לוקחים"
    // תקלה 3: לא היה LIMIT ← worker אחד "לקח" את כל התור, והשאר עמדו בטלים
    const [rows] = await conn.query<any[]>("SELECT id FROM jobs WHERE status = 'queued' ORDER BY id LIMIT ? FOR UPDATE SKIP LOCKED", [limit]);
    const ids = rows.map((r) => r.id as number);
    if (ids.length) await conn.query("UPDATE jobs SET status = 'running', locked_by = ? WHERE id IN (?)", [workerId, ids]);
    await conn.commit();
    return ids;
  } catch (err) {
    await conn.rollback();
    throw err;
  } finally {
    conn.release();
  }
}
⚠️ טעויות נפוצות
  • "לתקן" עם FOR UPDATE בלי טרנזקציה — ב־autocommit הנעילה משתחררת בסוף ה־SELECT עצמו.

P25.5-E61 · העברה בין ארנקים — בלי deadlock 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1
SELECT customer_id, balance FROM wallets WHERE customer_id IN (?, ?) ORDER BY customer_id FOR UPDATE
💡 רמז 2
try { beginTransaction … commit } catch { rollback; throw } finally { release }

כמו בשיעור 4.

✅ פתרון
// P25.5-E61: העברה בין ארנקים — בלי deadlock
import type { Pool, RowDataPacket } from "mysql2/promise";

export async function transfer(pool: Pool, fromId: number, toId: number, amount: number) {
  if (!Number.isInteger(amount) || amount <= 0) throw new RangeError(`סכום לא תקין: ${amount}`);
  if (fromId === toId) throw new Error("SAME_WALLET");
  const conn = await pool.getConnection();
  try {
    await conn.beginTransaction();
    // תמיד מהקטן לגדול — כך שתי העברות הפוכות לא נועלות "אחת מכל צד"
    const [rows] = await conn.query<RowDataPacket[]>(
      "SELECT customer_id, balance FROM wallets WHERE customer_id IN (?, ?) ORDER BY customer_id FOR UPDATE",
      [fromId, toId],
    );
    if (rows.length !== 2) throw new Error("WALLET_NOT_FOUND");
    const balance = new Map(rows.map((r) => [Number(r.customer_id), Number(r.balance)]));
    const from = balance.get(fromId)! - amount;
    const to = balance.get(toId)! + amount;
    if (from < 0) throw new Error("INSUFFICIENT_FUNDS");
    await conn.query("UPDATE wallets SET balance = ? WHERE customer_id = ?", [from, fromId]);
    await conn.query("UPDATE wallets SET balance = ? WHERE customer_id = ?", [to, toId]);
    await conn.commit();
    return { from, to };
  } catch (err) {
    await conn.rollback();
    throw err;
  } finally {
    conn.release();
  }
}

נעילה בשאילתה אחת עם ORDER BY — InnoDB נועל את השורות לפי סדר הקריאה. העברה 1←4 והעברה 4←1 נועלות שתיהן קודם את 1: השנייה מחכה, ואין מעגל.

⚠️ טעויות נפוצות
  • שני SELECT … FOR UPDATE — קודם fromId ואז toId. בהעברות הפוכות במקביל: deadlock (‏1213), ואחת מהן נכשלת.

P25.5-E62 · מושב — עכשיו או אף פעם (NOWAIT) 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

SELECT reserved_by FROM seats WHERE id = ? FOR UPDATE NOWAIT.

💡 רמז 2

ב־catch: (err as { errno?: number }).errno === 3572 ← rollback ו־"busy".

✅ פתרון
// P25.5-E62: מושב — עכשיו או אף פעם (NOWAIT)
import type { Pool, RowDataPacket } from "mysql2/promise";

const ER_LOCK_NOWAIT = 3572;

export async function reserveSeat(pool: Pool, seatId: number, customerId: number) {
  const conn = await pool.getConnection();
  try {
    await conn.beginTransaction();
    const [rows] = await conn.query<RowDataPacket[]>("SELECT reserved_by FROM seats WHERE id = ? FOR UPDATE NOWAIT", [seatId]);
    let result: "reserved" | "taken" | "not_found";
    if (rows.length === 0) result = "not_found";
    else if (rows[0].reserved_by !== null) result = "taken";
    else {
      await conn.query("UPDATE seats SET reserved_by = ? WHERE id = ?", [customerId, seatId]);
      result = "reserved";
    }
    await conn.commit();
    return result;
  } catch (err) {
    await conn.rollback();
    if ((err as { errno?: number }).errno === ER_LOCK_NOWAIT) return "busy" as const;
    throw err;
  } finally {
    conn.release();
  }
}

בלי NOWAIT, המשתמש השני "נתקע" עד שהראשון מסיים (ואם הוא באמצע תשלום של דקה — עד ה־timeout של 50 שניות). עם NOWAIT — תשובה תוך מילישניות, וה־UI מציג "המושב בתהליך הזמנה".

⚠️ טעויות נפוצות
  • לתפוס את כל השגיאות כ־"busy" — ואז מסד שנפל נראה למשתמש כמו "מישהו אחר מזמין".

P25.5-E63 · דוח עקבי — תמונה אחת 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

START TRANSACTION READ ONLY, WITH CONSISTENT SNAPSHOT — התמונה נלקחת מיד, ולא בקריאה הראשונה.

💡 רמז 2

‏SUM של DECIMAL חוזר כמחרוזת (בלי decimalNumbers) — ‏Number(...), ‏COALESCE(…, 0) לרשימה ריקה.

✅ פתרון
// P25.5-E63: דוח עקבי — תמונה אחת
import type { Pool, RowDataPacket } from "mysql2/promise";

export async function salesReport(pool: Pool, between?: () => Promise<void>) {
  const conn = await pool.getConnection();
  try {
    await conn.query("START TRANSACTION READ ONLY, WITH CONSISTENT SNAPSHOT");
    const [[sum]] = await conn.query<RowDataPacket[]>(
      "SELECT COUNT(*) AS orders, COALESCE(SUM(total), 0) AS revenue FROM orders WHERE status IN ('paid', 'shipped')",
    );
    await between?.();
    const [rows] = await conn.query<RowDataPacket[]>("SELECT id FROM orders WHERE status IN ('paid', 'shipped') ORDER BY id");
    await conn.query("COMMIT");
    return { orders: Number(sum.orders), revenue: Number(sum.revenue), ids: rows.map((r) => Number(r.id)) };
  } catch (err) {
    await conn.query("ROLLBACK");
    throw err;
  } finally {
    conn.release();
  }
}

‏READ ONLY אומר ל־InnoDB שלא יהיו כתיבות — קצת פחות עבודה, ושגיאה אם מישהו בטעות מוסיף UPDATE. בלי טרנזקציה, כל שאילתה רואה את המצב של הרגע שלה — והדוח "40 הזמנות" עם רשימה של 41.

⚠️ טעויות נפוצות
  • pool.query לכל שאילתה, עם START TRANSACTION ב־pool.query נפרד — הן לא באותו חיבור, ואין snapshot משותף.

P25.5-E64 · ‏READ COMMITTED מפרק 18 מול REPEATABLE READ 🧠 הבנה רמה 2

💡 רמז 1

‏UPDATE עם תנאי — תמיד על הגרסה האחרונה, בשני המסדים.

💡 רמז 2

ב־REPEATABLE READ — כל SELECT רגיל מאותה תמונה.

✅ פתרון
  1. לא משתנה — בטוח בשניהם. ההחלטה בתוך ה־UPDATE.
  2. שבור בשניהם (lost update) — אבל ב־MySQL גרוע יותר: גם אם עברו כמה שניות בין שני SELECTים באותה טרנזקציה, הוא ימשיך לראות את הערך הישן.
  3. משתנה לטובה: ב־PostgreSQL (READ COMMITTED) הספירה והסכום יכולים לא להתאים; ב־MySQL — אותה תמונה (E63).
  4. לא משתנה — בטוח בשניהם.
⚠️ טעויות נפוצות
  • "להתאים" את MySQL ל־PostgreSQL עם SET GLOBAL transaction_isolation = 'READ-COMMITTED' בלי לבדוק — זה משנה התנהגות לכל המערכת, כולל דוחות שסמכו על RR.

P25.5-E65 · ‏INSERT IGNORE — למה מסוכן? 🧠 הבנה רמה 2

💡 רמז 1

‏IGNORE הופך שגיאות ל־warnings — לא רק duplicate key.

💡 רמז 2

ערך ארוך מדי לעמודה, NULL בעמודת NOT NULL, מפתח זר שלא קיים.

✅ פתרון
  1. ‏IGNORE מוריד את רמת השגיאה של כמעט כל בעיה בשורה: מפתח ארוך מ־VARCHAR ← נחתך בשקט; NULL בעמודת NOT NULL ← ערך ברירת מחדל ("" או 0); מפתח זר לא קיים ← השורה לא נכנסת, עם warning.
  2. מפתח של 300 תווים נחתך ל־255 — שני מפתחות שונים שמתחילים באותו דבר "מתנגשים", והשני מקבל replay של הראשון. מפתח זר שגוי ← ‏affectedRows 0 ← "מישהו אחר תפס" ← לולאה של 409. הכול בלי שגיאה בלוג.
  3. INSERT רגיל, ותפיסה של errno 1062 (‏ER_DUP_ENTRY) בלבד — שגיאה אחרת היא שגיאה (‏P25.5-E17). או INSERT … ON DUPLICATE KEY UPDATE idem_key = idem_key ו־affectedRows (1 = חדש, 0 = קיים) — שמגיב רק להתנגשות במפתח.
⚠️ טעויות נפוצות
  • להשתמש ב־IGNORE בייבוא נתונים "כדי שלא ייעצר" — ואז מגלים חודש אחר כך ש־3% מהשורות נחתכו.

P25.5-E66 · ‏Prisma, ‏$transaction ו־deadlock 🧠 הבנה רמה 2

💡 רמז 1

‏deadlock מבטל את כל הטרנזקציה.

💡 רמז 2

Prisma לא בוחר עבורך את הסדר שבו אתה ניגש לשורות.

✅ פתרון
  1. מערך — פקודות מוכנות מראש, שרצות ברצף בטרנזקציה אחת; קצר וצפוי. interactive (‏async (tx)) — קוד שלך באמצע, שיכול לקרוא, להחליט ולכתוב — ולהחזיק נעילות זמן ארוך יותר (במיוחד אם יש בו await לשירות חיצוני).
  2. מסביב: אחרי deadlock כל הטרנזקציה בוטלה, ולכן מנסים שוב את כולה — withDeadlockRetry(() => prisma.$transaction(…)) (‏P25.5-E15), על P2034 בלבד.
  3. לגשת לשורות באותו סדר (למשל orderBy: { id: "asc" } לפני עדכונים, או עדכונים ממוינים לפי id), טרנזקציות קצרות בלי קריאות רשת באמצע, ואינדקסים שמצמצמים מה ננעל (E58).
⚠️ טעויות נפוצות
  • retry רק על הפקודה שנכשלה בתוך async (tx) — הטרנזקציה כבר בוטלה, וה־tx לא שמיש.

P25.5-E67 · ספירת צפיות — 50 במקביל 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1
INSERT INTO product_views (product_id, day, views) VALUES (?, ?, 1) AS n ON DUPLICATE KEY UPDATE views = product_views.views + 1
💡 רמז 2

‏LIMIT ? עובד עם execute ו־query.

✅ פתרון
// P25.5-E67: ספירת צפיות — 50 במקביל
import type { Pool, RowDataPacket } from "mysql2/promise";

export async function recordView(pool: Pool, productId: number, day: string): Promise<void> {
  await pool.execute(
    "INSERT INTO product_views (product_id, day, views) VALUES (?, ?, 1) AS n ON DUPLICATE KEY UPDATE views = product_views.views + 1",
    [productId, day],
  );
}

export async function topProducts(pool: Pool, day: string, limit: number) {
  const [rows] = await pool.query<RowDataPacket[]>(
    "SELECT product_id, views FROM product_views WHERE day = ? ORDER BY views DESC, product_id LIMIT ?",
    [day, limit],
  );
  return rows.map((r) => ({ productId: Number(r.product_id), views: Number(r.views) }));
}
⚠️ טעויות נפוצות
  • ‏SELECT ואז INSERT או UPDATE — שתי הבעיות של P25.5-E52: Duplicate entry, וצפיות שנעלמות.

P25.5-E68 · ‏POST /orders עם mysql2 — בלי למכור יותר מדי 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1
UPDATE products SET stock = stock - ? WHERE id = ? AND is_active AND stock >= ?

← ‏affectedRows. אם 0 — ‏SELECT קטן כדי להבדיל בין 404 ל־409.

💡 רמז 2

אגורות: Math.round(Number(price) * 100) * quantity — ‏price מגיע כמחרוזת (שיעור 4).

✅ פתרון
// P25.5-E68: POST /orders עם mysql2 — בלי למכור יותר מדי
import { Router } from "express";
import type { Pool, ResultSetHeader, RowDataPacket } from "mysql2/promise";

const fail = (code: string) => ({ error: { code } });
const isPositiveInt = (v: unknown) => Number.isInteger(v) && (v as number) > 0;

export function ordersRouter(pool: Pool) {
  const router = Router();
  router.post("/orders", async (req, res, next) => {
    const { customerId, productId, quantity } = req.body ?? {};
    if (![customerId, productId, quantity].every(isPositiveInt)) {
      res.status(400).json(fail("VALIDATION_ERROR"));
      return;
    }
    const conn = await pool.getConnection();
    try {
      await conn.beginTransaction();
      const [upd] = await conn.query<ResultSetHeader>(
        "UPDATE products SET stock = stock - ? WHERE id = ? AND is_active AND stock >= ?",
        [quantity, productId, quantity],
      );
      if (upd.affectedRows === 0) {
        const [found] = await conn.query<RowDataPacket[]>("SELECT id FROM products WHERE id = ? AND is_active", [productId]);
        await conn.rollback();
        res.status(found.length ? 409 : 404).json(fail(found.length ? "OUT_OF_STOCK" : "PRODUCT_NOT_FOUND"));
        return;
      }
      const [[p]] = await conn.query<RowDataPacket[]>("SELECT price FROM products WHERE id = ?", [productId]);
      const [order] = await conn.query<ResultSetHeader>(
        "INSERT INTO orders (customer_id, status, total) VALUES (?, 'pending_payment', ? * ?)",
        [customerId, p.price, quantity],
      );
      await conn.query("INSERT INTO order_items (order_id, product_id, quantity, unit_price) VALUES (?, ?, ?, ?)", [order.insertId, productId, quantity, p.price]);
      await conn.commit();
      res.status(201).json({ orderId: order.insertId, totalCents: Math.round(Number(p.price) * 100) * quantity });
    } catch (err) {
      await conn.rollback();
      if ((err as { errno?: number }).errno === 1452) {
        res.status(404).json(fail("CUSTOMER_NOT_FOUND"));
        return;
      }
      next(err);
    } finally {
      conn.release();
    }
  });
  return router;
}

ה־UPDATE עם התנאי הוא גם הבדיקה וגם הנעילה: שתי בקשות על היחידה האחרונה — השנייה מחכה לראשונה, ואחרי ה־COMMIT שלה רואה stock = 0 ולא מעדכנת.

⚠️ טעויות נפוצות
  • להוריד מלאי ואחר כך ליצור הזמנה — מחוץ לטרנזקציה. לקוח לא קיים ← ההזמנה נכשלת, והמלאי כבר ירד.

P25.5-E69 · מחיקת לקוח — בלי לשבור הזמנות 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

CONCAT('deleted+', id, '@invalid.local') — ב־SQL, או בונים את המחרוזת ב־TS.

💡 רמז 2

‏affectedRows של ה־UPDATE — 0 ← הלקוח לא קיים ← throw (וה־catch עושה rollback של המחיקה).

✅ פתרון
// P25.5-E69: מחיקת לקוח — בלי לשבור הזמנות
import type { Pool, ResultSetHeader } from "mysql2/promise";

export async function anonymizeCustomer(pool: Pool, customerId: number) {
  const conn = await pool.getConnection();
  try {
    await conn.beginTransaction();
    const [cart] = await conn.query<ResultSetHeader>("DELETE FROM cart_items WHERE customer_id = ?", [customerId]);
    const [upd] = await conn.query<ResultSetHeader>(
      "UPDATE customers SET name = 'Deleted user', email = CONCAT('deleted+', id, '@invalid.local'), city = '' WHERE id = ?",
      [customerId],
    );
    if (upd.affectedRows === 0) throw new Error("NOT_FOUND");
    await conn.commit();
    return { cartItemsRemoved: cart.affectedRows };
  } catch (err) {
    await conn.rollback();
    throw err;
  } finally {
    conn.release();
  }
}

האימייל עם ה־id נשאר ייחודי (ה־UNIQUE לא נשבר), לא מגיע לאף אחד (.invalid הוא דומיין שמור), ומאפשר לאדם להירשם שוב עם הכתובת האמיתית שלו.

⚠️ טעויות נפוצות
  • email = '' — הלקוח השני שנמחק נכשל על UNIQUE.
  • למחוק את העגלה בפקודה נפרדת לפני הטרנזקציה — כישלון ב־UPDATE משאיר לקוח "חי" עם עגלה ריקה.
