P25.5-E43 · ‏LAST_INSERT_ID — של מי? 🧠 הבנה רמה 2

💡 רמז 1

‏LAST_INSERT_ID() שייך לחיבור. ‏pool.query — כל קריאה יכולה לקבל חיבור אחר.

💡 רמז 2

שרת אחר (או בקשה אחרת באותו שרת) יכול להכניס לקוח בין שתי הפקודות.

✅ פתרון
  1. א — לא. שתי הקריאות יכולות לרוץ על שני חיבורים שונים מה־pool, וה־LAST_INSERT_ID() של החיבור השני הוא של מישהו אחר (או 0). עם getConnection ושתי הפקודות עליו — כן.
  2. ב — כן. ‏insertId מגיע בתשובה לאותה פקודה. זו הדרך.
  3. ג — לא. בקשה אחרת יכולה להכניס שורה מיד אחרי — זה מרוץ קלאסי (פרק 18).

שלוש שורות: insertId (ו־LAST_INSERT_ID()) הוא ה־id של הראשונה (שיעור 2). ב־InnoDB עם INSERT פשוט של כמה שורות, המזהים רציפים — insertId, ‏+1, ‏+2. ואם צריך ודאות מלאה — לשאול אחרי, לפי מפתח טבעי (WHERE email IN (?)).

⚠️ טעויות נפוצות
  • "עובד אצלי" — בבדיקה עם בקשה אחת, ה־pool נותן אותו חיבור. תחת עומס — לא.

P25.5-E44 · ‏upsert על טבלה עם שני מפתחות ייחודיים 🧠 הבנה רמה 3

💡 רמז 1

‏ON DUPLICATE KEY מגיב להתנגשות בכל מפתח ייחודי — כאן ב־username.

💡 רמז 2

ב־PostgreSQL: ON CONFLICT (email) — בוחרים את המפתח.

✅ פתרון
CREATE TABLE accounts (
  id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  email VARCHAR(100) NOT NULL UNIQUE,
  username VARCHAR(50) NOT NULL UNIQUE,
  visits INT NOT NULL DEFAULT 1
);
INSERT INTO accounts (email, username) VALUES ('dana@x.com', 'dana'), ('yossi@x.com', 'yossi');
INSERT INTO accounts (email, username) VALUES ('new@x.com', 'dana') AS n
  ON DUPLICATE KEY UPDATE visits = accounts.visits + 1, email = n.email;
SELECT id, email, username, visits FROM accounts ORDER BY id;
+----+-------------+----------+--------+
| id | email       | username | visits |
+----+-------------+----------+--------+
|  1 | new@x.com   | dana     |      2 |
|  2 | yossi@x.com | yossi    |      1 |
+----+-------------+----------+--------+

ה־username dana כבר תפוס ← "התנגשות" ← ה־UPDATE רץ על השורה של דנה: האימייל שלה הוחלף ב־new@x.com. מי שניסה להירשם "השתלט" על חשבון קיים — בלי שגיאה. ב־PostgreSQL: ‏ON CONFLICT (email) DO UPDATE … — התנגשות ב־username הייתה זורקת שגיאה, כמו שצריך. ב־MySQL: upsert רק על טבלה שיש בה בדיוק מפתח ייחודי אחד רלוונטי — אחרת INSERT רגיל, ותפיסה של שגיאת 1062.

⚠️ טעויות נפוצות
  • להוסיף UNIQUE לטבלה קיימת בלי לבדוק אילו upserts כבר רצים עליה — ה־upsert משנה התנהגות בשקט.

P25.5-E45 · ‏ROW_COUNT אחרי upsert — 0, ‏1 או 2 🧠 הבנה רמה 2

💡 רמז 1

1 — נוספה שורה. 2 — עודכנה. ומה אם ה־UPDATE לא שינה כלום?

💡 רמז 2

אותו ערך בדיוק — "לא השתנה".

✅ פתרון
INSERT INTO cart_items (customer_id, product_id, quantity) VALUES (2, 6, 1) AS n
  ON DUPLICATE KEY UPDATE quantity = n.quantity;
SELECT ROW_COUNT() AS first;
INSERT INTO cart_items (customer_id, product_id, quantity) VALUES (2, 6, 3) AS n
  ON DUPLICATE KEY UPDATE quantity = n.quantity;
SELECT ROW_COUNT() AS second;
INSERT INTO cart_items (customer_id, product_id, quantity) VALUES (2, 6, 3) AS n
  ON DUPLICATE KEY UPDATE quantity = n.quantity;
SELECT ROW_COUNT() AS third;
+-------+
| first |
+-------+
|     1 |
+-------+
+--------+
| second |
+--------+
|      2 |
+--------+
+-------+
| third |
+-------+
|     0 |
+-------+

ב־CLI: ‏1 = נוצר, 2 = עודכן, 0 = כבר היה בדיוק כך. ב־mysql2 זה affectedRows — אבל mysql2 מבקש מהשרת "found rows" כברירת מחדל, ואז "כבר היה כך" מחזיר 1, כמו "נוצר" (E71). כלומר: ‏2 ← בטוח עודכן; ‏1 ← נוצר או לא השתנה. אם ה־API חייב להבדיל בין 201 ל־200 — בודקים קיום לפני (בטרנזקציה, עם נעילה), או מחזירים 200 תמיד (‏PUT idempotent, פרק 24).

⚠️ טעויות נפוצות
  • לבדוק affectedRows === 1 בתור "הצליח" — עדכון מחזיר 2, ומסומן כ"נכשל".

P25.5-E46 · ‏ONLY_FULL_GROUP_BY — מה עובר? 🧠 הבנה רמה 2

💡 רמז 1

עמודה שלא ב־GROUP BY מותרת רק אם היא תלויה פונקציונלית במה שכן — למשל במפתח הראשי.

💡 רמז 2

‏ANY_VALUE אומר ל־MySQL "אני יודע שזה ערך כלשהו מהקבוצה".

✅ פתרון
SELECT category, COUNT(*) AS n FROM products GROUP BY category;
SELECT category, name FROM products GROUP BY category;
SELECT p.id, p.name, SUM(oi.quantity) AS sold FROM products p JOIN order_items oi ON oi.product_id = p.id GROUP BY p.id;
SELECT category, ANY_VALUE(name) AS some_name, MAX(price) AS top FROM products GROUP BY category;
+-------------+---+
| category    | n |
+-------------+---+
| accessories | 2 |
| beans       | 3 |
| brewing     | 4 |
| grinders    | 2 |
+-------------+---+
ERROR 1055 (42000): Expression #2 of SELECT list is not in GROUP BY clause and contains nonaggregated column 'snippet.products.name' which is not functionally dependent on columns in GROUP BY clause; this is incompatible with sql_mode=only_full_group_by
+----+----------------------+------+
| id | name                 | sold |
+----+----------------------+------+
|  1 | Ethiopia Beans 1kg   |    2 |
|  4 | Hand Grinder         |    1 |
|  5 | Electric Grinder Pro |    1 |
|  9 | Paper Filters (100)  |    1 |
|  6 | French Press 1L      |    3 |
+----+----------------------+------+
+-------------+---------------------+--------+
| category    | some_name           | top    |
+-------------+---------------------+--------+
| accessories | Paper Filters (100) | 129.00 |
| beans       | Ethiopia Beans 1kg  |  89.90 |
| brewing     | French Press 1L     | 229.00 |
| grinders    | Hand Grinder        | 649.00 |
+-------------+---------------------+--------+
  1. עוברת.
  2. נכשלת — name לא נקבע לפי category.
  3. עוברת — p.name תלוי ב־p.id, המפתח הראשי.
  4. עוברת — אבל some_name הוא שם כלשהו מהקטגוריה, לא בהכרח של המוצר היקר. ‏ANY_VALUE מכבה את הבדיקה; הוא לא מוצא "את השורה של המקסימום". בשביל זה — window function (‏P25.5-E07).
⚠️ טעויות נפוצות
  • לכבות ONLY_FULL_GROUP_BY ב־sql_mode "כי המערכת הישנה עבדה ככה" — הבאגים של התוצאות ה"כלשהן" חוזרים.

P25.5-E47 · ‏‎->‎ מול ‎->>‎ 🧠 הבנה רמה 2

💡 רמז 1

‏-> מחזיר ערך JSON (עם מרכאות, לטקסט). ‏->> — טקסט רגיל.

💡 רמז 2

MySQL משווה JSON למחרוזת לפי כללי JSON.

✅ פתרון
SELECT name,
       attributes->'$.roast' = 'light' AS arrow,
       attributes->>'$.roast' = 'light' AS double_arrow,
       attributes->'$.weight_g' > 500 AS heavy,
       attributes->'$.missing' IS NULL AS missing_is_null
FROM products WHERE category = 'beans' ORDER BY id;
+--------------------+-------+--------------+-------+-----------------+
| name               | arrow | double_arrow | heavy | missing_is_null |
+--------------------+-------+--------------+-------+-----------------+
| Ethiopia Beans 1kg |     1 |            1 |     1 |               1 |
| Colombia Beans 1kg |     0 |            0 |     1 |               1 |
| Brazil Beans 250g  |     0 |            0 |     0 |               1 |
+--------------------+-------+--------------+-------+-----------------+

‏->> לטקסט שמשווים, מציגים או ממיינים כמחרוזת. ‏-> כשרוצים את הערך כ־JSON (מספר שנשאר מספר, אובייקט שעובר הלאה לפונקציות JSON). בספק — ->> עם המרה מפורשת: CAST(attributes->>'$.weight_g' AS UNSIGNED). ומפתח שלא קיים — NULL, כמו ב־PostgreSQL.

⚠️ טעויות נפוצות
  • להציג attributes->'$.origin' ב־API — הלקוח מקבל "\"Ethiopia\"", עם מרכאות כפולות בתוך הטקסט.

P25.5-E48 · ‏FULLTEXT או LIKE? 🧠 הבנה רמה 1

💡 רמז 1

‏LIKE 'abc%' יכול להשתמש באינדקס רגיל. ‏LIKE '%abc%' — לא.

💡 רמז 2

FULLTEXT ב־InnoDB מפרק לפי רווחים, ויש לו אורך מילה מינימלי (innodb_ft_min_token_size, ברירת מחדל 3) ורשימת מילים שמדלגים עליהן.

✅ פתרון
  1. LIKE 'pre%' עם אינדקס על name — חיפוש תחילית משתמש ב־B-tree.
  2. FULLTEXT — ‏MATCH … AGAINST ('+grinder +ceramic' IN BOOLEAN MODE). ‏LIKE '%…%' יסרוק 200,000 שורות בכל הקשה.
  3. = עם אינדקס (ובקולציה בינארית — E35). לא חיפוש טקסט בכלל.
  4. FULLTEXT של InnoDB לא יודע תחיליות של עברית ("ה", "ל" צמודות למילה). צריך parser אחר (‏ngram, עם מחיר), או מנוע חיפוש ייעודי (Elasticsearch/OpenSearch, ‏Meilisearch) — או ב־PostgreSQL, ‏trigram (‏pg_trgm).
  5. FULLTEXT מוצא — "cup" הוא 3 תווים, בדיוק המינימום. מילה של שתי אותיות ("v6") לא תימצא בלי לשנות את ההגדרה ולבנות את האינדקס מחדש.
⚠️ טעויות נפוצות
  • להוסיף FULLTEXT ולצפות ש־LIKE '%x%' ישתמש בו — הוא לא. רק MATCH … AGAINST.

P25.5-E07 · היקר ביותר בכל קטגוריה 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

אין DISTINCT ON. יש window functions.

💡 רמז 2

ROW_NUMBER() OVER (PARTITION BY category ORDER BY price DESC, id) בתת־שאילתה, ו־WHERE rn = 1 בחוץ.

✅ פתרון
-- P25.5-E07
-- המוצר היקר ביותר בכל קטגוריה (פעיל ובמלאי); בתיקו — ה־id הקטן. window functions קיימות מ־MySQL 8.0
SELECT category, name, price
FROM (
  SELECT category, name, price,
         ROW_NUMBER() OVER (PARTITION BY category ORDER BY price DESC, id) AS rn
  FROM products
  WHERE is_active AND stock > 0
) ranked
WHERE rn = 1
ORDER BY category;
+-------------+----------------------+--------+
| category    | name                 | price  |
+-------------+----------------------+--------+
| accessories | Paper Filters (100)  |  24.90 |
| beans       | Ethiopia Beans 1kg   |  89.90 |
| brewing     | Gooseneck Kettle     | 229.00 |
| grinders    | Electric Grinder Pro | 649.00 |
+-------------+----------------------+--------+
⚠️ טעויות נפוצות
  • SELECT category, name, MAX(price) … GROUP BY category — ב־MySQL ישן זה "עבד" ונתן name אקראי; ב־8 עם ONLY_FULL_GROUP_BY — שגיאה. וטוב שכך.

P25.5-E08 · upsert לעגלה 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

INSERT … ON DUPLICATE KEY UPDATE.

💡 רמז 2

VALUES(quantity) בתוך ה־UPDATE מיושן מ־8.0.20 (warning). במקומו: VALUES (1, 3, 2) AS new … quantity = cart_items.quantity + new.quantity.

✅ פתרון
-- P25.5-E08
-- "הוסף 2 יחידות של מוצר 3 לעגלה של לקוח 1": אם השורה קיימת — מוסיפים לכמות. ב־PostgreSQL: ON CONFLICT … DO UPDATE.
-- ב־MySQL: ON DUPLICATE KEY UPDATE, עם alias לשורה החדשה (VALUES() בתוך UPDATE מיושן מ־8.0.20 ומחזיר warning)
INSERT INTO cart_items (customer_id, product_id, quantity)
VALUES (1, 3, 2) AS new
ON DUPLICATE KEY UPDATE quantity = cart_items.quantity + new.quantity;

שימו לב להבדל מ־PostgreSQL: ON CONFLICT (customer_id, product_id) בוחר מפתח; ON DUPLICATE KEY מופעל על כל מפתח ייחודי בטבלה. בטבלה עם שני מפתחות ייחודיים זה יכול לעדכן שורה שלא התכוונת אליה.

⚠️ טעויות נפוצות
  • REPLACE INTO — "upsert" שבעצם מוחק ומכניס מחדש: ה־id משתנה, וטריגרים ומפתחות זרים עם ON DELETE מופעלים.

P25.5-E11 · GROUP BY נכון 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

כל עמודה ב־SELECT — או ב־GROUP BY, או בתוך פונקציה מצטברת, או תלויה פונקציונלית במה שב־GROUP BY.

💡 רמז 2

GROUP BY c.id מספיק ל־c.name ו־c.city — כי id הוא המפתח הראשי.

✅ פתרון
-- P25.5-E11
-- לכל לקוח עם הזמנות ששולמו: כמה, כמה כסף, ומתי האחרונה. ONLY_FULL_GROUP_BY מרשה name ו־city
-- כי הם תלויים פונקציונלית ב־c.id (המפתח הראשי) — לא צריך להוסיף אותם ל־GROUP BY
SELECT c.name, c.city,
       COUNT(*) AS paid_orders,
       SUM(o.total) AS paid_total,
       MAX(o.created_at) AS last_order
FROM customers c
JOIN orders o ON o.customer_id = c.id AND o.status IN ('paid', 'shipped')
GROUP BY c.id
ORDER BY paid_total DESC, c.id;
+-------------+-----------+-------------+------------+-------------------------+
| name        | city      | paid_orders | paid_total | last_order              |
+-------------+-----------+-------------+------------+-------------------------+
| Yossi Cohen | Tel Aviv  |           1 |     649.00 | 2026-03-02 11:30:00.000 |
| Dana Levi   | Haifa     |           1 |     278.90 | 2026-03-01 09:00:00.000 |
| Noa Mizrahi | Tel Aviv  |           1 |     238.00 | 2026-03-04 16:45:00.000 |
| Avi Peretz  | Jerusalem |           1 |     119.00 | 2026-03-06 10:10:00.000 |
+-------------+-----------+-------------+------------+-------------------------+
⚠️ טעויות נפוצות
  • לכבות את ONLY_FULL_GROUP_BY ב־sql_mode כי "השאילתה הישנה נשברה". השאילתה הישנה החזירה ערכים שרירותיים — עכשיו פשוט יודעים.

P25.5-E12 · עמודת JSON 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

attributes->>'$.material' — טקסט; -> — JSON (עם מרכאות).

💡 רמז 2

CAST(attributes->>'$.cups' AS UNSIGNED), ו־ORDER BY cups IS NULL, cups DESC.

✅ פתרון
-- P25.5-E12
-- עמודת JSON: ->> מחזיר טקסט (בלי מרכאות), -> מחזיר JSON. מספר — CAST, כדי למיין ולהשוות כמספר
SELECT name,
       attributes->>'$.material' AS material,
       CAST(attributes->>'$.cups' AS UNSIGNED) AS cups
FROM products
WHERE category = 'brewing'
  AND attributes->>'$.material' IS NOT NULL
ORDER BY cups IS NULL, cups DESC, name;
+------------------+-----------+------+
| name             | material  | cups |
+------------------+-----------+------+
| French Press 1L  | glass     |    8 |
| Moka Pot 6 Cups  | aluminium |    6 |
| Gooseneck Kettle | steel     | NULL |
| V60 Ceramic      | ceramic   | NULL |
+------------------+-----------+------+

וכשמחפשים לפי שדה ב־JSON הרבה: עמודה מחושבת (GENERATED ALWAYS AS (attributes->>'$.material')) עם אינדקס, או functional index. אבל אם שדה מופיע בכל שורה ומחפשים לפיו — הוא כנראה צריך להיות עמודה רגילה.

⚠️ טעויות נפוצות
  • להשוות attributes->'$.material' = 'glass' — ה־-> מחזיר JSON ("glass" עם מרכאות), וההשוואה מתנהגת אחרת ממה שנראה.

P25.5-E20 · שאילתה מ־PostgreSQL — שלוש תקלות 🤖 💻 כתיבת קוד 🤖 רמה 4

💡 רמז 1

שלושה דברים ש־MySQL לא מכיר, או מכיר אחרת.

💡 רמז 2

||, ILIKE, DISTINCT ON.

✅ פתרון
-- P25.5-E20
-- "השאילתה עבדה ב־PostgreSQL": שלוש בעיות ב־MySQL
-- תקלה 1: || ב־MySQL הוא OR לוגי (מחזיר 0/1), לא חיבור מחרוזות ← CONCAT
-- תקלה 2: אין ILIKE ← LIKE, שבקולציה של הטבלה (_ai_ci) כבר לא רגיש לרישיות
-- תקלה 3: DISTINCT ON לא קיים ← ROW_NUMBER() בתת־שאילתה
SELECT customer, city, last_total
FROM (
  SELECT CONCAT(c.name, ' (', c.email, ')') AS customer,
         c.city,
         o.total AS last_total,
         ROW_NUMBER() OVER (PARTITION BY c.id ORDER BY o.created_at DESC) AS rn
  FROM customers c
  JOIN orders o ON o.customer_id = c.id
  WHERE c.city LIKE '%aviv%'
) t
WHERE rn = 1
ORDER BY customer;
+---------------------------------+----------+------------+
| customer                        | city     | last_total |
+---------------------------------+----------+------------+
| Noa Mizrahi (noa@example.com)   | Tel Aviv |     238.00 |
| Yossi Cohen (yossi@example.com) | Tel Aviv |      89.90 |
+---------------------------------+----------+------------+
⚠️ טעויות נפוצות
  • להפעיל PIPES_AS_CONCAT ב־sql_mode כדי ש־|| יעבוד — עכשיו הקוד תלוי בהגדרת שרת, ושרת אחר יחזיר 0.

P25.5-E26 · דוח לקוחות ב־MySQL — מקובץ ריק 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

שתי טבלאות "רבות" לכל לקוח (הזמנות ועגלה). ‏JOIN לשתיהן יחד מכפיל שורות: לדנה יש שני פריטים בעגלה, וההזמנה שלה נספרת פעמיים. לכן מסכמים כל אחת בנפרד ב־CTE (WITH spent AS (... GROUP BY customer_id), cart AS (...)), ואז LEFT JOIN ללקוחות.

💡 רמז 2

MySQL: ‏IFNULL(s.spent, 0) (או COALESCE), ‏DATE_FORMAT(s.last_at, '%d/%m/%Y'). ‏DATE_FORMAT של NULL הוא NULL. בחלון: RANK() OVER (PARTITION BY c.city ORDER BY IFNULL(s.spent, 0) DESC), ובסוף ORDER BY c.city, city_rank, c.name (מותר למיין לפי כינוי של עמודה).

✅ פתרון
WITH spent AS (
  SELECT customer_id, COUNT(*) AS orders, SUM(total) AS spent, MAX(created_at) AS last_at
  FROM orders
  WHERE status IN ('paid', 'shipped')
  GROUP BY customer_id
),
cart AS (
  SELECT customer_id, SUM(quantity) AS units
  FROM cart_items
  GROUP BY customer_id

מה כאן MySQL ומה לא? ‏CTE, ‏LEFT JOIN, ‏RANK ו־GROUP BY זהים ל־PostgreSQL (מגרסה 8). ההבדלים: ‏DATE_FORMAT עם %d/%m/%Y (ב־PostgreSQL: ‏to_char(..., 'DD/MM/YYYY')), ו־IFNULL, שקיים רק ב־MySQL. ‏COALESCE עובד בשניהם, ולכן הוא בחירה טובה כשכותבים SQL שצריך לרוץ בשני המסדים.

⚠️ טעויות נפוצות
  • JOIN במקום LEFT JOIN — מאיה, שעוד לא הזמינה, נעלמת מהדוח.
  • WHERE o.status IN (...) אחרי LEFT JOIN ל־orders — הופך אותו ל־JOIN רגיל, ומאיה שוב נעלמת. את הסינון שמים בתוך ה־CTE (או בתנאי ה־ON).
  • ROW_NUMBER במקום RANK — בתיקו אחד מקבל 1 והשני 2, לפי סדר מקרי.
  • '%d/%m/%y' — ‏y קטנה היא שנה בשתי ספרות (26).

P25.5-E51 · אין RETURNING — מה משתנה בקוד? 🧠 הבנה רמה 2

💡 רמז 1

‏insertId, ‏affectedRows — ואז עוד SELECT.

💡 רמז 2

מה צריך כדי שה־SELECT שאחרי יראה בדיוק את מה שה־UPDATE עשה?

✅ פתרון
  1. INSERT ← insertId, ואז SELECT … WHERE id = ? בשביל ברירות המחדל (status, ‏created_at). שתי פקודות במקום אחת.
  2. UPDATE ← affectedRows (1 = הצליח, 0 = אין מלאי — P25.5-E13). את המלאי החדש — SELECT, באותה טרנזקציה (ועם FOR UPDATE, אם חשוב שיהיה מדויק).
  3. DELETE ← אם צריך את ה־ids: קודם SELECT id … FOR UPDATE, ואז DELETE לפיהם, בטרנזקציה. אחרת — רק affectedRows.

Prisma עושה את זה בשבילך: ב־MySQL ה־create שולח INSERT ואחריו SELECT. המחיר — עוד round trip, שלא רואים בקוד (וב־$queryRaw — כן רואים).

⚠️ טעויות נפוצות
  • להחזיר ללקוח את ה־body ששלח, עם ה־id, במקום לקרוא מהמסד — ואז ברירות מחדל (status, ‏created_at) חסרות או שגויות.

P25.5-E52 · ‏upsert במקביל — יש מרוץ? 🧠 הבנה רמה 2

💡 רמז 1

שתי הבקשות קוראות "אין שורה" — מה עכשיו?

💡 רמז 2

פקודה אחת = נעילה אחת על השורה (או על המפתח).

✅ פתרון
  1. א: (1) שתיהן לא מוצאות ← שתיהן INSERT ← אחת נכשלת עם Duplicate entry (500 למשתמש). (2) שתיהן מוצאות 1 ← שתיהן כותבות 2 ← אחת מהלחיצות "נעלמה" (lost update). ב: שתיהן מצליחות, הכמות 2.
  2. ה־INSERT וה־UPDATE הם פעולה אחת בתוך InnoDB: ההתנגשות במפתח, הנעילה של השורה הקיימת, והחישוב cart_items.quantity + 1 — מהערך העדכני, לא ממה שנקרא קודם.
  3. INSERT … ON CONFLICT (customer_id, product_id) DO UPDATE עם quantity = cart_items.quantity + EXCLUDED.quantity — אותו רעיון בדיוק.
⚠️ טעויות נפוצות
  • "לתקן" את א׳ בטרנזקציה בלי FOR UPDATE — ב־REPEATABLE READ שתיהן עדיין קוראות את אותה תמונה (שיעור 3).

P25.5-E53 · דפדוף ב־MySQL — OFFSET או keyset? 🧠 הבנה רמה 2

💡 רמז 1

‏OFFSET לא "קופץ" — הוא קורא ומדלג.

💡 רמז 2

שתי הזמנות באותה מילישנייה.

✅ פתרון
  1. 100,020 — קורא ומדלג על כל מה שלפני. ככל שהעמוד רחוק, כך איטי יותר.
  2. OFFSET: כל השורות "זזות" 3 מקומות — המשתמש רואה שוב 3 הזמנות מהעמוד הקודם. keyset: ממשיך בדיוק מאיפה שעצר — בלי כפילויות (החדשות יופיעו כשיחזור להתחלה).
  3. ‏created_at לא ייחודי. עם cursor רק עליו, הזמנות עם אותו זמן בגבול העמוד — נעלמות או מוכפלות. id שובר את התיקו.
  4. כמו ב־PostgreSQL: ‏WHERE (created_at, id) < (?, ?) עם ORDER BY created_at DESC, id DESC (‏row constructor), עם אינדקס על (created_at, id) (E54).
⚠️ טעויות נפוצות
  • cursor שהוא מספר העמוד מוצפן ב־base64 — זה עדיין OFFSET.

P25.5-E27 · INSERT מרובה שורות, עם upsert 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

שמות לא יכולים להיות פרמטרים (? הוא רק לערכים), ולכן בודקים אותם מול רשימה מותרת: פונקציה קטנה ident(name) שזורקת אם ה־regex לא מתאים, ומחזירה את השם עטוף ב־backticks. כל שם עובר דרכה.

💡 רמז 2

const columns = Object.keys(rows[0]). השוואת עמודות: Object.keys(row).sort().join(",") מול אותו דבר בשורה הראשונה. פרמטרים: rows.flatMap((row) => columns.map((c) => row[c])). ‏placeholders: ‏rows.map(() => "(?, ?, ?)").join(", ").

✅ פתרון
// P25.5-E27 — INSERT מרובה שורות, עם upsert
type Value = string | number | boolean | null;

const IDENT = /^[a-z_][a-z0-9_]*$/;

function ident(name: string): string {
  if (!IDENT.test(name)) throw new Error(`שם לא חוקי: ${name}`);
  return `\`${name}\``;
}

export function buildBulkInsert(
  table: string,
  rows: Record<string, Value>[],
  options: { add?: string[]; set?: string[] } = {},
): { sql: string; params: Value[] } {
  if (rows.length === 0) throw new Error("אין שורות");
  const columns = Object.keys(rows[0]);
  const key = [...columns].sort().join(",");
  for (const row of rows) {
    if (Object.keys(row).sort().join(",") !== key) throw new Error("לכל השורות צריכות להיות אותן עמודות");
  }

  const placeholders = `(${columns.map(() => "?").join(", ")})`;
  let sql = `INSERT INTO ${ident(table)} (${columns.map(ident).join(", ")}) VALUES ${rows.map(() => placeholders).join(", ")}`;
  const params = rows.flatMap((row) => columns.map((c) => row[c]));

  const updates = [
    ...(options.add ?? []).map((c) => `${ident(c)} = ${ident(table)}.${ident(c)} + new.${ident(c)}`),
    ...(options.set ?? []).map((c) => `${ident(c)} = new.${ident(c)}`),
  ];
  if (updates.length > 0) sql += ` AS new ON DUPLICATE KEY UPDATE ${updates.join(", ")}`;
  return { sql, params };
}

console.log(buildBulkInsert("cart_items", [
  { customer_id: 1, product_id: 3, quantity: 2 },
  { product_id: 4, customer_id: 1, quantity: 1 },
], { add: ["quantity"] }));
try {
  buildBulkInsert("products; DROP TABLE orders", [{ id: 1 }]);
} catch (err) {
  console.log((err as Error).message);
}

שם לא חוקי: products; DROP TABLE orders

שני חלקים, ולכל אחד הגנה משלו מ־injection. ערכים עוברים תמיד כ־?, ולכן "x'); DROP TABLE orders; --" נשמר כשם של לקוח. שמות אי אפשר להעביר כפרמטר, ולכן הם עוברים בדיקה מול regex קשוח. שם כמו products; DROP TABLE orders לא מגיע ל־SQL בכלל.

flatMap לפי columns, ולא Object.values(row): בשורה השנייה בדוגמה המפתחות כתובים בסדר אחר. ‏Object.values היה מכניס את מספר המוצר לעמודת הלקוח, בלי שום שגיאה.

‏MySQL מגביל את מספר ה־placeholders בשאילתה (65,535). לכן בטעינה גדולה מחלקים את השורות לקבוצות של כמה מאות, ומריצים כל קבוצה בנפרד.

⚠️ טעויות נפוצות
  • Object.values(row) — תלוי בסדר שבו המפתחות נכתבו בכל שורה.
  • לשרשר ערכים לתוך ה־SQL (VALUES ('${name}')) — ‏injection, וגם שבירה על כל שם עם גרש (O'Brien).
  • VALUES(quantity) במקום new.quantity — עובד, אבל deprecated מ־MySQL 8.0.20.
  • לבדוק רק שמספר העמודות שווה — ‏{a, b} ו־{a, c} עוברים.

START TRANSACTION;
INSERT INTO orders (customer_id, status, total)
  SELECT 1, 'pending_payment', SUM(ci.quantity * p.price)
  FROM cart_items ci JOIN products p ON p.id = ci.product_id
  WHERE ci.customer_id = 1;
SET @order_id = LAST_INSERT_ID();

  SELECT @order_id, ci.product_id, ci.quantity, p.price

  WHERE ci.customer_id = 1;
DELETE FROM cart_items WHERE customer_id = 1;
