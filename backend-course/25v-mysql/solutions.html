P25.5-E26 · דוח לקוחות ב־MySQL — מקובץ ריק 🤖 ✍️ מאפס רמה 3

💡 רמז 1

שתי טבלאות "רבות" לכל לקוח (הזמנות ועגלה). ‏JOIN לשתיהן יחד מכפיל שורות: לדנה יש שני פריטים בעגלה, וההזמנה שלה נספרת פעמיים. לכן מסכמים כל אחת בנפרד ב־CTE (WITH spent AS (... GROUP BY customer_id), cart AS (...)), ואז LEFT JOIN ללקוחות.

💡 רמז 2

MySQL: ‏IFNULL(s.spent, 0) (או COALESCE), ‏DATE_FORMAT(s.last_at, '%d/%m/%Y'). ‏DATE_FORMAT של NULL הוא NULL. בחלון: RANK() OVER (PARTITION BY c.city ORDER BY IFNULL(s.spent, 0) DESC), ובסוף ORDER BY c.city, city_rank, c.name (מותר למיין לפי כינוי של עמודה).

✅ פתרון
WITH spent AS (
  SELECT customer_id, COUNT(*) AS orders, SUM(total) AS spent, MAX(created_at) AS last_at
  FROM orders
  WHERE status IN ('paid', 'shipped')
  GROUP BY customer_id
),
cart AS (
  SELECT customer_id, SUM(quantity) AS units
  FROM cart_items
  GROUP BY customer_id
)
SELECT
  c.name,
  c.city,
  IFNULL(s.orders, 0) AS orders,
  IFNULL(s.spent, 0) AS spent,
  DATE_FORMAT(s.last_at, '%d/%m/%Y') AS last_order,
  IFNULL(ct.units, 0) AS cart_units,
  RANK() OVER (PARTITION BY c.city ORDER BY IFNULL(s.spent, 0) DESC) AS city_rank
FROM customers c
LEFT JOIN spent s ON s.customer_id = c.id
LEFT JOIN cart ct ON ct.customer_id = c.id
ORDER BY c.city, city_rank, c.name;

דנה: הזמנה אחת ששולמה (278.90). ההזמנה המבוטלת לא נספרת. בעגלה שלה 2 + 1 = 3 יחידות. מי שמצרף את orders ואת cart_items באותו FROM מקבל לה spent של 557.80, כי כל הזמנה מופיעה פעם לכל פריט בעגלה. זה ה־"fan-out" מפרק 17, והוא נראה בדיוק אותו דבר ב־MySQL.

מה כאן MySQL ומה לא? ‏CTE, ‏LEFT JOIN, ‏RANK ו־GROUP BY זהים ל־PostgreSQL (מגרסה 8). ההבדלים: ‏DATE_FORMAT עם %d/%m/%Y (ב־PostgreSQL: ‏to_char(..., 'DD/MM/YYYY')), ו־IFNULL, שקיים רק ב־MySQL. ‏COALESCE עובד בשניהם, ולכן הוא בחירה טובה כשכותבים SQL שצריך לרוץ בשני המסדים.

⚠️ טעויות נפוצות
  • JOIN במקום LEFT JOIN — מאיה, שעוד לא הזמינה, נעלמת מהדוח.
  • WHERE o.status IN (...) אחרי LEFT JOIN ל־orders — הופך אותו ל־JOIN רגיל, ומאיה שוב נעלמת. את הסינון שמים בתוך ה־CTE (או בתנאי ה־ON).
  • ROW_NUMBER במקום RANK — בתיקו אחד מקבל 1 והשני 2, לפי סדר מקרי.
  • '%d/%m/%y' — ‏y קטנה היא שנה בשתי ספרות (26).

P25.5-E27 · INSERT מרובה שורות, עם upsert 🤖 🔁 חזרה רמה 2

💡 רמז 1

שמות לא יכולים להיות פרמטרים (? הוא רק לערכים), ולכן בודקים אותם מול רשימה מותרת: פונקציה קטנה ident(name) שזורקת אם ה־regex לא מתאים, ומחזירה את השם עטוף ב־backticks. כל שם עובר דרכה.

💡 רמז 2

const columns = Object.keys(rows[0]). השוואת עמודות: Object.keys(row).sort().join(",") מול אותו דבר בשורה הראשונה. פרמטרים: rows.flatMap((row) => columns.map((c) => row[c])). ‏placeholders: ‏rows.map(() => "(?, ?, ?)").join(", ").

✅ פתרון
// P25.5-E27 — INSERT מרובה שורות, עם upsert
type Value = string | number | boolean | null;

const IDENT = /^[a-z_][a-z0-9_]*$/;

function ident(name: string): string {
  if (!IDENT.test(name)) throw new Error(`שם לא חוקי: ${name}`);
  return `\`${name}\``;
}

export function buildBulkInsert(
  table: string,
  rows: Record<string, Value>[],
  options: { add?: string[]; set?: string[] } = {},
): { sql: string; params: Value[] } {
  if (rows.length === 0) throw new Error("אין שורות");
  const columns = Object.keys(rows[0]);
  const key = [...columns].sort().join(",");
  for (const row of rows) {
    if (Object.keys(row).sort().join(",") !== key) throw new Error("לכל השורות צריכות להיות אותן עמודות");
  }

  const placeholders = `(${columns.map(() => "?").join(", ")})`;
  let sql = `INSERT INTO ${ident(table)} (${columns.map(ident).join(", ")}) VALUES ${rows.map(() => placeholders).join(", ")}`;
  const params = rows.flatMap((row) => columns.map((c) => row[c]));

  const updates = [
    ...(options.add ?? []).map((c) => `${ident(c)} = ${ident(table)}.${ident(c)} + new.${ident(c)}`),
    ...(options.set ?? []).map((c) => `${ident(c)} = new.${ident(c)}`),
  ];
  if (updates.length > 0) sql += ` AS new ON DUPLICATE KEY UPDATE ${updates.join(", ")}`;
  return { sql, params };
}

שני חלקים, ולכל אחד הגנה משלו מ־injection. ערכים עוברים תמיד כ־?, ולכן "x'); DROP TABLE orders; --" נשמר כשם של לקוח. שמות אי אפשר להעביר כפרמטר, ולכן הם עוברים בדיקה מול regex קשוח. שם כמו products; DROP TABLE orders לא מגיע ל־SQL בכלל.

flatMap לפי columns, ולא Object.values(row): בשורה השנייה בדוגמה המפתחות כתובים בסדר אחר. ‏Object.values היה מכניס את מספר המוצר לעמודת הלקוח, בלי שום שגיאה.

‏MySQL מגביל את מספר ה־placeholders בשאילתה (65,535). לכן בטעינה גדולה מחלקים את השורות לקבוצות של כמה מאות, ומריצים כל קבוצה בנפרד.

⚠️ טעויות נפוצות
  • Object.values(row) — תלוי בסדר שבו המפתחות נכתבו בכל שורה.
  • לשרשר ערכים לתוך ה־SQL (VALUES ('${name}')) — ‏injection, וגם שבירה על כל שם עם גרש (O'Brien).
  • VALUES(quantity) במקום new.quantity — עובד, אבל deprecated מ־MySQL 8.0.20.
  • לבדוק רק שמספר העמודות שווה — ‏{a, b} ו־{a, c} עוברים.

P25.5-E28 · שאילתה מ־PostgreSQL ל־MySQL 🤖 🔁 חזרה רמה 2

💡 רמז 1

הטריק: regex אחד עם שלוש חלופות, ו־replace עם פונקציה. החלופה של המחרוזת באה ראשונה: ‏/'(?:[^']|'')*'|"([^"]+)"|\$(\d+)/g. ה־regex סורק משמאל לימין, וכשהוא פוגש ' הוא "בולע" את כל המחרוזת. כך $1 שבתוכה לא נתפס בנפרד.

💡 רמז 2

הפונקציה מקבלת (match, name, n) — קבוצה 1 וקבוצה 2. אם name !== undefined ← backticks. אם n !== undefined ← out.push(params[Number(n) - 1]) ומחזירים "?". אחרת זו מחרוזת ← return match.

✅ פתרון
// P25.5-E28 — שאילתה מ־PostgreSQL ל־MySQL: placeholders ושמות
export function pgToMysql(sql: string, params: unknown[]): { sql: string; params: unknown[] } {
  const out: unknown[] = [];
  // מחרוזת '...' (עם '' בפנים) — כמו שהיא; "שם" ← `שם`; $n ← ?
  const converted = sql.replace(/'(?:[^']|'')*'|"([^"]+)"|\$(\d+)/g, (match, name, n) => {
    if (name !== undefined) return `\`${name}\``;
    if (n !== undefined) {
      const i = Number(n);
      if (i < 1 || i > params.length) throw new RangeError(`$${n} — אין פרמטר כזה (יש ${params.length})`);
      out.push(params[i - 1]);
      return "?";
    }
    return match;
  });
  return { sql: converted, params: out };
}

ב־PostgreSQL ‏$2 הוא "הפרמטר השני", בכל מקום שהוא מופיע. ב־MySQL כל ? הוא "הפרמטר הבא". לכן ההמרה צריכה לבנות מערך חדש לפי סדר ההופעה, ו־$2 שמופיע פעמיים נכנס פעמיים.

הסדר של החלופות ב־regex הוא מה שעושה את העבודה. ה־regex לא "יודע" שהוא בתוך מחרוזת. הוא פשוט פוגש קודם את הגרש הפותח, ומתאים את כל המחרוזת כחתיכה אחת. זה אותו רעיון כמו ה־TOKENS ב־_ts.mjs של הבודקים, שמוריד הערות בלי לגעת במחרוזות.

ההמרה הזו מכסה את ההבדלים התחביריים בלבד. ‏ILIKE, ‏RETURNING ו־::int צריכים שינוי ידני (שיעור 1).

⚠️ טעויות נפוצות
  • sql.replace(/\$\d+/g, "?") ושמירת params כמו שהם — ‏$2 ... $1 מחליף בין הערכים, ו־$2 כפול חסר.
  • בלי חלופה למחרוזות — 'cost: $1' הופך ל־'cost: ?', נוסף פרמטר מיותר, ו־MySQL נכשל (או, גרוע יותר, מקבל ערך במקום הלא נכון).
  • /\$(\d)/ — ‏$10 נקרא כ־$1 ואחריו 0.
  • להחליף " גם בתוך מחרוזות — הטקסט 'say "hi"' שנשמר במסד משתנה.

P25.5-E01 · מילון PostgreSQL ← MySQL רמה 1

💡 רמז 1

רוב השפה זהה: SELECT, JOIN, GROUP BY, CTE, window functions (מ־8.0), CHECK (נאכף מ־8.0.16).

💡 רמז 2

שלושה מהם "קיימים, אבל עושים משהו אחר".

✅ פתרון
  1. INT UNSIGNED AUTO_INCREMENT PRIMARY KEY.
  2. אין RETURNING. ה־driver מחזיר insertId (mysql2), או SELECT LAST_INSERT_ID() באותו חיבור.
  3. INSERT … AS new ON DUPLICATE KEY UPDATE col = new.col — על כל מפתח ייחודי בטבלה, לא על אחד שבוחרים (E08).
  4. מלכודת: || ב־MySQL הוא OR לוגי — 'a' || 'b' מחזיר 0. חיבור מחרוזות: CONCAT('a', 'b').
  5. אין ILIKE. אבל ברירת המחדל (utf8mb4_0900_ai_ci) כבר לא רגישה לרישיות ולסימנים — LIKE מספיק. לרגישות: COLLATE utf8mb4_bin.
  6. BOOLEAN הוא TINYINT(1) (חוזר כ־0/1); JSON (בינארי, דומה ל־jsonb); DATETIME(3) בלי אזור זמן — שומרים UTC בעצמך, או TIMESTAMP (ממיר לפי אזור הזמן של החיבור, טווח עד 2038).
  7. אין. ROW_NUMBER() OVER (PARTITION BY …) בתת־שאילתה (E07, E20).
  8. אין. LEFT JOIN … UNION … RIGHT JOIN.
  9. ? (mysql2: execute(sql, [a, b])).
⚠️ טעויות נפוצות
  • להעתיק שאילתה מ־PostgreSQL ולהאמין לה כי "לא הייתה שגיאה". || לא זורק — הוא מחזיר 0 בשקט.

P25.5-E02 · קולציה: מה שווה למה? רמה 1

💡 רמז 1

ai = accent-insensitive, ci = case-insensitive. וקולציות 0900 הן NO PAD — רווח בסוף נחשב.

💡 רמז 2

השוואה בין שתי מחרוזות מילוליות משתמשת בקולציה של החיבור, לא של טבלה.

✅ פתרון
  1. 0 — הרווח בסוף נחשב (NO PAD).
  2. 1 — Café ו־cafe שווים: בלי רישיות ובלי ניקוד.
  3. Duplicate entry 'DANA@x.com' — ה־UNIQUE משתמש באותה קולציה. ל־email זה בדיוק מה שרוצים (ב־PostgreSQL היינו צריכים lower(email)).
  4. מדדתי: ב־mysql2 החיבור הוא utf8mb4_unicode_ci ← 1; ב־mysql CLI בקונטיינר הוא latin1_swedish_ci ← 0. אותה שאילתה, תשובות שונות — לכן משווים מול עמודות, וקובעים charset בחיבור במפורש.
  5. בעיה: abc ו־ABC שווים — מפתח "כמעט נכון" עובר. לעמודות כאלה: VARBINARY או COLLATE utf8mb4_bin (ועדיף לשמור hash ולא את המפתח).
⚠️ טעויות נפוצות
  • להניח שההתנהגות זהה ל־PostgreSQL (שם ההשוואה רגישה לרישיות ולניקוד) — ולגלות כפילויות "דנה"/"DANA" רק בפרודקשן.

P25.5-E03 · REPEATABLE READ רמה 1

💡 רמז 1

ב־REPEATABLE READ, SELECT רגיל קורא מ"תמונה" שנלקחה בקריאה הראשונה של הטרנזקציה.

💡 רמז 2

UPDATE ו־FOR UPDATE קוראים את הגרסה המחויבת האחרונה ("locking read").

✅ פתרון
  1. 10 — אותה תמונה. (ב־PostgreSQL, READ COMMITTED: 7.)
  2. 7 — קריאה נועלת רואה את האחרון.
  3. 6 — ה־UPDATE עובד על 7, ואחריו A רואה את השינוי שלו עצמו.

המסקנה: ב־MySQL, "SELECT ואז החלטה ואז UPDATE" גרוע עוד יותר מב־PostgreSQL — ה־SELECT יכול להחזיר ערך ישן בתוך הטרנזקציה. ההחלטה צריכה להיות בתוך ה־UPDATE (WHERE stock >= ?, E13) או אחרי FOR UPDATE (E09). בשיעור 3 — ההרצה האמיתית של התרחיש.

⚠️ טעויות נפוצות
  • "אני בטרנזקציה, אז אני מוגן" — טרנזקציה לא נועלת שורות שרק קראת.

P25.5-E04 · DATETIME או TIMESTAMP? רמה 1

💡 רמז 1

TIMESTAMP נשמר ב־UTC ומומר לפי time_zone של החיבור; טווח 1970–2038.

💡 רמז 2

DATETIME נשמר כמו שהוא — "שעון על הקיר", בלי אזור זמן.

✅ פתרון
  1. DATETIME(3) שבו האפליקציה תמיד כותבת UTC (ומתעדים את זה). TIMESTAMP אפשרי, אבל ההמרה לפי החיבור היא מקור לבאגים כשחיבורים מוגדרים שונה — והטווח נגמר ב־2038.
  2. DATE — אין שעה, ו־TIMESTAMP לא מגיע לפני 1970 (E23).
  3. DATETIME — TIMESTAMP לא מגיע ל־2040.
  4. DATE — יום מקומי, לא רגע (פרק 24: "רגע" מול "תאריך").
⚠️ טעויות נפוצות
  • לערבב: חלק מהקוד כותב UTC וחלק שעון ישראל, לאותה עמודה. החלטה אחת, בתיעוד, ובדיקה.

P25.5-E09 · הזמנה בטרנזקציה עם mysql2 🤖 רמה 2

💡 רמז 1

💡 רמז 2

✅ פתרון
// P25.5-E09
import type { Pool } from "mysql2/promise";

export class OutOfStock extends Error {}

// הזמנה בטרנזקציה ב־mysql2: חיבור אחד מה־pool לכל הטרנזקציה (getConnection), ו־release בכל מקרה.
// execute = prepared statement עם ? — אף פעם לא שרשור מחרוזות. ואין RETURNING: את ה־id נותן insertId
export async function insertOrder(pool: Pool, order: { customerId: number; items: { productId: number; quantity: number }[] }) {
  const conn = await pool.getConnection();
  try {
    await conn.beginTransaction();
    const ids = order.items.map((i) => i.productId).sort((a, b) => a - b); // נועלים תמיד באותו סדר — פחות deadlocks
    const [rows] = await conn.query<any[]>("SELECT id, price, stock FROM products WHERE id IN (?) ORDER BY id FOR UPDATE", [ids]);
    const byId = new Map(rows.map((r) => [r.id, r]));
    let totalCents = 0;
    for (const item of order.items) {
      const p = byId.get(item.productId);
      if (!p || p.stock < item.quantity) throw new OutOfStock(`אין מספיק מלאי למוצר ${item.productId}`);
      totalCents += Math.round(Number(p.price) * 100) * item.quantity;
    }
    const [res] = await conn.execute<any>("INSERT INTO orders (customer_id, status, total) VALUES (?, 'pending_payment', ?)", [order.customerId, (totalCents / 100).toFixed(2)]);
    const orderId: number = res.insertId;
    await conn.query("INSERT INTO order_items (order_id, product_id, quantity, unit_price) VALUES ?", [
      order.items.map((i) => [orderId, i.productId, i.quantity, byId.get(i.productId).price]),
    ]);
    for (const item of order.items) {
      await conn.execute("UPDATE products SET stock = stock - ? WHERE id = ?", [item.quantity, item.productId]);
    }
    await conn.commit();
    return { orderId, totalCents };
  } catch (err) {
    await conn.rollback();
    throw err;
  } finally {
    conn.release();
  }
}
⚠️ טעויות נפוצות
  • pool.query("START TRANSACTION") ואז pool.query(…) — כל קריאה ל־pool יכולה לקבל חיבור אחר. טרנזקציה חיה על חיבור אחד.

P25.5-E14 · תור עבודות: SKIP LOCKED 🤖 רמה 3

💡 רמז 1

טרנזקציה: SELECT id … ORDER BY id LIMIT ? FOR UPDATE SKIP LOCKED, ואז UPDATE על ה־ids, ו־COMMIT.

💡 רמז 2

בלי SKIP LOCKED — worker שני מחכה לראשון (ואז מוצא את אותן שורות כבר running). עם — מדלג ולוקח את הבאות.

✅ פתרון
// P25.5-E14
import type { Pool } from "mysql2/promise";

// תור עבודות על טבלה: כמה workers לוקחים עבודות במקביל, בלי שאותה עבודה תילקח פעמיים.
// FOR UPDATE נועל את השורות שנבחרו; SKIP LOCKED (MySQL 8.0+) מדלג על נעולות במקום לחכות להן
export async function claimJobs(pool: Pool, workerId: string, limit: number): Promise<number[]> {
  const conn = await pool.getConnection();
  try {
    await conn.beginTransaction();
    const [rows] = await conn.query<any[]>("SELECT id FROM jobs WHERE status = 'queued' ORDER BY id LIMIT ? FOR UPDATE SKIP LOCKED", [limit]);
    const ids = rows.map((r) => r.id as number);
    if (ids.length) await conn.query("UPDATE jobs SET status = 'running', locked_by = ? WHERE id IN (?)", [workerId, ids]);
    await conn.commit();
    return ids;
  } catch (err) {
    await conn.rollback();
    throw err;
  } finally {
    conn.release();
  }
}

זה דפוס שמאפשר תור בלי Redis ובלי broker — כשהעומס צנוע. ביחידה 26.5 נראה מתי עוברים ל־RabbitMQ, Kafka או SQS.

⚠️ טעויות נפוצות
  • לשכוח שהנעילה חיה רק עד ה־COMMIT — אם הסימון (UPDATE) לא באותה טרנזקציה, אחרים יראו את העבודות כ־queued.

P25.5-E15 · deadlock, ואיך חיים איתו 🤖 רמה 3

💡 רמז 1

💡 רמז 2

✅ פתרון
// P25.5-E15
// InnoDB מזהה deadlock ומבטל את אחת הטרנזקציות (errno 1213, ER_LOCK_DEADLOCK); המתנה ארוכה לנעילה — 1205.
// שתיהן "בטוחות לנסות שוב": הטרנזקציה בוטלה כולה. מנסים שוב את *כל* הטרנזקציה, עם המתנה קצרה ואקראית
export const RETRYABLE = new Set([1213, 1205]);

export async function withDeadlockRetry<T>(
  fn: (attempt: number) => Promise<T>,
  { retries = 3, sleep = (ms: number) => new Promise<void>((r) => setTimeout(r, ms)), random = Math.random } = {},
): Promise<T> {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fn(attempt);
    } catch (err) {
      const errno = (err as { errno?: number }).errno;
      if (attempt >= retries || errno === undefined || !RETRYABLE.has(errno)) throw err;
      await sleep(Math.floor(random() * 20 * 2 ** attempt));
    }
  }
}

מה עדיף על retry: שה־deadlock לא יקרה — לנעול תמיד באותו סדר (ORDER BY id FOR UPDATE, כמו ב־E09 ו־E24), טרנזקציות קצרות, ואינדקסים שמונעים נעילה של יותר שורות מהנדרש. אבל במערכת עמוסה deadlock יקרה בסוף — ו־retry הוא חלק מהתשובה.

⚠️ טעויות נפוצות
  • retry על פקודה בודדת מתוך הטרנזקציה — אחרי deadlock כל הטרנזקציה בוטלה, והפקודות שלפני כבר לא קיימות.

P25.5-E17 · idempotency ב־MySQL 🤖 רמה 3

💡 רמז 1

💡 רמז 2

✅ פתרון
// P25.5-E17
import type { Pool } from "mysql2/promise";

export class InProgress extends Error {}

// Idempotency ב־MySQL: INSERT IGNORE על מפתח ראשי — affectedRows 1 = "אני הראשון", 0 = כבר קיים.
// (ב־PostgreSQL: ON CONFLICT DO NOTHING RETURNING.) התוצאה נשמרת כ־JSON, והבקשה החוזרת מקבלת אותה
export async function once<T>(pool: Pool, key: string, fn: () => Promise<T>): Promise<{ result: T; replayed: boolean }> {
  const [ins] = await pool.execute<any>("INSERT IGNORE INTO idempotency (idem_key, status) VALUES (?, 'pending')", [key]);
  if (ins.affectedRows === 1) {
    try {
      const result = await fn();
      await pool.execute("UPDATE idempotency SET status = 'done', result = ? WHERE idem_key = ?", [JSON.stringify(result), key]);
      return { result, replayed: false };
    } catch (err) {
      await pool.execute("DELETE FROM idempotency WHERE idem_key = ?", [key]); // נכשל ← אפשר לנסות שוב עם אותו מפתח
      throw err;
    }
  }
  const [rows] = await pool.execute<any[]>("SELECT status, result FROM idempotency WHERE idem_key = ?", [key]);
  if (!rows[0] || rows[0].status !== "done") throw new InProgress(`בקשה ${key} עדיין בטיפול`);
  const stored = rows[0].result;
  return { result: (typeof stored === "string" ? JSON.parse(stored) : stored) as T, replayed: true };
}
⚠️ טעויות נפוצות
  • INSERT IGNORE מתעלם לא רק מכפילות — גם משגיאות אחרות (ערך ארוך מדי נחתך, ועוד). כאן זה בטוח (מפתח קצר), אבל בכל מקום אחר — ON DUPLICATE KEY UPDATE idem_key = idem_key מדויק יותר.

💡 רמז 2

הנעילה שייכת לחיבור — לכן pool.getConnection(), לא pool.query.

✅ פתרון
// P25.5-E19
import type { Pool } from "mysql2/promise";

// כלי migrations בקטן. שני דברים שמיוחדים ל־MySQL:
// (1) DDL עושה COMMIT מרומז — אי אפשר לעטוף CREATE/ALTER בטרנזקציה ולבטל. migration שנכשל באמצע — נשאר באמצע.
// (2) GET_LOCK: נעילה בשם, לכל השרתים — כך שני שרתים שעולים יחד לא מריצים את אותו migration פעמיים
export async function migrate(pool: Pool, migrations: readonly { id: string; sql: string }[], { lockTimeoutSeconds = 10 } = {}): Promise<string[]> {
  const conn = await pool.getConnection();
  try {
    const [[lock]] = await conn.query<any[]>("SELECT GET_LOCK('schema_migrations', ?) AS ok", [lockTimeoutSeconds]);
    if (lock.ok !== 1) throw new Error("לא התקבלה נעילה ל־migrations");
    try {
      await conn.query("CREATE TABLE IF NOT EXISTS schema_migrations (id VARCHAR(100) PRIMARY KEY, applied_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3))");
      const [done] = await conn.query<any[]>("SELECT id FROM schema_migrations");
      const applied = new Set(done.map((r) => r.id));
      const ran: string[] = [];
      for (const m of [...migrations].sort((a, b) => (a.id < b.id ? -1 : 1))) {
        if (applied.has(m.id)) continue;
        await conn.query(m.sql);
        await conn.execute("INSERT INTO schema_migrations (id) VALUES (?)", [m.id]);
        ran.push(m.id);
      }
      return ran;
    } finally {
      await conn.query("SELECT RELEASE_LOCK('schema_migrations')");
    }
  } finally {
    conn.release();
  }
}

ההבדל הגדול מ־PostgreSQL: שם, CREATE TABLE בתוך טרנזקציה אפשר לבטל. ב־MySQL כל DDL עושה COMMIT מרומז — migration עם שלוש פקודות שנכשל בשלישית משאיר את שתי הראשונות. לכן: migration קטן, פקודה אחת אם אפשר, ו־"expand/contract" (פרק 25).

⚠️ טעויות נפוצות
  • GET_LOCK על pool.query — הנעילה נלקחת בחיבור אחד, ה־migrations רצים באחרים, וה־RELEASE משחרר (או לא) בשלישי.

// P25.5-E22
import type { Pool } from "mysql2/promise";

export async function claimJobs(pool: Pool, workerId: string, limit: number): Promise<number[]> {
  const conn = await pool.getConnection(); // תקלה 1: היה pool.query ישירות ← כל פקודה בחיבור אחר, בלי טרנזקציה — הנעילה משתחררת מיד אחרי ה־SELECT
  try {
    await conn.beginTransaction();
    // תקלה 2: בלי FOR UPDATE SKIP LOCKED ← שני workers קוראים אותן שורות ושניהם "לוקחים"
    // תקלה 3: לא היה LIMIT ← worker אחד "לקח" את כל התור, והשאר עמדו בטלים
    const [rows] = await conn.query<any[]>("SELECT id FROM jobs WHERE status = 'queued' ORDER BY id LIMIT ? FOR UPDATE SKIP LOCKED", [limit]);
    const ids = rows.map((r) => r.id as number);
    if (ids.length) await conn.query("UPDATE jobs SET status = 'running', locked_by = ? WHERE id IN (?)", [workerId, ids]);
    await conn.commit();
    return ids;
  } catch (err) {
    await conn.rollback();
    throw err;
  } finally {
    conn.release();
  }
}

💡 רמז 1

💡 רמז 2

✅ פתרון
// P25.5-E24
import type { Pool } from "mysql2/promise";

export class EmptyCart extends Error {}
export class OutOfStock extends Error {
  productId: number;
  constructor(productId: number) {
    super(`אין מספיק מלאי למוצר ${productId}`);
    this.productId = productId;
  }
}

// "הזמן" של חנות הקפה — ב־MySQL. טרנזקציה אחת: מפתח idempotency, עגלה, נעילת המוצרים (FOR UPDATE, לפי id —
// סדר קבוע מונע deadlocks), בדיקת מלאי, הזמנה ופריטים עם המחיר של עכשיו, הורדת מלאי, ריקון העגלה
export async function createOrderFromCart(pool: Pool, customerId: number, idemKey: string): Promise<{ orderId: number; totalCents: number; replayed: boolean }> {
  const conn = await pool.getConnection();
  try {
    await conn.beginTransaction();
    // אותו מפתח בבקשה מקבילה: ה־INSERT מחכה לנעילה על המפתח, וממשיך כשהראשונה מסתיימת
    const [ins] = await conn.execute<any>("INSERT IGNORE INTO order_requests (idem_key, customer_id) VALUES (?, ?)", [idemKey, customerId]);
    if (ins.affectedRows === 0) {
      // FOR SHARE — קריאה "נועלת" רואה את הגרסה המחויבת האחרונה (לא את ה־snapshot של REPEATABLE READ)
      const [[prev]] = await conn.execute<any[]>("SELECT r.customer_id, r.order_id, o.total FROM order_requests r LEFT JOIN orders o ON o.id = r.order_id WHERE r.idem_key = ? FOR SHARE", [idemKey]);
      await conn.commit();
      if (!prev || prev.customer_id !== customerId || prev.order_id === null) throw new Error("Idempotency-Key בשימוש");
      return { orderId: prev.order_id, totalCents: Math.round(Number(prev.total) * 100), replayed: true };
    }
    const [cart] = await conn.execute<any[]>("SELECT product_id, quantity FROM cart_items WHERE customer_id = ? ORDER BY product_id", [customerId]);
    if (cart.length === 0) throw new EmptyCart("העגלה ריקה");
    const [products] = await conn.query<any[]>("SELECT id, price, stock FROM products WHERE id IN (?) ORDER BY id FOR UPDATE", [cart.map((c) => c.product_id)]);
    const byId = new Map(products.map((p) => [p.id, p]));
    let totalCents = 0;
    for (const c of cart) {
      const p = byId.get(c.product_id);
      if (!p || p.stock < c.quantity) throw new OutOfStock(c.product_id);
      totalCents += Math.round(Number(p.price) * 100) * c.quantity;
    }
    const [order] = await conn.execute<any>("INSERT INTO orders (customer_id, status, total) VALUES (?, 'pending_payment', ?)", [customerId, (totalCents / 100).toFixed(2)]);
    const orderId: number = order.insertId;
    await conn.query("INSERT INTO order_items (order_id, product_id, quantity, unit_price) VALUES ?", [cart.map((c) => [orderId, c.product_id, c.quantity, byId.get(c.product_id).price])]);
    for (const c of cart) await conn.execute("UPDATE products SET stock = stock - ? WHERE id = ?", [c.quantity, c.product_id]);
    await conn.execute("DELETE FROM cart_items WHERE customer_id = ?", [customerId]);
    await conn.execute("UPDATE order_requests SET order_id = ? WHERE idem_key = ?", [orderId, idemKey]);
    await conn.commit();
    return { orderId, totalCents, replayed: false };
  } catch (err) {
    await conn.rollback(); // גם שורת ה־idempotency מתבטלת — אפשר לנסות שוב עם אותו מפתח
    throw err;
  } finally {
    conn.release();
  }
}
⚠️ טעויות נפוצות
  • לשמור את ה־idempotency בטרנזקציה נפרדת מההזמנה — קריסה ביניהן משאירה מפתח "בטיפול" לנצח, או הזמנה בלי מפתח.

// P25.5-E25
import type pg from "pg";
import type { Pool } from "mysql2/promise";

// העברת טבלה מ־PostgreSQL ל־MySQL — משימה אמיתית כשמחליפים מסד או מאחדים מערכות.
// בקבוצות (keyset לפי id, לא OFFSET), עם המרת טיפוסים, ו־idempotent: הרצה שנייה לא מכפילה (ON DUPLICATE KEY UPDATE)
export async function copyCustomers(source: pg.Client | pg.Pool, target: Pool, { batchSize = 500 } = {}): Promise<{ copied: number; batches: number }> {
  let lastId = 0;
  let copied = 0;
  let batches = 0;
  for (;;) {
    const { rows } = await source.query(
      "SELECT id, name, email, is_vip, balance::text AS balance, created_at FROM customers WHERE id > $1 ORDER BY id LIMIT $2",
      [lastId, batchSize],
    );
    if (rows.length === 0) break;
    const values = rows.map((r: any) => [
      r.id,
      r.name,
      r.email,
      r.is_vip ? 1 : 0, // boolean ← TINYINT(1)
      r.balance, // numeric כמחרוזת ← DECIMAL — בלי לעבור דרך float
      // timestamptz ← DATETIME(3) ב־UTC (MySQL DATETIME לא שומר אזור זמן — מחליטים ומתעדים: UTC)
      (r.created_at as Date).toISOString().slice(0, 23).replace("T", " "),
    ]);
    await target.query(
      "INSERT INTO customers (id, name, email, is_vip, balance, created_at) VALUES ? AS new " +
        "ON DUPLICATE KEY UPDATE name = new.name, email = new.email, is_vip = new.is_vip, balance = new.balance, created_at = new.created_at",
      [values],
    );
    copied += rows.length;
    batches++;
    lastId = rows[rows.length - 1].id;
  }
  return { copied, batches };
}
