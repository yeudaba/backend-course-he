שיעור 5 — אינדקסים, EXPLAIN, migrations והעברת נתונים

⏱ ~50 דקות

🎯 בשיעור הזה
  • InnoDB: הטבלה היא האינדקס של המפתח הראשי — ומה זה אומר על בחירת מפתח.
  • EXPLAIN לפני ואחרי אינדקס — על 30,000 הזמנות.
  • migrations ב־MySQL: DDL בלי rollback, ו־GET_LOCK.
  • להעביר נתונים מ־PostgreSQL ל־MySQL.

1. clustered index

ב־InnoDB, הטבלה עצמה שמורה כ־B-tree לפי המפתח הראשי (clustered index), וכל אינדקס משני מחזיק, ליד כל ערך, את המפתח הראשי של השורה:

שלוש השלכות: מפתח ראשי קצר — הוא מוכפל בכל אינדקס; ממוין — AUTO_INCREMENT מוסיף תמיד בסוף העץ, בעוד UUID אקראי מכניס באמצע ומפצל דפים (UUIDv7 או BINARY(16) ממוין — אם חייבים UUID); וcovering index — אם האינדקס כולל את מה שה־SELECT מבקש, MySQL לא קורא את השורה בכלל.

2. EXPLAIN

"ההזמנות ששולמו של לקוח 3, מהחדשה". הוספתי ללקוח 3 עשרות אלפי הזמנות, רובן מבוטלות, והרצתי EXPLAIN עם האינדקס הקיים (customer_id, created_at), ואז עם אינדקס שכולל גם את status:

-- 30,000 הזמנות ללקוח 3, מתוכן 20 ששולמו
EXPLAIN FORMAT=TREE SELECT id, total FROM orders WHERE customer_id = 3 AND status = 'paid' ORDER BY created_at DESC LIMIT 10;
CREATE INDEX idx_orders_customer_status_created ON orders (customer_id, status, created_at);
EXPLAIN FORMAT=TREE SELECT id, total FROM orders WHERE customer_id = 3 AND status = 'paid' ORDER BY created_at DESC LIMIT 10;
-> Limit: 10 row(s)  (cost=376 rows=10)
    -> Filter: (orders.`status` = 'paid')  (cost=376 rows=3751)
        -> Index lookup on orders using idx_orders_customer_created (customer_id=3) (reverse)  (cost=376 rows=15003)
..
-> Limit: 10 row(s)  (cost=2.75 rows=10)
    -> Filter: (orders.`status` = 'paid')  (cost=2.75 rows=20)
        -> Index lookup on orders using idx_orders_customer_status_created (customer_id=3, status='paid') (reverse)  (cost=2.75 rows=20)

(הפלט מהרצה אמיתית על MySQL 8.4 — מקוצר רק במסגרת הטבלה. מספרי cost ו־rows הם הערכות מסטטיסטיקה, ויכולים להשתנות מעט בין הרצות.)

קוראים את העץ מלמטה למעלה. לפני: Index lookup … using idx_orders_customer_created (customer_id=3) (reverse) — הולך על כל ההזמנות של לקוח 3 מהסוף (ההערכה: כ־15,000 שורות), ומעליו Filter: status = 'paid' זורק את המבוטלות עד שמצטברות 10. אחרי: האינדקס החדש כולל את status, אז ה־lookup הוא (customer_id=3, status='paid') — ההערכה יורדת ל־20 שורות, והעלות (cost) מ־376 ל־2.75. (reverse) — קורא את האינדקס מהסוף, אז ORDER BY created_at DESC בחינם, בלי מיון (בטבלה רגילה תראה Using filesort כשאין אינדקס מתאים). ולזמנים אמיתיים: EXPLAIN ANALYZE (מ־8.0.18), כמו בפרק 18.

3. migrations

ההבדל הכי חשוב מ־PostgreSQL בעבודה יומיומית: ב־MySQL כל CREATE/ALTER/DROP עושה COMMIT מרומז. אין "migration בתוך טרנזקציה":

START TRANSACTION;
INSERT INTO customers (name, email, city) VALUES ('Before DDL', 'before@x.com', 'Haifa');
ALTER TABLE customers ADD COLUMN phone VARCHAR(20) NULL;
ROLLBACK;
SELECT name FROM customers WHERE email = 'before@x.com';
SELECT COUNT(*) AS has_phone FROM information_schema.COLUMNS WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'customers' AND COLUMN_NAME = 'phone';
+------------+
| name       |
+------------+
| Before DDL |
+------------+
+-----------+
| has_phone |
+-----------+
|         1 |
+-----------+

ה־ROLLBACK לא ביטל כלום — לא את ה־INSERT (שה־ALTER "מחייב") ולא את ה־ALTER. לכן: migration קטן (פקודת DDL אחת אם אפשר), expand/contract (פרק 25), ו־GET_LOCK כדי ששני שרתים שעולים יחד לא ירוצו את אותו migration פעמיים (E19). ועוד דבר טוב: הרבה ALTER ב־MySQL 8 רצים ALGORITHM=INSTANT (הוספת עמודה בסוף, למשל) — בלי לנעול את הטבלה.

4. מ־PostgreSQL ל־MySQL

משימה שקורית בעבודה: לאחד מערכות, או להעביר שירות למסד של החברה. העקרונות (E25):

  • בקבוצות, לפי מפתח (WHERE id > $last ORDER BY id LIMIT n) — לא OFFSET, ולא "הכול לזיכרון".
  • המרת טיפוסים מפורשת: boolean ← 0/1; numeric כמחרוזת ← DECIMAL (בלי לעבור דרך float); timestamptz ← DATETIME ב־UTC; ובדיקה ש־utf8mb4 מקבל את כל הטקסט.
  • idempotent: ON DUPLICATE KEY UPDATE — הרצה שנייה לא מכפילה, ומעדכנת שינויים.
  • אימות: ספירה וסכומים בשני הצדדים (SUM(balance) זהה עד האגורה).
