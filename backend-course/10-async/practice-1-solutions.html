P10-E31 · כמה זמן חיכה הטיימר? 🧠 הבנה רמה 1

💡 רמז 1

הטיימר "מבשיל" בזמן, אבל רץ רק כשהקוד הנוכחי מסתיים. הלולאה היא קוד נוכחי.

💡 רמז 2

הטיימר של 400ms לא מושפע: כשהלולאה נגמרת (300ms), עוד לא הגיע הזמן שלו.

✅ פתרון
const start = Date.now();
const round = () => Math.round((Date.now() - start) / 100) * 100;

setTimeout(() => console.log("טיימר של 100ms רץ אחרי", round()), 100);
setTimeout(() => console.log("טיימר של 400ms רץ אחרי", round()), 400);

while (Date.now() - start < 300) {
  // עבודה סינכרונית כבדה
}
console.log("סוף הלולאה", round());
סוף הלולאה 300
טיימר של 100ms רץ אחרי 300

הטיימר של 100ms איחר ב־200ms — הוא חיכה ללולאה. הטיימר של 400ms רץ בזמן, כי כשהלולאה נגמרה עוד היה לו זמן.

בשרת: כל 300ms שבהם הקוד שלך מחשב משהו סינכרוני, אף בקשה אחרת לא מקבלת תשובה — גם לא בקשה פשוטה שהייתה לוקחת מילישנייה. עשר בקשות כבדות בבת אחת = האחרונה מחכה שלוש שניות.

⚠️ טעויות נפוצות
  • לחשוב ש־setTimeout(fn, 100) מבטיח "בדיוק בעוד 100ms". הוא מבטיח "לא לפני 100ms".

P10-E32 · מה נשלח "למטבח"? 🧠 הבנה רמה 1

💡 רמז 1

שאל: מי עושה את העבודה בזמן ההמתנה? אם זה הקוד שלך (JavaScript) — הוא חוסם. אם זו מערכת ההפעלה, הרשת או המסד — הוא "במטבח".

💡 רמז 2

שים לב ל־Sync בשם הפונקציה: זה בדיוק "המלצר עומד ומחכה".

✅ פתרון
  1. למטבח. רק נרשם טיימר; הקוד ממשיך מיד.
  2. חוסם. זה חישוב של JavaScript — המלצר עצמו עובד.
  3. חוסם. Sync = עוצרים עד שהקובץ נקרא.
  4. למטבח. המסד עובד, Node ממשיך ומקבל את התוצאה ב־callback.
  5. חוסם. גם זה חישוב של JavaScript — ועל 50MB הוא יכול לקחת זמן מורגש.
  6. למטבח. הגרסה האסינכרונית (שיעור 2).

הכי מסוכנים בשרת: 2 ו־5 — חישוב כבד שאי אפשר "לשלוח למטבח" פשוט בהחלפת פונקציה. ‏3 קל לתקן (מחליפים ל־readFile). בזמן שאחד מהם רץ, כל שאר הבקשות מחכות.

⚠️ טעויות נפוצות
  • לחשוב ש־JSON.parse "מהיר תמיד". על קלט ענק הוא חוסם בדיוק כמו לולאה.

P10-E06 · delay 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

new Promise((resolve) => setTimeout(() => resolve(value), ms))

💡 רמז 2

countdown: async עם לולאה ו־await delay(ms) בכל סיבוב.

✅ פתרון
// P10-E06
function delay(ms, value) {
  return new Promise((resolve) => setTimeout(() => resolve(value), ms));
}

async function countdown(from, ms, log = console.log) {
  for (let n = from; n >= 1; n--) {
    log(n);
    await delay(ms);
  }
  log("🚀");
}

P10-E34 · הודעות במרווחים 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

לולאה שרושמת טיימר לכל הודעה. הלולאה עצמה רצה מיד — רק ה־callbacks מחכים.

💡 רמז 2

בתוך for (let i = 0; ...): setTimeout(() => log(messages[i]), i * gap);

✅ פתרון
// P10-E34: הודעות במרווחים
function logInOrder(messages, gap, log) {
  for (let i = 0; i < messages.length; i++) {
    setTimeout(() => log(messages[i]), i * gap);
  }
}

logInOrder(["שלוש", "שתיים", "אחת"], 20, console.log);
console.log("מתחילים");

module.exports = { logInOrder };

שלוש
שתיים
אחת

שלושת הטיימרים נרשמים בבת אחת — כל אחד עם זמן אחר. זה מה שיוצר את המרווחים, לא ההמתנה בתוך הלולאה (אין דבר כזה "לחכות" בתוך לולאה רגילה).

⚠️ טעויות נפוצות
  • כל הטיימרים עם gap — כולם רצים יחד אחרי gap.
  • var i במקום let i — כל ה־callbacks רואים את אותו i, שבסוף הלולאה הוא messages.length (ראה P10-E40).

P10-E35 · לחסום בכוונה 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

const start = Date.now(); ואחריו while שהתנאי שלו משווה את Date.now() - start ל־ms.

💡 רמז 2

גוף הלולאה ריק. אחרי הלולאה: return Date.now() - start;

✅ פתרון
// P10-E35: לחסום בכוונה
function blockFor(ms) {
  const start = Date.now();
  while (Date.now() - start < ms) {
    // לא עושים כלום — רק תופסים את המלצר
  }
  return Date.now() - start;
}

setTimeout(() => console.log("טיימר"), 0);
console.log(blockFor(50) >= 50);
console.log("אחרי החסימה");

module.exports = { blockFor };

טיימר של 0ms חיכה 50ms — כי JavaScript לא קוטע קוד שרץ. זו בדיוק הסיבה שאסור לכתוב לולאות כאלה בשרת: נשתמש בה רק כדי להדגים חסימה (P10-E39).

⚠️ טעויות נפוצות

  • להחזיר את ms עצמו במקום הזמן שנמדד.

P10-E36 · שעון מתקתק 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

פונקציה פנימית step(n) שרושמת טיימר. בתוך ה־callback של הטיימר: אם n > times — onDone(); אחרת onTick(n) וקריאה ל־step(n + 1).

💡 רמז 2

שים לב ש־onDone בא מיד אחרי הטיק האחרון, בלי המתנה נוספת. אפשר לבדוק אחרי onTick(n): אם n === times — onDone(), אחרת step(n + 1).

✅ פתרון
// P10-E36: שעון מתקתק
function ticker(times, ms, onTick, onDone) {
  function step(n) {
    setTimeout(() => {
      if (n > times) {
        onDone();
        return;
      }
      onTick(n);
      if (n === times) {
        onDone();
      } else {
        step(n + 1);
      }
    }, ms);
  }
  step(1);
}

ticker(3, 10, (n) => console.log("טיק", n), () => console.log("סוף"));
ticker(0, 5, () => console.log("לא אמור לרוץ"), () => console.log("סוף בלי טיקים"));

module.exports = { ticker };

טיק 2
טיק 3
סוף

"טיימר בתוך טיימר" שומר על מרווח בין טיק לטיק גם אם onTick לוקח זמן: הטיימר הבא נרשם רק כשהקודם הסתיים. המקרה n > times קורה רק עם times = 0.

⚠️ טעויות נפוצות
  • לולאה שרושמת את כל הטיימרים מראש עם אותו ms — כל הטיקים רצים יחד.
  • לקרוא ל־onDone גם אחרי הטיק האחרון וגם בסיבוב נוסף — פעמיים.

P10-E37 · מתי כולם סיימו? 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

אי אפשר לדעת מראש איזה טיימר יהיה אחרון. במקום זה: כל טיימר מוסיף את עצמו ל־order, ובודק אם order.length הגיע ל־delays.length.

💡 רמז 2

המקרה הריק: if (delays.length === 0) { setTimeout(() => done([]), 0); return; }

✅ פתרון
// P10-E37: מתי כולם סיימו?
function afterAll(delays, done) {
  if (delays.length === 0) {
    setTimeout(() => done([]), 0);
    return;
  }
  const order = [];
  for (const ms of delays) {
    setTimeout(() => {
      order.push(ms);
      if (order.length === delays.length) done(order);
    }, ms);
  }
}

afterAll([30, 10, 20], (order) => console.log(order));
afterAll([], (order) => console.log("ריק:", order));

module.exports = { afterAll };
ריק: []
[ 10, 20, 30 ]

זה הדפוס של "סופרים מי סיים": אין מקום אחד שבו "מחכים לכולם", ולכן כל callback בודק בעצמו אם הוא האחרון. בשיעור 4 Promise.all יעשה את זה בשבילך.

⚠️ טעויות נפוצות
  • לקרוא ל־done בסוף הלולאה — הלולאה מסתיימת לפני שאף טיימר רץ, ו־order עדיין ריק.
  • לבחור את ה־delay הגדול ביותר ולקרוא ל־done ממנו — עובד כאן, אבל לא כשהזמנים לא ידועים מראש (קריאות לשרת).

P10-E38 · עבודה כבדה בחתיכות 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

פונקציה פנימית runFrom(start) שרושמת טיימר. בתוכו: לולאה מ־start עד Math.min(start + size, items.length), ואחריה — או done() או runFrom(start + size).

💡 רמז 2

אם start + size >= items.length — זו הייתה החתיכה האחרונה. המערך הריק עובר באותה דרך: הלולאה לא רצה, ו־done() נקראת בטיימר.

✅ פתרון
// P10-E38: עבודה כבדה בחתיכות
function inChunks(items, size, work, done) {
  function runFrom(start) {
    setTimeout(() => {
      const end = Math.min(start + size, items.length);
      for (let i = start; i < end; i++) {
        work(items[i]);
      }
      if (end >= items.length) {
        done();
      } else {
        runFrom(end);
      }
    }, 0);
  }
  runFrom(0);
}

const out = [];
inChunks([1, 2, 3, 4, 5], 2, (n) => out.push(`עבודה ${n}`), () => console.log(out.join(", ") + ", סוף"));
setTimeout(() => out.push("בקשה אחרת"), 0);

module.exports = { inChunks };
עבודה 1, עבודה 2, בקשה אחרת, עבודה 3, עבודה 4, עבודה 5, סוף

ה"בקשה האחרת" נרשמה אחרי החתיכה הראשונה ולפני השנייה — ולכן היא רצה ביניהן. אילו הכול היה לולאה אחת, היא הייתה מחכה עד הסוף. ככה Node "משתף" זמן בין עבודה כבדה לשאר הבקשות.

⚠️ טעויות נפוצות
  • לרשום את כל החתיכות מראש בלולאה (כל אחת בטיימר משלה) — עובד, אבל טיימרים אחרים שנרשמו אחרי הקריאה כבר לא ייכנסו ביניהן.
  • לבצע את החתיכה הראשונה מיד (בלי טיימר) — הבודק דורש שגם היא תחכה.

P10-E39 · כמה הטיימר איחר? 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

שומרים const start = Date.now() לפני שרושמים את הטיימר. בתוך ה־callback: Date.now() - start - requested.

💡 רמז 2

Math.max(0, ...) מבטיח שלא תצא תוצאה שלילית.

✅ פתרון
// P10-E39: כמה הטיימר איחר?
function measureLateness(requested, blockMs, report) {
  const start = Date.now();
  setTimeout(() => {
    report(Math.max(0, Date.now() - start - requested));
  }, requested);
  while (Date.now() - start < blockMs) {
    // חוסמים בכוונה
  }
}

measureLateness(10, 60, (late) => console.log("עם חסימה:", late >= 45));
measureLateness(50, 0, (late) => console.log("בלי חסימה:", late < 30));

module.exports = { measureLateness };
עם חסימה: true
בלי חסימה: true

שים לב לסדר: הטיימר השני נרשם רק אחרי שהחסימה הראשונה הסתיימה (60ms), והוא עצמו רץ בזמן. כלי ניטור אמיתיים ב־Node מודדים בדיוק את זה ("event loop lag") — אם הוא גבוה, משהו חוסם את השרת.

⚠️ טעויות נפוצות
  • למדוד את start בתוך הטיימר — תמיד יוצא 0.
  • לשים את הלולאה לפני רישום הטיימר — אז הטיימר לא מאחר בכלל, כי הוא מתחיל לספור אחרי החסימה.

P10-E40 · var, let וטיימרים 🧠 הבנה רמה 2

💡 רמז 1

מתי רצים ה־callbacks — בזמן הלולאה או אחריה? ומה הערך של i אחרי הלולאה?

💡 רמז 2

עם var יש i אחד לכל הלולאה. עם let — j חדש בכל סיבוב.

✅ פתרון
for (var i = 1; i <= 3; i++) {
  setTimeout(() => console.log("var:", i), 0);
}
for (let j = 1; j <= 3; j++) {
  setTimeout(() => console.log("let:", j), 0);
}
console.log("הלולאות הסתיימו", i);
הלולאות הסתיימו 4
var: 4
var: 4
var: 4
let: 1
let: 2
let: 3

כל ה־callbacks רצים אחרי שהקוד הסינכרוני (שתי הלולאות וה־log האחרון) הסתיים. עד אז i כבר 4 — ושלושת ה־callbacks הראשונים רואים את אותו i. עם let כל סיבוב יוצר משתנה חדש, וכל callback זוכר את שלו.

⚠️ טעויות נפוצות
  • לחשוב שהבעיה היא ב־setTimeout. הבעיה היא var; הטיימר רק חושף אותה.

P10-E41 · try/catch סביב טיימר 🧠 הבנה רמה 2

💡 רמז 1

מתי ה־try מסתיים? ומתי ה־callback רץ?

💡 רמז 2

כשה־callback רץ, כבר אין try פתוח — ה־finally ו"אחרי הכול" כבר הודפסו.

✅ פתרון
try {
  setTimeout(() => console.log("בתוך הטיימר"), 0);
  console.log("סוף ה־try");
} catch (err) {
  console.log("catch:", err.message);
} finally {
  console.log("finally");
}
console.log("אחרי הכול");

בתוך הטיימר

ה־try רק רושם את הטיימר, ומסתיים מיד. לכן throw בתוך ה־callback לא היה נתפס: אין אף try פתוח כשהוא רץ, והתוכנית הייתה קורסת. את השגיאה צריך לתפוס בתוך ה־callback — וזה מה ש־error-first (שיעור 2) ו־Promises (שיעור 3) פותרים בצורה מסודרת.

⚠️ טעויות נפוצות
  • לחשוב שה־finally מחכה לטיימר. הוא לא יודע שיש טיימר.

"callback" לא אומר "אסינכרוני". של map רץ עכשיו ומחזיר ערך; של setTimeout נרשם ורץ אחר כך — ואת מה שהוא מחזיר אף אחד לא מקבל.

P10-E43 · סדר הטיימרים — בלי להריץ אותם 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

[...timers].sort((a, b) => a.ms - b.ms) — ואחר כך map.

💡 רמז 2

אין צורך לטפל בשוויון בעצמך: sort של JavaScript יציב, כך שבין שני טיימרים עם אותו ms הסדר המקורי נשמר.

✅ פתרון
// P10-E43: סדר הטיימרים — בלי להריץ אותם
function timerOrder(timers) {
  return [...timers].sort((a, b) => a.ms - b.ms).map((t) => t.label);
}

const timers = [
  { label: "A", ms: 100 },
  { label: "B", ms: 0 },
  { label: "C", ms: 50 },
  { label: "D", ms: 0 },
];
console.log(timerOrder(timers));
console.log(timers[0].label); // המקור לא השתנה

module.exports = { timerOrder };

הניבוי מתאים למה שקורה באמת כל עוד הקוד לא חוסם, וכל הטיימרים נרשמו באותו רגע. (טיימר שנרשם מתוך טיימר אחר — כמו C ב־P10-E29 — מתחיל לספור רק כשהוא נרשם.)

⚠️ טעויות נפוצות
  • timers.sort(...) בלי העתקה — המערך של מי שקרא לך משתנה (הבודק תופס).
  • sort() בלי פונקציה — ממיין אובייקטים כמחרוזות, כלומר לא ממיין בכלל.

P10-E44 · מנבא ה־event loop 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

שלושה מערכים: sync, ‏micro, ‏timers. עוברים פעם אחת על השלבים, ומכניסים כל אחד למקום שלו.

💡 רמז 2

בסוף: [...sync, ...micro, ...timers.sort((a, b) => a.ms - b.ms).map((t) => t.label)].

✅ פתרון
// P10-E44: מנבא ה־event loop
function predictOrder(steps) {
  const sync = [];
  const micro = [];
  const timers = [];
  for (const step of steps) {
    switch (step.kind) {
      case "sync":
        sync.push(step.label);
        break;
      case "promise":
        micro.push(step.label);
        break;
      case "timeout":
        timers.push(step);
        break;
      default:
        throw new Error(`סוג לא מוכר: ${step.kind}`);
    }
  }
  timers.sort((a, b) => a.ms - b.ms);
  return [...sync, ...micro, ...timers.map((t) => t.label)];
}

console.log(predictOrder([
  { kind: "sync", label: "1" },
  { kind: "timeout", label: "timeout", ms: 0 },
  { kind: "promise", label: "promise" },
  { kind: "sync", label: "2" },
]));

module.exports = { predictOrder };
[ '1', '2', 'promise', 'timeout' ]

המנבא הזה עונה נכון על P10-E01 ועל השיעור. הוא לא יודע לטפל בטיימר שנרשם מתוך callback (P10-E29, ‏P10-E30) — שם צריך לדמות את התורים צעד אחר צעד.

⚠️ טעויות נפוצות
  • לשכוח break באחד ה־cases — השלב נכנס לשתי קופסאות.
  • למיין את הטיימרים לפני שעברת על כל השלבים — לא שגיאה, אבל מיותר; ממיינים פעם אחת בסוף.

P10-E45 · מונה עצלן 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

let count = 0; בתוך lazyCounter, ו־return { add(n) { ... }, get() { ... } };

💡 רמז 2

בתוך add: setTimeout(() => { count += n; }, ms);

✅ פתרון
// P10-E45: מונה עצלן
function lazyCounter(ms) {
  let count = 0;
  return {
    add(n) {
      setTimeout(() => {
        count += n;
      }, ms);
    },
    get() {
      return count;
    },
  };
}

const c = lazyCounter(20);
c.add(5);
c.add(2);
console.log(c.get());
setTimeout(() => console.log(c.get()), 40);

module.exports = { lazyCounter };
0
7

כל מונה שנוצר מקבל count משלו (הבודק יוצר שניים ומוודא שהם לא מתערבבים). זה גם טעימה ממה שיקרה בשרת אמיתי: "כתבתי למסד" ו"המסד כבר מעודכן" הם שני רגעים שונים.

⚠️ טעויות נפוצות
  • let count מחוץ לפונקציה — כל המונים חולקים מספר אחד.
  • get() שמחזירה Promise או מחכה — המשימה מבקשת את הערך הנוכחי.
