P17-E01 · לתכנן ספרייה 🧠 הבנה רמה 1

💡 רמז 1

ספרים ↔ מחברים הוא רבים־לרבים.

💡 רמז 2

האם מוחקים חבר שיש לו היסטוריית השאלות?

✅ פתרון
  • authors(id, full_name), books(id, title, isbn UNIQUE, published_year)
  • book_authors(book_id → books ON DELETE CASCADE, author_id → authors, PRIMARY KEY (book_id, author_id)) — טבלת קישור. מחיקת ספר מוחקת את הקישורים; מחיקת מחבר שיש לו ספרים — חסומה (ברירת מחדל).
  • members(id, full_name, email UNIQUE, joined_on)
  • loans(id, book_id → books, member_id → members, loaned_at, due_at, returned_at NULL) — שני ה־FK עם ברירת המחדל (RESTRICT): היסטוריית השאלות היא מידע שלא רוצים לאבד, אז אי אפשר למחוק ספר או חבר שיש להם השאלות. (במקום למחוק חבר — מסמנים is_active = false.)

(ואם יש כמה עותקים מאותו ספר? טבלה נוספת copies(id, book_id, barcode), וההשאלה מצביעה על עותק.)

⚠️ טעויות נפוצות
  • books.author_id — מאפשר רק מחבר אחד לספר.
  • ON DELETE CASCADE על loans — מחיקת חבר מוחקת בשקט את כל ההיסטוריה.

P17-E29 · איפה שמים את ה־foreign key? 🧠 הבנה רמה 1

💡 רמז 1

ה־FK תמיד בצד ה"רבים": שואלים "למי יש אחד?" — שם שמים עמודה שמצביעה עליו.

💡 רמז 2

אם לשני הצדדים יש "הרבה" — אף אחת מהטבלאות לא יכולה להחזיק עמודה אחת. צריך טבלה שלישית. ובסעיף 5: FK יכול להצביע על אותה טבלה.

✅ פתרון
  1. אחד־לרבים. comments.post_id ← posts.id.
  2. רבים־לרבים. טבלת קישור enrollments(student_id, course_id), מפתח ראשי של הזוג (סטודנט לא נרשם פעמיים לאותו קורס). אפשר להוסיף לה עמודות של הקשר עצמו — enrolled_on, grade — כמו quantity ב־order_items.
  3. אחד־לאחד. privacy_settings.user_id ← users.id עם UNIQUE (או שה־user_id הוא גם המפתח הראשי). ולרוב — פשוט עוד עמודות ב־users.
  4. אחד־לרבים. products.supplier_id ← suppliers.id (הצד של ה"רבים" הוא המוצרים).
  5. אחד־לרבים בתוך אותה טבלה: employees.manager_id ← employees.id, ו־NULL למנכ״ל (אין לו מנהל).
⚠️ טעויות נפוצות
  • לשים comment_ids (רשימה) בטבלת הפוסטים — עמודה מחזיקה ערך אחד; רשימה היא שורות בטבלה אחרת.
  • טבלת קישור בלי מפתח ראשי על הזוג — אותו סטודנט נרשם פעמיים לאותו קורס, וכל ספירה יוצאת כפולה.

P17-E30 · מה יעבור ומה ייחסם? 🧠 הבנה רמה 2

💡 רמז 1

FK נבדק לשני הכיוונים: כשכותבים "ילד" (חייב להצביע על הורה קיים), וכשמוחקים "הורה" (אסור שיישארו ילדים שמצביעים עליו — אלא אם הוגדר CASCADE או SET NULL).

💡 רמז 2

גם UPDATE של עמודת FK הוא "כתיבה של ילד".

✅ פתרון

1 ו־2 נחסמים בכתיבה של "ילד" שמצביע על הורה שלא קיים (מוצר 99, לקוח 50). 3 עובר — אף פריט לא מצביע על מוצר 11. 4 נחסם — מוצר 1 נמצא בארבע הזמנות, ו־order_items.product_id הוגדר בלי ON DELETE (ברירת המחדל: לחסום). 5 עובר — אין מוצר שמצביע על gift cards.

⚠️ טעויות נפוצות
  • לחשוב שה־FK בודק רק INSERT. הוא בודק כל שינוי שעלול ליצור "יתום": ‏INSERT ו־UPDATE בצד הילד, DELETE ו־UPDATE של המפתח בצד ההורה.

P17-E31 · CASCADE, ‏SET NULL או לחסום? 🧠 הבנה רמה 1

💡 רמז 1

שאל: "האם לילד יש משמעות בלי ההורה?" אם לא — CASCADE. אם הקשר לא חובה — SET NULL. אם הילד הוא מידע שאסור לאבד — לחסום.

💡 רמז 2

SET NULL אפשרי רק כשעמודת ה־FK יכולה להיות NULL (בלי NOT NULL).

✅ פתרון
  1. CASCADE — פריט בעגלה בלי העגלה הוא חסר משמעות.
  2. לחסום — חשבונית היא מסמך חשבונאי; מחיקת לקוח לא אמורה למחוק אותה (ובדרך כלל גם לא מוחקים לקוח כזה — מסמנים אותו כלא פעיל).
  3. SET NULL — העובד עזב, המשימה נשארת ומחכה להקצאה מחדש. העמודה בלי NOT NULL.
  4. לחסום — מחיקת מוצר הייתה מוחקת שורות מהזמנות ישנות ומשנה הכנסות עבר. מוצר שירד מהמדף מסמנים is_active = false.
  5. CASCADE — טוקן לאיפוס סיסמה של משתמש שנמחק לא שווה כלום (ואפילו מסוכן להשאיר אותו).
⚠️ טעויות נפוצות
  • CASCADE "ליתר ביטחון" בכל מקום — מחיקה אחת של לקוח מוחקת הזמנות, פריטים ותשלומים, בלי שגיאה ובלי דרך חזרה.
  • SET NULL על עמודה שהוגדרה NOT NULL — המחיקה תיכשל בשגיאת NOT NULL.

P17-E33 · אותו מוצר פעמיים באותה הזמנה 🧠 הבנה רמה 2

💡 רמז 1

מה המפתח הראשי של order_items? (store.sql, או הטבלה בשיעור.)

💡 רמז 2

מפתח ראשי של זוג אומר: לכל זוג (הזמנה, מוצר) — שורה אחת לכל היותר.

✅ פתרון

ה־INSERT נכשל: המפתח הראשי (order_id, product_id) לא מרשה שתי שורות לאותו מוצר באותה הזמנה. וזה טוב — אחרת "2 יחידות" היו שתי שורות של 1, וכל דוח של "כמה שורות בהזמנה" היה משקר. הדרך הנכונה היא לעדכן את הכמות של השורה הקיימת. ‏RETURNING * (פרק 16) מראה שהכמות עלתה ל־3.

⚠️ טעויות נפוצות
  • להוריד את המפתח הראשי "כדי שה־INSERT יעבור" — זה מעביר את הבעיה לכל השאילתות שיבואו אחר כך.

P17-E26 · הספרייה מ־P17-E01 — בקוד 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

הסדר חשוב: טבלה שמצביעים עליה נוצרת לפני הטבלה שמצביעה. ‏authors ו־books ← book_authors; ‏members ← loans. ‏FK: ‏book_id integer NOT NULL REFERENCES books (id) ON DELETE CASCADE. בלי ON DELETE, ברירת המחדל חוסמת מחיקה.

💡 רמז 2

מפתח ראשי של זוג נכתב בסוף הטבלה: PRIMARY KEY (book_id, author_id). גם אילוץ על שתי עמודות: CHECK (returned_on >= loaned_on). בשאילתה: שני JOIN (ספרים וחברים) ו־WHERE l.returned_on IS NULL.

✅ פתרון
CREATE TABLE authors (
  id         integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  full_name  text NOT NULL
);

CREATE TABLE books (
  id              integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title           text NOT NULL,
  isbn            text NOT NULL UNIQUE,
  published_year  integer
);

CREATE TABLE book_authors (
  book_id    integer NOT NULL REFERENCES books (id) ON DELETE CASCADE,
  author_id  integer NOT NULL REFERENCES authors (id),
  PRIMARY KEY (book_id, author_id)
);

CREATE TABLE members (
  id         integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  full_name  text NOT NULL,
  email      text NOT NULL UNIQUE
);

CREATE TABLE loans (
  id           integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  book_id      integer NOT NULL REFERENCES books (id),
  member_id    integer NOT NULL REFERENCES members (id),
  loaned_on    date NOT NULL DEFAULT CURRENT_DATE,
  returned_on  date,
  CHECK (returned_on >= loaned_on)
);

ההחלטות מ־P17-E01 נמצאות עכשיו במסד, ולא רק במסמך: ‏ON DELETE CASCADE רק בקישור ספר־מחבר (קישור בלי ספר הוא חסר משמעות), ובכל השאר ברירת המחדל שחוסמת. היסטוריית השאלות היא מידע שלא רוצים לאבד, אז המסד מסרב למחוק ספר או חבר שיש להם השאלות.

⚠️ טעויות נפוצות
  • ON DELETE CASCADE גם ב־loans — מחיקת חבר מוחקת בשקט את כל ההיסטוריה שלו.
  • id נוסף ב־book_authors בלי PRIMARY KEY (book_id, author_id) — אותו מחבר יכול להיות מקושר לאותו ספר פעמיים.
  • ליצור את loans לפני members — ‏relation "members" does not exist.
  • להכניס ids במפורש ב־INSERT INTO books (id, ...) — עם GENERATED ALWAYS המסד מסרב. סומכים על הסדר: 1, 2, 3.

ואז customerIds.has(o.customer_id).

💡 רמז 2

פונקציה קטנה לנוסח:

const missing = (col: string, value: number, table: string) => `Key (${col})=(${value}) is not present in table "${table}".`
✅ פתרון
// P17-E43: בודק FK בזיכרון
export type Data = {
  customers: { id: number }[];
  products: { id: number }[];
  orders: { id: number; customer_id: number }[];
  order_items: { order_id: number; product_id: number }[];
};

const missing = (col: string, value: number, table: string) => `Key (${col})=(${value}) is not present in table "${table}".`;

export function checkForeignKeys(data: Data): string[] {
  const customerIds = new Set(data.customers.map((c) => c.id));
  const productIds = new Set(data.products.map((p) => p.id));
  const orderIds = new Set(data.orders.map((o) => o.id));
  const problems: string[] = [];
  for (const o of data.orders) {
    if (!customerIds.has(o.customer_id)) problems.push(missing("customer_id", o.customer_id, "customers"));
  }
  for (const i of data.order_items) {
    if (!orderIds.has(i.order_id)) problems.push(missing("order_id", i.order_id, "orders"));
    if (!productIds.has(i.product_id)) problems.push(missing("product_id", i.product_id, "products"));
  }
  return problems;
}

שלושה Setים — ואז כל בדיקה היא has אחד. זה בדיוק מה שהמסד עושה בכל INSERT (עם index על המפתח הראשי במקום Set). שים לב: פריט שמצביע על הזמנה יתומה (שההזמנה שלה מצביעה על לקוח חסר) עדיין עובר — הוא מצביע על הזמנה שקיימת במערך. גם המסד בודק רק קשר אחד בכל פעם.

⚠️ טעויות נפוצות
  • data.customers.some((c) => c.id === o.customer_id) בתוך הלולאה — נכון, אבל לכל הזמנה עובר על כל הלקוחות. בייצוא של 100,000 הזמנות — מיליארדי השוואות.
  • לשכוח את הנקודה בסוף ההודעה, או מירכאות רגילות במקום כפולות — הנוסח צריך להיות זהה.

// P17-E44: הוספת פריט מ־Node, עם קודי השגיאה
export type Db = { query(text: string, values?: unknown[]): Promise<{ rows: any[] }> };
export type AddResult = { ok: true; unitPrice: number } | { ok: false; error: "not_found" | "duplicate" | "invalid" };

const ERRORS: Record<string, "not_found" | "duplicate" | "invalid"> = {
  "23503": "not_found", // foreign key: אין הזמנה כזו
  "23505": "duplicate", // המפתח הראשי (order_id, product_id)
  "23514": "invalid", // CHECK (quantity > 0)
};

export async function addOrderItem(client: Db, orderId: number, productId: number, quantity: number): Promise<AddResult> {
  const { rows } = await client.query("SELECT price FROM products WHERE id = $1 AND is_active", [productId]);
  if (rows.length === 0) return { ok: false, error: "not_found" };
  const unitPrice = Number(rows[0].price);
  try {
    await client.query("INSERT INTO order_items (order_id, product_id, quantity, unit_price) VALUES ($1, $2, $3, $4)", [orderId, productId, quantity, unitPrice]);
  } catch (err: any) {
    const error = ERRORS[err.code];
    if (error) return { ok: false, error };
    throw err;
  }
  return { ok: true, unitPrice };
}

שלוש בדיקות שלא כתבת בקוד: "ההזמנה קיימת" (FK), "המוצר לא כבר בהזמנה" (מפתח ראשי), "הכמות חיובית" (CHECK). המסד עושה אותן בכל מקרה — הקוד רק מתרגם את התשובה לשפה של האפליקציה. ו־throw err בסוף חשוב: שגיאה שלא הבנת (המסד נפל, טיפוס לא נכון) לא הופכת בשקט ל"לא נמצא".

⚠️ טעויות נפוצות
  • catch { return { ok: false, error: "not_found" } } לכל שגיאה — תקלת רשת נראית ללקוח כמו "ההזמנה לא קיימת".
  • מחיר מהלקוח (מגוף הבקשה) במקום מהמסד — כל אחד יכול לקנות ב־1 ש״ח.

P17-E45 · מ־JSON מקונן לטבלאות 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

שתי מפות: Map<string, number> של אימייל ← id ושל שם מוצר ← id. אם אין — map.size + 1, ומוסיפים שורה לטבלה.

💡 רמז 2

לפריטים של הזמנה: Map<number, row> של product_id ← השורה, כדי לחבר כמות כשהמוצר חוזר.

✅ פתרון
// P17-E45: מ־JSON מקונן לטבלאות
export type FlatOrder = { orderId: number; email: string; fullName: string; items: { product: string; price: number; qty: number }[] };
export type Tables = {
  customers: { id: number; email: string; full_name: string }[];
  products: { id: number; name: string }[];
  orders: { id: number; customer_id: number }[];
  order_items: { order_id: number; product_id: number; quantity: number; unit_price: number }[];
};

export function normalize(input: FlatOrder[]): Tables {
  const t: Tables = { customers: [], products: [], orders: [], order_items: [] };
  const customerIds = new Map<string, number>();
  const productIds = new Map<string, number>();

  for (const o of input) {
    const email = o.email.toLowerCase();
    let customerId = customerIds.get(email);
    if (customerId === undefined) {
      customerId = customerIds.size + 1;
      customerIds.set(email, customerId);
      t.customers.push({ id: customerId, email, full_name: o.fullName });
    }
    t.orders.push({ id: o.orderId, customer_id: customerId });

    const lines = new Map<number, Tables["order_items"][number]>();
    for (const item of o.items) {
      let productId = productIds.get(item.product);
      if (productId === undefined) {
        productId = productIds.size + 1;
        productIds.set(item.product, productId);
        t.products.push({ id: productId, name: item.product });
      }
      const line = lines.get(productId);
      if (line) line.quantity += item.qty;
      else {
        const row = { order_id: o.orderId, product_id: productId, quantity: item.qty, unit_price: item.price };
        lines.set(productId, row);
        t.order_items.push(row);
      }
    }
  }
  return t;
}

ה־Mapים הם ה"UNIQUE" שלך: לפני שמוסיפים שורה — בודקים אם כבר יש כזו. ‏lines מתאפס לכל הזמנה, כי המפתח הראשי הוא הזוג (הזמנה, מוצר) — אותו מוצר בהזמנה אחרת הוא שורה חדשה.

⚠️ טעויות נפוצות
  • מפתח לפי האימייל כמו שהוא — Dana@Example.com ו־dana@example.com הופכים לשני לקוחות.
  • lines אחד לכל הקלט (במקום לכל הזמנה) — כמויות מהזמנות שונות מתחברות.
