P17-E04 · WHERE או HAVING? 🧠 הבנה רמה 1

💡 רמז 1

WHERE — לפני הקיבוץ, בלי צבירות.

💡 רמז 2

ב־SELECT וב־HAVING — רק עמודות הקיבוץ או צבירות.

✅ פתרון
  1. ✘ צבירה ב־WHERE.
  2. ✔ סטטוסים שיש להם יותר מ־2 הזמנות, עם הכמות.
  3. ✔ כמה הזמנות בכל סטטוס, מאז מרץ.
  4. ✘ customer_id לא בקיבוץ ולא בצבירה.
  5. ✘ status ב־HAVING בלי צבירה — לאיזה status בקבוצה? (התכוונת: WHERE status = 'paid'.)
⚠️ טעויות נפוצות
  • להעביר כל תנאי ל־HAVING "ליתר ביטחון" — עובד לפעמים, אבל איטי (מקבצים שורות שאחר כך זורקים).

P17-E58 · שלושה סוגי COUNT 🧠 הבנה רמה 1

💡 רמז 1

COUNT(*) סופר שורות. ‏COUNT(עמודה) סופר ערכים שאינם NULL (כמו במלכודת מהשיעור).

💡 רמז 2

DISTINCT בתוך COUNT — סופר כל ערך שונה פעם אחת.

✅ פתרון
SELECT COUNT(*) AS all_rows, COUNT(city) AS with_city, COUNT(DISTINCT city) AS cities
FROM customers;
 all_rows | with_city | cities
----------+-----------+--------
        8 |         6 |      4
(1 row)

8 שורות; 6 עם עיר; 4 ערים שונות (Tel Aviv, ‏Haifa, ‏Jerusalem, ‏Beer Sheva — ו־NULL לא נספר כ"עיר"). ‏COUNT(DISTINCT o.id) הוא גם התיקון הקלאסי כש־JOIN מכפיל שורות (P17-E22).

⚠️ טעויות נפוצות
  • לחשוב ש־COUNT(city) סופר "כמה ערים יש" — הוא סופר שורות עם עיר.

P17-E59 · כינוי ב־WHERE, ב־HAVING וב־ORDER BY 🧠 הבנה רמה 2

💡 רמז 1

FROM ← WHERE ← GROUP BY ← HAVING ← SELECT ← ORDER BY. הכינוי נולד ב־SELECT.

💡 רמז 2

מי רץ אחרי ה־SELECT?

✅ פתרון
SELECT o.id, SUM(oi.quantity * oi.unit_price) AS revenue
FROM orders o JOIN order_items oi ON oi.order_id = o.id
WHERE revenue > 300
GROUP BY o.id;

SELECT o.id, SUM(oi.quantity * oi.unit_price) AS revenue
FROM orders o JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id
HAVING revenue > 300;

SELECT o.id, SUM(oi.quantity * oi.unit_price) AS revenue
FROM orders o JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id
HAVING SUM(oi.quantity * oi.unit_price) > 300
ORDER BY revenue DESC;
ERROR:  column "revenue" does not exist
LINE 3: WHERE revenue > 300
              ^
ERROR:  column "revenue" does not exist
LINE 4: HAVING revenue > 300;
               ^
 id | revenue
----+---------
  4 |  649.00
 11 |  305.00
(2 rows)

רק השלישית. ‏WHERE ו־HAVING רצים לפני ה־SELECT — הכינוי עוד לא קיים, ולכן ב־HAVING חוזרים על הביטוי. ‏ORDER BY רץ אחרי — שם הכינוי מותר. (וגם ב־WHERE, צבירה לא מותרת בכלל — זה תפקיד ה־HAVING.)

⚠️ טעויות נפוצות
  • להעביר את התנאי ל־WHERE עם הביטוי המלא (WHERE SUM(...) > 300) — שגיאה אחרת: צבירה ב־WHERE.

P17-E60 · שתי דנה לוי 🧠 הבנה רמה 2

💡 רמז 1

GROUP BY יוצר קבוצה לכל ערך שונה. כמה ערכים שונים של full_name יש לשתי הלקוחות?

💡 רמז 2

ולמה מותר HAVING c.full_name = ... בשאילתה השנייה? (החריג מהשיעור.)

✅ פתרון
INSERT INTO customers (full_name, email, city, joined_on) VALUES ('Dana Levi', 'dana.l@example.com', 'Eilat', '2026-05-01');
INSERT INTO orders (customer_id, status, created_at) VALUES (9, 'paid', '2026-05-02 10:00:00+03');

SELECT c.full_name, COUNT(*) AS orders
FROM customers c JOIN orders o ON o.customer_id = c.id
GROUP BY c.full_name
HAVING c.full_name = 'Dana Levi';

SELECT c.id, c.full_name, COUNT(*) AS orders
FROM customers c JOIN orders o ON o.customer_id = c.id
GROUP BY c.id
HAVING c.full_name = 'Dana Levi'
ORDER BY c.id;
INSERT 0 1
INSERT 0 1
 full_name | orders
-----------+--------
 Dana Levi |      4
(1 row)

 id | full_name | orders
----+-----------+--------
  1 | Dana Levi |      3
  9 | Dana Levi |      1
(2 rows)

הראשון "מאחד" שתי לקוחות שונות לשורה אחת עם 4 הזמנות — דוח שגוי שנראה סביר. השני מקבץ לפי המזהה: שתי שורות, 3 ו־1. לכן בשיעור כתוב GROUP BY c.id, c.full_name: מקבצים לפי מה שמזהה, ומציגים מה שקריא.

⚠️ טעויות נפוצות
  • "אצלנו אין שמות כפולים" — עד הלקוח ה־200. גם מוצרים, ערים וקטגוריות — לקבץ לפי id כשיש.

P17-E61 · ממוצע הזמנה — או ממוצע שורה? 🧠 הבנה רמה 2

💡 רמז 1

על מה רץ AVG? מה שורה אחת אחרי ה־JOIN?

💡 רמז 2

ממוצע הזמנה = סך ההכנסה ÷ מספר ההזמנות.

✅ פתרון
SELECT ROUND(AVG(oi.quantity * oi.unit_price), 2) AS avg_order
FROM orders o JOIN order_items oi ON oi.order_id = o.id
WHERE o.status <> 'cancelled';

SELECT ROUND(SUM(oi.quantity * oi.unit_price) / COUNT(DISTINCT o.id), 2) AS avg_order
FROM orders o JOIN order_items oi ON oi.order_id = o.id
WHERE o.status <> 'cancelled';
 avg_order
-----------
    122.56
(1 row)

 avg_order
-----------
    233.98
(1 row)

הראשונה היא ממוצע של שורת פריט — לא של הזמנה. השנייה נכונה. דרך שלישית, קריאה יותר: קודם סכום לכל הזמנה (GROUP BY o.id), ואז AVG על התוצאה — עם WITH (שיעור 4; הדוגמה עם order_totals שם).

⚠️ טעויות נפוצות
  • לבדוק "נראה סביר" — 122.56 או 233.98, שניהם נראים כמו סכומי הזמנה. השאלה תמיד: על מה רצה הצבירה?

P17-E62 · סכום של כלום אחרי LEFT JOIN 🧠 הבנה רמה 2

💡 רמז 1

לאבי יש קבוצה של שורה אחת, וכל העמודות של oi בה הן NULL.

💡 רמז 2

COUNT של NULLים = 0. ‏SUM של NULLים = ?

✅ פתרון
SELECT c.full_name,
       COUNT(oi.order_id) AS items,
       SUM(oi.quantity * oi.unit_price) AS spent,
       COALESCE(SUM(oi.quantity * oi.unit_price), 0) AS spent_or_zero
FROM customers c
LEFT JOIN orders o       ON o.customer_id = c.id
LEFT JOIN order_items oi ON oi.order_id = o.id
GROUP BY c.id
ORDER BY c.id;
  full_name   | items | spent  | spent_or_zero
--------------+-------+--------+---------------
 Dana Levi    |     6 | 550.30 |        550.30
 Yossi Cohen  |     3 | 448.50 |        448.50
 Noa Mizrahi  |     2 | 838.00 |        838.00
 Avi Peretz   |     0 |        |             0
 Michal Biton |     5 | 593.70 |        593.70
 Ron Avraham  |     3 | 558.50 |        558.50
 Shira David  |     3 | 233.80 |        233.80
 Omer Shalom  |     0 |        |             0
(8 rows)

COUNT נותן 0, ו־SUM נותן NULL (פרק 16: צבירה על "כלום"). ב־Node זה null — ו־spent.toFixed(2) קורס. לכן COALESCE(SUM(...), 0). (ושים לב: נואה הוציאה גם את ההזמנה המבוטלת — כאן לא סיננו סטטוס.)

⚠️ טעויות נפוצות
  • לסנן מבוטלות עם WHERE o.status <> 'cancelled' — זה זורק גם את אבי ועומר (P17-E46). התנאי צריך להיות ב־ON.

P17-E12 · הכנסה לפי עיר 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

שלוש טבלאות: customers, orders, order_items.

💡 רמז 2

COALESCE(c.city, 'unknown') — גם ב־SELECT וגם ב־GROUP BY (או GROUP BY 1).

✅ פתרון
SELECT COALESCE(c.city, 'unknown') AS city, SUM(oi.quantity * oi.unit_price) AS revenue

P17-E63 · באיזה חודש נכנסת ההזמנה? 🧠 הבנה רמה 2

💡 רמז 1

00:30+02 ב־1 בפברואר — איזו שעה ותאריך זה ב־UTC?

💡 רמז 2

timestamptz שומר רגע בזמן. "באיזה חודש" — תלוי איפה בעולם שואלים.

✅ פתרון
SET timezone = 'Asia/Jerusalem';
SELECT date_trunc('month', timestamptz '2026-02-01 00:30:00+02')::date AS month;
SET timezone = 'UTC';
SELECT date_trunc('month', timestamptz '2026-02-01 00:30:00+02')::date AS month;
SET
   month
------------
 2026-02-01
(1 row)

SET
   month
------------
 2026-01-01
(1 row)

אותו רגע: 31 בינואר 22:30 ב־UTC. בדוח ב־UTC ההזמנה נספרת בינואר, ובדוח בשעון ישראל — בפברואר. הסכום החודשי "זז" לפי השרת שמריץ. התיקון: לקבוע במפורש את אזור הזמן של הדוח —

date_trunc('month', o.created_at AT TIME ZONE 'Asia/Jerusalem')

או SET timezone בחיבור של האפליקציה. (בפרק 19 תראה ש־Prisma מכריח להחליט על זה.)

⚠️ טעויות נפוצות
  • לבדוק את הדוח רק במחשב שלך (בשעון ישראל), ולגלות את ההפרש רק בשרת — בדוח של סוף החודש.

P17-E64 · ‏?min=300 — מה יכול להשתבש? 🧠 הבנה רמה 2

💡 רמז 1

req.query.min הוא תמיד מחרוזת (או undefined). מה נהיה הטקסט של השאילתה בכל מקרה?

💡 רמז 2

פרמטר אפשר לשים בכל מקום שבו יש ערך — גם ב־HAVING. לא במקום שם עמודה או מילת SQL.

✅ פתרון
  1. 300 — עובד. ‏abc — השאילתה היא >= abc: שגיאת SQL ("column abc does not exist") ← 500. בלי min — >= undefined: אותו דבר.
  2. 0 OR true — HAVING תמיד מתקיים: כל הלקוחות. ‏0; DROP TABLE orders — שתי פקודות; ‏pool.query בלי פרמטרים מוכן להריץ כמה פקודות בטקסט אחד. SQL injection.
  3. כן — פרמטר מותר בכל מקום של ערך:
const Query = z.object({ min: z.coerce.number().min(0).default(0) });
const { min } = Query.parse(req.query); // ‏abc ← ZodError ← 400 ב־error middleware
const { rows } = await pool.query(`... GROUP BY c.id HAVING SUM(oi.quantity * oi.unit_price) >= $1 ORDER BY spent DESC`, [min]);

שתי שכבות, לשני דברים שונים: Zod דואג ש־min הוא מספר הגיוני (400 במקום 500), והפרמטר דואג שגם אם משהו יעבור — הוא ערך ולא קוד.

⚠️ טעויות נפוצות
  • "זה רק מספר, לא צריך פרמטר" — המספר הגיע מה־URL, כלומר מכל אחד.

P17-E65 · ממוצע עם 16 ספרות 🧠 הבנה רמה 2

💡 רמז 1

AVG של numeric מחזיר numeric בדיוק גבוה — הרבה ספרות אחרי הנקודה.

💡 רמז 2

למחרוזת אין toFixed.

✅ פתרון
SELECT cat.name AS category, AVG(p.price) AS avg_price, ROUND(AVG(p.price), 2) AS avg_rounded

P17-E28 · JOIN ו־GROUP BY בקוד 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

שני "אינדקסים": new Map(customers.map((c) => [c.id, c])) ואותו דבר להזמנות. ואז לולאה אחת על הפריטים: הזמנה ← לקוח ← עיר.

💡 רמז 2

קיבוץ: Map<string, number> של עיר ← אגורות. ‏Math.round(item.quantity * item.unit_price * 100) לכל פריט. בסוף: [...map].map(([city, agorot]) => ({ city, revenue: agorot / 100 })) ו־sort עם שני קריטריונים (P14-E27).

✅ פתרון
// P17-E28: JOIN ו־GROUP BY בקוד
export type Customer = { id: number; full_name: string; city: string | null };
export type Order = { id: number; customer_id: number; status: string };
export type OrderItem = { order_id: number; quantity: number; unit_price: number };
export type CityRevenue = { city: string; revenue: number };

export function revenueByCity(customers: Customer[], orders: Order[], items: OrderItem[]): CityRevenue[] {
  // "אינדקס" לפי id — כמו JOIN ... ON c.id = o.customer_id, בלי לחפש במערך כל פעם
  const customerById = new Map(customers.map((c) => [c.id, c]));
  const orderById = new Map(orders.map((o) => [o.id, o]));

  const agorotByCity = new Map<string, number>();
  for (const item of items) {
    const order = orderById.get(item.order_id);
    if (!order || order.status === "cancelled") continue;
    const city = customerById.get(order.customer_id)?.city ?? "unknown";
    const agorot = Math.round(item.quantity * item.unit_price * 100);
    agorotByCity.set(city, (agorotByCity.get(city) ?? 0) + agorot);
  }

  return [...agorotByCity]
    .map(([city, agorot]) => ({ city, revenue: agorot / 100 }))
    .sort((a, b) => b.revenue - a.revenue || a.city.localeCompare(b.city));
}

const customers = [
  { id: 1, full_name: "Dana", city: "Haifa" },
  { id: 2, full_name: "Avi", city: null },
];
const orders = [
  { id: 10, customer_id: 1, status: "paid" },
  { id: 11, customer_id: 2, status: "pending" },
  { id: 12, customer_id: 1, status: "cancelled" },
];
const items = [
  { order_id: 10, quantity: 3, unit_price: 19.9 },
  { order_id: 11, quantity: 1, unit_price: 89.9 },
  { order_id: 12, quantity: 5, unit_price: 100 },
];
console.log(revenueByCity(customers, orders, items));
[
  { city: 'unknown', revenue: 89.9 },
  { city: 'Haifa', revenue: 59.7 }
]

כל חלק בשאילתה של P17-E12 קיבל מקבילה בקוד. ‏JOIN ... ON הוא Map.get לפי id. ‏WHERE status <> 'cancelled' הוא continue. ‏GROUP BY עם SUM הוא Map של צוברים. ‏ORDER BY הוא sort. גם PostgreSQL עושה בדיוק את זה (נקרא hash join): בונה טבלת גיבוב מצד אחד, ועובר על הצד השני.

ההבדל: SQL עושה את זה ליד הנתונים, ומחזיר 4 שורות. בקוד היית צריך קודם להעביר את כל ההזמנות והפריטים מהמסד. לכן ברוב המקרים עדיף SQL, וזה תרגיל כדי לראות מה קורה "מתחת למכסה".

numeric ב־PostgreSQL מדויק, ו־number ב־JavaScript לא. לכן הסכום עובר באגורות שלמות (פרק 2), והחילוק ב־100 נעשה רק בסוף.

⚠️ טעויות נפוצות
  • orders.find((o) => o.id === item.order_id) בתוך הלולאה — עובד, אבל איטי מאוד על נתונים גדולים.
  • לצבור בשקלים — ‏59.699999999999996, והבודק משווה למספר המדויק מהמסד.
  • city || "unknown" — עובד כאן, אבל ?? מדויק יותר: רק null/undefined הופכים ל־unknown.

P17-E66 · הכנסה לפי קטגוריה בטווח תאריכים 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

השוואת מחרוזות "2026-03-01" >= "2026-04-01" עובדת כמו השוואת תאריכים — בפורמט הזה.

💡 רמז 2

HAVING SUM(oi.quantity * oi.unit_price) >= $3. ‏SUM של integer מחזיר bigint — שגם הוא מגיע כמחרוזת; ‏Number(...) לשניהם.

✅ פתרון
// P17-E66: הכנסה לפי קטגוריה בטווח תאריכים
export type Db = { query(text: string, values?: unknown[]): Promise<{ rows: any[] }> };
export type CategoryRevenue = { category: string; units: number; revenue: number };

export async function categoryRevenue(client: Db, { from, to, minRevenue = 0 }: { from: string; to: string; minRevenue?: number }): Promise<CategoryRevenue[]> {
  if (from >= to) throw new Error("טווח תאריכים לא תקין");
  const { rows } = await client.query(
    `SELECT cat.name AS category, SUM(oi.quantity) AS units, SUM(oi.quantity * oi.unit_price) AS revenue
     FROM order_items oi
     JOIN orders o       ON o.id = oi.order_id
     JOIN products p     ON p.id = oi.product_id
     JOIN categories cat ON cat.id = p.category_id
     WHERE o.status <> 'cancelled' AND o.created_at >= $1 AND o.created_at < $2
     GROUP BY cat.name
     HAVING SUM(oi.quantity * oi.unit_price) >= $3
     ORDER BY revenue DESC, category`,
    [from, to, minRevenue],
  );
  return rows.map((r) => ({ category: r.category, units: Number(r.units), revenue: Number(r.revenue) }));
}

>= from ו־< to (ולא BETWEEN) — טווח "חצי פתוח": כל מרץ הוא from: "2026-03-01", to: "2026-04-01", בלי לחשוב כמה ימים בחודש ובלי לפספס את 23:59:59.5.

⚠️ טעויות נפוצות
  • created_at <= to — הזמנה ב־1 באפריל בחצות נספרת גם במרץ וגם באפריל.
  • לסנן את minRevenue ב־JS אחרי השאילתה — עובד, אבל מעביר ברשת את כל הקבוצות. זה התפקיד של HAVING.

P17-E67 · דוח עם קיבוץ לבחירה 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1
const KEYS = { city: "COALESCE(c.city, 'unknown')", status: "o.status", month: "date_trunc('month', o.created_at)::date::text" };

— ואז KEYS[by]. ‏by כבר עבר Zod, אז הוא בטוח אחד מהשלושה.

💡 רמז 2

GROUP BY 1 — "לפי העמודה הראשונה ב־SELECT" — חוסך לכתוב את הביטוי פעמיים. ‏HAVING COUNT(*) >= $1.

✅ פתרון
// P17-E67: דוח עם קיבוץ לבחירה
import { z } from "zod";

export const ReportQuery = z.object({
  by: z.enum(["city", "status", "month"]),
  minOrders: z.coerce.number().int().min(1).default(1),
});

const KEYS: Record<z.infer<typeof ReportQuery>["by"], string> = {
  city: "COALESCE(c.city, 'unknown')",
  status: "o.status",
  month: "date_trunc('month', o.created_at)::date::text",
};

export function buildReport(query: unknown): { text: string; values: unknown[] } {
  const { by, minOrders } = ReportQuery.parse(query);
  const text = `SELECT ${KEYS[by]} AS key, COUNT(*) AS orders
FROM orders o
JOIN customers c ON c.id = o.customer_id
GROUP BY 1
HAVING COUNT(*) >= $1
ORDER BY orders DESC, key`;
  return { text, values: [minOrders] };
}

שני סוגים של קלט, שני כלים: by בוחר קוד — אז הוא חייב להגיע מרשימה סגורה שכתבת (Zod מבטיח שהוא אחד מהשלושה, והטקסט מגיע מ־KEYS, לא מהמשתמש). ‏minOrders הוא ערך — אז הוא פרמטר.

⚠️ טעויות נפוצות
  • GROUP BY ${query.by} — גם עם "בדיקה" שהערך לא ריק: ?by=1; DROP TABLE orders.
  • z.number() בלי coerce — מה־URL מגיע "2" (מחרוזת), ו־Zod דוחה.
