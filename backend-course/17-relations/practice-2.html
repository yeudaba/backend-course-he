P17-E46 · התנאי ב־ON או ב־WHERE?

🧠 הבנהרמה 2⏱ 10 דק׳ידע נדרש: שיעור 2

"כל הלקוחות, ולידם ההזמנות ששולמו (paid), אם יש". שתי גרסאות — ההבדל היחיד הוא איפה כתוב o.status = 'paid'. כמה שורות תחזיר כל אחת, ומי מהלקוחות ייעלם?

SELECT c.full_name, o.id AS paid_order
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'paid'
ORDER BY c.id, o.id;

SELECT c.full_name, o.id AS paid_order
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'paid'
ORDER BY c.id, o.id;

P17-E48 · LEFT ואחריו JOIN

🧠 הבנהרמה 2⏱ 10 דק׳ידע נדרש: שיעור 2

"כל הלקוחות, ולידם המוצרים שהזמינו (אם הזמינו)". השאילתה מסתכלת על שלושה לקוחות: אבי ועומר (בלי הזמנות) ושירה (הזמנה אחת). כמה שורות יחזרו, ולמי? למה?

SELECT c.full_name, o.id AS order_id, oi.product_id
FROM customers c
LEFT JOIN orders o       ON o.customer_id = c.id
JOIN order_items oi      ON oi.order_id = o.id
WHERE c.id IN (4, 7, 8)
ORDER BY c.id, oi.product_id;

P17-E49 · איזה JOIN מתאים?

🧠 הבנהרמה 1⏱ 10 דק׳ידע נדרש: שיעור 2

  1. רשימת ההזמנות, עם שם הלקוח ליד כל אחת.

  4. פריטי ההזמנה, עם שם המוצר ושם הקטגוריה.
  5. כל הלקוחות, עם העיר שלהם ומספר ההזמנה האחרונה (אם יש).

P17-E52 · ‏SELECT * עם JOIN, ו־Node

🧠 הבנהרמה 2⏱ 10 דק׳ידע נדרש: פרק 7, פרק 16, שיעור 2

pg הופך כל שורה לאובייקט: שם העמודה ← הערך. מה יחזיר SELECT * על JOIN של הזמנות ולקוחות — ומה יקרה לאובייקט? הקוד השני מדמה בדיוק את מה ש־pg עושה עם השורה הראשונה.

SELECT * FROM orders o JOIN customers c ON c.id = o.customer_id WHERE o.id = 6;
const columns = ["id", "customer_id", "status", "created_at", "id", "full_name", "email", "city", "joined_on"];
const values = [6, 2, "paid", "2026-03-02", 2, "Yossi Cohen", "yossi@example.com", "Haifa", "2025-12-15"];
const row = {};
columns.forEach((name, i) => (row[name] = values[i]));
console.log(row);
console.log(`order #${row.id}`);

🔗 איך זה מתחבר: אובייקטים מפרק 7 — מפתח מופיע פעם אחת, והשמה שנייה דורסת. ‏pg מפרק 16 — והשיעור: JOIN מביא עמודות עם אותו שם משתי טבלאות.

P17-E53 · הטיפוס של שורה מ־LEFT JOIN

🧠 הבנהרמה 2⏱ 10 דק׳ידע נדרש: פרק 11, שיעור 2

שורה מ־customers c LEFT JOIN orders o עם o.id AS order_id. מתכנתת הגדירה את הטיפוס כך, והקוד עבר בלי שגיאות. מה הבעיה? מה יקרה כשהקוד ירוץ על אבי? ואיך תשנה את הטיפוס — ומה TypeScript יגיד אז על השורה האחרונה?

type Row = { full_name: string; order_id: number };
const rows: Row[] = await getCustomersWithOrders(); // LEFT JOIN

🔗 איך זה מתחבר: null בטיפוסים ו־strict מפרק 11 — והשיעור: ב־LEFT JOIN כל עמודה מהטבלה הימנית יכולה להיות NULL.

P17-E55 · משורות שטוחות לאובייקטים 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 20 דק׳ידע נדרש: פרק 2, פרק 7, פרק 11, שיעור 2

תוצאה של LEFT JOIN בין הזמנות, לקוחות ופריטים מגיעה כשורות שטוחות. בקובץ 17-relations/starter/P17-E55.ts כתוב וייצא:

export type FlatRow = { order_id: number; full_name: string; status: string; product: string | null; quantity: number | null; unit_price: number | null };
export type Item = { product: string; quantity: number; unitPrice: number; lineTotal: number };
export type OrderView = { id: number; customer: string; status: string; items: Item[]; total: number };
export function nestOrders(rows: FlatRow[]): OrderView[]
  • אובייקט אחד לכל order_id, לפי סדר ההופעה הראשונה. הפריטים — לפי הסדר בשורות.

P17-E57 · ‏leftJoin גנרי 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 20 דק׳ידע נדרש: פרק 6, פרק 11, שיעור 2

JOIN בזיכרון, לכל טיפוס. בקובץ 17-relations/starter/P17-E57.ts כתוב וייצא:

export function innerJoin<L, R>(left: L[], right: R[], on: (l: L, r: R) => boolean): { left: L; right: R }[]
export function leftJoin<L, R>(left: L[], right: R[], on: (l: L, r: R) => boolean): { left: L; right: R | null }[]
  • בדיוק כמו ב־SQL: לכל שורה משמאל — זוג עם כל שורה מימין שמתאימה (לפי סדר המערכים). ב־leftJoin, שורה משמאל בלי אף התאמה ← זוג אחד עם right: null.
  • הטיפוסים חשובים: ב־leftJoin הבודק מוודא ש־TypeScript לא נותן לגשת ל־right.x בלי בדיקת null.

📄 כותבים בקובץ 17-relations/starter/P17-E57.ts (יש בו רק הערה), ובודקים:

% npm run check P17-E57

🔗 איך זה מתחבר: לולאות ומערכים מפרק 6, generics ו־| null מפרק 11 — והשיעור: מה בדיוק INNER ו־LEFT JOIN עושים, שורה אחרי שורה.
