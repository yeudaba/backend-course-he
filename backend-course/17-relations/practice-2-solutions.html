P17-E02 · כמה שורות? 🧠 הבנה רמה 1

💡 רמז 1

INNER: שורה לכל זוג מתאים. LEFT: + שורה ל"שמאלי בלי התאמה".

💡 רמז 2

ב־3, הטבלה השמאלית היא orders. יש הזמנה בלי לקוח?

✅ פתרון
SELECT
  (SELECT COUNT(*) FROM customers c JOIN orders o ON o.customer_id = c.id) AS q1,
  (SELECT COUNT(*) FROM customers c LEFT JOIN orders o ON o.customer_id = c.id) AS q2,
  (SELECT COUNT(*) FROM orders o LEFT JOIN customers c ON c.id = o.customer_id) AS q3,
  (SELECT COUNT(*) FROM customers c JOIN orders o ON true) AS q4;
 q1 | q2 | q3 | q4
----+----+----+----
 12 | 14 | 12 | 96
(1 row)

1: 12 (כל הזמנה מתאימה ללקוח אחד). 2: 12 + 2 לקוחות בלי הזמנות. 3: 12 — אין הזמנה בלי לקוח (ה־FK דואג). 4: 8 × 12 — כל צירוף; זה מה שקורה כששוכחים את תנאי ה־ON.

⚠️ טעויות נפוצות
  • לחשוב ש־LEFT JOIN "מוסיף שורות" תמיד — רק לשורות שאין להן התאמה.

P17-E03 · למה הסכום כפול? 🧠 הבנה רמה 1

💡 רמז 1

כמה שורות יש להזמנה הזו אחרי שני ה־JOIN־ים?

💡 רמז 2

לסכם כל צד בנפרד, ורק אז לחבר.

✅ פתרון

אחרי שני ה־JOIN־ים יש 3 × 2 = 6 שורות להזמנה (כל פריט עם כל תשלום). total יוצא פי 2 (כל פריט נספר פעמיים), ו־paid פי 3. זה ה־"fan-out" — אחד הבאגים הנפוצים בדוחות.

WITH items AS (SELECT order_id, SUM(quantity * unit_price) AS total FROM order_items GROUP BY order_id),
     pays  AS (SELECT order_id, SUM(amount) AS paid FROM payments GROUP BY order_id)
SELECT o.id, i.total, COALESCE(p.paid, 0) AS paid
FROM orders o
JOIN items i     ON i.order_id = o.id
LEFT JOIN pays p ON p.order_id = o.id;
⚠️ טעויות נפוצות
  • "לתקן" עם SUM(DISTINCT ...) — שני פריטים באותו מחיר ייספרו כאחד.

P17-E46 · התנאי ב־ON או ב־WHERE? 🧠 הבנה רמה 2

💡 רמז 1

ב־LEFT JOIN, תנאי ב־ON קובע איזו הזמנה מתאימה — לקוח בלי התאמה עדיין נשאר (עם NULL). WHERE רץ אחרי ה־JOIN, על השורות שכבר נוצרו.

💡 רמז 2

מה התוצאה של NULL = 'paid'?

✅ פתרון
SELECT c.full_name, o.id AS paid_order
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'paid'
ORDER BY c.id, o.id;

SELECT c.full_name, o.id AS paid_order
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'paid'
ORDER BY c.id, o.id;
  full_name   | paid_order
--------------+------------
 Dana Levi    |          8
 Yossi Cohen  |          6
 Noa Mizrahi  |         10
 Avi Peretz   |
 Michal Biton |
 Ron Avraham  |
 Shira David  |
 Omer Shalom  |
(8 rows)

  full_name  | paid_order
-------------+------------
 Dana Levi   |          8
 Yossi Cohen |          6
 Noa Mizrahi |         10
(3 rows)

הראשונה: כל 8 הלקוחות. למי שיש הזמנה ששולמה — מספר ההזמנה; לכל השאר — שורה אחת עם NULL. השנייה: רק 3 שורות. ה־LEFT JOIN יצר שורות לכל ההזמנות (ושורות NULL למי שאין לו), ואז ה־WHERE השאיר רק את paid — ולשורות ה־NULL NULL = 'paid' אינו true. ה־LEFT JOIN הפך ל־INNER בשקט.

⚠️ טעויות נפוצות
  • "לתקן" את השנייה עם WHERE o.status = 'paid' OR o.id IS NULL — עדיין מאבד את מי שיש לו הזמנות, אבל אף אחת מהן לא שולמה (למשל Michal).

P17-E47 · איזה id? 🧠 הבנה רמה 1

💡 רמז 1

בכמה טבלאות יש עמודה בשם id? ובשם name?

💡 רמז 2

הכינויים p ו־c קיימים בדיוק בשביל זה.

✅ פתרון
SELECT id, name, name AS category
FROM products p
JOIN categories c ON c.id = p.category_id;
ERROR:  column reference "id" is ambiguous
LINE 1: SELECT id, name, name AS category
               ^
SELECT p.id, p.name, c.name AS category
FROM products p
JOIN categories c ON c.id = p.category_id
WHERE p.id <= 3
ORDER BY p.id;

----+--------------------+----------

  2 | Colombia Beans 1kg | beans

(3 rows)

אחרי JOIN, כל עמודה ששמה מופיע ביותר מטבלה אחת צריכה כינוי. המסד לא מנחש — וזה טוב: ניחוש היה מחזיר את ה־id של הקטגוריה בתור "id של המוצר". והרגל טוב: לתת כינוי לכל עמודה ב־JOIN, גם כשהיא לא עמומה — היום. מחר מישהו יוסיף עמודה עם אותו שם לטבלה השנייה, והשאילתה תישבר.

⚠️ טעויות נפוצות
  • לפתור עם SELECT * — מקבלים שתי עמודות id ושתי name, וב־Node אחת מהן דורסת את השנייה (P17-E52).

P17-E48 · LEFT ואחריו JOIN 🧠 הבנה רמה 2

💡 רמז 1

JOIN רץ משמאל לימין: קודם customers LEFT JOIN orders — ועל התוצאה הזו רץ ה־JOIN הבא.

💡 רמז 2

לאבי, אחרי ה־LEFT JOIN, יש שורה עם o.id = NULL. איזה פריט מקיים oi.order_id = NULL?

✅ פתרון
SELECT c.full_name, o.id AS order_id, oi.product_id
FROM customers c
LEFT JOIN orders o       ON o.customer_id = c.id
JOIN order_items oi      ON oi.order_id = o.id
WHERE c.id IN (4, 7, 8)
ORDER BY c.id, oi.product_id;
  full_name  | order_id | product_id
-------------+----------+------------
 Shira David |        9 |          1
 Shira David |        9 |          6
 Shira David |        9 |          9
(3 rows)

רק שירה. ה־LEFT JOIN השאיר את אבי ועומר עם NULL — וה־JOIN (INNER) הבא זרק אותם, כי אין פריט שמתאים ל־NULL. הכלל: אחרי LEFT JOIN, כל JOIN לטבלה שתלויה בצד הימני צריך להיות גם הוא LEFT:

SELECT c.full_name, o.id AS order_id, oi.product_id
FROM customers c
LEFT JOIN orders o       ON o.customer_id = c.id
LEFT JOIN order_items oi ON oi.order_id = o.id
WHERE c.id IN (4, 7, 8)
ORDER BY c.id, oi.product_id;
  full_name  | order_id | product_id
-------------+----------+------------
 Avi Peretz  |          |
 Shira David |        9 |          1
 Shira David |        9 |          6
 Shira David |        9 |          9
 Omer Shalom |          |
(5 rows)
⚠️ טעויות נפוצות
  • לבדוק רק "האם התוצאה נראית סבירה" — היא נראית מצוין, פשוט חסרים בה שני לקוחות. בדיקה טובה: כמה שורות של לקוחות בלי הזמנות חזרו?

P17-E49 · איזה JOIN מתאים? 🧠 הבנה רמה 1

💡 רמז 1

שאל: "האם מותר לשורה מהטבלה הראשית להיעלם אם אין לה התאמה?" אם לא — LEFT.

💡 רמז 2

"שאין להם" = LEFT JOIN + WHERE <הימנית>.id IS NULL.

✅ פתרון
  1. FROM orders JOIN customers — לכל הזמנה יש לקוח (ה־FK מבטיח), אז INNER לא מאבד כלום.
  2. FROM products LEFT JOIN order_items — מוצר שלא נמכר צריך להופיע (עם 0 — נלמד בשיעור 3 איך לספור).
  3. FROM categories LEFT JOIN products ... WHERE p.id IS NULL.
  4. FROM order_items JOIN products JOIN categories — לכל פריט יש מוצר ולכל מוצר קטגוריה (שני FK עם NOT NULL).
  5. FROM customers LEFT JOIN orders — לקוח בלי הזמנות צריך להישאר.

שים לב ל־1 ו־4: INNER בטוח כשה־FK הוא NOT NULL — אין מצב שאין התאמה. כשה־FK יכול להיות NULL (כמו customer_id בפניות של P17-E39) — INNER יעלים את השורות עם NULL.

⚠️ טעויות נפוצות
  • LEFT JOIN "ליתר ביטחון" בכל מקום — לא מזיק לתוצאה כשה־FK חובה, אבל מסתיר את הכוונה, ומבלבל את מי שיקרא: "אה, יש הזמנות בלי לקוח?"

P17-E51 · מי קנה ספלים? 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

ארבע טבלאות: order_items (הכמות) ← products (השם, לסינון) ← orders (התאריך) ← customers (השם).

💡 רמז 2

תאריך מ־timestamptz: ‏o.created_at::date.

✅ פתרון
SELECT o.id AS order_id, c.full_name, o.created_at::date AS ordered_on, oi.quantity
FROM order_items oi
JOIN products p  ON p.id = oi.product_id
JOIN orders o    ON o.id = oi.order_id
JOIN customers c ON c.id = o.customer_id
WHERE p.name = 'Ceramic Mug'
ORDER BY o.id;
 order_id |  full_name   | ordered_on | quantity
----------+--------------+------------+----------
        3 | Dana Levi    | 2026-02-03 |        2
        8 | Dana Levi    | 2026-03-28 |        1
       11 | Michal Biton | 2026-05-01 |        4
(3 rows)

שורה אחת בתוצאה = פריט אחד (הספלים בהזמנה אחת). מתחילים מהטבלה שה"גרעין" שלה הוא מה שרוצים לראות, ומוסיפים JOIN לכל טבלה שמביאה עמודה.

⚠️ טעויות נפוצות
  • WHERE oi.product_id = 10 — נכון היום, אבל המשימה ביקשה לפי שם; בנתונים אחרים (או אחרי טעינה מחדש) המספר משתנה.

P17-E53 · הטיפוס של שורה מ־LEFT JOIN 🧠 הבנה רמה 2

💡 רמז 1

TypeScript לא יודע מה המסד מחזיר. הוא מאמין לטיפוס שכתבת.

💡 רמז 2

order_id: number | null — ואז TypeScript דורש לטפל ב־null.

✅ פתרון

הטיפוס משקר: לאבי ולעומר order_id הוא null, ו־null.toString() קורס בזמן ריצה (TypeError: Cannot read properties of null) — בדיוק מה ש־TypeScript היה אמור למנוע. עם הטיפוס הנכון:

// P17-E55: משורות שטוחות לאובייקטים
export type FlatRow = { order_id: number; full_name: string; status: string; product: string | null; quantity: number | null; unit_price: number | null };
export type Item = { product: string; quantity: number; unitPrice: number; lineTotal: number };
export type OrderView = { id: number; customer: string; status: string; items: Item[]; total: number };

export function nestOrders(rows: FlatRow[]): OrderView[] {
  const byId = new Map<number, OrderView>();
  const cents = new Map<number, number>();
  for (const r of rows) {
    let order = byId.get(r.order_id);
    if (!order) {
      order = { id: r.order_id, customer: r.full_name, status: r.status, items: [], total: 0 };
      byId.set(r.order_id, order);
      cents.set(r.order_id, 0);
    }
    if (r.product === null || r.quantity === null || r.unit_price === null) continue;
    const line = Math.round(r.unit_price * 100) * r.quantity;
    order.items.push({ product: r.product, quantity: r.quantity, unitPrice: r.unit_price, lineTotal: line / 100 });
    cents.set(r.order_id, cents.get(r.order_id)! + line);
  }
  for (const order of byId.values()) order.total = cents.get(order.id)! / 100;
  return [...byId.values()];
}


ה־Map עושה את ה"GROUP BY" בקוד. בדיקת ה־null היא בדיוק המקרה של P17-E53 — ובזכות הטיפוס, TypeScript לא היה נותן לך לשכוח אותה.




    
⚠️ טעויות נפוצות


  • order.total += r.quantity * r.unit_price — שגיאות עיגול מצטברות (0.1 + 0.2).
  • להוסיף פריט { product: null, ... } להזמנה בלי פריטים.

// P17-E56: פרטי הזמנה מהמסד, בשאילתה אחת
export type Db = { query(text: string, values?: unknown[]): Promise<{ rows: any[] }> };
export type OrderDetails = { id: number; status: string; customer: { id: number; name: string };
  items: { product: string; quantity: number; unitPrice: number }[] };

export async function getOrderDetails(client: Db, orderId: number): Promise<OrderDetails | null> {
  const { rows } = await client.query(
    `SELECT o.id AS order_id, o.status, c.id AS customer_id, c.full_name,
            p.name AS product, oi.quantity, oi.unit_price
     FROM orders o
     JOIN customers c        ON c.id = o.customer_id
     LEFT JOIN order_items oi ON oi.order_id = o.id
     LEFT JOIN products p     ON p.id = oi.product_id
     WHERE o.id = $1
     ORDER BY p.name`,
    [orderId],
  );
  if (rows.length === 0) return null;
  const first = rows[0];
  return {
    id: first.order_id,
    status: first.status,
    customer: { id: first.customer_id, name: first.full_name },
    items: rows
      .filter((r) => r.product !== null)
      .map((r) => ({ product: r.product, quantity: r.quantity, unitPrice: Number(r.unit_price) })),
  };
}

// P17-E57: leftJoin גנרי
export function innerJoin<L, R>(left: L[], right: R[], on: (l: L, r: R) => boolean): { left: L; right: R }[] {
  const out: { left: L; right: R }[] = [];
  for (const l of left) for (const r of right) if (on(l, r)) out.push({ left: l, right: r });
  return out;
}

export function leftJoin<L, R>(left: L[], right: R[], on: (l: L, r: R) => boolean): { left: L; right: R | null }[] {
  const out: { left: L; right: R | null }[] = [];
  for (const l of left) {
    const matches = right.filter((r) => on(l, r));
    if (matches.length === 0) out.push({ left: l, right: null });
    else for (const r of matches) out.push({ left: l, right: r });
  }
  return out;
}
