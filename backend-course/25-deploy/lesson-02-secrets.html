שיעור 2 — הגדרות וסודות

⏱ ~40 דקות

🎯 בשיעור הזה
  • הגדרות מחוץ לקוד — ולמה.
  • איפה גר כל ערך: קוד, .env, GitHub Secrets ו־Variables, הפלטפורמה.
  • להיכשל מהר: שרת עם הגדרה שגויה לא עולה.
  • חיבור מאובטח למסד בענן — ושני גילויים אמיתיים בדרך.

1. אותו קוד, הגדרות אחרות

אותו image רץ אצלך, ב־CI ובפרודקשן. מה שמשתנה — הגדרות: לאיזה מסד להתחבר, איזה סוד חותם את הטוקנים, מאיזה דומיין מותר CORS. לכן הן במשתני סביבה, לא בקוד (אחד מעקרונות The Twelve-Factor App). וסוד הוא הגדרה שמי שמחזיק אותה יכול להזיק: סיסמת מסד, JWT_SECRET, כתובת deploy hook.

איפהמה שםמי רואה
בקודברירות מחדל שאינן סוד (ACCESS_TOKEN_TTL_SECONDS=900), ערכים מזויפים לבדיקותכל מי שרואה את ה־repo — ובתיק עבודות: כל העולם
.env מקומיההגדרות שלך לפיתוח. ב־.gitignore; .env.example — כן ב־Git, בלי ערכים אמיתייםרק אתה
GitHub Secretsמה שה־CI צריך ושאסור שיופיע: DATABASE_URL של הפרודקשן (ל־migrations), deploy hookאף אחד — גם לא אתה, אחרי השמירה. בלוגים מוחלף ב־***
GitHub Variablesהגדרות גלויות של ה־CI: PRODUCTION_URLמי שיש לו גישה להגדרות ה־repo
הפלטפורמה (Render)מה שהשרת צריך בזמן ריצה: DATABASE_URL, JWT_SECRET, CORS_ORIGINSרק בחשבון שלך

ב־workflow: ${{ secrets.DATABASE_URL }} ו־${{ vars.PRODUCTION_URL }}. שלושה כללים:

  • הסוד רק איפה שצריך אותו. ב־env של הצעד שמשתמש בו — לא ברמת ה־workflow, ובוודאי לא ב־job של הבדיקות. ב־E20 תראה workflow שבו DATABASE_URL של הפרודקשן "דלף" לבדיקות, ו־migrate reset מחק את המשתמשים.
  • דרך env, לא בתוך הסקריפט. run: curl "${{ secrets.HOOK }}" מכניס את הערך לטקסט של הסקריפט לפני שהוא רץ. env: { HOOK: … } ו־run: curl "$HOOK" — משתנה רגיל.
  • pull requests מ־forks לא מקבלים secrets — כדי שזר לא יוכל לשלוח PR שמדפיס אותם. לכן deploy רץ רק ב־push ל־main.

ו־environment: production ב־job של ה־deploy: ב־GitHub אפשר להגדיר ל־environment כללים — סודות משלו, ואפילו "צריך אישור של מישהו לפני שה־job רץ".

⚠️ סוד שנכנס ל־Git

מחיקה ב־commit הבא לא עוזרת — ההיסטוריה זוכרת, ובוטים סורקים את GitHub בחיפוש אחרי מפתחות תוך דקות. מה שעושים: מחליפים את הסוד (rotate): סיסמה חדשה למסד, JWT_SECRET חדש (כל המשתמשים יתחברו מחדש), deploy hook חדש. ורק אחר כך — לנקות.

2. להיכשל מהר

בפרק 20 הוספנו בדיקה עם zod ל־JWT_SECRET. בשלב ח׳ נוסף loadServerConfig — ההגדרות של השרת עצמו, עם כללים מחמירים יותר בפרודקשן:

src/server-config.ts 
const schema = z
  .object({
    NODE_ENV: z.enum(["development", "test", "production"]).default("development"),
    PORT: z.coerce.number().int().min(1).max(65535).default(3000),
    CORS_ORIGINS: z.string().optional(),
    TRUST_PROXY: z.coerce.number().int().min(0).max(5).default(0),
    DATABASE_URL: z.string().optional(),
  })
  .superRefine((e, ctx) => {
    if (e.NODE_ENV !== "production") return;
    if (!e.DATABASE_URL) ctx.addIssue({ code: "custom", path: ["DATABASE_URL"], message: "חובה בפרודקשן" });
    if (!e.CORS_ORIGINS) ctx.addIssue({ code: "custom", path: ["CORS_ORIGINS"], message: "חובה בפרודקשן — רשימת כתובות מופרדת בפסיקים" });
    for (const origin of e.CORS_ORIGINS?.split(",") ?? []) {
      if (!/^https:\/\/[^/*]+$/.test(origin.trim())) {
        ctx.addIssue({ code: "custom", path: ["CORS_ORIGINS"], message: `בפרודקשן רק https ובלי * או נתיב: ${origin.trim()}` });
      }
    }
  });

למה זה חשוב דווקא בפריסה? כי בפלטפורמה, שרת שלא עולה = deploy שנכשל — והגרסה הקודמת ממשיכה לרוץ. שרת שעולה עם הגדרה שגויה (CORS פתוח, סוד ברירת מחדל) — "עובד", ונכשל רק מול משתמשים, או גרוע מזה: לא נכשל בכלל, ופשוט לא מאובטח. ובפרודקשן הכללים מחמירים יותר מבפיתוח: נוחות לך, ביטחון למשתמשים (E06).

שים לב: ה־image מגדיר NODE_ENV=production (פרק 23). לכן ב־compose.yaml המקומי נוסף NODE_ENV: development — אחרת השרת מסרב לעלות עם CORS ל־http://localhost:5500. בדיוק כמו שצריך.

3. חיבור למסד בענן: TLS

מסד בענן מחובר דרך האינטרנט, ולכן החיבור מוצפן (TLS). Neon נותן כתובת עם ?sslmode=require. בדקנו איך שני הצדדים של הפרויקט מבינים אותה, מול PostgreSQL מקומי בלי TLS (פלטים אמיתיים, מקוצרים):

ה־driver בזמן ריצה (pg), עם sslmode=require:

Warning: SECURITY WARNING: The SSL modes 'prefer', 'require', and 'verify-ca' are treated as aliases for 'verify-full'.
In the next major version (pg-connection-string v3.0.0 and pg v9.0.0), these modes will adopt standard libpq semantics…
error: The server does not support SSL connections

Prisma CLI (migrate), עם sslmode=require — דורש TLS ונכשל, כמו שצריך. אבל עם sslmode=verify-full (שה־warning הציע) — התחבר בלי TLS בכלל, בלי אזהרה: ה־CLI לא מכיר את הערך הזה ומתעלם ממנו.

% DATABASE_URL="…?sslmode=require" npx prisma migrate status
Error: P1011: Error opening a TLS connection: error performing TLS handshake: server does not support TLS
% DATABASE_URL="…?sslmode=verify-full" npx prisma migrate status
To apply migrations in production run prisma migrate deploy.

מסקנה: הכתובת נשארת sslmode=require — מה ש־Neon נותן, ומה שה־CLI מבין. ובזמן ריצה, PrismaService מעביר ל־pg את ההגדרה במפורש — TLS עם בדיקת תעודה, בלי אזהרה:

src/prisma/pg-options.ts 
export function pgConnectionOptions(url: string): { connectionString: string; ssl?: { rejectUnauthorized: boolean } } {
  if (!url) return { connectionString: url };
  const u = new URL(url);
  const mode = u.searchParams.get("sslmode");
  u.searchParams.delete("sslmode");
  u.searchParams.delete("channel_binding");
  if (!mode || mode === "disable") return { connectionString: u.toString() };
  return { connectionString: u.toString(), ssl: { rejectUnauthorized: true } };
}

הלקח הרחב יותר: הגדרת אבטחה שלא נבדקה — לא קיימת. "הוספתי sslmode=verify-full, אז זה מאובטח" היה נכון ל־driver אחד ושקרי לשני.
