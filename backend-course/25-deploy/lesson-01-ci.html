🎯 בשיעור הזה
  • CI: למה "אצלי זה עובר" לא מספיק — עם דוגמה אמיתית מהפרויקט שלך.
  • GitHub Actions: workflow, job, step, runner ו־action.
  • שירות PostgreSQL בתוך ה־CI, cache, ו־needs.
  • לקרוא ריצה שנכשלה — ולתקן.

1. "אצלי זה עובר"

בזמן כתיבת הפרק, העלינו את פרויקט 2 (שלב ח׳) ל־GitHub, עם ה־workflow של השיעור הזה. כל הבדיקות עברו אצלנו. הריצה הראשונה ב־GitHub נכשלה — בצעד npm run typecheck (פלט אמיתי, מקוצר):

##[error]src/auth/auth.schema.spec.ts(3,1): error TS2593: Cannot find name 'describe'. Do you need to install
  type definitions for a test runner? Try `npm i --save-dev @types/jest` …
##[error]prisma/seed.ts(16,1): error TS1309: The current file is a CommonJS module and cannot use 'await' at the top level.
##[error]Process completed with exit code 2.

190 שגיאות. איך זה עבר "אצלנו"? כי בדקנו טיפוסים רק עם tsconfig.build.json (שלא כולל בדיקות ו־seed), ואף אחד לא הריץ את npm run typecheck המלא — עוד מפרק 22. ה־tsconfig.json הגביל את הטיפוסים ל־"types": ["node"], בלי Jest; ו־seed.ts משתמש ב־await ברמה העליונה בפרויקט CommonJS. התיקון: "types": ["node", "jest"], ו־seed.ts ← seed.mts (קובץ ESM). והפתרונות של שלבים ד׳–ז׳ תוקנו בהתאם.

זה בדיוק התפקיד של CI (Continuous Integration): שרת שמריץ את כל הבדיקות על כל push ו־pull request, בסביבה נקייה — בלי הקבצים שלא עשית להם commit, בלי node_modules ישן, ובלי "את זה אני אף פעם לא מריץ".

2. האנטומיה של workflow

מושגמה
workflowקובץ YAML ב־.github/workflows/. on: — מתי הוא רץ
jobרצף צעדים על מכונה אחת. jobs רצים במקביל, אלא אם יש needs
runnerהמכונה: ubuntu-latest — VM חדש ונקי לכל job, שנמחק בסוף
steprun: — פקודת shell; uses: — action מוכן
actionצעד לשימוש חוזר: actions/checkout@v5 מוריד את הקוד, actions/setup-node@v5 מתקין Node

ה־job של הבדיקות בפרויקט:

.github/workflows/ci.yml 
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    services:
      postgres:
        image: postgres:18-alpine
        env:
          POSTGRES_USER: tasks
          POSTGRES_PASSWORD: tasks
          POSTGRES_DB: tasks_test
        ports:
          - 5432:5432
        options: >-
          --health-cmd "pg_isready -U tasks -d tasks_test"
          --health-interval 2s
          --health-timeout 3s
          --health-retries 30
    env:
      DATABASE_URL: postgresql://tasks:tasks@localhost:5432/tasks_test
      DATABASE_URL_TEST: postgresql://tasks:tasks@localhost:5432/tasks_test
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npx prisma generate
      - run: npm run typecheck
      - run: npm test
      - run: npx prisma migrate deploy
      - run: npm run test:int
      - run: npm run build
  • services — PostgreSQL אמיתי, בקונטיינר ליד ה־job. הצעדים רצים על ה־runner עצמו, ולכן מגיעים אליו ב־localhost:5432. ה־--health-cmd גורם ל־GitHub לחכות שהמסד מוכן לפני הצעד הראשון. בלוג: postgres service is healthy.
  • cache: npm — שומר את ה־cache של npm בין ריצות. npm ci — בדיוק מה שב־lock (פרק 23).
  • permissions: contents: read — ל־GITHUB_TOKEN שה־workflow מקבל: רק לקרוא את הקוד. ברירת המחדל רחבה יותר; עדיף מינימום (שיעור 2).
  • timeout-minutes — ברירת המחדל היא 6 שעות. בדיקה תקועה תבזבז את כולן.

ואחרי התיקון, הריצה ירוקה. זמני הצעדים בריצה האמיתית:

צעדזמן
הקמת שירות PostgreSQL7 שניות
npm ci (653 חבילות)7 שניות
typecheck · npm test (51 בדיקות)2 + 2 שניות
migrate deploy · test:int (9 בדיקות)1 + 2 שניות
build2 שניות
job של docker (build + בדיקה של ה־image), במקביל35 שניות

כל ה־workflow — 35 שניות. על כל push, על כל pull request, בלי שמישהו צריך לזכור.

3. YAML: שלוש מלכודות

YAML נראה פשוט, אבל הוא מנחש טיפוסים. מה js-yaml (YAML 1.2) עושה עם כמה ערכים תמימים:

import { load } from "js-yaml";
console.log(JSON.stringify(load("version: 1.10\nport: 08\nnorway: NO\non: [push]")));
{"version":1.1,"port":8,"norway":"NO","on":["push"]}

1.10 הפך ל־1.1 — ו־python-version: 3.10 מתקין Python 3.1. כשהערך הוא "מחרוזת שנראית כמו מספר" — מרכאות: "3.10". (ב־YAML 1.1, שחלק מהכלים עוד משתמשים בו, גם NO הופך ל־false, ו־on ל־true.) ושלישית — הזחה: רווחים בלבד, ושינוי הזחה משנה את המבנה. התוסף של GitHub Actions ל־VS Code מסמן את רוב הטעויות בזמן הכתיבה.

4. כשה־CI אדום

  1. בלשונית Actions ב־GitHub (או ליד ה־commit: ✗ אדום ← Details) — הצעד שנכשל, פתוח, עם הלוג.
  2. שגיאות מסומנות ##[error]. הראשונה היא כמעט תמיד הסיבה; השאר — תוצאה שלה.
  3. משחזרים אצלך בדיוק אותה פקודה (npm run typecheck, לא "משהו דומה"). אם אצלך עובר — מה שונה? קובץ שלא ב־Git (git status), גרסה של Node, משתנה סביבה, אזור זמן.
  4. מתקנים, push — וה־CI רץ שוב לבד.
💡 branch protection

ב־Settings ← Branches של ה־repo אפשר לדרוש שה־CI ירוק לפני merge ל־main. בצוות — זה הסטנדרט. בפרויקט אישי — הרגל טוב, והמראיין רואה אותו.
