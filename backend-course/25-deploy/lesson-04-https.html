שיעור 4 — HTTPS, proxy ובריאות בפרודקשן

⏱ ~45 דקות

🎯 בשיעור הזה

  • reverse proxy — עם ניסוי אמיתי: Caddy לפני הפרויקט שלך.

1. HTTPS ו־TLS termination

HTTPS = HTTP בתוך חיבור TLS. TLS נותן שלושה דברים: הצפנה (מי שבאמצע — ה־Wi-Fi בבית קפה — לא רואה את הסיסמה), שלמות (אי אפשר לשנות את התוכן בדרך), וזהות — תעודה שחתומה על ידי רשות מוכרת אומרת "זה באמת tasks-api.onrender.com". בלי HTTPS, Authorization: Bearer … עובר ברשת כטקסט פתוח.

האפליקציה עצמה לא מחזיקה תעודה. מי שמחזיק — ה־proxy שלפניה: ה־load balancer של Render, או nginx/Caddy בשרת משלך. זה TLS termination, וזה המודל הרגיל: תעודות מתחדשות לבד (Let's Encrypt, כל 90 יום), ומקום אחד מטפל בזה.

2. הניסוי: Caddy לפני הפרויקט

כדי לראות את זה בעיניים, הרצנו את ה־image של שלב ח׳ מאחורי Caddy — reverse proxy שמנפיק תעודות לבד. ל־localhost הוא יוצר רשות תעודות מקומית משלו (tls internal):

Caddyfile 
localhost {
	tls internal
	reverse_proxy api:3000
}

ב־compose — שירות caddy (ports 80 ו־443), ול־api: NODE_ENV: production, CORS_ORIGINS: https://localhost, TRUST_PROXY: "1", ובלי ports — מבחוץ מגיעים רק דרך Caddy. התוצאות (פלטים אמיתיים, מקוצרים):

% curl -sI http://localhost/health
HTTP/1.1 308 Permanent Redirect
Location: https://localhost/health
% curl -skv https://localhost/health
* SSL connection using TLSv1.3 / TLS_AES_128_GCM_SHA256 / X25519 / id-ecPublicKey
*  issuer: CN=Caddy Local Authority - ECC Intermediate
< HTTP/2 200
< via: 1.1 Caddy
< x-request-id: 8d89c205-05a8-4eb5-898f-114da3ef9624
% curl -sk https://localhost/ready
{"ok":true,"db":"up"}
% curl -sS https://localhost/health
curl: (60) SSL certificate problem: unable to get local issuer certificate
  • HTTP ← HTTPS: Caddy מפנה לבד (308).
  • TLS 1.3, ו־HTTP/2 בין הדפדפן ל־proxy — בלי שינוי אחד בקוד ה־Nest.
  • בלי -k, curl מסרב: התעודה חתומה על ידי רשות מקומית שהמחשב לא מכיר. זה בדיוק מה ש־TLS אמור לעשות. ב־Render התעודה מ־Let's Encrypt, וכל דפדפן מכיר אותה.

3. trust proxy — מי הלקוח

מאחורי proxy, כל הבקשות מגיעות מה־proxy. בלי trust proxy, req.ip זהה לכולם — והגבלת הקצב מפרק 24 תחסום את כל המשתמשים יחד אחרי 10 ניסיונות כניסה בדקה. ה־proxy מוסיף את הכתובת האמיתית בסוף X-Forwarded-For, ו־TRUST_PROXY=1 אומר ל־Express לקחת אותה משם — רק את מה שה־proxy שלנו הוסיף.

בדקנו את זה באותו ניסוי: 11 ניסיונות כניסה, כל אחד עם X-Forwarded-For מזויף אחר (פלט אמיתי):

% for i in $(seq 1 11); do curl -sk -o /dev/null -w "%{http_code} " -X POST https://localhost/auth/login \
  -H "X-Forwarded-For: 10.0.0.$i" -H 'content-type: application/json' -d '{"email":"x@example.com","password":"wrong-password"}'; done
401 401 401 401 401 401 401 401 401 401 429

הזיוף לא עזר: Caddy הוסיף אחרי הכתובת המזויפת את הכתובת האמיתית, ו־Express לקח את האחרונה. עם trust proxy: true ("סמוך על הכול") Express היה לוקח את הראשונה — את מה שהלקוח כתב — וכל ניסיון היה "לקוח חדש" (E18, E23). המספר הנכון = כמה proxies שלך יש לפני השרת. ב־Render: 1.

ועוד שני דברים ש־trust proxy מתקן: req.protocol ו־req.secure (מ־X-Forwarded-Proto) — חשוב ל־HSTS, לקישורים שהשרת בונה, ול־cookies עם Secure.

4. security headers

headerמה
Strict-Transport-Security"לאתר הזה — רק HTTPS, לתקופה X". רק על HTTPS אמיתי (לא localhost)
X-Content-Type-Options: nosniffהדפדפן לא "מנחש" סוג קובץ

בעבודה — helmet (app.use(helmet())), שעושה את זה ועוד. ב־E07 תכתוב את הגרסה הבסיסית בעצמך, כדי לדעת מה כל אחד עושה.

5. health מול readiness, בפרודקשן

/health/ready
שאלה"התהליך חי?""אפשר לשלוח אליי בקשות?"
בודקכלום — עונה ופחותאת המסד (SELECT 1, עד 2 שניות)
כשנכשלמפעילים מחדש את הקונטיינרלא שולחים תנועה (deploy לא מחליף את הקודם)
בפרויקטHEALTHCHECK ב־DockerfileHealth Check Path ב־Render, ובדיקת העשן

למה לא לבדוק את המסד ב־/health? כי תקלה רגעית במסד הייתה גורמת לפלטפורמה להפעיל מחדש שרתים תקינים — ולהחמיר את התקלה. ושתי הבקשות האלה נכתבות ללוג ב־debug: הפלטפורמה שואלת אותן כל כמה שניות.

ולבסוף — מישהו צריך לשים לב כשהאתר נופל בשלוש בלילה. שירותי uptime monitoring (UptimeRobot, Better Stack, ועוד — רובם עם תוכנית חינמית) שולחים בקשה ל־/health כל כמה דקות, ומודיעים במייל כשהוא לא עונה. בונוס לא מתוכנן: ב־Render החינמי זה גם מונע מהשרת "להירדם" — שימו לב שזה על חשבון 750 השעות החודשיות שלכם.
