🔒 אחרי שסיימת

הפתרון לדוגמה נמצא ב־29x-project-events/solutions/events-platform. קרא אותו אחרי שכל הבודקים שלך ירוקים — ההשוואה מלמדת הרבה יותר מאשר להעתיק.

קובץשורות שכדאי לקרוא

החלטות, ומה היה משתנה בקנה מידה אחר

  • טרנזקציה לכל הודעה פשוטה ונכונה, ועולה round trip לכל אירוע. ב־10,000 אירועים בשנייה: batch של הודעות לטרנזקציה (INSERT מרובה), commit ל־Kafka על ה־offset האחרון ב־batch. הנכונות לא משתנה — INSERT IGNORE עדיין מגן מכפילויות.
  • DuckDB על קבצים מקומיים מתאים לעשרות מיליוני אירועים. מעבר לזה: lake ב־S3 עם partitions לפי יום (day=…/, יחידה 28.5 E16), ו־ClickHouse, BigQuery או Snowflake במקום DuckDB — אותו SQL כמעט.
  • הפרדה בין tenants היא בכל שאילתה (WHERE tenant_id = ?) ובמפתח ה־cache. בחברה עם לקוחות גדולים: database או topic לכל לקוח גדול.
  • מה חסר בכוונה: dead letter topic להודעות פגומות (כאן רק נספרות), rate limit לכל API key (פרק 24/26), ו־retention ל־events במסד (מוחקים אחרי 90 יום — ה־lake נשאר).
