שיעור 3 — בדיקות HTTP ומסד בדיקות

⏱ ~45 דקות

🎯 בשיעור הזה
  • בדיקות HTTP: שרת אמיתי על פורט פנוי, ו־fetch.
  • מסד בדיקות: נפרד, ריק, ומאופס בין בדיקות.
  • builders לנתוני בדיקה, ובדיקות e2e של זרימה שלמה.

1. בדיקת HTTP

בדיקת unit של controller לא תגלה ש־express.json() רשום אחרי ה־routes, ש־Location חסר, או ש־404 הפך ל־500. לשם כך מריצים את האפליקציה באמת:

items.spec.ts 
import { test } from "node:test";
import assert from "node:assert/strict";
import type { AddressInfo } from "node:net";
import { createApp } from "./app.ts";

async function start(t) {
  const server = await new Promise((resolve) => {
    const s = createApp().listen(0, () => resolve(s));     // 0 = כל פורט פנוי
  });
  t.after(() => server.close());                           // סוגרים בסוף הבדיקה
  const base = `http://localhost:${(server.address() as AddressInfo).port}`;
  return (method, path, body?) =>
    fetch(base + path, { method, headers: { "Content-Type": "application/json" }, body: body && JSON.stringify(body) });
}

test("POST ← 201 עם Location", async (t) => {
  const call = await start(t);
  const res = await call("POST", "/items", { name: "Mug" });
  assert.equal(res.status, 201);
  assert.equal(res.headers.get("location"), "/items/1");
});
  • פורט 0 — מערכת ההפעלה בוחרת פורט פנוי. כך בדיקות רצות במקביל בלי "port already in use".
  • אפליקציה חדשה לכל בדיקה — createApp() יוצר state חדש, אז כל בדיקה מתחילה מאפס.
  • helper אחד (start) — כל בדיקה כותבת רק את מה שמעניין אותה.

זה בדיוק מה שהבודק של הקורס עשה מפרק 15 (listen ו־api ב־tools/load.mjs). עכשיו אתה כותב את זה בעצמך.

2. מסד בדיקות

שלושה כללים:

  1. לעולם לא מסד הפיתוח (ובטח לא פרודקשן). משתנה נפרד, DATABASE_URL_TEST — ואם הוא חסר, הבדיקות נכשלות מיד עם הודעה ברורה, במקום "ליפול" ל־DATABASE_URL.
  2. מבנה זהה לאמיתי — מריצים את אותם migrations. לא CREATE TABLE ביד שמתיישן.
  3. מצב ידוע לפני כל בדיקה — TRUNCATE ... RESTART IDENTITY ב־beforeEach. כך id: 1 הוא באמת 1, ובדיקה לא רואה את מה שהקודמת השאירה.
test/db.ts 
export async function createTestDatabase() {
  const url = process.env.DATABASE_URL_TEST;
  if (!url) throw new Error("חסר DATABASE_URL_TEST");
  const schema = `test_${randomBytes(4).toString("hex")}`;
  const admin = new pg.Client({ connectionString: url });
  await admin.connect();
  await admin.query(`CREATE SCHEMA "${schema}"`);
  await admin.query(`SET search_path TO "${schema}"`);
  for (const m of migrationDirs()) await admin.query(fs.readFileSync(path.join(m, "migration.sql"), "utf8"));
  const prisma = new PrismaClient({
    adapter: new PrismaPg({ connectionString: url, options: `-c timezone=UTC -c search_path=${schema}` }, { schema }),
  });
  return {
    prisma,
    reset: () => admin.query("TRUNCATE users, tasks, refresh_tokens RESTART IDENTITY CASCADE"),
    close: async () => { await prisma.$disconnect(); await admin.query(`DROP SCHEMA "${schema}" CASCADE`); await admin.end(); },
  };
}
💡 ואם הבדיקות רצות במקביל?

schema לכל קובץ פותר את זה: שני קבצים לא כותבים לאותה טבלה. חלופות שתפגוש: transaction שעושים לו ROLLBACK בסוף כל בדיקה (מהיר, אבל לא עובד כשהקוד עצמו פותח transaction), או מסד שלם לכל ריצה ב־Docker (פרק 23). ב־CI (פרק 25) — שירות PostgreSQL שעולה לצד הבדיקות.

3. builders

בדיקה שצריכה "משימה של admin שהסתיימה" לא צריכה לפרט 8 שדות:

const admin = aUser({ role: "admin" });
const task = aTask({ ownerId: admin.id, status: "done" });

הכול האחר — ברירות מחדל תקינות ו־ids ייחודיים. שתי מטרות: הבדיקה מראה רק את מה שחשוב לה; וכשמוסיפים שדה חובה — משנים את ה־builder, לא מאה בדיקות (E16).

4. e2e: זרימה שלמה

בדיקת e2e מספרת סיפור של משתמש: דנה מתחברת ויוצרת פתק; יוסי מתחבר ומנסה לראות ולמחוק אותו — 404; ואז בודקים שאצל דנה הפתק עדיין שם. השורה האחרונה היא מה שמפריד בדיקה טובה מבינונית: קוד שמוחק ואז מחזיר 404 עובר בלעדיה (E18).

⚠️ e2e לא מחליפות unit

בדיקת e2e אחת שנכשלת אומרת "משהו שבור". בדיקת unit אומרת מה. ו־e2e איטיות יותר — מאות כאלה הופכות ריצה של שנייה לדקות. מעט e2e לזרימות החשובות (כניסה, בעלות, תשלום), והרבה unit ללוגיקה.
