1. Jest

הרעיונות זהים — רק התחביר שונה. ב־Nest 12, nest new שואל באיזו מערכת מודולים להשתמש: ESM עם Vitest (ברירת המחדל החדשה) או CJS עם Jest. בקורס בחרנו CJS עם Jest (פרק 20), כי Jest נפוץ מאוד במשרות ובקוד קיים. Vitest הוא החלופה החדשה, עם תחביר כמעט זהה (vi.fn() במקום jest.fn()), כך שמה שתלמד כאן עובר אליו כמעט כמו שהוא.

ב־TypeScript, Jest צריך מתרגם: ts-jest. וב־Nest 12 יש עוד פרט: גם כשהפרויקט שלך CommonJS, החבילות של Nest עצמן הן ESM, ו־Jest טוען אותן רק ב־Node 24 עם --experimental-vm-modules. לכן התבנית מריצה node --experimental-vm-modules node_modules/jest/bin/jest.js ולא סתם jest. בלי הדגל (או ב־Node 22) תקבל:

2. unit ב־Nest — בלי Nest

service הוא מחלקה רגילה. לבדיקת unit לא צריך את Nest בכלל — יוצרים אותו עם כפילים:

src/tasks/tasks.service.spec.ts 
describe("TasksService", () => {
  let clock: TestClock;
  let service: TasksService;

  beforeEach(() => {
    clock = new TestClock();                                   // 2026-11-04T10:00Z
    service = new TasksService(new InMemoryTasksRepository(), clock);
  });

  it("dueDate: היום מותר, אתמול — 422", async () => {
    await expect(service.create(1, input({ dueDate: "2026-11-04" }))).resolves.toMatchObject({ dueDate: "2026-11-04" });
    await expect(service.create(1, input({ dueDate: "2026-11-03" }))).rejects.toMatchObject({ status: 422, code: "DUE_DATE_IN_PAST" });
  });
});

3. e2e ב־Nest — supertest

לבדיקת השרשרת המלאה — אותו AppModule, אותו configureApp כמו ב־main.ts, ו־overrideProvider לתלויות (בדיוק מה שהבודק של PR2 עשה מפרק 20). supertest שולח בקשות ישר ל־app.getHttpServer(), בלי פורט:

test/app.e2e-spec.ts 
it("משימה של משתמש אחר — 404 בכל פעולה", async () => {
  const dana = (await signUp(app, "dana@example.com")).accessToken;
  const yossi = (await signUp(app, "yossi@example.com")).accessToken;
  const created = await http().post("/tasks").set(auth(dana)).send({ title: "של דנה" }).expect(201);
  const path = `/tasks/${created.body.id}`;

  await http().get(path).set(auth(yossi)).expect(404);
  await http().delete(path).set(auth(yossi)).expect(404);
  await http().get(path).set(auth(dana)).expect(200);
});

5. mutation testing — לבדוק את הבדיקות

זה מה שהבודק של הפרק עושה: בכל תרגיל "כתוב בדיקות" יש רשימת מוטנטים (למשל >= ← >, שורה שנמחקה, UTC ← שעון מקומי). הבדיקות שלך רצות על כל אחד, וכל מוטנט ששרד מוצג לך כבאג שהבדיקות לא תופסות. בפרויקטים אמיתיים עושים את זה עם Stryker — איטי (מריץ את כל הבדיקות מאות פעמים), ולכן בדרך כלל רק על הקוד החשוב, או פעם בלילה.

💡 כמה coverage צריך?

אין מספר קסם. 70–80% על הקוד העסקי זה טוב; 100% עולה הרבה ולא מבטיח כלום. שאלה טובה יותר ב־code review: "איזה באג הבדיקה הזו הייתה תופסת?". אם אין תשובה — הבדיקה כנראה לא שווה הרבה.
