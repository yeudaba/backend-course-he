P24-E27 · registry של מדדים 🤖

💻 כתיבת קוד 🤖רמה 2⏱ 30 דק׳ידע נדרש: שיעור 6

בקובץ P24-E27.ts כתוב createRegistry() שמחזיר { counter, histogram, metrics }:

  • counter({ name, help, labelNames }) ← { inc(labels, by = 1) }. by שלילי ← RangeError.
  • histogram({ name, help, labelNames, buckets }) ← { observe(labels, value) }. הדליים — ממוינים, ומצטברים: le="0.5" סופר כל ערך קטן או שווה ל־0.5.
  • label שלא ב־labelNames, או label חסר ← Error. שם שכבר נרשם ← Error.
  • metrics() ← טקסט בפורמט של Prometheus: לכל מדד, לפי סדר הרישום, # HELP, # TYPE, ושורה לכל צירוף labels (לפי הסדר שבו הופיע לראשונה). labels — לפי הסדר של labelNames. ב־histogram: _bucket לכל דלי ועוד le="+Inf", ואחריהם _sum ו־_count. הטקסט מסתיים ב־\n.
  • ערכי labels עוברים escaping: \ ← \\, " ← \", ירידת שורה ← \n.

הפלט של השיעור (סעיף 2) הוא בדיוק הצורה.

P24-E31 · דוח latency מלוגים של JSON 🤖

💻 כתיבת קוד 🤖✍️ מאפסרמה 3⏱ 25 דק׳ידע נדרש: שיעור 6

הלוגים של השרת הם שורות JSON (שיעור 1). לפני שיש Prometheus, אפשר להוציא מהם דוח: איזה route איטי, ואיפה יש שגיאות. כתוב מקובץ ריק וייצא:

  • routeOf(method, path): string — המתודה באותיות גדולות, רווח, והנתיב בלי query string. כל קטע בנתיב שהוא רק ספרות הופך ל־:id: ‏("get", "/tasks/17/comments?x=1") ← "GET /tasks/:id/comments". כך /tasks/17 ו־/tasks/4 נספרים יחד.
  • routeReport(lines: string[]): { routes, skipped }. שורה נספרת רק אם היא JSON תקין, ‏msg שלה הוא "request", ו־ms הוא מספר. כל שורה אחרת (טקסט חופשי, ‏"server started") מוסיפה 1 ל־skipped.
  • ב־routes שורה לכל route: ‏{ route, count, errorPct, p95 }. ‏errorPct — אחוז הבקשות עם status ‏500 ומעלה, מעוגל לספרה אחת אחרי הנקודה (‏33.3). ‏p95 — אחוזון 95 בשיטת nearest-rank (שיעור 6): ממיינים, ולוקחים את האיבר במקום Math.ceil(0.95 × n) (מ־1).
  • מיון: p95 מהגבוה לנמוך, ובתיקו לפי route בסדר אלפביתי.

P24-E116 · ‏histogram_quantile ביד 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 20 דק׳ידע נדרש: שיעור 6

איך Prometheus מעריך p95 מדליים (E110)? בקובץ 24-production/starter/P24-E116.ts (יש בו רק הערה) כתוב וייצא:

export function quantileFromBuckets(buckets: { le: number; count: number }[], q: number): number
  • buckets — מצטברים, ממוינים לפי le, והאחרון הוא le: Infinity. הסך הכול = ה־count של האחרון.
  • rank = q × total. מוצאים את הדלי הראשון שה־count שלו ≥ ‏rank, ומעריכים בקו ישר בתוכו: מהגבול התחתון (ה־le של הדלי הקודם, או 0 לדלי הראשון) עד ה־le שלו, לפי מקום ה־rank בין ה־count הקודם לנוכחי.
  • אם הדלי שנמצא הוא Infinity ← מחזירים את ה־le הסופי הגבוה ביותר.
  • ‏total = 0 ← NaN. ‏q לא בין 0 ל־1 (כולל) ← RangeError.

P24-E24 · אתגר: API של הזמנות, מוכן לפרודקשן 🤖

💻 כתיבת קוד 🤖רמה 5⏱ 90 דק׳ידע נדרש: כל הפרק

בקובץ P24-E24.ts כתוב createApp({ clock, logSink, rateLimitPerMinute = 5 }) — Express, בזיכרון:

  • X-Request-Id כמו ב־E08, ושורת לוג JSON לכל בקשה דרך logSink: time (מה־clock), level לפי status, msg: "request", requestId, userId (אם יש), method, path בלי query, status, durationMs.
  • שגיאות: תמיד { error: { code, message, requestId } } — אותו requestId כמו ב־header.
  • GET /health ← 200 תמיד. GET /ready ← 200, או 503 DRAINING כש־app.locals.draining.
  • "אימות": header x-user-id, חובה ב־/orders (אחרת 401 UNAUTHORIZED).
  • GET /orders ← ההזמנות של המשתמש.
  • POST /orders { item, quantity } (item לא ריק, מקוצץ; quantity שלם 1–100; אחרת 400 VALIDATION_ERROR) ← 201 + Location, { id, userId, item, quantity, createdAt }.
    • Idempotency-Key חובה (400 IDEMPOTENCY_KEY_REQUIRED); replay עם Idempotent-Replayed; גוף אחר ← 422 IDEMPOTENCY_KEY_REUSED; בקשה לא תקינה לא "תופסת" את המפתח.
    • הגבלת קצב לכל משתמש: rateLimitPerMinute ב־60 שניות ← 429 TOO_MANY_REQUESTS עם Retry-After.
  • 404 NOT_FOUND, JSON שבור ← 400 INVALID_JSON.

🔗 איך זה מתחבר: Express ו־middleware מפרק 15, ‏status codes מפרק 14 — וכל שיעורי הפרק יחד: request ID ולוגים, Idempotency-Key, הגבלת קצב ו־/ready בזמן כיבוי.

🔁 חזרה על class עם שדות ומתודות פרטיים ו־getter (פרק 12), לולאת while (פרק 4) ושעון מוזרק (‏P21-E28). התראה "יותר מ־10% שגיאות" צריכה חלון זמן ומינימום בקשות: שתי שגיאות מתוך שלוש בקשות בלילה הן לא תקלה. כתוב וייצא class ErrorRateAlarm:

  • constructor({ windowMs, threshold, minRequests }, now = () => Date.now()). ‏threshold הוא שבר: גדול מ־0 ועד 1 כולל. אחרת ← RangeError.
  • record(status) — רושם בקשה בזמן now(). שגיאה = status >= 500.
  • getter ‏count ו־getter ‏errorRate (‏0 כשאין בקשות) — רק על בקשות מהחלון: זמן גדול מ־now() - windowMs. בקשה בדיוק בגבול כבר לא בחלון.
  • shouldAlert() — ‏count >= minRequests וגם errorRate >= threshold.
  • בקשות ישנות נמחקות מהזיכרון (לא רק לא נספרות), במתודה פרטית #prune() עם while. כל השדות פרטיים.

🔗 איך זה מתחבר: ‏class עם שדות פרטיים ו־getter מפרק 12 ושעון מוזרק מפרק 21 — והשיעור: התראה על סימפטום (שיעור שגיאות) ולא על סיבה.

P24-E120 · ‏span לכל פעולה, עם AsyncLocalStorage 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 25 דק׳ידע נדרש: שיעור 1, פרק 10, שיעור 6

E29 יצר span לכל בקשת HTTP. בתוך הבקשה יש פעולות — שאילתה, קריאה לשירות אחר — וכל אחת צריכה span משלה, "תלוי" על הנוכחי. בקובץ 24-production/starter/P24-E120.ts (יש בו רק הערה) כתוב וייצא:

export type Span = { traceId: string; spanId: string; parentSpanId: string | null; name: string; durationMs: number; error: boolean };
export function createTracer(opts: { onSpan: (s: Span) => void; now: () => number; randomHex: (bytes: number) => string }): {
  withSpan<T>(name: string, fn: () => Promise<T>): Promise<T>;
  currentTraceId(): string | undefined;
}
  • withSpan מחוץ לכל span ← trace חדש: ‏traceId = randomHex(16), ‏parentSpanId: null. בתוך span ← אותו traceId, וההורה הוא ה־span הנוכחי.
  • spanId = randomHex(8). ‏fn רצה כך שכל מה שבתוכה (גם אחרי await) רואה את ה־span החדש כנוכחי.
  • כש־fn נגמרת — onSpan עם durationMs = now() - start ו־error (‏true אם היא זרקה). התוצאה / השגיאה עוברת הלאה.
  • spans שרצים במקביל באותו הורה — כל אחד עם ההורה הנכון. ‏currentTraceId() — מחוץ ל־span ← undefined.
  • כל קריאה ל־createTracer — עם AsyncLocalStorage משלה.
