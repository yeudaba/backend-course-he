P24-E04 · מה בטוח לשלוח פעמיים? 🧠 הבנה רמה 1

💡 רמז 1

Idempotent = לבצע פעם אחת או עשר — אותו מצב בשרת בסוף. (לא בהכרח אותה תשובה.)

💡 רמז 2

"קבע ל־X" מול "שנה ב־X".

✅ פתרון
  1. בטוח. GET לא משנה כלום (safe).
  2. בטוח. PUT = "המצב הוא בדיוק זה". פעמיים — אותו מצב.
  3. בטוח כאן — "קבע status ל־done". PATCH לא מובטח idempotent לפי התקן, אבל הזה כן.
  4. לא! "הורד 100" פעמיים = הורדנו 200. אותו PATCH, תוצאה אחרת — לכן מעדיפים "קבע" על "שנה ב־", או מוסיפים Idempotency-Key.
  5. בטוח במצב: אחרי הראשון — המשימה לא קיימת, והשני מחזיר 404. התשובה שונה, המצב אותו.
  6. לא. שתי משימות "לקנות חלב". מעצבן.
  7. לא — וזה המקרה החשוב. חיוב כפול. זו בדיוק הסיבה ש־Stripe ודומיו דורשים Idempotency-Key ב־POST.

"לא לשלוח שוב" לא עובד כי הלקוח באמת לא יודע אם זה קרה. אין לו דרך להבחין בין "השרת לא קיבל" ל"השרת ביצע והתשובה אבדה". וגם — אפליקציות מובייל, proxies וספריות HTTP שולחים שוב לבד. הפתרון: הלקוח מייצר מפתח לפני השליחה הראשונה (UUID), ושולח אותו בכל ניסיון. השרת מבצע פעם אחת לכל מפתח.

⚠️ טעויות נפוצות
  • לייצר מפתח חדש בכל ניסיון — ואז כל ניסיון נראה כמו בקשה חדשה. המפתח שייך לפעולה, לא לבקשה.

P24-E60 · איך הופכים פעולה ל־idempotent? 🧠 הבנה רמה 2

💡 רמז 1

שלוש טכניקות: (א) לנסח כ"קבע ל־X" במקום "שנה ב־X"; (ב) מזהה ייחודי (מהלקוח, או אילוץ UNIQUE) שהמסד דוחה פעם שנייה; (ג) Idempotency-Key.

💡 רמז 2

לפעמים "כמעט נכון" מספיק — ספירת צפיות לא חייבת להיות מדויקת. ולפעמים לא — העברת כסף.

✅ פתרון
  1. לא — פעמיים = כמות 2. אפשר PUT /cart/items/7 ‏{"quantity": 1} ("הכמות היא 1"), או Idempotency-Key.
  2. לא. שומרים welcome_sent_at במשתמש ושולחים רק אם הוא ריק — בעדכון אטומי (UPDATE ... WHERE welcome_sent_at IS NULL RETURNING), כדי ששני workers לא ישלחו יחד.
  3. לא — אבל אולי זה בסדר: צפייה כפולה נדירה לא שווה מנגנון. אם כן חשוב — מזהה צפייה מהלקוח עם UNIQUE.
  4. כן — "קבע ל־true".
  5. לא, וזה הכי מסוכן. Idempotency-Key חובה (או transferId מהלקוח עם UNIQUE).
  6. כמעט: ה־UNIQUE על email מונע כפילות — אבל הניסיון השני מקבל 409 "כבר קיים" במקום ה־201 שהלקוח מחכה לו. Idempotency-Key נותן את אותה תשובה בדיוק.
⚠️ טעויות נפוצות
  • "אוסיף UNIQUE על כל הטבלה" — לפעמים שתי פעולות זהות הן באמת שתי פעולות (שתי העברות של 100 לאותו אדם).

P24-E61 · מפתח חדש בכל ניסיון 🧠 הבנה רמה 2

💡 רמז 1

המפתח מזהה את הפעולה. כמה פעולות יש כאן — אחת או שלוש?

💡 רמז 2

לחיצה שנייה = קריאה שנייה ל־pay.

✅ פתרון
  1. מפתח חדש בכל ניסיון — לשרת זה נראה כמו שלושה תשלומים שונים. הניסיון הראשון בוצע, התשובה אבדה, השני מבצע שוב — חיוב כפול. המנגנון כולו לא עושה כלום.
  2. const key = crypto.randomUUID() פעם אחת לפני הלולאה, ובכל ניסיון — אותו key (E67).
  3. לא — כל קריאה ל־pay מייצרת מפתח חדש. צריך שהמפתח יהיה של "הטופס": נוצר כשהטופס נפתח (או בלחיצה הראשונה), ומתחלף רק אחרי הצלחה. ובנוסף, ב־UI — לנטרל את הכפתור בזמן שליחה (E102).
⚠️ טעויות נפוצות
  • לחשוב שהשרת "יזהה" שזה אותו תשלום לפי הסכום — שני תשלומים זהים יכולים להיות לגיטימיים.

P24-E62 · למה לא שומרים תשובת 5xx? 🧠 הבנה רמה 2

💡 רמז 1

בשביל מה הלקוח שולח שוב בכלל?

💡 רמז 2

בקשה לא תקינה (422) — האם שליחה חוזרת שלה יכולה להצליח?

✅ פתרון

הניסיון השני מקבל replay של 503 — לנצח (או עד שהמפתח פג). הלקוח עשה בדיוק את מה שהמנגנון נועד לו, והוא תקוע. (זו אחת התקלות של P24-E22.) 5xx אומר "לא הצלחנו לבצע" — אז המפתח משתחרר (release), והניסיון הבא מבצע באמת.

4xx (למשל 422 על dueDate בעבר) — אותה בקשה תיכשל שוב בכל מקרה, אז אפשר לשמור. ובפרויקט בחרנו release גם לשגיאה עסקית, כדי שהלקוח יוכל לתקן את הבקשה ולשלוח עם אותו מפתח (E92) — שתי הגישות קיימות בעולם.

⚠️ טעויות נפוצות
  • לשמור "רק 2xx" ולשכוח את המצב "בטיפול" — ואז אחרי קריסה באמצע, המפתח תקוע ב־409 לנצח. צריך תוקף גם לרשומה בטיפול.

P24-E63 · ‏409 IN_PROGRESS — ומה עכשיו? 🧠 הבנה רמה 2

💡 רמז 1

חיבור שמחכה תופס משאבים בשרת. כמה ניסיונות כאלה יכולים להצטבר?

💡 רמז 2

רשומה "בטיפול" שאף אחד כבר לא מטפל בה.

✅ פתרון
  1. 409 IDEMPOTENCY_IN_PROGRESS. לחכות בשרת = חיבור פתוח וזיכרון לכל ניסיון; לקוח עם timeout קצר יכול לייצר עשרות כאלה. פשוט יותר ובטוח יותר: לענות מיד, ולתת ללקוח להחליט.
  2. מחכה קצת (backoff) ושולח שוב עם אותו מפתח. בסוף יקבל replay של התוצאה האמיתית. (409 הוא בין התשובות ששווה לנסות עליהן שוב — E67.)
  3. הרשומה נשארת "בטיפול". לכן יש תוקף: אחרי ה־TTL הרשומה נחשבת לא קיימת, והניסיון הבא מבצע. (יש מערכות שנותנות לרשומה "בטיפול" תוקף קצר בהרבה מ־24 שעות — דקות.)
⚠️ טעויות נפוצות
  • להחזיר 500 ל"בטיפול" — הלקוח חושב שנכשל, ואולי מייצר מפתח חדש.

P24-E64 · מה נכנס לטביעת האצבע? 🧠 הבנה רמה 2

💡 רמז 1

מה שקובע הוא "האם השרת היה עושה אותו דבר".

💡 רמז 2

JSON.stringify שומר על סדר המפתחות כמו שהגיעו.

✅ פתרון
  1. אותה בקשה — אבל JSON.stringify נותן מחרוזות שונות. צריך JSON קנוני: מפתחות ממוינים (E65).
  2. אותה בקשה, אם מחשבים את הטביעה אחרי ה־validation (כמו בפרויקט). לפני — הן "שונות", והלקוח מקבל 422 בלי סיבה.
  3. שונות — פעולות שונות לגמרי. לכן גם method ונתיב נכנסים לטביעה (או להיקף של המפתח).
  4. אותה בקשה. headers כמו User-Agent ו־Date לא משנים את הפעולה ולא נכנסים.
  5. שונות — במערך, הסדר הוא חלק מהתוכן. מיון מפתחות — כן; מיון מערכים — לא.
⚠️ טעויות נפוצות
  • טביעה על הגוף הגולמי (המחרוזת שהגיעה) — רווח או ירידת שורה אחרת = 422.

P24-E14 · מאגר של Idempotency-Key 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

Map מ־id לרשומה { fingerprint, response: null | {...}, createdAt }. response === null = בטיפול.

💡 רמז 2

id בטוח: JSON.stringify([scope, key]).

✅ פתרון
// P24-E14
export interface StoredResponse {
  status: number;
  body: unknown;
}
export type Begin =
  | { kind: "new" }
  | { kind: "replay"; response: StoredResponse }
  | { kind: "mismatch" }
  | { kind: "in_progress" };

interface Entry {
  fingerprint: string;
  response: StoredResponse | null; // null = עדיין בטיפול
  createdAt: number;
}

export class IdempotencyStore {
  #entries = new Map<string, Entry>();
  #ttlMs: number;
  #now: () => number;

  constructor({ ttlMs = 24 * 3600_000, now = () => Date.now() }: { ttlMs?: number; now?: () => number } = {}) {
    this.#ttlMs = ttlMs;
    this.#now = now;
  }

  // scope = מי (בדרך כלל userId). אותו key של שני משתמשים — שתי רשומות נפרדות
  #id(scope: string, key: string) {
    return JSON.stringify([scope, key]); // לא `${scope}:${key}` — "a:b"+"c" ו־"a"+"b:c" היו מתנגשים
  }

  #live(id: string): Entry | undefined {
    const e = this.#entries.get(id);
    if (e && this.#now() - e.createdAt >= this.#ttlMs) {
      this.#entries.delete(id);
      return undefined;
    }
    return e;
  }

  begin(scope: string, key: string, fingerprint: string): Begin {
    const id = this.#id(scope, key);
    const e = this.#live(id);
    if (!e) {
      this.#entries.set(id, { fingerprint, response: null, createdAt: this.#now() });
      return { kind: "new" };
    }
    if (e.fingerprint !== fingerprint) return { kind: "mismatch" };
    if (e.response === null) return { kind: "in_progress" };
    return { kind: "replay", response: e.response };
  }

  complete(scope: string, key: string, response: StoredResponse) {
    const e = this.#entries.get(this.#id(scope, key));
    if (!e) throw new Error("אין בקשה כזו בטיפול");
    e.response = response;
  }

  release(scope: string, key: string) {
    const id = this.#id(scope, key);
    if (this.#entries.get(id)?.response === null) this.#entries.delete(id); // רק מה שלא הושלם
  }

  // מוחק רשומות שפג תוקפן; מחזיר כמה נמחקו. בשרת — כל כמה דקות
  sweep(): number {
    let removed = 0;
    for (const id of [...this.#entries.keys()]) if (!this.#live(id)) removed++;
    return removed;
  }

  get size() {
    return this.#entries.size;
  }
}
⚠️ טעויות נפוצות
  • להחזיר replay בלי לבדוק טביעה — לקוח עם באג ששולח מפתח קבוע יקבל לנצח את התשובה של הבקשה הראשונה, בלי שגיאה (E22).

P24-E15 · middleware של Idempotency-Key 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

const json = res.json.bind(res); res.json = (body) => { ...; return json(body); }.

💡 רמז 2

res.on("close", ...) רץ תמיד בסוף; דגל done אומר אם כבר טיפלנו.

✅ פתרון
// P24-E15
import { createHash } from "node:crypto";
import type { NextFunction, Request, Response } from "express";

export interface StoredResponse {
  status: number;
  body: unknown;
}
export interface Store {
  begin(scope: string, key: string, fingerprint: string): { kind: "new" } | { kind: "replay"; response: StoredResponse } | { kind: "mismatch" } | { kind: "in_progress" };
  complete(scope: string, key: string, response: StoredResponse): void;
  release(scope: string, key: string): void;
}

const VALID_KEY = /^[A-Za-z0-9_-]{8,100}$/;

export function idempotency({ store, scope = (req) => req.get("x-user-id") ?? "anonymous" }: { store: Store; scope?: (req: Request) => string }) {
  return (req: Request, res: Response, next: NextFunction) => {
    const key = req.get("idempotency-key");
    if (req.method !== "POST" || key === undefined) return next(); // GET/PUT/DELETE כבר idempotent; בלי מפתח — רגיל
    if (!VALID_KEY.test(key)) return res.status(400).json({ error: "Idempotency-Key לא תקין" });

    const who = scope(req);
    // אותו מפתח לבקשה אחרת (נתיב או גוף אחר) — זו טעות של הלקוח, לא "ניסיון חוזר"
    const fingerprint = createHash("sha256").update(JSON.stringify([req.method, req.path, req.body ?? null])).digest("hex");
    const r = store.begin(who, key, fingerprint);
    if (r.kind === "mismatch") return res.status(422).json({ error: "המפתח כבר שימש לבקשה אחרת" });
    if (r.kind === "in_progress") return res.status(409).json({ error: "בקשה עם המפתח הזה עדיין בטיפול" });
    if (r.kind === "replay") return res.status(r.response.status).set("Idempotent-Replayed", "true").json(r.response.body);

    let done = false;
    const json = res.json.bind(res);
    res.json = (body: unknown) => {
      done = true;
      // 5xx — תקלה אצלנו, לא תשובה: משחררים, כדי שניסיון חוזר באמת ינסה שוב
      if (res.statusCode >= 500) store.release(who, key);
      else store.complete(who, key, { status: res.statusCode, body });
      return json(body);
    };
    // נגמר בלי res.json (חריגה ← טיפול השגיאות של Express, או החיבור נסגר) — משחררים
    res.on("close", () => {
      if (!done) store.release(who, key);
    });
    next();
  };
}

למה 4xx כן נשמר? כי זו תשובה סופית ונכונה — שליחה חוזרת של אותה בקשה לא תקינה תקבל את אותה תשובה בכל מקרה. 5xx — "לא הצלחנו", וניסיון חוזר הוא בדיוק מה שאנחנו רוצים שיקרה.

⚠️ טעויות נפוצות
  • טביעה רק של ה־body — אותו מפתח ל־POST /orders ול־POST /refunds יחזיר את ההזמנה.

P24-E16 · מרוץ במסד: תשלום אחד בלבד 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

"קודם SELECT, ואם אין — INSERT" לא עובד: שתי טרנזקציות עושות SELECT באותו רגע, ושתיהן לא מוצאות.

💡 רמז 2

טרנזקציה אחת: INSERT INTO idempotency_keys ... ON CONFLICT (user_id, key) DO NOTHING RETURNING key ראשון. אם חזרה שורה — אתה "זכית". אם לא — מישהו אחר כבר יצר, ומותר לקרוא את מה שהוא שמר.

✅ פתרון
// P24-E16
import type pg from "pg";

export interface Payment {
  id: number;
  userId: number;
  amountCents: number;
}

export async function createPayment(pool: pg.Pool, userId: number, key: string, amountCents: number): Promise<{ replayed: boolean; payment: Payment }> {
  const fingerprint = JSON.stringify({ amountCents });
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    // שתי טרנזקציות עם אותו (user_id, key): השנייה *מחכה* כאן עד שהראשונה מסתיימת (נעילה על ה־PRIMARY KEY),
    // ואז — אם הראשונה עשתה COMMIT — DO NOTHING ולא מחזירה שורה
    const claimed = await client.query(
      "INSERT INTO idempotency_keys (user_id, key, fingerprint) VALUES ($1, $2, $3) ON CONFLICT (user_id, key) DO NOTHING RETURNING key",
      [userId, key, fingerprint],
    );
    if (claimed.rowCount === 1) {
      const { rows } = await client.query("INSERT INTO payments (user_id, amount_cents) VALUES ($1, $2) RETURNING id", [userId, amountCents]);
      await client.query("UPDATE idempotency_keys SET payment_id = $1 WHERE user_id = $2 AND key = $3", [rows[0].id, userId, key]);
      await client.query("COMMIT");
      return { replayed: false, payment: { id: rows[0].id, userId, amountCents } };
    }
    // המפתח כבר קיים (ו־committed — אחרת היינו עדיין מחכים): מחזירים את מה שנוצר אז
    const { rows } = await client.query(
      `SELECT k.fingerprint, p.id, p.amount_cents FROM idempotency_keys k JOIN payments p ON p.id = k.payment_id
       WHERE k.user_id = $1 AND k.key = $2`,
      [userId, key],
    );
    await client.query("COMMIT");
    if (rows[0].fingerprint !== fingerprint) throw new Error("IDEMPOTENCY_KEY_REUSED");
    return { replayed: true, payment: { id: rows[0].id, userId, amountCents: rows[0].amount_cents } };
  } catch (err) {
    await client.query("ROLLBACK").catch(() => {});
    throw err;
  } finally {
    client.release();
  }
}

הקסם הוא ב־PRIMARY KEY: כשטרנזקציה א׳ הכניסה מפתח ועדיין לא עשתה COMMIT, טרנזקציה ב׳ שמנסה להכניס את אותו מפתח מחכה. אם א׳ עושה COMMIT — ב׳ מקבלת DO NOTHING ורואה את השורה. אם א׳ עושה ROLLBACK — ב׳ מכניסה ו"זוכה". המסד עושה את התיאום, לא הקוד.

ומה עושה הגרסה הנאיבית (SELECT ואז INSERT, בלי טרנזקציה) עם 20 קריאות במקביל? הרצנו (פלט אמיתי): בקשה אחת הצליחה, 19 נכשלו עם duplicate key value violates unique constraint "idempotency_keys_pkey" — ו־20 שורות ב־payments. הלקוח קיבל שגיאות, וחויב 20 פעמים.

⚠️ טעויות נפוצות

// P24-E22
import { createHash } from "node:crypto";
import type { NextFunction, Request, Response } from "express";

export function idempotency() {
  const saved = new Map<string, { fingerprint: string; status: number; body: unknown }>();

  return (req: Request, res: Response, next: NextFunction) => {
    const key = req.get("idempotency-key");
    if (req.method !== "POST" || !key) return next();
    const userId = req.get("x-user-id") ?? "anonymous";
    // תקלה 1: המפתח היה גלובלי — יוסי עם אותו מפתח כמו דנה קיבל את ההזמנה של דנה (דליפת מידע!)
    const id = JSON.stringify([userId, key]);
    // תקלה 2: בלי טביעת אצבע — אותו מפתח עם גוף אחר החזיר בשקט את התשובה הישנה
    const fingerprint = createHash("sha256").update(JSON.stringify([req.path, req.body ?? null])).digest("hex");

    const hit = saved.get(id);
    if (hit && hit.fingerprint !== fingerprint) return res.status(422).json({ error: "המפתח כבר שימש לבקשה אחרת" });
    if (hit) return res.status(hit.status).set("Idempotent-Replayed", "true").json(hit.body);

    const json = res.json.bind(res);
    res.json = (body: unknown) => {
      // תקלה 3: גם 500 נשמר — וכל ניסיון חוזר קיבל את אותה שגיאה לנצח, בלי לנסות באמת
      if (res.statusCode < 500) saved.set(id, { fingerprint, status: res.statusCode, body });
      return json(body);
    };
    next();
  };
}
⚠️ טעויות נפוצות

// P24-E65: טביעת אצבע קנונית
import { createHash } from "node:crypto";

export function canonicalJson(value: unknown): string {
  if (Array.isArray(value)) return `[${value.map((v) => (v === undefined ? "null" : canonicalJson(v))).join(",")}]`;
  if (value !== null && typeof value === "object") {
    const obj = value as Record<string, unknown>;
    const keys = Object.keys(obj).filter((k) => obj[k] !== undefined).sort();
    return `{${keys.map((k) => `${JSON.stringify(k)}:${canonicalJson(obj[k])}`).join(",")}}`;
  }
  return JSON.stringify(value);
}

export function fingerprint(method: string, path: string, body: unknown): string {
  return createHash("sha256").update(`${method.toUpperCase()} ${path}\n${canonicalJson(body)}`).digest("hex");
}

// P24-E66: מה עושים עם הבקשה?
export type Entry = { fingerprint: string; status: number | null; body?: unknown; createdAt: number };
export type Decision =
  | { action: "execute" }
  | { action: "replay"; status: number; body: unknown }
  | { action: "reject"; status: 409 | 422; code: string };

export function decide(entry: Entry | undefined, fp: string, now: number, ttlMs: number): Decision {
  if (!entry || now - entry.createdAt >= ttlMs) return { action: "execute" }; // פג תוקף = כאילו לא קיים
  if (entry.fingerprint !== fp) return { action: "reject", status: 422, code: "IDEMPOTENCY_KEY_REUSED" };
  if (entry.status === null) return { action: "reject", status: 409, code: "IDEMPOTENCY_IN_PROGRESS" };
  return { action: "replay", status: entry.status, body: entry.body };
}

export function shouldStore(status: number): boolean {
  return status >= 200 && status < 500; // 5xx = "לא הצלחנו" ← release, כדי שאפשר יהיה לנסות שוב
}
⚠️ טעויות נפוצות

// P24-E67: לקוח שמנסה שוב — עם אותו מפתח
export type Send = (body: unknown, key: string) => Promise<{ status: number; body: unknown }>;

const retryable = (status: number) => status >= 500 || status === 409;

export async function sendWithRetry(
  send: Send,
  body: unknown,
  { retries, sleep, newKey }: { retries: number; sleep: (ms: number) => Promise<void>; newKey: () => string },
) {
  const key = newKey(); // מפתח אחד לפעולה — לא לניסיון
  let lastError: unknown;
  let lastResponse: { status: number; body: unknown } | undefined;
  for (let attempt = 1; attempt <= retries + 1; attempt++) {
    if (attempt > 1) await sleep(200 * 2 ** (attempt - 2));
    try {
      lastResponse = await send(body, key);
      lastError = undefined;
      if (!retryable(lastResponse.status)) return { ...lastResponse, attempts: attempt, key };
    } catch (err) {
      lastError = err;
      lastResponse = undefined;
    }
    if (attempt === retries + 1) {
      if (lastResponse) return { ...lastResponse, attempts: attempt, key };
      throw lastError;
    }
  }
  throw new Error("unreachable");
}

אותו מפתח בכל ניסיון — זה כל הסוד. השרת רואה פעולה אחת: הניסיון הראשון ביצע, והבאים מקבלים 409 (בזמן שהוא רץ) או replay (אחרי).

⚠️ טעויות נפוצות
  • לנסות שוב על 400 או 422 — הבקשה לא תקינה, היא תיכשל שוב בכל ניסיון.
  • לא לנסות שוב על 409 — ואז הלקוח מוותר בדיוק כשהבקשה הראשונה עוד רצה.

// P24-E68: למצוא חיובים כפולים
export type Payment = { id: number; userId: number; amountCents: number; createdAt: string };

export function suspectedDuplicates(payments: Payment[], windowMs: number): number[][] {
  const byKey = new Map<string, Payment[]>();
  for (const p of payments) {
    const k = `${p.userId}:${p.amountCents}`;
    byKey.set(k, [...(byKey.get(k) ?? []), p]);
  }
  const groups: Payment[][] = [];
  for (const list of byKey.values()) {
    const sorted = [...list].sort((a, b) => Date.parse(a.createdAt) - Date.parse(b.createdAt));
    let current: Payment[] = [];
    for (const p of sorted) {
      const prev = current.at(-1);
      if (prev && Date.parse(p.createdAt) - Date.parse(prev.createdAt) < windowMs) current.push(p);
      else {
        if (current.length >= 2) groups.push(current);
        current = [p];
      }
    }
    if (current.length >= 2) groups.push(current);
  }
  return groups
    .sort((a, b) => Date.parse(a[0].createdAt) - Date.parse(b[0].createdAt))
    .map((g) => g.map((p) => p.id));
}

// P24-E72: webhook פעם אחת — במסד
import type { Pool } from "pg";

export async function handlePaymentEvent(pool: Pool, event: { id: string; orderId: number; amountCents: number }) {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const claimed = await client.query(
      "INSERT INTO processed_events (event_id) VALUES ($1) ON CONFLICT DO NOTHING RETURNING event_id",
      [event.id],
    );
    if (claimed.rowCount === 0) {
      await client.query("ROLLBACK");
      return "duplicate" as const;
    }
    const updated = await client.query(
      "UPDATE orders SET status = 'paid', paid_cents = paid_cents + $2 WHERE id = $1",
      [event.orderId, event.amountCents],
    );
    if (updated.rowCount === 0) throw new Error("ORDER_NOT_FOUND");
    await client.query("COMMIT");
    return "processed" as const;
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}

במקביל: הראשון מכניס את השורה ומחזיק אותה עד COMMIT. התשעה האחרים מחכים על ה־PRIMARY KEY, ואחרי ה־COMMIT מקבלים DO NOTHING. ואם הראשון עשה ROLLBACK (הזמנה לא קיימת) — אחד מהם "זוכה" ומנסה בעצמו.

// P24-E73: PUT עם מזהה מהלקוח
import { Router } from "express";

type Note = { id: string; text: string; version: number };
const UUID = /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/;

export function notesRouter() {
  const notes = new Map<string, Note>();
  const router = Router();
  const fail = (code: string, message: string) => ({ error: { code, message } });

  router.put("/notes/:id", (req, res) => {
    const { id } = req.params;
    if (!UUID.test(id)) {
      res.status(400).json(fail("INVALID_ID", "המזהה חייב להיות UUID"));
      return;
    }
    const raw = req.body?.text;
    const text = typeof raw === "string" ? raw.trim() : "";
    if (!text) {
      res.status(400).json(fail("VALIDATION_ERROR", "text חייב להיות מחרוזת לא ריקה"));
      return;
    }
    const existing = notes.get(id);
    if (!existing) {
      const note = { id, text, version: 1 };
      notes.set(id, note);
      res.status(201).location(`/notes/${id}`).json(note);
      return;
    }
    if (existing.text !== text) {
      existing.text = text;
      existing.version += 1;
    }
    res.json(existing); // אותו תוכן ← אותו מצב, בלי שינוי
  });

  router.get("/notes/:id", (req, res) => {
    const note = notes.get(req.params.id);
    if (!note) {
      res.status(404).json(fail("NOT_FOUND", "הפתק לא נמצא"));
      return;
    }
    res.json(note);
  });
  return router;
}

P24-E74 · ‏single flight: אותה פעולה, ריצה אחת 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

שתי מפות: inFlight: Map<string, Promise<T>> ו־done: Map<string, T>.

💡 רמז 2

שומרים את ה־Promise ב־inFlight לפני ה־await — ומוחקים אותה כשהיא נגמרת (גם בכישלון).

✅ פתרון
// P24-E74: single flight — אותה פעולה, ריצה אחת
export function createSingleFlight<T>() {
  const inFlight = new Map<string, Promise<T>>();
  const done = new Map<string, T>();
  return {
    run(key: string, fn: () => Promise<T>): Promise<T> {
      if (done.has(key)) return Promise.resolve(done.get(key) as T); // replay
      const running = inFlight.get(key);
      if (running) return running; // "בטיפול" — מחכים לאותה ריצה
      const p = (async () => {
        try {
          const value = await fn();
          done.set(key, value);
          return value;
        } finally {
          inFlight.delete(key); // גם בכישלון — כדי שהבא ינסה שוב
        }
      })();
      inFlight.set(key, p);
      return p;
    },
    forget(key: string) {
      done.delete(key);
    },
  };
}

זה המנגנון של שיעור 3 בקטן — "בטיפול" (ה־Promise ב־inFlight), "הושלם" (ב־done), ושחרור בכישלון. הוא עובד רק בתהליך אחד; עם שני שרתים — שוב צריך מסד (או Redis).

⚠️ טעויות נפוצות
  • לשמור ב־done גם שגיאות — ואז תקלה רגעית "ננעלת" לתמיד (כמו 5xx שנשמר, E62).
  • inFlight.set אחרי await — עד שהוא קורה, קריאה שנייה כבר התחילה ריצה משלה.
