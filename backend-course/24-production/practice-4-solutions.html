P24-E05 · שלוש דרכים לספור 🧠 הבנה רמה 1

💡 רמז 1

ב־fixed window, 12:00:50 ו־12:01:05 הן בשתי דקות שונות.

💡 רמז 2

ב־token bucket: כמה אסימונים התמלאו בין 12:00:50 ל־12:01:05?

✅ פתרון
  1. כל 20 עוברות — 10 בדקה של 12:00, ו־10 בדקה של 12:01. 20 בקשות ב־15 שניות, כפול מהמגבלה. זו החולשה של fixed window: פרץ בגבול.
  2. 10 עוברות, ה־10 הבאות נדחות (ב־12:01:05 יש כבר 10 בחלון). ב־12:01:50 הראשונות יוצאות מהחלון. Retry-After: 45 שניות.
  3. 12 עוברות: 10 מהדלי המלא, ועד 12:01:05 התמלאו עוד 2 (15 שניות ÷ 6).
  4. ל־login — sliding window: מגבלה קשיחה ופשוטה להסביר ("10 ניסיונות בדקה"), וזה מה שבפרויקט. ל־API עם פרצים — token bucket: מאפשר פרץ קצר (טעינת מסך שמביאה 8 דברים), ושומר על ממוצע. (fixed window — כשצריך הכי פשוט וזול, למשל מונה ב־Redis עם תוקף.)
⚠️ טעויות נפוצות
  • לחשוב שהגבלת קצב היא "אבטחה מלאה". היא מאטה ניחוש סיסמאות מ־IP אחד; תוקף עם אלף IPs צריך גם נעילת חשבון (פרק 21, E19) ו־CAPTCHA.

P24-E75 · בקשה שנדחתה — לספור אותה? 🧠 הבנה רמה 1

💡 רמז 1

בחלון נע, בקשה "יוצאת" מהחלון 60 שניות אחרי שנכנסה.

💡 רמז 2

כמה עולה לשרת לדחות בקשה, לעומת לטפל בה?

✅ פתרון
  1. אף פעם. בכל שנייה נכנסת לחלון בקשה חדשה (שנדחתה), ותמיד יש בו 60 בקשות ומעלה. הלקוח נעול כל עוד הוא מנסה.
  2. ב־12:01:00 הבקשות של 12:00:00 יוצאות מהחלון, והבקשה של 12:01:00 עוברת.

⚠️ טעויות נפוצות
  • לחשוב ש"להעניש" לקוח שלא מכבד Retry-After זה רעיון טוב — לרוב זה באג ב־frontend של המשתמשים שלך, והם נעולים.

P24-E76 · ‏trust proxy — מה יהיה req.ip? 🧠 הבנה רמה 2

💡 רמז 1

‏trust proxy = N אומר: "N התחנות האחרונות בשרשרת הן שלי, ואני סומך על מה שהן הוסיפו". הולכים מימין לשמאל.

💡 רמז 2

ב־X-Forwarded-For כל proxy מוסיף בסוף את מי שפנה אליו. מה שבהתחלה — מי שכתב אותו קודם, כולל הלקוח עצמו.

✅ פתרון
  1. 203.0.113.7 — הכתובת של החיבור. ה־header מתעלמים ממנו. נכון.
  2. 1.2.3.4 — Express "סומך" על header שהלקוח כתב. כל בקשה עם כתובת אחרת = הגבלת הקצב לא קיימת (P24-E23).
  3. 10.0.0.5 לכל המשתמשים. כל העולם הוא "לקוח אחד", ואחרי 10 בקשות כולם חסומים.
  4. 203.0.113.7 — לוקחים את הכתובת שה־proxy שלנו הוסיף (הימנית), והמזויפת נשארת בצד. נכון.
  5. הכתובת של ה־CDN — זה מה ש־nginx ראה. כל המשתמשים שמגיעים דרך אותו שרת CDN — "לקוח אחד". צריך trust proxy = 2 (את החישוב עצמו תכתוב בפרק 25, P25-E18).
⚠️ טעויות נפוצות
  • app.set("trust proxy", true) — "סומך על כולם", כלומר לוקח את הכתובת השמאלית ביותר — שהלקוח כתב. זה מקרה 2.

P24-E77 · את מי מגבילים ב־login? 🧠 הבנה רמה 2

💡 רמז 1

הגבלה לפי IP לא רואה התקפה מהרבה כתובות. הגבלה לפי חשבון לא רואה התקפה על הרבה חשבונות.

💡 רמז 2

תרחיש 5 הוא התקפה על הזמינות, לא על הסיסמה.

✅ פתרון
  1. (א) עוצר. גם (ב).
  2. רק (ב) — כל IP שולח בקשה אחת.
  3. רק (א) — כל חשבון מקבל ניסיון אחד.
  4. (א) עם מגבלה נמוכה חוסם את המשרד. לכן המגבלה לפי IP גבוהה יותר (למשל 20–50 לדקה), והקשוחה — לפי חשבון.
  5. (ב) "נועל" את דנה — זה מה שהתוקף רוצה. מקטינים את הנזק: סופרים לפי חשבון רק כישלונות, מאפסים בהצלחה, חוסמים לזמן קצר ולא "עד שתפנה לתמיכה", ומוסיפים CAPTCHA במקום חסימה.

לכן בפועל — (ג): IP עם מגבלה נדיבה, ואימייל עם מגבלה על כישלונות (E87).

⚠️ טעויות נפוצות
  • להגביל לפי האימייל כמו שהגיע — Dana@Example.com ו־dana@example.com הם "חשבונות שונים" ועוקפים את המגבלה. מנרמלים כמו בהרשמה.

P24-E78 · ‏SIGTERM — מה קודם למה? 🧠 הבנה רמה 2

💡 רמז 1

ה־load balancer בודק את /ready כל כמה שניות. מה קורה עם בקשות שהוא שולח בינתיים?

💡 רמז 2

מה קורה לבקשה שבאמצע, שעוד צריכה את המסד, אם המסד כבר סגור?

✅ פתרון

ב ← ד ← א ← ג.

  • ב לפני ד: קודם אומרים ל־load balancer "אל תשלח לי", ורק אחר כך מפסיקים לקבל. הפוך — בקשות שה־LB כבר שלח נתקלות בחיבור סגור.
  • ד לפני א: הבקשות שבאמצע עוד צריכות את המסד. הפוך — הן נכשלות עם 500 (בדיוק המלכודת של onModuleDestroy בשיעור).
  • א לפני ג: סוגרים חיבורים בצורה מסודרת — אחרת המסד רואה חיבורים שנקטעו. ו־exit רק בסוף, אחרת שום דבר מהשאר לא קורה.

‏/health = "התהליך חי". אם הוא יחזיר 503, ה־orchestrator יחשוב שהתהליך תקוע ויהרוג אותו מיד — בדיוק באמצע הכיבוי המסודר.

⚠️ טעויות נפוצות
  • לכבות בלי גבול זמן — בקשה אחת שלא נגמרת (stream, long polling) תשאיר את התהליך עד ה־SIGKILL.

✅ פתרון

⚠️ טעויות נפוצות

P24-E17 · Token Bucket 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

בלי טיימרים: שומרים tokens ו־last. בכל take: tokens = min(capacity, tokens + (now − last) / 1000 × rate).

💡 רמז 2

חסר cost − tokens אסימונים; בקצב rate לשנייה — Math.ceil(missing / rate) שניות.

✅ פתרון
// P24-E17
export interface TakeResult {
  allowed: boolean;
  remaining: number;
  retryAfterSeconds: number;
}

// דלי עם capacity אסימונים, שמתמלא בקצב קבוע. כל בקשה לוקחת אסימון.
// מאפשר "פרץ" של עד capacity בקשות, ובממוצע — refillPerSecond בשנייה
export class TokenBucket {
  #capacity: number;
  #rate: number;
  #now: () => number;
  #tokens: number;
  #last: number;

  constructor({ capacity, refillPerSecond, now = () => Date.now() }: { capacity: number; refillPerSecond: number; now?: () => number }) {
    if (capacity <= 0 || refillPerSecond <= 0) throw new RangeError("capacity ו־refillPerSecond חייבים להיות חיוביים");
    this.#capacity = capacity;
    this.#rate = refillPerSecond;
    this.#now = now;
    this.#tokens = capacity; // מתחיל מלא
    this.#last = now();
  }

  #refill() {
    const t = this.#now();
    // לא שומרים טיימר — מחשבים כמה התמלא מאז הפעם הקודמת
    this.#tokens = Math.min(this.#capacity, this.#tokens + ((t - this.#last) / 1000) * this.#rate);
    this.#last = t;
  }

  take(cost = 1): TakeResult {
    if (cost > this.#capacity) throw new RangeError("cost גדול מהקיבולת — הבקשה לעולם לא תעבור");
    this.#refill();
    if (this.#tokens >= cost) {
      this.#tokens -= cost;
      return { allowed: true, remaining: Math.floor(this.#tokens), retryAfterSeconds: 0 };
    }
    // לא מורידים כלום כשנדחה — אחרת לקוח שמנסה שוב ושוב לא יעבור לעולם
    const missing = cost - this.#tokens;
    return { allowed: false, remaining: Math.floor(this.#tokens), retryAfterSeconds: Math.ceil(missing / this.#rate) };
  }
}
⚠️ טעויות נפוצות
  • setInterval שממלא את כל הדליים — אלף לקוחות = אלף טיימרים, והכול לא מדויק.

P24-E18 · middleware של הגבלת קצב 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

Map מלקוח למערך זמנים. בכל בקשה: filter(t => t > now − windowMs).

💡 רמז 2

ניקוי: פעם ב־windowMs, עוברים על ה־Map ומוחקים לקוחות שהבקשה האחרונה שלהם יצאה מהחלון.

✅ פתרון
// P24-E18
import type { NextFunction, Request, Response } from "express";

export function rateLimit({ limit, windowMs, now = () => Date.now(), key = (req) => req.ip ?? "unknown" }: {
  limit: number;
  windowMs: number;
  now?: () => number;
  key?: (req: Request) => string;
}) {
  const hits = new Map<string, number[]>(); // לכל לקוח — הזמנים של הבקשות שעברו, בחלון האחרון
  let lastSweep = now();

  return (req: Request, res: Response, next: NextFunction) => {
    const t = now();
    // ניקוי מדי פעם: לקוח שהלך — לא נשאר בזיכרון לנצח
    if (t - lastSweep >= windowMs) {
      for (const [k, times] of hits) if (times.at(-1)! <= t - windowMs) hits.delete(k);
      lastSweep = t;
    }
    const id = key(req);
    const recent = (hits.get(id) ?? []).filter((x) => x > t - windowMs);
    const resetSeconds = (oldest: number) => Math.max(1, Math.ceil((oldest + windowMs - t) / 1000));
    res.setHeader("RateLimit-Limit", String(limit));

    if (recent.length >= limit) {
      hits.set(id, recent); // הבקשה שנדחתה לא נספרת
      const retry = resetSeconds(recent[0]);
      res.setHeader("RateLimit-Remaining", "0");
      res.setHeader("RateLimit-Reset", String(retry));
      res.setHeader("Retry-After", String(retry)); // בשניות, לפי התקן — לא מילישניות
      return res.status(429).json({ error: "יותר מדי בקשות" });
    }
    recent.push(t);
    hits.set(id, recent);
    res.setHeader("RateLimit-Remaining", String(limit - recent.length));
    res.setHeader("RateLimit-Reset", String(resetSeconds(recent[0])));
    next();
  };
}

ה־headers האלה (RateLimit-*) הם טיוטת תקן של IETF; GitHub ו־Cloudflare שולחים גרסאות שלהם (X-RateLimit-*). לקוח טוב קורא אותם ומאט לפני שהוא נחסם.

⚠️ טעויות נפוצות
  • זה עובד בשרת אחד. עם שלושה שרתים מאחורי load balancer, כל אחד סופר לבד — והמגבלה האמיתית פי 3. לשם צריך מונה משותף (Redis, פרק 26).

P24-E19 · כיבוי מסודר 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

server.close(cb) — מפסיק לקבל, ו־cb נקרא כשכל החיבורים נסגרו. server.closeIdleConnections(), server.closeAllConnections().

💡 רמז 2

Promise.race בין "נסגר" ל־timeout. ואל תשכח clearTimeout — אחרת התהליך לא יוצא עד שהטיימר נגמר.

✅ פתרון
// P24-E19
import type { Server } from "node:http";

export function gracefulShutdown(server: Server, { timeoutMs = 10_000, onClose = async () => {} }: { timeoutMs?: number; onClose?: () => Promise<void> } = {}) {
  let running: Promise<{ forced: boolean }> | undefined;
  let shuttingDown = false;

  async function shutdown() {
    shuttingDown = true;
    // 1. לא מקבלים חיבורים חדשים. close() מחכה שכל החיבורים הקיימים ייסגרו
    const closed = new Promise<void>((resolve) => server.close(() => resolve()));
    // 2. חיבורי keep-alive שלא באמצע בקשה — סוגרים עכשיו (מ־Node 19 close עושה את זה בעצמו; מפורש — ברור יותר)
    server.closeIdleConnections();
    // 3. בקשות שבאמצע — מקבלות עד timeoutMs לסיים. אחר כך — בכוח
    let timer: NodeJS.Timeout | undefined;
    const timedOut = new Promise<boolean>((resolve) => {
      timer = setTimeout(() => resolve(true), timeoutMs);
    });
    const forced = await Promise.race([closed.then(() => false), timedOut]);
    clearTimeout(timer);
    if (forced) {
      server.closeAllConnections();
      await closed;
    }
    // 4. רק אחרי שאין בקשות — סוגרים את מה שהן משתמשות בו (מסד, תורים)
    await onClose();
    return { forced };
  }

  return {
    // אפשר לקרוא כמה פעמים (SIGTERM ואז SIGINT) — מתבצע פעם אחת
    shutdown: () => (running ??= shutdown()),
    isShuttingDown: () => shuttingDown,
  };
}

ובשרת אמיתי:

const { shutdown } = gracefulShutdown(server, { timeoutMs: 10_000, onClose: () => pool.end() });
process.on("SIGTERM", async () => {
  const { forced } = await shutdown();
  process.exit(forced ? 1 : 0);
});

docker stop שולח SIGTERM ומחכה 10 שניות לפני SIGKILL (פרק 23) — לכן ה־timeout שלנו קצר מזה. ב־Nest זה app.enableShutdownHooks(), שכבר בפרויקט.

⚠️ טעויות נפוצות
  • process.exit(0) מיד ב־SIGTERM — כל בקשה שבאמצע נחתכת; לקוח שבאמצע תשלום מקבל שגיאת רשת (ומזל שיש Idempotency-Key).
  • לסגור את המסד לפני שהבקשות סיימו — הן נכשלות עם "pool is closed".

P24-E23 · הגבלת קצב עם שלוש תקלות 🤖 💻 כתיבת קוד 🤖 רמה 4

💡 רמז 1

מאיפה מגיע X-Forwarded-For? מי קובע מה כתוב בו?

💡 רמז 2

מתי recent.push(t) קורה — לפני או אחרי הבדיקה? ובאיזו יחידה Retry-After?

✅ פתרון
// P24-E23
import type { NextFunction, Request, Response } from "express";

export function rateLimit({ limit, windowMs, now = () => Date.now() }: { limit: number; windowMs: number; now?: () => number }) {
  const hits = new Map<string, number[]>();
  return (req: Request, res: Response, next: NextFunction) => {
    // תקלה 1: X-Forwarded-For הוא header שהלקוח שולח כרצונו — כל בקשה עם ערך אחר "עוקפת" את המגבלה.
    // req.ip בלבד; מאחורי proxy מוכר — app.set("trust proxy", 1), ו־Express מחשב את req.ip נכון
    const client = req.ip ?? "unknown";
    const t = now();
    const recent = (hits.get(client) ?? []).filter((x) => x > t - windowMs);
    if (recent.length >= limit) {
      hits.set(client, recent);
      // תקלה 3: Retry-After הוא בשניות (RFC 9110). 60000 = "חכה 16 שעות"
      res.setHeader("Retry-After", String(Math.ceil((recent[0] + windowMs - t) / 1000)));
      return res.status(429).json({ error: "יותר מדי בקשות" });
    }
    // תקלה 2: הבקשה נספרה לפני הבדיקה — גם הנדחות. לקוח שממשיך לנסות היה חסום לתמיד
    recent.push(t);
    hits.set(client, recent);
    next();
  };
}

ומתי כן X-Forwarded-For? כשהשרת מאחורי proxy שאתה שולט בו (load balancer בפרק 25). אז app.set("trust proxy", 1) — "סמוך על hop אחד" — ו־Express לוקח מה־header את הכתובת שה־proxy הוסיף, לא את מה שהלקוח כתב לפניה.

⚠️ טעויות נפוצות

// P24-E80: fixed window
export function createFixedWindow({ limit, windowMs, now }: { limit: number; windowMs: number; now: () => number }) {
  const counters = new Map<string, { start: number; count: number }>();
  return {
    hit(key: string) {
      const t = now();
      const start = Math.floor(t / windowMs) * windowMs;
      let entry = counters.get(key);
      if (!entry || entry.start !== start) {
        entry = { start, count: 0 };
        counters.set(key, entry);
      }
      const allowed = entry.count < limit;
      if (allowed) entry.count++; // בקשה שנדחתה לא נספרת
      return { allowed, remaining: Math.max(0, limit - entry.count), resetSeconds: Math.ceil((start + windowMs - t) / 1000) };
    },
    size: () => counters.size,
    sweep() {
      const start = Math.floor(now() / windowMs) * windowMs;
      let removed = 0;
      for (const [key, entry] of counters) {
        if (entry.start < start) {
          counters.delete(key);
          removed++;
        }
      }
      return removed;
    },
  };
}

שימו לב לחולשה (E05): עם limit 10 בדקה, 10 בקשות ב־12:00:59 ו־10 ב־12:01:00 — כולן עוברות. בתמורה: מספר אחד לכל לקוח, וזה כל הזיכרון.

⚠️ טעויות נפוצות

// P24-E82: כמה בקשות באמצע?
export function createInflight() {
  let active = 0;
  let waiters: Array<() => void> = [];
  const notify = () => {
    if (active !== 0) return;
    const list = waiters;
    waiters = [];
    for (const w of list) w();
  };
  return {
    start() {
      active++;
      let ended = false;
      return () => {
        if (ended) return; // finish וגם close — נספר פעם אחת
        ended = true;
        active--;
        notify();
      };
    },
    count: () => active,
    drained(timeoutMs: number): Promise<boolean> {
      if (active === 0) return Promise.resolve(true);
      return new Promise<boolean>((resolve) => {
        let done = false;
        const finish = (ok: boolean) => {
          if (done) return;
          done = true;
          clearTimeout(timer);
          resolve(ok);
        };
        const timer = setTimeout(() => finish(false), timeoutMs);
        waiters.push(() => finish(true));
      });
    },
  };
}

ב־Express: const end = inflight.start(); res.on("finish", end); res.on("close", end); — ‏close קורה גם כשהלקוח ניתק באמצע, ובלעדיו המונה היה "תקוע" על 1 לנצח. ובכיבוי: const ok = await inflight.drained(10_000) — ואם false, סוגרים בכוח.

⚠️ טעויות נפוצות

  • לא לבטל את הטיימר — התהליך מחכה עוד timeoutMs אחרי שהכול נגמר, רק בגלל טיימר שאף אחד לא צריך.

// P24-E83: סדר הכיבוי
type Deps = {
  setReady(ready: boolean): void;
  closeServer(): Promise<void>;
  closeDb(): Promise<void>;
  exit(code: number): void;
  log(msg: string): void;
  timeoutMs: number;
  delay?: (ms: number) => Promise<void>;
};

const sleep = (ms: number) => new Promise<void>((r) => setTimeout(r, ms).unref());

export function createShutdown({ setReady, closeServer, closeDb, exit, log, timeoutMs, delay = sleep }: Deps) {
  let running: Promise<void> | undefined;
  const run = async (signal: string) => {
    log(`${signal} received`);
    setReady(false); // קודם: ה־load balancer מפסיק לשלוח
    let ok = true;
    const result = await Promise.race([closeServer().then(() => "closed"), delay(timeoutMs).then(() => "timeout")]);
    if (result === "timeout") {
      log("timeout");
      ok = false;
    }
    try {
      await closeDb(); // רק אחרי שהבקשות סיימו
    } catch {
      log("db close failed");
      ok = false;
    }
    exit(ok ? 0 : 1);
  };
  return (signal: string) => (running ??= run(signal));
}

P24-E84 · ‏429 או 503? 🧠 הבנה רמה 1

💡 רמז 1

💡 רמז 2

‏Retry-After מוגדר בתקן לשניהם.

✅ פתרון

// P24-E87: הגבלה ל־login — לפי IP ולפי חשבון
type Rule = { limit: number; windowMs: number };

export function createLoginLimiter({
  now,
  perIp = { limit: 20, windowMs: 60_000 },
  perEmail = { limit: 5, windowMs: 15 * 60_000 },
}: { now: () => number; perIp?: Rule; perEmail?: Rule }) {
  const byIp = new Map<string, number[]>();
  const failures = new Map<string, number[]>();
  const norm = (email: string) => email.trim().toLowerCase();
  const recent = (map: Map<string, number[]>, key: string, windowMs: number) => {
    const t = now();
    const list = (map.get(key) ?? []).filter((x) => t - x < windowMs);
    if (list.length) map.set(key, list);
    else map.delete(key); // לא משאירים מפתחות ריקים (E79)
    return list;
  };
  const wait = (list: number[], windowMs: number) => Math.ceil((list[0] + windowMs - now()) / 1000);

  return {
    check(ip: string, email: string) {
      const ips = recent(byIp, ip, perIp.windowMs);
      if (ips.length >= perIp.limit) return { allowed: false as const, reason: "ip" as const, retryAfterSeconds: wait(ips, perIp.windowMs) };
      const fails = recent(failures, norm(email), perEmail.windowMs);
      if (fails.length >= perEmail.limit) return { allowed: false as const, reason: "email" as const, retryAfterSeconds: wait(fails, perEmail.windowMs) };
      byIp.set(ip, [...ips, now()]); // רק ניסיון שעבר נספר
      return { allowed: true as const };
    },
    fail(email: string) {
      const key = norm(email);
      failures.set(key, [...recent(failures, key, perEmail.windowMs), now()]);
    },
    succeed(email: string) {
      failures.delete(norm(email));
    },
  };
}

בשימוש: check ב־guard; אם הסיסמה שגויה — fail; אם נכונה — succeed. דנה, שהתוקף "נועל", נעולה רק 15 דקות מהכישלון הוותיק — ולא לתמיד.

⚠️ טעויות נפוצות
  • לספור לחשבון גם ניסיונות מוצלחים — משתמש שנכנס ויוצא 5 פעמים נחסם.
  • בלי נרמול — Dana@Example.com ו־dana@example.com נספרים בנפרד, והתוקף מקבל פי כמה ניסיונות.

P24-E88 · לקוח שמכבד Retry-After 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

const ra = res.headers.get("retry-after"), ואז /^\d+$/.test(ra).

💡 רמז 2

לולאה: for (let attempt = 0; ; attempt++) — יוצאים עם return res בכל מקרה שלא מחכים.

✅ פתרון
// P24-E88: לקוח שמכבד Retry-After
export async function fetchPolitely(
  fetchFn: typeof fetch,
  url: string,
  init: RequestInit,
  { sleep, maxRetries = 2, maxWaitSeconds = 60 }: { sleep: (ms: number) => Promise<void>; maxRetries?: number; maxWaitSeconds?: number },
): Promise<Response> {
  for (let attempt = 0; ; attempt++) {
    const res = await fetchFn(url, init);
    if (res.status !== 429 && res.status !== 503) return res;
    const ra = res.headers.get("retry-after");
    if (ra === null || !/^\d+$/.test(ra)) return res;
    const seconds = Number(ra);
    if (seconds > maxWaitSeconds || attempt >= maxRetries) return res;
    await res.body?.cancel(); // לא קוראים את הגוף — משחררים את החיבור
    await sleep(seconds * 1000);
  }
}

‏res.body?.cancel() — תשובה שלא קראו את הגוף שלה מחזיקה את החיבור פתוח. (‏await res.text() גם עובד.)

⚠️ טעויות נפוצות
  • sleep(Number(ra)) — 57 מילישניות במקום 57 שניות, והלקוח "מציף" את השרת בדיוק כשהוא ביקש להאט.
  • לחכות כל זמן שהשרת אומר — ‏Retry-After: 86400 והאפליקציה "תקועה" יום.
חזרהתרגול שיעור 4הבאשיעור 5 — פרויקט 2, שלב ז׳: מוכן לפרודקשן
