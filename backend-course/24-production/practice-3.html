P24-E14 · מאגר של Idempotency-Key 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 25 דק׳ידע נדרש: שיעור 3

בקובץ P24-E14.ts כתוב את IdempotencyStore (בזיכרון) — new IdempotencyStore({ ttlMs, now }):

  • begin(scope, key, fingerprint) ← {kind:"new"} (נשמר "בטיפול") · {kind:"in_progress"} · {kind:"replay", response} · {kind:"mismatch"} (אותו מפתח, טביעה אחרת — גם בזמן טיפול).
  • complete(scope, key, response) — בלי begin ← Error("אין בקשה כזו בטיפול").
  • release(scope, key) — מוחק רק אם עדיין בטיפול.
  • תוקף: רשומה בת ttlMs ומעלה — כאילו לא קיימת. sweep() מוחק אותן ומחזיר כמה; size — getter.
  • ("a:b", "c") ו־("a", "b:c") — שתי רשומות שונות.

(שדות פרטיים עם #, לא constructor(private x) — Node מריץ TypeScript בלי קומפילציה, ו־parameter properties לא נתמכות.)

P24-E15 · middleware של Idempotency-Key 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 30 דק׳ידע נדרש: שיעור 3

בקובץ P24-E15.ts כתוב idempotency({ store, scope }) ל־Express. ה־store הוא בדיוק הממשק של E14 (הבודק מביא אחד משלו).

  • רק ל־POST עם header Idempotency-Key. אחרת — next() בלי לגעת במאגר.
  • מפתח לא תקין (/^[A-Za-z0-9_-]{8,100}$/) ← 400.
  • טביעה: sha256 של [method, path, body]. scope — ברירת מחדל x-user-id או "anonymous".
  • mismatch ← 422 · in_progress ← 409 · replay ← אותו status ו־body, עם Idempotent-Replayed: true.
  • new: עוטפים את res.json. תשובה < 500 ← complete. 5xx ← release. בקשה שנגמרת בלי res.json (חריגה, חיבור שנסגר) ← release.

P24-E66 · מה עושים עם הבקשה? 🤖

💻 כתיבת קוד 🤖רמה 2⏱ 15 דק׳ידע נדרש: שיעור 3

האיור של מחזור החיים של מפתח (שיעור 3, איור 2) — כפונקציה אחת, בלי מאגר ובלי HTTP. בקובץ 24-production/starter/P24-E66.ts (יש בו רק הערה) כתוב וייצא:

export type Entry = { fingerprint: string; status: number | null; body?: unknown; createdAt: number };
export type Decision =
  | { action: "execute" }
  | { action: "replay"; status: number; body: unknown }
  | { action: "reject"; status: 409 | 422; code: string };
export function decide(entry: Entry | undefined, fp: string, now: number, ttlMs: number): Decision
export function shouldStore(status: number): boolean
  • אין רשומה, או שהיא בת ttlMs ומעלה ← execute.
  • טביעה שונה ← 422 IDEMPOTENCY_KEY_REUSED (גם כשהרשומה בטיפול).
  • status === null (בטיפול) ← 409 IDEMPOTENCY_IN_PROGRESS.
  • אחרת ← replay עם ה־status וה־body השמורים.
  • shouldStore — האם לשמור תשובה עם הסטטוס הזה: כן ל־2xx ול־4xx, לא ל־5xx.

    • id חייב להיות UUID באותיות קטנות (8-4-4-4-12 תווי hex, למשל 3f1c9a7e-0b5d-4c2a-9e11-7a6b5c4d3e2f). אחרת ← 400 INVALID_ID.
    • text — מחרוזת לא ריקה אחרי trim (נשמרת אחרי trim). אחרת ← 400 VALIDATION_ERROR.
    • לא קיים ← 201, ‏{ id, text, version: 1 }, ו־Location: /notes/:id.
    • קיים עם אותו text ← 200 עם הפתק כמו שהוא (‏version לא עולה).
    • קיים עם text אחר ← 200, ‏text חדש ו־version + 1.
  • GET /notes/:id ← 200 עם הפתק, או 404 NOT_FOUND.
  • שגיאות בצורה { error: { code, message } }. האפליקציה של הבודק כבר עושה express.json().

בזיכרון, בתוך תהליך אחד: כמה קריאות עם אותו מפתח באותו זמן צריכות לחכות לאותה ריצה. בקובץ 24-production/starter/P24-E74.ts (יש בו רק הערה) כתוב וייצא:

export function createSingleFlight<T>(): {
  run(key: string, fn: () => Promise<T>): Promise<T>;
  forget(key: string): void;
}
  • run — אם אין ריצה ולא נשמרה תוצאה למפתח ← קורא ל־fn. אם יש ריצה באמצע ← מחזיר את אותה Promise (בלי לקרוא ל־fn שוב).
  • הצלחה ← התוצאה נשמרת: run הבא עם המפתח מחזיר אותה בלי לקרוא ל־fn.
  • כישלון ← כל מי שחיכה מקבל את השגיאה, ושום דבר לא נשמר: run הבא מנסה מחדש.
  • forget(key) — מוחק תוצאה שמורה.
