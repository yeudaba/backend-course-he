שיעור 3 — Idempotency: לשלוח שוב בלי לחשוש

⏱ ~50 דקות

🎯 בשיעור הזה
  • הבעיה: הבקשה נשלחה, התשובה אבדה. בוצע או לא?
  • אילו methods בטוחים לשליחה חוזרת — ואילו לא.
  • Idempotency-Key: איך Stripe ודומיו מונעים חיוב כפול.
  • טביעת אצבע, מה שומרים, ולכמה זמן.
  • מרוץ: שתי בקשות עם אותו מפתח באותו רגע — והמסד כפתרון.

1. התשובה שאבדה

זה לא מקרה נדיר: טלפון שעובר מ־Wi-Fi לסלולר, load balancer שמנתק אחרי 30 שניות, ספריית HTTP ש"מנסה שוב אוטומטית". במשימות — מעצבן. בתשלומים, בהזמנות, בהעברות כספים — אסון.

2. idempotent

פעולה idempotent — אם מבצעים אותה פעם אחת או עשר, המצב בשרת בסוף זהה. (לא בהכרח אותה תשובה: DELETE שני מחזיר 404, אבל המשימה מחוקה בשני המקרים.)

methodidempotent?למה
GET, HEAD✔ (וגם safe)לא משנים כלום
PUT✔"המשאב הוא בדיוק זה"
DELETE✔"המשאב לא קיים"
PATCHתלוי{"status":"done"} — כן. {"balanceDelta":-100} — לא
POST✖"צור עוד אחד"

אז עם GET, PUT ו־DELETE שולחים שוב בלי לחשוב. הבעיה היא POST — ושם נכנס המפתח.

3. Idempotency-Key

הלקוח מייצר מזהה לפני השליחה הראשונה (crypto.randomUUID()), ושולח אותו ב־header בכל ניסיון. השרת זוכר: "המפתח הזה, של המשתמש הזה — כבר בוצע, וזו הייתה התשובה". בניסיון חוזר הוא מחזיר את אותה תשובה — בלי לבצע שוב. מהפרויקט (פלט אמיתי, מקוצר):

% curl -si -X POST localhost:3000/tasks -H "Authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' -H 'Idempotency-Key: 3f1c9a7e-new-task' -d '{"title":"לשלם חשבון חשמל"}'
HTTP/1.1 201 Created
Location: /tasks/1
{"id":1,"title":"לשלם חשבון חשמל","description":null,"status":"todo",…}
% # אותה בקשה, אותו מפתח:
HTTP/1.1 201 Created
Idempotent-Replayed: true
Location: /tasks/1
{"id":1,"title":"לשלם חשבון חשמל","status":"todo",…}
% # אותו מפתח, תוכן אחר:
{"error":{"code":"IDEMPOTENCY_KEY_REUSED","message":"המפתח כבר שימש לבקשה עם תוכן אחר"}}

(ושמת לב שבתשובה השנייה סדר השדות שונה? היא מגיעה מעמודת jsonb במסד — ו־PostgreSQL שומר מפתחות של jsonb בסדר משלו. לפי JSON זה אותו אובייקט בדיוק, ולקוח תקין לא תלוי בסדר. אבל אם אי פעם תשווה תשובות כמחרוזות — זו הסיבה שזה ייכשל.)

ההחלטות שבתוך האיור:

  • בהיקף של משתמש. המפתח הוא (userId, key). מפתח גלובלי = יוסי ששולח במקרה את אותו מפתח מקבל את המשימה של דנה (E22).
  • טביעת אצבע. sha256 של גוף הבקשה (ובמקרה הכללי גם method ונתיב). אותו מפתח עם תוכן אחר הוא באג אצל הלקוח — מחזירים 422, לא את התשובה הישנה בשקט.
  • מה שומרים. תשובה סופית — 2xx וגם 4xx (שליחה חוזרת של בקשה לא תקינה תיכשל שוב בכל מקרה). לא 5xx: זה "לא הצלחנו", ובשביל ניסיון חוזר בדיוק כזה המנגנון קיים. בפרויקט: פעולה שזרקה שגיאה — release, והמפתח פנוי.
  • לכמה זמן. ניסיונות חוזרים קורים תוך שניות עד שעות. Stripe שומר 24 שעות; גם אנחנו (IDEMPOTENCY_TTL_HOURS). אחר כך המפתח "חדש".
  • חובה או רשות? בפרויקט — רשות: בלי header, POST עובד כרגיל. ב־API של תשלומים — כדאי לחייב (E24).

4. המרוץ

"נבדוק אם המפתח קיים, ואם לא — נבצע ונשמור". נשמע נכון. אבל ספריית HTTP שולחת שוב אחרי timeout קצר — בזמן שהבקשה הראשונה עדיין רצה. שתיהן בודקות, שתיהן לא מוצאות, ושתיהן מבצעות. הרצנו גרסה כזו — SELECT ואז INSERT — עם 20 בקשות במקביל (פלט אמיתי):

fulfilled: 1 rejected: 19
duplicate key value violates unique constraint "idempotency_keys_pkey"
payments rows: 20

בקשה אחת הצליחה, 19 קיבלו שגיאה — ו־20 תשלומים נוצרו. ה־PRIMARY KEY על המפתח תפס את הכפילות רק בטבלת המפתחות, אחרי שהתשלום כבר נכתב.

הפתרון: קודם לתפוס את המפתח, באופן אטומי, ורק מי שתפס — מבצע. במסד זה INSERT למפתח עם אילוץ UNIQUE:

BEGIN;
INSERT INTO idempotency_keys (user_id, key, fingerprint) VALUES ($1, $2, $3)
  ON CONFLICT (user_id, key) DO NOTHING RETURNING key;
-- חזרה שורה? אתה "זכית": INSERT INTO payments ... ; UPDATE idempotency_keys SET payment_id = ...
-- לא חזרה? מישהו אחר כבר תפס — SELECT את מה שהוא שמר
COMMIT;

הקסם: כשטרנזקציה א׳ הכניסה מפתח ועוד לא עשתה COMMIT, טרנזקציה ב׳ שמנסה את אותו מפתח מחכה על האינדקס. COMMIT של א׳ ← ב׳ מקבלת DO NOTHING ורואה את התוצאה. ROLLBACK של א׳ ← ב׳ "זוכה". המסד מתאם, לא הקוד (E16). בפרויקט, עם Prisma: create על idempotencyKey; שגיאת P2002 (unique) ← מישהו כבר תפס, וקוראים את השורה שלו. בלי טרנזקציה אחת ארוכה, ולכן יש מצב "בטיפול" (409) — מה שמונע ביצוע כפול הוא שוב ה־UNIQUE.

⚠️ בזיכרון — רק לשרת אחד

Map בזיכרון (E14) מספיק לתרגול ולשרת יחיד. עם שני שרתים מאחורי load balancer, הניסיון החוזר יכול להגיע לשרת השני — שלא יודע כלום. לכן בפרויקט המפתחות במסד, ובמערכות גדולות — ב־Redis (פרק 26).
