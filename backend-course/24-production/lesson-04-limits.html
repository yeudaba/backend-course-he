שיעור 4 — הגבלת קצב וכיבוי מסודר

⏱ ~45 דקות

🎯 בשיעור הזה
  • למה מגבילים קצב, ואת מי.
  • שלושה אלגוריתמים: fixed window, sliding window, token bucket.
  • 429 נכון: Retry-After ו־RateLimit-*.
  • "מי הלקוח": req.ip, proxies ו־trust proxy.
  • כיבוי מסודר: SIGTERM, לסיים בקשות, ורק אז לסגור את המסד.

1. למה להגביל

POST /auth/login בלי הגבלה: סקריפט מנסה רשימה של מיליון סיסמאות נפוצות, בכמה מאות בקשות בשנייה. bcrypt מאט כל ניסיון (פרק 21) — אבל גם תופס את המעבד, ושרת שעסוק ב־bcrypt בשביל תוקף לא עונה למשתמשים אמיתיים. ובלי תוקף בכלל: באג ב־frontend שקורא ל־API בלולאה. הגבלת קצב (rate limiting) — "לקוח X: עד N בקשות בפרק זמן; מעבר לזה ← 429 Too Many Requests".

2. שלוש דרכים לספור

בפרויקט — sliding window על register ו־login: 10 ניסיונות בדקה לכל IP (AUTH_RATE_LIMIT_PER_MINUTE). קל להסביר, קשיח, ומספר הבקשות קטן — אז לזכור זמן לכל אחת זה זול. ב־API ציבורי, שבו אפליקציה טוענת מסך ושולחת 8 בקשות בבת אחת — token bucket (E17).

3. 429 שלקוח יכול לעבוד איתו

מהפרויקט — הרשמה, ואחריה 9 ניסיונות כניסה עם סיסמה שגויה; העשירי (עם הסיסמה הנכונה!) נחסם (פלט אמיתי, מקוצר):

% curl -si -X POST localhost:3000/auth/login -H 'content-type: application/json' \
  -d '{"email":"dana@example.com","password":"long-password-1"}'
HTTP/1.1 429 Too Many Requests
X-Request-Id: bc6e7d69-7b69-464f-a4ec-1ee60f321598
Retry-After: 57
RateLimit-Limit: 10
RateLimit-Remaining: 0
RateLimit-Reset: 57
{"error":{"code":"TOO_MANY_REQUESTS","message":"יותר מדי ניסיונות. נסה שוב בעוד 57 שניות"}}
  • Retry-After — בשניות (תקן HTTP). לקוח טוב מחכה בדיוק את זה. מילישניות כאן = "חכה 16 שעות" (E23).
  • RateLimit-Limit / -Remaining / -Reset — גם בתשובות מוצלחות: הלקוח רואה שהוא מתקרב, ומאט לפני שהוא נחסם. (טיוטת תקן של IETF; GitHub שולח X-RateLimit-*.)
  • בקשה שנדחתה לא נספרת — אחרת לקוח שמנסה שוב כל שנייה לא ייצא מהחסימה לעולם.

4. מי הלקוח?

בלי משתמש מחובר (login!) — כתובת ה־IP: req.ip. אבל כשהשרת מאחורי proxy (nginx, load balancer של הענן), כל הבקשות מגיעות מה־proxy — וכל העולם הוא "לקוח אחד", שנחסם אחרי 10 בקשות. ה־proxy מוסיף header: X-Forwarded-For: <הכתובת האמיתית>.

הפיתוי: req.get("x-forwarded-for"). הבעיה: זה header — הלקוח יכול לשלוח אותו בעצמו, עם כתובת אחרת בכל בקשה, ולעקוף את ההגבלה לגמרי (E23). הדרך הנכונה: app.set("trust proxy", 1) — "יש בדיוק proxy אחד שאני סומך עליו". Express לוקח מה־header רק את מה שה־proxy הוסיף, ומעדכן את req.ip. בפרויקט: TRUST_PROXY ב־env — כבוי כברירת מחדל, ונדליק אותו בפריסה (פרק 25).

⚠️ בזיכרון — רק לשרת אחד

המונים ב־Map. שלושה שרתים = כל אחד סופר לבד, והמגבלה האמיתית פי 3. ושרת שעושה restart — מתאפס. בשביל מגבלה משותפת — Redis (פרק 26). ולקוחות שנעלמו צריך לנקות, אחרת ה־Map רק גדל.

5. כיבוי מסודר

deploy חדש, הגדלה או הקטנה של מספר השרתים, docker compose down — כולם שולחים לתהליך SIGTERM: "סיים יפה". אחרי זמן קצוב (10 שניות ב־Docker) — SIGKILL, בלי לשאול. בזמן הזה צריך:

  1. להפסיק לקבל חיבורים חדשים (ולהגיד ל־load balancer — /ready מחזיר 503).
  2. לסגור חיבורי keep-alive שלא באמצע בקשה.
  3. לחכות שהבקשות שבאמצע יסתיימו — עם גבול זמן.
  4. רק אז — לסגור את המסד, ולצאת.
import http from "node:http";

const server = http.createServer((req, res) => {
  console.log("server: start", req.url);
  setTimeout(() => res.end("ok"), 300); // "עבודה" של 300ms
});
await new Promise<void>((r) => server.listen(0, "127.0.0.1", r));
const url = `http://127.0.0.1:${(server.address() as { port: number }).port}`;

const slow = fetch(url + "/slow").then(async (r) => console.log("client: got", r.status, await r.text()));
await new Promise((r) => setTimeout(r, 50));

console.log("SIGTERM → stop accepting");
const closed = new Promise((r) => server.close(r)); // מחכה שכל החיבורים ייסגרו
server.closeIdleConnections();
await fetch(url + "/new").catch((e) => console.log("client: new request →", e.cause?.code));
await slow;
await closed;
console.log("server closed → now close the DB, exit 0");
server: start /slow
SIGTERM → stop accepting
client: new request → ECONNREFUSED
client: got 200 ok
server closed → now close the DB, exit 0

הבקשה שבאמצע קיבלה את התשובה שלה; חדשה — נדחתה; והשרת נסגר רק אחרי. (מ־Node 19, server.close() סוגר בעצמו גם חיבורי keep-alive פנויים; closeIdleConnections() כאן — כדי שיהיה מפורש.) מה שחסר: בקשה שלא נגמרת לעולם תשאיר את השרת פתוח עד ה־SIGKILL. E19 משלים: גבול זמן, סגירה בכוח, ו־onClose.

ב־Nest: app.enableShutdownHooks() (בפרויקט מ־main.ts) מאזין ל־SIGTERM וקורא ל־app.close(). אבל הסדר מפתיע — בדקנו בניסוי: אפליקציה עם בקשה של 300ms באמצע, SIGTERM, ומסד שנסגר ב־hook (פלט אמיתי):

המסד נסגר ב־onModuleDestroyהמסד נסגר ב־onApplicationShutdown

Nest מפעיל את onModuleDestroy לפני שהוא סוגר את שרת ה־HTTP, ואת onApplicationShutdown — אחרי. אז מי שסוגר את המסד ב־onModuleDestroy (כמו ה־PrismaService שלנו עד עכשיו, וכמו הרבה מדריכים) — חותך בקשות באמצע. בפרויקט עברנו ל־onApplicationShutdown. ובגלל CMD בצורת מערך ב־Dockerfile (פרק 23), ה־SIGTERM באמת מגיע ל־Node.
