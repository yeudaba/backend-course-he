שיעור 4 — GitHub: push, Pull Request וסודות

⏱ ~40 דקות

🎯 בשיעור הזה
  • להעלות פרויקט ל־GitHub: remote, push.
  • לעבוד מול השרת: pull, clone.
  • זרימת עבודה עם Pull Request — כמו בחברה.
  • סודות: למה לא בקוד, ומה עושים אם זה קרה.

1. Git מול GitHub

Git הוא הכלי שרץ אצלך במחשב. GitHub הוא אתר ששומר עותק של המאגר בענן (remote), עם ממשק לצפייה בקוד, Pull Requests, ובהמשך — הרצת בדיקות אוטומטית (פרק 25). יש חלופות (GitLab, Bitbucket) — העקרונות זהים.

2. 👣 העלאת פרויקט 1

מומלץ לתת לפרויקט תיקייה משלו מחוץ לתיקיית הקורס: העתק את 08p-project-expenses/starter/expenses-cli אל ~/dev/expenses-cli (ב־Finder), ופתח אותה ב־VS Code.

% cd ~/dev/expenses-cli
% git init
% printf "node_modules/\n.env\n.DS_Store\nexpenses.json\n" > .gitignore
% git add .
% git status
% git commit -m "Initial commit: expenses CLI"

(expenses.json ב־.gitignore — הנתונים האישיים שלך לא חלק מהקוד. ובדוק את git status לפני ה־commit: רק הקבצים שאתה מצפה להם.)

  1. ב־GitHub: + (למעלה) ← New repository. שם: expenses-cli. Public. אל תסמן "Add a README" (כבר יש לך — אחרת יהיו שתי היסטוריות שצריך לאחד). Create repository.
  2. GitHub מציג פקודות. השתמש באלה של "…or push an existing repository from the command line":
% git remote add origin https://github.com/YOUR-USER/expenses-cli.git
% git push -u origin main
Enumerating objects: 8, done.
...
To https://github.com/YOUR-USER/expenses-cli.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.

-u קושר את main המקומי ל־origin/main, כך שבפעם הבאה מספיק git push. אם נפתח חלון התחברות של VS Code/GitHub — אשר. רענן את עמוד המאגר: הקוד וה־README מוצגים.

3. clone ו־pull

% cd ~/dev
% git clone https://github.com/YOUR-USER/expenses-cli.git expenses-copy
% cd expenses-copy && git log --oneline

clone מוריד מאגר שלם עם כל ההיסטוריה (כך תתחיל בכל עבודה חדשה: clone לפרויקט של החברה). git pull מושך commits חדשים שמישהו אחר דחף — תעשה את זה בתחילת כל יום עבודה.

4. זרימת עבודה עם Pull Request

  1. git switch -c feature/edit-command — ענף למשימה.
  2. עבודה + commits קטנים.
  3. git push -u origin feature/edit-command — הענף עולה ל־GitHub.
  4. ב־GitHub יופיע באנר Compare & pull request. כתוב כותרת ותיאור: מה עשית, למה, ואיך בודקים.
  5. סקירת קוד (code review): בחברה — חבר צוות קורא, מעיר הערות על שורות, ומאשר. אצלך — עבור בעצמך על לשונית "Files changed" כאילו אתה הסוקר. (זה תרגיל מצוין, ואני יכול לסקור לך PR אם תשלח קישור.)
  6. Merge pull request ← ואז אצלך: git switch main ו־git pull.

למה לא ישר ל־main? כי ב־PR רואים בדיוק מה משתנה, יש מקום לדיון, ובהמשך הקורס — בדיקות אוטומטיות ירוצו על כל PR לפני המיזוג (פרק 25).

5. 🔐 סודות

כלל ברזל: סודות לא נכנסים ל־Git

סיסמאות, מפתחות API, כתובות מסד עם סיסמה — לעולם לא בקוד ולא ב־commit. בוטים סורקים את GitHub ומוצאים מפתחות תוך דקות מרגע הדחיפה. בפרק 13 נלמד לשמור אותם ב־.env (שנמצא ב־.gitignore).

ואם זה קרה? מחיקה של הסוד מהקוד ו־commit חדש לא מספיקה — הוא עדיין בהיסטוריה, וכל מי שעושה clone יכול למצוא אותו (git log -p). הצעדים הנכונים, לפי הסדר:

  1. לבטל את הסוד מיד (revoke/rotate) — אצל ספק השירות: ליצור מפתח חדש, ולמחוק את הישן. מרגע זה הסוד שדלף חסר ערך. זה הצעד החשוב ביותר.
  2. להעביר את הערך ל־.env ולהוסיף אותו ל־.gitignore.
  3. לדווח (בחברה — לראש הצוות/אבטחה). זה קורה לכולם; להסתיר זה הדבר הגרוע.
  4. (ניקוי ההיסטוריה עצמה אפשרי בכלים מתקדמים, אבל הוא משני — הסוד כבר נחשף.)
💼 בעולם העבודה

מראיינים מסתכלים על ה־GitHub שלך: האם יש README? האם ההיסטוריה עם הודעות ברורות, או commit אחד ענק "upload project"? האם יש node_modules במאגר (סימן רע)? ושאלות ראיון נפוצות: "מה ההבדל בין merge ל־rebase?" (rebase — "מעביר" את ה־commits שלך לסוף הענף השני, להיסטוריה ישרה; שווה לקרוא עליו אחרי הקורס), "איך פותרים conflict?", "מה עושים אם דחפת סיסמה?".
