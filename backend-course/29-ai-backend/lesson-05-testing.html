2. לקוח מדומה

כל הבודקים בפרק עובדים כך (בגרסה מקוצרת של tests/_claude.mjs): לקוח אמיתי של ה־SDK, עם fetch שלא יוצא לרשת. הקוד שלך לא יודע שזה מדומה; הבדיקה רואה בדיוק מה נשלח, ומחליטה מה לענות — כולל תקלות:

export function fakeClaude(respond) {
  const requests = [];
  const client = new Anthropic({
    apiKey: "sk-test-fake",
    maxRetries: 0, // בבדיקות — לא לחכות ל־backoff
    fetch: async (url, init) => {
      const body = JSON.parse(init.body);
      requests.push({ url: String(url), body });
      const r = await respond(body, requests.length - 1); // הודעה, או { error: 529 }
      if (r.error) return new Response(JSON.stringify({ type: "error", error: { type: "overloaded_error", message: "fake" } }), { status: r.error });
      return Response.json(r);
    },
  });
  return { client, bodies: () => requests.map((r) => r.body) };
}

// בבדיקה:
const { client, bodies } = fakeClaude((body, i) => (i === 0 ? { error: 529 } : message("from fallback", { model: body.model })));
const r = await createWithFallback(client, params, "claude-sonnet-5-5");
assert.deepEqual(bodies().map((b) => b.model), ["claude-opus-5-5", "claude-sonnet-5-5"]);

למה דרך fetch ולא mock של client.messages.create? כי ככה עובר גם הקוד של ה־SDK: הסריאליזציה, פענוח התשובה, ה־parse של structured output, וסוגי השגיאות (InternalServerError אמיתי עם status). mock של המתודה בודק את מה שחשבת שה־SDK עושה; זה בודק את מה שהוא עושה. (ב־Nest — אותו רעיון עם DI, פרק 22: ה־Anthropic מגיע כ־provider, ובבדיקה מחליפים אותו במדומה.)

3. evals

שינית את ה־prompt של הסיווג, והוא "נראה טוב יותר" על שלוש דוגמאות. האם הוא באמת טוב יותר? eval עונה במספר: 30–50 מקרים אמיתיים (מהלוגים, בלי מידע אישי), עם בדיקה לכל אחד, ומריצים את שתי הגרסאות:

// הדגמה של המבנה — כאן ה"מודל" הוא שתי פונקציות מדומות, כדי שהפלט יהיה קבוע
type Case = { name: string; input: string; expected: string };
const cases: Case[] = [
  { name: "איפה החבילה", input: "ההזמנה שלי עוד לא הגיעה", expected: "order_status" },
  { name: "החזר", input: "המטחנה שבורה, אני רוצה את הכסף בחזרה", expected: "refund" },
  { name: "שאלה", input: "המטחנה מתאימה לאספרסו?", expected: "product_question" },
  { name: "כועס", input: "שירות גרוע, אף אחד לא עונה!!!", expected: "complaint" },
  { name: "החזר בעקיפין", input: "קיבלתי צבע לא נכון, מה עושים?", expected: "refund" },
];
const promptV1 = async (t: string) => (/כסף|החזר/.test(t) ? "refund" : /הגיע|חבילה/.test(t) ? "order_status" : "product_question");
const promptV2 = async (t: string) => (/כסף|החזר|לא נכון|שבור/.test(t) ? "refund" : /הגיע|חבילה/.test(t) ? "order_status" : /!!|גרוע/.test(t) ? "complaint" : "product_question");

for (const [label, fn] of [["v1", promptV1], ["v2", promptV2]] as const) {
  const results = await Promise.all(cases.map(async (c) => ({ c, got: await fn(c.input) })));
  const failed = results.filter((r) => r.got !== r.c.expected);
  console.log(`${label}: ${cases.length - failed.length}/${cases.length}`, failed.map((f) => `✗ ${f.c.name} (${f.got})`).join(" "));
}
v1: 3/5 ✗ כועס (product_question) ✗ החזר בעקיפין (product_question)
v2: 5/5

בעולם האמיתי, fn קורא למודל (עם מפתח, בעלות של כמה סנטים להרצה), והבדיקה לתשובות חופשיות לפעמים היא עצמה מודל — "שופט" שמדרג לפי קריטריונים. E19 בונה את ה־runner: מקביליות מוגבלת, תוצאות בסדר, וסיבה לכל כישלון. וזה הכלי שעונה על "אפשר לעבור למודל זול יותר בנתיב הזה?" — לא תחושה, מספר.

4. workflow, לא סוכן

"סוכן" — מודל שמקבל מטרה וכלים, ומחליט בעצמו מה לעשות ובאיזה סדר — מתאים למשימות פתוחות באמת, שבהן טעויות נתפסות (כמו כלי תכנות שמריץ בדיקות). לרוב הפיצ׳רים בשרת מתאים workflow: הקוד מחזיק את הזרימה, והמודל עושה צעדים מוגדרים (E24):

  1. סיווג מובנה (structured output).
  2. כללים בקוד: תלונה, החזר מעל 500 ש״ח, ביטחון נמוך ← בן אדם. בלי קריאה נוספת.
  3. רק אז — טיוטת תשובה, שנציג מאשר.

כל צעד נבדק לבד, ההחלטות על כסף בקוד (וב־unit tests), והעלות צפויה: לכל היותר שתי קריאות לפנייה.

5. RAG בקטן

"כמה זמן אחריות על מטחנה?" — התשובה במסמכי החנות, לא ב"ידע הכללי" של המודל. RAG: שולפים את המסמכים הרלוונטיים, שולחים אותם עם השאלה, ודורשים תשובה מתוכם — עם מקורות (E25):

  • שליפה — בתרגיל, ספירת מילים משותפות. בפרודקשן: חיפוש full-text של PostgreSQL, או embeddings עם pgvector. אין מסמך רלוונטי ← "לא מצאתי", בלי לקרוא למודל בכלל (חינם, ובלי סיכוי להמצאה).
  • הקשר — רק המסמכים שנשלפו, בתגיות עם id. לא "את כל המסמכים כי יש מקום" — יקר, איטי, ומגדיל את הסיכוי שמסמך פנימי ידלוף לתשובה.
  • מקורות — המודל מחזיר אילו מסמכים שימשו, והקוד בודק שהם באמת נשלחו. מקור שלא נשלח = המצאה ← לא מציגים.

💼 בעולם העבודה

בצוותים שמשלבים מודלים, רוב העבודה היא Backend רגיל: ולידציה, הרשאות, תורים, cache, לוגים, בדיקות — סביב קופסה שאי אפשר לסמוך עליה עד הסוף. שאלות ראיון שתשמע: "איך מונעים מהמודל לעשות משהו שהמשתמש לא מורשה?", "איך יודעים ששינוי ב־prompt לא קלקל?", "איך שולטים בעלות?", "מה עושים כשהספק נופל?". יש לך עכשיו תשובה לכל אחת — עם קוד שבדקת.
