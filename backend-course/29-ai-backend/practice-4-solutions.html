P29-E72 · ‏streaming, בקשה רגילה, או תור 🧠 הבנה רמה 1

streaming עוזר רק כשמישהו מסתכל על המסך ומחכה לטקסט ארוך.

💡 רמז 2

Message Batches: אסינכרוני, עד שעות, בחצי מחיר.

✅ פתרון
  1. streaming — המשתמש מתחיל לקרוא אחרי שנייה, במקום לחכות 10 שניות מול ספינר.
  2. בקשה רגילה — אבל לא בתוך בקשת ה־HTTP של הטופס: הפנייה נשמרת, והסיווג רץ ב־job (פרק 26). ‏JSON חלקי לא שימושי, אז אין טעם ב־stream.
  3. תור + Batches — אף אחד לא מחכה, חצי מחיר, ובלי להיתקע במגבלות קצב.
  4. תור + Batches — מתוזמן (cron), התוצאה נשמרת ונשלחת כשמוכנה.
  5. בקשה רגילה — שורה אחת חוזרת מהר; streaming מוסיף מורכבות (SSE, שגיאה באמצע) בלי תועלת.
⚠️ טעויות נפוצות
  • להפעיל 40,000 קריאות במקביל מתוך endpoint — מגבלות קצב, timeout של ה־HTTP, ובלי אפשרות להמשיך מאמצע.

💡 רמז 2

מה כבר נשלח ללקוח לפני שהשגיאה קרתה?

✅ פתרון
  1. ירידת שורה בטקסט שוברת את הפורמט: \n\n בתוך התשובה מסיים אירוע באמצע, והשורה הבאה (בלי data:) נזרקת. הפתרון: data: ${JSON.stringify({ text })} — ירידות שורה הופכות ל־\n בתוך המחרוזת.
  2. ‏thinking_delta הוא גם content_block_delta, ול־e.delta.text אין ערך ← "undefined" ללקוח (או החשיבה עצמה, אם ניגשים לשדה הלא נכון). בודקים e.delta.type === "text_delta".
  3. החריגה עוברת ל־Express, אבל ה־status (200) וחלק מהתשובה כבר נשלחו — אי אפשר להחזיר 500. שולחים event: error בתוך הזרם, סוגרים, והלקוח מציג "התשובה נקטעה".

⚠️ טעויות נפוצות
  • לבדוק streaming רק מול localhost בלי ה־proxy — שם הכול עובד.

P29-E74 · כמה בקשות יוצאות בפועל? 🧠 הבנה רמה 1

💡 רמז 1

כל שכבה מכפילה: 3 × 3 × 3.

💡 רמז 2

פרק 28: retry בשכבה אחת בלבד.

✅ פתרון
  1. ‏3 (frontend: ניסיון + 2) × 3 (העטיפה) × 3 (ה־SDK) = 27 בקשות.
  2. ‏27,000 בקשות לספק שכבר עמוס — retry storm שמאריך את התקלה (ומשלמים על חלקן).

⚠️ טעויות נפוצות
  • להגדיל maxRetries "ליתר ביטחון" — זה מכפיל את הסערה, לא מקטין אותה.

P29-E75 · ארבע בקשות — מי נקראת מה־cache? 🧠 הבנה רמה 1

💡 רמז 1

התאמה של תחילת הבקשה, בית אחרי בית.

💡 רמז 2

ה־cache נשמר כמה דקות, לא לנצח.

✅ פתרון
  1. כן. כל מה שמשתנה — אחרי החלק הקבוע.
  2. לא (למשתמש אחר). השם בתחילת ה־system ← prefix שונה לכל לקוח. מעבירים אותו להודעת ה־user.
  3. כן בין לקוחות, לא בין לקוח לאיש צוות. ‏tools לפני system, ורשימת כלים שונה = prefix שונה. אפשר לחיות עם זה (שני cache-ים), אבל לא עם סדר כלים שמשתנה בין בקשות.
  4. כנראה לא. ה־cache נשמר כמה דקות (ומתחדש בכל קריאה ממנו). בתנועה נמוכה — כל בקשה כותבת מחדש; זה עדיין נכון, פשוט לא חוסך.
⚠️ טעויות נפוצות
  • להסיק "ה־cache לא עובד" מבדיקה אחת אחרי הפסקה ארוכה — מודדים על תנועה אמיתית (E78).

P29-E76 · מתי cache לתשובות מזיק 🧠 הבנה רמה 1

💡 רמז 1

מה צריך להיות במפתח, ומה לא צריך להיכנס ל־cache בכלל?

💡 רמז 2

TTL הוא הבטחה: "מוכן לראות תשובה ישנה עד X".

✅ פתרון
  1. תשובה אישית — לקוח שני מקבל את ההזמנה של הראשון. לא שומרים תשובות שתלויות במשתמש (או בכלים שקוראים מידע אישי). רק שאלות כלליות.
  2. המפתח לא כולל system ומודל ← עוד שבוע של תשובות לפי המדיניות הישנה. המפתח כולל hash של מודל + system (+ גרסת prompt).
  3. מידע שמשתנה ← TTL קצר, או ביטול (invalidation) כשהמחיר מתעדכן (פרק 26). ועדיף שהמחיר יגיע מכלי/מהמסד בזמן אמת, לא מתשובה שמורה.
  4. שומרים רק end_turn עם טקסט — אחרת תשובה פגומה מוגשת לכולם שבוע.
⚠️ טעויות נפוצות
  • להוסיף cache "כי זה זול יותר" בלי לשאול לכל נתיב: האם התשובה זהה לכל המשתמשים?

P29-E12 · מודל חלופי 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

err instanceof Anthropic.APIError ו־err.status.

💡 רמז 2

למה לא על 429? כי ה־SDK כבר ניסה שוב (E05), ולרוב המגבלה היא על החשבון — לא על המודל. ו־400 ייכשל בכל מודל.

✅ פתרון
// P29-E12
import Anthropic from "@anthropic-ai/sdk";

// ה־SDK כבר מנסה שוב לבד (maxRetries, ברירת מחדל 2) על 408/409/429/5xx. מה שנשאר לנו: מה עושים אחרי שגם זה נכשל.
// עומס או תקלה אצל הספק (5xx, 529 overloaded) ← מודל חלופי. בקשה שגויה (4xx) — אותה בקשה תיכשל גם שם ← זורקים
export async function createWithFallback(
  client: Anthropic,
  params: Anthropic.MessageCreateParamsNonStreaming,
  fallbackModel: string,
): Promise<{ message: Anthropic.Message; usedFallback: boolean }> {
  try {
    return { message: await client.messages.create(params), usedFallback: false };
  } catch (err) {
    const overloaded = err instanceof Anthropic.InternalServerError || (err instanceof Anthropic.APIError && (err.status ?? 0) >= 500);
    if (!overloaded || params.model === fallbackModel) throw err;
    return { message: await client.messages.create({ ...params, model: fallbackModel }), usedFallback: true };
  }
}

(ב־Opus 5.5 יש גם fallbacks בצד השרת — למקרה של סירוב, לא של עומס. שני מנגנונים לשתי בעיות שונות.)

⚠️ טעויות נפוצות
  • fallback בלי לרשום בלוג שהוא קרה — "הכול עובד", ואף אחד לא יודע ש־30% מהבקשות רצות על מודל אחר.

P29-E15 · streaming ללקוח 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

event.type === "content_block_delta" && event.delta.type === "text_delta".

💡 רמז 2

אחרי שהתחלת לכתוב תשובה — אי אפשר להחזיר status 500. השגיאה חייבת לעבור בתוך הזרם.

✅ פתרון
// P29-E15
import type Anthropic from "@anthropic-ai/sdk";

// streaming ללקוח: האירועים של ה־SDK ← Server-Sent Events. רק טקסט יוצא החוצה (לא thinking, לא tool input),
// כל שורת data היא JSON (כך ירידות שורה בטקסט לא שוברות את הפורמט), ובסוף — event: done עם stop_reason
export async function streamToSse(events: AsyncIterable<Anthropic.MessageStreamEvent>, write: (chunk: string) => void): Promise<{ chars: number }> {
  let chars = 0;
  let stopReason: string | null = null;
  try {
    for await (const event of events) {
      if (event.type === "content_block_delta" && event.delta.type === "text_delta") {
        chars += event.delta.text.length;
        write(`data: ${JSON.stringify({ text: event.delta.text })}\n\n`);
      } else if (event.type === "message_delta") {
        stopReason = event.delta.stop_reason ?? stopReason;
      }
    }
  } catch (err) {
    // הזרם כבר התחיל — אי אפשר להחזיר 500. מודיעים בתוך הזרם, והלקוח מציג "משהו השתבש"
    write(`event: error\ndata: ${JSON.stringify({ message: "התשובה נקטעה" })}\n\n`);
    throw err;
  }
  write(`event: done\ndata: ${JSON.stringify({ stop_reason: stopReason })}\n\n`);
  return { chars };
}

ב־Nest: @Sse() מחזיר Observable, או ידנית עם res.setHeader("content-type", "text/event-stream") ו־res.write. ובדפדפן: EventSource, או fetch וקריאה של response.body. (זכור את ה־reverse proxy — nginx צריך proxy_buffering off, אחרת הוא מחזיק את כל התשובה עד הסוף.)

⚠️ טעויות נפוצות
  • לשלוח data: ${text} בלי JSON — ירידת שורה בטקסט מסיימת את האירוע באמצע.

P29-E16 · cache לתשובות 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

cache-aside מפרק 26 — אותו דפוס בדיוק.

💡 רמז 2

למה hash ולא השאלה עצמה? מפתח קצר וקבוע, ובלי מידע אישי בשמות מפתחות.

✅ פתרון
// P29-E16
import { createHash } from "node:crypto";
import type Anthropic from "@anthropic-ai/sdk";

export interface KV {
  get(key: string): Promise<string | null>;
  set(key: string, value: string, ttlSeconds: number): Promise<void>;
}

// cache לתשובות (cache-aside, פרק 26) — לשאלות שחוזרות ("מה שעות המשלוח?").
// המפתח: hash של כל מה שמשפיע על התשובה — מודל, system, והשאלה המנורמלת. שומרים רק תשובה שלמה (end_turn)
export function createCachedAsk(client: Anthropic, kv: KV, { model, system, ttlSeconds = 3600 }: { model: string; system: string; ttlSeconds?: number }) {
  const stats = { hits: 0, misses: 0 };
  async function askCached(question: string): Promise<string> {
    const normalized = question.trim().replace(/\s+/g, " ").toLowerCase();
    const key = "ai:" + createHash("sha256").update(JSON.stringify([model, system, normalized])).digest("hex");
    const hit = await kv.get(key);
    if (hit !== null) {
      stats.hits++;
      return hit;
    }
    stats.misses++;
    const response = await client.messages.create({ model, max_tokens: 2048, system, messages: [{ role: "user", content: question.trim() }] });
    const text = response.content.filter((b): b is Anthropic.TextBlock => b.type === "text").map((b) => b.text).join("");
    if (response.stop_reason === "end_turn" && text) await kv.set(key, text, ttlSeconds);
    return text;
  }
  return { ask: askCached, stats };
}

מתי זה עובד? כששאלות באמת חוזרות (FAQ, תיאורי מוצרים) והתשובה לא אישית. "איפה ההזמנה שלי" — אסור ב־cache משותף (פרק 26). וזה שונה מprompt caching של ה־API (שיעור 4): שם ה־API זוכר את תחילת ה־prompt ומוזיל את הקלט; כאן אנחנו לא קוראים בכלל.

⚠️ טעויות נפוצות
  • מפתח בלי המודל או ה־system — מחליפים prompt, והתשובות הישנות ממשיכות לצאת שעה.

P29-E17 · תקציב יומי 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

מפתח ${day}:${userId}, כש־day הוא toISOString().slice(0, 10).

💡 רמז 2

שומרים במיקרו־דולרים — מספרים שלמים (כמו אגורות בפרויקט 3).

✅ פתרון
// P29-E17
// תקציב יומי למשתמש: כל קריאה עולה כסף, ומשתמש אחד (או סקריפט) יכול לשרוף את התקציב של כולם.
// בודקים לפני הקריאה, רושמים אחרי (לפי usage אמיתי), ומתאפסים בחצות UTC
export function createBudget({ dailyUsdPerUser, now = () => Date.now() }: { dailyUsdPerUser: number; now?: () => number }) {
  const spent = new Map<string, number>(); // `${day}:${userId}` ← מיקרו־דולרים (שלמים — בלי שגיאות עיגול)
  const day = () => new Date(now()).toISOString().slice(0, 10);
  const key = (userId: string) => `${day()}:${userId}`;
  const limit = Math.round(dailyUsdPerUser * 1_000_000);
  return {
    check(userId: string): { allowed: boolean; remainingUsd: number } {
      const used = spent.get(key(userId)) ?? 0;
      return { allowed: used < limit, remainingUsd: Math.max(0, limit - used) / 1_000_000 };
    },
    record(userId: string, usd: number) {
      if (!(usd >= 0)) throw new Error("עלות לא תקינה");
      const k = key(userId);
      spent.set(k, (spent.get(k) ?? 0) + Math.round(usd * 1_000_000));
      for (const old of spent.keys()) if (!old.startsWith(day() + ":")) spent.delete(old); // לא שומרים ימים קודמים
    },
  };
}

בשרת עם כמה עותקים — המונה ב־Redis (INCRBY ו־EXPIRE, פרק 26). ובדרך כלל עוד שכבה: מגבלה של כל הארגון בקונסולה של הספק, כרשת ביטחון אחרונה.

⚠️ טעויות נפוצות
  • לבדוק תקציב רק אחרי הקריאה — הכסף כבר הוצא. בודקים לפני, רושמים אחרי.

P29-E18 · קיצור היסטוריה עם כלים 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

מהסוף להתחלה, מצטברים עד שעוברים.

💡 רמז 2

Array.isArray(m.content) && m.content.some((b) => b.type === "tool_result").

✅ פתרון
// P29-E18
import type Anthropic from "@anthropic-ai/sdk";

// קיצור היסטוריה לפי תקציב טוקנים: משאירים את הסוף. אסור לחתוך בין tool_use לבין ה־tool_result שלו
// (ה־API דוחה tool_result בלי tool_use לפניו), וההודעה הראשונה חייבת להיות user עם טקסט — לא tool_result
const hasToolResult = (m: Anthropic.MessageParam) => Array.isArray(m.content) && m.content.some((b) => b.type === "tool_result");

export function trimHistory(messages: readonly Anthropic.MessageParam[], maxTokens: number, estimate: (m: Anthropic.MessageParam) => number): Anthropic.MessageParam[] {
  let total = 0;
  let start = messages.length;
  for (let i = messages.length - 1; i >= 0; i--) {
    const cost = estimate(messages[i]);
    if (total + cost > maxTokens) break;
    total += cost;
    start = i;
  }
  // מקדמים את ההתחלה עד הודעת user "נקייה" — כך לא נשאר tool_result יתום ולא assistant ראשון
  while (start < messages.length && (messages[start].role !== "user" || hasToolResult(messages[start]))) start++;
  return messages.slice(start);
}

export function buildRequest(policyDocument: string, question: string, now: Date): Anthropic.MessageCreateParamsNonStreaming {

    max_tokens: 2048,

      // תקלה 1: התאריך היה בתוך ה־system ← כל בקשה עם prefix שונה, וה־cache לא נקרא אף פעם.

export function costUsd(usage: Anthropic.Usage, prices = { input: 4, output: 20, cacheWrite: 5, cacheRead: 0.2 }): number {
  // תקלה 3: היה (input + output) * prices.output ← הקלט חויב במחיר הפלט, ו־cache לא נספר בכלל
  return (

      usage.output_tokens * prices.output +

      (usage.cache_read_input_tokens ?? 0) * prices.cacheRead) /
    1_000_000
  );
}

// P29-E77: לסווג שגיאה של ה־API
import Anthropic from "@anthropic-ai/sdk";

type Kind = "rate_limited" | "overloaded" | "timeout" | "network" | "bad_request" | "config" | "bug";
const RETRY: Kind[] = ["rate_limited", "overloaded", "timeout", "network"];

export function classifyApiError(err: unknown) {
  let kind: Kind = "bug";
  let status: number | null = null;
  if (err instanceof Anthropic.APIConnectionTimeoutError) kind = "timeout";
  else if (err instanceof Anthropic.APIConnectionError) kind = "network";
  else if (err instanceof Anthropic.APIError && typeof err.status === "number") {
    status = err.status;
    if (status === 429) kind = "rate_limited";
    else if (status >= 500) kind = "overloaded";
    else if (status === 401 || status === 403) kind = "config";
    else kind = "bad_request";
  }
  const retryLater = RETRY.includes(kind);
  return { kind, status, retryLater, userMessage: retryLater ? "העוזר עמוס כרגע, נסה שוב בעוד דקה" : "משהו השתבש אצלנו, כבר בודקים" };
}

⚠️ טעויות נפוצות

✅ פתרון
// P29-E78: האם ה־prompt cache עובד?
type Usage = { input_tokens: number; output_tokens: number; cache_creation_input_tokens?: number | null; cache_read_input_tokens?: number | null };

const n = (x?: number | null) => x ?? 0;

export function cacheReport(usages: Usage[]) {
  const writes = usages.filter((u) => n(u.cache_creation_input_tokens) > 0).length;
  const reads = usages.filter((u) => n(u.cache_read_input_tokens) > 0).length;
  const readTokens = usages.reduce((s, u) => s + n(u.cache_read_input_tokens), 0);
  const allInput = usages.reduce((s, u) => s + u.input_tokens + n(u.cache_creation_input_tokens) + n(u.cache_read_input_tokens), 0);
  const cachedShare = allInput === 0 ? 0 : Math.round((readTokens / allInput) * 100) / 100;
  let verdict: "no_cache" | "warming_up" | "never_read" | "working";
  if (reads > 0) verdict = "working";
  else if (writes === 0) verdict = "no_cache";
  else verdict = usages.length < 2 ? "warming_up" : "never_read";
  return { calls: usages.length, writes, reads, cachedShare, verdict };
}

‏never_read עם כתיבה בכל קריאה הוא המצב הכי יקר: משלמים תוספת על כתיבה, ולא נהנים אף פעם.

⚠️ טעויות נפוצות
  • לחלק ב־input_tokens בלבד — ב־API, ‏input_tokens הוא רק הקלט שלא מה־cache.

// P29-E82: תקציב יומי ב־Redis
import type { Redis } from "ioredis";

const MICRO = 1_000_000;

export function createRedisBudget(redis: Redis, opts: { dailyUsdPerUser: number; now?: () => number }) {
  const now = opts.now ?? Date.now;
  const capMicro = Math.round(opts.dailyUsdPerUser * MICRO);
  const key = (userId: string) => `ai:budget:${userId}:${new Date(now()).toISOString().slice(0, 10)}`;

  return {
    async check(userId: string) {
      const spent = Number((await redis.get(key(userId))) ?? 0);
      return { allowed: spent < capMicro, remainingUsd: Math.max(0, capMicro - spent) / MICRO };
    },
    async record(userId: string, usd: number) {
      if (!Number.isFinite(usd) || usd < 0) throw new RangeError(`usd לא תקין: ${usd}`);
      const k = key(userId);
      await redis.incrby(k, Math.round(usd * MICRO));
      await redis.expire(k, 2 * 24 * 3600);
    },
  };
}

אפשר לשלב את שתי הפקודות ב־multi() — כאן גם בלי זה אין נזק: ‏EXPIRE שלא רץ פעם אחת יתוקן בקריאה הבאה.

⚠️ טעויות נפוצות
  • ‏INCRBYFLOAT בדולרים — אותן שגיאות עיגול של float, רק ב־Redis.
  • לחשב את התאריך פעם אחת ביצירה — אחרי חצות כולם ממשיכים לכתוב למפתח של אתמול.

// P29-E83: GET /ask/stream ב־Express
import express from "express";
import { z } from "zod";

const Query = z.object({ q: z.string().trim().min(1).max(500) });

export function sseApp(streamText: (question: string, signal: AbortSignal) => AsyncIterable<string>) {
  const app = express();
  app.get("/ask/stream", async (req, res) => {
    const parsed = Query.safeParse(req.query);
    if (!parsed.success) return res.status(400).json({ error: "q: 1–500 תווים" });

    res.setHeader("Content-Type", "text/event-stream");
    res.setHeader("Cache-Control", "no-cache");
    res.setHeader("X-Accel-Buffering", "no");
    res.flushHeaders();

    const ac = new AbortController();
    res.on("close", () => {
      if (!res.writableEnded) ac.abort();
    });

    try {
      for await (const text of streamText(parsed.data.q, ac.signal)) {
        if (ac.signal.aborted) break;
        res.write(`data: ${JSON.stringify({ text })}\n\n`);
      }
      if (!ac.signal.aborted) res.write("event: done\ndata: {}\n\n");
    } catch {
      if (!ac.signal.aborted) res.write(`event: error\ndata: ${JSON.stringify({ error: "ai_failed" })}\n\n`);
    }
    res.end();
  });
  return app;
}

עם ה־SDK: ‏client.messages.stream(params, { signal }) — ביטול ה־signal סוגר את החיבור לספק, והמודל מפסיק לייצר (ולחייב).

⚠️ טעויות נפוצות
  • ‏req.on("close") — ב־Node החדש הוא נורה כשגוף הבקשה נקרא, לא כשהלקוח התנתק. מאזינים ל־res.
  • ‏res.status(500) ב־catch — ה־headers כבר נשלחו; Express יזרוק "Cannot set headers after they are sent".
