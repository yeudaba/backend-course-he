P18-E04 · index או לא?

🧠 הבנהרמה 1⏱ 10 דק׳ידע נדרש: שיעור 3

טבלת orders עם 10 מיליון שורות. לכל שאילתה — האם index יעזור, ואיזה?

  1. WHERE customer_id = $1 ORDER BY created_at DESC LIMIT 20
  2. WHERE status = 'shipped' (95% מההזמנות)
  3. WHERE lower(coupon_code) = $1
  4. WHERE note LIKE '%gift%'
  5. WHERE created_at >= now() - interval '1 day'
  6. טבלת countries עם 200 שורות, WHERE code = 'IL'

P18-E55 · ‏index על שתי עמודות — מתי הוא עוזר?

🧠 הבנהרמה 2⏱ 10 דק׳ידע נדרש: שיעור 3

יש index על (status, created_at) בלבד. לכל אחת מארבע השאילתות — האם התוכנית תשתמש בו? נחש לפני שאתה מסתכל.

CREATE INDEX big_orders_status_created_idx ON big_orders (status, created_at);
EXPLAIN (COSTS OFF) SELECT id FROM big_orders WHERE status = 'pending' AND created_at >= '2025-12-20';
EXPLAIN (COSTS OFF) SELECT id FROM big_orders WHERE status = 'cancelled';
EXPLAIN (COSTS OFF) SELECT id FROM big_orders WHERE created_at >= '2025-12-20';
EXPLAIN (COSTS OFF) SELECT id FROM big_orders WHERE status = 'pending' ORDER BY created_at DESC LIMIT 5;

P18-E56 · ‏index שהשאילתה "מסתירה" ממנו

🧠 הבנהרמה 2⏱ 10 דק׳ידע נדרש: שיעור 3

יש index על customer_id. שלוש שאילתות מחפשות את אותו לקוח. לאיזו מהן המסד ישתמש ב־index?

CREATE INDEX big_orders_customer_id_idx ON big_orders (customer_id);
EXPLAIN (COSTS OFF) SELECT id FROM big_orders WHERE customer_id = 42;
EXPLAIN (COSTS OFF) SELECT id FROM big_orders WHERE customer_id + 0 = 42;
EXPLAIN (COSTS OFF) SELECT id FROM big_orders WHERE customer_id::text = '42';

P18-E57 · איזה indexes כבר יש?

🧠 הבנהרמה 1⏱ 5 דק׳ידע נדרש: שיעור 3

לא יצרנו אף index על shop_orders ו־shop_order_lines. מה תחזיר השאילתה? מאיפה הגיע כל אחד — ואיזה index חסר לפי השיעור?

SELECT tablename, indexname
FROM pg_indexes
WHERE schemaname = current_schema() AND tablename IN ('shop_orders', 'shop_order_lines')
ORDER BY tablename, indexname;

(זכור את ההגדרות: shop_orders — ‏id מפתח ראשי ו־idempotency_key ... UNIQUE; ‏shop_order_lines — ‏PRIMARY KEY (order_id, product_id) ו־FK ל־catalog.)

P18-E58 · למה המסד מתעלם מה־index?

🧠 הבנהרמה 2⏱ 10 דק׳ידע נדרש: שיעור 3

שתי שאילתות על מפתח ראשי — כלומר יש index. מה תהיה כל תוכנית? איך יכול להיות שהמסד בוחר לא להשתמש ב־index שקיים?

EXPLAIN (COSTS OFF) SELECT owner FROM accounts WHERE id = 2;
EXPLAIN (COSTS OFF) SELECT id FROM big_orders WHERE id > 1000;
EXPLAIN (COSTS OFF) SELECT id FROM big_orders WHERE id > 199000;

P18-E59 · באיזה סדר העמודות?

🧠 הבנהרמה 1⏱ 10 דק׳ידע נדרש: שיעור 3

"ההזמנות של לקוח X מהחודש האחרון": WHERE customer_id = $1 AND created_at >= $2. שתי הצעות:

  1. CREATE INDEX ON big_orders (customer_id, created_at);
  2. CREATE INDEX ON big_orders (created_at, customer_id);

איזה עדיף לשאילתה הזו, ולמה? ואיזה מהם עוזר גם ל־WHERE customer_id = $1 לבד?

P18-E22 · ה־index שלא בשימוש 🤖

P18-E63 · חיפוש "מכיל" ב־endpoint

🧠 הבנהרמה 2⏱ 10 דק׳ידע נדרש: פרק 15, פרק 16, שיעור 3

ל־GET /customers?q=... (פרק 15) יש שאילתה עם ILIKE (פרק 16). הטבלה גדלה למיליון לקוחות, ויש index על full_name. מה התוכנית של כל אחת?

CREATE INDEX people_full_name_idx ON people (full_name);
EXPLAIN (COSTS OFF) SELECT id FROM people WHERE full_name = 'Customer #4242';
EXPLAIN (COSTS OFF) SELECT id FROM people WHERE full_name ILIKE '%4242%';

ומה אפשר לעשות כדי שהחיפוש יהיה מהיר?

🔗 איך זה מתחבר: query string מפרק 15 ו־ILIKE מפרק 16 — והשיעור: LIKE '%...' בטבלת ה"לא יעזור".

P18-E64 · ‏JOIN ו־index על ה־FK

🧠 הבנהרמה 2⏱ 10 דק׳ידע נדרש: פרק 17, שיעור 3

"ההזמנות של הלקוח עם השם X" — JOIN מפרק 17 בין people ל־big_orders. מה התוכנית לפני ה־index ואחריו? באיזה צד של ה־JOIN ה־index חשוב?

EXPLAIN (COSTS OFF)
SELECT o.id, o.total FROM people p JOIN big_orders o ON o.customer_id = p.id
WHERE p.id = 42;

CREATE INDEX big_orders_customer_id_idx ON big_orders (customer_id);

EXPLAIN (COSTS OFF)
SELECT o.id, o.total FROM people p JOIN big_orders o ON o.customer_id = p.id
WHERE p.id = 42;

🔗 איך זה מתחבר: JOIN על FK מפרק 17 — והשיעור: PostgreSQL לא יוצר index ל־FK אוטומטית.

P18-E65 · ‏"עמוד 1 מתוך 10,000" — כמה עולה המספר?

🧠 הבנהרמה 2⏱ 10 דק׳ידע נדרש: פרק 16, שיעור 3

כל טעינה של רשימת ההזמנות מציגה "עמוד 1 מתוך N" — ולשם כך מריצה SELECT COUNT(*) FROM big_orders. מה התוכנית? האם index יעזור? הצע חלופה לממשק.

EXPLAIN (COSTS OFF) SELECT COUNT(*) FROM big_orders;
EXPLAIN (COSTS OFF) SELECT COUNT(*) FROM big_orders WHERE customer_id = 42;
SELECT reltuples::bigint AS estimate FROM pg_class WHERE oid = 'big_orders'::regclass;

🔗 איך זה מתחבר: COUNT ו־LIMIT/OFFSET מפרק 16 — והשיעור: מה index יכול ומה לא.

P18-E66 · האם השאילתה משתמשת ב־index? — בקוד 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 25 דק׳ידע נדרש: פרק 7, פרק 13, פרק 16, שיעור 3

כלי לבדיקות אוטומטיות: "השאילתה הזו לא סורקת את הטבלה". ‏EXPLAIN (FORMAT JSON) מחזיר את התוכנית כעץ: כל צומת עם "Node Type", ולפעמים "Relation Name" ו־"Index Name", וילדים ב־"Plans". בקובץ 18-consistency/starter/P18-E66.ts כתוב וייצא:

export type PlanSummary = { nodes: string[]; seqScans: string[]; indexes: string[] };
export async function planSummary(pool: Pool, sql: string, params?: unknown[]): Promise<PlanSummary>
  • מריצה EXPLAIN (FORMAT JSON) + השאילתה (עם הפרמטרים). ה־JSON מגיע בשורה הראשונה, בעמודה "QUERY PLAN"; התוכנית — ב־[0].Plan.
  • nodes — כל ה־Node Type בעץ, לפי סדר "קודם הצומת, אחר כך הילדים שלו לפי הסדר".
  • seqScans — ה־Relation Name של כל צומת Seq Scan. ‏indexes — כל Index Name בעץ, בלי כפילויות.

📄 כותבים בקובץ 18-consistency/starter/P18-E66.ts (יש בו רק הערה), ובודקים:

% npm run check P18-E66

🔗 איך זה מתחבר: רקורסיה על אובייקטים מקוננים (פרק 7), JSON (פרק 13), ‏pool.query עם פרמטרים (פרק 16) — והשיעור: לקרוא תוכנית, הפעם בקוד.

P18-E67 · ‏"index" ממוין בזיכרון 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 25 דק׳ידע נדרש: פרק 5, פרק 6, פרק 11, שיעור 3

מה B-tree עושה, בקטן: מערך ממוין וחיפוש בינארי — במקום לעבור על הכול. בקובץ 18-consistency/starter/P18-E67.ts כתוב וייצא:

export function createIndex<T>(rows: T[], key: (row: T) => number): { eq(value: number): T[]; range(from: number, to: number): T[]; comparisons(): number }
  • בזמן היצירה — ממיינת עותק של השורות לפי key (המקור לא משתנה). בשוויון — הסדר המקורי נשמר.
  • eq(v) — כל השורות עם key === v. ‏range(from, to) — כל השורות עם from <= key < to. שתיהן לפי הסדר הממוין.
  • החיפוש — בינארי: comparisons() מחזירה כמה השוואות של מפתחות נעשו בחיפושים עד עכשיו (בלי המיון). הבודק מוודא שעל 100,000 שורות, eq עושה לכל היותר 40 השוואות (ולא 100,000).

📄 כותבים בקובץ 18-consistency/starter/P18-E67.ts (יש בו רק הערה), ובודקים:

% npm run check P18-E67

🔗 איך זה מתחבר: closures (פרק 5), ‏sort ו־slice (פרק 6), generics (פרק 11) — והשיעור: למה index מוצא 100 שורות מתוך 200,000 בכמה קפיצות.
