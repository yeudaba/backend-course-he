P18-E05 · כמה שאילתות? 🧠 הבנה רמה 1

💡 רמז 1

1 + 50 × (1 + 1 + 3).

💡 רמז 2

WHERE id = ANY($1) עם מערך, ו־JOIN בין order_items ל־products.

✅ פתרון

1 + 50 + 50 + 150 = 251 שאילתות, ברצף (כל await מחכה לקודם).

const orders = (await pool.query("SELECT * FROM orders ORDER BY id DESC LIMIT 50")).rows;
const orderIds = orders.map((o) => o.id);
const customerIds = [...new Set(orders.map((o) => o.customer_id))];
const customers = (await pool.query("SELECT * FROM customers WHERE id = ANY($1)", [customerIds])).rows;
const items = (await pool.query(
  `SELECT oi.*, p.name AS product_name, p.price AS product_price
   FROM order_items oi JOIN products p ON p.id = oi.product_id
   WHERE oi.order_id = ANY($1)`, [orderIds])).rows;
const customersById = new Map(customers.map((c) => [c.id, c]));
for (const o of orders) {
  o.customer = customersById.get(o.customer_id);
  o.items = items.filter((i) => i.order_id === o.id);
}

3 שאילתות, תמיד. (ה־filter בלולאה הוא O(n·m) — עם 50 הזמנות זה זניח; עם אלפים — Map מ־order_id לרשימה.)

⚠️ טעויות נפוצות
  • "לתקן" עם Promise.all על 250 השאילתות — פחות זמן המתנה, אבל אותו עומס על המסד, ו־pool של 10 חיבורים מתמלא.

P18-E69 · למצוא N+1 ביומן 🧠 הבנה רמה 1

💡 רמז 1

אותה שאילתה, עם פרמטר שונה, פעם לכל שורה מהשאילתה הראשונה.

💡 רמז 2

שים לב גם ל־1544 שמופיע פעמיים.

✅ פתרון

שאילתה לרשימה, ואז לולאה עם await ששולפת את שם הלקוח לכל הזמנה — N+1. ב־limit=50: ‏51 שאילתות. ולקוח שמופיע פעמיים נשלף פעמיים. אחרי תיקון — אחת משתיים:

SELECT o.id, o.total, p.full_name FROM big_orders o JOIN people p ON p.id = o.customer_id ORDER BY o.created_at DESC LIMIT 4

או שתיים (ה־id־ים בלי כפילויות, ב־ANY):

SELECT id, customer_id, total FROM big_orders ORDER BY created_at DESC LIMIT 4
SELECT id, full_name FROM people WHERE id = ANY($1)   [[1544, 1463, 1302]]

הסימן ביומן תמיד אותו סימן: "גל" של שאילתות זהות שרק הפרמטר משתנה בהן.

⚠️ טעויות נפוצות
  • "כל שאילתה לוקחת מילישנייה" — וכל אחת היא גם נסיעה ברשת ותור ב־pool. 51 קטנות איטיות מאחת בינונית.

P18-E70 · ‏OFFSET ושורה חדשה בין עמודים 🧠 הבנה רמה 2

💡 רמז 1

OFFSET 3 = "דלג על 3 הראשונות עכשיו". מי הן עכשיו?

💡 רמז 2

ה־cursor אומר "אחרי מה שכבר ראיתי" — שורה חדשה בראש לא משנה אותו.

✅ פתרון
CREATE TABLE feed (id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY, body text NOT NULL);
INSERT INTO feed (body) SELECT 'post ' || i FROM generate_series(1, 8) AS i;

SELECT id, body FROM feed ORDER BY id DESC LIMIT 3 OFFSET 0;      -- עמוד 1
INSERT INTO feed (body) VALUES ('post 9 (new)');
SELECT id, body FROM feed ORDER BY id DESC LIMIT 3 OFFSET 3;      -- עמוד 2, עם OFFSET
SELECT id, body FROM feed WHERE id < 6 ORDER BY id DESC LIMIT 3;  -- עמוד 2, עם cursor (האחרון בעמוד 1 היה 6)
CREATE TABLE
INSERT 0 8
 id |  body
----+--------
  8 | post 8
  7 | post 7
  6 | post 6
(3 rows)

INSERT 0 1
 id |  body
----+--------
  6 | post 6
  5 | post 5
  4 | post 4
(3 rows)

 id |  body
----+--------
  5 | post 5
  4 | post 4
  3 | post 3
(3 rows)

עם OFFSET, ההודעה החדשה "דחפה" הכול אחד למטה — ו־post 6 מופיע שוב בראש עמוד 2. (ובמחיקה — הפוך: שורה מדלגת ולא מוצגת אף פעם.) עם cursor — בדיוק ההמשך.

⚠️ טעויות נפוצות
  • "לתקן" עם הסרת כפילויות ב־frontend — מטפל בהוספה, לא במחיקה (שורות שנעלמות).

P18-E71 · ‏cursor בלי שובר שוויון 🧠 הבנה רמה 2

💡 רמז 1

האחרון בעמוד 1 הוא d (12:00, id 4). מה עוד יש ב־12:00?

💡 רמז 2

(a, b) < (x, y) — כמו השוואת מילים במילון: קודם a מול x; אם שווים — b מול y.

✅ פתרון
CREATE TABLE posts (id integer PRIMARY KEY, title text, created_at timestamptz);
INSERT INTO posts VALUES (1, 'a', '2026-01-01 10:00+02'), (2, 'b', '2026-01-01 11:00+02'),
  (3, 'c', '2026-01-01 12:00+02'), (4, 'd', '2026-01-01 12:00+02'), (5, 'e', '2026-01-01 13:00+02');

SELECT id, title FROM posts ORDER BY created_at DESC, id DESC LIMIT 2;           -- עמוד 1: e, d
SELECT id, title FROM posts
WHERE created_at < '2026-01-01 12:00+02'
ORDER BY created_at DESC, id DESC LIMIT 2;                                        -- עמוד 2, רק לפי זמן
SELECT id, title FROM posts
WHERE (created_at, id) < ('2026-01-01 12:00+02', 4)
ORDER BY created_at DESC, id DESC LIMIT 2;                                        -- עמוד 2, עם שובר שוויון
CREATE TABLE
INSERT 0 5
 id | title
----+-------
  5 | e
  4 | d
(2 rows)

 id | title
----+-------
  2 | b
  1 | a
(2 rows)

 id | title
----+-------
  3 | c
  2 | b
(2 rows)

"רק לפי זמן" דילג על c — היא לא "לפני 12:00", היא ב־12:00. השוואת זוגות שואלת "האם השורה באה אחרי (12:00, 4) בסדר המיון" — ו־c (12:00, 3) באה. בגלל זה ה־cursor הוא שני ערכים, וה־ORDER BY חייב לכלול את שובר השוויון. (ו־P18-E31: כל השורות של transaction אחד מקבלות אותו now() — שוויון ב־created_at נפוץ יותר משנדמה.)

⚠️ טעויות נפוצות
  • <= במקום < ב"רק לפי זמן" — עכשיו d (שכבר הוצג) חוזר. אין דרך נכונה בלי שובר שוויון.

P18-E72 · ‏ANY($1) מול IN משורשר 🧠 הבנה רמה 2

💡 רמז 1

מה יקרה ב־א׳ כש־ids ריק? וכש־ids הגיעו מה־query string?

💡 רמז 2

ב־ב׳, pg שולח מערך JavaScript כפרמטר אחד מסוג מערך של PostgreSQL.

✅ פתרון
  • א׳: (1) ids = [] ← IN () — שגיאת תחביר. (2) אם ids הגיעו מהמשתמש (?ids=1,2)%20OR%20(1=1) — SQL injection. (3) לכל אורך רשימה טקסט שאילתה אחר — המסד לא יכול למחזר תוכניות, ויומני השאילתות מתמלאים בגרסאות.
  • ב׳: טקסט שאילתה אחד תמיד, ופרמטר אחד — מערך. ריק ← אפס שורות, בלי שגיאה. אותו טקסט ל־3 ול־500 id־ים, והערכים לעולם לא הופכים לקוד.

זה מה שהשיעור השתמש בו בתיקון של N+1, ומה ש־WHERE id IN של ORMs מייצר מאחורי הקלעים.

⚠️ טעויות נפוצות
  • "ids הם מספרים, אז אין injection" — רק אם וידאת שהם מספרים (Zod). ב־ב׳ לא צריך לסמוך על זה.

P18-E73 · ‏JOIN או שתי שאילתות? 🧠 הבנה רמה 2

💡 רמז 1

JOIN של אחד־לרבים מחזיר שורה לכל הזמנה — עם כל עמודות הלקוח בכל אחת.

💡 רמז 2

20 × 100 = ?

✅ פתרון
  1. JOIN: ‏2,000 שורות, וכל bio עובר 100 פעמים — 20 × 100 × 5KB ≈ 10MB של כפילויות, רק בשביל הביו.
  2. שתי שאילתות: 20 + 2,000 שורות; כל bio פעם אחת. נסיעה אחת נוספת למסד.

כשהצד ה"אחד" צר והקשר קטן (הזמנה ← הלקוח שלה; שם, אימייל) — JOIN. כשהצד ה"אחד" רחב או שיש כמה קשרים של "רבים" (לקוח ← הזמנות וגם כתובות — JOIN של שניהם הוא מכפלה, P17-E03) — שאילתה לכל קשר. זה בדיוק מה ש־Prisma עושה עם include (פרק 19).

⚠️ טעויות נפוצות
  • "JOIN תמיד מהיר יותר כי זו שאילתה אחת" — לא כשהוא מכפיל את הנתונים שעוברים ברשת פי מאה.

P18-E17 · בלי N+1 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

JOIN — שאילתה אחת.

💡 רמז 2

SELECT o.id, o.total, p.full_name FROM big_orders o JOIN people p ON p.id = o.customer_id ORDER BY o.created_at DESC LIMIT $1

✅ פתרון
// P18-E17
import type { Pool } from "pg";

export async function latestOrdersWithCustomers(pool: Pool, limit: number) {
  const { rows } = await pool.query(
    `SELECT o.id, o.total, p.full_name
     FROM big_orders o
     JOIN people p ON p.id = o.customer_id
     ORDER BY o.created_at DESC
     LIMIT $1`,
    [limit]
  );
  return rows.map((r) => ({ id: r.id, total: Number(r.total), customerName: r.full_name }));
}
⚠️ טעויות נפוצות
  • לולאה עם await pool.query(... WHERE id = $1) לכל הזמנה — 1 + limit שאילתות.

P18-E18 · pagination עם cursor 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

WHERE id > $1 ORDER BY id LIMIT $2, עם $1 = after ?? 0.

💡 רמז 2

LIMIT limit + 1: אם חזרו יותר מ־limit — יש עוד; מחזירים רק limit.

✅ פתרון
// P18-E18
import type { Pool } from "pg";

export async function listOrders(pool: Pool, { after, limit = 20 }: { after?: number; limit?: number } = {}) {
  if (!Number.isInteger(limit) || limit < 1 || limit > 100) throw new RangeError("limit חייב להיות בין 1 ל־100");
  const { rows } = await pool.query("SELECT id, total FROM big_orders WHERE id > $1 ORDER BY id LIMIT $2", [after ?? 0, limit + 1]);
  const hasMore = rows.length > limit;
  const data = rows.slice(0, limit).map((r) => ({ id: r.id, total: Number(r.total) }));
  return { data, nextCursor: hasMore ? data[data.length - 1].id : null };
}

ה"שורה הנוספת" חוסכת COUNT על 200,000 שורות בכל עמוד. ב־API: GET /orders?after=150000&limit=20 ← { data, nextCursor: 150020 }.

⚠️ טעויות נפוצות
  • nextCursor = data.at(-1).id תמיד — בעמוד האחרון הלקוח יבקש עוד עמוד ויקבל רשימה ריקה. עובד, אבל בקשה מיותרת.

P18-E23 · 21 שאילתות לעמוד 🤖 💻 כתיבת קוד 🤖 רמה 4

💡 רמז 1

WHERE id = ANY($1), ו־GROUP BY customer_id.

💡 רמז 2

החזרה באותו סדר: Map מ־id לשורה, ואז ids.map(...).

✅ פתרון
// P18-E23: מתוקן — 2 שאילתות במקום 2 לכל לקוח
import type { Pool } from "pg";

export async function customersWithOrderCounts(pool: Pool, ids: number[]) {
  const people = await pool.query("SELECT id, full_name FROM people WHERE id = ANY($1)", [ids]);
  const counts = await pool.query("SELECT customer_id, COUNT(*)::int AS orders FROM big_orders WHERE customer_id = ANY($1) GROUP BY customer_id", [ids]);
  const byId = new Map(people.rows.map((p) => [p.id, p]));
  const countById = new Map(counts.rows.map((c) => [c.customer_id, c.orders]));
  return ids
    .filter((id) => byId.has(id))
    .map((id) => ({ id, fullName: byId.get(id).full_name, orders: countById.get(id) ?? 0 }));
}

(אפשר גם בשאילתה אחת עם LEFT JOIN ו־GROUP BY. שתיים פשוטות לקריאה — ושתיהן משתמשות ב־indexes, אם יש על customer_id.)

⚠️ טעויות נפוצות
  • countById.get(id) בלי ?? 0 — לקוח בלי הזמנות יקבל undefined.

P18-E75 · הזמנות עם השורות שלהן — שתי שאילתות 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

WHERE l.order_id = ANY($1) ORDER BY l.order_id, c.name — ואז Map של order_id ← מערך שורות.

💡 רמז 2

לסדר הסופי: [...new Set(orderIds)], ולכל id — ה־Map של ההזמנות (ודילוג אם אין).

✅ פתרון
// P18-E75: הזמנות עם השורות שלהן — שתי שאילתות
import type { Pool } from "pg";

export type OrderWithLines = { id: number; total: number; lines: { product: string; quantity: number; unitPrice: number }[] };

export async function ordersWithLines(pool: Pool, orderIds: number[]): Promise<OrderWithLines[]> {
  if (orderIds.length === 0) return [];
  const ids = [...new Set(orderIds)];
  const orders = await pool.query("SELECT id, total FROM shop_orders WHERE id = ANY($1)", [ids]);
  const lines = await pool.query(
    `SELECT l.order_id, c.name AS product, l.quantity, l.unit_price
     FROM shop_order_lines l JOIN catalog c ON c.id = l.product_id
     WHERE l.order_id = ANY($1)
     ORDER BY l.order_id, c.name`,
    [ids],
  );
  const byOrder = new Map<number, OrderWithLines["lines"]>();
  for (const l of lines.rows) {
    if (!byOrder.has(l.order_id)) byOrder.set(l.order_id, []);
    byOrder.get(l.order_id)!.push({ product: l.product, quantity: l.quantity, unitPrice: Number(l.unit_price) });
  }
  const found = new Map<number, number>(orders.rows.map((o) => [o.id, Number(o.total)]));
  return ids.filter((id) => found.has(id)).map((id) => ({ id, total: found.get(id)!, lines: byOrder.get(id) ?? [] }));
}

מספר השאילתות לא תלוי בכמות — זה כל העניין. הסדר מגיע מ־orderIds (ולא מהמסד, שמחזיר את ANY בסדר כלשהו).

⚠️ טעויות נפוצות
  • לסמוך על הסדר של ANY — המסד לא מבטיח סדר בלי ORDER BY.
  • JOIN אחד של שלוש הטבלאות — אפשרי, אבל אז צריך לקבץ שורות שטוחות (P17-E55), והזמנה בלי שורות דורשת LEFT JOIN.

P18-E76 · פיד עם cursor אטום 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

Buffer.from(cursor, "base64url").toString(), ‏split("|"), ‏new Date(...) ו־Number.isNaN(d.getTime()).

💡 רמז 2

שתי גרסאות של WHERE: עם cursor — customer_id = $1 AND (created_at, id) < ($2, $3); בלי — רק customer_id = $1.

✅ פתרון
// P18-E76: פיד עם cursor אטום
import type { Pool } from "pg";

export class AppError extends Error {
  code: string;
  constructor(code: string, message = code) {
    super(message);
    this.code = code;
  }
}

export function encodeCursor(createdAt: Date, id: number): string {
  return Buffer.from(`${createdAt.toISOString()}|${id}`).toString("base64url");
}

export function decodeCursor(cursor: string): { createdAt: Date; id: number } {
  const [iso, idText, ...rest] = Buffer.from(cursor, "base64url").toString().split("|");
  const createdAt = new Date(iso);
  const id = Number(idText);
  if (rest.length > 0 || !iso || Number.isNaN(createdAt.getTime()) || !Number.isInteger(id) || id <= 0) throw new AppError("BAD_CURSOR");
  return { createdAt, id };
}

export async function feed(pool: Pool, { customerId, cursor, limit = 20 }: { customerId: number; cursor?: string; limit?: number }) {
  if (!Number.isInteger(limit) || limit < 1 || limit > 100) throw new AppError("BAD_LIMIT");
  const params: unknown[] = [customerId];
  let where = "customer_id = $1";
  if (cursor !== undefined) {
    const c = decodeCursor(cursor);
    params.push(c.createdAt, c.id);
    where += " AND (created_at, id) < ($2, $3)";
  }
  params.push(limit + 1);
  const { rows } = await pool.query(
    `SELECT id, total, created_at FROM big_orders WHERE ${where} ORDER BY created_at DESC, id DESC LIMIT $${params.length}`,
    params,
  );
  const page = rows.slice(0, limit);
  const last = page.at(-1);
  return {
    data: page.map((r) => ({ id: r.id, total: Number(r.total) })),
    nextCursor: rows.length > limit && last ? encodeCursor(last.created_at, last.id) : null,
  };
}

‏limit + 1 עונה על "יש עוד?" בלי שאילתת COUNT (P18-E65). ה־cursor האטום נותן חופש: מחר אפשר לשנות את המיון או להוסיף שדה, והלקוחות לא נשברים — הם רק מעבירים את המחרוזת חזרה.

⚠️ טעויות נפוצות
  • nextCursor תמיד (גם בעמוד האחרון) — הלקוח מבקש עוד עמוד ומקבל ריק. עובד, אבל בקשה מיותרת בכל רשימה.

P18-E78 · הכנסת אלפי שורות — בכמה פקודות? 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

💡 רמז 2

לכל שורה j בקבוצה: ($${j * 3 + 1}, $${j * 3 + 2}, $${j * 3 + 3}). ‏RETURNING id מחזיר את השורות בסדר שבו הוכנסו.

✅ פתרון
// P18-E78: הכנסת אלפי שורות — בכמה פקודות?
import type { Pool } from "pg";

export async function insertTransfers(pool: Pool, rows: { from: number; to: number; amount: number }[]): Promise<number[]> {
  if (rows.length === 0) return [];
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const ids: number[] = [];
    for (let i = 0; i < rows.length; i += 1000) {
      const chunk = rows.slice(i, i + 1000);
      const values = chunk.map((_, j) => `($${j * 3 + 1}, $${j * 3 + 2}, $${j * 3 + 3})`).join(", ");
      const params = chunk.flatMap((r) => [r.from, r.to, r.amount]);
      const { rows: inserted } = await client.query(`INSERT INTO transfers (from_id, to_id, amount) VALUES ${values} RETURNING id`, params);
      ids.push(...inserted.map((r) => r.id));
    }
    await client.query("COMMIT");
    return ids;
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}

2,500 שורות: 3 פקודות במקום 2,500 — מאות פעמים מהר יותר (כל פקודה היא נסיעה למסד). למה לא אחת ענקית? לפקודה יש תקרה של 65,535 פרמטרים, ופקודות ענקיות קשות למסד ולרשת — קבוצות של מאות עד אלפים הן הפשרה הנפוצה.

⚠️ טעויות נפוצות
  • לבנות את ה־VALUES עם הערכים עצמם בטקסט — "מהיר" ופתוח ל־injection (ומסוכן גם עם מספרים, אם מישהו העביר מחרוזת).
  • להכניס כל קבוצה ב־transaction משלה — קבוצה שלישית נכשלת, ושתי הראשונות כבר נשמרו.

P18-E24 · אתגר: checkout אמיתי 🤖 💻 כתיבת קוד 🤖 רמה 5

💡 רמז 1

בדיקת מפתח קיים בהתחלה + UNIQUE על idempotency_key לטיפול במרוץ: אם ה־INSERT של ההזמנה נכשל ב־23505 — ROLLBACK, ואז קרא את ההזמנה הקיימת והחזר אותה.

💡 רמז 2

סדר: מאחדים items ← BEGIN ← SELECT ... FOR UPDATE לכל המוצרים ← בדיקות ← INSERT להזמנה ← שורות ← עדכוני מלאי ← COMMIT.

✅ פתרון
// P18-E24
import type { Pool } from "pg";

export class AppError extends Error {
  code: string;
  productId?: number;
  constructor(code: string, message = code) {
    super(message);
    this.code = code;
  }
}

interface Item { productId: number; quantity: number }

async function existingOrder(pool: Pool, key: string) {
  const { rows } = await pool.query("SELECT id, total FROM shop_orders WHERE idempotency_key = $1", [key]);
  return rows[0] && { orderId: rows[0].id, total: Number(rows[0].total), replayed: true };
}

export async function checkout(pool: Pool, { customerId, items, idempotencyKey }: { customerId: number; items: Item[]; idempotencyKey: string }) {
  if (items.length === 0) throw new AppError("EMPTY_CART");
  const before = await existingOrder(pool, idempotencyKey);
  if (before) return before;

  const qty = new Map<number, number>();
  for (const i of items) qty.set(i.productId, (qty.get(i.productId) ?? 0) + i.quantity);
  const ids = [...qty.keys()].sort((a, b) => a - b);

  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const { rows: products } = await client.query("SELECT id, price, stock FROM catalog WHERE id = ANY($1) ORDER BY id FOR UPDATE", [ids]);
    if (products.length !== ids.length) throw new AppError("PRODUCT_NOT_FOUND");
    for (const p of products) {
      if (p.stock < qty.get(p.id)!) {
        const err = new AppError("OUT_OF_STOCK");
        err.productId = p.id;
        throw err;
      }
    }
    const total = products.reduce((sum, p) => sum + Number(p.price) * qty.get(p.id)!, 0);
    let orderId: number;
    try {
      const { rows } = await client.query(
        "INSERT INTO shop_orders (customer_id, idempotency_key, total) VALUES ($1, $2, $3) RETURNING id",
        [customerId, idempotencyKey, total.toFixed(2)]
      );
      orderId = rows[0].id;
    } catch (err) {
      if ((err as { code?: string }).code !== "23505") throw err;
      await client.query("ROLLBACK");
      return (await existingOrder(pool, idempotencyKey))!; // בקשה מקבילה עם אותו מפתח ניצחה
    }
    for (const p of products) {
      await client.query("INSERT INTO shop_order_lines (order_id, product_id, quantity, unit_price) VALUES ($1, $2, $3, $4)", [orderId, p.id, qty.get(p.id), p.price]);
      await client.query("UPDATE catalog SET stock = stock - $1 WHERE id = $2", [qty.get(p.id), p.id]);
    }
    await client.query("COMMIT");
    return { orderId, total: Number(total.toFixed(2)), replayed: false };
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}

זה הלב של פרויקט הדגל, בגרסה מוקטנת. (ROLLBACK כפול — אחד ב־catch הפנימי ואחד בחיצוני — לא קורה, כי ה־return יוצא לפני. אבל אם תשנה את הזרימה, שים לב: ROLLBACK בלי transaction פתוח מחזיר רק אזהרה.)

⚠️ טעויות נפוצות
  • לבדוק idempotency רק בהתחלה — שתי לחיצות באותה מילישנייה עוברות שתיהן את הבדיקה. ה־UNIQUE הוא מה שבאמת מגן.

P18-E27 · מאחד שליפות (batch loader) 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

ה־closure שומר Map של id ← רשימת "ממתינים" ({ resolve, reject } מתוך new Promise). ‏load מוסיף ממתין. אם ה־Map היה ריק לפני ההוספה, זו הקריאה הראשונה בסיבוב, ולכן היא מתזמנת את השליחה: setTimeout(flush, 0).

💡 רמז 2

ב־flush: קודם const batch = waiting; waiting = new Map();, כדי שקריאות חדשות ייכנסו לסיבוב הבא. אחר כך שאילתה עם [...batch.keys()], ‏Map של התוצאות לפי id, ולולאה שקוראת ל־resolve(byId.get(id) ?? null) לכל ממתין. ב־catch: ‏reject(err) לכולם.

✅ פתרון
// P18-E27: מאחד שליפות (batch loader)
import type { Pool } from "pg";

export type Person = { id: number; full_name: string };
type Waiter = { resolve: (p: Person | null) => void; reject: (err: unknown) => void };

export function createPersonLoader(pool: Pick<Pool, "query">) {
  let waiting = new Map<number, Waiter[]>();

  async function flush() {
    const batch = waiting;
    waiting = new Map();
    try {
      const { rows } = await pool.query("SELECT id, full_name FROM people WHERE id = ANY($1)", [[...batch.keys()]]);
      const byId = new Map<number, Person>(rows.map((p: Person) => [p.id, p]));
      for (const [id, waiters] of batch) {
        for (const w of waiters) w.resolve(byId.get(id) ?? null);
      }
    } catch (err) {
      for (const waiters of batch.values()) {
        for (const w of waiters) w.reject(err);
      }
    }
  }

  return function load(id: number): Promise<Person | null> {
    return new Promise((resolve, reject) => {
      if (waiting.size === 0) setTimeout(flush, 0);
      const list = waiting.get(id) ?? [];
      list.push({ resolve, reject });
      waiting.set(id, list);
    });
  };
}

שלושה דברים חיים ב־closure, ובכל loader יש עותק משלהם: ה־Map של הממתינים, הפונקציה flush, והחיבור למסד. לכן שני loaders לא מערבבים בקשות.

new Promise((resolve, reject) => ...) מאפשר "להחזיר תשובה אחר כך": ‏load מחזירה Promise מיד, ושומרת את resolve בצד. רק כשהשאילתה חוזרת, flush קוראת לו. זה ה־Promise "הידני" מפרק 10, ופה רואים בשביל מה הוא קיים.

ההחלפה waiting = new Map() לפני ה־await חשובה. בזמן שהשאילתה רצה, קריאות חדשות נכנסות ל־Map החדש ומתזמנות סיבוב משלהן, במקום ללכת לאיבוד.

בפרויקטי GraphQL זה הכלי הסטנדרטי נגד N+1: כל שדה "מבקש" את מה שהוא צריך, וה־loader מאחד הכול.

⚠️ טעויות נפוצות
  • setTimeout(flush, 0) בכל קריאה — כמה flush רצים, והשני שולח שאילתה עם רשימה ריקה (או שולח שוב את אותם ids).
  • לנקות את ה־Map רק אחרי ה־await — קריאות שהגיעו בזמן השאילתה נמחקות ולא מקבלות תשובה לעולם.
  • לחזור עם rows[i] לפי מקום במערך — המסד לא מבטיח שהשורות יחזרו באותו סדר, ו־id חסר מזיז את כולם.
  • לשכוח reject ב־catch — כשהמסד נופל, כל הקוראים תקועים לנצח.

P18-E28 · שלושת הלקוחות המובילים בכל חודש 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

שלושה שלבים, כל אחד ב־CTE משלו: (1) monthly — ‏GROUP BY לפי חודש ולקוח. (2) ranked — ‏ROW_NUMBER() OVER (PARTITION BY month ORDER BY revenue DESC, customer_id). ‏(3) WHERE place <= 3.

💡 רמז 2

  SELECT month, customer_id, revenue,

הדוח הזה דורש שני "צמצומים" שונים: ‏GROUP BY הופך מאות הזמנות של לקוח בחודש לשורה אחת, והחלון מדרג את השורות האלה בתוך כל חודש. כל שלב ב־CTE משלו, וכל שלב קריא לבד.

הטווח נכתב כ־>= התחלה ו־< סוף, ולא date_trunc(...) IN (...). כך, אם יש index על created_at (שיעור 3), המסד יכול לקרוא רק את שלושת החודשים במקום את כל 200,000 השורות. פונקציה על העמודה ב־WHERE מונעת שימוש ב־index.

ORDER BY revenue DESC, customer_id בתוך החלון: בלי קריטריון שני, בתיקו המסד בוחר סדר כרצונו, והדוח יוצא שונה בכל הרצה.

⚠️ טעויות נפוצות
  • RANK() במקום ROW_NUMBER() — בתיקו שני לקוחות מקבלים אותו מקום, ויכולים לחזור ארבעה.
  • created_at <= '2025-03-31' — זה 2025-03-31 00:00, ורוב היום האחרון נחתך.
  • PARTITION BY customer_id — מדרג חודשים לכל לקוח, במקום לקוחות לכל חודש.
