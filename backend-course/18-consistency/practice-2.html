P18-E03 · איזה כלי?

🧠 הבנהרמה 1⏱ 10 דק׳ידע נדרש: שיעור 2

לכל תרחיש — איזה פתרון מתאים: עדכון אטומי עם תנאי, FOR UPDATE, אילוץ (UNIQUE/CHECK), או Serializable + ניסיון חוזר? למה?

  1. הורדת מלאי בקנייה.
  2. הרשמה עם אימייל — שני אנשים נרשמים עם אותו אימייל באותו רגע.

  4. "לכל רופא לפחות רופא תורן אחד בכל משמרת" — שני רופאים מבטלים תורנות באותו רגע.
  5. מונה צפיות בסרטון.

P18-E44 · ‏deadlock או רק המתנה?

🧠 הבנהרמה 2⏱ 10 דק׳ידע נדרש: שיעור 2

לכל זוג transactions שרצים במקביל — יכול להיווצר deadlock, או שבמקרה הגרוע אחד מחכה לשני? (כל שורה היא UPDATE של חשבון, לפי הסדר.)

  1. A: חשבון 1 ← חשבון 4. ‏B: חשבון 1 ← חשבון 4.
  2. A: חשבון 1 ← חשבון 4. ‏B: חשבון 4 ← חשבון 1.
  3. A: חשבון 1 ← חשבון 2. ‏B: חשבון 3 ← חשבון 4.
  4. A: חשבונות 1, 2, 3. ‏B: חשבונות 3, 1.
  5. A: ‏SELECT ... WHERE id IN (1, 4) ORDER BY id FOR UPDATE. ‏B: אותו דבר עם IN (4, 1).

P18-E45 · תשלום בתוך הנעילה

🧠 הבנהרמה 2⏱ 10 דק׳ידע נדרש: שיעור 2

P18-E46 · איזו שגיאה שווה ניסיון חוזר?

🧠 הבנהרמה 1⏱ 10 דק׳ידע נדרש: שיעור 2

ל־withSerializableRetry (P18-E19) מגיעות שגיאות. לכל אחת — לנסות שוב את כל ה־transaction, או להחזיר שגיאה מיד? למה?

  1. 40001 — could not serialize access due to concurrent update.
  2. 40P01 — deadlock detected.
  3. 23505 — duplicate key (אימייל תפוס).
  4. 23514 — check constraint (יתרה שלילית).
  5. 42703 — column "balanse" does not exist.
  6. ECONNREFUSED — המסד לא זמין.

P18-E13 · העברה עם נעילה 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 30 דק׳ידע נדרש: שיעור 2

בקובץ 18-consistency/starter/P18-E13.ts השלם transferSafe(pool, fromId, toId, amount), עם בדיקות לפני כל שינוי:

  • fromId === toId ← AppError("SAME_ACCOUNT"); amount לא חיובי ← AppError("INVALID_AMOUNT") (בלי לגשת למסד).
  • ב־transaction: נעל את שני החשבונות עם SELECT ... FOR UPDATE, לפי סדר id. חסר אחד ← AppError("ACCOUNT_NOT_FOUND"). יתרה לא מספיקה ← AppError("INSUFFICIENT_FUNDS"). אחרת — העדכונים, רישום ב־transfers, COMMIT. מחזירה { transferId, fromBalance, toBalance } (מספרים).

הבדיקה מריצה 40 העברות במקביל בין Dana ל־Avi, בשני הכיוונים — בלי סדר נעילה קבוע זה מייצר deadlocks.

P18-E19 · ניסיון חוזר ב־Serializable 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 30 דק׳ידע נדרש: שיעור 2

בקובץ 18-consistency/starter/P18-E19.ts השלם withSerializableRetry(pool, work, { retries = 5 } = {}):

  • מריצה את work(client) בתוך BEGIN ISOLATION LEVEL SERIALIZABLE ... COMMIT, ומחזירה את מה ש־work החזיר.
  • שגיאה עם code 40001 (serialization) או 40P01 (deadlock) — גם ב־COMMIT עצמו! — ← ROLLBACK, המתנה קצרה (אקראית, 5–25ms), וניסיון חוזר של כל העבודה. אחרי retries ניסיונות חוזרים — השגיאה האחרונה נזרקת.
  • כל שגיאה אחרת ← ROLLBACK ונזרקת מיד. החיבור משתחרר תמיד.

הבדיקה: 15 "העלאות מונה" במקביל (קרא ← הוסף 1 ← כתוב) ב־Serializable — בלי ניסיון חוזר רובן נכשלות; עם — המונה מגיע ל־15.

const lock = createMutex();
app.post("/buy/:id", async (req, res) => {
  const left = await lock.run(async () => {

    if (rows[0].stock < 1) throw new AppError("OUT_OF_STOCK");
    await pool.query("UPDATE inventory SET stock = $1 WHERE product_id = $2", [rows[0].stock - 1, req.params.id]);
    return rows[0].stock - 1;
  });
  res.json({ left });
});

P18-E52 · ‏mutex בזיכרון 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 25 דק׳ידע נדרש: פרק 5, פרק 10, פרק 11, שיעור 2

הכלי מ־P18-E49 — שימושי לכל משאב בתוך תהליך אחד (קובץ, מטמון). בקובץ 18-consistency/starter/P18-E52.ts כתוב וייצא:

export function createMutex(): { run<T>(fn: () => Promise<T>): Promise<T>; pending(): number }
  • run(fn) מריצה את fn רק אחרי שכל ה־fnים שנשלחו לפניה הסתיימו (הצליחו או נכשלו), ומחזירה את התוצאה שלה (או זורקת את השגיאה שלה).
  • שגיאה של fn אחת לא עוצרת את הבאות בתור.
  • pending() — כמה runים עוד לא הסתיימו (כולל זו שרצה עכשיו).

% npm run check P18-E52

🔗 איך זה מתחבר: closure מפרק 5 (משתנה "הזנב של התור" שחי בין קריאות), Promise ו־then מפרק 10, generics מפרק 11 — והשיעור: "אחד אחרי השני" זה מה שנעילה עושה. (ו־P18-E49: למה במסד זה לא מספיק.)

P18-E53 · מימוש קופון — פעם אחת לכל משתמש 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 30 דק׳ידע נדרש: פרק 8, פרק 17, שיעור 2

CREATE TABLE coupons (code text PRIMARY KEY, uses_left integer NOT NULL CHECK (uses_left >= 0));
CREATE TABLE coupon_redemptions (
  code     text NOT NULL REFERENCES coupons (code),
  user_id  integer NOT NULL,
  PRIMARY KEY (code, user_id)
);

export async function redeem(pool: Pool, code: string, userId: number): Promise<number>

  • העדכון לא עדכן שורה: אין קופון כזה ← AppError("COUPON_NOT_FOUND"); יש אבל נגמר ← AppError("COUPON_EXHAUSTED").
  • המשתמש כבר מימש (23505 ברישום) ← AppError("ALREADY_REDEEMED") — וה־ROLLBACK מחזיר את המימוש שירד.
