P18-E02 · ציר זמן

🧠 הבנהרמה 1⏱ 10 דק׳ידע נדרש: שיעור 2

בחשבון של Yossi 250. שתי בקשות "משיכה של 200" מגיעות כמעט יחד. הקוד:

const { rows } = await pool.query("SELECT balance FROM accounts WHERE id = 2");
if (rows[0].balance < 200) throw new AppError("INSUFFICIENT_FUNDS");
await pool.query("UPDATE accounts SET balance = $1 WHERE id = 2", [rows[0].balance - 200]);

(1) תאר סדר אירועים שבו שתיהן מצליחות. מה היתרה בסוף, וכמה כסף יצא? (2) האם ה־CHECK (balance >= 0) יציל? (3) האם עטיפה ב־BEGIN/COMMIT תציל?

P18-E03 · איזה כלי?

🧠 הבנהרמה 1⏱ 10 דק׳ידע נדרש: שיעור 2

לכל תרחיש — איזה פתרון מתאים: עדכון אטומי עם תנאי, FOR UPDATE, אילוץ (UNIQUE/CHECK), או Serializable + ניסיון חוזר? למה?

  1. הורדת מלאי בקנייה.
  2. הרשמה עם אימייל — שני אנשים נרשמים עם אותו אימייל באותו רגע.
  3. העברה בין חשבונות, עם בדיקות: חשבון קפוא? מגבלה יומית? הנחה לפי סוג לקוח?
  4. "לכל רופא לפחות רופא תורן אחד בכל משמרת" — שני רופאים מבטלים תורנות באותו רגע.
  5. מונה צפיות בסרטון.

P18-E13 · העברה עם נעילה 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 30 דק׳ידע נדרש: שיעור 2

בקובץ 18-consistency/starter/P18-E13.ts השלם transferSafe(pool, fromId, toId, amount), עם בדיקות לפני כל שינוי:

  • fromId === toId ← AppError("SAME_ACCOUNT"); amount לא חיובי ← AppError("INVALID_AMOUNT") (בלי לגשת למסד).
  • ב־transaction: נעל את שני החשבונות עם SELECT ... FOR UPDATE, לפי סדר id. חסר אחד ← AppError("ACCOUNT_NOT_FOUND"). יתרה לא מספיקה ← AppError("INSUFFICIENT_FUNDS"). אחרת — העדכונים, רישום ב־transfers, COMMIT. מחזירה { transferId, fromBalance, toBalance } (מספרים).

הבדיקה מריצה 40 העברות במקביל בין Dana ל־Avi, בשני הכיוונים — בלי סדר נעילה קבוע זה מייצר deadlocks.

P18-E14 · הזמנת מקומות 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 25 דק׳ידע נדרש: שיעור 2

בקובץ 18-consistency/starter/P18-E14.ts השלם bookSeat(pool, eventId, userId) לטבלאות events (עם capacity) ו־bookings:

  • אירוע לא קיים ← AppError("EVENT_NOT_FOUND").
  • המשתמש כבר רשום ← AppError("ALREADY_BOOKED").
  • האירוע מלא ← AppError("SOLD_OUT").
  • אחרת — רישום, ומחזירה את מספר המקומות שנשארו.

הבדיקה: 20 משתמשים נרשמים במקביל לאירוע עם 5 מקומות — בדיוק 5 מצליחים.

P18-E19 · ניסיון חוזר ב־Serializable 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 30 דק׳ידע נדרש: שיעור 2

בקובץ 18-consistency/starter/P18-E19.ts השלם withSerializableRetry(pool, work, { retries = 5 } = {}):

  • מריצה את work(client) בתוך BEGIN ISOLATION LEVEL SERIALIZABLE ... COMMIT, ומחזירה את מה ש־work החזיר.
  • שגיאה עם code 40001 (serialization) או 40P01 (deadlock) — גם ב־COMMIT עצמו! — ← ROLLBACK, המתנה קצרה (אקראית, 5–25ms), וניסיון חוזר של כל העבודה. אחרי retries ניסיונות חוזרים — השגיאה האחרונה נזרקת.
  • כל שגיאה אחרת ← ROLLBACK ונזרקת מיד. החיבור משתחרר תמיד.

הבדיקה: 15 "העלאות מונה" במקביל (קרא ← הוסף 1 ← כתוב) ב־Serializable — בלי ניסיון חוזר רובן נכשלות; עם — המונה מגיע ל־15.
