P18-E02 · ציר זמן 🧠 הבנה רמה 1

💡 רמז 1

שני ה־SELECT־ים לפני שני ה־UPDATE־ים.

💡 רמז 2

ה־UPDATE כותב מספר קבוע (50), לא balance - 200.

✅ פתרון
  1. A קורא 250, B קורא 250, A כותב 50, B כותב 50. היתרה 50 — אבל יצאו 400 ש״ח. הבנק הפסיד 200.
  2. לא. אף כתיבה לא שלילית (שתיהן כותבות 50). ה־CHECK תופס רק ערכים לא חוקיים, לא חישוב שגוי.
  3. לא, ב־Read Committed: שני ה־SELECT־ים רואים 250 (אף אחד עוד לא עשה commit), והכתיבות פשוט ממתינות אחת לשנייה. מה שכן מציל: UPDATE accounts SET balance = balance - 200 WHERE id = 2 AND balance >= 200 ובדיקת rowCount, או SELECT ... FOR UPDATE בתוך transaction.
⚠️ טעויות נפוצות
  • "זה לא יקרה, הבקשות לא מגיעות באותה מילישנייה" — לחיצה כפולה על כפתור, ו־retry אוטומטי של אפליקציה, שולחים בדיוק כך.

P18-E03 · איזה כלי? 🧠 הבנה רמה 1

💡 רמז 1

מה הכי פשוט שעובד? עדכון אטומי ואילוצים — קודם.

💡 רמז 2

4 הוא חוק על כמה שורות יחד — אף שורה בודדת לא "שגויה".

✅ פתרון
  1. עדכון אטומי עם תנאי (WHERE stock >= $qty) + CHECK כרשת ביטחון.
  2. UNIQUE על האימייל. אל תבדוק "האם קיים" ואז תכניס — המסד יתפוס, ואת השגיאה (23505) מתרגמים ל־409.
  3. FOR UPDATE על שני החשבונות (לפי סדר id), ואז כל הבדיקות בקוד, ואז העדכונים — הכול ב־transaction אחד.
  4. Serializable + ניסיון חוזר: כל ביטול לבד חוקי; רק השילוב שבור. (חלופה: לנעול את כל שורות המשמרת עם FOR UPDATE לפני הבדיקה.)
  5. עדכון אטומי: SET views = views + 1. (בהיקפים ענקיים — צוברים בזיכרון/Redis ומעדכנים בקבוצות, פרק 26.)
⚠️ טעויות נפוצות
  • להשתמש ב־Serializable "בכל מקום ליתר ביטחון" — כל transaction צריך מנגנון ניסיון חוזר, והביצועים יורדים.

P18-E43 · מי מחכה, ומה הוא רואה אחר כך? 🧠 הבנה רמה 2

💡 רמז 1

UPDATE נועל את השורה עד סוף ה־transaction של A. ‏B (בלי BEGIN — כל פקודה transaction משלה) מגיע לאותה שורה.

💡 רמז 2

אחרי ROLLBACK, מה הערך ש־B "רואה" כשהוא סוף־סוף מקבל את השורה?

✅ פתרון
  1. ה־UPDATE של A נועל את שורה 1. ה־UPDATE של B נתקע — מחכה ש־A יסיים.
  2. A עושה ROLLBACK: השינוי שלו מתבטל והנעילה משתחררת. B ממשיך מיד, ומחשב balance - 50 מהערך העדכני — 1000 (לא 900, שהוא ערך שמעולם לא נשמר).
  3. הסוף: 950.

זו הסיבה שעדכון אטומי (balance = balance - 50) בטוח: המסד מחשב אותו אחרי שהוא מקבל את השורה, מהערך שבאמת שמור. ואם A היה עושה COMMIT — B היה מחשב מ־900, ומגיע ל־850.

⚠️ טעויות נפוצות
  • לחשוב ש־B נכשל כי "השורה תפוסה" — ב־Read Committed הוא מחכה, לא נכשל.

P18-E44 · ‏deadlock או רק המתנה? 🧠 הבנה רמה 2

💡 רמז 1

deadlock צריך מעגל: A מחזיק X ומחכה ל־Y, ו־B מחזיק Y ומחכה ל־X.

💡 רמז 2

בסעיף 5 — באיזה סדר נועלות השורות? (לפי ה־ORDER BY, לא לפי ה־IN.)

✅ פתרון
  1. המתנה — שניהם מתחילים ב־1; מי שהגיע שני מחכה, ואז ממשיך.
  2. deadlock אפשרי — A מחזיק 1 ומחכה ל־4, B מחזיק 4 ומחכה ל־1.
  3. אין קשר — שורות שונות, אף אחד לא מחכה.
  4. deadlock אפשרי — A נעל 1 (ואולי 2) ומחכה ל־3; ‏B נעל 3 ומחכה ל־1.
  5. המתנה בלבד — ה־ORDER BY id קובע שהשורות ננעלות 1 ואז 4 בשניהם. זה הפתרון מ־P18-E13: אותו סדר נעילה לכולם.
⚠️ טעויות נפוצות
  • לחשוב ש־IN (4, 1) נועל קודם את 4. הסדר של הרשימה לא קובע כלום; רק ORDER BY.

P18-E45 · תשלום בתוך הנעילה 🧠 הבנה רמה 2

💡 רמז 1

כל אחד מחזיק את הנעילה כ־2 שניות, והם עוברים אחד־אחד.

💡 רמז 2

מי שמחכה לנעילה — מחזיק חיבור מה־pool כל הזמן הזה.

✅ פתרון
  1. כ־60 שניות (29 × 2 לפניו, ועוד שלו). רוב הדפדפנים/שרתי proxy יוותרו לפני כן — והלקוח ילחץ שוב.
  2. 10 בקשות קנייה תופסות את כל 10 החיבורים (כולן מחכות לנעילה), וכל בקשה אחרת — גם "הצג פרופיל" — מחכה לחיבור פנוי. האתר כולו "נתקע" בגלל מוצר אחד.
  3. להחזיק נעילה רק לרגע: קודם עדכון אטומי ששומר את המלאי (UPDATE ... WHERE stock >= 1, אולי בסטטוס "שמור"), COMMIT, ואז לחייב. אם החיוב נכשל — transaction קצר שני שמחזיר את המלאי. ככה מחזיקים נעילה מילישניות, לא שניות.
⚠️ טעויות נפוצות
  • להגדיל את ה־pool ל־100 — הבעיה היא הנעילה, לא החיבורים; מאה בקשות יחכו בתור במקום עשר.

P18-E46 · איזו שגיאה שווה ניסיון חוזר? 🧠 הבנה רמה 1

💡 רמז 1

השאלה: "אם אריץ את אותו דבר שוב בעוד רגע — יש סיכוי שיצליח?"

💡 רמז 2

שגיאה שנובעת מתזמון עם מישהו אחר — שונה משגיאה שנובעת מהנתונים או מהקוד.

✅ פתרון
  1. שוב — התנגשות תזמון; בניסיון הבא הסדר יהיה אחר.
  2. שוב — המסד ביטל את ה־transaction שלך כדי לשבור את המעגל; השני כבר ממשיך.
  3. לא — האימייל תפוס, ויישאר תפוס. 409 ללקוח.
  4. לא — אין מספיק כסף; ניסיון חוזר ייכשל באותה צורה (אלא אם במקרה הופקד כסף — וזה לא מה שהלקוח ביקש).
  5. לא — באג בקוד. ניסיון חוזר רק מעמיס. 500 ולוג.
  6. אולי, בזהירות — זמני, אבל לא בלולאה צפופה: כמה ניסיונות עם המתנה שגדלה (backoff), ואז 503. (וב־retry של ה־transaction כולו, לא רק של הפקודה האחרונה.)
⚠️ טעויות נפוצות
  • retry על כל שגיאה "ליתר ביטחון" — באג בקוד הופך לפי 5 עומס על המסד, ולקוח שמחכה פי 5 עד שהוא מקבל את אותה שגיאה.

P18-E10 · buy בלי מרוץ 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

עדכון אטומי (E09) עם פרמטרים. rowCount === 0 — לא נמכר.

💡 רמז 2

אבל למה 0? כדי להבדיל בין "אין מוצר" ל"אין מלאי" — שאילתה נוספת, רק במקרה של כישלון.

✅ פתרון
// P18-E10
import type { Pool } from "pg";

export class AppError extends Error {
  code: string;
  constructor(code: string, message = code) {
    super(message);
    this.code = code;
  }
}

export async function buy(pool: Pool, productId: number, qty: number): Promise<number> {
  const { rows } = await pool.query(
    "UPDATE inventory SET stock = stock - $2 WHERE product_id = $1 AND stock >= $2 RETURNING stock",
    [productId, qty]
  );
  if (rows.length > 0) return rows[0].stock;
  const exists = await pool.query("SELECT 1 FROM inventory WHERE product_id = $1", [productId]);
  throw new AppError(exists.rowCount === 0 ? "PRODUCT_NOT_FOUND" : "OUT_OF_STOCK");
}

במקרה הנפוץ (יש מלאי) — שאילתה אחת. השאילתה השנייה רק כדי לתת הודעת שגיאה מדויקת.

⚠️ טעויות נפוצות
  • לבדוק קודם אם המוצר קיים ויש מלאי, ואז לעדכן — חזרנו לבאג של E02.

P18-E13 · העברה עם נעילה 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

SELECT id, balance FROM accounts WHERE id = ANY($1) ORDER BY id FOR UPDATE — שורה אחת, נעילה מסודרת.

💡 רמז 2

balance מגיע מ־pg כמחרוזת (numeric) — Number(...) להשוואה.

✅ פתרון
// P18-E13
import type { Pool } from "pg";

export class AppError extends Error {
  code: string;
  constructor(code: string, message = code) {
    super(message);
    this.code = code;
  }
}

export async function transferSafe(pool: Pool, fromId: number, toId: number, amount: number) {
  if (fromId === toId) throw new AppError("SAME_ACCOUNT");
  if (!(amount > 0)) throw new AppError("INVALID_AMOUNT");

  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    // נעילה לפי סדר id — שתי העברות הפוכות לא יחכו זו לזו במעגל
    const { rows } = await client.query("SELECT id, balance FROM accounts WHERE id = ANY($1) ORDER BY id FOR UPDATE", [[fromId, toId]]);
    const from = rows.find((r) => r.id === fromId);
    const to = rows.find((r) => r.id === toId);
    if (!from || !to) throw new AppError("ACCOUNT_NOT_FOUND");
    if (Number(from.balance) < amount) throw new AppError("INSUFFICIENT_FUNDS");

    const a = await client.query("UPDATE accounts SET balance = balance - $1 WHERE id = $2 RETURNING balance", [amount, fromId]);
    const b = await client.query("UPDATE accounts SET balance = balance + $1 WHERE id = $2 RETURNING balance", [amount, toId]);
    const t = await client.query("INSERT INTO transfers (from_id, to_id, amount) VALUES ($1, $2, $3) RETURNING id", [fromId, toId, amount]);
    await client.query("COMMIT");
    return { transferId: t.rows[0].id, fromBalance: Number(a.rows[0].balance), toBalance: Number(b.rows[0].balance) };
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}
⚠️ טעויות נפוצות
  • לנעול fromId ואז toId — זה בדיוק התרחיש של deadlock מהשיעור.

P18-E14 · הזמנת מקומות 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

אין עמודת "מקומות פנויים" לעדכן אטומית — צריך לספור. ספירה במקביל = מרוץ. מה אפשר לנעול?

💡 רמז 2

SELECT capacity FROM events WHERE id = $1 FOR UPDATE — כל ההרשמות לאותו אירוע עוברות בתור. ו־ALREADY_BOOKED: ה־UNIQUE על (event_id, user_id), עם קוד השגיאה 23505.

✅ פתרון
// P18-E14
import type { Pool } from "pg";

export class AppError extends Error {
  code: string;
  constructor(code: string, message = code) {
    super(message);
    this.code = code;
  }
}

export async function bookSeat(pool: Pool, eventId: number, userId: number): Promise<number> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const event = await client.query("SELECT capacity FROM events WHERE id = $1 FOR UPDATE", [eventId]);
    if (event.rowCount === 0) throw new AppError("EVENT_NOT_FOUND");
    const { rows } = await client.query("SELECT COUNT(*)::int AS taken FROM bookings WHERE event_id = $1", [eventId]);
    const capacity = event.rows[0].capacity;
    try {
      await client.query("INSERT INTO bookings (event_id, user_id) VALUES ($1, $2)", [eventId, userId]);
    } catch (err) {
      if ((err as { code?: string }).code === "23505") throw new AppError("ALREADY_BOOKED");
      throw err;
    }
    if (rows[0].taken >= capacity) throw new AppError("SOLD_OUT");
    await client.query("COMMIT");
    return capacity - rows[0].taken - 1;
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}

שים לב לסדר: קודם ה־INSERT (כדי ש"כבר רשום" ינצח את "מלא" — משתמש רשום שמנסה שוב צריך לשמוע "אתה כבר רשום"), ואז בדיקת המקום — ואם מלא, ה־ROLLBACK מבטל את ה־INSERT. הנעילה על שורת האירוע היא מה שהופך את "סופרים ← בודקים ← מכניסים" לבטוח.

⚠️ טעויות נפוצות
  • לנעול את bookings עם FOR UPDATE — נועל רק שורות קיימות; את ההרשמה ה"חדשה" של המשתמש הבא אי אפשר לנעול מראש.

P18-E19 · ניסיון חוזר ב־Serializable 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

לולאת for (let attempt = 0; ; attempt++) סביב try/catch שלם (כמו P14-E19).

💡 רמז 2

COMMIT יכול להיכשל ב־40001 — לכן הוא בתוך ה־try.

✅ פתרון
// P18-E19
import type { Pool, PoolClient } from "pg";

const RETRYABLE = new Set(["40001", "40P01"]);
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

export async function withSerializableRetry<T>(pool: Pool, work: (client: PoolClient) => Promise<T>, { retries = 5 } = {}): Promise<T> {
  const client = await pool.connect();
  try {
    for (let attempt = 0; ; attempt++) {
      try {
        await client.query("BEGIN ISOLATION LEVEL SERIALIZABLE");
        const result = await work(client);
        await client.query("COMMIT");
        return result;
      } catch (err) {
        await client.query("ROLLBACK");
        const code = (err as { code?: string }).code;
        if (!code || !RETRYABLE.has(code) || attempt >= retries) throw err;
        await sleep(5 + Math.random() * 20);
      }
    }
  } finally {
    client.release();
  }
}

ההמתנה האקראית ("jitter") חשובה: בלי, כל המתנגשים מנסים שוב באותה מילישנייה — ומתנגשים שוב.

⚠️ טעויות נפוצות
  • לנסות שוב רק את הפקודה שנכשלה — ב־40001 כל ה־transaction פסול; צריך להתחיל מה־SELECT הראשון.

import type { Pool } from "pg";

export class AppError extends Error {
  code: string;
  constructor(code: string, message = code) {
    super(message);
    this.code = code;
  }
}

export async function reserve(pool: Pool, productId: number, qty: number): Promise<number> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const { rows } = await client.query("SELECT stock FROM inventory WHERE product_id = $1 FOR UPDATE", [productId]);
    if (rows.length === 0) throw new AppError("PRODUCT_NOT_FOUND");
    const stock: number = rows[0].stock;
    if (stock < 5 && qty > 2) throw new AppError("LOW_STOCK_LIMIT");
    if (qty > stock) throw new AppError("OUT_OF_STOCK");
    const updated = await client.query("UPDATE inventory SET stock = stock - $2 WHERE product_id = $1 RETURNING stock", [productId, qty]);
    await client.query("COMMIT");
    return updated.rows[0].stock;
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}

עדכון אטומי אחד לא מספיק כאן: הכלל "פחות מ־5 ← עד 2" אפשר לכתוב ב־WHERE, אבל אז "למה זה נכשל" נעלם (0 שורות — אזל? כלל? אין מוצר?). עם FOR UPDATE הקוד קורא, מחליט ומסביר — ואף אחד לא משנה את השורה באמצע.

⚠️ טעויות נפוצות
  • SELECT בלי FOR UPDATE — שני לקוחות רואים 6, כל אחד שומר 3, ונשארות... 0, כשהכלל אמר שהשני היה צריך לקבל עד 2. (ועם מלאי קטן — גם מלאי שלילי שנעצר רק ב־CHECK.)
  • pool.query("... FOR UPDATE") מחוץ ל־transaction — הנעילה משתחררת מיד בסוף הפקודה.

P18-E49 · נעילה בזיכרון — ושני שרתים 🧠 הבנה רמה 2

💡 רמז 1

ה־lock הוא משתנה בזיכרון של תהליך אחד.

💡 רמז 2

מה כל שלושת השרתים (והסקריפט) חולקים?

✅ פתרון
  1. לא — על תהליך אחד, ה־mutex באמת מסדר את הקניות בתור (וזה גם מאט: כל הקניות, של כל המוצרים, בתור אחד).
  2. לכל עותק יש lock משלו. שני עותקים מריצים את הקריאה־חישוב־כתיבה במקביל — המרוץ חוזר, והוא יופיע רק בייצור (בפיתוח יש תהליך אחד).
  3. הסקריפט לא מכיר את ה־lock בכלל.
  4. לנעול במקום המשותף — המסד: עדכון אטומי עם תנאי (stock = stock - 1 WHERE stock >= 1), או FOR UPDATE. המסד רואה את כל הבקשות מכל השרתים.
⚠️ טעויות נפוצות
  • "נריץ רק עותק אחד" — עד שהשרת הראשון נופל, או שצריך עוד אחד לעומס. ההנחה הזו נשברת בלי שאף אחד שם לב.

P18-E50 · איזה status לכל התנגשות? 🧠 הבנה רמה 2

💡 רמז 1

409 Conflict — "הבקשה תקינה, אבל מתנגשת במצב הנוכחי". 503 — "זמני, נסה שוב".

💡 רמז 2

מה שהשרת פתר בעצמו — הלקוח בכלל לא צריך לדעת עליו.

✅ פתרון
  1. 409 (OUT_OF_STOCK). הלקוח מציג "אזל" — לא מנסה שוב.
  2. 409 (ALREADY_BOOKED) — או 200 עם ההרשמה הקיימת, אם רוצים שהפעולה תהיה idempotent. לא 500.
  3. 200/201 רגיל. ה־retry היה פנימי; הלקוח לא צריך לדעת.
  4. 503 עם Retry-After: 1 — עומס זמני. הלקוח יכול לנסות שוב בעוד רגע.
  5. 409 (או 412 Precondition Failed, אם הגרסה נשלחה בכותרת If-Match). הלקוח טוען מחדש, מראה למשתמש את השינויים, ונותן לו להחליט. (זה "optimistic locking": ה־UPDATE כולל AND version = $2 ומעלה את version ב־1 — ו־0 שורות אומר שמישהו הקדים.)
⚠️ טעויות נפוצות
  • 500 על כל שגיאה מהמסד — הלקוח לא יודע אם לנסות שוב, ומערכות ניטור מתריעות על "באג" שהוא בעצם "אזל".

P18-E52 · ‏mutex בזיכרון 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

שמור Promise של "הזנב": let tail: Promise<unknown> = Promise.resolve();. כל run: ‏const result = tail.then(() => fn());

💡 רמז 2

הזנב החדש צריך להמשיך גם אם fn נכשלה: tail = result.catch(() => {});.

✅ פתרון
// P18-E52: mutex בזיכרון
export function createMutex() {
  let tail: Promise<unknown> = Promise.resolve();
  let count = 0;
  return {
    run<T>(fn: () => Promise<T>): Promise<T> {
      count++;
      const result = tail.then(() => fn());
      tail = result.catch(() => {}).finally(() => count--);
      return result;
    },
    pending: () => count,
  };
}

שלוש שורות של Promise: כל משימה "נתלית" על סוף התור, והתור החדש הוא המשימה הזו — אחרי שהסתיימה, בהצלחה או בכישלון. אין כאן נעילה של מערכת ההפעלה: JavaScript רץ בחוט אחד, ו"לחכות" זה פשוט להירשם ל־then.

⚠️ טעויות נפוצות
  • tail = result בלי catch — שגיאה אחת "תוקעת" את כל התור: כל ה־then הבאים מדלגים על fn וזורקים אותה שגיאה.
  • להריץ את fn() מיד ורק "לחכות" לתוצאה הקודמת — המשימות עדיין רצות במקביל.

P18-E53 · מימוש קופון — פעם אחת לכל משתמש 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1
UPDATE coupons SET uses_left = uses_left - 1 WHERE code = $1 AND uses_left > 0 RETURNING uses_left

. 0 שורות ← SELECT 1 FROM coupons WHERE code = $1 כדי לדעת איזו שגיאה.

💡 רמז 2

ב־catch, אחרי ROLLBACK:

if (err.code === "23505") throw new AppError("ALREADY_REDEEMED");
✅ פתרון
// P18-E53: מימוש קופון — פעם אחת לכל משתמש
import type { Pool } from "pg";

export class AppError extends Error {
  code: string;
  constructor(code: string, message = code) {
    super(message);
    this.code = code;
  }
}

export async function redeem(pool: Pool, code: string, userId: number): Promise<number> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const { rows } = await client.query("UPDATE coupons SET uses_left = uses_left - 1 WHERE code = $1 AND uses_left > 0 RETURNING uses_left", [code]);
    if (rows.length === 0) {
      const exists = await client.query("SELECT 1 FROM coupons WHERE code = $1", [code]);
      throw new AppError(exists.rowCount === 0 ? "COUPON_NOT_FOUND" : "COUPON_EXHAUSTED");
    }
    await client.query("INSERT INTO coupon_redemptions (code, user_id) VALUES ($1, $2)", [code, userId]);
    await client.query("COMMIT");
    return rows[0].uses_left;
  } catch (err: any) {
    await client.query("ROLLBACK");
    if (err.code === "23505") throw new AppError("ALREADY_REDEEMED");
    throw err;
  } finally {
    client.release();
  }
}

שני מנגנונים, שתי שאלות: "נשארו מימושים?" — עדכון אטומי עם תנאי, כמו מלאי. "המשתמש כבר מימש?" — המפתח הראשי של הזוג; שתי בקשות במקביל של אותו משתמש — אחת תקבל 23505. ובזכות ה־transaction, המימוש שירד מהמונה חוזר.

⚠️ טעויות נפוצות
  • לבדוק "כבר מימש?" עם SELECT לפני — שתי בקשות במקביל עוברות את הבדיקה (P18-E51).
  • לרשום קודם ולהוריד אחר כך, בלי transaction — רישום שהצליח וקופון שנגמר משאירים "מימוש" בלי כיסוי.

P18-E54 · מגבלה יומית להעברות 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1
SELECT COALESCE(SUM(amount), 0) AS sent FROM transfers WHERE from_id = $1 AND created_at >= date_trunc('day', now())

את השאילתה הזו מריצים אחרי ה־FOR UPDATE.

💡 רמז 2

בלי ה־FOR UPDATE, עשר בקשות קוראות "נשלחו היום 0" באותו רגע, וכולן עוברות. עם — כל אחת מחכה שהקודמת תסיים (ותרשום את ההעברה שלה).

✅ פתרון
// P18-E54: מגבלה יומית להעברות
import type { Pool } from "pg";

export class AppError extends Error {
  code: string;
  constructor(code: string, message = code) {
    super(message);
    this.code = code;
  }
}

export async function transferWithLimit(pool: Pool, fromId: number, toId: number, amount: number, dailyLimit: number): Promise<number> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const acc = await client.query("SELECT id FROM accounts WHERE id = $1 FOR UPDATE", [fromId]);
    if (acc.rowCount === 0) throw new AppError("ACCOUNT_NOT_FOUND");
    const { rows } = await client.query(
      "SELECT COALESCE(SUM(amount), 0) AS sent FROM transfers WHERE from_id = $1 AND created_at >= date_trunc('day', now())",
      [fromId],
    );
    if (Number(rows[0].sent) + amount > dailyLimit) throw new AppError("DAILY_LIMIT");
    await client.query("UPDATE accounts SET balance = balance - $1 WHERE id = $2", [amount, fromId]);
    await client.query("UPDATE accounts SET balance = balance + $1 WHERE id = $2", [amount, toId]);
    const t = await client.query("INSERT INTO transfers (from_id, to_id, amount) VALUES ($1, $2, $3) RETURNING id", [fromId, toId, amount]);
    await client.query("COMMIT");
    return t.rows[0].id;
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}

הנעילה על שורת החשבון משמשת "מנעול" לכל ההעברות שלו — גם אם החוק הוא על שורות ב־transfers. זו התבנית לכל "מגבלה על סכום של כמה שורות" (מגבלת אשראי, מכסת API, "עד 3 תורים לשבוע").

⚠️ טעויות נפוצות
  • לנעול את שורות ה־transfers של היום (SELECT ... FOR UPDATE עליהן) — בתחילת היום אין שורות, אז אין מה לנעול, וכולם עוברים.
  • להשוות עם Date מ־Node במקום now() של המסד — שני שעונים, ושני אזורי זמן.
