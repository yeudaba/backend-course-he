P18-E26 · withTransaction — עוזר שכותבים פעם אחת 🤖 ✍️ מאפס רמה 3

💡 רמז 1

ה־import: import type { Pool, PoolClient } from "pg";. גוף withTransaction הוא בדיוק הדפוס מ־P18-E07. ההבדל היחיד: במקום שלוש שאילתות באמצע, ‏const result = await fn(client);.

💡 רמז 2

transferAll מחזירה את מה ש־withTransaction מחזירה: return withTransaction(pool, async (client) => { ...; return amount; });. בתוך ה־callback, כל throw מגיע ל־catch של withTransaction, ומשם ל־ROLLBACK. ‏יעד לא קיים: ‏rowCount === 0 אחרי ה־UPDATE שלו. ‏balance מגיע מ־pg כמחרוזת (‏numeric), ולכן Number(...).

✅ פתרון
// P18-E26: withTransaction — עוזר שכותבים פעם אחת
import type { Pool, PoolClient } from "pg";

export async function withTransaction<T>(pool: Pool, fn: (client: PoolClient) => Promise<T>): Promise<T> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const result = await fn(client);
    await client.query("COMMIT");
    return result;
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}

export async function transferAll(pool: Pool, fromId: number, toId: number): Promise<number> {
  return withTransaction(pool, async (client) => {
    const { rows } = await client.query("SELECT balance FROM accounts WHERE id = $1 FOR UPDATE", [fromId]);
    if (rows.length === 0) throw new Error(`חשבון לא קיים: ${fromId}`);
    const amount = Number(rows[0].balance);
    if (amount === 0) throw new Error("אין מה להעביר");
    await client.query("UPDATE accounts SET balance = 0 WHERE id = $1", [fromId]);
    const to = await client.query("UPDATE accounts SET balance = balance + $1 WHERE id = $2", [amount, toId]);
    if (to.rowCount === 0) throw new Error(`חשבון לא קיים: ${toId}`);
    await client.query("INSERT INTO transfers (from_id, to_id, amount) VALUES ($1, $2, $3)", [fromId, toId, amount]);
    return amount;
  });
}

עכשיו transferAll מכילה רק את מה שמיוחד לה. אין בה BEGIN, ‏ROLLBACK או release, ולכן גם אין איפה לשכוח אותם. כל פונקציה עתידית שצריכה transaction תקבל את אותה התנהגות נכונה בחינם. זה בדיוק מה ש־Prisma נותן ב־$transaction(async (tx) => ...) (פרק 19).

ה־<T> (generic, פרק 11) מעביר את הטיפוס של מה ש־fn מחזירה הלאה. ‏withTransaction(pool, async () => 5) היא Promise<number>, ו־TypeScript יודע את זה בלי שתכתוב.

שגיאה ב"יעד לא קיים" מגיעה אחרי שכבר איפסנו את המקור. בלי transaction הכסף היה נעלם. כאן ה־ROLLBACK מחזיר הכול.

⚠️ טעויות נפוצות
  • ב־catch לבלוע את השגיאה (return null) — מי שקרא חושב שהכול הצליח.
  • client.release() בסוף ה־try ולא ב־finally — כל שגיאה משאירה חיבור תפוס, ואחרי כמה שגיאות ה־pool נתקע.
  • fn(client) בלי await — ‏COMMIT רץ לפני שהשאילתות של fn הסתיימו, ושגיאה שלהן כבר לא תגיע ל־catch.
  • לקרוא ל־pool.query בתוך fn במקום ל־client.query — השאילתה רצה בחיבור אחר, מחוץ ל־transaction.

P18-E27 · מאחד שליפות (batch loader) 🤖 🔁 חזרה רמה 3

💡 רמז 1

ה־closure שומר Map של id ← רשימת "ממתינים" ({ resolve, reject } מתוך new Promise). ‏load מוסיף ממתין. אם ה־Map היה ריק לפני ההוספה, זו הקריאה הראשונה בסיבוב, ולכן היא מתזמנת את השליחה: setTimeout(flush, 0).

💡 רמז 2

ב־flush: קודם const batch = waiting; waiting = new Map();, כדי שקריאות חדשות ייכנסו לסיבוב הבא. אחר כך שאילתה עם [...batch.keys()], ‏Map של התוצאות לפי id, ולולאה שקוראת ל־resolve(byId.get(id) ?? null) לכל ממתין. ב־catch: ‏reject(err) לכולם.

✅ פתרון
// P18-E27: מאחד שליפות (batch loader)
import type { Pool } from "pg";

export type Person = { id: number; full_name: string };
type Waiter = { resolve: (p: Person | null) => void; reject: (err: unknown) => void };

export function createPersonLoader(pool: Pick<Pool, "query">) {
  let waiting = new Map<number, Waiter[]>();

  async function flush() {
    const batch = waiting;
    waiting = new Map();
    try {
      const { rows } = await pool.query("SELECT id, full_name FROM people WHERE id = ANY($1)", [[...batch.keys()]]);
      const byId = new Map<number, Person>(rows.map((p: Person) => [p.id, p]));
      for (const [id, waiters] of batch) {
        for (const w of waiters) w.resolve(byId.get(id) ?? null);
      }
    } catch (err) {
      for (const waiters of batch.values()) {
        for (const w of waiters) w.reject(err);
      }
    }
  }

  return function load(id: number): Promise<Person | null> {
    return new Promise((resolve, reject) => {
      if (waiting.size === 0) setTimeout(flush, 0);
      const list = waiting.get(id) ?? [];
      list.push({ resolve, reject });
      waiting.set(id, list);
    });
  };
}

שלושה דברים חיים ב־closure, ובכל loader יש עותק משלהם: ה־Map של הממתינים, הפונקציה flush, והחיבור למסד. לכן שני loaders לא מערבבים בקשות.

new Promise((resolve, reject) => ...) מאפשר "להחזיר תשובה אחר כך": ‏load מחזירה Promise מיד, ושומרת את resolve בצד. רק כשהשאילתה חוזרת, flush קוראת לו. זה ה־Promise "הידני" מפרק 10, ופה רואים בשביל מה הוא קיים.

ההחלפה waiting = new Map() לפני ה־await חשובה. בזמן שהשאילתה רצה, קריאות חדשות נכנסות ל־Map החדש ומתזמנות סיבוב משלהן, במקום ללכת לאיבוד.

בפרויקטי GraphQL זה הכלי הסטנדרטי נגד N+1: כל שדה "מבקש" את מה שהוא צריך, וה־loader מאחד הכול.

⚠️ טעויות נפוצות
  • setTimeout(flush, 0) בכל קריאה — כמה flush רצים, והשני שולח שאילתה עם רשימה ריקה (או שולח שוב את אותם ids).
  • לנקות את ה־Map רק אחרי ה־await — קריאות שהגיעו בזמן השאילתה נמחקות ולא מקבלות תשובה לעולם.
  • לחזור עם rows[i] לפי מקום במערך — המסד לא מבטיח שהשורות יחזרו באותו סדר, ו־id חסר מזיז את כולם.
  • לשכוח reject ב־catch — כשהמסד נופל, כל הקוראים תקועים לנצח.

P18-E28 · שלושת הלקוחות המובילים בכל חודש 🤖 🔁 חזרה רמה 3

💡 רמז 1

שלושה שלבים, כל אחד ב־CTE משלו: (1) monthly — ‏GROUP BY לפי חודש ולקוח. (2) ranked — ‏ROW_NUMBER() OVER (PARTITION BY month ORDER BY revenue DESC, customer_id). ‏(3) WHERE place <= 3.

💡 רמז 2

למה לא WHERE ROW_NUMBER() ... <= 3 ישר? כי WHERE רץ לפני פונקציות החלון, ולכן אי אפשר לסנן לפיהן באותה רמה. כאן צריך עוד שכבה. הטווח: created_at >= '2025-01-01' AND created_at < '2025-04-01'.

✅ פתרון
WITH monthly AS (
  SELECT date_trunc('month', created_at)::date AS month, customer_id, SUM(total) AS revenue
  FROM big_orders
  WHERE status IN ('paid', 'shipped')
    AND created_at >= '2025-01-01' AND created_at < '2025-04-01'
  GROUP BY 1, 2
),
ranked AS (
  SELECT month, customer_id, revenue,
         ROW_NUMBER() OVER (PARTITION BY month ORDER BY revenue DESC, customer_id) AS place
  FROM monthly
)
SELECT month, place, customer_id, revenue
FROM ranked
WHERE place <= 3
ORDER BY month, place;

הדוח הזה דורש שני "צמצומים" שונים: ‏GROUP BY הופך מאות הזמנות של לקוח בחודש לשורה אחת, והחלון מדרג את השורות האלה בתוך כל חודש. כל שלב ב־CTE משלו, וכל שלב קריא לבד.

הטווח נכתב כ־>= התחלה ו־< סוף, ולא date_trunc(...) IN (...). כך, אם יש index על created_at (שיעור 3), המסד יכול לקרוא רק את שלושת החודשים במקום את כל 200,000 השורות. פונקציה על העמודה ב־WHERE מונעת שימוש ב־index.

ORDER BY revenue DESC, customer_id בתוך החלון: בלי קריטריון שני, בתיקו המסד בוחר סדר כרצונו, והדוח יוצא שונה בכל הרצה.

⚠️ טעויות נפוצות
  • RANK() במקום ROW_NUMBER() — בתיקו שני לקוחות מקבלים אותו מקום, ויכולים לחזור ארבעה.
  • created_at <= '2025-03-31' — זה 2025-03-31 00:00, ורוב היום האחרון נחתך.
  • PARTITION BY customer_id — מדרג חודשים לכל לקוח, במקום לקוחות לכל חודש.

P18-E01 · מה נשמר? רמה 1

💡 רמז 1

ב־ב' אין BEGIN — כל פקודה עומדת לבד. ומה קורה ב־UPDATE שלא מוצא שורה?

💡 רמז 2

ב־ג', ל־Dana יש 1000.

✅ פתרון
  1. Dana 1000, Noa 0 — הכול בוטל.
  2. Dana 900, Noa 0 — באג: הפקודה השנייה לא נכשלה, היא פשוט עדכנה 0 שורות (UPDATE 0). 100 ש״ח נעלמו. transaction לא היה עוזר כאן — צריך לבדוק rowCount ולזרוק (ואז ה־ROLLBACK יבטל את הראשונה).
  3. Dana 1000, Noa 0 — העדכון הראשון הפר את ה־CHECK, ה־transaction בוטל, ו־COMMIT הפך ל־ROLLBACK.
⚠️ טעויות נפוצות
  • לחשוב ש"0 שורות עודכנו" זו שגיאה — מבחינת המסד זו הצלחה.

P18-E02 · ציר זמן רמה 1

💡 רמז 1

שני ה־SELECT־ים לפני שני ה־UPDATE־ים.

💡 רמז 2

ה־UPDATE כותב מספר קבוע (50), לא balance - 200.

✅ פתרון
  1. A קורא 250, B קורא 250, A כותב 50, B כותב 50. היתרה 50 — אבל יצאו 400 ש״ח. הבנק הפסיד 200.
  2. לא. אף כתיבה לא שלילית (שתיהן כותבות 50). ה־CHECK תופס רק ערכים לא חוקיים, לא חישוב שגוי.
  3. לא, ב־Read Committed: שני ה־SELECT־ים רואים 250 (אף אחד עוד לא עשה commit), והכתיבות פשוט ממתינות אחת לשנייה. מה שכן מציל: UPDATE accounts SET balance = balance - 200 WHERE id = 2 AND balance >= 200 ובדיקת rowCount, או SELECT ... FOR UPDATE בתוך transaction.
⚠️ טעויות נפוצות
  • "זה לא יקרה, הבקשות לא מגיעות באותה מילישנייה" — לחיצה כפולה על כפתור, ו־retry אוטומטי של אפליקציה, שולחים בדיוק כך.

P18-E03 · איזה כלי? רמה 1

💡 רמז 1

מה הכי פשוט שעובד? עדכון אטומי ואילוצים — קודם.

💡 רמז 2

4 הוא חוק על כמה שורות יחד — אף שורה בודדת לא "שגויה".

✅ פתרון
  1. עדכון אטומי עם תנאי (WHERE stock >= $qty) + CHECK כרשת ביטחון.
  2. UNIQUE על האימייל. אל תבדוק "האם קיים" ואז תכניס — המסד יתפוס, ואת השגיאה (23505) מתרגמים ל־409.
  3. FOR UPDATE על שני החשבונות (לפי סדר id), ואז כל הבדיקות בקוד, ואז העדכונים — הכול ב־transaction אחד.
  4. Serializable + ניסיון חוזר: כל ביטול לבד חוקי; רק השילוב שבור. (חלופה: לנעול את כל שורות המשמרת עם FOR UPDATE לפני הבדיקה.)
  5. עדכון אטומי: SET views = views + 1. (בהיקפים ענקיים — צוברים בזיכרון/Redis ומעדכנים בקבוצות, פרק 26.)
⚠️ טעויות נפוצות
  • להשתמש ב־Serializable "בכל מקום ליתר ביטחון" — כל transaction צריך מנגנון ניסיון חוזר, והביצועים יורדים.

P18-E04 · index או לא? רמה 1

💡 רמז 1

index עוזר כשהוא מצמצם הרבה, או חוסך מיון.

💡 רמז 2

index על col לא עוזר ל־f(col).

✅ פתרון
  1. ✔ (customer_id, created_at) — מוצא את הלקוח וכבר ממוין, עוצר אחרי 20.
  2. ✘ — 95% מהטבלה; סריקה מלאה זולה יותר מקפיצות. (index חלקי על 5% הנותרים — כן, אם שואלים עליהם.)

  5. ✔ (created_at) — טווח קטן מתוך טבלה גדולה.
  6. ✘ צריך — אבל כבר יש: code הוא כנראה מפתח ראשי או UNIQUE. וגם בלי — 200 שורות נסרקות במיקרו־שניות.
⚠️ טעויות נפוצות
  • להוסיף index על כל עמודה שמופיעה ב־WHERE כלשהו — כל INSERT ישלם על כולם.

P18-E05 · כמה שאילתות? רמה 1

💡 רמז 1

1 + 50 × (1 + 1 + 3).

💡 רמז 2

WHERE id = ANY($1) עם מערך, ו־JOIN בין order_items ל־products.

✅ פתרון

1 + 50 + 50 + 150 = 251 שאילתות, ברצף (כל await מחכה לקודם).

const orders = (await pool.query("SELECT * FROM orders ORDER BY id DESC LIMIT 50")).rows;
const orderIds = orders.map((o) => o.id);
const customerIds = [...new Set(orders.map((o) => o.customer_id))];
const customers = (await pool.query("SELECT * FROM customers WHERE id = ANY($1)", [customerIds])).rows;
const items = (await pool.query(
  `SELECT oi.*, p.name AS product_name, p.price AS product_price
   FROM order_items oi JOIN products p ON p.id = oi.product_id
   WHERE oi.order_id = ANY($1)`, [orderIds])).rows;
const customersById = new Map(customers.map((c) => [c.id, c]));
for (const o of orders) {
  o.customer = customersById.get(o.customer_id);
  o.items = items.filter((i) => i.order_id === o.id);
}

3 שאילתות, תמיד. (ה־filter בלולאה הוא O(n·m) — עם 50 הזמנות זה זניח; עם אלפים — Map מ־order_id לרשימה.)

⚠️ טעויות נפוצות
  • "לתקן" עם Promise.all על 250 השאילתות — פחות זמן המתנה, אבל אותו עומס על המסד, ו־pool של 10 חיבורים מתמלא.

P18-E07 · transfer מ־Node 🤖 רמה 2

💡 רמז 1

הדפוס מהשיעור: pool.connect(), try/catch/finally.

💡 רמז 2

INSERT ... RETURNING id, ו־rows[0].id.

✅ פתרון
// P18-E07
import type { Pool } from "pg";

export async function transfer(pool: Pool, fromId: number, toId: number, amount: number): Promise<number> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    await client.query("UPDATE accounts SET balance = balance - $1 WHERE id = $2", [amount, fromId]);
    await client.query("UPDATE accounts SET balance = balance + $1 WHERE id = $2", [amount, toId]);
    const { rows } = await client.query("INSERT INTO transfers (from_id, to_id, amount) VALUES ($1, $2, $3) RETURNING id", [fromId, toId, amount]);
    await client.query("COMMIT");
    return rows[0].id;
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}
⚠️ טעויות נפוצות
  • return לפני COMMIT — ה־finally משחרר חיבור עם transaction פתוח, והבקשה הבאה שתקבל אותו תמשיך בתוך ה־transaction הזה.

P18-E08 · פרמטרים, לא שרשור 🤖 רמה 2

💡 רמז 1

pool.query("... WHERE owner = $1", [owner])

💡 רמז 2

בחיפוש: התו % שהמשתמש הקליד הוא "כל רצף" ב־LIKE. צריך לנטרל אותו: text.replace(/[\\%_]/g, "\\$&"), ואז ILIKE '%' || $1 || '%'.

✅ פתרון
// P18-E08
import type { Pool } from "pg";

export async function findByOwner(pool: Pool, owner: string) {
  const { rows } = await pool.query("SELECT id, owner, balance FROM accounts WHERE owner = $1 ORDER BY id", [owner]);
  return rows;
}

export async function searchOwners(pool: Pool, text: string) {
  const escaped = text.replace(/[\\%_]/g, "\\$&"); // % ו־_ שהמשתמש הקליד — כתווים רגילים
  const { rows } = await pool.query("SELECT id, owner, balance FROM accounts WHERE owner ILIKE '%' || $1 || '%' ORDER BY id", [escaped]);
  return rows;
}

💡 רמז 2

✅ פתרון
// P18-E13
import type { Pool } from "pg";

export class AppError extends Error {
  code: string;
  constructor(code: string, message = code) {
    super(message);
    this.code = code;
  }
}

export async function transferSafe(pool: Pool, fromId: number, toId: number, amount: number) {
  if (fromId === toId) throw new AppError("SAME_ACCOUNT");
  if (!(amount > 0)) throw new AppError("INVALID_AMOUNT");

  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    // נעילה לפי סדר id — שתי העברות הפוכות לא יחכו זו לזו במעגל
    const { rows } = await client.query("SELECT id, balance FROM accounts WHERE id = ANY($1) ORDER BY id FOR UPDATE", [[fromId, toId]]);
    const from = rows.find((r) => r.id === fromId);
    const to = rows.find((r) => r.id === toId);
    if (!from || !to) throw new AppError("ACCOUNT_NOT_FOUND");
    if (Number(from.balance) < amount) throw new AppError("INSUFFICIENT_FUNDS");

    const a = await client.query("UPDATE accounts SET balance = balance - $1 WHERE id = $2 RETURNING balance", [amount, fromId]);
    const b = await client.query("UPDATE accounts SET balance = balance + $1 WHERE id = $2 RETURNING balance", [amount, toId]);
    const t = await client.query("INSERT INTO transfers (from_id, to_id, amount) VALUES ($1, $2, $3) RETURNING id", [fromId, toId, amount]);
    await client.query("COMMIT");
    return { transferId: t.rows[0].id, fromBalance: Number(a.rows[0].balance), toBalance: Number(b.rows[0].balance) };
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}
⚠️ טעויות נפוצות
  • לנעול fromId ואז toId — זה בדיוק התרחיש של deadlock מהשיעור.

✅ פתרון
// P18-E14
import type { Pool } from "pg";

export class AppError extends Error {
  code: string;
  constructor(code: string, message = code) {
    super(message);
    this.code = code;
  }

export async function bookSeat(pool: Pool, eventId: number, userId: number): Promise<number> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const event = await client.query("SELECT capacity FROM events WHERE id = $1 FOR UPDATE", [eventId]);
    if (event.rowCount === 0) throw new AppError("EVENT_NOT_FOUND");
    const { rows } = await client.query("SELECT COUNT(*)::int AS taken FROM bookings WHERE event_id = $1", [eventId]);
    const capacity = event.rows[0].capacity;
    try {
      await client.query("INSERT INTO bookings (event_id, user_id) VALUES ($1, $2)", [eventId, userId]);
    } catch (err) {
      if ((err as { code?: string }).code === "23505") throw new AppError("ALREADY_BOOKED");
      throw err;
    }
    if (rows[0].taken >= capacity) throw new AppError("SOLD_OUT");
    await client.query("COMMIT");
    return capacity - rows[0].taken - 1;
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}

שים לב לסדר: קודם ה־INSERT (כדי ש"כבר רשום" ינצח את "מלא" — משתמש רשום שמנסה שוב צריך לשמוע "אתה כבר רשום"), ואז בדיקת המקום — ואם מלא, ה־ROLLBACK מבטל את ה־INSERT. הנעילה על שורת האירוע היא מה שהופך את "סופרים ← בודקים ← מכניסים" לבטוח.

⚠️ טעויות נפוצות
  • לנעול את bookings עם FOR UPDATE — נועל רק שורות קיימות; את ההרשמה ה"חדשה" של המשתמש הבא אי אפשר לנעול מראש.

// P18-E18
import type { Pool } from "pg";

export async function listOrders(pool: Pool, { after, limit = 20 }: { after?: number; limit?: number } = {}) {

P18-E19 · ניסיון חוזר ב־Serializable 🤖 רמה 3

💡 רמז 1

💡 רמז 2

COMMIT יכול להיכשל ב־40001 — לכן הוא בתוך ה־try.

✅ פתרון
// P18-E19
import type { Pool, PoolClient } from "pg";

const RETRYABLE = new Set(["40001", "40P01"]);
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

export async function withSerializableRetry<T>(pool: Pool, work: (client: PoolClient) => Promise<T>, { retries = 5 } = {}): Promise<T> {
  const client = await pool.connect();
  try {
    for (let attempt = 0; ; attempt++) {
      try {
        await client.query("BEGIN ISOLATION LEVEL SERIALIZABLE");
        const result = await work(client);
        await client.query("COMMIT");
        return result;
      } catch (err) {
        await client.query("ROLLBACK");
        const code = (err as { code?: string }).code;
        if (!code || !RETRYABLE.has(code) || attempt >= retries) throw err;
        await sleep(5 + Math.random() * 20);
      }
    }
  } finally {
    client.release();
  }
}

ההמתנה האקראית ("jitter") חשובה: בלי, כל המתנגשים מנסים שוב באותה מילישנייה — ומתנגשים שוב.

⚠️ טעויות נפוצות
  • לנסות שוב רק את הפקודה שנכשלה — ב־40001 כל ה־transaction פסול; צריך להתחיל מה־SELECT הראשון.

P18-E24 · אתגר: checkout אמיתי 🤖 רמה 5

💡 רמז 1

💡 רמז 2

✅ פתרון
// P18-E24
import type { Pool } from "pg";

export class AppError extends Error {
  code: string;
  productId?: number;
  constructor(code: string, message = code) {
    super(message);
    this.code = code;
  }
}

interface Item { productId: number; quantity: number }

async function existingOrder(pool: Pool, key: string) {
  const { rows } = await pool.query("SELECT id, total FROM shop_orders WHERE idempotency_key = $1", [key]);
  return rows[0] && { orderId: rows[0].id, total: Number(rows[0].total), replayed: true };
}

export async function checkout(pool: Pool, { customerId, items, idempotencyKey }: { customerId: number; items: Item[]; idempotencyKey: string }) {
  if (items.length === 0) throw new AppError("EMPTY_CART");
  const before = await existingOrder(pool, idempotencyKey);
  if (before) return before;

  const qty = new Map<number, number>();
  for (const i of items) qty.set(i.productId, (qty.get(i.productId) ?? 0) + i.quantity);
  const ids = [...qty.keys()].sort((a, b) => a - b);

  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const { rows: products } = await client.query("SELECT id, price, stock FROM catalog WHERE id = ANY($1) ORDER BY id FOR UPDATE", [ids]);
    if (products.length !== ids.length) throw new AppError("PRODUCT_NOT_FOUND");
    for (const p of products) {
      if (p.stock < qty.get(p.id)!) {
        const err = new AppError("OUT_OF_STOCK");
        err.productId = p.id;
        throw err;
      }
    }
    const total = products.reduce((sum, p) => sum + Number(p.price) * qty.get(p.id)!, 0);
    let orderId: number;
    try {
      const { rows } = await client.query(
        "INSERT INTO shop_orders (customer_id, idempotency_key, total) VALUES ($1, $2, $3) RETURNING id",
        [customerId, idempotencyKey, total.toFixed(2)]
      );
      orderId = rows[0].id;
    } catch (err) {
      if ((err as { code?: string }).code !== "23505") throw err;
      await client.query("ROLLBACK");
      return (await existingOrder(pool, idempotencyKey))!; // בקשה מקבילה עם אותו מפתח ניצחה
    }
    for (const p of products) {
      await client.query("INSERT INTO shop_order_lines (order_id, product_id, quantity, unit_price) VALUES ($1, $2, $3, $4)", [orderId, p.id, qty.get(p.id), p.price]);
      await client.query("UPDATE catalog SET stock = stock - $1 WHERE id = $2", [qty.get(p.id), p.id]);
    }
    await client.query("COMMIT");
    return { orderId, total: Number(total.toFixed(2)), replayed: false };
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}

זה הלב של פרויקט הדגל, בגרסה מוקטנת. (ROLLBACK כפול — אחד ב־catch הפנימי ואחד בחיצוני — לא קורה, כי ה־return יוצא לפני. אבל אם תשנה את הזרימה, שים לב: ROLLBACK בלי transaction פתוח מחזיר רק אזהרה.)

⚠️ טעויות נפוצות
  • לבדוק idempotency רק בהתחלה — שתי לחיצות באותה מילישנייה עוברות שתיהן את הבדיקה. ה־UNIQUE הוא מה שבאמת מגן.
