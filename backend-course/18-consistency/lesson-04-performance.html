שיעור 4 — N+1 ו־pagination מהירה

⏱ ~30 דקות

🎯 בשיעור הזה
  • N+1: הבאג הכי נפוץ בביצועים של שרתים — ואיך מתקנים.
  • OFFSET גדול מול keyset pagination.

1. N+1

endpoint של "20 ההזמנות האחרונות, עם שם הלקוח":

const orders = await db.query("SELECT * FROM orders ORDER BY created_at DESC LIMIT 20");    // 1 שאילתה
for (const order of orders.rows) {
  const c = await db.query("SELECT full_name FROM customers WHERE id = $1", [order.customer_id]); // + 20 שאילתות
  order.customerName = c.rows[0].full_name;
}

21 שאילתות. כל אחת "מהירה" (1ms), אבל כל אחת היא נסיעה הלוך־חזור למסד (ובענן, המסד על שרת אחר — 1–5ms רשת לכל אחת). עם 100 הזמנות בעמוד — 101 שאילתות. ובסקירת קוד זה נראה תמים לגמרי: לולאה עם await.

התיקון — לתת למסד לעשות את העבודה, בשאילתה אחת או שתיים:

// אפשרות 1: JOIN
const { rows } = await db.query(`
  SELECT o.*, c.full_name AS customer_name
  FROM orders o JOIN customers c ON c.id = o.customer_id
  ORDER BY o.created_at DESC LIMIT 20`);

// אפשרות 2: שתי שאילתות — הרשימה, ואז כל הלקוחות שלה בבת אחת
const orders = (await db.query("SELECT * FROM orders ORDER BY created_at DESC LIMIT 20")).rows;
const ids = [...new Set(orders.map((o) => o.customer_id))];
const customers = (await db.query("SELECT id, full_name FROM customers WHERE id = ANY($1)", [ids])).rows;
const byId = new Map(customers.map((c) => [c.id, c]));
for (const o of orders) o.customerName = byId.get(o.customer_id).full_name;

אפשרות 2 היא מה ש־ORMs עושים כשמבקשים "include" (פרק 19) — ו־Map מפרק 7 הוא בדיוק הכלי לחבר. איך מגלים N+1? ביומן השאילתות: אותה שאילתה עם id שונה, עשרות פעמים ברצף לבקשה אחת.

2. OFFSET גדול

EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF, BUFFERS OFF)
SELECT id, total FROM big_orders ORDER BY id LIMIT 20 OFFSET 150000;
                                      QUERY PLAN
--------------------------------------------------------------------------------------
 Limit (actual rows=20.00 loops=1)
   ->  Index Scan using big_orders_pkey on big_orders (actual rows=150020.00 loops=1)
         Index Searches: 1
(3 rows)

OFFSET 150000 — המסד קורא 150,020 שורות וזורק 150,000. עמוד 7,500 איטי פי אלפים מעמוד 1. (ובונוס: אם בין עמוד לעמוד נוספה שורה, הלקוח יראה שורה פעמיים.)

Keyset ("cursor") pagination

EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF, BUFFERS OFF)
SELECT id, total FROM big_orders WHERE id > 150000 ORDER BY id LIMIT 20;
                                    QUERY PLAN
----------------------------------------------------------------------------------
 Limit (actual rows=20.00 loops=1)
   ->  Index Scan using big_orders_pkey on big_orders (actual rows=20.00 loops=1)
         Index Cond: (id > 150000)
         Index Searches: 1
(4 rows)

"תן לי 20 אחרי id 150000" — המסד קופץ ב־index ישר לשם וקורא 20 שורות. מהיר באותה מידה בעמוד 1 ובעמוד מיליון. ב־API: התשובה מחזירה nextCursor (ה־id האחרון), והלקוח שולח ?after=150000. זה מה שתראה ב־API של Stripe, GitHub ו־Slack.

💼 בעולם העבודה

"איך תמנע מכירה כפולה של הפריט האחרון?" ו"השאילתה איטית — מה תעשה?" הן שתי שאלות שמבדילות Junior חזק. תשובה טובה לשנייה: EXPLAIN ← לזהות Seq Scan על טבלה גדולה או N+1 ← index מתאים או שינוי שאילתה ← למדוד שוב. ולראשונה: עדכון אטומי עם תנאי, ואילוץ כרשת ביטחון.
