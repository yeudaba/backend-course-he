P18-E04 · index או לא? 🧠 הבנה רמה 1

💡 רמז 1

index עוזר כשהוא מצמצם הרבה, או חוסך מיון.

💡 רמז 2

index על col לא עוזר ל־f(col).

✅ פתרון
  1. ✔ (customer_id, created_at) — מוצא את הלקוח וכבר ממוין, עוצר אחרי 20.
  2. ✘ — 95% מהטבלה; סריקה מלאה זולה יותר מקפיצות. (index חלקי על 5% הנותרים — כן, אם שואלים עליהם.)
  3. ✔ index על ביטוי: ON orders (lower(coupon_code)). index על coupon_code לא יעזור.
  4. ✘ B-tree — אחוז בהתחלה. (יש index מיוחד לזה — pg_trgm — או מנוע חיפוש.)
  5. ✔ (created_at) — טווח קטן מתוך טבלה גדולה.
  6. ✘ צריך — אבל כבר יש: code הוא כנראה מפתח ראשי או UNIQUE. וגם בלי — 200 שורות נסרקות במיקרו־שניות.
⚠️ טעויות נפוצות
  • להוסיף index על כל עמודה שמופיעה ב־WHERE כלשהו — כל INSERT ישלם על כולם.

P18-E55 · ‏index על שתי עמודות — מתי הוא עוזר? 🧠 הבנה רמה 2

💡 רמז 1

ה־index ממוין קודם לפי status, ובתוך כל status — לפי created_at. כמו ספר טלפונים: שם משפחה, ואז שם פרטי.

💡 רמז 2

שאילתה 2: כמה מההזמנות הן cancelled? (אחת מכל שש.) כשהרבה שורות מתאימות, Bitmap — "אסוף את המיקומים, וקרא בלוקים לפי הסדר".

✅ פתרון
CREATE INDEX big_orders_status_created_idx ON big_orders (status, created_at);
EXPLAIN (COSTS OFF) SELECT id FROM big_orders WHERE status = 'pending' AND created_at >= '2025-12-20';
EXPLAIN (COSTS OFF) SELECT id FROM big_orders WHERE status = 'cancelled';
EXPLAIN (COSTS OFF) SELECT id FROM big_orders WHERE created_at >= '2025-12-20';
EXPLAIN (COSTS OFF) SELECT id FROM big_orders WHERE status = 'pending' ORDER BY created_at DESC LIMIT 5;
CREATE INDEX
                                                       QUERY PLAN
-------------------------------------------------------------------------------------------------------------------------
 Bitmap Heap Scan on big_orders
   Recheck Cond: ((status = 'pending'::text) AND (created_at >= '2025-12-20 00:00:00+02'::timestamp with time zone))
   ->  Bitmap Index Scan on big_orders_status_created_idx
         Index Cond: ((status = 'pending'::text) AND (created_at >= '2025-12-20 00:00:00+02'::timestamp with time zone))
(4 rows)

                        QUERY PLAN
----------------------------------------------------------
 Bitmap Heap Scan on big_orders
   Recheck Cond: (status = 'cancelled'::text)
   ->  Bitmap Index Scan on big_orders_status_created_idx
         Index Cond: (status = 'cancelled'::text)
(4 rows)

                                       QUERY PLAN
----------------------------------------------------------------------------------------
 Bitmap Heap Scan on big_orders
   Recheck Cond: (created_at >= '2025-12-20 00:00:00+02'::timestamp with time zone)
   ->  Bitmap Index Scan on big_orders_status_created_idx
         Index Cond: (created_at >= '2025-12-20 00:00:00+02'::timestamp with time zone)
(4 rows)

                                 QUERY PLAN
-----------------------------------------------------------------------------
 Limit
   ->  Index Scan Backward using big_orders_status_created_idx on big_orders
         Index Cond: (status = 'pending'::text)
(3 rows)

1 — כן, שתי העמודות בתנאי (שוויון ואז טווח). 2 — כן, דרך העמודה הראשונה. 3 — מפתיע: כן, אבל בלי "לקפוץ". ‏created_at לבד הוא "שם פרטי בלי שם משפחה" — הערכים מפוזרים בין כל ה־status־ים, אז המסד עובר על כל ה־index ובודק כל ערך (ה־Index Cond כאן הוא סינון, לא חיפוש). זה עדיין זול מסריקת הטבלה, כי ה־index קטן ממנה — אבל index שמתחיל ב־created_at היה מוצא את הטווח בקפיצה. 4 — כן, ובלי מיון: בתוך pending השורות כבר ממוינות לפי תאריך, והמסד פשוט קורא את העץ מהסוף (Backward).

⚠️ טעויות נפוצות
  • להוסיף index נפרד לכל עמודה ב־WHERE "ליתר ביטחון" — index מרובה עמודות בסדר הנכון עדיף כמעט תמיד על שניים נפרדים.

P18-E56 · ‏index שהשאילתה "מסתירה" ממנו 🧠 הבנה רמה 2

💡 רמז 1

ה־index ממוין לפי customer_id. האם הוא ממוין גם לפי customer_id + 0? (אנחנו יודעים שזה אותו דבר — המסד לא מנסה להוכיח את זה.)

💡 רמז 2

מיון של מספרים כטקסט: '10' < '9'.

✅ פתרון
CREATE INDEX big_orders_customer_id_idx ON big_orders (customer_id);
EXPLAIN (COSTS OFF) SELECT id FROM big_orders WHERE customer_id = 42;
EXPLAIN (COSTS OFF) SELECT id FROM big_orders WHERE customer_id + 0 = 42;
EXPLAIN (COSTS OFF) SELECT id FROM big_orders WHERE customer_id::text = '42';
CREATE INDEX
                      QUERY PLAN
-------------------------------------------------------
 Bitmap Heap Scan on big_orders
   Recheck Cond: (customer_id = 42)
   ->  Bitmap Index Scan on big_orders_customer_id_idx
         Index Cond: (customer_id = 42)
(4 rows)

                QUERY PLAN
------------------------------------------
 Gather
   Workers Planned: 1
   ->  Parallel Seq Scan on big_orders
         Filter: ((customer_id + 0) = 42)
(4 rows)

                     QUERY PLAN
----------------------------------------------------
 Gather
   Workers Planned: 1
   ->  Parallel Seq Scan on big_orders
         Filter: ((customer_id)::text = '42'::text)
(4 rows)

רק הראשונה. כל פונקציה או חישוב על העמודה — ‏+ 0, ‏::text, ‏lower(email), ‏date_trunc(...) — הופכים אותה לערך אחר, שה־index לא ממוין לפיו. הכלל: את החישוב עושים על הצד של הערך, והעמודה נשארת "חשופה" (או יוצרים index על הביטוי עצמו, כמו lower(owner) ב־P18-E12). זו בדיוק התקלה של P18-E22.

⚠️ טעויות נפוצות
  • ORM ששולח את המזהה כטקסט ועושה CAST על העמודה — השאילתה "עובדת" ואיטית פי אלף.

P18-E57 · איזה indexes כבר יש? 🧠 הבנה רמה 1

💡 רמז 1

מפתח ראשי ו־UNIQUE מקבלים index אוטומטית — כך המסד בודק כפילויות מהר.

💡 רמז 2

FK לא מקבל index אוטומטית. איזה FK לא "מכוסה" ב־index שמתחיל בו?

✅ פתרון
SELECT tablename, indexname
FROM pg_indexes
WHERE schemaname = current_schema() AND tablename IN ('shop_orders', 'shop_order_lines')
ORDER BY tablename, indexname;
    tablename     |            indexname
------------------+---------------------------------
 shop_order_lines | shop_order_lines_pkey
 shop_orders      | shop_orders_idempotency_key_key
 shop_orders      | shop_orders_pkey
(3 rows)

שלושה, כולם מהאילוצים: מפתח ראשי ו־UNIQUE ב־shop_orders, ומפתח ראשי של הזוג ב־shop_order_lines. ה־FK order_id מכוסה — הוא העמודה הראשונה במפתח הראשי. אבל product_id (FK ל־catalog) לא: "כל השורות של מוצר X" ומחיקת מוצר מ־catalog יסרקו את כל shop_order_lines. חסר CREATE INDEX ON shop_order_lines (product_id) (כמו ב־P18-E16).

⚠️ טעויות נפוצות
  • להוסיף index על order_id לבד — כפילות של המפתח הראשי (שמתחיל בו); עוד עלות כתיבה, בלי תועלת.

P18-E58 · למה המסד מתעלם מה־index? 🧠 הבנה רמה 2

💡 רמז 1

ב־accounts יש 4 שורות — דף אחד בדיסק.

💡 רמז 2

id > 1000 מחזיר 99.5% מהטבלה. כמה עולה לקפוץ ב־index 199,000 פעמים, לעומת לקרוא את הטבלה ברצף?

✅ פתרון
EXPLAIN (COSTS OFF) SELECT owner FROM accounts WHERE id = 2;
EXPLAIN (COSTS OFF) SELECT id FROM big_orders WHERE id > 1000;
EXPLAIN (COSTS OFF) SELECT id FROM big_orders WHERE id > 199000;
      QUERY PLAN
----------------------
 Seq Scan on accounts
   Filter: (id = 2)
(2 rows)

       QUERY PLAN
------------------------
 Seq Scan on big_orders
   Filter: (id > 1000)
(2 rows)

                     QUERY PLAN
-----------------------------------------------------
 Index Only Scan using big_orders_pkey on big_orders
   Index Cond: (id > 199000)
(2 rows)

המסד לא "חייב" להשתמש ב־index — הוא מעריך עלות (לפי סטטיסטיקות שנאספות ב־ANALYZE) ובוחר את הזולה. בטבלה של 4 שורות, וכשהתנאי מחזיר כמעט הכול — לקרוא הכול ברצף זול יותר. רק כשהתנאי בררני (1,000 מתוך 200,000) — index. Seq Scan בתוכנית הוא לא באג בפני עצמו; הוא באג כשהטבלה גדולה והתנאי מחזיר מעט.

⚠️ טעויות נפוצות
  • "לכפות" index (יש מסדים עם hints) — ברוב המקרים המסד צודק, ואם לא — הסטטיסטיקות ישנות (ANALYZE), לא האופטימייזר.

P18-E59 · באיזה סדר העמודות? 🧠 הבנה רמה 1

💡 רמז 1

חשוב על ספר טלפונים ממוין לפי (עיר, שם) מול (שם, עיר) — כשאתה מחפש "כל ה־Cohen בחיפה".

💡 רמז 2

בהצעה 2, כל ההזמנות מהחודש האחרון (של כל הלקוחות) הן רצף אחד בעץ. בתוכו — הלקוחות מעורבבים.

✅ פתרון

הצעה 1. בעץ ממוין לפי (customer_id, created_at), כל ההזמנות של לקוח 42 הן רצף אחד, ובתוכו ממוינות לפי תאריך — המסד קופץ ל"לקוח 42, מהתאריך הזה" וקורא רק את מה שצריך. בהצעה 2 הוא קופץ לתחילת החודש וצריך לעבור על ההזמנות של כל הלקוחות מאז, ולסנן. הכלל מהשיעור: עמודות השוויון קודם, עמודת הטווח/המיון בסוף. והצעה 1 עוזרת גם ל־customer_id = $1 לבד (העמודה הראשונה) — כך שהיא מחליפה גם index על customer_id בלבד.

⚠️ טעויות נפוצות
  • "העמודה עם הכי הרבה ערכים שונים ראשונה" — כלל אצבע נפוץ, אבל מה שקובע הוא איך השאילתה משתמשת בעמודות: שוויון ← טווח.

P18-E11 · index להזמנות של לקוח 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

על איזו עמודה השוויון, ולפי איזו ממיינים?

💡 רמז 2

(customer_id, created_at) — PostgreSQL יודע לקרוא index גם מהסוף להתחלה (DESC).

✅ פתרון
CREATE INDEX big_orders_customer_created_idx ON big_orders (customer_id, created_at);
CREATE INDEX
CREATE INDEX big_orders_customer_created_idx ON big_orders (customer_id, created_at);
EXPLAIN (COSTS OFF)
SELECT id, total, created_at FROM big_orders WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 10;
CREATE INDEX
                                  QUERY PLAN
-------------------------------------------------------------------------------
 Limit
   ->  Index Scan Backward using big_orders_customer_created_idx on big_orders
         Index Cond: (customer_id = 42)
(3 rows)

"Index Scan Backward" — קורא את ה־index מהסוף, ועוצר אחרי 10. אין צומת Sort בתוכנית.

⚠️ טעויות נפוצות
  • index על customer_id בלבד — אין סריקה מלאה, אבל יש Sort. index על (created_at, customer_id) — הסדר הפוך, והוא כמעט לא יעזור.

💡 רמז 2

P18-E15 · index חלקי 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

CREATE INDEX ... ON big_orders (created_at) WHERE ...

התנאי ב־index צריך להתאים לתנאי בשאילתה.

CREATE INDEX big_orders_open_created_idx ON big_orders (created_at) WHERE status IN ('paid', 'pending');
CREATE INDEX

P18-E16 · index ל־foreign keys 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

PostgreSQL יוצר index אוטומטית למפתח ראשי ול־UNIQUE — לא ל־foreign key.

💡 רמז 2

שני indexes, אחד לכל עמודה.

✅ פתרון
CREATE INDEX transfers_from_id_idx ON transfers (from_id);
CREATE INDEX transfers_to_id_idx ON transfers (to_id);
CREATE INDEX
CREATE INDEX

בלי index על ה־FK, כל DELETE FROM accounts סורק את כל טבלת transfers כדי לוודא שאין "יתומים". עם מיליוני העברות — מחיקה של חשבון אחד לוקחת שניות ונועלת. Prisma (פרק 19) ממליץ על זה, ו־MySQL אפילו עושה את זה אוטומטית.

⚠️ טעויות נפוצות
  • index אחד על (from_id, to_id) — עוזר ל־from_id, לא ל־to_id לבד.

P18-E22 · ה־index שלא בשימוש 🤖 💻 כתיבת קוד 🤖 רמה 4

💡 רמז 1

index על created_at לא עוזר לביטוי created_at::date — זו "פונקציה על העמודה".

💡 רמז 2

טווח: created_at >= '2025-06-01' AND created_at < '2025-06-02' (ב־session של שעון ישראל, אלה חצות בישראל).

✅ פתרון
CREATE INDEX big_orders_created_idx ON big_orders (created_at);

SELECT COUNT(*) AS orders, SUM(total) AS revenue
FROM big_orders
WHERE created_at >= '2025-06-01' AND created_at < '2025-06-02';
CREATE INDEX
 orders |  revenue
--------+-----------
    550 | 182965.75
(1 row)
⚠️ טעויות נפוצות
  • BETWEEN '2025-06-01' AND '2025-06-02' — כולל את חצות של ה־2, וכמעט אף פעם לא זה מה שמתכוונים.

P18-E60 · ‏index לחיפוש לפי סכום 🤖 💻 כתיבת קוד 🤖 רמה 1

💡 רמז 1

על איזו עמודה התנאי?

💡 רמז 2

CREATE INDEX big_orders_total_idx ON big_orders (total);

✅ פתרון
CREATE INDEX big_orders_total_idx ON big_orders (total);
EXPLAIN (COSTS OFF) SELECT id, customer_id FROM big_orders WHERE total = 123.45;
CREATE INDEX
                   QUERY PLAN

P18-E61 · ‏"ההזמנות ששולמו" של לקוח 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

שתי עמודות בשוויון, ועמודה אחת למיון.

💡 רמז 2

שוויון קודם (בכל סדר), המיון בסוף: (customer_id, status, created_at).

✅ פתרון
CREATE INDEX big_orders_customer_status_created_idx ON big_orders (customer_id, status, created_at);
EXPLAIN (COSTS OFF)
SELECT id, total, created_at FROM big_orders
WHERE customer_id = 42 AND status = 'paid'
ORDER BY created_at DESC LIMIT 5;
CREATE INDEX
                                      QUERY PLAN
--------------------------------------------------------------------------------------
 Limit
   ->  Index Scan Backward using big_orders_customer_status_created_idx on big_orders
         Index Cond: ((customer_id = 42) AND (status = 'paid'::text))
(3 rows)

"לקוח 42, סטטוס paid" הם רצף אחד בעץ, ממוין לפי תאריך — המסד קורא אותו מהסוף, חמש שורות, ועוצר. בלי created_at ב־index הוא היה מוצא את כל ההזמנות ששולמו של הלקוח וממיין אותן.

⚠️ טעויות נפוצות
  • (created_at, customer_id, status) — המיון ראשון; המסד יקרא את כל ההזמנות לפי תאריך עד שימצא חמש של הלקוח.

P18-E62 · בעלים ייחודי — רק לחשבונות פתוחים 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

שני רעיונות מהשיעור ביחד: UNIQUE INDEX ... (lower(owner)) ו־WHERE ... בסוף ה־index.

💡 רמז 2
CREATE UNIQUE INDEX accounts_open_owner_key ON accounts (lower(owner)) WHERE closed_at IS NULL;
✅ פתרון
ALTER TABLE accounts ADD COLUMN closed_at timestamptz;
CREATE UNIQUE INDEX accounts_open_owner_key ON accounts (lower(owner)) WHERE closed_at IS NULL;
ALTER TABLE
CREATE INDEX

ה־index מכיל רק חשבונות פתוחים, ולכן ה"ייחודיות" חלה רק עליהם. חשבון שנסגר "יוצא" מה־index, ואפשר לפתוח חדש. אותו טריק לכל "אחד פעיל בכל רגע": כתובת ברירת מחדל אחת ללקוח, משמרת פתוחה אחת לעובד, עגלה פתוחה אחת למשתמש.

⚠️ טעויות נפוצות
  • UNIQUE (owner, closed_at) — ב־UNIQUE רגיל שני NULLים נחשבים שונים, אז שני חשבונות פתוחים עוברים.

P18-E63 · חיפוש "מכיל" ב־endpoint 🧠 הבנה רמה 2

💡 רמז 1

בעץ ממוין לפי שם — איפה "מתחילים לחפש" כשאתה לא יודע את תחילת השם?

💡 רמז 2

יש indexes מסוג אחר (לא B-tree) שבנויים לחיפוש "מכיל": ‏trigram ‏(pg_trgm), וחיפוש טקסט מלא.

✅ פתרון
CREATE INDEX people_full_name_idx ON people (full_name);
EXPLAIN (COSTS OFF) SELECT id FROM people WHERE full_name = 'Customer #4242';
EXPLAIN (COSTS OFF) SELECT id FROM people WHERE full_name ILIKE '%4242%';
CREATE INDEX
                     QUERY PLAN
----------------------------------------------------
 Index Scan using people_full_name_idx on people
   Index Cond: (full_name = 'Customer #4242'::text)
(2 rows)

                QUERY PLAN
------------------------------------------
 Seq Scan on people
   Filter: (full_name ~~* '%4242%'::text)
(2 rows)

שוויון — דרך ה־index. "מכיל" — סריקה של כל הטבלה, לכל חיפוש. כמה אפשרויות, לפי הצורך: (1) חיפוש לפי תחילת השם (LIKE 'Dan%') — אפשר עם B-tree (עם text_pattern_ops); (2) "מכיל" — index מסוג GIN עם התוסף pg_trgm; (3) חיפוש מילים בטקסט ארוך — full-text search של PostgreSQL, או מנוע חיפוש חיצוני. ובכל מקרה: אורך מינימלי ל־q ב־Zod (min(2)) ו־LIMIT, כדי שחיפוש של אות אחת לא יחזיר מיליון שורות.

⚠️ טעויות נפוצות
  • להוסיף index רגיל על full_name ולהניח שהחיפוש "מאונדקס" — ה־EXPLAIN יראה שלא.

P18-E64 · ‏JOIN ו־index על ה־FK 🧠 הבנה רמה 2

💡 רמז 1

את הלקוח המסד מוצא מהר (מפתח ראשי). השאלה היא איך הוא מוצא את ההזמנות שלו.

💡 רמז 2

Nested Loop — לכל שורה בצד אחד, חפש בצד השני (כמו ה־leftJoin מ־P17-E57).

✅ פתרון
EXPLAIN (COSTS OFF)
SELECT o.id, o.total FROM people p JOIN big_orders o ON o.customer_id = p.id
WHERE p.id = 42;

CREATE INDEX big_orders_customer_id_idx ON big_orders (customer_id);

EXPLAIN (COSTS OFF)

WHERE p.id = 42;
                     QUERY PLAN
-----------------------------------------------------
 Nested Loop
   ->  Index Only Scan using people_pkey on people p
         Index Cond: (id = 42)
   ->  Seq Scan on big_orders o
         Filter: (customer_id = 42)
(5 rows)

CREATE INDEX
                         QUERY PLAN
-------------------------------------------------------------
 Nested Loop
   ->  Index Only Scan using people_pkey on people p

לפני: הלקוח נמצא ב־index של המפתח הראשי, אבל big_orders נסרקת כולה. אחרי: גם ההזמנות נמצאות דרך index. בכל JOIN, הצד ה"רבים" (העמודה עם ה־FK) הוא זה שצריך index — הצד של ה־id כבר מאונדקס כמפתח ראשי.

⚠️ טעויות נפוצות
  • להניח ש"יש FK, אז יש index" — ב־MySQL זה נכון (יחידה 25v); ב־PostgreSQL לא.

P18-E65 · ‏"עמוד 1 מתוך 10,000" — כמה עולה המספר? 🧠 הבנה רמה 2

💡 רמז 1

לספור את כל השורות — צריך לעבור על כולן (או על index שלם).

💡 רמז 2

האם המשתמש באמת צריך את המספר המדויק?

COUNT(*) של כל הטבלה תמיד עובר על כל השורות (אולי במקביל, עם כמה workers) — index לא חוסך את זה, כי המסד צריך לבדוק כל שורה. חלופות: (1) "יש עוד" במקום "מתוך N" — לבקש LIMIT 21 ולהציג 20 (keyset — שיעור 4); (2) הערכה מהסטטיסטיקות (reltuples) — "כ־200,000"; (3) מונה ששומרים בטבלה נפרדת ומעדכנים. ספירה של לקוח אחד עם index על customer_id — זולה.

⚠️ טעויות נפוצות
  • להריץ COUNT(*) על כל הטבלה בכל בקשה "כי זה רק מספר" — בטבלה של 50 מיליון שורות זו השאילתה הכי יקרה בעמוד.

P18-E66 · האם השאילתה משתמשת ב־index? — בקוד 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1
const { rows } = await pool.query(`EXPLAIN (FORMAT JSON) ${sql}`, params); const root = rows[0]["QUERY PLAN"][0].Plan;

(‏pg כבר מפענח את ה־JSON.)

💡 רמז 2

פונקציה רקורסיבית:

function walk(node: any) { ...; for (const child of node.Plans ?? []) walk(child); }
✅ פתרון
// P18-E66: האם השאילתה משתמשת ב־index? — בקוד
import type { Pool } from "pg";

export type PlanSummary = { nodes: string[]; seqScans: string[]; indexes: string[] };

export async function planSummary(pool: Pool, sql: string, params: unknown[] = []): Promise<PlanSummary> {
  const { rows } = await pool.query(`EXPLAIN (FORMAT JSON) ${sql}`, params);
  const root = rows[0]["QUERY PLAN"][0].Plan;
  const summary: PlanSummary = { nodes: [], seqScans: [], indexes: [] };
  const walk = (node: any) => {
    summary.nodes.push(node["Node Type"]);
    if (node["Node Type"] === "Seq Scan") summary.seqScans.push(node["Relation Name"]);
    if (node["Index Name"] && !summary.indexes.includes(node["Index Name"])) summary.indexes.push(node["Index Name"]);
    for (const child of node.Plans ?? []) walk(child);
  };
  walk(root);
  return summary;
}

עם הכלי הזה, בדיקה אוטומטית יכולה לוודא "השאילתה של מסך ההזמנות לא עושה Seq Scan על big_orders" — ואם מישהו ימחק index או ישנה את השאילתה, הבדיקה תיכשל לפני שהלקוחות ירגישו. (הבודקים של הפרק הזה עושים משהו דומה, עם טקסט במקום JSON.)

⚠️ טעויות נפוצות
  • לחפש "Seq Scan" בטקסט של התוכנית — עובד, אבל לא אומר על איזו טבלה; ב־JSON יש Relation Name.
  • להעביר את הפרמטרים בתוך המחרוזת — EXPLAIN מקבל $1 כמו כל שאילתה.

P18-E67 · ‏"index" ממוין בזיכרון 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

חיפוש בינארי של "האינדקס הראשון שבו המפתח >= v": ‏lo = 0, hi = n; כל עוד lo < hi — ‏mid, השוואה אחת, וחצי מהטווח נזרק. ‏range(from, to) = מ"הראשון ש־>= from" עד "הראשון ש־>= to". ול־eq(v) צריך גם "הראשון ש־> v".

💡 רמז 2

שמור את המפתחות במערך נפרד (keys) אחרי המיון, כדי לא לקרוא ל־key() בכל השוואה.

✅ פתרון
// P18-E67: "index" ממוין בזיכרון
export function createIndex<T>(rows: T[], key: (row: T) => number) {
  const sorted = rows.map((row, i) => ({ row, k: key(row), i })).sort((a, b) => a.k - b.k || a.i - b.i);
  const keys = sorted.map((s) => s.k);
  let count = 0;

  // האינדקס הראשון שבו keys[i] >= v (או > v כש־strict)
  const bound = (v: number, strict: boolean) => {
    let lo = 0;
    let hi = keys.length;
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      count++;
      if (strict ? keys[mid] <= v : keys[mid] < v) lo = mid + 1;
      else hi = mid;
    }
    return lo;
  };
  const slice = (a: number, b: number) => sorted.slice(a, Math.max(a, b)).map((s) => s.row);

  return {
    eq: (v: number) => slice(bound(v, false), bound(v, true)),
    range: (from: number, to: number) => slice(bound(from, false), bound(to, false)),
    comparisons: () => count,
  };
}

שני חיפושים בינאריים — "איפה מתחיל" ו"איפה נגמר" — ואז slice של רצף. זה בדיוק "Index Cond" ב־EXPLAIN: קפיצה לתחילת הטווח וקריאה ברצף. ‏log2(100,000) ≈ 17, כך ש־eq עושה כ־34 השוואות. המחיר: מיון אחד בהתחלה, וכל הוספה לנתונים מחייבת לשמור על הסדר — "כל כתיבה מעדכנת את ה־index".

⚠️ טעויות נפוצות
  • sorted.filter(...) בתוך eq — נכון, אבל 100,000 השוואות לכל חיפוש: Seq Scan בתחפושת.
  • למיין את rows עצמו (rows.sort) — משנה את המערך של מי שקרא לפונקציה.
