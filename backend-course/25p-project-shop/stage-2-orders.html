שיעור 3 — שלב 2: עגלה, הזמנה ומרוץ על המלאי

⏱ ~300 דקות · 🤖 PR3-ORDERS, PR3-RACE

🎯 בשלב הזה
  • עגלה לכל משתמש.
  • עגלה ← הזמנה, בטרנזקציה אחת, עם המחיר של עכשיו.
  • הלב של הפרויקט: שני לקוחות, יחידה אחרונה, אותו רגע.

1. עגלה

PUT /cart/items/:productId עם { quantity } קובע כמות (0 = הסרה) — PUT, כי זה idempotent: לחיצה כפולה לא מכפילה. יותר מהמלאי ← 409 OUT_OF_STOCK. אבל העגלה היא כוונה, לא שמירת מלאי: עד שהלקוח מזמין, מישהו אחר יכול לקנות. הבדיקה האמיתית — ברגע ההזמנה.

2. ההזמנה

POST /orders (עם Idempotency-Key, חובה — 400 IDEMPOTENCY_KEY_REQUIRED בלעדיו) עושה ארבעה דברים, הכול או כלום:

  1. מוריד מלאי לכל מוצר בעגלה.
  2. יוצר הזמנה עם שורה לכל מוצר — עם השם והמחיר של עכשיו.
  3. מחשב totalCents.
  4. מרוקן את העגלה.

מוצר אחד חסר ← 409 OUT_OF_STOCK עם details: [{ productId, requested, available }] — ושום דבר לא השתנה: גם המלאי של מוצרים אחרים שכבר "ירד" חוזר, והעגלה נשארת. זו טרנזקציה (פרק 18). ב־Prisma: prisma.$transaction(async (tx) => { … }) — שגיאה שנזרקת בתוכה = ROLLBACK.

3. המרוץ

יחידה אחת במלאי. שני לקוחות לוחצים "הזמן" באותה שנייה. הגרסה ה"טבעית":

const product = await tx.product.findUnique({ where: { id } });
if (product.stock < quantity) throw new HttpError(409, "OUT_OF_STOCK", "…");
await tx.product.update({ where: { id }, data: { stock: product.stock - quantity } });

שתי הבקשות קוראות stock = 1, שתיהן עוברות את הבדיקה, ושתיהן כותבות 0. הרצנו בדיוק את זה על הפתרון לדוגמה (עם השהיה קטנה בין הקריאה לכתיבה, כמו שקורה תחת עומס) — 12 לקוחות, 3 יחידות במלאי (פלט אמיתי של הבודק):

AssertionError [ERR_ASSERTION]: בדיוק 3 הצליחו, השאר 409 OUT_OF_STOCK: 201,201,201,201,201,201,201,201,201,201,201,201

12 הזמנות על 3 יחידות. והמלאי? לא שלילי — כל אחד כתב "מה שקראתי פחות אחד". זה lost update: גם ה־CHECK במסד לא עוזר, כי אף ערך שנכתב לא שלילי. טרנזקציה לבד גם לא — ב־READ COMMITTED (ברירת המחדל) הקריאה לא נועלת.

הפתרונות (פרק 18): עדכון מותנה — UPDATE products SET stock = stock - $q WHERE id = $id AND stock >= $q, ואם 0 שורות עודכנו ← אין מספיק. ב־Prisma: updateMany עם stock: { gte: q } ו־decrement, ובדיקה של count. PostgreSQL נועל את השורה בעדכון, הבקשה השנייה מחכה, ואחרי ה־COMMIT של הראשונה התנאי נבדק שוב על הערך העדכני. (חלופה: SELECT … FOR UPDATE — נועל כבר בקריאה.) ועוד שני דברים:

  • סדר קבוע: עגלה עם מוצרים 3 ו־7, ועגלה עם 7 ו־3 — אם כל אחת נועלת בסדר אחר, הן יכולות לחכות זו לזו לנצח (deadlock). ממיינים לפי productId.
  • רשת ביטחון: CHECK (stock >= 0) ב־migration. Prisma לא יודע להגדיר CHECK — מוסיפים ביד לקובץ ה־migration.sql (--create-only, עורכים, ואז migrate dev).

4. לבדוק

% npm run check PR3-ORDERS -- --dir ~/dev/coffee-shop
% npm run check PR3-RACE -- --dir ~/dev/coffee-shop

PR3-ORDERS: עגלה (קביעת כמות, מלאי, הסרה, עגלה לכל משתמש); הזמנה (מלאי יורד, עגלה מתרוקנת, ושינוי מחיר אחר כך לא משנה אותה); rollback כשמוצר אחד חסר; 422 על עגלה ריקה; Idempotency-Key (חובה, ו־replay); הזמנה של אחר ← 404; מנהל רואה הכול. PR3-RACE: 12 לקוחות על 3 יחידות ← בדיוק 3 הזמנות; 5 לחיצות במקביל עם אותו מפתח ← הזמנה אחת; ו־CHECK על המלאי במסד.
