P28.5-E02 · OLTP או OLAP? 🧠 הבנה רמה 1

💡 רמז 1

OLTP: הרבה פעולות קטנות על שורות בודדות, עם טרנזקציות. OLAP: מעט שאילתות שסורקות מיליונים — אבל רק כמה עמודות.

💡 רמז 2

שאלה "על מצב ברגע זה, שמשפיע על פעולה של משתמש" — איפה הנתון הכי עדכני?

✅ פתרון
  1. OLTP. שורה אחת לפי מפתח, ב־1ms, והנתון חייב להיות עדכני.
  2. OLAP. סורק את כל ההזמנות אבל רק 3–4 עמודות. ב־PostgreSQL של האפליקציה זה גם איטי וגם מאט את הלקוחות שקונים באותו רגע.
  3. OLTP. כתיבה קטנה עם טרנזקציה — מחסני נתונים לא בנויים לזה (ומשלמים בהם לפי סריקה, לא לפי כתיבה).
  4. OLAP, ועם APPROX_COUNT_DISTINCT (HyperLogLog, E18) — ספירה מדויקת של ייחודיים על 2 מיליארד שורות יקרה מאוד, והערכה של כמה אחוזים מספיקה לדוח (שיעור 4 מראה כמה היא סוטה בפועל).
  5. OLTP — ובתוך הטרנזקציה של ה־checkout (פרק 18). מחסן נתונים מתעדכן בדרך כלל באיחור של דקות־שעות (ETL).

הדפוס הנפוץ: האפליקציה כותבת ל־OLTP; תהליך (ETL/CDC) מעתיק למחסן; דוחות ואנליטיקה רצים שם. E25 בונה גרסה קטנה של זה.

P28.5-E04 · שורות מול עמודות 🧠 הבנה רמה 1

💡 רמז 1

CSV שומר שורה אחרי שורה, כטקסט. Parquet שומר עמודה אחרי עמודה, בינארי ודחוס.

💡 רמז 2

עמודה עם 5 ערכים שחוזרים מיליון פעמים — כמה מקום היא צריכה, אם שומרים אותה ביחד?

✅ פתרון
import fs from "node:fs";
import os from "node:os";
import path from "node:path";
import { DuckDBInstance } from "@duckdb/node-api";

const dir = fs.mkdtempSync(path.join(os.tmpdir(), "e04-"));
const db = await DuckDBInstance.create(":memory:");
const c = await db.connect();
await c.run(`CREATE TABLE events AS
  SELECT range AS id,
         ['view', 'click', 'add_to_cart', 'checkout', 'purchase'][1 + range % 5] AS type,
         1 + (range * 7919) % 50000 AS user_id,
         '/products/' || (range % 300) AS path,
         TIMESTAMP '2026-10-01' + to_seconds(range * 3) AS ts,
         (range * 31) % 1000 AS duration_ms
  FROM range(1000000)`);
await c.run(`COPY events TO '${dir}/events.csv' (HEADER)`);
await c.run(`COPY events TO '${dir}/events.parquet' (FORMAT parquet)`);
const mb = (f: string) => (fs.statSync(path.join(dir, f)).size / 1e6).toFixed(1) + " MB";
console.log("csv:    ", mb("events.csv"));
console.log("parquet:", mb("events.parquet"));

const r = await c.runAndReadAll(`SELECT type, count(*)::INTEGER AS n FROM '${dir}/events.parquet' GROUP BY type ORDER BY type`);
console.log(r.getRowObjects().map((x) => `${x.type}=${x.n}`).join(" "));
c.closeSync();
fs.rmSync(dir, { recursive: true });
csv:     58.4 MB
parquet: 14.6 MB
add_to_cart=200000 checkout=200000 click=200000 purchase=200000 view=200000

הקובץ קטן פי כמה, ועוד יותר חשוב — מה נקרא: לשאילתה על type, DuckDB קורא מה־Parquet רק את העמודה type (ועמודה עם 5 ערכים שונים נדחסת כמעט לאפס — dictionary encoding). מה־CSV הוא חייב לקרוא ולפרש את כל הקובץ, כל העמודות, כטקסט. כך בדיוק עובדים BigQuery, Snowflake ו־Databricks — ולכן שם משלמים לפי עמודות שנסרקו (E05, E17).

P28.5-E05 · כמה עולה שאילתה? 🧠 הבנה רמה 1

💡 רמז 1

LIMIT מקטין את מה שמוחזר — לא את מה שנסרק.

💡 רמז 2

partition pruning עובד רק כשה־WHERE על עמודת ה־partition עצמה, בצורה שהמנוע מזהה.

✅ פתרון
  1. 2TB. כל העמודות, כל השורות — ה־LIMIT מופעל אחרי הסריקה. (בקונסולה של BigQuery יש "preview" חינמי בדיוק בשביל זה.)
  2. ~100GB — עמודה אחת, כל השנה.
  3. ~270MB — עמודה אחת, יום אחד (100GB / 365).
  4. ~100GB — המנוע לא יודע שיום ב־ts שווה ל־day, אז אין pruning. אותה תוצאה, פי 365 בעלות.

כללי אצבע: לא SELECT *; תמיד WHERE על עמודת ה־partition; ו־clustering (מיון לפי עמודה שמסננים עליה הרבה, כמו customer_id) מקטין עוד. E17 מחשב את זה בקוד.

P28.5-E15 · SQL אנליטי ב־DuckDB 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

הכנסה של שורה: quantity * price_cents.

💡 רמז 2

אחוז מהסך הכולל — window function על האגרגציה: sum(sum(x)) OVER ().

✅ פתרון
-- P28.5-E15: דוח קטגוריות על 60,000 הזמנות (orders = files/orders.parquet)
SELECT
  category,
  count(*) AS orders,
  sum(quantity) AS units,
  round(sum(quantity * price_cents) / 100.0, 2) AS revenue,
  round(100.0 * sum(quantity * price_cents) / sum(sum(quantity * price_cents)) OVER (), 1) AS share_pct
FROM orders
GROUP BY category
ORDER BY revenue DESC;

P28.5-E16 · Parquet מחולק לפי יום 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

COPY (SELECT …, strftime(timezone('Asia/Jerusalem', created_at), '%Y-%m-%d') AS day FROM read_parquet(…)) TO 'dir' (FORMAT parquet, PARTITION_BY (day)).

💡 רמז 2

קריאה: read_parquet('dir/**/*.parquet', hive_partitioning = true) — עמודת day חוזרת מתוך שמות התיקיות.

✅ פתרון
// P28.5-E16: ייצוא ל־Parquet מחולק לפי יום — כך שאילתה על יום אחד קוראת קובץ אחד
import type { DuckDBConnection } from "@duckdb/node-api";

const q = (s: string) => `'${s.replaceAll("'", "''")}'`; // מחרוזת SQL בטוחה (נתיבים)

export async function exportByDay(conn: DuckDBConnection, sourceParquet: string, outDir: string): Promise<void> {
  await conn.run(`
    COPY (
      SELECT *, strftime(timezone('Asia/Jerusalem', created_at), '%Y-%m-%d') AS day
      FROM read_parquet(${q(sourceParquet)})
    ) TO ${q(outDir)} (FORMAT parquet, PARTITION_BY (day), OVERWRITE_OR_IGNORE)`);
}

export async function ordersPerDay(conn: DuckDBConnection, outDir: string): Promise<Record<string, number>> {
  const r = await conn.runAndReadAll(`
    SELECT day::VARCHAR AS day, count(*)::INTEGER AS n
    FROM read_parquet(${q(outDir + "/**/*.parquet")}, hive_partitioning = true)
    GROUP BY day ORDER BY day`);
  return Object.fromEntries(r.getRowObjects().map((x) => [String(x.day), Number(x.n)]));
}

זו בדיוק הצורה של data lake על S3 (יחידה 26.3): s3://lake/orders/day=2026-10-01/part-0.parquet. שאילתה עם WHERE day = '2026-10-15' קוראת תיקייה אחת מתוך 32 — partition pruning, כמו ב־BigQuery (E05).

P28.5-E17 · הערכת עלות סריקה 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

rows × (days/totalDays) × Σ bytes של העמודות.

💡 רמז 2

טבלה בלי partitions + days בשאילתה ← אין pruning.

✅ פתרון
// P28.5-E17: כמה בתים שאילתה סורקת במחסן נתונים עמודתי — וכמה זה עולה
export interface TableStats {
  rows: number;
  columns: Record<string, number>; // ממוצע בתים לערך, לכל עמודה
  partitionedBy?: string; // עמודת תאריך
  days?: number; // כמה ימים יש בטבלה (פרטישן לכל יום)
}

export interface QueryShape {
  columns: string[] | "*";
  days?: number; // WHERE על עמודת ה־partition: כמה ימים נבחרו
  limit?: number; // לא משנה את הסריקה!
}

const TiB = 2 ** 40;

export function estimateScan(t: TableStats, q: QueryShape, { pricePerTiB = 6.25 } = {}) {
  const cols = q.columns === "*" ? Object.keys(t.columns) : q.columns;
  for (const c of cols) if (!(c in t.columns)) throw new Error(`עמודה לא קיימת: ${c}`);
  const bytesPerRow = cols.reduce((s, c) => s + t.columns[c], 0); // עמודתי: רק העמודות שנבחרו
  const fraction = t.partitionedBy && t.days && q.days !== undefined ? Math.min(1, q.days / t.days) : 1; // partition pruning
  const bytes = Math.round(t.rows * fraction * bytesPerRow);
  return { bytes, costUsd: Math.round((bytes / TiB) * pricePerTiB * 100) / 100 };
}

(המחיר כאן — פרמטר. מחירים של שירותי ענן משתנים; בעבודה — מהדף הרשמי, ובדרך כלל דרך "dry run" שמחזיר את מספר הבתים לפני שמריצים.)

P28.5-E18 · HyperLogLog 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

idx = x >>> (32 − p); w = (x << p) >>> 0; ρ = Math.clz32(w) + 1.

💡 רמז 2

האינטואיציה: אם ראית hash שמתחיל ב־10 אפסים, כנראה ראית בסביבות 210 ערכים שונים. m רגיסטרים — m ניסויים, וממוצע הרמוני שלהם.

✅ פתרון
// P28.5-E18: HyperLogLog — כמה ערכים שונים, ב־4KB זיכרון
import { createHash } from "node:crypto";

export interface HLL {
  p: number;
  registers: Uint8Array;
}

export const createHLL = (p = 12): HLL => ({ p, registers: new Uint8Array(1 << p) });

export const hash32 = (value: string | number): number => createHash("sha1").update(String(value)).digest().readUInt32BE(0);

export function add(h: HLL, value: string | number): void {
  const x = hash32(value);
  const idx = x >>> (32 - h.p); // p הביטים העליונים ← איזה רגיסטר
  const w = (x << h.p) >>> 0; // השאר
  const rho = w === 0 ? 32 - h.p + 1 : Math.clz32(w) + 1; // מיקום ה־1 הראשון
  if (rho > h.registers[idx]) h.registers[idx] = rho;
}

export function count(h: HLL): number {
  const m = h.registers.length;
  let sum = 0;
  let zeros = 0;
  for (const r of h.registers) {
    sum += 2 ** -r;
    if (r === 0) zeros++;
  }
  const alpha = 0.7213 / (1 + 1.079 / m);
  const e = (alpha * m * m) / sum;
  if (e <= 2.5 * m && zeros > 0) return Math.round(m * Math.log(m / zeros)); // מעט ערכים: linear counting
  return Math.round(e);
}

export function mergeHLL(a: HLL, b: HLL): HLL {
  if (a.p !== b.p) throw new Error("p שונה");
  const out = createHLL(a.p);
  for (let i = 0; i < out.registers.length; i++) out.registers[i] = Math.max(a.registers[i], b.registers[i]);
  return out;
}

זה מה שמאחורי PFADD/PFCOUNT ב־Redis, APPROX_COUNT_DISTINCT ב־BigQuery ו־approx_count_distinct ב־DuckDB ו־Spark. ו־merge הוא הקסם: HLL לכל יום ← איחוד ← ייחודיים לחודש, בלי לספור מחדש.

P28.5-E22 · דוח יומי — שלוש תקלות 🤖 💻 כתיבת קוד 🤖 רמה 4

💡 רמז 1

created_at::DATE — באיזה אזור זמן?

💡 רמז 2

price_cents הוא מחיר ליחידה.

✅ פתרון
-- P28.5-E22: לקוחות פעילים והכנסה לכל יום (בשעון ישראל) — אחרי התיקון
SELECT
  strftime(timezone('Asia/Jerusalem', created_at), '%Y-%m-%d') AS day, -- תיקון 1: יום בישראל, לא UTC
  count(DISTINCT customer_id) AS active_customers,                      -- תיקון 2: לקוחות שונים, לא הזמנות
  round(sum(quantity * price_cents) / 100.0, 2) AS revenue               -- תיקון 3: כמות × מחיר
FROM orders
WHERE country = 'IL'
GROUP BY day
ORDER BY day
LIMIT 10;

P28.5-E27 · סיכום יומי של צפיות 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

שני CTE. ‏daily: ‏GROUP BY day עם COUNT(*) ו־COUNT(DISTINCT user_id). ‏by_path: ‏GROUP BY day, path עם COUNT(*), ועליו חלון. אחר כך JOIN ביניהם, רק לשורה הראשונה בכל יום.

💡 רמז 2

אפשר לשים חלון על תוצאה של GROUP BY באותה שאילתה: ROW_NUMBER() OVER (PARTITION BY viewed_at::date ORDER BY COUNT(*) DESC, path) AS rn. החלון רץ אחרי הקיבוץ, ולכן COUNT(*) בתוכו הוא הספירה של הקבוצה. ‏path שני ב־ORDER BY שובר את התיקו.

✅ פתרון
WITH daily AS (
  SELECT viewed_at::date AS day, COUNT(*) AS views, COUNT(DISTINCT user_id) AS users
  FROM page_views
  GROUP BY day
),
by_path AS (
  SELECT
    viewed_at::date AS day,
    path,
    COUNT(*) AS path_views,
    ROW_NUMBER() OVER (PARTITION BY viewed_at::date ORDER BY COUNT(*) DESC, path) AS rn
  FROM page_views
  GROUP BY viewed_at::date, path
)
SELECT d.day, d.views, d.users, p.path AS top_path, p.path_views AS top_path_views
FROM daily d
JOIN by_path p ON p.day = d.day AND p.rn = 1
ORDER BY d.day;

ב־2 בנובמבר יש תיקו: ‏/cart ו־/checkout עם 2 צפיות כל אחד. בלי path ב־ORDER BY של החלון, הבחירה ביניהם תלויה בסדר הפיזי של השורות. היום יוצא /cart, ואחרי VACUUM אולי /checkout. דשבורד שמחליף ערך בלי שהנתונים השתנו מאבד אמון מהר.

‏COUNT(DISTINCT user_id) הוא החלק היקר בשאילתה: צריך לזכור כל משתמש שנראה באותו יום. על מיליארד שורות משתמשים במקומו ב־HyperLogLog (‏E18), שנותן אומדן בזיכרון קבוע. ב־DuckDB (שיעור 4) זה approx_count_distinct.

⚠️ טעויות נפוצות
  • COUNT(user_id) — סופר צפיות, לא משתמשים.
  • לשים COUNT(DISTINCT user_id) ב־CTE של הנתיבים ולצרף — מקבלים משתמשים לנתיב, לא ליום.
  • MAX(COUNT(*)) — אי אפשר לקנן פונקציות צבירה. ובכל מקרה זה נותן את המספר, לא את הנתיב.
  • date_trunc('day', viewed_at) — עובד, אבל מחזיר timestamptz (חצות), לא תאריך.
