שיעור 4 — עמודות: Parquet, DuckDB ומחסני נתונים

⏱ ~55 דקות

🎯 בשיעור הזה
  • OLTP מול OLAP: שני סוגי עבודה, שני סוגי מסדים.
  • אחסון עמודתי ו־Parquet: למה שאילתה אנליטית קוראת פי 20 פחות.
  • DuckDB: מנוע אנליטי בתוך Node.
  • מחסני נתונים — BigQuery, Snowflake, Databricks: partitions, עלות, והערכות.

1. שני סוגי עבודה

PostgreSQL ו־MySQL בנויים ל־OLTP — הרבה פעולות קטנות: "שלוף את הזמנה 4821", "הוסף לעגלה", "הורד מלאי" — עם טרנזקציות ואינדקסים. שאלה כמו "הכנסה לפי קטגוריה וחודש, שלוש שנים אחורה" היא OLAP: קוראת מיליוני שורות, אבל רק 3–4 עמודות מתוך 30. על המסד של האפליקציה היא גם איטית וגם מאטה את הלקוחות שקונים באותו רגע (E02).

2. שורות מול עמודות

Parquet הוא פורמט הקבצים העמודתי הסטנדרטי: בינארי, דחוס, עם סכמה, ועם סטטיסטיקות (min/max) לכל קבוצת שורות — כך שמנוע יכול לדלג על חלקים שלא מתאימים ל־WHERE בלי לקרוא אותם. E04 מראה את ההבדל בגודל ובקריאה מול CSV.

3. DuckDB

DuckDB הוא "SQLite לאנליטיקה": ספרייה שרצה בתוך התהליך שלך, בלי שרת, ומריצה SQL עמודתי ומקבילי על Parquet, CSV, JSON — גם ישירות מ־S3. מ־Node:

import { DuckDBInstance } from "@duckdb/node-api";

const db = await DuckDBInstance.create(":memory:");
const conn = await db.connect();
const r = await conn.runAndReadAll(
  `SELECT category, round(sum(quantity * price_cents) / 100.0, 2) AS revenue
   FROM read_parquet('files/orders.parquet')
   WHERE country = $1
   GROUP BY category ORDER BY revenue DESC`,
  ["IL"],
);
console.log(r.getRowObjects());

שימו לב ל־$1 — פרמטרים, כמו ב־pg (פרק 16). ו־DuckDB מדבר SQL כמעט זהה ל־PostgreSQL — window functions, CTE, QUALIFY (E15, E22, E25).

4. מחסני נתונים

כשהנתונים גדלים לטרה־בייטים, אותן שאילתות רצות על מחסן נתונים — BigQuery (Google), Snowflake, Databricks (Spark ו־Delta Lake), Redshift (AWS). כולם עמודתיים, ושלושה רעיונות משותפים להם:

  • הפרדה בין אחסון לחישוב: הנתונים יושבים בזול (S3 / GCS), וכוח חישוב עולה רק בזמן שאילתה.
  • משלמים לפי סריקה (ב־BigQuery on-demand — לפי בתים; ב־Snowflake — לפי זמן של warehouse). SELECT * על טבלה של 2TB עולה כסף אמיתי — גם עם LIMIT 10 (E05, E17).
  • partitions ו־clustering: טבלה מחולקת לפי יום — שאילתה עם WHERE day = … קוראת חלק אחד מ־365. בדיוק כמו התיקיות day=… שתיצור ב־E16.

ועוד כלי אחד שחוזר בכולם — הערכות. "כמה משתמשים ייחודיים?" על מיליארד שורות — ספירה מדויקת דורשת לזכור כל משתמש; APPROX_COUNT_DISTINCT (HyperLogLog, E18) מעריך בזיכרון זעיר. הרצה אמיתית ב־DuckDB, על 5 מיליון צפיות:

import { DuckDBInstance } from "@duckdb/node-api";

const db = await DuckDBInstance.create(":memory:");
const c = await db.connect();
await c.run(`CREATE TABLE views AS SELECT range AS id, hash(range) % 1000000 AS user_id FROM range(5000000)`);
const r = await c.runAndReadAll(`
  SELECT count(*)::BIGINT AS views,
         count(DISTINCT user_id)::BIGINT AS exact_users,
         approx_count_distinct(user_id)::BIGINT AS approx_users
  FROM views`);
const row = r.getRowObjectsJson()[0];
console.log(row);
console.log("error:", ((Number(row.approx_users) / Number(row.exact_users) - 1) * 100).toFixed(1) + "%");
c.closeSync();
{ views: '5000000', exact_users: '993393', approx_users: '962761' }
error: -3.1%

הערכה, לא תשובה: כאן כמה אחוזים מתחת. ובבדיקות שהרצנו בזמן כתיבת היחידה, על מזהים רציפים (1, 2, 3…) הסטייה של DuckDB הגיעה לכ־12% — תלוי בהתפלגות ובמימוש. לדשבורד "כמה צפו השבוע" זה בסדר; לחיוב לקוחות — לעולם לא. לפני שמשתמשים בהערכה, בודקים אותה מול ספירה מדויקת על מדגם מהנתונים האמיתיים.

💼 בעולם העבודה

מודעה שמזכירה "BigQuery/Snowflake/Databricks" לא מצפה שג׳וניור Backend ינהל מחסן נתונים. היא מצפה שתבין למה הדוח לא רץ על המסד של האפליקציה, תכתוב SQL אנליטי (window functions, אגרגציות), תדע ש־SELECT * עולה כסף, ותבנה את הצינור שמעביר נתונים מהשירות שלך למחסן (שיעור 5). DuckDB על הלפטופ שלך מלמד את כל זה בלי חשבון ענן.
