P28.5-E05 · כמה עולה שאילתה?

🧠 הבנהרמה 1⏱ 15 דק׳ידע נדרש: שיעור 4

במחסן נתונים עמודתי (כמו BigQuery במצב on-demand) משלמים לפי בתים שנסרקו. טבלה events: 2TB, 20 עמודות, מחולקת (partitioned) לפי יום — שנה של נתונים. עמודת user_id תופסת כ־5% מהגודל. כמה בתים תסרוק כל שאילתה, בערך?

  1. SELECT * FROM events LIMIT 10
  2. SELECT user_id FROM events
  3. SELECT user_id FROM events WHERE day = '2026-11-01'
  4. SELECT user_id FROM events WHERE DATE(ts) = '2026-11-01' — כש־day היא עמודת ה־partition, ו־ts עמודה אחרת.

P28.5-E16 · Parquet מחולק לפי יום 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 20 דק׳ידע נדרש: שיעור 4

ב־P28.5-E16.ts:

  • exportByDay(conn, sourceParquet, outDir) — מעתיקה את כל ההזמנות ל־outDir, מחולקות לתיקייה לכל יום בשעון ישראל: day=2026-10-01/…parquet (hive partitioning).

P28.5-E17 · הערכת עלות סריקה 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 20 דק׳ידע נדרש: שיעור 4

ב־P28.5-E17.ts: estimateScan(table, query, { pricePerTiB = 6.25 }) ← { bytes, costUsd }. עמודתי: נסרקות רק העמודות שבשאילתה ("*" = כולן; עמודה לא קיימת — שגיאה). partition pruning: אם הטבלה מחולקת (partitionedBy + days) והשאילתה מסננת days — רק החלק הזה. P28.5-E18 · HyperLogLog 🤖

💻 כתיבת קוד 🤖רמה 3⏱ 30 דק׳ידע נדרש: שיעור 4

"כמה משתמשים ייחודיים?" על מיליארד צפיות — Set של מיליוני מחרוזות לא נכנס בזיכרון, ובטח לא ב־Redis לכל מוצר. HyperLogLog מעריך את המספר בטעות של ~1.6%, ב־4KB. ב־P28.5-E18.ts (hash32 מוכן), עם m = 2^p רגיסטרים:

  • add(h, value) — hash של 32 ביט; p הביטים העליונים בוחרים רגיסטר; ברגיסטר נשמר המקסימום של ρ — המיקום של ה־1 הראשון בשאר הביטים (משמאל, מ־1; כולם אפס ← 32 − p + 1).
  • count(h) — E = α·m² / Σ 2^(−M[j]), עם α = 0.7213 / (1 + 1.079/m); ואם E ≤ 2.5m ויש רגיסטרים ריקים (V) — m · ln(m/V) (linear counting). מעוגל.
  • mergeHLL(a, b) — מקסימום לכל רגיסטר.
