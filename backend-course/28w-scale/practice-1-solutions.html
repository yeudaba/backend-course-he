P28.5-E01 · ממוצע, p50, p99 🧠 הבנה רמה 1

💡 רמז 1

p99 = הערך ש־99% מהבקשות מהירות ממנו (או שוות לו). כאן — בקשה מספר 990 בסדר עולה.

💡 רמז 2

הסיכוי שכל 30 מהירות: 0.98^30.

✅ פתרון
  1. ממוצע: (980×40 + 20×3000) / 1000 = 99.2ms. p50: 40ms. p99: הבקשה ה־990 — 3000ms (980 הראשונות מהירות).
  2. לא. 2% מהבקשות מעל 500ms — p99 הוא 3 שניות. והממוצע (99ms) נראה מצוין.
  3. 1 − 0.98^30 ≈ 45%. כמעט חצי מהצפיות בדף איטיות, למרות ש"רק 2%" מהבקשות איטיות. זו הסיבה שאתרים גדולים מודדים p99 ו־p99.9 — המשתמש פוגש את הזנב הרבה יותר ממה שנדמה.
  4. ממוצע מערבב שתי אוכלוסיות ומסתיר את שתיהן: הוא גבוה מדי למקרה הרגיל ונמוך מדי לזנב. percentiles (p50 — החוויה הרגילה, p95/p99 — הזנב) מספרים את הסיפור; ו־max — את המקרה הגרוע (לפעמים GC או cold start).

// P28.5-E06: percentiles — לא ממוצע
export function percentile(sorted: number[], p: number): number {
  if (sorted.length === 0) throw new Error("אין דגימות");
  if (!(p > 0 && p <= 100)) throw new Error("p בין 0 (לא כולל) ל־100");
  const rank = Math.ceil((p / 100) * sorted.length); // nearest-rank: 1..n
  return sorted[rank - 1];
}

export interface Summary {
  count: number;
  min: number;
  max: number;
  mean: number;
  p50: number;
  p95: number;
  p99: number;
}

export function summarize(samples: number[]): Summary {
  const s = [...samples].sort((a, b) => a - b); // עותק, ומיון מספרי
  const mean = s.reduce((a, b) => a + b, 0) / s.length;
  return {
    count: s.length,
    min: s[0],
    max: s[s.length - 1],
    mean: Math.round(mean * 100) / 100,
    p50: percentile(s, 50),
    p95: percentile(s, 95),
    p99: percentile(s, 99),
  };
}
⚠️ טעויות נפוצות
  • samples.sort() בלי פונקציה — ממיין כמחרוזות: [100, 9, 25] ← [100, 25, 9]. וגם משנה את המערך של מי שקרא לך.

💡 רמז 2

✅ פתרון
// P28.5-E07: histogram שאפשר לאחד בין שרתים
// דליים לוגריתמיים: הגבול העליון של דלי i הוא 1.1^i מילישניות — שגיאה של עד 10%, בכל טווח
const GROWTH = 1.1;

export interface Histogram {
  counts: number[];
  total: number;
}

export const createHistogram = (): Histogram => ({ counts: [], total: 0 });

export const bucketOf = (ms: number): number => (ms <= 1 ? 0 : Math.ceil(Math.log(ms) / Math.log(GROWTH) - 1e-9));
export const upperBound = (i: number): number => GROWTH ** i;

export function record(h: Histogram, ms: number): void {
  if (!(ms >= 0)) throw new Error(`זמן לא תקין: ${ms}`);
  const i = bucketOf(ms);
  h.counts[i] = (h.counts[i] ?? 0) + 1;
  h.total++;
}

export function merge(...hs: Histogram[]): Histogram {
  const out = createHistogram();
  for (const h of hs) {
    h.counts.forEach((c, i) => {
      if (c) out.counts[i] = (out.counts[i] ?? 0) + c;
    });
    out.total += h.total;
  }
  return out;
}

export function histPercentile(h: Histogram, p: number): number {
  if (h.total === 0) throw new Error("histogram ריק");
  const rank = Math.ceil((p / 100) * h.total);
  let seen = 0;
  for (let i = 0; i < h.counts.length; i++) {
    seen += h.counts[i] ?? 0;
    if (seen >= rank) return Math.round(upperBound(i) * 100) / 100;
  }
  throw new Error("לא אמור לקרות");
}

למה זה חשוב: אי אפשר לחשב ממוצע של p99. שרת אחד מהיר (p99 = 20ms) ושרת אחד עמוס (p99 = 1000ms) — הממוצע 510ms לא מתאר אף אחד, וגם לא את p99 של המערכת. histograms מתאחדים בחיבור פשוט, ומהאיחוד מחשבים percentile אמיתי. (E21 — הבאג הזה בפועל.)

💡 רמז 1

💡 רמז 2

performance.now() לפני ואחרי כל בקשה.

✅ פתרון
// P28.5-E08: מחולל עומס קטן — concurrency קבוע, ו־percentiles של זמני תגובה
import { performance } from "node:perf_hooks";

export interface LoadResult {
  total: number;
  errors: number;
  durationMs: number;
  rps: number;
  latency: { p50: number; p95: number; p99: number; max: number };
}

const pct = (s: number[], p: number) => s[Math.max(0, Math.ceil((p / 100) * s.length) - 1)];

export async function runLoad(request: () => Promise<unknown>, { concurrency, total }: { concurrency: number; total: number }): Promise<LoadResult> {
  const latencies: number[] = [];
  let errors = 0;
  let next = 0;
  const started = performance.now();
  // concurrency "עובדים", כל אחד שולח בקשה, מחכה לתשובה, ושולח את הבאה — כמו concurrency משתמשים
  async function worker() {
    while (next < total) {
      next++;
      const t0 = performance.now();
      try {
        await request();
      } catch {
        errors++;
      }
      latencies.push(performance.now() - t0);
    }
  }
  await Promise.all(Array.from({ length: Math.min(concurrency, total) }, worker));
  const durationMs = performance.now() - started;
  latencies.sort((a, b) => a - b);
  const r = (x: number) => Math.round(x * 10) / 10;
  return {
    total,
    errors,
    durationMs: r(durationMs),
    rps: r((total / durationMs) * 1000),
    latency: { p50: r(pct(latencies, 50)), p95: r(pct(latencies, 95)), p99: r(pct(latencies, 99)), max: r(latencies.at(-1)!) },
  };
}

זה "closed model" — כמו N משתמשים שכל אחד מחכה לתשובה לפני הבקשה הבאה. כלים אמיתיים: autocannon (Node), k6, wrk. ושימו לב: ב־closed model, שרת שמאט גם מאט את הבדיקה — מספר הבקשות יורד, וזה מסתיר את הבעיה. כלים כמו k6 מציעים גם "open model": קצב הגעה קבוע, לא משנה כמה השרת איטי.

Math.ceil — חצי instance לא קיים.

✅ פתרון
// P28.5-E09: תכנון קיבולת עם חוק Little
// L = λ × W : כמה בקשות "בתוך המערכת" בממוצע = קצב הגעה × זמן שהייה
export const inFlight = (rps: number, latencyMs: number): number => (rps * latencyMs) / 1000;

export function instancesNeeded({ peakRps, latencyMs, perInstance, headroom = 0.3, min = 2 }: { peakRps: number; latencyMs: number; perInstance: number; headroom?: number; min?: number }): number {
  if (!(headroom >= 0 && headroom < 1)) throw new Error("headroom בין 0 ל־1");
  const usable = perInstance * (1 - headroom); // לא מתכננים ל־100% — שם ה־latency מתפוצץ
  return Math.max(min, Math.ceil(inFlight(peakRps, latencyMs) / usable));
}

// כמה חיבורים למסד כל instance מחזיק, ואם כולם יחד חורגים מה־max_connections
export function checkDbConnections({ instances, poolPerInstance, maxConnections, reserved = 10 }: { instances: number; poolPerInstance: number; maxConnections: number; reserved?: number }) {
  const needed = instances * poolPerInstance;
  const available = maxConnections - reserved; // לאדמין, migrations, monitoring
  return { needed, available, ok: needed <= available, maxPoolPerInstance: Math.floor(available / instances) };
}

השורה האחרונה היא תקלה אמיתית ונפוצה: autoscaling מוסיף instances ← כל אחד פותח pool של 20 ← PostgreSQL מגיע ל־max_connections ← too many clients, דווקא בשיא. הפתרונות: pool קטן לכל instance, ו־connection pooler (PgBouncer, RDS Proxy) באמצע.

// P28.5-E21: דוח latency מכמה שרתים — אחרי התיקון
export function latencyReport(perInstance: number[][]): { count: number; p50: number; p99: number } {
  // תיקון 3: percentile של כל הדגימות יחד — לא ממוצע של ה־p99 של כל שרת
  const all = perInstance.flat();
  all.sort((a, b) => a - b); // תיקון 1: מיון מספרי (ברירת המחדל ממיינת כמחרוזות: 100 < 9)
  // תיקון 2: nearest-rank — ceil(p × n), ואינדקס מ־0
  const at = (p: number) => all[Math.ceil((p / 100) * all.length) - 1];
  return { count: all.length, p50: at(50), p99: at(99) };
}

// P28.5-E28 — דוח של בדיקת עומס
export type Result = { name: string; requests: number; seconds: number; p50: number; p99: number };

const fmt = new Intl.NumberFormat("en-US");

export function report(results: Result[]): string {
  if (results.length === 0) return "";
  const rows = results
    .map((r) => ({ ...r, rps: r.requests / r.seconds }))
    .sort((a, b) => b.rps - a.rps);
  const best = rows[0].rps;
  const cells = rows.map((r) => [
    r.name,
    fmt.format(Math.round(r.rps)),
    r.p50.toFixed(1),
    r.p99.toFixed(1),
    r.rps === best ? "fastest" : `${(best / r.rps).toFixed(2)}x slower`,
  ]);
  const header = ["name", "req/s", "p50 ms", "p99 ms", ""];
  const widths = header.map((h, i) => Math.max(h.length, ...cells.map((c) => c[i].length)));
  const line = (c: string[]) =>
    c
      .map((v, i) => (i === 0 || i === c.length - 1 ? v.padEnd(widths[i]) : v.padStart(widths[i])))
      .join("  ")
      .trimEnd();
  return [line(header), ...cells.map(line)].join("\n");
}

המטמון נותן פי 6.6 מה־baseline, ו־p99 של 6ms במקום 31.8ms. טבלה כזו ב־PR עונה על השאלה "האם השינוי שווה את המורכבות?" טוב יותר מפסקה. ‏p99 לצד req/s חשוב: שינוי שמעלה תפוקה ומכפיל את p99 הוא לא תמיד שיפור (שיעור 1).

‏trimEnd בסוף כל שורה: העמודה האחרונה מרופדת לרוחב הארוך שלה (6.60x slower), ובשורת הכותרת היא ריקה. בלי trimEnd נשארים רווחים בסוף שורות, ו־git מסמן אותם באדום ב־diff.
