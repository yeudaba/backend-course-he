שיעור 2 — Node.js תחת עומס: event loop, thread pool ו־workers

⏱ ~45 דקות

🎯 בשיעור הזה
  • thread אחד ל־JavaScript: מה זה אומר כשיש 1,000 משתמשים.
  • מה חוסם: פונקציות Sync, לולאות חישוב, JSON ענק, regex גרוע.
  • thread pool של libuv מול worker threads — מתי כל אחד.
  • למצוא את החוסם: lag monitor ו־CPU profile.

1. thread אחד

בפרק 10 למדת שה־event loop מריץ callbacks אחד אחרי השני. בשרת זה אומר: כל בקשה שמגיעה, כל תשובה מהמסד וכל timer — מחכים בתור אחד, ל־thread אחד. כל עוד הקוד שלך רק מחכה (למסד, לרשת, לדיסק), זה מצוין — אלפי בקשות "ממתינות" במקביל, בלי thread לכל אחת. אבל ברגע שקוד עובד — מחשב, מצפין, דוחס — הוא תופס את ה־thread, וכל השאר מחכים:

מה חוסם, בפועל: crypto.pbkdf2Sync/scryptSync/bcrypt סינכרוני; zlib.gzipSync; fs.readFileSync על קובץ גדול; JSON.parse/stringify של עשרות מגה; מיון של מיליון איברים; regex עם backtracking קטסטרופלי על קלט של משתמש (ReDoS); ולולאות חישוב (E03).

הכלל: אם יש גרסה אסינכרונית — משתמשים בה, ונגמר (E23). אם העבודה היא JavaScript שלך — מעבירים ל־worker, ומחזיקים pool קבוע של workers (worker חדש לכל בקשה עולה עשרות מילי־שניות ו־~10MB). ואם יש הרבה עבודת CPU — אולי היא בכלל לא שייכת ל־API: תור (יחידה 26.5) ו־worker נפרד.

3. למצוא את החוסם

בפרודקשן לא רואים "pbkdf2Sync" — רואים p99 שקופץ, ו־health checks שנכשלים. שני כלים:

  1. מדד lag: monitorEventLoopDelay מ־perf_hooks מודד כמה timers מאחרים. p99 lag של 200ms = כל בקשה בשרת עלולה לחכות 200ms לפני שהקוד שלה בכלל התחיל. מייצאים כמדד, ומתריעים (E14).
  2. CPU profile: מריצים את השרת תחת עומס עם פרופיילר, ורואים באילו פונקציות ה־CPU בילה:
node --cpu-prof dist/main.js        # בסוף הריצה נוצר קובץ .cpuprofile
# פותחים ב־Chrome DevTools ← Performance ← Load profile, ורואים flame graph
npx clinic flame -- node dist/main.js   # או: clinic בונה flame graph אוטומטית תחת עומס

ב־flame graph, הרוחב הוא זמן CPU. פונקציה רחבה בראש — היא החשודה. בתקלה של E23 תראה את pbkdf2Sync תופס חצי מהרוחב.

⚠️ גם async יכול להעמיס

הגרסה האסינכרונית משחררת את ה־event loop, אבל ה־thread pool קטן: 100 התחברויות במקביל עם pbkdf2 ← 4 רצות, 96 בתור. ה־API נשאר זמין (health עונה), אבל התחברות לוקחת שניות. מגבילים concurrency (rate limit על login — פרק 24), ובודקים בבדיקת עומס.
