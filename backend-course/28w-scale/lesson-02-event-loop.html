1. thread אחד

בפרק 10 למדת שה־event loop מריץ callbacks אחד אחרי השני. בשרת זה אומר: כל בקשה שמגיעה, כל תשובה מהמסד וכל timer — מחכים בתור אחד, ל־thread אחד. כל עוד הקוד שלך רק מחכה (למסד, לרשת, לדיסק), זה מצוין — אלפי בקשות "ממתינות" במקביל, בלי thread לכל אחת. אבל ברגע שקוד עובד — מחשב, מצפין, דוחס — הוא תופס את ה־thread, וכל השאר מחכים:

מה חוסם, בפועל: crypto.pbkdf2Sync/scryptSync/bcrypt סינכרוני; zlib.gzipSync; fs.readFileSync על קובץ גדול; JSON.parse/stringify של עשרות מגה; מיון של מיליון איברים; regex עם backtracking קטסטרופלי על קלט של משתמש (ReDoS); ולולאות חישוב (E03).

3. למצוא את החוסם

בפרודקשן לא רואים "pbkdf2Sync" — רואים p99 שקופץ, ו־health checks שנכשלים. שני כלים:

  1. מדד lag: monitorEventLoopDelay מ־perf_hooks מודד כמה timers מאחרים. p99 lag של 200ms = כל בקשה בשרת עלולה לחכות 200ms לפני שהקוד שלה בכלל התחיל. מייצאים כמדד, ומתריעים (E14).
  2. CPU profile: מריצים את השרת תחת עומס עם פרופיילר, ורואים באילו פונקציות ה־CPU בילה:
node --cpu-prof dist/main.js        # בסוף הריצה נוצר קובץ .cpuprofile
# פותחים ב־Chrome DevTools ← Performance ← Load profile, ורואים flame graph
npx clinic flame -- node dist/main.js   # או: clinic בונה flame graph אוטומטית תחת עומס

ב־flame graph, הרוחב הוא זמן CPU. פונקציה רחבה בראש — היא החשודה. בתקלה של E23 תראה את pbkdf2Sync תופס חצי מהרוחב.

⚠️ גם async יכול להעמיס

הגרסה האסינכרונית משחררת את ה־event loop, אבל ה־thread pool קטן: 100 התחברויות במקביל עם pbkdf2 ← 4 רצות, 96 בתור. ה־API נשאר זמין (health עונה), אבל התחברות לוקחת שניות. מגבילים concurrency (rate limit על login — פרק 24), ובודקים בבדיקת עומס.

4. generators: ערכים לפי בקשה

בסעיף 1 ראית ש־JSON.stringify של מערך ענק חוסם את השרת. פתרון אחד: לחלק את העבודה לחתיכות, ובין חתיכה לחתיכה לתת ל־event loop לנשום. בשביל זה צריך פונקציה שיודעת לעצור באמצע: להחזיר חתיכה אחת, לחכות, ולהמשיך בדיוק מאותו מקום. פונקציה רגילה לא יודעת לעשות את זה. return מסיים אותה, וכל המשתנים המקומיים נעלמים. לזה יש ב־JavaScript סוג מיוחד של פונקציה: generator.

‏function*, ‏yield ו־next()

function* countdown(): Generator<number, string> {
  console.log("  [התחלתי]");
  yield 3;
  console.log("  [ממשיך אחרי 3]");
  yield 2;
  yield 1;
  return "שיגור";
}

const g = countdown();
console.log("נוצר generator");
console.log(g.next());
console.log(g.next());
console.log(g.next());
console.log(g.next());
console.log(g.next());
נוצר generator
  [התחלתי]
{ value: 3, done: false }
  [ממשיך אחרי 3]
{ value: 2, done: false }
{ value: 1, done: false }
{ value: 'שיגור', done: true }
{ value: undefined, done: true }

מה קרה כאן, שורה אחרי שורה:

  • הכוכבית ב־function* הופכת את הפונקציה ל־generator. ההבדל הראשון: הקריאה countdown() לא מריצה אף שורה מהגוף. "נוצר generator" מודפס לפני "[התחלתי]". הקריאה רק מחזירה אובייקט, ה־generator, שמחכה.
  • כל g.next() מריץ את הגוף עד ה־yield הבא, ושם הפונקציה נעצרת. next() מחזיר אובייקט עם שני שדות: value (מה שבא אחרי yield) ו־done: false.
  • ה־next() הבא ממשיך מהשורה שאחרי ה־yield, עם כל המשתנים המקומיים כמו שהיו.
  • כשהגוף מגיע ל־return (או לסוף), מתקבל done: true. ומשם כל next() מחזיר { value: undefined, done: true }.
  • הטיפוס ב־TypeScript: Generator<number, string> — מה ש־yield מחזיר, ומה ש־return מחזיר. בדרך כלל כותבים רק את הראשון: Generator<string>.

‏for...of על generator

לקרוא ל־next() ביד זה מסורבל. generator הוא iterable, בדיוק כמו מערך, ולכן for...of ו־spread (...) עובדים עליו:

function* inChunks<T>(items: T[], size: number): Generator<T[]> {
  for (let i = 0; i < items.length; i += size) {
    yield items.slice(i, i + size);
  }
}

const orders = [101, 102, 103, 104, 105, 106, 107];
for (const part of inChunks(orders, 3)) {
  console.log(part);
}
console.log([...inChunks(orders, 5)]);

const once = inChunks(orders, 4);
console.log([...once].length, [...once].length);
[ 101, 102, 103 ]
[ 104, 105, 106 ]
[ 107 ]
[ [ 101, 102, 103, 104, 105 ], [ 106, 107 ] ]
2 0

‏for...of קורא ל־next() בשבילך, ונעצר לבד כש־done הופך ל־true. (את הערך של return הוא לא מעביר ללולאה.) ושים לב לשורה האחרונה: generator עובר על הערכים פעם אחת. ה־spread הראשון מיצה אותו, והשני קיבל מערך ריק, בלי שום שגיאה. רוצה לעבור שוב? קוראים שוב ל־inChunks(...) ומקבלים generator חדש.

סדרה אינסופית, ו־break

מכיוון שה־generator מחשב ערך רק כשמבקשים אותו, מותר לו לא להיגמר אף פעם. while (true) בתוך generator לא תוקע את התוכנית, כי כל yield עוצר אותה:

function* orderIds(prefix: string): Generator<string> {
  let n = 1;
  try {
    while (true) {
      yield `${prefix}-${n}`;
      n++;
    }
  } finally {
    console.log(`  [${prefix}: נעצר אחרי ${n}]`);
  }
}

const ids = orderIds("ORD");
console.log(ids.next().value, ids.next().value);

for (const id of orderIds("INV")) {
  if (id === "INV-4") break;
  console.log(id);
}
console.log("אחרי הלולאה");
ORD-1 ORD-2
INV-1
INV-2
INV-3
  [INV: נעצר אחרי 4]
אחרי הלולאה
  • ‏ids נתן שני מזהים, ולא ביקשנו יותר. אף אחד לא חישב את השלישי. זו עצלות (lazy): עבודה נעשית רק כשמבקשים את התוצאה.
  • ‏break בתוך for...of קורא ל־return() של ה־generator. הגוף מסתיים במקום שבו הוא עצר, וה־finally רץ. כאן זה הדפסה, אבל בקוד אמיתי זה המקום לסגור קובץ, חיבור למסד, או לעצור עבודה שעולה כסף.
  • ל־ids לא קראנו break ולא return(). לכן ה־finally שלו לא רץ: הוא עדיין מחכה ב־yield השני.

ובחזרה לבעיה של סעיף 1: עם generator אפשר לייצר תשובה ענקית בחתיכות, ובין חתיכה לחתיכה לשחרר את ה־event loop:

for (const part of inChunks(rows, 500)) {
  res.write(JSON.stringify(part));
  await new Promise((r) => setImmediate(r)); // בקשות אחרות מקבלות תור כאן
}

(זה עדיין לא JSON תקין. כל חתיכה היא מערך בפני עצמו, וביחד יוצא […][…]. איך מחברים את החתיכות לתשובה אחת תקינה — בתרגיל E51.)

‏async function* ו־for await: עמודים וזרמים

הרבה פעמים הערך הבא לא מוכן מיד: הוא מגיע מה־API, מהמסד, או מקובץ. בשביל זה יש async generator: async function*. בתוכו מותר await, ומי שצורך אותו עובר עליו ב־for await, שלמדת בפרק 13 על readline. הדוגמה הקלאסית היא API עם עמודים (pagination): כל קריאה מחזירה כמה פריטים ואת מספר העמוד הבא.

type Page = { items: string[]; next: number | null };
const fakeApi: Record<number, Page> = {
  1: { items: ["a1", "a2"], next: 2 },
  2: { items: ["b1", "b2"], next: 3 },
  3: { items: ["c1"], next: null },
};

async function fetchPage(n: number): Promise<Page> {
  console.log(`  [GET /orders?page=${n}]`);
  await new Promise((r) => setTimeout(r, 10));
  return fakeApi[n];
}

async function* allOrders(): AsyncGenerator<string> {
  let page: number | null = 1;
  while (page !== null) {
    const res = await fetchPage(page);
    for (const item of res.items) yield item;
    page = res.next;
  }
}

for await (const id of allOrders()) {
  console.log(id);
}
console.log("---");
for await (const id of allOrders()) {
  console.log(id);
  if (id === "b1") break;
}

מי שמשתמש ב־allOrders() לא יודע שיש עמודים. הוא רואה רצף אחד של הזמנות. העמוד הבא נטען רק כשהלולאה צריכה אותו. ובלולאה השנייה, אחרי break על b1, עמוד 3 לא נטען בכלל. אותה עצלות, עכשיו עם await: לא קוראים ל־API יותר ממה שצריך, וגם זה backpressure. הצרכן קובע את הקצב, והיצרן מחכה לו.

אותו דפוס משמש בכל מקום שבו נתונים מגיעים ברצף: שורות מקובץ (שיעור 3), אצוות של INSERT (שיעור 3, תרגיל E64), הודעות מתור (יחידה 26.5), ואירועי התקדמות של סוכן AI (יחידה 29.5, שיעור 5). ו־Readable.from(allOrders()) מ־node:stream הופך async generator ל־stream רגיל, שאפשר לחבר ב־pipeline.

⚠️ טעויות נפוצות עם generators
  • "קראתי לפונקציה ושום דבר לא קרה". countdown() בלבד לא מריץ את הגוף. צריך next(), ‏for...of או spread.
  • לעבור פעמיים על אותו generator. בפעם השנייה הוא ריק, בלי שגיאה. שומרים את התוצאה במערך, או יוצרים generator חדש.
  • ‏yield בתוך callback. yield עובד רק ישירות בגוף של function*, לא בתוך פונקציה פנימית כמו החץ של forEach. משתמשים ב־for...of רגיל (למטה, השגיאה הראשונה).
  • ‏for...of על async generator. צריך for await. TypeScript מסמן את זה מראש (השגיאה השנייה למטה). בלי TypeScript, Node נכשל בזמן ריצה עם TypeError: allOrders is not a function or its return value is not iterable.
function* each(items: string[]) {
  items.forEach((x) => {
    yield x;
  });
}
