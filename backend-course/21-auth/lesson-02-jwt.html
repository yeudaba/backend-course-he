⏱ ~50 דקות

🎯 בשיעור הזה

  • JWT מבפנים — מה כתוב בו, ומה החתימה מבטיחה.

1. אחרי הכניסה — איך השרת יודע מי אתה?

HTTP לא זוכר כלום: כל בקשה עומדת לבד (פרק 14). אחרי כניסה מוצלחת השרת נותן ללקוח "כרטיס", והלקוח מציג אותו בכל בקשה. יש שתי דרכים נפוצות:

SessionJWT
מה הלקוח מקבלמזהה אקראי (sid=...), בדרך כלל ב־cookieטוקן חתום שמכיל את המידע עצמו (sub, role, exp)
מה השרת בודקמחפש את ה־sid במסד/Redisבודק חתימה ותוקף — בלי מסד
יציאה / ביטולמוחקים את ה־session — מיידיאי אפשר "לבטל" טוקן חתום עד שיפוג — לכן תוקף קצר (שיעור 3)
מתאים לאתר אחד עם שרת אחדAPI, אפליקציות מובייל, כמה שרתים

שתיהן לגיטימיות. בפרויקט נשתמש ב־JWT — הנפוץ ב־API ובמשרות Node — ונשלב אותו עם refresh token ששמור במסד, שנותן את היתרון של session (ביטול).

2. JWT מבפנים

JWT הם שלושה חלקים מופרדים בנקודה: header.payload.signature. שני הראשונים הם סתם JSON ב־Base64url — encoding, לא הצפנה:

import { JwtService } from "@nestjs/jwt";

const jwt = new JwtService({ secret: "dev-secret-change-me" });
const token = await jwt.signAsync({ sub: 7, role: "user", iat: 1793872800 }, { expiresIn: 900 });
console.log(token);

const [header, payload] = token.split(".");
console.log(Buffer.from(header, "base64url").toString());
console.log(Buffer.from(payload, "base64url").toString());
console.log(new Date(1793873700 * 1000).toISOString());

כל אחד שמחזיק את הטוקן יכול לקרוא את ה־payload — גם בלי הסוד (נסה להדביק טוקן ב־jwt.io). לכן לא שמים ב־JWT שום דבר סודי: לא סיסמה, לא מספר כרטיס, ובדרך כלל גם לא אימייל. מה שכן: sub (subject — מזהה המשתמש), role, ו־iat/exp (מתי נוצר ועד מתי — בשניות מאז 1970, UTC).

3. החתימה — מה היא מבטיחה

החלק השלישי הוא HMAC-SHA256 של שני הראשונים, עם הסוד שרק השרת יודע. אז מה קורה אם המשתמש משנה את ה־payload ל־"role":"admin"?

import { JwtService } from "@nestjs/jwt";

const jwt = new JwtService({ secret: "dev-secret-change-me" });
const token = await jwt.signAsync({ sub: 7, role: "user", iat: 1793872800 }, { expiresIn: 900 });
const [header, , signature] = token.split(".");
const evil = Buffer.from(JSON.stringify({ sub: 7, role: "admin", iat: 1793872800, exp: 1793873700 })).toString("base64url");
const forged = `${header}.${evil}.${signature}`;

try {
  await jwt.verifyAsync(forged, { clockTimestamp: 1793872800 });
} catch (err) {
  console.log("verify:", err.name, "—", err.message);
}
console.log("decode:", jwt.decode(forged));
verify: JsonWebTokenError — invalid signature
decode: { sub: 7, role: 'admin', iat: 1793872800, exp: 1793873700 }

verify מחשב את החתימה מחדש ומגלה שהיא לא מתאימה. decode — לא בודק כלום, רק מפענח Base64. זה אחד הבאגים הנפוצים והמסוכנים בקוד אמיתי (תמצא אותו ב־E20): מי שמשתמש ב־decode כדי "לדעת מי המשתמש" — נתן לכל אחד להיות admin.

ומה עם תוקף? exp נבדק בתוך verify:

import { JwtService } from "@nestjs/jwt";

const jwt = new JwtService({ secret: "dev-secret-change-me" });
const token = await jwt.signAsync({ sub: 7, iat: 1793872800 }, { expiresIn: 900 });
for (const seconds of [899, 900]) {
  try {
    await jwt.verifyAsync(token, { clockTimestamp: 1793872800 + seconds });
    console.log(seconds, "ok");
  } catch (err) {
    console.log(seconds, err.name);
  }
}
899 ok
900 TokenExpiredError

clockTimestamp — "מה השעה עכשיו" לצורך הבדיקה. בקוד רגיל לא מעבירים אותו (ברירת המחדל: השעון של המחשב). אנחנו מעבירים אותו מה־CLOCK — כדי שהבדיקות יוכלו "להזיז את הזמן" 15 דקות קדימה, בלי לחכות.

⚠️ הסוד

מי שיודע את JWT_SECRET יכול להנפיק טוקן לכל משתמש, כולל admin. לכן: לפחות 32 תווים אקראיים (node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"), רק ב־.env ובהגדרות השרת — לא בקוד ולא ב־Git — וסוד שונה לפיתוח ולפרודקשן. בפרויקט, loadConfig מסרב לעלות עם סוד קצר. ועוד דבר: מגדירים algorithms: ["HS256"] ב־verify — כדי שטוקן שמצהיר על אלגוריתם אחר (למשל "none") לא יתקבל.

4. ב־Nest: guard גלובלי

ב־E14 של פרק 20 שמת @UseGuards(ApiKeyGuard) על route. עם משתמשים זה הפוך: כמעט הכול דורש התחברות, ורק מעט routes פתוחים (health, register, login). אז רושמים guard גלובלי, ומסמנים את היוצאים מן הכלל:

src/auth/jwt-auth.guard.ts 
@Injectable()
export class JwtAuthGuard implements CanActivate {
  constructor(private readonly reflector: Reflector, private readonly auth: AuthService) {}

  async canActivate(context: ExecutionContext) {
    const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC, [context.getHandler(), context.getClass()]);
    if (isPublic) return true;
    const req = context.switchToHttp().getRequest();
    const match = /^Bearer\s+(\S+)$/i.exec(req.get("authorization") ?? "");
    if (!match) throw new HttpError(401, "UNAUTHORIZED", "נדרשת התחברות");
    req.user = await this.auth.verifyAccessToken(match[1]);   // 401 INVALID_TOKEN אם לא תקין
    return true;
  }
}
src/auth/auth.decorators.ts 
export const Public = () => SetMetadata(IS_PUBLIC, true);

export const CurrentUser = createParamDecorator((_data: unknown, ctx: ExecutionContext): AuthUser => {
  return ctx.switchToHttp().getRequest().user;
});
  • SetMetadata ו־Reflector: decorator ששומר מידע על מתודה או class, ו־guard שקורא אותו. getAllAndOverride בודק קודם את המתודה ואחר כך את ה־class — כך @Public() עובד על שניהם.
  • רישום: { provide: APP_GUARD, useClass: JwtAuthGuard } ב־module. בזכות DI, ה־guard מקבל את AuthService ו־Reflector.
  • @CurrentUser(): במקום @Req() req ו־req.user בכל handler — decorator שמחזיר בדיוק את מה שצריך: list(@CurrentUser() user: AuthUser).
  • "Bearer" — לפי התקן, בלי תלות באותיות (/i). קטן, אבל לקוחות שולחים גם bearer.
💡 "default deny"

למה guard גלובלי עדיף על @UseGuards בכל controller? כי מי שמוסיף מחר controller חדש ושוכח — מקבל route מוגן, לא פתוח. שכחה צריכה להיכשל לכיוון הבטוח. זה עיקרון שחוזר בכל אבטחה.
