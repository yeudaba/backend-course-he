למה 404 ולא 403 במקרה השלישי? 403 אומר "יש כאן משימה מספר 17, היא פשוט לא שלך" — וזה כבר מידע: כמה משימות יש במערכת, אילו מספרים קיימים. מבחינת יוסי, המשימה של דנה לא קיימת. (403 נשאר למצב שבו הפעולה עצמה אסורה לך, לא האובייקט.)

2. תפקידים

src/auth/roles.guard.ts 
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private readonly reflector: Reflector) {}

  canActivate(context: ExecutionContext) {
    const roles = this.reflector.getAllAndOverride<Role[] | undefined>(ROLES, [context.getHandler(), context.getClass()]);
    if (!roles || roles.length === 0) return true;                  // בלי @Roles — כל מחובר
    const user = context.switchToHttp().getRequest().user;
    if (!user || !roles.includes(user.role)) throw new HttpError(403, "FORBIDDEN", "אין הרשאה");
    return true;
  }
}

// שימוש:
@Controller("users")
@Roles("admin")
export class UsersController { ... }

שני guards גלובליים, והסדר ביניהם הוא סדר הרישום ב־providers: קודם JwtAuthGuard (שקובע req.user, או 401), אחר כך RolesGuard (403). הפוך — RolesGuard היה רץ בלי req.user, ומשתמש לא מחובר היה מקבל 403 במקום 401.

ומאיפה ה־role? מה־JWT. זה מהיר (בלי מסד), אבל אם admin מוריד למישהו הרשאה — הטוקן הישן עדיין אומר admin עד שיפוג. עוד סיבה לתוקף קצר.

3. בעלות על מידע — BOLA / IDOR

ברשימת OWASP API Security Top 10 (2023), מקום ראשון: Broken Object Level Authorization. בעברית: "שיניתי את המספר ב־URL וקיבלתי את ההזמנה של מישהו אחר". זה לא דורש שום כלי — רק סקרנות.

src/tasks/tasks.prisma-repository.ts 
async findById(ownerId: number, id: number) {
  const row = await this.prisma.task.findFirst({ where: { id, ownerId } });
  return row ? toTask(row) : undefined;
}

async update(ownerId: number, id: number, changes: Partial<Omit<Task, "id">>) {
  const { count } = await this.prisma.task.updateMany({ where: { id, ownerId }, data: toData(changes) });
  return count === 1 ? this.findById(ownerId, id) : undefined;
}

שלושה כללים שעושים את זה בטוח:

  1. הבעלים מגיע מהטוקן (@CurrentUser()) — אף פעם לא מ־?userId= או מהגוף.
  2. הבעלות חלק מה־WHERE, בכל פעולה — גם ב־update וב־delete, לא רק ב־get. הבאג הנפוץ: בודקים בעלות ב־GET /tasks/:id, ושוכחים ב־DELETE (E22).
  3. ב־repository, לא ב־controller: כל פונקציה מקבלת ownerId כפרמטר חובה. אי אפשר "לשכוח" — TypeScript לא יקמפל.

4. Mass assignment

מקום שלישי ברשימה: Broken Object Property Level Authorization — הלקוח קובע שדה שהוא לא אמור לקבוע. הקלאסיקה:

% curl -X POST localhost:3000/auth/register -H "Content-Type: application/json" -d '{"email":"evil@example.com","password":"my-long-password","role":"admin"}'

אם הקוד עושה users.insert({ ...body, passwordHash }) — יש לנו admin חדש. אצלנו זה נחסם פעמיים: registerSchema הוא z.strictObject (שדה לא מוכר ← 400), וה־service קובע role: "user" במפורש. אותו דבר ב־PATCH של משימה: updateTaskSchema לא מכיר ownerId. הכלל: רשימה מפורשת של מה מותר, לא "הכול חוץ מ־".

ועוד שלושה הרגלים: SQL injection — Prisma ו־pg עם פרמטרים ($1) מגנים, אבל רק אם לא מדביקים מחרוזות ל־$queryRawUnsafe. HTTPS — בלי זה, הטוקן עובר ברשת כטקסט (פרק 25). תלויות — npm audit מדי פעם.

⚠️ אבטחה היא לא פיצ'ר בסוף

שים לב שאף אחד מהפריטים כאן לא היה "קוד אבטחה" נפרד: WHERE עם ownerId, schema מחמיר, הודעת שגיאה אחידה. אבטחה היא הרבה החלטות קטנות בקוד רגיל. ולכן בודקים אותה כמו כל דבר אחר — PR2-AUTH מנסה בדיוק את התקיפות מהשיעור.
