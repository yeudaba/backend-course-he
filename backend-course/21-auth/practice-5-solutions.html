P21-E82 · ‏migration על טבלה מלאה 🧠 הבנה רמה 1

💡 רמז 1

מה הערך של owner_id בשורות שכבר קיימות?

💡 רמז 2

Prisma עצמו כותב אזהרה בראש הקובץ שנוצר.

✅ פתרון
  • (א) נכשל: לשורות הקיימות אין ערך ל־owner_id, ו־NOT NULL לא מאפשר NULL. PostgreSQL מסרב, וה־migration לא מוחל (‏column "owner_id" of relation "tasks" contains null values).
  • (ב) בפיתוח הנתונים מזויפים: ה־seed יוצר אותם מחדש. אין מה לשמור.
  • (ג) כדי לקרוא את ה־SQL ולתקן אותו לפני שהוא רץ. ‏migrate dev מריץ מיד.
  • (ד) כל המשימות הקיימות שייכות פתאום למשתמש 1, בלי שאף אחד החליט את זה. אולי משתמש 1 בכלל לא קיים (FK נכשל), ואם קיים, הוא רואה משימות של אחרים. ו־DEFAULT שנשאר בעמודה ממשיך לחלק משימות חדשות למשתמש 1 אם קוד שוכח ownerId.
⚠️ טעויות נפוצות
  • להריץ prisma migrate reset "כדי שיעבוד". בפיתוח זה בסדר, אבל זה בדיוק ההרגל שמוחק נתונים של לקוחות.

P21-E83 · ‏expand, backfill, contract 🧠 הבנה רמה 2

💡 רמז 1

שלב 1 לא שובר שום קוד קיים. שלב 3 מחייב שכבר אין שורות עם NULL, וגם שלא ייווצרו חדשות כאלה.

💡 רמז 2

UPDATE על 2 מיליון שורות נועל אותן לזמן ארוך.

✅ פתרון
-- 1. expand
ALTER TABLE tasks ADD COLUMN owner_id int REFERENCES users(id) ON DELETE CASCADE;
-- 2. backfill (אחרי שהקוד החדש כבר כותב owner_id)
UPDATE tasks SET owner_id = (SELECT id FROM users WHERE email = 'legacy@tasks.example') WHERE owner_id IS NULL;
-- 3. contract
ALTER TABLE tasks ALTER COLUMN owner_id SET NOT NULL;
  • (ב) לפני ה־backfill. אחרת, בזמן ה־backfill, הקוד הישן ממשיך ליצור משימות עם NULL, ושלב 3 ייכשל.
  • (ג) כל משימה שהגרסה הישנה יוצרת נכשלת (‏NOT NULL): שגיאות 500 למשתמשים. לכן הסדר הוא: קוד חדש בכל השרתים, אחר כך backfill, ורק אז contract.
  • (ד) עדיף בקבוצות (‏WHERE id BETWEEN ..., אלף שורות כל פעם). כך כל טרנזקציה קצרה, לא נועלת הרבה, ולא מאטה את האפליקציה. (אם הוא נקטע, ממשיכים מאיפה שעצר, בזכות WHERE owner_id IS NULL.)
⚠️ טעויות נפוצות
  • לחשוב ש"שלוש migrations" זה באותו deploy. הכוח של השיטה הוא שבין השלבים עובר זמן, ובכל רגע הקוד הרץ והמסד מתאימים.

P21-E84 · מוחקים משתמש — מה נמחק איתו? 🧠 הבנה רמה 1

💡 רמז 1

‏@relation(..., onDelete: Cascade) מופיע גם ב־Task.owner וגם ב־RefreshToken.user.

💡 רמז 2

ה־guard לא שואל את המסד.

✅ פתרון
  • (א) המשתמש, 4 המשימות ו־3 ה־refresh tokens. PostgreSQL מוחק אותם באותה פקודה.
  • (ב) ה־DELETE נכשל עם שגיאת foreign key (‏P2003 ב־Prisma): אי אפשר למחוק משתמש שיש שורות שמצביעות עליו. צריך למחוק קודם את התלויים.
  • (ג) הטוקן עדיין עובר את ה־guard (חתימה ותוקף תקינים). ‏GET /tasks מחזיר רשימה ריקה (אין משימות עם owner_id = 1). ‏GET /auth/me לא מוצא משתמש, ובפרויקט מחזיר 401. אחרי 15 דקות הטוקן פג, וה־refresh tokens כבר לא קיימים.
  • (ד) כדי לשמור היסטוריה (הזמנות, חשבוניות, יומן פעולות), לאפשר שחזור, ולעמוד בחוקים שמחייבים שמירה. ומצד שני, חוקי פרטיות (GDPR) מחייבים לפעמים מחיקה אמיתית, או לפחות אנונימיזציה של הפרטים האישיים.
⚠️ טעויות נפוצות
  • לשים Cascade על כל relation "כדי שלא יהיו שגיאות". מחיקה של לקוח שמוחקת לו את כל החשבוניות היא בדרך כלל באג, לא פיצ'ר.

P21-E85 · ‏@Global ו־overrideProvider(CONFIG) 🧠 הבנה רמה 2

💡 רמז 1
registerAsync({ inject: [CONFIG], useFactory: (c) => ({ secret: c.jwtSecret }) })

— ה־factory מקבל את ה־CONFIG דרך DI.

💡 רמז 2

מתי process.env.JWT_SECRET נקרא, ב־register רגיל?

✅ פתרון
  • (א) להוסיף imports: [ConfigModule] בכל module שצריך CONFIG או CLOCK (‏Tasks, ‏Auth, ‏Users).
  • (ב) כי JwtModule.registerAsync מקבל את הסוד מ־CONFIG דרך DI. ‏overrideProvider מחליף את CONFIG לכל מי שמבקש אותו, כולל ה־factory של JwtModule.
  • (ג) הסוד נקרא כשהקובץ נטען, בלי בדיקה. בבדיקות צריך להגדיר process.env לפני ה־import, ו־overrideProvider(CONFIG) לא משפיע עליו. וסוד חסר הופך ל־undefined, וזו שגיאה רק בכניסה הראשונה.
  • (ד) fail fast: עדיף שהשרת לא יעלה בכלל (ופריסה נעצרת, פרק 25) מאשר שיעלה ויכשל אצל המשתמש הראשון. או גרוע מזה, יעבוד עם סוד חלש.
⚠️ טעויות נפוצות
  • לקרוא process.env ישירות בכל service. זה עובד, אבל אין בדיקה אחת, אין טיפוסים, ובדיקות צריכות לשנות משתנים גלובליים.

P21-E87 · למה seed.mts? 🧠 הבנה רמה 2

💡 רמז 1

הפרויקט של Nest מתקמפל ל־CommonJS (פרק 20). ומה ה־seed עושה ברמה העליונה של הקובץ?

💡 רמז 2

await מחוץ לפונקציה מותר רק ב־ES modules (פרק 8).

✅ פתרון
  • (א) .mts הוא תמיד ES module, בלי קשר להגדרות של הפרויקט. ‏.ts בפרויקט CommonJS הוא CommonJS.
  • (ב) ה־seed משתמש ב־await ברמה העליונה (‏await prisma.user.create(...)), וזה עובד רק ב־ESM. הוא רץ ישירות עם node (‏seed: "node prisma/seed.mts"), ולא דרך הקומפילציה של Nest.
  • (ג) נמוך (4–8). אלה משתמשי דמו עם סיסמאות שכתובות ב־README, אין מה להגן עליהן. cost ‏12 רק מאט כל db:seed. אבל זה רק ב־seed. בהרשמה האמיתית: BCRYPT_ROUNDS.
  • (ד) תלוי בקוד. אם הוא עושה create על אימייל שכבר קיים, הוא נכשל על UNIQUE. seed טוב מוחק קודם, או משתמש ב־upsert (E94), כדי שיהיה אפשר להריץ אותו שוב ושוב.
⚠️ טעויות נפוצות
  • לעטוף הכול ב־async function main() ולשכוח main().catch(...). שגיאה הופכת לאזהרה שקטה, ו־db:seed "מצליח".

P21-E88 · ‏migration בשלושה שלבים — ב־SQL 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

שלוש פקודות:

ALTER TABLE ... ADD COLUMN owner_id int REFERENCES users(id) ON DELETE CASCADE;

UPDATE ..., ‏ALTER TABLE ... ALTER COLUMN owner_id SET NOT NULL;.

💡 רמז 2

ב־UPDATE:

SET owner_id = (SELECT id FROM users WHERE email = 'legacy@tasks.example')

ובסוף CREATE INDEX ... ON tasks (owner_id);.

✅ פתרון
-- P21-E88: expand, backfill, contract
-- 1. expand: עמודה שמותר בה NULL — לא שוברת כלום
ALTER TABLE tasks ADD COLUMN owner_id int REFERENCES users(id) ON DELETE CASCADE;

-- 2. backfill: כל המשימות הקיימות למשתמש "ישן"
UPDATE tasks
   SET owner_id = (SELECT id FROM users WHERE email = 'legacy@tasks.example')
 WHERE owner_id IS NULL;

-- 3. contract: מעכשיו חובה
ALTER TABLE tasks ALTER COLUMN owner_id SET NOT NULL;

CREATE INDEX tasks_owner_id_idx ON tasks (owner_id);

כאן שלושת השלבים באותו קובץ, כי במסד של הבודק אף אחד לא כותב בזמן ה־migration. בפרודקשן, כפי שראית ב־E83, הם שלושה קבצים, ובין השני לשלישי עולה קוד חדש. ‏WHERE owner_id IS NULL הופך את ה־backfill לבטוח להרצה חוזרת.

⚠️ טעויות נפוצות
  • SET owner_id = 1 — במסד של הבודק ה־id של legacy הוא לא 1.
  • ADD COLUMN owner_id int NOT NULL ישר — נכשל על טבלה מלאה (E82).

P21-E89 · ‏loadConfig עם Zod 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1
z.object({ JWT_SECRET: z.string().min(32), ACCESS_TOKEN_TTL_SECONDS: z.coerce.number().int().min(30).max(3600).default(900), ... })
💡 רמז 2

השמות: [...new Set(r.error.issues.map((i) => String(i.path[0])))]. ואם הסדר לא לפי הטבלה, אפשר לסנן את רשימת המפתחות של הסכמה (Object.keys(envSchema.shape)).

✅ פתרון
// P21-E89: loadConfig — בדיקה אחת של ה־env, בעלייה
import { z } from "zod";

export type AppConfig = { jwtSecret: string; accessTtlSeconds: number; refreshTtlDays: number; bcryptRounds: number };

const envSchema = z.object({
  JWT_SECRET: z.string().min(32),
  ACCESS_TOKEN_TTL_SECONDS: z.coerce.number().int().min(30).max(3600).default(900),
  REFRESH_TOKEN_TTL_DAYS: z.coerce.number().int().min(1).max(90).default(7),
  BCRYPT_ROUNDS: z.coerce.number().int().min(4).max(15).default(12),
});

export function loadConfig(env: Record<string, string | undefined>): AppConfig {
  const r = envSchema.safeParse(env);
  if (!r.success) {
    const bad = new Set(r.error.issues.map((i) => String(i.path[0])));
    const names = Object.keys(envSchema.shape).filter((k) => bad.has(k));
    throw new Error(`הגדרות לא תקינות: ${names.join(", ")}`);
  }
  const e = r.data;
  return {
    jwtSecret: e.JWT_SECRET,
    accessTtlSeconds: e.ACCESS_TOKEN_TTL_SECONDS,
    refreshTtlDays: e.REFRESH_TOKEN_TTL_DAYS,
    bcryptRounds: e.BCRYPT_ROUNDS,
  };
}

שני דברים קטנים שחשובים בפרודקשן: הודעת השגיאה מכילה רק שמות (לוגים של פריסה נקראים ע"י הרבה אנשים), והשמות בתוך הקוד הם camelCase, לא SCREAMING_CASE מה־env. מעכשיו שאר הקוד לא יודע ש־process.env קיים.

⚠️ טעויות נפוצות
  • להכניס את i.message להודעה — ב־Zod ההודעה לפעמים כוללת את הערך שהתקבל.
  • z.number() בלי coerce — כל משתנה סביבה הוא מחרוזת.

P21-E90 · ‏repository בזיכרון עם ownerId מוסתר 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1
const strip = ({ ownerId, ...task }: StoredTask): Task => task;
💡 רמז 2

ב־update: ‏if ("title" in changes) ..., או const { title, done } = changes; ולהעתיק רק את מה שהוגדר. לא Object.assign(stored, changes).

✅ פתרון
// P21-E90: repository בזיכרון — ownerId בפנים, לא בחוץ
export type Task = { id: number; title: string; done: boolean };
type StoredTask = Task & { ownerId: number };

const strip = ({ ownerId, ...task }: StoredTask): Task => task;

export class InMemoryTasksRepository {
  #tasks: StoredTask[] = [];
  #nextId = 1;

  #find(ownerId: number, id: number) {
    return this.#tasks.find((t) => t.id === id && t.ownerId === ownerId);
  }

  insert(ownerId: number, data: { title: string; done?: boolean }): Task {
    const task: StoredTask = { id: this.#nextId++, title: data.title, done: data.done ?? false, ownerId };
    this.#tasks.push(task);
    return strip(task);
  }

  list(ownerId: number): Task[] {
    return this.#tasks.filter((t) => t.ownerId === ownerId).map(strip);
  }

  findById(ownerId: number, id: number): Task | undefined {
    const t = this.#find(ownerId, id);
    return t && strip(t);
  }

  update(ownerId: number, id: number, changes: Partial<Omit<Task, "id">>): Task | undefined {
    const t = this.#find(ownerId, id);
    if (!t) return undefined;
    if (changes.title !== undefined) t.title = changes.title;
    if (changes.done !== undefined) t.done = changes.done;
    return strip(t);
  }

  delete(ownerId: number, id: number): boolean {
    const i = this.#tasks.findIndex((t) => t.id === id && t.ownerId === ownerId);
    if (i === -1) return false;
    this.#tasks.splice(i, 1);
    return true;
  }
}

אותה צורה בדיוק כמו tasks.repository.ts בפרויקט. ה־controller וה־service לא יודעים ש־ownerId קיים בשורה, וה־API נשאר זהה לשלבים הקודמים. ובגלל ש־ownerId הוא תמיד הפרמטר הראשון, אי אפשר לקרוא לאף פעולה "בלי בעלים".

⚠️ טעויות נפוצות
  • return t במקום strip(t) — מחזיר את האובייקט הפנימי עם ownerId, ומי שמשנה אותו משנה את האחסון.
  • Object.assign(t, changes) — ‏{ ownerId: 2 } מעביר את המשימה למשתמש אחר (E22).

type Tokens = { accessToken: string; refreshToken: string };

const KEY = "refreshToken";

export class AuthSession {
  #access: string | null = null;
  readonly #baseUrl: string;
  readonly #storage: StorageLike;

  constructor(baseUrl: string, storage: StorageLike) {
    this.#baseUrl = baseUrl;
    this.#storage = storage;
  }

  get accessToken(): string | null {
    return this.#access;
  }

  #post(path: string, body: unknown) {
    return fetch(this.#baseUrl + path, { method: "POST", headers: { "content-type": "application/json" }, body: JSON.stringify(body) });
  }

  #save(t: Tokens) {
    this.#access = t.accessToken;
    this.#storage.setItem(KEY, t.refreshToken);
  }

  async login(email: string, password: string): Promise<void> {
    const res = await this.#post("/auth/login", { email, password });
    const data = await res.json();
    if (res.status !== 200) throw new Error(data.message);
    this.#save(data);
  }

  async restore(): Promise<boolean> {
    const refreshToken = this.#storage.getItem(KEY);
    if (!refreshToken) return false;
    const res = await this.#post("/auth/refresh", { refreshToken });
    if (res.status !== 200) {
      this.#storage.removeItem(KEY);
      return false;
    }
    this.#save(await res.json());
    return true;
  }

  async logout(): Promise<void> {
    const refreshToken = this.#storage.getItem(KEY);
    if (refreshToken) await this.#post("/auth/logout", { refreshToken }).catch(() => {});
    this.#access = null;
    this.#storage.removeItem(KEY);
  }
}

ככה "רענון הדף" עובד: הזיכרון נמחק (ה־access token איננו), אבל ה־refresh token ב־sessionStorage נשאר, ו־restore() מקבל זוג חדש. וכשה־refresh לא עובד (בוטל, פג), מוחקים אותו מיד, כדי לא לשלוח אותו שוב ושוב.

⚠️ טעויות נפוצות
  • לשמור גם את ה־access token ב־storage "כדי לחסוך refresh". עכשיו XSS קורא שניים במקום אחד, ובשביל מה? refresh אחד בטעינת דף זה זול.
  • לא למחוק ב־logout כשהבקשה נכשלה (אין רשת). המשתמש לחץ "יציאה" ונשאר מחובר.

// P21-E94: seed אידמפוטנטי
import bcrypt from "bcryptjs";

type Db = { query(text: string, params?: unknown[]): Promise<any> };
export type DemoUser = { email: string; password: string; role: "user" | "admin" };

export async function seedUsers(db: Db, users: DemoUser[], rounds: number): Promise<number> {
  const hashes = await Promise.all(users.map((u) => bcrypt.hash(u.password, rounds)));
  let added = 0;
  for (const [i, u] of users.entries()) {
    const { rowCount } = await db.query(
      "INSERT INTO users (email, password_hash, role) VALUES ($1, $2, $3) ON CONFLICT (email) DO NOTHING",
      [u.email.toLowerCase(), hashes[i], u.role],
    );
    added += rowCount;
  }
  return added;
}

"אידמפוטנטי" (פרק 14): להריץ פעם אחת או עשר — אותה תוצאה. זה מה שמאפשר npm run db:seed בכל פעם שמישהו מקים סביבה, בלי "קודם תמחק את המסד".

// P21-E95: עמוד משימות של משתמש אחד
type Db = { query(text: string, params?: unknown[]): Promise<any> };

export async function listTasks(db: Db, ownerId: number, opts: { status?: "todo" | "done"; limit: number; offset: number }) {
  const where = "WHERE owner_id = $1 AND ($2::text IS NULL OR status = $2)";
  const status = opts.status ?? null;

// ---------- auth ----------
const sha256 = (v: string) => createHash("sha256").update(v).digest("hex");
const relogin = () => new UnauthorizedException("צריך להתחבר מחדש");

@Injectable()
export class AuthService {
  private readonly refresh = new Map<string, { userId: number; expiresAt: number; revoked: boolean }>();
  private readonly dummy: Promise<string>;

  constructor(
    private readonly users: UsersService,
    private readonly jwt: JwtService,
    @Inject(CONFIG) private readonly config: Config,
    @Inject(CLOCK) private readonly clock: Clock,
  ) {
    this.dummy = bcrypt.hash("dummy-password-nobody-knows", config.bcryptRounds);
  }

  private nowSeconds() {
    return Math.floor(this.clock.now().getTime() / 1000);
  }

  private async issue(user: User) {
    const accessToken = await this.jwt.signAsync({ sub: user.id, role: user.role, iat: this.nowSeconds() }, { expiresIn: this.config.accessTtlSeconds });
    const refreshToken = randomBytes(32).toString("base64url");
    this.refresh.set(sha256(refreshToken), { userId: user.id, expiresAt: this.clock.now().getTime() + this.config.refreshTtlDays * 86_400_000, revoked: false });
    return { accessToken, refreshToken };
  }

  async login(email: string, password: string) {
    const user = this.users.findByEmail(email);
    const ok = await bcrypt.compare(password, user ? user.passwordHash : await this.dummy);
    if (!user || !ok) throw new UnauthorizedException("אימייל או סיסמה שגויים");
    return this.issue(user);
  }

  async rotate(token: string) {
    const record = this.refresh.get(sha256(token));
    if (!record) throw relogin();
    if (record.revoked) {
      for (const r of this.refresh.values()) if (r.userId === record.userId) r.revoked = true;
      throw relogin();
    }
    if (record.expiresAt <= this.clock.now().getTime()) throw relogin();
    record.revoked = true;
    const user = this.users.findById(record.userId);
    if (!user) throw relogin();
    return this.issue(user);
  }

  logout(token: string) {
    const record = this.refresh.get(sha256(token));
    if (record) record.revoked = true;
  }

  async verify(token: string): Promise<AuthUser> {
    try {
      const p = await this.jwt.verifyAsync<{ sub: number; role: Role }>(token, { clockTimestamp: this.nowSeconds() });
      return { id: p.sub, role: p.role };
    } catch {
      throw new UnauthorizedException("טוקן לא תקין");
    }
  }
}

@Injectable()
export class JwtAuthGuard implements CanActivate {
  constructor(private readonly reflector: Reflector, private readonly auth: AuthService) {}

  async canActivate(context: ExecutionContext) {
    if (this.reflector.getAllAndOverride<boolean>(IS_PUBLIC, [context.getHandler(), context.getClass()])) return true;
    const req = context.switchToHttp().getRequest<Request & { user?: AuthUser }>();
    const match = /^Bearer\s+(\S+)$/i.exec(req.get("authorization") ?? "");
    if (!match) throw new UnauthorizedException("נדרשת התחברות");
    req.user = await this.auth.verify(match[1]);
    return true;
  }
}

@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private readonly reflector: Reflector) {}

  canActivate(context: ExecutionContext) {
    const roles = this.reflector.getAllAndOverride<Role[] | undefined>(ROLES, [context.getHandler(), context.getClass()]);
    if (!roles?.length) return true;
    const user = context.switchToHttp().getRequest().user as AuthUser | undefined;
    if (!user || !roles.includes(user.role)) throw new ForbiddenException("אין הרשאה");
    return true;
  }
}

P21-E99 · בודק IDOR משלך 🤖 💻 כתיבת קוד 🤖 רמה 4

💡 רמז 1

פונקציית עזר:

const call = (method, path, token, body?) => fetch(baseUrl + path, { method, headers: {...}, body: ... })
💡 רמז 2

הבקשות של B חייבות להיות ברצף (await אחרי await), לא ב־Promise.all: ה־DELETE לא אמור לרוץ לפני ה־PATCH.

✅ פתרון
// P21-E99: בודק IDOR — מה קורה כש־B נוגע במשימה של A
export type OwnershipReport = { get: number; patch: number; delete: number; stillExists: boolean; title: string };

export async function probeOwnership(baseUrl: string, tokenA: string, tokenB: string): Promise<OwnershipReport> {
  const call = (method: string, path: string, token: string, body?: unknown) =>
    fetch(baseUrl + path, {
      method,
      headers: { authorization: `Bearer ${token}`, ...(body === undefined ? {} : { "content-type": "application/json" }) },
      body: body === undefined ? undefined : JSON.stringify(body),
    });

  const created = await (await call("POST", "/tasks", tokenA, { title: "של A" })).json();
  const path = `/tasks/${created.id}`;
  const get = (await call("GET", path, tokenB)).status;
  const patch = (await call("PATCH", path, tokenB, { title: "B היה כאן" })).status;
  const del = (await call("DELETE", path, tokenB)).status;
  const after = await call("GET", path, tokenA);
  const stillExists = after.status === 200;
  const title = stillExists ? (await after.json()).title : "";
  return { get, patch, delete: del, stillExists, title };
}

export function isSafe(r: OwnershipReport): boolean {
  return r.get === 404 && r.patch === 404 && r.delete === 404 && r.stillExists && r.title === "של A";
}

שים לב למה שהבודק תופס: שרת שמחזיר 404 על ה־PATCH אבל משנה את המשימה נראה בטוח לפי ה־status. לכן בודקים גם מה קרה בפועל (קריאה של A בסוף). ככה כתובים בדיקות אבטחה: לא רק "מה ענו לי", אלא "מה השתנה".

⚠️ טעויות נפוצות
  • להסתפק ב־status. השרת הפגיע בבודק מחזיר 404 ובכל זאת משנה.
  • Promise.all על שלוש הבקשות של B — ה־DELETE יכול לרוץ ראשון, וה־PATCH מקבל 404 "בצדק".

P21-E100 · החלפת סיסמה בטרנזקציה 🤖 💻 כתיבת קוד 🤖 רמה 4

💡 רמז 1

המבנה מפרק 18:

const client = await pool.connect(); try { await client.query("BEGIN"); ...; await client.query("COMMIT"); } catch (err) { await client.query("ROLLBACK"); throw err; } finally { client.release(); }
💡 רמז 2

ביציאה מוקדמת (NOT_FOUND, ‏WRONG_PASSWORD) גם צריך ROLLBACK לפני ה־return (או COMMIT: לא שינית כלום, אבל הנעילה של FOR UPDATE חייבת להשתחרר).

✅ פתרון
// P21-E100: החלפת סיסמה וביטול refresh tokens — הכול או כלום
import bcrypt from "bcryptjs";

type Client = { query(text: string, params?: unknown[]): Promise<any>; release(): void };
type Pool = { connect(): Promise<Client> };

export async function changePassword(
  pool: Pool,
  userId: number,
  oldPassword: string,
  newPassword: string,
  rounds: number,
  now: Date,
): Promise<"OK" | "NOT_FOUND" | "WRONG_PASSWORD"> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const { rows } = await client.query("SELECT password_hash FROM users WHERE id = $1 FOR UPDATE", [userId]);
    if (rows.length === 0) {
      await client.query("ROLLBACK");
      return "NOT_FOUND";
    }
    if (!(await bcrypt.compare(oldPassword, rows[0].password_hash))) {
      await client.query("ROLLBACK");
      return "WRONG_PASSWORD";
    }
    const hash = await bcrypt.hash(newPassword, rounds);
    await client.query("UPDATE users SET password_hash = $1 WHERE id = $2", [hash, userId]);
    await client.query("UPDATE refresh_tokens SET revoked_at = $1 WHERE user_id = $2 AND revoked_at IS NULL", [now, userId]);
    await client.query("COMMIT");
    return "OK";
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}

למה טרנזקציה? בלעדיה, אם ביטול הטוקנים נכשל, הסיסמה כבר הוחלפה, אבל התוקף שגנב refresh token ממשיך להיכנס. המשתמש בטוח שהוא "נעל" את החשבון, וזה מצב גרוע יותר מכישלון גלוי. ו־FOR UPDATE: שתי החלפות סיסמה באותו רגע לא ידרסו אחת את השנייה בלי לבדוק.

⚠️ טעויות נפוצות
  • pool.query("BEGIN") — כל פקודה יכולה ללכת לחיבור אחר, וה־BEGIN לא משפיע על כלום (פרק 18).
  • לשכוח release ביציאה מוקדמת — אחרי כמה ניסיונות כושלים ה־pool ריק והשרת נתקע.
