P21-E01 · hash, הצפנה או encoding? 🧠 הבנה רמה 1

💡 רמז 1

טבלת שלוש השורות בתחילת שיעור 1.

💡 רמז 2

חשוב מה יש לתוקף שמחזיק עותק של המסד וגם של קוד השרת וה־env.

✅ פתרון
  1. לא. הצפנה הפיכה — מי שמשיג את המפתח (שיושב באותו שרת, ב־env) מקבל את כל הסיסמאות. ומי שעובד בחברה עם גישה למפתח — גם.
  2. לא. Base64 הוא encoding: Buffer.from(x, "base64").toString() וזהו. זו לא הגנה בכלל.
  3. לא. הוא חד־כיווני, אבל מהיר ובלי salt: תוקף מנחש מיליארדי סיסמאות נפוצות בשנייה, וכל ניחוש נבדק מול כל המשתמשים בבת אחת.
  4. לא. ל־bcrypt יש salt אקראי חדש בכל hash — ראית בשיעור ש־a === b הוא false.
  5. לא. בגלל ה־salt, hash חדש לעולם לא יהיה שווה לישן. משתמשים ב־bcrypt.compare(password, hash), שקורא את ה־salt מתוך ה־hash.
  6. לא — ואם זה אפשרי, משהו שבור. השרת לא אמור להיות מסוגל לשחזר סיסמה. "שכחתי סיסמה" שולח קישור חד־פעמי עם טוקן אקראי לקביעת סיסמה חדשה.
⚠️ טעויות נפוצות
  • להשתמש ב"מוצפן" כמילה כללית ל"מוגן". בראיון — "שומרים hash איטי עם salt (bcrypt או Argon2)", לא "מצפינים".

P21-E29 · לקרוא מחרוזת של bcrypt 🧠 הבנה רמה 1

💡 רמז 1

חזור לאיור 1 בשיעור: $2b$, אחר כך שתי ספרות, ואז 22 + 31 תווים.

💡 רמז 2

כל +1 ב־cost מכפיל את הזמן.

✅ פתרון
  • (א) cost ‏11 — פי 2 מ־10 (‏211 מול 210 סבבים).
  • (ב) אחרי $2b$11$: ‏22 התווים הראשונים הם ה־salt (‏C6UzMDM.H6dfI/f/IKxGhu), ו־31 האחרונים הם התוצאה.
  • (ג) מהמחרוזת עצמה. ‏compare קורא ממנה גרסה, cost ו־salt, מחשב שוב עם הסיסמה שהוקלדה, ומשווה. לכן לא צריך עמודה נפרדת ל־salt.
  • (ד) לא: salt חדש בכל קריאה, אז המחרוזת שונה. זה לא מפריע: הכניסה לא משווה מחרוזות, היא קוראת ל־compare מול מה ששמור.
⚠️ טעויות נפוצות
  • לחשוב שה־salt "סודי" וצריך להסתיר אותו. הוא לא סוד: התפקיד שלו הוא רק שכל hash יהיה שונה.

P21-E30 · כמה עולה ניחוש? 🧠 הבנה רמה 2

💡 רמז 1

כל +1 מכפיל ב־2. מ־10 ל־12 זה ‏2×2.

💡 רמז 2

בזכות ה־salt, כל משתמש דורש חישוב נפרד לכל ניחוש.

✅ פתרון
  • (א) cost ‏12 ← כ־280ms (‏×4). ‏14 ← כ־1.1 שניות (‏×16).
  • (ב) בערך 3–4 כניסות בשנייה לליבה. השרת צריך את זה רק פעם אחת בכניסה, אז זה סביר.
  • (ג) מיליון ניחושים × 0.28 שנייה = כ־280,000 שניות־ליבה. חלקי 10,000 ליבות = כ־28 שניות למשתמש אחד. על 100,000 משתמשים: כ־2.8 מיליון שניות, יותר מחודש. עם SHA-256 בלי salt היו מחשבים כל ניחוש פעם אחת לכולם, בשבריר שנייה.
  • (ד) cost ‏20 הוא כ־70 שניות לכניסה. המשתמש לא יחכה, ועשרה ניסיונות כניסה בו־זמנית יתקעו את השרת (תוקף יכול לנצל את זה). בוחרים את ה־cost הכי גבוה שעדיין נותן עשיריות שנייה.
⚠️ טעויות נפוצות
  • לשכוח שה־salt הוא מה שמכפיל את העבודה במספר המשתמשים. ה־cost לבד רק מאט כל ניחוש.

P21-E31 · 72 בתים: מה עובר? 🧠 הבנה רמה 2

💡 רמז 1

Buffer.byteLength(s, "utf8"). אותיות לטיניות בסיסיות: בית אחד. עברית ו־ä: שניים. אמוג'י: ארבעה.

💡 רמז 2

ואמוג'י הוא גם 2 ב־length של JavaScript (שני "חצאים" של UTF-16).

✅ פתרון
const list = ["a".repeat(72), "שלום".repeat(9), "שלום".repeat(10), "סיסמה ארוכה מאוד בעברית עם רווחים", "🔒".repeat(18), "pässwörd"];
for (const s of list) {
  const bytes = Buffer.byteLength(s, "utf8");
  console.log(s.length, bytes, s.length >= 8 && bytes <= 72 ? "מתקבלת" : "נדחית");
}
72 72 מתקבלת
36 72 מתקבלת
40 80 נדחית
33 61 מתקבלת
36 72 מתקבלת
8 10 מתקבלת

‏length סופר יחידות של UTF-16, לא בתים. ‏"שלום".repeat(10) היא 40 תווים, אבל 80 בתים: length <= 72 היה מאשר אותה, ו־bcrypt היה חותך בשקט את 8 הבתים האחרונים. האמוג'י: 36 ב־length, ‏72 בתים, בדיוק על הגבול.

⚠️ טעויות נפוצות
  • לבדוק length ולחשוב שזה "בערך אותו דבר". בעברית זה פי 2.

P21-E32 · למה אין "חיפוש לפי hash"? 🧠 הבנה רמה 2

💡 רמז 1

מה נותנות שתי קריאות ל־hash על אותה סיסמה (שיעור 1, סעיף 3)?

💡 רמז 2

salt קבוע לכולם מחזיר את שתי הבעיות של SHA-256.

✅ פתרון
  • (א) כל hash מגריל salt חדש, אז ה־hash החדש אף פעם לא שווה לשמור.
  • (ב) עם salt קבוע לכל המשתמשים, שתי סיסמאות זהות נותנות hash זהה, ואפשר לנחש פעם אחת לכולם. זה בדיוק מה שה־salt היה אמור למנוע.
  • (ג) מחפשים לפי מה שייחודי וגלוי (האימייל), ובודקים עם compare:
const user = await this.users.findByEmail(email);
if (!user || !(await bcrypt.compare(password, user.passwordHash))) throw invalidCredentials();
return this.issueTokens(user);

(ובקוד המלא: גם כשאין משתמש מריצים compare מול hash "דמה", כדי שהזמן לא יסגיר. ראה E18.)

⚠️ טעויות נפוצות
  • לפתור "את הבאג" ולשבור את האבטחה. אם התיקון הוא "salt קבוע", חזור לשאלה למה ה־salt קיים.

P21-E33 · מה מותר לכתוב בלוג? 🧠 הבנה רמה 1

שלושה דברים לא נכנסים אף פעם ללוג: סיסמה, hash, טוקן.

איפה בבקשה יש טוקן? ב־headers.

P21-E06 · hash לסיסמאות 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

bcrypt.hash, bcrypt.compare, bcrypt.getRounds — כולם בשיעור 1.

💡 רמז 2

hashPassword היא async, אז throw בתוכה הופך ל־Promise שנדחה — וזה מה שהבודק מצפה (assert.rejects).

✅ פתרון
// P21-E06
import bcrypt from "bcryptjs";

export async function hashPassword(password: string, rounds = 12): Promise<string> {
  if (password.length === 0) throw new Error("סיסמה ריקה");
  return bcrypt.hash(password, rounds);
}

export function verifyPassword(password: string, hash: string): Promise<boolean> {
  return bcrypt.compare(password, hash);
}

// hash ישן עם cost נמוך מהנוכחי? בכניסה הבאה (כשיש לנו את הסיסמה) — מחשבים מחדש
export function needsRehash(hash: string, rounds = 12): boolean {
  return bcrypt.getRounds(hash) < rounds;
}

למה needsRehash? כי cost טוב היום יהיה חלש בעוד כמה שנים (מחשבים מתחזקים). אי אפשר לחשב hash חדש בלי הסיסמה — אבל בכניסה מוצלחת הסיסמה בידיים: if (needsRehash(user.passwordHash)) save(await hashPassword(password)). כך המשתמשים "משתדרגים" בהדרגה, בלי שאף אחד יקליד סיסמה מחדש.

⚠️ טעויות נפוצות
  • hash === await hashPassword(password) במקום compare — תמיד false (salt).
  • לשכוח await לפני bcrypt.compare ← Promise הוא "truthy", וכל סיסמה עוברת!

P21-E07 · מדיניות סיסמאות 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

Buffer.byteLength(password, "utf8") — בתים, לא תווים.

💡 רמז 2

"תווים": [...password].length סופר נכון גם אימוג'י (ש־.length סופר כ־2).

✅ פתרון
// P21-E07
export const COMMON_PASSWORDS = ["password", "12345678", "123456789", "qwerty123", "iloveyou", "11111111", "password1", "abcd1234"];

export function validatePassword(password: string, email: string): string[] {
  const problems: string[] = [];
  if ([...password].length < 8) problems.push("לפחות 8 תווים");
  if (Buffer.byteLength(password, "utf8") > 72) problems.push("עד 72 בתים");
  if (COMMON_PASSWORDS.includes(password.toLowerCase())) problems.push("סיסמה נפוצה מדי");
  const local = email.split("@")[0].toLowerCase();
  if (local.length >= 3 && password.toLowerCase().includes(local)) problems.push("הסיסמה לא יכולה להכיל את האימייל");
  return problems;
}

למה להחזיר רשימה ולא לזרוק בבעיה הראשונה? כי הלקוח (טופס ההרשמה) יכול להציג את כולן בבת אחת. ולמה אין "חייב אות גדולה"? כי זה מוביל ל־Password1 — שנמצא ברשימה. אורך, וחסימת סיסמאות מוכרות, מגנים יותר.

⚠️ טעויות נפוצות
  • password.length > 72 — סופר תווים. 40 אותיות בעברית הן 80 בתים, ו־bcrypt יחתוך בשקט.
  • לבדוק את האימייל כולו (dana@example.com) במקום את החלק המקומי — אף אחד לא כותב את הכתובת המלאה בסיסמה, אבל dana123 נפוץ מאוד.

P21-E18 · לא לגלות מי רשום 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

את ה־hash הדמה מחשבים פעם אחת (ושומרים את ה־Promise), לא בכל ניסיון.

💡 רמז 2

timingSafeEqual זורק כשהאורכים שונים. אם תעביר לו את ה־SHA-256 של שני הצדדים — הם תמיד 32 בתים.

✅ פתרון
// P21-E18
import { createHash, timingSafeEqual } from "node:crypto";
import { Inject, Injectable, UnauthorizedException } from "@nestjs/common";

export const PASSWORD_HASHER = "PASSWORD_HASHER";
export interface PasswordHasher {
  hash(password: string): Promise<string>;
  compare(password: string, hash: string): Promise<boolean>;
}

interface User {
  id: number;
  email: string;
  passwordHash: string;
}

@Injectable()
export class LoginService {
  private readonly users: User[] = [];
  private dummyHash?: Promise<string>;

  constructor(@Inject(PASSWORD_HASHER) private readonly hasher: PasswordHasher) {}

  async addUser(email: string, password: string) {
    this.users.push({ id: this.users.length + 1, email, passwordHash: await this.hasher.hash(password) });
  }

  async login(email: string, password: string): Promise<{ userId: number }> {
    const user = this.users.find((u) => u.email === email);
    // compare רץ בדיוק פעם אחת בכל מקרה — גם כשאין משתמש
    this.dummyHash ??= this.hasher.hash("dummy-password-nobody-knows");
    const ok = await this.hasher.compare(password, user ? user.passwordHash : await this.dummyHash);
    if (!user || !ok) throw new UnauthorizedException("אימייל או סיסמה שגויים");
    return { userId: user.id };
  }
}

// השוואה בזמן קבוע: === עוצר בתו הראשון שונה, ולכן "מדליף" כמה תווים נכונים
export function safeEqual(a: string, b: string): boolean {
  // hash קודם — כך שני הצדדים באותו אורך, ו־timingSafeEqual לא זורק
  const ha = createHash("sha256").update(a).digest();
  const hb = createHash("sha256").update(b).digest();
  return timingSafeEqual(ha, hb);
}

למה זה חשוב: בלי hash דמה, "אין משתמש" חוזר תוך מילישנייה ו"סיסמה שגויה" אחרי עשירית שנייה — וזה מספיק כדי לבנות רשימת לקוחות. ו־=== על מחרוזות עוצר בתו הראשון שונה: מדידה זהירה מגלה כמה תווים מההתחלה נכונים, וכך אפשר לנחש מפתח תו אחר תו. (ב־E25 תשתמש ב־timingSafeEqual על מפתחות API.)

⚠️ טעויות נפוצות
  • if (a.length !== b.length) return false לפני timingSafeEqual — מדליף את האורך. ה־hash פותר גם את זה.

P21-E34 · ‏normalizeEmail 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

const email = input.trim().toLowerCase(); ואז email.split("@"): צריך לצאת מערך של בדיוק שני חלקים.

💡 רמז 2

domain.includes("."), ‏domain.startsWith("."), ‏domain.endsWith("."), ו־/\s/.test(email).

✅ פתרון
// P21-E34: normalizeEmail
export function normalizeEmail(input: string): string | null {
  const email = input.trim().toLowerCase();
  if (email.length > 254 || /\s/.test(email)) return null;
  const parts = email.split("@");
  if (parts.length !== 2) return null;
  const [local, domain] = parts;
  if (local === "" || !domain.includes(".") || domain.startsWith(".") || domain.endsWith(".")) return null;
  return email;
}

בפרויקט את זה עושה ה־schema של Zod (z.email() עם trim ו־toLowerCase). הנקודה החשובה היא איפה: מנרמלים פעם אחת, בכניסה למערכת. כך גם register וגם login מחפשים באותה צורה, וה־UNIQUE במסד באמת מונע כפילות.

⚠️ טעויות נפוצות
  • לנרמל בהרשמה ולשכוח בכניסה. מי שנרשם עם Dana@ לא יצליח להיכנס.
  • split("@").length === 2 נבדק לפני trim. אז " a@b.co" עובר, אבל עם רווח בהתחלה.

P21-E35 · ‏toPublicUser — בלי מה שלא יוצא 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

"הכול חוץ מ־" (const { passwordHash, ...rest } = user) מוציא גם את מה שיתווסף בעתיד. כאן צריך "רק את אלה".

💡 רמז 2
return { id: user.id, email: user.email, role: user.role, createdAt: user.createdAt };

ו־users.map(toPublicUser).

✅ פתרון
// P21-E35: toPublicUser — רשימה מפורשת של מה שיוצא
export type User = { id: number; email: string; passwordHash: string; role: "user" | "admin"; createdAt: string };
export type PublicUser = Omit<User, "passwordHash">;

export function toPublicUser(user: User): PublicUser {
  return { id: user.id, email: user.email, role: user.role, createdAt: user.createdAt };
}

export function toPublicUsers(users: User[]): PublicUser[] {
  return users.map(toPublicUser);
}

זה אותו עיקרון כמו ב־mass assignment (שיעור 4), רק בכיוון ההפוך: רשימה מפורשת של מה שמותר לצאת, לא "הכול חוץ מ־". מחר מישהו יוסיף לטבלה reset_token או mfa_secret. עם rest, השדה יוצא לכל לקוח בלי שאף אחד שם לב.

⚠️ טעויות נפוצות
  • delete user.passwordHash — משנה את האובייקט המקורי. אם הוא בא מ־cache, ה־hash נעלם גם לכניסה הבאה.

P21-E36 · להסתיר סודות לפני לוג 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

רקורסיה (פרק 5): אם Array.isArray(value) ← value.map(redact). אם אובייקט (ולא null) ← עוברים על Object.entries.

💡 רמז 2
const SENSITIVE = /password|token|secret|authorization|cookie/i;

ואז SENSITIVE.test(key) ? "[REDACTED]" : redact(v).

✅ פתרון
// P21-E36: redact — עותק בלי סודות, לפני שרושמים ללוג
const SENSITIVE = /password|token|secret|authorization|cookie/i;

export function redact(value: unknown): unknown {
  if (Array.isArray(value)) return value.map(redact);
  if (value === null || typeof value !== "object") return value;
  const out: Record<string, unknown> = {};
  for (const [key, v] of Object.entries(value)) {
    out[key] = SENSITIVE.test(key) ? "[REDACTED]" : redact(v);
  }
  return out;
}

הגנה כזו כדאי לשים במקום אחד (ה־logger), ולא לסמוך על כל מפתח שיזכור. בפרק 24 תראה שספריות לוגים (pino) מקבלות רשימת נתיבים להסתרה, וזה אותו רעיון.

⚠️ טעויות נפוצות

  • להחליף רק ברמה העליונה. ‏{ user: { password } } עדיין דולף.
  • להשתמש ב־regex עם הדגל g ו־test. ‏lastIndex נשמר בין קריאות, ומפתח רגיש "מדלג" כל פעם שנייה.

P21-E37 · ‏PasswordService עם hash "דמה" 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

שדה פרטי private dummy?: Promise<string>. ב־verifyAgainstDummy: ‏this.dummy ??= bcrypt.hash("dummy-password", this.rounds).

💡 רמז 2

שומרים את ה־Promise ולא את התוצאה. כך גם שתי קריאות ראשונות באותו רגע מחשבות פעם אחת. ואחרי ה־compare: ‏return false.

✅ פתרון
// P21-E37: PasswordService — hash, verify, ו־verifyAgainstDummy באותו זמן
import bcrypt from "bcryptjs";

export class PasswordService {
  private readonly rounds: number;
  private dummy?: Promise<string>;

  constructor(rounds: number) {
    this.rounds = rounds;
  }

  hash(password: string): Promise<string> {
    return bcrypt.hash(password, this.rounds);
  }

  verify(password: string, hash: string): Promise<boolean> {
    return bcrypt.compare(password, hash);
  }

  async verifyAgainstDummy(password: string): Promise<false> {
    this.dummy ??= bcrypt.hash("dummy-password-not-a-real-user", this.rounds);
    await bcrypt.compare(password, await this.dummy);
    return false;
  }
}

למה אותו cost? ‏compare מול hash עם cost ‏4 לוקח מילישניות, ומול cost ‏12 כ־250ms. אם הדמה "זול" יותר, ההבדל בזמן עדיין מסגיר מי רשום.

⚠️ טעויות נפוצות
  • להחזיר את התוצאה של compare. אם מישהו מקליד את סיסמת הדמה, הוא "נכנס" כמשתמש שלא קיים.
  • hash דמה קבוע בקוד עם cost אחר מה־rounds של השרת.
  • לחשב hash חדש בכל קריאה. זה כפול זמן (hash ואז compare), וההבדל בזמן חוזר.

// P21-E38: parseBcrypt
export type BcryptParts = { version: string; cost: number; salt: string; hash: string };

const RE = /^\$(2[aby])\$(\d{2})\$([./A-Za-z0-9]{22})([./A-Za-z0-9]{31})$/;

export function parseBcrypt(value: string): BcryptParts | null {
  const m = value.match(RE);
  if (!m) return null;
  const cost = Number(m[2]);
  if (cost < 4 || cost > 31) return null;
  return { version: m[1], cost, salt: m[3], hash: m[4] };
}

P21-E42 · הרשמה בלי כפילויות, גם במקביל 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

אם הבדיקה "קיים?" קורית לפני await bcrypt.hash, כל חמש הבקשות עוברות אותה. איפה עוד אפשר לבדוק?

💡 רמז 2

בדוק אחרי ה־await, ומיד לפני set, בלי await ביניהם. כך הבדיקה וההכנסה קורות "ביחד" (כמו UNIQUE במסד). אפשר לבדוק גם לפני ה־hash, כדי לחסוך עבודה.

✅ פתרון
// P21-E42: הרשמה בלי כפילויות — גם כשהבקשות מגיעות יחד
import bcrypt from "bcryptjs";

type Stored = { id: number; email: string; passwordHash: string };

export class UsersRegistry {
  private byEmail = new Map<string, Stored>();
  private nextId = 1;
  private readonly rounds: number;

  constructor(rounds: number) {
    this.rounds = rounds;
  }

  async register(email: string, password: string): Promise<{ id: number; email: string }> {
    const normalized = email.trim().toLowerCase();
    if (this.byEmail.has(normalized)) throw new Error("EMAIL_TAKEN"); // חיסכון: לא מחשבים hash סתם
    const passwordHash = await bcrypt.hash(password, this.rounds);
    // מכאן ועד ה־set אין await — שום בקשה אחרת לא יכולה "להיכנס באמצע"
    if (this.byEmail.has(normalized)) throw new Error("EMAIL_TAKEN");
    const user = { id: this.nextId++, email: normalized, passwordHash };
    this.byEmail.set(normalized, user);
    return { id: user.id, email: user.email };
  }

  findByEmail(email: string): Stored | undefined {
    return this.byEmail.get(email.trim().toLowerCase());
  }

  get size(): number {
    return this.byEmail.size;
  }
}

ב־JavaScript, קוד בין שני await רץ ברצף אחד, בלי הפרעה. לכן "בדיקה + set" בלי await ביניהם הוא אטומי בתוך תהליך אחד. ועם כמה שרתים? רק המסד רואה את כולם, ולכן בפרויקט סומכים על UNIQUE ולא על בדיקה בקוד.

⚠️ טעויות נפוצות
  • לבדוק רק לפני ה־hash: כל החמש עוברות, ויש חמישה משתמשים.
  • לקדם את nextId לפני הבדיקה השנייה. אז יש "חורים" במספרים.

P21-E43 · לעבור מ־SHA-256 ל־bcrypt בלי לאפס סיסמאות 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

createHash("sha256").update(password).digest() נותן Buffer של 32 בתים. ‏Buffer.from(user.passwordHash, "hex") נותן את מה ששמור.

💡 רמז 2

timingSafeEqual(a, b) משני Buffers באותו אורך. הבדיקה /^[0-9a-f]{64}$/ מבטיחה שהאורך 32.

✅ פתרון
// P21-E43: מעבר הדרגתי מ־SHA-256 ל־bcrypt
import bcrypt from "bcryptjs";
import { createHash, timingSafeEqual } from "node:crypto";

export type StoredUser = { id: number; passwordHash: string };

export async function verifyAndUpgrade(
  user: StoredUser,
  password: string,
  save: (id: number, newHash: string) => Promise<void>,
  rounds: number,
): Promise<boolean> {
  if (user.passwordHash.startsWith("$2")) return bcrypt.compare(password, user.passwordHash);
  if (!/^[0-9a-f]{64}$/.test(user.passwordHash)) return false;
  const given = createHash("sha256").update(password).digest();
  const stored = Buffer.from(user.passwordHash, "hex");
  if (!timingSafeEqual(given, stored)) return false;
  await save(user.id, await bcrypt.hash(password, rounds));
  return true;
}

כך משדרגים מערכת בלי "כולם מאפסים סיסמה": כל מי שנכנס עובר ל־bcrypt. מי שלא נכנס חודשים? בדרך כלל, אחרי תקופה, מוחקים את ה־hash הישן שלו ושולחים לו קישור לאיפוס. (יש גם טכניקה של bcrypt על ה־SHA-256 הישן, כדי להגן על כולם מיד. חפש "password hash wrapping".)

⚠️ טעויות נפוצות
  • === בין מחרוזות hex — עובד, אבל לא בזמן קבוע.
  • לשמור את ה־hash החדש לפני שבדקת שהסיסמה נכונה. אז כל אחד "משנה" סיסמה של אחר.

// P21-E44: registerSchema — strict, אימייל מנורמל, 8 תווים עד 72 בתים
import { z } from "zod";

export const registerSchema = z.strictObject({
  email: z.string().trim().toLowerCase().pipe(z.email()),
  password: z
    .string()
    .min(8, "לפחות 8 תווים")
    .refine((p) => Buffer.byteLength(p, "utf8") <= 72, "עד 72 בתים"),
});

export function parseRegister(body: unknown) {
  const r = registerSchema.safeParse(body);
  if (r.success) return { ok: true as const, data: r.data };
  const errors = r.error.issues.map((i) => (i.path.length ? `${i.path.join(".")}: ${i.message}` : i.message));
  return { ok: false as const, errors };
}
