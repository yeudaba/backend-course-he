P26.3-E85 · ‏controller, ‏agent ו־Multibranch 🧠 הבנה רמה 1

💡 רמז 1

ה־controller מחזיק את כל הסודות ואת ההיסטוריה.

💡 רמז 2

"pipeline as code" — הקובץ בתוך ה־repo.

✅ פתרון
  1. ה־controller: הממשק, התזמון, ההיסטוריה, ה־Credentials. ה־agents: מריצים את ה־steps. build על ה־controller — קוד של כל ענף רץ ליד כל הסודות של כל הפרויקטים, ו־build כבד מאט את ה־Jenkins כולו.
  2. כל build מתחיל מקונטיינר נקי, עם גרסה מדויקת של Node שכתובה בקובץ. בלי "אצלי עובד" בגלל משהו שנשאר מ־build קודם, ושני פרויקטים עם גרסאות שונות לא מתנגשים.
  3. יוצר job לענף/PR ומריץ את ה־Jenkinsfile מהענף. לכן שינוי ב־pipeline נבדק ב־PR לפני שהוא נכנס ל־main — וגם לכן when { branch 'main' } חשוב: PR לא יכול לדחוף image (‏E90).
⚠️ טעויות נפוצות
  • "ה־Jenkinsfile מוגדר בממשק של Jenkins" — זה ה־"Pipeline script" הישן; ‏pipeline as code הוא קובץ ב־repo.

P26.3-E86 · מ־GitHub Actions ל־Jenkins 🧠 הבנה רמה 2

💡 רמז 1

טבלת ההשוואה בשיעור.

💡 רמז 2

‏checkout — ב־Multibranch הוא קורה לבד.

✅ פתרון
  • container: node:24-alpine ← ‏agent { docker { image 'node:24-alpine' } }.
  • timeout-minutes: 15 ← ‏options { timeout(time: 15, unit: 'MINUTES') }.
  • actions/checkout ← לא צריך (Multibranch עושה checkout), או checkout scm.
  • ‏run: npm ci ו־npm test ← ‏stage('Install') { steps { sh 'npm ci' } } וכן הלאה.
  • if: github.ref == …main ← ‏when { branch 'main' } בתוך stage.
  • secrets.GHCR_TOKEN ← ‏withCredentials עם string(credentialsId: 'ghcr-token', variable: 'TOKEN'), ו־sh 'echo $TOKEN | …' במרכאות בודדות.
  • if: failure() ← ‏post { failure { echo 'CI failed' } }.
⚠️ טעויות נפוצות
  • לתרגם "$TOKEN" ל־sh "echo ${TOKEN} | …" — ב־Groovy זו בדיוק ה־interpolation של הסוד (‏E87).

P26.3-E87 · מה מגיע ל־shell? 🧠 הבנה רמה 2

💡 רמז 1

מרכאות כפולות ב־Groovy ← Groovy מציב לפני ה־shell.

💡 רמז 2

מרכאות בודדות ← הטקסט עובר כמו שהוא, וה־shell קורא את משתנה הסביבה.

✅ פתרון
  1. ‏curl -H "Authorization: token $TOKEN" … — ה־shell מציב. הטוקן לא בטקסט של הפקודה. בטוח.
  2. ‏curl -H 'Authorization: token ghp_abc123' … — הטוקן בתוך הפקודה: נראה ב־ps על ה־agent, ו־Jenkins מזהיר "insecure interpolation".
  3. ‏echo building main — בסדר: שם ענף הוא לא סוד. (ובכל זאת — שם ענף מגיע ממשתמש; מרכאות בודדות בטוחות יותר גם מפני הזרקה.)
  4. ‏echo building $BRANCH_NAME — ה־shell מציב. בטוח.
  5. גרוע פעמיים: הטוקן בטקסט, וגם כארגומנט -p — גלוי ב־ps לכל תהליך במכונה. ‏--password-stdin.
⚠️ טעויות נפוצות
  • "Jenkins מסתיר סודות בלוג, אז זה בסדר" — ההסתרה היא בלוג בלבד, לא ב־ps, ולא בקבצים שהפקודה כותבת.

P26.3-E88 · איפה זה נשבר, ומה רואים? 🧠 הבנה רמה 2

💡 רמז 1

כל שלב — מערכת אחרת: Jenkins, ‏registry, ‏Git, ‏Argo, ‏Kubernetes.

💡 רמז 2

pod חדש שלא Ready — לא מקבל תנועה.

✅ פתרון
  1. Jenkins — אדום, ה־image לא נבנה. הלקוחות: כלום. איפה: הלוג של ה־build ודוח הבדיקות.
  2. Jenkins — אדום ב־Push. לקוחות: כלום. איפה: הלוג (‏denied/unauthorized) ← לחדש את ה־Credential.
  3. Jenkins — אדום ב־Update config. ה־image קיים ב־registry, אבל לא בפרודקשן. איפה: הלוג; התיקון: ‏git pull --rebase וניסיון חוזר בתוך הצעד.
  4. Argo: ‏Synced, ‏Progressing ← Degraded. לקוחות: כלום — ה־rollout נתקע, הישנים עונים (‏E60). איפה: Argo ← ה־pod ← ‏logs --previous.
  5. אותו דבר: Running 0/1, ה־rollout תקוע, הלקוחות לא מרגישים. איפה: Events של ה־probe, ולוג העלייה. התיקון: המשתנה ב־values (או Secret) — commit ל־repo התצורה.
⚠️ טעויות נפוצות
  • לחפש ב־Jenkins למה הפרודקשן לא התעדכן כשה־build ירוק — מאותו רגע זה Argo ו־Kubernetes.

P26.3-E89 · איזה post רץ? 🧠 הבנה רמה 2

💡 רמז 1

‏always — תמיד. ‏cleanup — תמיד, ואחרון.

💡 רמז 2

stage שדולג בגלל when הוא לא כישלון.

✅ פתרון
  1. always, ‏success, ‏cleanup.
  2. always, ‏failure, ‏cleanup — וה־stages שאחרי הבדיקות לא רצים.
  3. always, ‏success, ‏cleanup — דילוג הוא לא כישלון.
  4. always, ‏cleanup (ו־aborted אם הוגדר). לא success ולא failure.

‏junit ב־always — כי דוח הבדיקות חשוב בדיוק כשהן נכשלות: Jenkins מראה איזו בדיקה ולמה. ב־success הוא היה מופיע רק כשאין מה לראות.

⚠️ טעויות נפוצות
  • לשים deleteDir() ב־always לפני junit — הדוח נמחק לפני שנקרא. לכן cleanup הוא נפרד, ורץ אחרון.

P26.3-E90 · ‏when { branch 'main' } ו־tag של image 🧠 הבנה רמה 1

💡 רמז 1

Multibranch מריץ את ה־Jenkinsfile של כל ענף.

💡 רמז 2

מה רץ בפרודקשן עכשיו? ומה עושה rollback?

✅ פתרון
  1. ה־PR דוחף image ל־registry עם הרשאות של main — קוד שאף אחד לא עשה לו review נבנה ונדחף, ואולי אף מחליף tag שבשימוש. (ועם repo ציבורי — PR מ־fork הוא קוד של זר שרץ עם הסודות שלך.)
  2. (א) אי אפשר לדעת איזו גרסה רצה. (ב) ‏rollback "ל־latest הקודם" לא קיים — הוא נדרס. (ג) ‏Kubernetes לא מזהה שינוי ב־template (אותה מחרוזת) ← אין rollout, ו־nodes שונים מריצים גרסאות שונות לפי מתי משכו.
  3. ‏GIT_COMMIT: מצביע בדיוק על הקוד, יציב בין builds ובין מערכות CI. ‏BUILD_NUMBER מתאפס כשה־job נוצר מחדש, ולא אומר מה הקוד.
⚠️ טעויות נפוצות
  • "נוסיף גם latest לנוחות" — אפשר, כל עוד שום manifest לא משתמש בו.

P26.3-E16 · Jenkinsfile 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

withCredentials([usernamePassword(credentialsId: 'ghcr', usernameVariable: '…', passwordVariable: '…')]) { … }.

💡 רמז 2

בתוך sh, מרכאות בודדות: ה־shell מציב את המשתנה, לא Groovy — אז הסוד לא נכנס למחרוזת של ה־pipeline.

✅ פתרון
// P26.3-E16: pipeline של coffee-api ב־Jenkins
pipeline {
  agent { docker { image 'node:24-alpine' } }

  options {
    timeout(time: 20, unit: 'MINUTES')
    disableConcurrentBuilds()
  }

  environment {
    IMAGE = 'ghcr.io/noa-cohen/coffee-shop'
    TAG = "${env.GIT_COMMIT.take(7)}"
  }

  stages {
    stage('Install') {
      steps {
        sh 'npm ci'
      }
    }
    stage('Lint & Typecheck') {
      steps {
        sh 'npm run lint'
        sh 'npm run typecheck'
      }
    }
    stage('Test') {
      steps {
        sh 'npm test'
      }
    }
    stage('Build image') {
      steps {
        sh 'docker build -t $IMAGE:$TAG .'
      }
    }
    stage('Push image') {
      when { branch 'main' }
      steps {
        withCredentials([usernamePassword(credentialsId: 'ghcr', usernameVariable: 'REG_USER', passwordVariable: 'REG_TOKEN')]) {
          sh 'echo $REG_TOKEN | docker login ghcr.io -u $REG_USER --password-stdin'
          sh 'docker push $IMAGE:$TAG'
        }
      }
    }
  }

  post {
    always {
      junit allowEmptyResults: true, testResults: 'reports/junit.xml'
    }
    failure {
      echo "Build failed: ${env.BUILD_URL}"
    }
  }
}

זה אותו CI מפרק 25, בשפה אחרת: stages ← jobs/steps, when { branch 'main' } ← if: github.ref == 'refs/heads/main', Credentials ← Secrets. Jenkins נפוץ בחברות עם שרתים משלהן ו־pipelines בני עשר שנים — מי שמכיר אחד, לומד את השני ביום.

⚠️ טעויות נפוצות
  • sh "docker login -p ${REG_TOKEN}" — Groovy מציב את הסוד לתוך הפקודה, Jenkins מזהיר "insecure interpolation", והסיסמה גלויה ב־ps.

P26.3-E23 · pipeline "שעובד" — ארבע תקלות 🤖 💻 כתיבת קוד 🤖 רמה 4

💡 רמז 1

מה קורה כשמישהו עושה push לענף feature/try-something?

💡 רמז 2

credentials('ghcr') ב־environment של משתמש וסיסמה יוצר שני משתנים: REG_USR ו־REG_PSW.

✅ פתרון
// P26.3-E23: אחרי התיקון
pipeline {
  agent { docker { image 'node:24-alpine' } }
  options {
    timeout(time: 20, unit: 'MINUTES') // תיקון 4: build תקוע לא תופס executor לנצח
  }
  environment {
    REG = credentials('ghcr') // תיקון 1: מ־Jenkins Credentials — יוצר REG_USR ו־REG_PSW, ומסתיר בלוג
  }
  stages {
    stage('Install') {
      steps {
        sh 'npm ci' // תיקון 2: בדיוק לפי package-lock
      }
    }
    stage('Test') {
      steps {
        sh 'npm test'
      }
    }
    stage('Push') {
      when { branch 'main' } // תיקון 3: רק מ־main
      steps {
        sh 'echo $REG_PSW | docker login ghcr.io -u $REG_USR --password-stdin'
        sh 'docker build -t ghcr.io/noa-cohen/coffee-shop:$GIT_COMMIT .'
        sh 'docker push ghcr.io/noa-cohen/coffee-shop:$GIT_COMMIT'
      }
    }
  }
}

וה־token שהיה בקובץ — מבטלים ב־GitHub עכשיו. הוא ב־history של ה־repo לתמיד, גם אחרי שמחקת את השורה.

⚠️ טעויות נפוצות
  • להעביר את ה־token ל־environment של ה־job בממשק של Jenkins כטקסט רגיל — הוא עדיין לא מוסתר בלוג. Credentials בלבד.

P26.3-E91 · ‏Jenkinsfile שמעדכן את repo התצורה 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

שינוי ה־tag בשורה אחת של shell:

sed -i "s/^\(\s*tag:\).*/\1 \"$GIT_COMMIT\"/" charts/coffee-api/values-staging.yaml
💡 רמז 2

‏sh '''…''' (שלוש מרכאות בודדות) — כמה שורות של shell, בלי interpolation של Groovy.

✅ פתרון
// P26.3-E91: Jenkinsfile שמעדכן את repo התצורה
pipeline {
  agent { docker { image 'node:24-alpine' } }
  environment {
    IMAGE = 'ghcr.io/noa-cohen/coffee-shop'
  }
  stages {
    stage('Test') {
      steps {
        sh 'npm ci'
        sh 'npm test'
      }
    }
    stage('Push image') {
      when { branch 'main' }
      steps {
        withCredentials([usernamePassword(credentialsId: 'ghcr', usernameVariable: 'REG_USER', passwordVariable: 'REG_TOKEN')]) {
          sh 'echo $REG_TOKEN | docker login ghcr.io -u $REG_USER --password-stdin'
          sh 'docker build -t $IMAGE:$GIT_COMMIT . && docker push $IMAGE:$GIT_COMMIT'
        }
      }
    }
    stage('Update config') {
      when { branch 'main' }
      steps {
        withCredentials([usernamePassword(credentialsId: 'config-repo', usernameVariable: 'GIT_USER', passwordVariable: 'GIT_TOKEN')]) {
          sh '''
            git clone https://$GIT_USER:$GIT_TOKEN@github.com/noa-cohen/coffee-deploy.git deploy
            cd deploy
            sed -i "s/^\\(\\s*tag:\\).*/\\1 \\"$GIT_COMMIT\\"/" charts/coffee-api/values-staging.yaml
            git -c user.name=jenkins -c user.email=ci@coffee.example commit -am "staging: coffee-api $GIT_COMMIT"
            git push origin main
          '''
        }
      }
    }
  }
  post {
    failure { echo 'Build failed' }
  }
}

שים לב מה אין כאן: שום הרשאה ל־cluster. הסוד היחיד שקשור לפרודקשן הוא הרשאת כתיבה ל־repo התצורה — ושם יש היסטוריה, review והגנות ענפים. (ב־sed בתוך ''' של Groovy צריך להכפיל את ה־backslash.)

⚠️ טעויות נפוצות
  • sh "git clone https://${GIT_USER}:${GIT_TOKEN}@…" — הטוקן בטקסט של הפקודה.
  • לשכוח when ב־Update config — כל PR מעדכן את staging לגרסה שלו.

P26.3-E92 · למצוא סודות במרכאות כפולות 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

סורק תו־תו עם "מצב": קוד, מחרוזת בודדת, מחרוזת כפולה, משולשת בודדת, משולשת כפולה, הערה. ‏\n מעלה את מספר השורה בכל מצב.

💡 רמז 2

בכל מחרוזת כפולה שנסגרה (עם השורה שבה התחילה) — ‏regex על התוכן:

new RegExp(`\\$(?:\\{(?:env\\.)?${v}\\}|${v}(?![A-Za-z0-9_]))`, "g")
✅ פתרון
// P26.3-E92: למצוא סודות במרכאות כפולות
export function findInterpolatedSecrets(text: string, secretVars: string[]) {
  const out: { line: number; variable: string; at: number }[] = [];
  const check = (body: string, startLine: number, startAt: number) => {
    for (const v of secretVars) {
      const re = new RegExp(`\\$(?:\\{(?:env\\.)?${v}\\}|${v}(?![A-Za-z0-9_]))`, "g");
      for (const m of body.matchAll(re)) {
        const before = body.slice(0, m.index);
        out.push({ line: startLine + (before.match(/\n/g)?.length ?? 0), variable: v, at: startAt + m.index! });
      }
    }
  };
  let i = 0;
  let line = 1;
  while (i < text.length) {
    if (text.startsWith("//", i)) {
      while (i < text.length && text[i] !== "\n") i++;
      continue;
    }
    const quote = ['"""', "'''", '"', "'"].find((q) => text.startsWith(q, i));
    if (!quote) {
      if (text[i] === "\n") line++;
      i++;
      continue;
    }
    const startLine = line;
    const start = i + quote.length;
    let j = start;
    while (j < text.length && !text.startsWith(quote, j)) {
      if (text[j] === "\\") j++;
      else if (text[j] === "\n") line++;
      j++;
    }
    if (quote.startsWith('"')) check(text.slice(start, j), startLine, start);
    i = j + quote.length;
  }
  return out.sort((a, b) => a.at - b.at).map(({ line, variable }) => ({ line, variable }));
}

זה (בערך) מה שהאזהרה "insecure interpolation of sensitive variables" של Jenkins בודקת — אבל ב־review, לפני שהסוד כבר רץ. אפשר להריץ אותו ב־CI של ה־repo, על ה־Jenkinsfile עצמו.

⚠️ טעויות נפוצות
  • regex אחד על כל הקובץ (/"[^"]*\$TOKEN/) — נופל על מרכאות בודדות שמכילות ", על מחרוזות משולשות, ועל הערות.
  • לבדוק """ אחרי " — כל משולשת נקראת כמחרוזת ריקה ואחריה עוד אחת.

export function junitSummary(xml: string) {
  const r = { tests: 0, failures: 0, errors: 0, skipped: 0, failed: [] as string[] };
  for (const m of xml.matchAll(/<testcase\b([^>]*?)(?:\/>|>([\s\S]*?)<\/testcase>)/g)) {

💡 רמז 2

✅ פתרון
// P26.3-E94: סימולציה של declarative pipeline
type Stage = { name: string; when?: boolean; fails?: boolean; unstable?: boolean };
type Result = "SUCCESS" | "UNSTABLE" | "FAILURE";

const ORDER = ["always", "failure", "success", "unstable", "unsuccessful", "cleanup"];

export function pipelineResult(stages: Stage[], post: string[]) {
  for (const p of post) if (!ORDER.includes(p)) throw new Error(`תנאי post לא מוכר: ${p}`);
  const ran: string[] = [];
  const skipped: string[] = [];
  let result: Result = "SUCCESS";
  for (const s of stages) {
    if (result === "FAILURE" || s.when === false) {
      skipped.push(s.name);
      continue;
    }
    ran.push(s.name);
    if (s.fails) result = "FAILURE";
    else if (s.unstable) result = "UNSTABLE";
  }
  const runs: Record<string, boolean> = {
    always: true,
    failure: result === "FAILURE",
    success: result === "SUCCESS",
    unstable: result === "UNSTABLE",
    unsuccessful: result !== "SUCCESS",
    cleanup: true,
  };
  return { ran, skipped, result, post: ORDER.filter((p) => post.includes(p) && runs[p]) };
}

UNSTABLE הוא הצהוב של Jenkins: ה־build עבר, אבל משהו לא בסדר — בדרך כלל בדיקות שנכשלו כש־junit מסמן אותן, או כיסוי קוד מתחת לסף. ה־pipeline ממשיך, אבל success לא רץ — ולכן deploy שמחובר ל־success לא קורה.

⚠️ טעויות נפוצות
  • לסמן UNSTABLE אחרי FAILURE — UNSTABLE לא "משפר" כישלון.

💡 רמז 2

✅ פתרון
// P26.3-E100: הגרסה הבאה מתוך ה־commits
export function nextVersion(current: string, commits: string[]): string | null {
  const v = /^(\d+)\.(\d+)\.(\d+)$/.exec(current);
  if (!v) throw new Error(`גרסה לא תקינה: ${current}`);
  let [major, minor, patch] = v.slice(1).map(Number);
  let level = 0;
  for (const c of commits) {
    const [first, ...rest] = c.split("\n");
    const m = /^(\w+)(?:\([^)]*\))?(!)?:/.exec(first);
    if (!m) continue;
    if (m[2] || rest.some((l) => l.startsWith("BREAKING CHANGE:"))) level = Math.max(level, 3);
    else if (m[1] === "feat") level = Math.max(level, 2);
    else if (m[1] === "fix" || m[1] === "perf") level = Math.max(level, 1);
  }
  if (level === 0) return null;
  if (level === 3) [major, minor, patch] = [major + 1, 0, 0];
  else if (level === 2) [minor, patch] = [minor + 1, 0];
  else patch++;
  return `${major}.${minor}.${patch}`;
}

כך עובדים כלים כמו semantic-release: ההודעה שכתבת ב־commit (פרק 9) היא מה שמחליט אם זו גרסת תיקון או גרסה ששוברת לקוחות. בגלל זה כדאי להקפיד על הפורמט כבר מהיום.

⚠️ טעויות נפוצות
  • להעלות patch על כל commit — docs: typo מוציא גרסה חדשה.
  • startsWith("feat") — ‏feature: … או feat-flag cleanup נספרים כ־feat.

type Target = "api" | "web" | "chart" | "ci";

export function changedTargets(files: string[]): Target[] {
  const out = new Set<Target>();
  for (const f of files) {
