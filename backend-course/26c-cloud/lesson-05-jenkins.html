שיעור 5 — Jenkins, והדרך המלאה מ־commit ל־cluster

⏱ ~45 דקות

🎯 בשיעור הזה
  • Jenkins: controller, agents, ו־Jenkinsfile שנמצא ב־repo.
  • declarative pipeline: stages, when, environment, post — מול GitHub Actions שכבר כתבת.
  • סודות ב־Jenkins: Credentials, ולמה מרכאות בודדות.
  • הדרך המלאה: commit ← Jenkins ← registry ← repo התצורה ← Argo CD ← pods.

1. Jenkins

Jenkins הוא שרת CI בקוד פתוח, ותיק (מ־2011) ונפוץ מאוד — במיוחד בחברות שמריצות את הכלים על שרתים משלהן. ה־controller מנהל את ה־jobs והממשק; ה־agents מריצים את העבודה עצמה (מכונות, או קונטיינרים ב־Kubernetes שנוצרים לכל build). ההגדרה של ה־pipeline היא קובץ Jenkinsfile בשורש ה־repo — "pipeline as code", כמו .github/workflows/ci.yml בפרק 25. בדרך כלל מגדירים ב־Jenkins "Multibranch Pipeline": כל ענף וכל pull request מקבלים build משלהם.

2. declarative pipeline

pipeline {
  agent { docker { image 'node:24-alpine' } }          // איפה רץ: קונטיינר נקי לכל build
  options { timeout(time: 20, unit: 'MINUTES') }       // build תקוע לא תופס agent לנצח
  environment { IMAGE = 'ghcr.io/noa-cohen/coffee-shop' }

  stages {
    stage('Install') { steps { sh 'npm ci' } }
    stage('Test')    { steps { sh 'npm test' } }
    stage('Push image') {
      when { branch 'main' }                           // רק מ־main
      steps {
        withCredentials([usernamePassword(credentialsId: 'ghcr', usernameVariable: 'REG_USER', passwordVariable: 'REG_TOKEN')]) {
          sh 'echo $REG_TOKEN | docker login ghcr.io -u $REG_USER --password-stdin'
          sh 'docker build -t $IMAGE:$GIT_COMMIT . && docker push $IMAGE:$GIT_COMMIT'
        }
      }
    }
  }
  post {
    always  { junit allowEmptyResults: true, testResults: 'reports/junit.xml' }
    failure { echo "Build failed: ${env.BUILD_URL}" }
  }
}

3. סודות: מרכאות בודדות

ב־Groovy, מחרוזת במרכאות כפולות מציבה משתנים ("${REG_TOKEN}") לפני שהפקודה מגיעה ל־shell. כלומר הסוד נכנס לטקסט של הפקודה — Jenkins מזהיר "insecure interpolation of sensitive variables", והסוד גלוי ב־ps של ה־agent ואולי בלוגים. במרכאות בודדות ('echo $REG_TOKEN | …') Groovy לא נוגע, וה־shell קורא את משתנה הסביבה. וה־--password-stdin — כדי שהסיסמה לא תהיה ארגומנט בשורת הפקודה בכלל (E16, E23).

הסוד עצמו נשמר ב־Jenkins Credentials (מוצפן, עם id), ו־Jenkins מסתיר אותו בלוג (****) כשהוא מודפס. סוד בתוך ה־Jenkinsfile — ב־environment { TOKEN = 'ghp_…' } — הוא סוד ב־Git, לתמיד.

4. הדרך המלאה

  1. pull request ← review ← merge ל־main ב־repo הקוד.
  2. Jenkins: npm ci, lint, בדיקות; docker build; push ל־registry עם tag של ה־commit (a1b2c3d — לא latest: כל גרסה ניתנת לזיהוי).
  3. Jenkins: clone של repo התצורה, עדכון ה־tag ב־values-staging.yaml, commit ו־push.
  4. Argo CD: OutOfSync ← sync ← ה־Deployment מתעדכן ← rolling update, שמתקדם רק כשה־pods החדשים Ready.
  5. production: אותו commit ל־values-prod.yaml — לרוב ב־pull request שמישהו מאשר. זה "Continuous Delivery" מפרק 25: מוכן תמיד, ולחיצה אחת.
  6. משהו לא בסדר? git revert ב־repo התצורה, ו־Argo CD מחזיר. ה־image הקודם עדיין ב־registry.

Argo CD אגב לא חייב Jenkins: אותו צעד 3 עובד מ־GitHub Actions, GitLab CI או כל CI אחר. וההפך — Jenkins יכול לעשות helm upgrade ישירות (push-based), וזה מה שתראה בהרבה מקומות. מי שמבין את שני המודלים יודע לעבוד בשניהם.

💼 בעולם העבודה

"ניסיון עם AWS, K8s, Jenkins, Argo CD" במודעה לג׳וניור לא אומר "הקמת cluster לבד". זה אומר: אתה כותב את ה־Deployment וה־values של השירות שלך, קורא Jenkinsfile ומתקן stage שנשבר, מבין למה ה־Application ב־Argo CD הוא Degraded, ומבקש הרשאת IAM מדויקת במקום *. בראיון: ספר על E24 — "כתבתי manifests לשירות Nest עם migrations ב־Job, probes, HPA ו־Ingress, ובדקתי אותם" — ועל ההבדל בין readiness ל־liveness. זו שאלה שחוזרת כמעט בכל ראיון.
