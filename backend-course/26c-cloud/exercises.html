P26.3-E04 · מה Kubernetes יעשה?

רמה 1⏱ 15 דק׳ידע נדרש: שיעור 3

Deployment של coffee-api עם 3 replicas, readiness על /ready ו־liveness על /health. מה קורה בכל מקרה?

  1. מוחקים pod אחד ידנית (kubectl delete pod …).
  2. המסד נופל. /ready מחזיר 503, /health מחזיר 200.
  3. באג: האפליקציה תקועה בלולאה, ו־/health לא עונה.
  4. pod מנסה להשתמש ב־700Mi כשה־limit הוא 512Mi.
  5. עדכון ל־image חדש שקורס מיד בעלייה.
  6. ה־node שעליו רצים שניים מה־pods נכבה.

P26.3-E12 · סודות כקבצים: *_FILE 🤖

רמה 2⏱ 20 דק׳ידע נדרש: שיעור 3

Kubernetes יכול לתת Secret כ־env, או כקובץ (volume) — עדיף, כי env דולף ל־/proc, לדוחות קריסה ולילדים של התהליך. המוסכמה (של Docker ושל הרבה images רשמיים): אם X_FILE מוגדר — קוראים את X מהקובץ. ב־P26.3-E12.ts: loadConfig(env, readFile) ל־DATABASE_URL, JWT_SECRET, REDIS_URL (חובה) ו־PORT (ברירת מחדל 3000):

  • X_FILE ← תוכן הקובץ, בלי ה־newline שבסוף. קובץ שלא נקרא או ריק ← שגיאה עם X_FILE.
  • X ו־X_FILE שניהם ← שגיאה. מחרוזת ריקה = חסר.
  • חסרות כמה ← שגיאה אחת שמונה את כולן.

P26.3-E13 · מעריך policies 🤖

רמה 3⏱ 25 דק׳ידע נדרש: שיעור 2

ב־P26.3-E13.ts, הלוגיקה ש־AWS מריץ על כל קריאה (בגרסה מצומצמת):

  • wildcardMatch(pattern, value, ignoreCase?) — * = כל רצף (גם ריק), ? = תו אחד. כל תו אחר — כפשוטו.
  • evaluate(policies, action, resource) — "explicit-deny" אם statement כלשהו עם Deny מתאים; אחרת "allow" אם יש Allow מתאים; אחרת "implicit-deny". Action ו־Resource — מחרוזת או מערך; שם הפעולה לא רגיש לרישיות, ה־ARN כן.

P26.3-E17 · rolling update בצעדים 🤖

רמה 3⏱ 25 דק׳ידע נדרש: שיעור 3

ב־P26.3-E17.ts:

  • rolloutBounds(replicas, maxSurge, maxUnavailable) ← { maxPods, minAvailable }. כל אחד — מספר או אחוז ("25%"); אחוז של surge מעוגל למעלה, של unavailable למטה (כמו Kubernetes). שניהם 0 (אחרי עיגול) ← שגיאה.
  • simulateRollout(…) ← { maxPods, minAvailable, steps }, כש־steps הוא רשימת { old, new } מ־{replicas, 0} עד {0, replicas}. בכל צעד: קודם מורידים כמה שיותר ישנים בלי לרדת מתחת ל־minAvailable (סופרים ישנים + חדשים שכבר היו בתחילת הצעד), ואז מוסיפים כמה שיותר חדשים בלי לעבור את maxPods. החדשים מוכנים בסוף הצעד.

P26.3-E25 · אתגר: עדכון tag ב־repo התצורה 🤖

רמה 5⏱ 45 דק׳ידע נדרש: שיעור 4

הצעד האחרון של ה־CI ב־GitOps: לשנות את ה־tag של ה־image בקובץ YAML ב־repo התצורה, ולעשות commit — ו־Argo CD עושה את השאר. ב־P26.3-E25.ts: bumpImageTag(text, repository, tag) ← { text, changed }:

  • מעדכנת כל image של אותו repository ב־containers וב־initContainers של Deployment, Job, CronJob (וכל מה שיש לו spec.template.spec) — גם אם היה עם tag אחר או digest (@sha256:…).
  • לא נוגעת ב־repository אחר — גם לא כזה שמתחיל באותו שם — ולא ב־ConfigMap.
  • שומרת על ההערות, הסדר והמרכאות: ה־diff הוא רק השורות של ה־image.
  • tag לא תקין (תווים מותרים: אותיות, ספרות, . _ -, עד 128) או repository שלא נמצא ← שגיאה. אותו tag פעמיים ← 0 שינויים, אותו טקסט.

🏁 מבחן מעבר

  • לבחור שירות AWS לכל רכיב של המערכת, ולהסביר role מול access key.
  • לכתוב IAM policy מצומצמת, ולהסביר למה Deny מפורש מנצח.
  • לעבוד עם S3 מ־Node.js: JSON, pagination, וכתובת חתומה להעלאה.
