שיעור 3 — Kubernetes: Pods, Deployments ו־Services

⏱ ~55 דקות

🎯 בשיעור הזה
  • הרעיון של Kubernetes: מצב רצוי, ולולאה שמתקנת.
  • Pod, Deployment, Service, Ingress, ConfigMap, Secret — מה כל אחד עושה, ואיך הם מתחברים.
  • probes ו־resources: מה קורה כשמשהו משתבש.
  • rolling update, autoscaling, ו־kubectl לפקודות היום־יום.

1. מצב רצוי

ב־Docker Compose (פרק 23) אמרת "תריץ את זה". ב־Kubernetes אתה אומר מה צריך להיות — "3 עותקים של coffee-api בגרסה 1.4.2" — ו־controllers בתוך ה־cluster משווים כל הזמן בין הרצוי למצוי ומתקנים: pod מת? נוצר חדש. node נכבה? ה־pods שלו עוברים. עדכנת גרסה? מחליפים בהדרגה. אתה לא כותב סקריפט של צעדים; אתה כותב YAML של מצב, ושולח אותו ל־API server (kubectl apply -f).

ה־cluster הוא כמה מכונות (nodes), ועליהן pods — היחידה הקטנה: קונטיינר (לפעמים כמה) עם IP משלו. pods הם זמניים: נוצרים ומתים, וה־IP שלהם משתנה. אף אחד לא יוצר pod ישירות — יוצרים משהו שמנהל אותם.

2. האובייקטים, ואיך הם מתחברים

אובייקטמה הוא אומרתרגיל
Deployment"N עותקים של ה־pod הזה". שינוי ב־template ← ReplicaSet חדש ו־rolling updateE09
Serviceשם DNS ו־IP יציבים, שמחלקים בקשות בין ה־pods שה־selector תופסE10
Ingressכניסה מבחוץ: host ו־path ← Service, עם תעודת TLSE24
ConfigMap / Secretהגדרות / סודות, שנטענים ל־pod כ־env או כקבציםE10, E12
Job / CronJobמשימה שרצה עד הסוף (migration) / לפי לוח זמנים (דוח לילי)E24
HPA / PDBכמה עותקים לפי עומס / כמה חייבים להישאר בזמן תחזוקהE11

הנה ה־Deployment של coffee-api, מקוצר. כל שדה כאן נבדק ב־E09:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: coffee-api
spec:
  replicas: 3
  selector:
    matchLabels: { app: coffee-api }    # אילו pods "שלי" — חייב להתאים ל־labels למטה
  template:                             # התבנית של כל pod
    metadata:
      labels: { app: coffee-api }
    spec:
      containers:
        - name: api
          image: ghcr.io/noa-cohen/coffee-shop:1.4.2   # גרסה קבועה, לא latest
          ports: [{ name: http, containerPort: 3000 }]
          envFrom: [{ configMapRef: { name: coffee-config } }]
          resources:
            requests: { cpu: 250m, memory: 256Mi }     # מה ה־scheduler שומר בשבילך
            limits: { memory: 512Mi }                  # מעבר לזה — OOMKilled
          readinessProbe: { httpGet: { path: /ready, port: http } }
          livenessProbe: { httpGet: { path: /health, port: http }, initialDelaySeconds: 10 }

({ … } ו־[ … ] הם YAML תקני — "flow style". ב־manifests אמיתיים רואים בעיקר את הצורה עם השורות וההזחות, כמו בתרגילים.)

3. probes ו־resources: כשמשהו משתבש

ה־/health וה־/ready שבנית בפרק 25 מקבלים כאן תפקיד מדויק:

  • readinessProbe נכשל ← ה־pod יוצא מה־Service (לא מקבל בקשות), ולא נוגעים בו. מתאים ל"המסד לא זמין" ול"עוד לא סיימתי לעלות".
  • livenessProbe נכשל כמה פעמים ← הקונטיינר מופעל מחדש. מתאים רק ל"התהליך תקוע" — לא לתלות חיצונית (E04).

ו־resources: requests הם הזמנה — לפיהם ה־scheduler בוחר node שיש בו מקום (E18), וה־HPA מחשב אחוזים (E11). limits הם תקרה: מעבר ל־memory ← OOMKilled; מעבר ל־CPU ← האטה (throttling). הכמויות: 250m = רבע ליבה; 256Mi = 256×1024² בתים, ו־256M = 256×1000² — הבדל של כמעט 5% (E14).

4. rolling update ו־autoscaling

שינית את ה־image ל־1.5.0 ו־apply. ה־Deployment יוצר ReplicaSet חדש ומעביר pods בהדרגה, בתוך שני גבולות: maxSurge — כמה pods מעל replicas מותר; maxUnavailable — כמה מתחת. pod חדש נספר רק כשהוא Ready — אז גרסה שקורסת עוצרת את ה־rollout, והישנים ממשיכים לשרת:

HPA משנה את replicas לפי מדד: יעד של 70% CPU, ו־3 עותקים ב־140% ← 6. ומי משלם על ה־nodes? Cluster Autoscaler (או Karpenter ב־EKS) מוסיף מכונות כשיש pods ב־Pending, ומוריד כשהן ריקות.

5. kubectl: חמש פקודות ליום־יום

kubectl apply -f k8s/                         # לשלוח את המצב הרצוי (יוצר או מעדכן)
kubectl get pods -n coffee                    # STATUS (Running / Pending / CrashLoopBackOff), READY, RESTARTS
kubectl describe pod <name> -n coffee         # Events בסוף: למה Pending? למה probe נכשל? OOMKilled?
kubectl logs <name> -n coffee --previous      # הלוג של הקונטיינר הקודם — זה שקרס
kubectl rollout undo deployment/coffee-api -n coffee   # חזרה ל־ReplicaSet הקודם

כמעט כל "למה זה לא עובד" נפתר ב־describe וב־logs. ובחברה עם GitOps (שיעור 4) — apply ו־undo כבר לא עושים ידנית: משנים את Git.

💡 לנסות על המחשב

הבודקים של היחידה קוראים את ה־YAML ולא צריכים cluster. אם התקנת את kind (קופסת 🧰): kind create cluster, ואז kubectl apply -f לקובץ של E09 עם image ציבורי כלשהו (למשל nginx:1.27 ופורט 80), ו־kubectl get pods -w. מחק pod ותראה אותו חוזר — זה "מצב רצוי".
