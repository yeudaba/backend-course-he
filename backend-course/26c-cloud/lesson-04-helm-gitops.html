שיעור 4 — Helm ו־GitOps עם Argo CD

⏱ ~45 דקות

🎯 בשיעור הזה
  • למה YAML מועתק בין סביבות הוא בעיה, ואיך Helm פותר אותה: templates + values.
  • GitOps: Git הוא האמת, וכלי בתוך ה־cluster מסנכרן אליו.
  • Argo CD: Application, sync, prune, selfHeal — ו־rollback שהוא revert.
  • repo קוד מול repo תצורה: מי משנה מה.

1. Helm: אותו YAML, ערכים אחרים

יש לך staging ו־production. אותו Deployment, אבל 1 עותק מול 3, דומיין אחר, resources אחרים. להעתיק את הקבצים ולשנות ידנית — עד שמישהו מתקן probe רק באחד. Helm הופך את ה־manifests לtemplates עם משתנים, ומקבל את הערכים מקובצי values. חבילה כזו נקראת chart:

charts/coffee-api/
├── Chart.yaml            # שם, גרסת ה־chart, appVersion
├── values.yaml           # ברירות מחדל
├── values-prod.yaml      # רק מה ששונה ב־production
└── templates/
    ├── deployment.yaml
    ├── service.yaml
    ├── ingress.yaml
    └── hpa.yaml
# templates/deployment.yaml (קטע)
spec:
  replicas: {{ .Values.replicas }}
  template:
    metadata:
      labels:
        app: {{ .Release.Name }}
      annotations:
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
    spec:
      containers:
        - name: api
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
          {{- with .Values.resources }}
          resources:
            {{- toYaml . | nindent 12 }}
          {{- end }}

השפה היא Go templates: {{ .Values.x }} מציב ערך, | default נותן ברירת מחדל, with/if מדלגים על בלוק כשהערך ריק, ו־toYaml | nindent מכניס מבנה שלם בהזחה הנכונה. ה־annotation checksum/config הוא טריק מוכר: שינוי ב־ConfigMap משנה את ה־hash, ולכן את ה־template — וה־Deployment עושה rollout (E10).

פקודות: helm template — רק להדפיס את התוצאה (הכי שימושי לבדיקה); helm upgrade --install coffee charts/coffee-api -f values-prod.yaml — להתקין או לעדכן; helm rollback. ו־Helm הוא גם מנהל חבילות: PostgreSQL, Redis, Argo CD עצמו, ingress-nginx — מותקנים מ־charts מוכנים.

חלופה שתפגוש: Kustomize (מובנה ב־kubectl, kubectl apply -k) — בלי templates, עם "בסיס" ו"שכבות" שמשנות שדות. הרעיון זהה: מקור אחד, הבדלים מפורשים.

2. GitOps

בפרק 25, ה־CI עשה deploy: בסוף ה־workflow — קריאה ל־Render. זה push: ה־CI מחזיק מפתח לפרודקשן ודוחף. ב־GitOps הכיוון הפוך:

היתרונות: היסטוריה — כל שינוי בפרודקשן הוא commit עם מחבר ו־review; rollback — git revert; drift — שינוי ידני ב־cluster מתגלה ומתוקן; ואבטחה — אין מפתח ל־cluster ב־CI.

3. Argo CD

ב־Argo CD מגדירים Application: מאיפה (repo, ענף, נתיב, values) ולאן (cluster, namespace):

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: coffee-api-prod
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/noa-cohen/coffee-deploy.git
    targetRevision: main
    path: charts/coffee-api
    helm: { valueFiles: [values-prod.yaml] }
  destination:
    server: https://kubernetes.default.svc
    namespace: coffee
  syncPolicy:
    automated: { prune: true, selfHeal: true }

שני מצבים מופיעים בממשק של Argo CD לכל Application: Sync — Synced (ה־cluster זהה ל־Git) או OutOfSync; ו־Health — Healthy, Progressing (rollout באמצע) או Degraded (pods לא Ready). prune — משאב שנמחק מ־Git נמחק מה־cluster; selfHeal — שינוי ידני מוחזר (E15). ולסדר: sync waves — annotation שאומר "קודם ה־Job של ה־migrations, אחר כך ה־Deployment" (E24).

4. שני repos

repo הקוד (coffee-shop)repo התצורה (coffee-deploy)
מה בוTypeScript, Dockerfile, בדיקות, Jenkinsfilecharts, values לכל סביבה, Applications
מי כותבמפתחיםה־CI (עדכון tag) ומפתחים/DevOps (שינויי תצורה)
מה commit גורםbuild, בדיקות, image חדשArgo CD מסנכרן

למה שניים? כדי ששינוי replicas לא יבנה image, ו־commit של קוד לא ישנה את הפרודקשן לפני שה־image נבנה ונבדק. הקשר ביניהם הוא שורה אחת: ה־tag. ה־CI, בסוף, משנה אותה ב־repo התצורה ועושה commit — וזה E25: לשנות את השורה בלי להרוס את שאר הקובץ.

💼 בעולם העבודה

ביום הראשון בחברה עם Argo CD תקבל קישור לממשק שלו ותראה עשרות Applications — כל שירות, בכל סביבה. השאלה הראשונה כש"משהו לא עובד בפרודקשן": האם ה־Application שלך Synced ו־Healthy? אם Degraded — לחיצה על ה־pod מראה את ה־Events והלוגים, בדיוק כמו kubectl describe.
