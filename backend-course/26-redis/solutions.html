P26-E01 · Redis או PostgreSQL? רמה 1

💡 רמז 1

שאלה אחת לכל שורה: מה קורה אם Redis מאבד את המידע (restart בלי persistence, או מחיקה)?

💡 רמז 2

Redis שומר בזיכרון. הוא יכול לשמור לדיסק — אבל ברוב ההגדרות לא מתייחסים אליו כמקור אמת לכסף.

✅ פתרון
  1. PostgreSQL. כסף, טרנזקציות, constraints, גיבויים. אסור לאבד.
  2. שניהם: מקור האמת ב־PostgreSQL, עותק ב־Redis (cache). נמחק? טוענים שוב.
  3. Redis. נתון קצר־חיים שמשתנה בכל בקשה, ושכל השרתים צריכים לראות (פרק 24 עשה את זה ב־Map — לשרת אחד). נאבד? הכי גרוע — מישהו קיבל עוד כמה ניסיונות.
  4. תלוי במוצר. בפרויקט — PostgreSQL (המשתמש מצפה לראות אותה גם מחר, ממכשיר אחר). אתרים עם המון אורחים — לפעמים ב־Redis עם TTL, עגלה של אורח.
  5. Redis — sorted set לכל דקה (E24). סטטיסטיקה "חמה", מקורבת, שמתה לבד.
  6. תלוי: בפרויקט — PostgreSQL, כי הוא חלק מאותה טרנזקציה ומאותן החלטות. ב־Redis עם TTL זה עובד ומהיר יותר, אבל אז "ההזמנה נשמרה" ו"המפתח נשמר" כבר לא אטומיים יחד.
  7. Redis (BullMQ). העבודה עצמה — המייל — יכולה להיווצר מחדש מהמסד; לכן גם אובדן התור לא שובר נכונות, רק מעכב.
⚠️ טעויות נפוצות
  • "Redis מהיר, אז הכול שם". מהירות לא שווה הרבה אם נתון שאסור לאבד נעלם ב־restart.

P26-E02 · איזה מבנה נתונים? רמה 1

💡 רמז 1

sorted set = set שכל איבר בו מקבל מספר (score), ונשמר ממוין לפיו.

💡 רמז 2

"הכי חדש ראשון, עד 10" — רשימה שדוחפים לראשה וחותכים את הזנב.

✅ פתרון
  1. string — SET key json EX 60.
  2. string כמספר — INCR (אטומי), או hash עם HINCRBY כשיש הרבה מונים קשורים (E08).
  3. list — LREM + LPUSH + LTRIM 0 9 (E11).
  4. set — SADD מחזיר 1 אם נוסף, 0 אם כבר היה. ההחזרה הזו היא כל הבדיקה.
  5. sorted set — ZINCRBY, ואז ZREVRANGE 0 9 WITHSCORES (E10).
  6. hash — HSET / HGETALL: שדות בשם, אפשר לעדכן אחד בלי לקרוא את כולם.
  7. sorted set עם הזמן כ־score — ZADD, ZREMRANGEBYSCORE, ZCARD (E15).
⚠️ טעויות נפוצות
  • לשמור הכול כ־JSON ב־string ולעדכן ב"קרא, שנה, כתוב" — מאבדים את האטומיות שהמבנים נותנים בחינם.

P26-E03 · מלכודות של cache רמה 1

💡 רמז 1

"שני הדברים הקשים במדעי המחשב: ביטול cache, ונתינת שמות."

💡 רמז 2

מה נמצא במפתח של ה־cache? וכל מה שמשפיע על התשובה — נמצא שם?

✅ פתרון
  1. ביטול (invalidation). TTL הוא רשת ביטחון, לא תוכנית. בכל שינוי — מבטלים: מוחקים את המפתח, או מעלים "גרסה" לקבוצה (E14, ובפרויקט). ו־TTL קצר לנתונים שמשתנים.
  2. stampede. כולם מגלים יחד שאין ערך, וכולם טוענים. פתרונות: רק אחד טוען (מנעול / single-flight — E13), TTL עם "רעש" אקראי כדי שלא כל המפתחות יפוגו יחד, או רענון ברקע לפני שפג.
  3. penetration. שומרים גם את "אין תוצאה" (רשימה ריקה, ל־TTL קצר) — E20. ובנוסף: rate limit.
  4. מפתח בלי המשתמש. כל מה שמשפיע על התשובה — כולל מי שואל — חייב להיות במפתח. או: לא לשמור ב־cache משותף נתונים פרטיים בכלל. זו דליפת מידע, לא באג קטן.
  5. cache הפך לתלות. cache הוא אופטימיזציה: אם Redis לא עונה — הולכים למסד (איטי, אבל עובד). בפרויקט: X-Cache: OFF, והכול ממשיך.
⚠️ טעויות נפוצות
  • "נשים TTL של יום, יהיה מהר" — ואז באג "המחיר לא מתעדכן" שאף אחד לא מצליח לשחזר.

P26-E04 · בתור או עכשיו? רמה 1

💡 רמז 1

שאלה: האם התשובה ללקוח תלויה בתוצאה?

💡 רמז 2

worker שסיים את העבודה ונפל רגע לפני שדיווח "סיימתי" — מה התור יעשה?

✅ פתרון
  1. עכשיו. התשובה ("הוזמן" / "אזל") תלויה בזה, וזה חלק מהטרנזקציה.
  2. תור. הלקוח לא צריך לחכות ל־SMTP, ו־SMTP שלא זמין לרגע לא צריך להכשיל הזמנה. נכשל ← retry עם backoff.
  3. תור. מחזירים מיד "בהכנה", וכשמוכן — מודיעים (או הלקוח בודק).
  4. תלוי. בפרויקט — עכשיו: הלקוח מחכה לתשובה "שולם / נדחה". במערכות גדולות — הספק עונה מאוחר יותר ב־webhook, וזה כבר אסינכרוני.
  5. תור עם delay (BullMQ: delay). לא cron שסורק כל דקה את כל ההזמנות.
  6. תור. עקביות "בסופו של דבר" מספיקה: חיפוש שמתעדכן אחרי שנייה זה בסדר.

לא נכון. תורים מבטיחים "לפחות פעם אחת" (at-least-once). worker שנפל אחרי העבודה ולפני ה־ack ← העבודה תרוץ שוב. לכן כל צרכן חייב להיות idempotent: jobId קבוע להוספה, ובצד הביצוע — "כבר טופל?" (E18, ו־UNIQUE (kind, order_id) בפרויקט).

⚠️ טעויות נפוצות
  • לשלוח מייל מתוך הטרנזקציה — ואז הטרנזקציה נכשלת (ROLLBACK), והמייל "ההזמנה התקבלה" כבר יצא.

P26-E05 · מה יחזיר Redis? רמה 1

💡 רמז 1

כל מה ש־Redis מחזיר כ"ערך" הוא מחרוזת — גם אחרי INCR. מונים מחזירים מספרים.

💡 רמז 2

SADD מחזיר כמה איברים חדשים נוספו. SET … NX מחזיר "OK" או null.

✅ פתרון
import { Redis } from "ioredis";
const r = new Redis(process.env.REDIS_URL ?? "redis://localhost:6379", { keyPrefix: "e05:" });
await r.del("n", "s", "l", "z");
console.log(await r.incr("n"), await r.incrby("n", 10), typeof (await r.get("n")));
console.log(await r.sadd("s", "a", "b", "a"), await r.sadd("s", "a"), await r.scard("s"));
await r.rpush("l", "1", "2", "3");
console.log(await r.lrange("l", 0, -1), await r.lpop("l"), await r.llen("l"));
await r.zadd("z", 30, "yossi", 50, "dana", 10, "noa");
console.log(await r.zrevrange("z", 0, 1), await r.zscore("z", "dana"));
console.log(await r.set("x", "1", "NX"), await r.set("x", "2", "NX"), await r.get("x"));
await r.del("n", "s", "l", "z", "x");
await r.quit();
1 11 string
2 0 2
[ '1', '2', '3' ] 1 2
[ 'dana', 'yossi' ] 50
OK null 1
  • INCR מחזיר מספר, אבל GET — מחרוזת. ב־Redis הכול מחרוזות; "מספר" זה רק מחרוזת ש־INCR יודע לקרוא.
  • SADD s a b a — 2: ה־"a" השני לא נוסף. ושוב a — 0. זה בדיוק "האם כבר הצביע".
  • ZSCORE מחזיר מחרוזת ("50").
  • SET NX: הראשון "OK", השני null, והערך נשאר "1" — הבסיס של מנעולים (E12).
⚠️ טעויות נפוצות
  • if (await r.get("n") > 5) — השוואה של מחרוזת למספר עובדת "במקרה" ב־JavaScript. Number(...) במפורש.

P26-E06 · מטמון JSON 🤖 רמה 2

💡 רמז 1

redis.set(key, json, "EX", ttl). redis.ttl מחזיר −2 כשאין מפתח, −1 כשאין תוקף.

💡 רמז 2

0 ו־false הם ערכים — בדוק raw === null, לא !raw.

✅ פתרון
// P26-E06
import type { Redis } from "ioredis";

// מטמון JSON פשוט מעל Redis: מחרוזות בלבד שם — לכן JSON.stringify / parse
export function createJsonStore(redis: Redis) {
  return {
    async set(key: string, value: unknown, ttlSeconds?: number) {
      if (value === undefined) throw new Error("אין ערך לשמור");
      const json = JSON.stringify(value);
      if (ttlSeconds) await redis.set(key, json, "EX", ttlSeconds);
      else await redis.set(key, json);
    },
    async get<T>(key: string): Promise<T | null> {
      const raw = await redis.get(key);
      return raw === null ? null : (JSON.parse(raw) as T);
    },
    async del(key: string) {
      return (await redis.del(key)) === 1;
    },
    // כמה שניות נשארו: null — אין מפתח; Infinity — בלי תוקף
    async ttl(key: string) {
      const t = await redis.ttl(key);
      return t === -2 ? null : t === -1 ? Infinity : t;
    },
  };
}
⚠️ טעויות נפוצות
  • redis.set(key, value) עם אובייקט — ioredis שומר "[object Object]".

P26-E07 · cache-aside 🤖 רמה 2

💡 רמז 1

"cache-aside" = הקוד שלך מנהל את ה־cache: בודק, טוען, שומר. Redis לא יודע כלום על המסד.

💡 רמז 2

למה לא לשמור null? "המוצר לא קיים" יישאר ל־TTL שלם גם אחרי שייווצר. (רשימה ריקה [] — כן שומרים: זו תשובה אמיתית, ראה E20.)

✅ פתרון
// P26-E07
import type { Redis } from "ioredis";

// cache-aside: קודם Redis; אין ← טוענים מהמקור ושומרים עם TTL
export function createCacheAside(redis: Redis) {
  const stats = { hits: 0, misses: 0 };
  async function get<T>(key: string, ttlSeconds: number, load: () => Promise<T>): Promise<T> {
    const raw = await redis.get(key);
    if (raw !== null) {
      stats.hits++;
      return JSON.parse(raw) as T;
    }
    stats.misses++;
    const value = await load(); // אם load זורק — לא שומרים כלום (לא מחזיקים שגיאות ב־cache)
    if (value !== undefined && value !== null) await redis.set(key, JSON.stringify(value), "EX", ttlSeconds);
    return value;
  }
  return { get, stats, invalidate: (key: string) => redis.del(key) };
}
⚠️ טעויות נפוצות
  • לשמור ב־cache את השגיאה ("db down") — וכל הלקוחות יקבלו אותה עד שה־TTL נגמר.

P26-E08 · מונים ודירוג 🤖 רמה 2

💡 רמז 1

HINCRBY, ZINCRBY, EXPIRE — ב־redis.multi()…exec().

💡 רמז 2

exec() מחזיר מערך של [error, result] לכל פקודה.

✅ פתרון
// P26-E08
import type { Redis } from "ioredis";

// צפיות במוצרים: מונה לכל יום (ומחיקה אוטומטית אחרי שבוע), ו־sorted set לדירוג
export async function trackView(redis: Redis, productId: number, now: Date) {
  const day = now.toISOString().slice(0, 10);
  const views = `views:${day}`;
  // MULTI: הכול יחד, בלי שבקשה אחרת תיכנס באמצע
  const results = await redis
    .multi()
    .hincrby(views, String(productId), 1)
    .expire(views, 7 * 86400)
    .zincrby(`top:${day}`, 1, String(productId))
    .expire(`top:${day}`, 7 * 86400)
    .exec();
  return Number(results![0][1]); // התוצאה של הפקודה הראשונה (HINCRBY)
}

export async function topProducts(redis: Redis, day: string, n: number): Promise<{ productId: number; views: number }[]> {
  const flat = await redis.zrevrange(`top:${day}`, 0, n - 1, "WITHSCORES");
  const out = [];
  for (let i = 0; i < flat.length; i += 2) out.push({ productId: Number(flat[i]), views: Number(flat[i + 1]) });
  return out;
}

הבודק שולח 50 צפיות במקביל ובודק שהמונה 50 — HINCRBY אטומי. "קרא, הוסף 1, כתוב" היה מאבד צפיות.

⚠️ טעויות נפוצות
  • מונה בלי תוקף — אחרי שנה יש 365 hashes שאף אחד לא קורא.

P26-E09 · הגבלת קצב משותפת 🤖 רמה 2

💡 רמז 1

מספר החלון: Math.floor(now / 1000 / windowSeconds).

💡 רמז 2

EXPIRE key seconds NX — רק אם אין תוקף (Redis 7+).

✅ פתרון
// P26-E09
import type { Redis } from "ioredis";

// fixed window ב־Redis: מונה לכל (לקוח, חלון). משותף לכל השרתים — בניגוד ל־Map בזיכרון (פרק 24)
export async function hit(redis: Redis, clientId: string, { limit, windowSeconds, now = Date.now() }: { limit: number; windowSeconds: number; now?: number }) {
  const window = Math.floor(now / 1000 / windowSeconds);
  const key = `rl:${clientId}:${window}`;
  // INCR אטומי; EXPIRE רק כשהמפתח נוצר עכשיו (NX) — המונה מת לבד בסוף החלון
  const [[, count]] = (await redis.multi().incr(key).expire(key, windowSeconds, "NX").exec()) as [[null, number], [null, number]];
  const resetSeconds = (window + 1) * windowSeconds - Math.floor(now / 1000);
  return { allowed: count <= limit, remaining: Math.max(0, limit - count), resetSeconds };
}

זו בדיוק ההגבלה מפרק 24 — אבל משותפת: עם שלושה שרתים, ה־Map בזיכרון סופר לכל שרת לבד, והמגבלה האמיתית פי 3.

⚠️ טעויות נפוצות
  • EXPIRE בלי NX — כל בקשה מאריכה את החלון, ומי שממשיך לשלוח לא משתחרר (E21).

P26-E10 · טבלת מובילים 🤖 רמה 2

💡 רמז 1

ZINCRBY, ZREVRANGE … WITHSCORES, ZREVRANK (מ־0).

💡 רמז 2

around: start = max(0, rank − radius).

✅ פתרון
// P26-E10
import type { Redis } from "ioredis";

// טבלת מובילים: sorted set — Redis שומר ממוין לפי score, וכל פעולה ב־O(log n)
export function leaderboard(redis: Redis, name: string) {
  const key = `lb:${name}`;
  return {
    add: (player: string, points: number) => redis.zincrby(key, points, player).then(Number),
    async top(n: number) {
      const flat = await redis.zrevrange(key, 0, n - 1, "WITHSCORES");
      return Array.from({ length: flat.length / 2 }, (_, i) => ({ player: flat[2 * i], score: Number(flat[2 * i + 1]), rank: i + 1 }));
    },
    // מקום (מ־1), או null
    async rank(player: string) {
      const r = await redis.zrevrank(key, player);
      return r === null ? null : r + 1;
    },
    async around(player: string, radius: number) {
      const r = await redis.zrevrank(key, player);
      if (r === null) return [];
      const start = Math.max(0, r - radius);
      const flat = await redis.zrevrange(key, start, r + radius, "WITHSCORES");
      return Array.from({ length: flat.length / 2 }, (_, i) => ({ player: flat[2 * i], score: Number(flat[2 * i + 1]), rank: start + i + 1 }));
    },
  };
}
⚠️ טעויות נפוצות
  • טבלת מובילים ב־SQL עם ORDER BY על כל צפייה — עובד ל־1,000 שחקנים, לא למיליון בזמן אמת.

P26-E11 · צפית לאחרונה 🤖 רמה 2

💡 רמז 1

LREM key 0 value — מוחק את כל המופעים.

💡 רמז 2

LTRIM key 0 max−1 — רשימה חסומה.

✅ פתרון
// P26-E11
import type { Redis } from "ioredis";

// "צפית לאחרונה": רשימה לכל משתמש, הכי חדש ראשון, בלי כפילויות, עד max, ונמחקת אחרי 30 יום בלי פעילות
export async function viewed(redis: Redis, userId: number, productId: number, max = 10) {
  const key = `recent:${userId}`;
  await redis
    .multi()
    .lrem(key, 0, String(productId)) // אם כבר שם — מוציאים, כדי שיעלה לראש
    .lpush(key, String(productId))
    .ltrim(key, 0, max - 1) // רשימה חסומה: לא גדלה לנצח
    .expire(key, 30 * 86400)
    .exec();
}

export async function recent(redis: Redis, userId: number): Promise<number[]> {
  return (await redis.lrange(`recent:${userId}`, 0, -1)).map(Number);
}
⚠️ טעויות נפוצות
  • בלי LTRIM — רשימה שגדלה לנצח.

P26-E12 · מנעול מבוזר 🤖 רמה 2

💡 רמז 1

SET lock:name token PX ttl NX — "רק אם לא קיים", עם תוקף, בפקודה אחת.

💡 רמז 2

שחרור: "אם הערך הוא ה־token שלי — מחק" חייב להיות אטומי. Lua: redis.eval(script, 1, key, token).

✅ פתרון
// P26-E12
import { randomUUID } from "node:crypto";
import type { Redis } from "ioredis";

// מחיקה רק אם הערך הוא ה־token שלי — בפקודה אחת (Lua רץ ב־Redis באופן אטומי)
const RELEASE = `if redis.call("GET", KEYS[1]) == ARGV[1] then return redis.call("DEL", KEYS[1]) else return 0 end`;

export async function acquire(redis: Redis, name: string, ttlMs: number): Promise<string | null> {
  const token = randomUUID();
  // SET NX PX: "רק אם לא קיים" ועם תוקף — באותה פקודה. אם התהליך מת, המנעול משתחרר לבד
  const ok = await redis.set(`lock:${name}`, token, "PX", ttlMs, "NX");
  return ok === "OK" ? token : null;
}

export async function release(redis: Redis, name: string, token: string): Promise<boolean> {
  return (await redis.eval(RELEASE, 1, `lock:${name}`, token)) === 1;
}

export async function withLock<T>(redis: Redis, name: string, ttlMs: number, fn: () => Promise<T>): Promise<T | null> {
  const token = await acquire(redis, name, ttlMs);
  if (!token) return null; // מישהו אחר מחזיק — לא מחכים (לפי הצורך: לנסות שוב אחר כך)
  try {
    return await fn();
  } finally {
    await release(redis, name, token);
  }
}

מתי צריך? "רק שרת אחד מריץ את הדוח הלילי", "רק אחד מרענן את ה־cache" (E13). ומתי לא: נכונות של כסף ומלאי — שם המסד מתאם (פרק 18, פרויקט 3). מנעול עם תוקף יכול לפוג באמצע עבודה איטית.

⚠️ טעויות נפוצות

P26-E13 · cache שעומד בעומס 🤖 רמה 3

💡 רמז 1

💡 רמז 2

✅ פתרון
// P26-E13
import { randomUUID } from "node:crypto";
import type { Redis } from "ioredis";

const RELEASE = `if redis.call("GET", KEYS[1]) == ARGV[1] then return redis.call("DEL", KEYS[1]) else return 0 end`;
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

// מניעת stampede: מפתח פופולרי פג תוקף, ו־500 בקשות טוענות אותו מהמסד בבת אחת.
// בתוך תהליך — "single flight" (Promise משותף). בין שרתים — מנעול: רק אחד טוען, האחרים מחכים לערך
export function createStampedeCache(redis: Redis, { lockMs = 5000, waitMs = 3000, pollMs = 25 } = {}) {
  const inFlight = new Map<string, Promise<unknown>>();

  async function load<T>(key: string, ttlSeconds: number, loader: () => Promise<T>): Promise<T> {
    const cached = await redis.get(key);
    if (cached !== null) return JSON.parse(cached) as T;
    const token = randomUUID();
    if ((await redis.set(`${key}:lock`, token, "PX", lockMs, "NX")) === "OK") {
      try {
        const value = await loader();
        await redis.set(key, JSON.stringify(value), "EX", ttlSeconds);
        return value;
      } finally {
        await redis.eval(RELEASE, 1, `${key}:lock`, token);
      }
    }
    // מישהו אחר טוען — מחכים שהערך יופיע. לא הופיע בזמן? טוענים בעצמנו (עדיף איטי מתקוע)
    for (const end = Date.now() + waitMs; Date.now() < end; ) {
      await sleep(pollMs);
      const v = await redis.get(key);
      if (v !== null) return JSON.parse(v) as T;
    }
    return loader();
  }

  return {
    get<T>(key: string, ttlSeconds: number, loader: () => Promise<T>): Promise<T> {
      const existing = inFlight.get(key);
      if (existing) return existing as Promise<T>;
      const p = load(key, ttlSeconds, loader).finally(() => inFlight.delete(key));
      inFlight.set(key, p);
      return p;
    },
  };
}
⚠️ טעויות נפוצות
  • לחכות למנעול בלי גבול — הטוען נתקע, וכל השרתים נתקעים איתו.

P26-E14 · ביטול עם גרסה 🤖 רמה 3

💡 רמז 1

💡 רמז 2

✅ פתרון
// P26-E14
import type { Redis } from "ioredis";

// cache עם "גרסה" לכל קבוצה: invalidate = INCR אחד, במקום לחפש ולמחוק את כל הווריאציות
export function createVersionedCache(redis: Redis) {
  const version = async (group: string) => (await redis.get(`v:${group}`)) ?? "0";
  return {
    async get<T>(group: string, key: string, ttlSeconds: number, load: () => Promise<T>): Promise<{ value: T; hit: boolean }> {
      const full = `c:${group}:${await version(group)}:${key}`;
      const raw = await redis.get(full);
      if (raw !== null) return { value: JSON.parse(raw) as T, hit: true };
      const value = await load();
      await redis.set(full, JSON.stringify(value), "EX", ttlSeconds);
      return { value, hit: false };
    },
    // המפתחות הישנים לא נמחקים — הם פשוט לא נקראים יותר, ומתים ב־TTL
    invalidate: (group: string) => redis.incr(`v:${group}`),
  };
}

⚠️ טעויות נפוצות

P26-E15 · חלון נע ב־sorted set 🤖 רמה 3

💡 רמז 1

💡 רמז 2

✅ פתרון
// P26-E15
import { randomUUID } from "node:crypto";
import type { Redis } from "ioredis";

// sliding window ב־sorted set: כל בקשה = איבר עם score = זמן. סופרים רק את ה־windowMs האחרונות
export async function slidingHit(redis: Redis, clientId: string, { limit, windowMs, now = Date.now() }: { limit: number; windowMs: number; now?: number }) {
  const key = `sw:${clientId}`;
  const results = await redis
    .multi()
    .zremrangebyscore(key, "-inf", now - windowMs) // מנקים את מה שיצא מהחלון
    .zcard(key)
    .zrange(key, 0, 0, "WITHSCORES")
    .exec();
  const count = Number(results![1][1]);
  const oldest = results![2][1] as string[];
  if (count >= limit) {
    // נדחה — לא נספר (פרק 24). Retry-After: עד שהוותיק יוצא מהחלון
    const retryAfterMs = Number(oldest[1]) + windowMs - now;
    return { allowed: false, remaining: 0, retryAfterSeconds: Math.max(1, Math.ceil(retryAfterMs / 1000)) };
  }
  await redis.multi().zadd(key, now, `${now}-${randomUUID()}`).pexpire(key, windowMs).exec();
  return { allowed: true, remaining: limit - count - 1, retryAfterSeconds: 0 };
}

מגבלה של הגרסה הזו: הבדיקה וההוספה הן שתי פקודות נפרדות — תחת עומס חזק, שתי בקשות יכולות לעבור את הבדיקה יחד. לאטומיות מלאה — סקריפט Lua (E25).

⚠️ טעויות נפוצות
  • member = now — בקשות באותה מילישנייה נספרות כאחת.

✅ פתרון
// P26-E17
import { Queue, Worker, type ConnectionOptions } from "bullmq";

// תזכורת מתוזמנת: עבודה עם delay. jobId לפי ההזמנה — כדי שאפשר יהיה לבטל אותה כשהלקוח שילם
export function createReminders(connection: ConnectionOptions, prefix: string) {
  const queue = new Queue<{ orderId: number }>("reminders", { connection, prefix });
  return {
    queue,
    schedule: (orderId: number, delayMs: number) => queue.add("remind", { orderId }, { jobId: `remind-${orderId}`, delay: delayMs }),
    // שולם לפני הזמן — מבטלים. מחזיר true אם הייתה עבודה ממתינה שבוטלה
    async cancel(orderId: number) {
      const job = await queue.getJob(`remind-${orderId}`);
      if (!job || !(await job.isDelayed())) return false;
      await job.remove();
      return true;
    },
    close: () => queue.close(),
  };
}

  return new Worker<{ orderId: number }>("reminders", (job) => remind(job.data.orderId), { connection, prefix });
}

P26-E18 · צרכן idempotent 🤖 רמה 3

💡 רמז 1

💡 רמז 2

למה TTL? כדי שהסימונים לא יצטברו לנצח. (כמה זמן? יותר מהזמן שבו הודעה יכולה להגיע שוב.)

✅ פתרון
// P26-E18
import type { Redis } from "ioredis";

// "צרכן idempotent": תורים מבטיחים "לפחות פעם אחת" — לא "בדיוק פעם אחת". retry, worker שנפל אחרי העבודה ולפני ack…
// לכן כל הודעה מסומנת כ"טופלה". SET NX: רק הראשון מצליח לסמן. נכשל באמצע? מוחקים את הסימון — שינסו שוב
export async function processOnce<T>(redis: Redis, messageId: string, ttlSeconds: number, handler: () => Promise<T>): Promise<{ processed: boolean; result?: T }> {
  const key = `processed:${messageId}`;
  if ((await redis.set(key, "1", "EX", ttlSeconds, "NX")) !== "OK") return { processed: false };
  try {
    return { processed: true, result: await handler() };
  } catch (err) {
    await redis.del(key);
    throw err;
  }
}

יש עדינות: אם ה־handler הצליח, אבל התהליך מת לפני שהחזיר — הסימון קיים, וההודעה לא תטופל שוב. מצוין לחיוב; פחות למשהו שבאמת לא קרה. הפתרון החזק יותר — כמו בפרויקט: הייחודיות בתוך אותה פעולה (UNIQUE בטבלת המיילים), כך ש"טופל" ו"קרה" הם אותו דבר.

⚠️ טעויות נפוצות
  • לסמן "טופל" רק אחרי ה־handler — שתי העתקות שמגיעות יחד יריצו שתיהן.

💡 רמז 2

✅ פתרון
// P26-E19
import type { Redis } from "ioredis";

// cache בזיכרון של התהליך (L1, הכי מהיר) — אבל עם כמה שרתים, כל אחד מחזיק עותק משלו.
// כששרת אחד משנה, הוא מפרסם ב־pub/sub, וכל השרתים מוחקים את העותק שלהם
export async function createL1Cache(redis: Redis, subscriber: Redis, channel = "cache-invalidate") {
  const local = new Map<string, unknown>();
  await subscriber.subscribe(channel);
  subscriber.on("message", (ch: string, key: string) => {
    if (ch === channel) local.delete(key);
  });
  return {
    async get<T>(key: string, load: () => Promise<T>): Promise<T> {
      if (local.has(key)) return local.get(key) as T;
      const value = await load();
      local.set(key, value);
      return value;
    },
    // מקומית מיד, ולכל השאר דרך Redis
    async invalidate(key: string) {
      local.delete(key);
      await redis.publish(channel, key);
    },
    size: () => local.size,
  };
}
⚠️ טעויות נפוצות

export async function acquire(redis: Redis, name: string, ttlMs: number): Promise<string | null> {
  // תקלה 1: בלי תוקף — שרת שקרס מחזיק את המנעול לנצח. SET … PX … NX: הכול בפקודה אחת

    // תקלה 2: jobId אקראי — כל קריאה היא עבודה חדשה (תשלום שנשלח פעמיים ← שני מיילים). מזהה עסקי
    // תקלה 3: בלי attempts — ניסיון אחד בלבד
    send: (orderId: number) => queue.add("confirm", { orderId }, { jobId: `confirm-${orderId}`, attempts: 5, backoff: { type: "exponential", delay: 50 } }),
    close: async () => {
      await worker.close();
      await queue.close();
    },
  };
}
⚠️ טעויות נפוצות
  • try/catch שבולע — "שקט" בלוגים, ומיילים שנעלמים בלי זכר. עדיף שעבודה תיכשל בקול ותגיע ל־failed.

P26-E24 · אתגר: חם עכשיו 🤖 רמה 5

💡 רמז 1

ZUNIONSTORE tmp N key1 key2 … — מחבר sorted sets (סכום scores). מפתח שלא קיים — כמו ריק.

💡 רמז 2

הכול ב־multi(): zunionstore, zrevrange, del.

✅ פתרון
// P26-E24
import type { Redis } from "ioredis";

const minuteOf = (now: number) => Math.floor(now / 60_000);

// "חם עכשיו": sorted set לכל דקה. צפייה ← ZINCRBY בדלי של הדקה הנוכחית (שמת לבד אחרי שעתיים)
export async function recordView(redis: Redis, productId: number, now = Date.now()) {
  const key = `trend:${minuteOf(now)}`;
  await redis.multi().zincrby(key, 1, String(productId)).expire(key, 7200).exec();
}

// N הדקות האחרונות: ZUNIONSTORE מחבר את הדליים (סכום ה־scores) למפתח זמני, ומשם — ה־top
export async function trending(redis: Redis, { windowMinutes, n, now = Date.now() }: { windowMinutes: number; n: number; now?: number }) {
  const m = minuteOf(now);
  const buckets = Array.from({ length: windowMinutes }, (_, i) => `trend:${m - i}`);
  const tmp = `trend:tmp:${m}:${windowMinutes}:${Math.random().toString(36).slice(2)}`;
  const results = await redis
    .multi()
    .zunionstore(tmp, buckets.length, ...buckets)
    .zrevrange(tmp, 0, n - 1, "WITHSCORES")
    .del(tmp)
    .exec();
  const flat = results![1][1] as string[];
  return Array.from({ length: flat.length / 2 }, (_, i) => ({ productId: Number(flat[2 * i]), views: Number(flat[2 * i + 1]) }));
}

זה דפוס כללי: "bucketing" — דלי לכל יחידת זמן, וחלון = איחוד של כמה דליים. אותו רעיון מאחורי מדדים ב־Prometheus ובכלי ניטור.

⚠️ טעויות נפוצות
  • מפתח זמני בשם קבוע (trend:tmp) — שתי בקשות במקביל דורסות זו את זו.

P26-E25 · אתגר: token bucket אטומי (Lua) 🤖 רמה 5

💡 רמז 1

redis.eval(script, 1, key, ...args). ב־Lua: KEYS[1], ARGV[1]…, tonumber, redis.call("HMGET", …).

💡 רמז 2

מ־Lua מחזירים מספרים שלמים בלבד (שברים נחתכים) — לכן math.floor ל־remaining, ו־tostring כששומרים שבר ב־hash.

✅ פתרון
// P26-E25
import type { Redis } from "ioredis";

// token bucket אטומי: הקריאה, החישוב והכתיבה — בסקריפט Lua אחד. Redis מריץ סקריפט בבת אחת,
// בלי שפקודה אחרת תיכנס באמצע: אין מרוץ בין שרתים, ואין round-trip נוסף
const TAKE = `
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])      -- אסימונים לשנייה
local now = tonumber(ARGV[3])       -- מילישניות
local cost = tonumber(ARGV[4])
local state = redis.call("HMGET", KEYS[1], "tokens", "ts")
local tokens = tonumber(state[1]) or capacity
local ts = tonumber(state[2]) or now
tokens = math.min(capacity, tokens + math.max(0, now - ts) / 1000 * rate)
local allowed = 0
if tokens >= cost then
  tokens = tokens - cost
  allowed = 1
end
redis.call("HSET", KEYS[1], "tokens", tostring(tokens), "ts", tostring(now))
redis.call("PEXPIRE", KEYS[1], math.ceil(capacity / rate * 1000) + 1000)
local retry = 0
if allowed == 0 then retry = math.ceil((cost - tokens) / rate) end
return { allowed, math.floor(tokens), retry }
`;

export async function take(redis: Redis, key: string, { capacity, refillPerSecond, now = Date.now(), cost = 1 }: { capacity: number; refillPerSecond: number; now?: number; cost?: number }) {
  const [allowed, remaining, retryAfterSeconds] = (await redis.eval(TAKE, 1, `tb:${key}`, capacity, refillPerSecond, now, cost)) as number[];
  return { allowed: allowed === 1, remaining, retryAfterSeconds };
}

למה לא MULTI? כי ב־MULTI אי אפשר להחליט באמצע לפי ערך שנקרא — כל הפקודות נשלחות מראש. Lua רץ בתוך Redis, בבת אחת. זו גם הדרך שבה BullMQ עצמו עובד: רוב הלוגיקה שלו היא סקריפטים של Lua.

⚠️ טעויות נפוצות
  • סקריפט Lua ארוך או עם לולאות על הרבה מפתחות — Redis עושה דבר אחד בכל רגע; בזמן שהסקריפט רץ, כל השאר מחכים.
