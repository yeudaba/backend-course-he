1. מה בונים

דרישהאיך זה נראה מבחוץ
cache ל־GET /productsheader X-Cache: MISS בפעם הראשונה, HIT בשנייה, OFF בלי Redis. שינוי מוצר (מנהל) או הזמנה (מלאי) ← הבקשה הבאה MISS עם הנתונים החדשים
מפתחות עם קידומתכל מפתח ב־Redis מתחיל ב־REDIS_PREFIX (ברירת מחדל shop) ונקודתיים
מייל אישוראחרי תשלום מוצלח — רשומה אחת ב־GET /emails (מנהל בלבד; 403 ללקוח): to, subject עם מספר ההזמנה, body. בדיוק אחת, גם עם retries
ביטול אוטומטיהזמנה ב־pending_payment יותר מ־ORDER_PAYMENT_TIMEOUT_SECONDS (ברירת מחדל 1800) ← cancelled, והמלאי חוזר. הזמנה ששולמה — לא נוגעים
בלי Redisבלי REDIS_URL השרת עולה ועובד: X-Cache: OFF, המייל נכתב מיד, ואין ביטול אוטומטי. כל בודקי PR3 הקודמים עוברים

"שליחת מייל" כאן היא כתיבה לטבלה email_outbox, ו־GET /emails מציג אותה — כמו כלי פיתוח (Mailpit, Mailtrap) שתופסים מיילים במקום לשלוח. להחליף אחר כך בספק אמיתי זה שינוי של מקום אחד.

3. שלוש החלטות שכדאי לשים לב אליהן

Redis אופציונלי. החיבור נוצר רק אם יש REDIS_URL, וכל שימוש בודק null. ב־cache, שגיאה של Redis לא מפילה בקשה — חוזרים למסד. לכן החיבור מוגדר עם maxRetriesPerRequest: 2 ו־enableOfflineQueue: false: כש־Redis למטה, פקודה נכשלת מהר במקום לחכות בתור, והבקשה ממשיכה בלעדיו.

עבודות אחרי ה־COMMIT, לא בתוך הטרנזקציה. אם מוסיפים לתור בתוך הטרנזקציה והיא נכשלת אחר כך — יש עבודה על הזמנה שלא קיימת. אחרי ה־COMMIT יש את הבעיה ההפוכה (קריסה בין השניים), שהיא פחות גרועה פה, וה־outbox פותר (שיעור 4, סעיף 5).

src/orders/orders.service.ts 
    });  // סוף הטרנזקציה של יצירת ההזמנה
    await this.cache.invalidate("products");
    await this.jobs.add("expire-order", order.id, this.config.orderPaymentTimeoutSeconds * 1000);
    return order;

ה־worker באותו תהליך — עם מתג. WORKER=true (ברירת מחדל): ה־API גם מעבד עבודות. בהיקף גדול מריצים את אותו image פעמיים: API עם WORKER=false, ו־worker נפרד שאפשר להגדיל בנפרד. ובשני המקרים, worker.close() ב־shutdown מחכה לעבודות שבאמצע (graceful, פרק 24).

PR3-REDIS מעלה את השרת שלך עם REDIS_URL ו־REDIS_PREFIX ייחודי, ובודק: (1) cache — MISS ואז HIT עם אותו גוף, query אחר = MISS, מפתחות תחת הקידומת, ושינוי של מנהל או הזמנה מבטלים; (2) מייל — אין לפני תשלום, יש אחד אחרי, רק למנהל, ונשאר אחד; (3) עם ORDER_PAYMENT_TIMEOUT_SECONDS=2 — הזמנה שלא שולמה מתבטלת והמלאי חוזר, וששולמה נשארת paid. הפקודה השנייה מריצה את כל בודקי הפרויקט — הם רצים בלי Redis, וחייבים להמשיך לעבור.

ב־README של הפרויקט: עדכן את דיאגרמת הארכיטקטורה (Redis, worker), הוסף את GET /emails לטבלת ה־API, ושלוש שורות תחת "החלטות": Redis אופציונלי, ביטול בגרסה, ו"בדיקה בזמן הריצה" בביטול האוטומטי. ותחת "מה הייתי משפר" — outbox.

💼 בעולם העבודה

Redis מופיע בחלק גדול ממודעות ה־Backend — ובראיון השאלות הן כמעט תמיד אותן: "איך היית מוסיף cache, ואיך הוא מתעדכן?", "מה קורה אם Redis נופל?", "איך מונעים ששני שרתים ישלחו את אותו מייל?", "תכנן rate limiter". עכשיו יש לך תשובות מקוד שכתבת: cache-aside עם TTL וגרסה, Redis כאופטימיזציה ולא כמקור אמת, jobId קבוע וצרכן idempotent עם UNIQUE, ו־INCR עם EXPIRE NX. ותשובה אחת שמראיינים אוהבים לשמוע: "לפני cache — בדקתי שאין אינדקס חסר."
