שיעור 4 — תורים ועבודות ברקע עם BullMQ

⏱ ~50 דקות

🎯 בשיעור הזה
  • למה לא לעשות הכול בתוך הבקשה.
  • BullMQ: Queue, Worker, ניסיונות חוזרים ו־backoff — בריצה אמיתית.
  • עבודות מתוזמנות: "בעוד 30 דקות, אם עוד לא שולם — בטל".
  • at-least-once, ולמה הצרכן חייב להיות idempotent.
  • ומה קורה בין "שמרתי במסד" ל"הוספתי לתור": outbox.

1. מה לא שייך לבקשה

לקוח משלם. בתוך POST /orders/:id/pay אפשר גם לשלוח מייל אישור. אבל:

  • שרת המייל עונה בעוד 3 שניות — הלקוח מחכה 3 שניות לתשובה על תשלום שכבר הצליח.
  • שרת המייל נופל — מה מחזירים? 500? התשלום עבר. ואם הלקוח ילחץ שוב?
  • המייל נכשל — מי ינסה שוב? אף אחד; הבקשה כבר נגמרה.

הפתרון: הבקשה רושמת "צריך לשלוח אישור להזמנה 7" ועונה מיד. תהליך אחר — worker — לוקח את העבודה, מבצע, ואם נכשל — מנסה שוב, עם המתנה שגדלה. אותו דבר לכל מה שאיטי, לא אמין או לא דחוף: מיילים, PDF של חשבונית, עיבוד תמונה, webhook ללקוח, סנכרון עם מערכת חיצונית.

2. BullMQ

BullMQ שומר את התור ב־Redis: עבודה ממתינה, פעילה, הושלמה, נכשלה, מתוזמנת — כל אחת ברשימה או ב־sorted set. Queue מוסיף עבודות; Worker מקבל ומריץ. הם יכולים לרוץ בתהליכים שונים, על שרתים שונים — Redis מתאם ביניהם.

import { Queue, Worker, QueueEvents } from "bullmq";
const u = new URL(process.env.REDIS_URL ?? "redis://localhost:6379");
const connection = { host: u.hostname, port: Number(u.port || 6379), maxRetriesPerRequest: null };
const prefix = "lesson26-bull";

const queue = new Queue("emails", { connection, prefix });
await queue.obliterate({ force: true }); // ניקוי מריצה קודמת
const events = new QueueEvents("emails", { connection, prefix });

let smtpUp = false; // "שרת המייל" נופל בניסיון הראשון
const worker = new Worker("emails", async (job) => {
  console.log("worker got", job.name, JSON.stringify(job.data), "attempt", job.attemptsMade + 1);
  if (!smtpUp) { smtpUp = true; throw new Error("smtp timeout"); }
  return "sent";
}, { connection, prefix });
worker.on("failed", (job, err) => console.log("failed attempt", job?.attemptsMade, err.message));

const job = await queue.add("email", { orderId: 7 }, { jobId: "confirm-7", attempts: 3, backoff: { type: "exponential", delay: 200 } });
await queue.add("email", { orderId: 7 }, { jobId: "confirm-7" }); // אותו jobId — מתעלמים
console.log("completed", await job.waitUntilFinished(events), "· jobs:", await queue.getJobCountByTypes("completed", "failed", "waiting"));

await worker.close(); await events.close(); await queue.obliterate({ force: true }); await queue.close();
worker got email {"orderId":7} attempt 1
failed attempt 1 smtp timeout
worker got email {"orderId":7} attempt 2
completed sent · jobs: 1
  • הבקשה לא חיכתה. queue.add כותב ל־Redis וחוזר; כל השאר קורה ב־worker.
  • זריקה = כישלון ← BullMQ מחזיר את העבודה לתור עם המתנה: 200ms, 400ms, 800ms… (exponential). אחרי attempts כישלונות — העבודה עוברת ל־failed ונשארת שם, עם השגיאה, כדי שתוכל לראות ולהריץ שוב. לכן ב־worker לא בולעים שגיאות: try/catch שמדפיס ולא זורק — BullMQ חושב שהצליח, ואין ניסיון חוזר (E23).
  • jobId קבוע = הוספה כפולה היא עבודה אחת. ה־add השני לא יצר עבודה. jobId: randomUUID() — כל לחיצה כפולה היא מייל נוסף.
  • maxRetriesPerRequest: null — ה־Worker מחכה לעבודות בחיבור חוסם; בלי זה ioredis "מוותר" על הפקודה, ו־BullMQ מזהיר.

3. עבודות מתוזמנות

בפרויקט 3, הזמנה ב־pending_payment מחזיקה מלאי. אם הלקוח לא משלם תוך 30 דקות — לבטל ולהחזיר למלאי. עם תור: ברגע יצירת ההזמנה מוסיפים עבודה עם delay.

src/orders/orders.service.ts 
await this.jobs.add("expire-order", order.id, this.config.orderPaymentTimeoutSeconds * 1000);
…
async expire(id: number) {
  // לא "בטל", אלא "בטל אם עדיין מחכה לתשלום" — בתנאי, בתוך UPDATE
  return (await this.cancelAndRestock(id, ["pending_payment"], order.items)) ? "expired" : "skipped";
}

שים לב מה לא עשינו: לבטל את העבודה כשהלקוח משלם. היה אפשר (job.remove(), E17) — אבל אם הביטול נכשל, העבודה תרוץ ותבטל הזמנה ששולמה. במקום זה, העבודה בודקת את המצב כשהיא רצה, עם UPDATE … WHERE status = 'pending_payment'. שולם? skipped. זה נכון תמיד, גם אם העבודה רצה פעמיים, גם אם רצה באיחור.

ולמה לא cron שרץ כל דקה ובודק "הזמנות ישנות"? אפשר, וזה פתרון לגיטימי (ופשוט). התור מדויק יותר ולא סורק את כל הטבלה כל דקה; cron עמיד יותר אם Redis אבד. מערכות רבות עושות את שניהם: תור לזמן אמת, ו־cron כרשת ביטחון.

4. at-least-once

worker לקח עבודה, שלח את המייל — וקרס לפני שסימן "הושלם". BullMQ רואה עבודה שה־worker שלה נעלם (stalled) ומחזיר אותה לתור. worker אחר שולח שוב. אין דרך להימנע מזה לגמרי: או שמסמנים לפני הביצוע (ואז קריסה = עבודה שלא קרתה — at-most-once), או אחרי (קריסה = עבודה שקרתה פעמיים — at-least-once). תורים בוחרים at-least-once, ולכן:

⚠️ הכלל: הצרכן idempotent

הרצה שנייה של אותה עבודה לא עושה נזק. בפרויקט: המייל נשמר בטבלה עם @@unique([kind, orderId]) — הרצה שנייה נתקלת ב־P2002 ומחזירה "duplicate". "נשלח" ו"נרשם שנשלח" הם אותה פעולה במסד. הביטול האוטומטי — UPDATE בתנאי, כמו שראינו. ובמערכת אמיתית שולחת מיילים: מעבירים לספק מפתח idempotency (ל־Stripe, ל־SendGrid וכו׳ יש), או רושמים "נשלח" באותה טרנזקציה של הסטטוס (E18 מראה גרסה עם SET NX ב־Redis — ואת המגבלה שלה).

5. ובין המסד לתור?

ב־pay: (1) UPDATE ל־paid, (2) queue.add("order-confirmation"). מה אם התהליך קורס ביניהם? ההזמנה שולמה, והמייל לא יישלח לעולם. ההפך (קודם התור) — מייל על תשלום שלא נשמר. אי אפשר לעשות טרנזקציה אחת על PostgreSQL ו־Redis.

הפתרון התעשייתי נקרא transactional outbox: באותה טרנזקציה של ה־UPDATE, כותבים שורה לטבלת outbox ("צריך לשלוח אישור ל־7"). תהליך נפרד קורא את הטבלה ומעביר לתור (או שולח בעצמו), ומסמן. עכשיו "שולם" ו"צריך לשלוח" נרשמים יחד או לא בכלל. בפרויקט שלנו לא הלכנו עד שם — זה מופיע ב־README תחת "מה הייתי משפר", וזו תשובה מצוינת לשאלה "מה קורה אם השרת קורס באמצע?".

💡 BullMQ ומה שמסביב

תורים אחרים שתפגוש: RabbitMQ, Amazon SQS (מנוהל, בלי Redis), ו־Kafka — שהוא בעצם יומן אירועים ש"צרכנים" רבים קוראים, לא תור עבודות. ב־Nest יש @nestjs/bullmq עם דקורטורים (@Processor); בפרויקט השתמשנו ב־BullMQ ישירות כדי לראות מה קורה. לניטור: bull-board — דף שמראה עבודות ממתינות, שנכשלו, ומאפשר להריץ שוב.
