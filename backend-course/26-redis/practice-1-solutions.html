P26-E01 · Redis או PostgreSQL? 🧠 הבנה רמה 1

💡 רמז 1

שאלה אחת לכל שורה: מה קורה אם Redis מאבד את המידע (restart בלי persistence, או מחיקה)?

💡 רמז 2

Redis שומר בזיכרון. הוא יכול לשמור לדיסק — אבל ברוב ההגדרות לא מתייחסים אליו כמקור אמת לכסף.

✅ פתרון
  1. PostgreSQL. כסף, טרנזקציות, constraints, גיבויים. אסור לאבד.
  2. שניהם: מקור האמת ב־PostgreSQL, עותק ב־Redis (cache). נמחק? טוענים שוב.
  3. Redis. נתון קצר־חיים שמשתנה בכל בקשה, ושכל השרתים צריכים לראות (פרק 24 עשה את זה ב־Map — לשרת אחד). נאבד? הכי גרוע — מישהו קיבל עוד כמה ניסיונות.
  4. תלוי במוצר. בפרויקט — PostgreSQL (המשתמש מצפה לראות אותה גם מחר, ממכשיר אחר). אתרים עם המון אורחים — לפעמים ב־Redis עם TTL, עגלה של אורח.
  5. Redis — sorted set לכל דקה (E24). סטטיסטיקה "חמה", מקורבת, שמתה לבד.
  6. תלוי: בפרויקט — PostgreSQL, כי הוא חלק מאותה טרנזקציה ומאותן החלטות. ב־Redis עם TTL זה עובד ומהיר יותר, אבל אז "ההזמנה נשמרה" ו"המפתח נשמר" כבר לא אטומיים יחד.
  7. Redis (BullMQ). העבודה עצמה — המייל — יכולה להיווצר מחדש מהמסד; לכן גם אובדן התור לא שובר נכונות, רק מעכב.
⚠️ טעויות נפוצות
  • "Redis מהיר, אז הכול שם". מהירות לא שווה הרבה אם נתון שאסור לאבד נעלם ב־restart.

P26-E02 · איזה מבנה נתונים? 🧠 הבנה רמה 1

💡 רמז 1

sorted set = set שכל איבר בו מקבל מספר (score), ונשמר ממוין לפיו.

💡 רמז 2

"הכי חדש ראשון, עד 10" — רשימה שדוחפים לראשה וחותכים את הזנב.

✅ פתרון
  1. string — SET key json EX 60.
  2. string כמספר — INCR (אטומי), או hash עם HINCRBY כשיש הרבה מונים קשורים (E08).
  3. list — LREM + LPUSH + LTRIM 0 9 (E11).
  4. set — SADD מחזיר 1 אם נוסף, 0 אם כבר היה. ההחזרה הזו היא כל הבדיקה.
  5. sorted set — ZINCRBY, ואז ZREVRANGE 0 9 WITHSCORES (E10).
  6. hash — HSET / HGETALL: שדות בשם, אפשר לעדכן אחד בלי לקרוא את כולם.
  7. sorted set עם הזמן כ־score — ZADD, ZREMRANGEBYSCORE, ZCARD (E15).
⚠️ טעויות נפוצות
  • לשמור הכול כ־JSON ב־string ולעדכן ב"קרא, שנה, כתוב" — מאבדים את האטומיות שהמבנים נותנים בחינם.

P26-E05 · מה יחזיר Redis? 🧠 הבנה רמה 1

💡 רמז 1

כל מה ש־Redis מחזיר כ"ערך" הוא מחרוזת — גם אחרי INCR. מונים מחזירים מספרים.

💡 רמז 2

SADD מחזיר כמה איברים חדשים נוספו. SET … NX מחזיר "OK" או null.

✅ פתרון
import { Redis } from "ioredis";
const r = new Redis(process.env.REDIS_URL ?? "redis://localhost:6379", { keyPrefix: "e05:" });
await r.del("n", "s", "l", "z");
console.log(await r.incr("n"), await r.incrby("n", 10), typeof (await r.get("n")));
console.log(await r.sadd("s", "a", "b", "a"), await r.sadd("s", "a"), await r.scard("s"));
await r.rpush("l", "1", "2", "3");
console.log(await r.lrange("l", 0, -1), await r.lpop("l"), await r.llen("l"));
await r.zadd("z", 30, "yossi", 50, "dana", 10, "noa");
console.log(await r.zrevrange("z", 0, 1), await r.zscore("z", "dana"));
console.log(await r.set("x", "1", "NX"), await r.set("x", "2", "NX"), await r.get("x"));
await r.del("n", "s", "l", "z", "x");
await r.quit();
1 11 string
2 0 2
[ '1', '2', '3' ] 1 2
[ 'dana', 'yossi' ] 50
OK null 1
  • INCR מחזיר מספר, אבל GET — מחרוזת. ב־Redis הכול מחרוזות; "מספר" זה רק מחרוזת ש־INCR יודע לקרוא.
  • SADD s a b a — 2: ה־"a" השני לא נוסף. ושוב a — 0. זה בדיוק "האם כבר הצביע".
  • ZSCORE מחזיר מחרוזת ("50").
  • SET NX: הראשון "OK", השני null, והערך נשאר "1" — הבסיס של מנעולים (E12).
⚠️ טעויות נפוצות
  • if (await r.get("n") > 5) — השוואה של מחרוזת למספר עובדת "במקרה" ב־JavaScript. Number(...) במפורש.

P26-E34 · ‏SET מוחק את התוקף? 🧠 הבנה רמה 2

💡 רמז 1

‏SET בלי EX כותב מפתח "חדש" — עם כל מה שהיה לו קודם?

💡 רמז 2

‏INCR משנה את הערך, לא את המפתח.

✅ פתרון
import { Redis } from "ioredis";
const r = new Redis(process.env.REDIS_URL ?? "redis://localhost:6379", { keyPrefix: "e34:" });
await r.set("code", "4821", "EX", 300);
console.log(await r.ttl("code"));
await r.set("code", "9999");
console.log(await r.ttl("code"));
await r.set("hits", "0", "EX", 300);
await r.incr("hits");
console.log((await r.ttl("hits")) > 0, await r.ttl("nothing"), await r.expire("nothing", 60));
await r.del("code", "hits");
await r.quit();
300
-1
true -2 0

‏SET מחליף את המפתח כולו — גם את התוקף. אחרי SET code 9999 בלי EX, ה־TTL הוא −1: הקוד החדש חי לנצח. ‏INCR רק משנה את הערך, והתוקף נשאר. ‏TTL על מפתח שלא קיים — ‏−2, ו־EXPIRE עליו מחזיר 0 (לא נוצר כלום).

ב־OTP: כל כתיבה של קוד חדש חייבת לכלול EX מחדש (SET otp:<user> 9999 EX 300). אחרת קוד אימות אחד נשאר תקף לתמיד — חור אבטחה.

⚠️ טעויות נפוצות
  • "ה־TTL שייך למפתח, אז הוא נשאר" — הוא נשאר רק בפקודות שמשנות ערך (INCR, HSET, LPUSH). ‏SET מחליף.

P26-E35 · ‏MULTI עם פקודה שנכשלה 🧠 הבנה רמה 2

💡 רמז 1

‏INCR על "dana" — מה Redis אומר כשהערך לא מספר?

💡 רמז 2

‏exec() לא זורק בגלל פקודה אחת שנכשלה — הוא מחזיר [err, value] לכל פקודה.

✅ פתרון
import { Redis } from "ioredis";
const r = new Redis(process.env.REDIS_URL ?? "redis://localhost:6379", { keyPrefix: "e35:" });
await r.del("count", "name");
await r.set("name", "dana");
const res = await r.multi().incr("count").incr("name").incr("count").exec();
console.log(JSON.stringify(res!.map(([err, value]) => (err ? err.message : value))));
console.log(await r.get("count"), await r.get("name"));
await r.del("count", "name");
await r.quit();
[1,"ERR value is not an integer or out of range",2]
2 dana
  1. שתיים מתוך שלוש: הראשונה והשלישית. השנייה נכשלה בזמן הריצה, והשאר בוצעו בכל זאת.
  2. ב־PostgreSQL השגיאה מבטלת את הטרנזקציה, ו־COMMIT הופך ל־ROLLBACK: אף שינוי לא נשמר (פרק 18).
  3. לעבור על התוצאות ולבדוק את err של כל פקודה. ‏MULTI מבטיח רק שאף פקודה של לקוח אחר לא תיכנס באמצע — לא "הכול או כלום".
⚠️ טעויות נפוצות
  • לקרוא רק res[0][1] ולהניח שהכול עבר.
  • לחשוב ש־exec() יזרוק — הוא זורק רק כשה־MULTI כולו נדחה (למשל פקודה עם שם לא קיים, שנדחית עוד לפני הריצה).

P26-E36 · ‏KEYS, ‏keyPrefix ו־Redis ריק 🧠 הבנה רמה 1

💡 רמז 1

Redis מריץ פקודה אחת בכל רגע.

💡 רמז 2

"Redis לא מקור האמת" — מה מכל אלה אפשר לבנות מחדש?

✅ פתרון
  1. ‏KEYS עובר על כל שני המיליון — שניות שלמות שבהן Redis לא עונה לאף אחד. כל בקשה בכל השרתים שמחכה ל־GET (cache, הגבלת קצב, sessions) נתקעת. במקום זה — לא לחפש מפתחות בכלל: גרסה לקבוצה (שיעור 2), ואם חייבים — SCAN בחלקים.
  2. הן דורסות זו את זו: החנות כותבת hash, הדוחות כותבים JSON, ו־HGETALL נכשל עם WRONGTYPE. עם keyPrefix: "shop:" ו־"reports:" המפתחות בפועל שונים — והקוד של כל אחת לא משתנה.
  3. קטלוג: הבקשות הראשונות איטיות יותר (MISS), ואז הכול חוזר — לא מורגש. הגבלת קצב: כולם מקבלים חלון חדש — בוט מקבל עוד כמה ניסיונות. sessions: כל המשתמשים מנותקים ונדרשים להתחבר שוב — מורגש, אבל אף נתון לא אבד. לכן sessions עם JWT או מקור אמת במסד הם החלטה ששוקלים.
⚠️ טעויות נפוצות
  • "נשתמש ב־FLUSHALL לניקוי" — מוחק גם את הנתונים של האפליקציה השנייה, וגם את התור של BullMQ.

P26-E06 · מטמון JSON 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

redis.set(key, json, "EX", ttl). redis.ttl מחזיר −2 כשאין מפתח, −1 כשאין תוקף.

💡 רמז 2

0 ו־false הם ערכים — בדוק raw === null, לא !raw.

✅ פתרון
// P26-E06
import type { Redis } from "ioredis";

// מטמון JSON פשוט מעל Redis: מחרוזות בלבד שם — לכן JSON.stringify / parse
export function createJsonStore(redis: Redis) {
  return {
    async set(key: string, value: unknown, ttlSeconds?: number) {
      if (value === undefined) throw new Error("אין ערך לשמור");
      const json = JSON.stringify(value);
      if (ttlSeconds) await redis.set(key, json, "EX", ttlSeconds);
      else await redis.set(key, json);
    },
    async get<T>(key: string): Promise<T | null> {
      const raw = await redis.get(key);
      return raw === null ? null : (JSON.parse(raw) as T);
    },
    async del(key: string) {
      return (await redis.del(key)) === 1;
    },
    // כמה שניות נשארו: null — אין מפתח; Infinity — בלי תוקף
    async ttl(key: string) {
      const t = await redis.ttl(key);
      return t === -2 ? null : t === -1 ? Infinity : t;
    },
  };
}
⚠️ טעויות נפוצות
  • redis.set(key, value) עם אובייקט — ioredis שומר "[object Object]".

P26-E08 · מונים ודירוג 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

HINCRBY, ZINCRBY, EXPIRE — ב־redis.multi()…exec().

💡 רמז 2

exec() מחזיר מערך של [error, result] לכל פקודה.

✅ פתרון
// P26-E08
import type { Redis } from "ioredis";

// צפיות במוצרים: מונה לכל יום (ומחיקה אוטומטית אחרי שבוע), ו־sorted set לדירוג
export async function trackView(redis: Redis, productId: number, now: Date) {
  const day = now.toISOString().slice(0, 10);
  const views = `views:${day}`;
  // MULTI: הכול יחד, בלי שבקשה אחרת תיכנס באמצע
  const results = await redis
    .multi()
    .hincrby(views, String(productId), 1)
    .expire(views, 7 * 86400)
    .zincrby(`top:${day}`, 1, String(productId))
    .expire(`top:${day}`, 7 * 86400)
    .exec();
  return Number(results![0][1]); // התוצאה של הפקודה הראשונה (HINCRBY)
}

export async function topProducts(redis: Redis, day: string, n: number): Promise<{ productId: number; views: number }[]> {
  const flat = await redis.zrevrange(`top:${day}`, 0, n - 1, "WITHSCORES");
  const out = [];
  for (let i = 0; i < flat.length; i += 2) out.push({ productId: Number(flat[i]), views: Number(flat[i + 1]) });
  return out;
}

הבודק שולח 50 צפיות במקביל ובודק שהמונה 50 — HINCRBY אטומי. "קרא, הוסף 1, כתוב" היה מאבד צפיות.

⚠️ טעויות נפוצות
  • מונה בלי תוקף — אחרי שנה יש 365 hashes שאף אחד לא קורא.

P26-E10 · טבלת מובילים 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

ZINCRBY, ZREVRANGE … WITHSCORES, ZREVRANK (מ־0).

💡 רמז 2

around: start = max(0, rank − radius).

✅ פתרון
// P26-E10
import type { Redis } from "ioredis";

// טבלת מובילים: sorted set — Redis שומר ממוין לפי score, וכל פעולה ב־O(log n)
export function leaderboard(redis: Redis, name: string) {
  const key = `lb:${name}`;
  return {
    add: (player: string, points: number) => redis.zincrby(key, points, player).then(Number),
    async top(n: number) {
      const flat = await redis.zrevrange(key, 0, n - 1, "WITHSCORES");
      return Array.from({ length: flat.length / 2 }, (_, i) => ({ player: flat[2 * i], score: Number(flat[2 * i + 1]), rank: i + 1 }));
    },
    // מקום (מ־1), או null
    async rank(player: string) {
      const r = await redis.zrevrank(key, player);
      return r === null ? null : r + 1;
    },
    async around(player: string, radius: number) {
      const r = await redis.zrevrank(key, player);
      if (r === null) return [];
      const start = Math.max(0, r - radius);
      const flat = await redis.zrevrange(key, start, r + radius, "WITHSCORES");
      return Array.from({ length: flat.length / 2 }, (_, i) => ({ player: flat[2 * i], score: Number(flat[2 * i + 1]), rank: start + i + 1 }));
    },
  };
}
⚠️ טעויות נפוצות
  • טבלת מובילים ב־SQL עם ORDER BY על כל צפייה — עובד ל־1,000 שחקנים, לא למיליון בזמן אמת.

P26-E11 · צפית לאחרונה 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

LREM key 0 value — מוחק את כל המופעים.

💡 רמז 2

LTRIM key 0 max−1 — רשימה חסומה.

✅ פתרון
// P26-E11
import type { Redis } from "ioredis";

// "צפית לאחרונה": רשימה לכל משתמש, הכי חדש ראשון, בלי כפילויות, עד max, ונמחקת אחרי 30 יום בלי פעילות
export async function viewed(redis: Redis, userId: number, productId: number, max = 10) {
  const key = `recent:${userId}`;
  await redis
    .multi()
    .lrem(key, 0, String(productId)) // אם כבר שם — מוציאים, כדי שיעלה לראש
    .lpush(key, String(productId))
    .ltrim(key, 0, max - 1) // רשימה חסומה: לא גדלה לנצח
    .expire(key, 30 * 86400)
    .exec();
}

export async function recent(redis: Redis, userId: number): Promise<number[]> {
  return (await redis.lrange(`recent:${userId}`, 0, -1)).map(Number);
}
⚠️ טעויות נפוצות
  • בלי LTRIM — רשימה שגדלה לנצח.

P26-E24 · אתגר: חם עכשיו 🤖 💻 כתיבת קוד 🤖 רמה 5

💡 רמז 1

ZUNIONSTORE tmp N key1 key2 … — מחבר sorted sets (סכום scores). מפתח שלא קיים — כמו ריק.

💡 רמז 2

הכול ב־multi(): zunionstore, zrevrange, del.

✅ פתרון
// P26-E24
import type { Redis } from "ioredis";

const minuteOf = (now: number) => Math.floor(now / 60_000);

// "חם עכשיו": sorted set לכל דקה. צפייה ← ZINCRBY בדלי של הדקה הנוכחית (שמת לבד אחרי שעתיים)
export async function recordView(redis: Redis, productId: number, now = Date.now()) {
  const key = `trend:${minuteOf(now)}`;
  await redis.multi().zincrby(key, 1, String(productId)).expire(key, 7200).exec();
}

// N הדקות האחרונות: ZUNIONSTORE מחבר את הדליים (סכום ה־scores) למפתח זמני, ומשם — ה־top
export async function trending(redis: Redis, { windowMinutes, n, now = Date.now() }: { windowMinutes: number; n: number; now?: number }) {
  const m = minuteOf(now);
  const buckets = Array.from({ length: windowMinutes }, (_, i) => `trend:${m - i}`);
  const tmp = `trend:tmp:${m}:${windowMinutes}:${Math.random().toString(36).slice(2)}`;
  const results = await redis
    .multi()
    .zunionstore(tmp, buckets.length, ...buckets)
    .zrevrange(tmp, 0, n - 1, "WITHSCORES")
    .del(tmp)
    .exec();
  const flat = results![1][1] as string[];
  return Array.from({ length: flat.length / 2 }, (_, i) => ({ productId: Number(flat[2 * i]), views: Number(flat[2 * i + 1]) }));
}

זה דפוס כללי: "bucketing" — דלי לכל יחידת זמן, וחלון = איחוד של כמה דליים. אותו רעיון מאחורי מדדים ב־Prometheus ובכלי ניטור.

⚠️ טעויות נפוצות
  • מפתח זמני בשם קבוע (trend:tmp) — שתי בקשות במקביל דורסות זו את זו.

P26-E31 · sessions ב־Redis 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

await redis.multi().hset(key, { ...data, userId: String(userId) }).expire(key, ttlSec).sadd(...).exec(). ‏HGETALL על מפתח שלא קיים מחזיר {}, לא null. ‏const { userId, ...data } = hash מפריד את userId משאר השדות.

💡 רמז 2

תוקף לרשימה: EXPIRE key ttl NX קובע תוקף רק אם אין לה עדיין, ו־EXPIRE key ttl GT רק מאריך. שניהם ברצף. ב־ioredis: .expire(key, ttl, "NX").expire(key, ttl, "GT"). ב־destroyAllForUser: ‏SMEMBERS, ואז redis.del(...ids.map(k)). ‏DEL מחזיר כמה מפתחות היו קיימים ונמחקו. זה בדיוק המספר.

✅ פתרון
// P26-E31 — sessions ב־Redis
import { randomUUID } from "node:crypto";
import type { Redis } from "ioredis";

export type Session = { userId: number; data: Record<string, string> };

const sessionKey = (id: string) => `session:${id}`;
const userKey = (userId: number) => `user:${userId}:sessions`;

export async function createSession(redis: Redis, userId: number, data: Record<string, string> = {}, ttlSec = 1800): Promise<string> {
  const id = randomUUID();
  await redis
    .multi()
    .hset(sessionKey(id), { ...data, userId: String(userId) })
    .expire(sessionKey(id), ttlSec)
    .sadd(userKey(userId), id)
    // הרשימה חיה כמו ה־session הארוך ביותר שבה: NX — אם אין לה עדיין תוקף, GT — רק להאריך
    .expire(userKey(userId), ttlSec, "NX")
    .expire(userKey(userId), ttlSec, "GT")
    .exec();
  return id;
}

export async function getSession(redis: Redis, id: string, ttlSec = 1800): Promise<Session | null> {
  const hash = await redis.hgetall(sessionKey(id));
  if (Object.keys(hash).length === 0) return null;
  const { userId, ...data } = hash;
  await redis.multi().expire(sessionKey(id), ttlSec).expire(userKey(Number(userId)), ttlSec, "GT").exec();
  return { userId: Number(userId), data };
}

export async function destroySession(redis: Redis, id: string): Promise<boolean> {
  const userId = await redis.hget(sessionKey(id), "userId");
  if (userId === null) return false;
  await redis.multi().del(sessionKey(id)).srem(userKey(Number(userId)), id).exec();
  return true;
}

export async function destroyAllForUser(redis: Redis, userId: number): Promise<number> {
  const ids = await redis.smembers(userKey(userId));
  const deleted = ids.length > 0 ? await redis.del(...ids.map(sessionKey)) : 0;
  await redis.del(userKey(userId));
  return deleted;
}

שורה 2: ה־session של הטלפון חי 60 שניות, והרשימה של המשתמש 1,800. בלי NX/‏GT, ה־session הקצר היה קובע לרשימה 60 שניות. אחרי דקה היא הייתה נמחקת, ו־"התנתק מכל המכשירים" לא היה מוצא את הלפטופ.

למה הרשימה בכלל? בלעדיה, כדי למצוא את כל ה־sessions של משתמש צריך לסרוק את כל המפתחות (SCAN session:*) ולקרוא כל אחד. זה איטי, ובשרת גדול זה מיליוני מפתחות. האינדקס ההפוך (משתמש ← מזהים) הוא אותו רעיון כמו אינדקס במסד. המחיר: לשמור על שניהם מעודכנים, ולכן MULTI.

הרשימה יכולה להכיל מזהים של sessions שכבר פגו. זה לא מזיק: ‏DEL עליהם לא עושה כלום, והרשימה עצמה פגה בסוף. בגלל זה destroyAllForUser סופרת לפי מה ש־DEL החזיר, ולא לפי אורך הרשימה.

⚠️ טעויות נפוצות
  • Math.random().toString(36) כמזהה — אפשר לנחש. מזהה session הוא סיסמה זמנית.
  • HSET ואז EXPIRE בלי MULTI — אם השרת נופל ביניהם, נשאר session בלי תוקף, לנצח.
  • if (!hash) — ‏{} הוא truthy, ו־session שלא קיים חוזר כ־{ userId: NaN }.
  • לקבוע לרשימה EXPIRE רגיל בכל יצירה — session קצר מקצר את הרשימה של כולם.

// P26-E37: עגלת קניות ב־hash
import type { Redis } from "ioredis";

const WEEK = 7 * 86400;
const key = (userId: number) => `cart:${userId}`;

export async function addToCart(redis: Redis, userId: number, productId: number, qty: number) {
  const [[, n]] = (await redis.multi().hincrby(key(userId), String(productId), qty).expire(key(userId), WEEK).exec()) as [Error | null, number][];
  if (n <= 0) {
    await redis.hdel(key(userId), String(productId));
    return 0;
  }
  return n;
}

export async function getCart(redis: Redis, userId: number) {
  const h = await redis.hgetall(key(userId));
  return Object.fromEntries(Object.entries(h).map(([k, v]) => [k, Number(v)]));
}

export async function clearCart(redis: Redis, userId: number) {
  return (await redis.del(key(userId))) === 1;
}

‏HINCRBY אטומי — שתי לשוניות שמוסיפות במקביל לא מאבדות אף יחידה. ההחלטה "0 ← למחוק" נעשית אחרי, בפקודה נפרדת; כאן זה בסדר, כי HDEL על שדה שכבר 0 לא מזיק.

⚠️ טעויות נפוצות
  • HGET, חישוב ב־JS ו־HSET — אותו מרוץ של "קרא, שנה, כתוב" משיעור 3.
  • להשאיר שדה עם 0 או -1 — הדף יראה "מוצר בכמות 0" בעגלה.

// P26-E38: סקר — הצבעה אחת למשתמש
import type { Redis } from "ioredis";

export async function vote(redis: Redis, pollId: string, userId: number, option: string) {
  const added = await redis.sadd(`poll:${pollId}:voters`, String(userId));
  if (added === 0) return false;
  await redis.hincrby(`poll:${pollId}:results`, option, 1);
  return true;
}

export async function results(redis: Redis, pollId: string) {
  const h = await redis.hgetall(`poll:${pollId}:results`);
  return Object.entries(h)
    .map(([option, v]) => ({ option, votes: Number(v) }))
    .sort((a, b) => b.votes - a.votes || a.option.localeCompare(b.option));
}

‏SADD הוא "בדוק והוסף" בפקודה אחת. אם היינו כותבים SISMEMBER ואז SADD, שתי בקשות במקביל היו רואות "עוד לא הצביע", ושתיהן נספרות.

⚠️ טעויות נפוצות

💡 רמז 2

✅ פתרון
// P26-E42: לבנות דירוג מחדש משורות SQL
import type { Redis } from "ioredis";

export async function rebuildBestsellers(redis: Redis, key: string, rows: { product_id: number; qty: string | number }[]) {
  const m = redis.multi().del(key);
  for (const r of rows) m.zadd(key, Number(r.qty), String(r.product_id));
  await m.expire(key, 86400).exec();
  return rows.length;
}

export async function topBestsellers(redis: Redis, key: string, n: number) {
  const flat = await redis.zrevrange(key, 0, n - 1, "WITHSCORES");
  const out: { productId: number; qty: number }[] = [];
  for (let i = 0; i < flat.length; i += 2) out.push({ productId: Number(flat[i]), qty: Number(flat[i + 1]) });
  return out;
}

‏DEL בתוך אותו MULTI חשוב: בלעדיו מוצר שהיה בדירוג הקודם ולא נמכר החודש נשאר. ובלי MULTI, קורא שמגיע בין ה־DEL ל־ZADD רואה דף בית בלי "הכי נמכרים".

⚠️ טעויות נפוצות
  • ZINCRBY במקום ZADD — בנייה שנייה מכפילה את הכמויות.
  • להשאיר את qty כמחרוזת ב־topBestsellers — ‏"12" > "9" הוא false.

// P26-E43: Express — מונה צפיות ודירוג
import express from "express";
import type { Redis } from "ioredis";

export function viewsApp(redis: Redis) {
  const app = express();
  app.post("/products/:id/view", async (req, res) => {
    if (!/^[1-9]\d*$/.test(req.params.id)) return res.status(400).json({ error: "id לא תקין" });
    const id = req.params.id;
    const r = await redis.multi().hincrby("views", id, 1).zincrby("top", 1, id).exec();
    res.json({ productId: Number(id), views: Number(r![0][1]) });
  });
  app.get("/products/top", async (req, res) => {
    const raw = req.query.n ?? "5";
    const n = Number(raw);
    if (typeof raw !== "string" || !Number.isInteger(n) || n < 1 || n > 50) return res.status(400).json({ error: "n בין 1 ל־50" });
    const flat = await redis.zrevrange("top", 0, n - 1, "WITHSCORES");
    const out = [];
    for (let i = 0; i < flat.length; i += 2) out.push({ productId: Number(flat[i]), views: Number(flat[i + 1]) });
    res.json(out);
  });
  return app;
}

⚠️ טעויות נפוצות
  • Number("1.5") או Number("") (‏0) כ־id — לכן regex.
  • ?n=abc ← ‏NaN ← ‏zrevrange(top, 0, NaN) — שגיאה מ־Redis במקום 400.

// P26-E44: פרופיל — Zod לפני HSET, וטיפוסים בחזרה
import type { Redis } from "ioredis";
import { z } from "zod";

const schema = z.strictObject({
  name: z.string().trim().min(1),
  city: z.string().trim().min(1),
  age: z.number().int().min(13).max(120),
  newsletter: z.boolean().default(false),
});
type Profile = z.infer<typeof schema>;

export async function saveProfile(redis: Redis, userId: number, input: unknown): Promise<Profile> {
  const r = schema.safeParse(input);
  if (!r.success) throw new Error("VALIDATION_ERROR");
  const p = r.data;
  await redis.hset(`profile:${userId}`, { name: p.name, city: p.city, age: String(p.age), newsletter: p.newsletter ? "1" : "0" });
  return p;
}

export async function loadProfile(redis: Redis, userId: number): Promise<Profile | null> {
  const h = await redis.hgetall(`profile:${userId}`);
  if (Object.keys(h).length === 0) return null;
  return { name: h.name, city: h.city, age: Number(h.age), newsletter: h.newsletter === "1" };
}

הגבול בין "עולם עם טיפוסים" (הקוד) ל"עולם של מחרוזות" (Redis) עובר בשתי הפונקציות האלה בלבד. כל שאר הקוד מקבל age: number אמיתי.

⚠️ טעויות נפוצות
  • hset(key, p) ישירות — ioredis ממיר false ל־"false", ובחזרה Boolean("false") הוא true.
  • לשמור את input במקום r.data — בלי trim ובלי ברירת המחדל.
