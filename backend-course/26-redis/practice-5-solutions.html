מי מריץ את בודקי PR3 הקודמים, ובאיזו סביבה?

💡 רמז 2

"כל שימוש בודק null".

✅ פתרון
  1. (א) בודקי PR3 הקודמים ו־npm run start:dev בלי Docker ממשיכים לעבוד. (ב) Redis הוא אופטימיזציה ותשתית עזר, לא מקור אמת — המערכת לא אמורה ליפול איתו. (ג) פריסה הדרגתית: אפשר להעלות את הקוד לפני שה־Redis המנוהל מוכן.

P26-E87 · ‏X-Cache: ‏HIT, ‏MISS או OFF? 🧠 הבנה רמה 1

💡 רמז 1

המפתח בנוי מה־DTO אחרי ולידציה, כולל ברירות מחדל.

💡 רמז 2

הזמנה משנה מלאי, והמלאי מופיע ברשימה.

✅ פתרון
  1. MISS.
  2. HIT.
  3. HIT — page=1 היא ברירת המחדל, ולכן אותו מפתח בדיוק.
  4. MISS — ה־PATCH העלה את הגרסה (INCR v:products).
  5. MISS — יצירת הזמנה מבטלת גם היא (המלאי השתנה).
  6. OFF — הקריאה ל־Redis נכשלת מהר (enableOfflineQueue: false), והבקשה חוזרת למסד. סטטוס 200, לא 500.
⚠️ טעויות נפוצות
  • לחשוב שבשורה 6 יחזור MISS — MISS אומר "Redis עבד ולא היה ערך". OFF אומר "Redis לא בתמונה", וזה מה שרוצים לראות בדיבאג.

P26-E88 · עבודה בתוך הטרנזקציה או אחריה? 🧠 הבנה רמה 2

💡 רמז 1

‏Redis לא משתתף בטרנזקציה של PostgreSQL.

💡 רמז 2

קריסה בין COMMIT ל־add.

✅ פתרון
  1. העבודה כבר ב־Redis, וההזמנה לא קיימת (ROLLBACK). בעוד 30 דקות העבודה רצה על הזמנה שלא קיימת — ‏skipped במקרה הטוב, ובמקרה גרוע (אם ה־id נוצל שוב) מבטלת הזמנה אחרת.
  2. קריסה בין ה־COMMIT ל־add: ההזמנה קיימת, ואין עבודה שתבטל אותה. מחזיקה מלאי לנצח.
  3. "הזמנה שלא בוטלה" היא נזק קטן וניתן לגילוי (שאילתה על pending_payment ישנות), לעומת "ביטול של משהו שלא קיים". הפתרון המלא: outbox (שיעור 4) — שורה בטבלה באותה טרנזקציה, ו־relay שמעביר לתור (‏E83). או cron כרשת ביטחון.
⚠️ טעויות נפוצות
  • "נעשה את ה־add ראשון, ואם הטרנזקציה נכשלת — נמחק את העבודה" — המחיקה יכולה להיכשל בדיוק כמו כל דבר אחר.

P26-E89 · מתי מבטלים את ה־cache של הקטלוג? 🧠 הבנה רמה 1

💡 רמז 1

מה מופיע ב־GET /products? שם, מחיר, מלאי…

💡 רמז 2

אם מבטלים לפני ה־COMMIT, בקשה שמגיעה בין השניים טוענת את הישן — לגרסה החדשה.

✅ פתרון
  1. כן.
  2. כן — המלאי ברשימה השתנה.
  3. לא — תשלום לא משנה מלאי או מחיר (המלאי ירד ביצירה).
  4. כן (‏cancelAndRestock עושה את זה).

P26-E90 · ‏WORKER=true בשלושה שרתים 🧠 הבנה רמה 2

💡 רמז 1

BullMQ מעביר עבודה מ־wait ל־active בסקריפט Lua.

💡 רמז 2

שליחת PDF של 3 שניות מאטה את מי?

✅ פתרון
  1. אחד. הלקיחה (wait ← active) אטומית, ורק worker אחד מקבל כל עבודה.
  2. at-least-once: worker שקרס באמצע (stalled), או retry אחרי כישלון שקרה אחרי שהמייל נכתב. בפרויקט: @@unique([kind, orderId]) ב־email_outbox ← ‏duplicate.
  3. (א) עבודות כבדות (PDF, תמונות) גוזלות CPU מאותו תהליך שעונה לבקשות HTTP — ה־API מאט. (ב) להגדיל בנפרד: 2 עותקי API ו־10 workers בזמן עומס של מיילים. וגם: deploy של ה־API לא עוצר עבודות באמצע.
⚠️ טעויות נפוצות
  • "צריך מנעול כדי שרק שרת אחד יריץ את ה־worker" — BullMQ כבר מחלק עבודות. מנעול רק יבטל את המקביליות.

P26-E91 · המפתח שבנוי מה־DTO 🧠 הבנה רמה 2

💡 רמז 1

‏keyPrefix: "shop:" ב־ioredis.

💡 רמז 2

ולידציה לפני cache — גם להגנה.

✅ פתרון
  1. shop: — ‏keyPrefix של ioredis (מ־REDIS_PREFIX). ‏cache:products: — הקבוצה, מהקוד. ‏0 — הגרסה (v:products). ה־JSON — ה־DTO אחרי ולידציה.
  2. ברירות המחדל של ה־DTO. כך ?q=V60 ו־?q=V60&page=1&limit=20 חולקות מפתח אחד (‏E45, E87).

⚠️ טעויות נפוצות

P26-E92 · חיבור Redis — או null 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

‏if (!url?.trim()) return null;

💡 רמז 2

הבודק קורא את redis.options — שם ioredis שומר את מה שהעברת.

✅ פתרון
// P26-E92: חיבור Redis — או null
import { Redis } from "ioredis";

export function createRedisOrNull(url: string | undefined, prefix: string): Redis | null {
  if (!url?.trim()) return null;
  return new Redis(url, { keyPrefix: `${prefix}:`, maxRetriesPerRequest: 2, enableOfflineQueue: false });
}

שתי ההגדרות האחרונות הן ההבדל בין "cache שנופל מהר" ל"בקשה שתלויה 20 ניסיונות": ‏enableOfflineQueue: false — כשאין חיבור, פקודה נכשלת מיד במקום לחכות בתור; ‏maxRetriesPerRequest: 2 — גם כשיש חיבור לא יציב, לא מנסים בלי סוף.

⚠️ טעויות נפוצות
  • להשתמש בחיבור הזה גם ל־BullMQ — ה־Worker דורש maxRetriesPerRequest: null, ו־BullMQ לא תומך ב־keyPrefix של ioredis. לתור — חיבור משלו (‏bullConnection).

P26-E93 · ‏getOrSet: ‏HIT, ‏MISS או OFF 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

שני try נפרדים: אחד לקריאה (שגיאה ← OFF), ואחד לכתיבה (שגיאה ← מתעלמים). ה־load() מחוץ לשניהם — כדי ששגיאה שלו תעלה.

💡 רמז 2

‏await redis.set(...).catch(() => {}).

✅ פתרון
// P26-E93: getOrSet — HIT, MISS או OFF
import type { Redis } from "ioredis";

type Status = "HIT" | "MISS" | "OFF";

export async function getOrSet<T>(redis: Redis | null, group: string, key: string, ttl: number, load: () => Promise<T>): Promise<{ value: T; status: Status }> {
  if (!redis) return { value: await load(), status: "OFF" };
  let fullKey: string;
  try {
    const version = (await redis.get(`v:${group}`)) ?? "0";
    fullKey = `cache:${group}:${version}:${key}`;
    const hit = await redis.get(fullKey);
    if (hit !== null) return { value: JSON.parse(hit) as T, status: "HIT" };
  } catch {
    return { value: await load(), status: "OFF" };
  }
  const value = await load();
  await redis.set(fullKey, JSON.stringify(value), "EX", ttl).catch(() => {});
  return { value, status: "MISS" };
}

export async function invalidate(redis: Redis | null, group: string) {
  await redis?.incr(`v:${group}`).catch(() => {});
}

שים לב איפה load() נמצא: אם הוא היה בתוך ה־try הראשון, שגיאה של המסד הייתה נתפסת כ"Redis נפל" — ו־load() היה רץ שוב, עם OFF. בפרויקט יש גם logger.warn בכל catch — בלי זה אף אחד לא יודע שה־cache כבוי.

⚠️ טעויות נפוצות
  • ‏try אחד סביב הכול — שגיאת מסד מריצה את load פעמיים.
  • await redis.set(...) בלי catch — Redis שנפל בין הקריאה לכתיבה מפיל בקשה שכבר יש לה תשובה.

P26-E94 · מפתח הקטלוג מתוך DTO עם zod 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

‏z.coerce.number().int().min(1).default(1) — ממיר מחרוזת למספר. ‏z.object (לא strict) מוריד שדות לא מוכרים.

💡 רמז 2

‏JSON.stringify שומר את סדר ההכנסה: בנה אובייקט חדש בסדר הרצוי — { ...(q ? { q } : {}), sort, page, limit }.

✅ פתרון
// P26-E94: מפתח הקטלוג מתוך DTO עם zod
import { z } from "zod";

const schema = z.object({
  q: z.string().trim().optional(),
  sort: z.enum(["newest", "price_asc", "price_desc"]).default("newest"),
  page: z.coerce.number().int().min(1).default(1),
  limit: z.coerce.number().int().min(1).max(50).default(20),
});

export function productsCacheKey(query: unknown): string {
  const r = schema.safeParse(query);
  if (!r.success) throw new Error("VALIDATION_ERROR");
  const { q, sort, page, limit } = r.data;
  return JSON.stringify({ ...(q ? { q } : {}), sort, page, limit });
}

שלוש בעיות של E45 נפתרות כאן בבת אחת: סדר הפרמטרים, ברירות מחדל, ופרמטרים שלא משפיעים (utm_source). ועוד אחת מ־E91: ‏limit=999999 לא מגיע לא למסד ולא ל־cache.

⚠️ טעויות נפוצות
  • z.number() בלי coerce — ‏"2" מה־query נדחה.
  • z.strictObject — ‏?utm_source=fb מחזיר 400 לכל מי שהגיע מפרסומת.

P26-E95 · גוף מייל האישור 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

‏(cents / 100).toFixed(2).

💡 רמז 2

‏[שלום ${name},, "", ...lines, "", סה״כ: ₪…].join("\n").

✅ פתרון
// P26-E95: גוף מייל האישור
type Order = { id: number; user: { name: string; email: string }; items: { name: string; quantity: number; priceCents: number }[]; totalCents: number };

const money = (cents: number) => `₪${(cents / 100).toFixed(2)}`;

export function confirmationEmail(order: Order) {
  const lines = order.items.map((i) => `${i.name} × ${i.quantity} — ${money(i.priceCents * i.quantity)}`);
  return {
    to: order.user.email,
    subject: `אישור הזמנה #${order.id}`,
    body: [`שלום ${order.user.name},`, "", ...lines, "", `סה״כ: ${money(order.totalCents)}`].join("\n"),
  };
}

פונקציה טהורה, בלי Prisma ובלי תור — לכן קל לבדוק אותה. ה־worker רק טוען את ההזמנה וקורא לה. הסה״כ נלקח מההזמנה (totalCents), לא מחושב מחדש: זה המחיר שהלקוח שילם.

⚠️ טעויות נפוצות
  • לחשב (priceCents / 100) * quantity — חלוקה לפני כפל מכניסה שגיאות של שברים עשרוניים. מכפילים באגורות, ומחלקים פעם אחת.

P26-E96 · ‏JobsService: עבודות עם jobId קבוע 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

‏removeOnComplete: 1000 — שומרים רק את 1000 האחרונות שהושלמו, כדי ש־Redis לא יתמלא.

💡 רמז 2

בדיקת השם — Set של השמות המותרים, ו־NAMES.has(name).

✅ פתרון
// P26-E96: JobsService — עבודות עם jobId קבוע
import { Queue, type ConnectionOptions } from "bullmq";

const NAMES = new Set(["order-confirmation", "expire-order"]);

export function createJobs(connection: ConnectionOptions, prefix: string) {
  const queue = new Queue("shop", { connection, prefix });
  return {
    queue,
    async add(name: string, orderId: number, delayMs = 0) {
      if (!NAMES.has(name)) throw new Error(`עבודה לא מוכרת: ${name}`);
      await queue.add(
        name,
        { orderId },
        { jobId: `${name}-${orderId}`, delay: delayMs, attempts: 5, backoff: { type: "exponential", delay: 1000 }, removeOnComplete: 1000, removeOnFail: 5000 },
      );
      return true;
    },
    close: () => queue.close(),
  };
}

‏removeOnComplete ו־removeOnFail הם תחזוקה: בלעדיהם כל עבודה שהושלמה נשארת ב־Redis לנצח. אבל שים לב לקשר ל־jobId: אחרי שעבודה נמחקה, אותו jobId כן ייצור עבודה חדשה. עוד סיבה שהצרכן חייב להיות idempotent בעצמו.

⚠️ טעויות נפוצות
  • jobId: ${name}:${orderId} — BullMQ לא מקבל נקודתיים ב־jobId מותאם.

P26-E97 · ביטול הזמנה שפגה — בתנאי, בטרנזקציה 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

‏const client = await pool.connect(), ואז BEGIN/COMMIT/ROLLBACK על client, ו־client.release() ב־finally (פרק 18).

💡 רמז 2
UPDATE products p SET stock = p.stock + i.quantity
FROM order_items i WHERE i.order_id = $1 AND i.product_id = p.id
✅ פתרון
// P26-E97: ביטול הזמנה שפגה — בתנאי, בטרנזקציה
import type pg from "pg";

export async function expireOrder(pool: pg.Pool, orderId: number): Promise<"expired" | "skipped"> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const r = await client.query("UPDATE orders SET status = 'cancelled' WHERE id = $1 AND status = 'pending_payment'", [orderId]);
    if (r.rowCount === 0) {
      await client.query("ROLLBACK");
      return "skipped";
    }
    await client.query(
      "UPDATE products p SET stock = p.stock + i.quantity FROM order_items i WHERE i.order_id = $1 AND i.product_id = p.id",
      [orderId],
    );
    await client.query("COMMIT");
    return "expired";
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}

כל הנכונות בשורה אחת: WHERE … AND status = 'pending_payment'. חמישה עותקים במקביל — PostgreSQL נועל את השורה לראשון, והשאר מחכים; כשהם ממשיכים, הסטטוס כבר cancelled, ו־rowCount הוא 0. בלי SELECT לפני, בלי מנעול Redis.

⚠️ טעויות נפוצות
  • SELECT status, בדיקה ב־JS, ואז UPDATE — חמישה עותקים רואים pending_payment, והמלאי חוזר חמש פעמים.
  • pool.query("BEGIN") ואז pool.query(...) — כל קריאה יכולה לקבל חיבור אחר מה־pool, וה־BEGIN לא חל עליהן.

P26-E98 · מייל פעם אחת: ‏UNIQUE ו־23505 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

‏to היא מילה שמורה ב־SQL — לכן במירכאות: "to".

💡 רמז 2
catch (e) {
  if ((e as { code?: string }).code === "23505") return "duplicate";
  throw e;
}

‏P2002 של Prisma הוא אותה שגיאה, עטופה.

✅ פתרון
// P26-E98: מייל פעם אחת — UNIQUE ו־23505
import type pg from "pg";

type Email = { kind: string; orderId: number; to: string; subject: string; body: string };

export async function recordEmailOnce(pool: pg.Pool, e: Email): Promise<"sent" | "duplicate"> {
  try {
    await pool.query('INSERT INTO email_outbox (kind, order_id, "to", subject, body) VALUES ($1, $2, $3, $4, $5)', [e.kind, e.orderId, e.to, e.subject, e.body]);
    return "sent";
  } catch (err) {
    if ((err as { code?: string }).code === "23505") return "duplicate";
    throw err;
  }
}

"נשלח" ו"נרשם שנשלח" הם אותה פעולה — ה־INSERT. אין רגע שבו אחד קרה והשני לא, ולכן זה שורד retries, workers במקביל, ו־Redis שהתאפס (‏E82).

⚠️ טעויות נפוצות

// P26-E99: ה־worker — עבודה ← פונקציה
type Deps = { emails: { sendOrderConfirmation(orderId: number): Promise<string> }; orders: { expire(orderId: number): Promise<string> } };

export async function handleJob(job: { name: string; data: { orderId: number } }, deps: Deps): Promise<string> {
  switch (job.name) {
    case "order-confirmation":
      return deps.emails.sendOrderConfirmation(job.data.orderId);
    case "expire-order":
      return deps.orders.expire(job.data.orderId);
    default:
      throw new Error(`עבודה לא מוכרת: ${job.name}`);
  }
}

זה ה־handle של JobsProcessor בפרויקט. כשה־worker הוא רק "ניתוב", כל הלוגיקה נשארת בשירותים — ואפשר לבדוק אותה בלי Redis ובלי BullMQ.

// P26-E104: config של Redis עם zod
import { z } from "zod";

const schema = z.object({
  REDIS_URL: z.string().regex(/^rediss?:\/\//, "חייב להתחיל ב־redis:// או rediss://").optional(),
  REDIS_PREFIX: z.string().regex(/^[a-z0-9_-]+$/i).default("shop"),
  PRODUCTS_CACHE_TTL_SECONDS: z.coerce.number().int().min(1).default(60),
  ORDER_PAYMENT_TIMEOUT_SECONDS: z.coerce.number().int().min(1).default(1800),
  WORKER: z.enum(["true", "false"]).default("true"),
});

export function loadRedisConfig(env: Record<string, string | undefined>) {
  const r = schema.safeParse(env);
  if (!r.success) throw new Error(`הגדרות לא תקינות — ${r.error.issues.map((i) => `${i.path.join(".")}: ${i.message}`).join("; ")}`);
  const e = r.data;
  return {
    ...(e.REDIS_URL ? { redis: { url: e.REDIS_URL, prefix: e.REDIS_PREFIX } } : {}),
    productsCacheTtlSeconds: e.PRODUCTS_CACHE_TTL_SECONDS,
    orderPaymentTimeoutSeconds: e.ORDER_PAYMENT_TIMEOUT_SECONDS,
    runWorker: e.WORKER === "true",
  };
}

// P26-E105: GET /products עם X-Cache וביטול
import express from "express";
import type { Redis } from "ioredis";

type Deps = { redis: Redis | null; loadProducts: (q: string) => Promise<unknown[]>; ttl?: number };

export function productsApp({ redis, loadProducts, ttl = 60 }: Deps) {
  const app = express();

  async function cached(q: string): Promise<{ value: unknown[]; status: string }> {
    if (!redis) return { value: await loadProducts(q), status: "OFF" };
    let key: string;
    try {
      const version = (await redis.get("v:products")) ?? "0";
      key = `cache:products:${version}:${q}`;
      const hit = await redis.get(key);
      if (hit !== null) return { value: JSON.parse(hit), status: "HIT" };
    } catch {
      return { value: await loadProducts(q), status: "OFF" };
    }
    const value = await loadProducts(q);
    await redis.set(key, JSON.stringify(value), "EX", ttl).catch(() => {});
    return { value, status: "MISS" };
  }

  app.get("/products", async (req, res) => {
    const q = typeof req.query.q === "string" ? req.query.q.trim().toLowerCase() : "";
    const { value, status } = await cached(q);
    res.set("X-Cache", status).json(value);
  });

  app.post("/products/invalidate", async (req, res) => {
    await redis?.incr("v:products").catch(() => {});
    res.status(204).end();
  });

  return app;
}

‏q מנורמל לפני שהוא נכנס למפתח (‏E45): V60, ‏v60 ו־" v60 " הם אותה בקשה — וגם loadProducts מקבל את אותו ערך, כך שהתשובה באמת זהה.

⚠️ טעויות נפוצות
  • לשמור את q המקורי במפתח ולהעביר ל־loadProducts את המנורמל — שלושה מפתחות לאותה תשובה.
  • להחזיר 500 כש־Redis זורק — ה־cache הוא אופטימיזציה.
