P26-E59 · איזה קוד בטוח עם שלושה שרתים? 🧠 הבנה רמה 1

💡 רמז 1

חפש את המבנה "קרא ← החלט ב־JS ← כתוב".

💡 רמז 2

כל פקודה אחת של Redis אטומית. שתי פקודות — לא.

✅ פתרון
  1. שבור — שני שרתים קוראים 1, שניהם כותבים 0, ונמכרו שתי יחידות. תיקון: סקריפט Lua כמו TAKE מהשיעור (או DECR ובדיקה שלא ירד מתחת ל־0 — ואז INCR חזרה).
  2. בטוח — פקודה אחת.
  3. שבור — שניהם רואים "אין", שניהם כותבים, ושניהם חושבים שהמנעול שלהם. תיקון: SET lock token PX 5000 NX — הבדיקה והכתיבה בפקודה אחת.
  4. בטוח — ‏MULTI מריץ את שתיהן ברצף, ושתיהן לא תלויות בערך שנקרא.
  5. שבור — פריט של שרת אחד נדרס. תיקון: list (RPUSH cart item) או hash (HINCRBY, ‏E37) — המבנה עצמו מאפשר עדכון בפקודה אחת.
⚠️ טעויות נפוצות
  • "נעטוף את 1 ב־MULTI" — אי אפשר: ההחלטה (n > 0) צריכה את הערך שנקרא, ו־MULTI לא מחזיר ערכים עד הסוף.

P26-E60 · כמה עוברות בגבול החלון? 🧠 הבנה רמה 2

💡 רמז 1

ב־12:01:00 מתחיל מפתח חדש.

💡 רמז 2

בלי NX כל INCR מאריך את חיי המפתח.

✅ פתרון
  1. 20 — עשר בחלון של 12:00, ועשר בחלון החדש של 12:01, בתוך פחות משנייה.
  2. 10 — ב־12:01:00.2 החלון הנע עדיין מכיל את עשר הבקשות מלפני 0.7 שניות.
  3. אף פעם, כל עוד הוא ממשיך: כל בקשה (גם נדחית) מאריכה את המפתח ל־60 שניות נוספות, והמונה לא מתאפס (E21).

⚠️ טעויות נפוצות
  • "חלון נע תמיד עדיף" — הוא יקר יותר, ומדויק יותר בדיוק במקרה שלעתים קרובות לא משנה.

P26-E61 · המנעול של A, ה־DEL של B 🧠 הבנה רמה 2

💡 רמז 1

‏DEL לא יודע של מי המנעול.

💡 רמז 2

בין GET ל־DEL המנעול יכול לפוג ולעבור יד.

✅ פתרון
  1. t=12: ‏A מוחק את המנעול של B. t=13: ‏C לוקח — B ו־C עובדים במקביל.
  2. כמעט תמיד בסדר — אבל אם המנעול פג ו־B לקח אותו בדיוק בין ה־GET (שראה את ה־token של A) ל־DEL, אותו באג. נדיר — ולכן הכי קשה למצוא.
  3. תקין: הסקריפט בודק ומוחק בפקודה אחת. ב־t=12 ה־token לא של A ← מחזיר 0, ו־B ממשיך להחזיק.
  4. בין 11 ל־12, A ו־B עובדים במקביל — A לא יודע שהמנעול שלו פג (GC, רשת איטית). מנעול עם תוקף מבטיח "כמעט תמיד אחד", לא "תמיד אחד". מה שחייב להיות נכון — המסד אוכף (UNIQUE, ‏WHERE stock >= qty, ‏FOR UPDATE).
⚠️ טעויות נפוצות
  • "נגדיל את ה־TTL לשעה" — שרת שקרס מחזיק את המנעול שעה, והבעיה רק נדירה יותר.

P26-E62 · מה Lua מחזיר ל־Node 🧠 הבנה רמה 2

Redis ממיר מספר של Lua ל־integer בתשובה.

💡 רמז 2

‏GET על מפתח שלא קיים מחזיר ל־Lua את false.

✅ פתרון
import { Redis } from "ioredis";
const r = new Redis(process.env.REDIS_URL ?? "redis://localhost:6379", { keyPrefix: "e62:" });
console.log(await r.eval("return 3.7", 0));
console.log(await r.eval("return {1, 2, 'three', 4.5}", 0));
console.log(await r.eval("return redis.call('GET', KEYS[1])", 1, "missing"));

console.log(await r.eval("return tonumber(ARGV[1]) + 1", 0, "41"));

  1. נחתכו לשלם (3 ו־4) — Redis הופך מספר של Lua ל־integer. ב־token bucket (‏E25) זה מאבד חלקי טוקנים בשקט.
  2. מחזירים מחרוזת: return tostring(x), ו־Number(...) ב־Node.
  3. ioredis הוסיף את ה־keyPrefix לכל מה שהועבר כ־KEYS. מפתח שכתוב בתוך הסקריפט (redis.call('GET', 'seats')) לא מקבל קידומת — הסקריפט ניגש למפתח של מישהו אחר. לכן כל מפתח עובר ב־KEYS.
⚠️ טעויות נפוצות
  • להחזיר nil באמצע טבלה — Lua חותך את המערך בנקודה הזו.

P26-E63 · ‏pub/sub: מי שמע? 🧠 הבנה רמה 2

💡 רמז 1

‏PUBLISH מחזיר כמה מנויים קיבלו.

💡 רמז 2

אין שמירה: מי שלא היה מנוי ברגע ה־publish — פספס.

✅ פתרון
import { Redis } from "ioredis";
const pub = new Redis(process.env.REDIS_URL ?? "redis://localhost:6379");
const sub = pub.duplicate();
console.log("before:", await pub.publish("e63:news", "first"));
await sub.subscribe("e63:news");

console.log("after:", await pub.publish("e63:news", "second"));
await new Promise((r) => setTimeout(r, 50));
console.log("got:", got);
try {
  await sub.get("x");
} catch (e) {
  console.log((e as Error).message);
}
await sub.quit();
await pub.quit();
before: 0
after: 1
got: [ 'e63:news second' ]
Connection in subscriber mode, only subscriber commands may be used
  1. כמה מנויים קיבלו את ההודעה ברגע הזה: 0 ואז 1.
  2. נעלם. אף אחד לא היה מנוי, ו־Redis לא שומר.
  3. חיבור במצב subscribe מקבל רק פקודות של מנויים. מחזיקים שני חיבורים: אחד לפקודות, ואחד (duplicate()) למנויים — כמו ב־E19 וב־E30.

⚠️ טעויות נפוצות
  • להסיק מ־publish שהחזיר 1 ש"ההודעה טופלה" — היא נמסרה למנוי; אם הוא קרס באמצע הטיפול, היא אבדה.

P26-E09 · הגבלת קצב משותפת 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

מספר החלון: Math.floor(now / 1000 / windowSeconds).

💡 רמז 2

EXPIRE key seconds NX — רק אם אין תוקף (Redis 7+).

✅ פתרון
// P26-E09
import type { Redis } from "ioredis";

// fixed window ב־Redis: מונה לכל (לקוח, חלון). משותף לכל השרתים — בניגוד ל־Map בזיכרון (פרק 24)
export async function hit(redis: Redis, clientId: string, { limit, windowSeconds, now = Date.now() }: { limit: number; windowSeconds: number; now?: number }) {
  const window = Math.floor(now / 1000 / windowSeconds);
  const key = `rl:${clientId}:${window}`;
  // INCR אטומי; EXPIRE רק כשהמפתח נוצר עכשיו (NX) — המונה מת לבד בסוף החלון
  const [[, count]] = (await redis.multi().incr(key).expire(key, windowSeconds, "NX").exec()) as [[null, number], [null, number]];
  const resetSeconds = (window + 1) * windowSeconds - Math.floor(now / 1000);
  return { allowed: count <= limit, remaining: Math.max(0, limit - count), resetSeconds };
}

זו בדיוק ההגבלה מפרק 24 — אבל משותפת: עם שלושה שרתים, ה־Map בזיכרון סופר לכל שרת לבד, והמגבלה האמיתית פי 3.

⚠️ טעויות נפוצות
  • EXPIRE בלי NX — כל בקשה מאריכה את החלון, ומי שממשיך לשלוח לא משתחרר (E21).

P26-E12 · מנעול מבוזר 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

SET lock:name token PX ttl NX — "רק אם לא קיים", עם תוקף, בפקודה אחת.

💡 רמז 2

שחרור: "אם הערך הוא ה־token שלי — מחק" חייב להיות אטומי. Lua: redis.eval(script, 1, key, token).

✅ פתרון
// P26-E12
import { randomUUID } from "node:crypto";
import type { Redis } from "ioredis";

// מחיקה רק אם הערך הוא ה־token שלי — בפקודה אחת (Lua רץ ב־Redis באופן אטומי)
const RELEASE = `if redis.call("GET", KEYS[1]) == ARGV[1] then return redis.call("DEL", KEYS[1]) else return 0 end`;

export async function acquire(redis: Redis, name: string, ttlMs: number): Promise<string | null> {
  const token = randomUUID();
  // SET NX PX: "רק אם לא קיים" ועם תוקף — באותה פקודה. אם התהליך מת, המנעול משתחרר לבד
  const ok = await redis.set(`lock:${name}`, token, "PX", ttlMs, "NX");
  return ok === "OK" ? token : null;
}

export async function release(redis: Redis, name: string, token: string): Promise<boolean> {
  return (await redis.eval(RELEASE, 1, `lock:${name}`, token)) === 1;
}

export async function withLock<T>(redis: Redis, name: string, ttlMs: number, fn: () => Promise<T>): Promise<T | null> {
  const token = await acquire(redis, name, ttlMs);
  if (!token) return null; // מישהו אחר מחזיק — לא מחכים (לפי הצורך: לנסות שוב אחר כך)
  try {
    return await fn();
  } finally {
    await release(redis, name, token);
  }
}

מתי צריך? "רק שרת אחד מריץ את הדוח הלילי", "רק אחד מרענן את ה־cache" (E13). ומתי לא: נכונות של כסף ומלאי — שם המסד מתאם (פרק 18, פרויקט 3). מנעול עם תוקף יכול לפוג באמצע עבודה איטית.

⚠️ טעויות נפוצות
  • SETNX ואז EXPIRE — שתי פקודות; תהליך שמת ביניהן משאיר מנעול לנצח (E22).

P26-E15 · חלון נע ב־sorted set 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

ZREMRANGEBYSCORE key -inf (now − windowMs), ZCARD, ZRANGE key 0 0 WITHSCORES (הוותיק).

💡 רמז 2

שתי בקשות באותה מילישנייה: ZADD key now now פעמיים = איבר אחד (אותו member). member ייחודי.

✅ פתרון
// P26-E15
import { randomUUID } from "node:crypto";
import type { Redis } from "ioredis";

// sliding window ב־sorted set: כל בקשה = איבר עם score = זמן. סופרים רק את ה־windowMs האחרונות
export async function slidingHit(redis: Redis, clientId: string, { limit, windowMs, now = Date.now() }: { limit: number; windowMs: number; now?: number }) {
  const key = `sw:${clientId}`;
  const results = await redis
    .multi()
    .zremrangebyscore(key, "-inf", now - windowMs) // מנקים את מה שיצא מהחלון
    .zcard(key)
    .zrange(key, 0, 0, "WITHSCORES")
    .exec();
  const count = Number(results![1][1]);
  const oldest = results![2][1] as string[];
  if (count >= limit) {
    // נדחה — לא נספר (פרק 24). Retry-After: עד שהוותיק יוצא מהחלון
    const retryAfterMs = Number(oldest[1]) + windowMs - now;
    return { allowed: false, remaining: 0, retryAfterSeconds: Math.max(1, Math.ceil(retryAfterMs / 1000)) };
  }
  await redis.multi().zadd(key, now, `${now}-${randomUUID()}`).pexpire(key, windowMs).exec();
  return { allowed: true, remaining: limit - count - 1, retryAfterSeconds: 0 };
}

מגבלה של הגרסה הזו: הבדיקה וההוספה הן שתי פקודות נפרדות — תחת עומס חזק, שתי בקשות יכולות לעבור את הבדיקה יחד. לאטומיות מלאה — סקריפט Lua (E25).

⚠️ טעויות נפוצות
  • member = now — בקשות באותה מילישנייה נספרות כאחת.

P26-E19 · cache בזיכרון + pub/sub 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

await subscriber.subscribe(channel), subscriber.on("message", (ch, msg) => …), redis.publish(channel, key).

💡 רמז 2

pub/sub לא שומר הודעות: מי שלא היה מחובר באותו רגע — לא יקבל. לכן גם ל־L1 כדאי TTL קצר.

✅ פתרון
// P26-E19
import type { Redis } from "ioredis";

// cache בזיכרון של התהליך (L1, הכי מהיר) — אבל עם כמה שרתים, כל אחד מחזיק עותק משלו.
// כששרת אחד משנה, הוא מפרסם ב־pub/sub, וכל השרתים מוחקים את העותק שלהם
export async function createL1Cache(redis: Redis, subscriber: Redis, channel = "cache-invalidate") {
  const local = new Map<string, unknown>();
  await subscriber.subscribe(channel);
  subscriber.on("message", (ch: string, key: string) => {
    if (ch === channel) local.delete(key);
  });
  return {
    async get<T>(key: string, load: () => Promise<T>): Promise<T> {
      if (local.has(key)) return local.get(key) as T;
      const value = await load();
      local.set(key, value);
      return value;
    },
    // מקומית מיד, ולכל השאר דרך Redis
    async invalidate(key: string) {
      local.delete(key);
      await redis.publish(channel, key);
    },
    size: () => local.size,
  };
}
⚠️ טעויות נפוצות
  • להשתמש באותו חיבור ל־subscribe ול־GET — ioredis זורק: "Connection in subscriber mode".

P26-E21 · הגבלת קצב עם שלוש תקלות 🤖 💻 כתיבת קוד 🤖 רמה 4

💡 רמז 1

מה במפתח? ו־GET ואז SET — מה קורה כששתי בקשות עושות את זה יחד?

💡 רמז 2

EXPIRE בכל בקשה — מתי החלון נגמר?

✅ פתרון
// P26-E21
import type { Redis } from "ioredis";

export async function allow(redis: Redis, clientId: string, limit: number, windowSeconds: number): Promise<boolean> {
  // תקלה 1: מפתח אחד לכולם — הלקוח העשירי חוסם את כל השאר. מפתח לכל לקוח
  const key = `ratelimit:${clientId}`;
  // תקלה 3: GET ואז SET — שתי בקשות קוראות 4 ושתיהן כותבות 5. INCR אטומי
  // תקלה 2: EXPIRE בכל בקשה מאריך את החלון שוב ושוב — מי שממשיך לשלוח לא משתחרר. NX: רק כשאין תוקף

P26-E22 · מנעול עם שלוש תקלות 🤖 💻 כתיבת קוד 🤖 רמה 4

💡 רמז 1

איפה התוקף? ומה הערך שנשמר?

💡 רמז 2

release של A, אחרי שהתוקף שלו נגמר ו־B לקח — מה הוא מוחק?

✅ פתרון
// P26-E22
import { randomUUID } from "node:crypto";
import type { Redis } from "ioredis";

const RELEASE = `if redis.call("GET", KEYS[1]) == ARGV[1] then return redis.call("DEL", KEYS[1]) else return 0 end`;

export async function acquire(redis: Redis, name: string, ttlMs: number): Promise<string | null> {
  // תקלה 1: בלי תוקף — שרת שקרס מחזיק את המנעול לנצח. SET … PX … NX: הכול בפקודה אחת

local capacity = tonumber(ARGV[1])

  allowed = 1

return { allowed, math.floor(tokens), retry }
`;

  return { allowed: allowed === 1, remaining, retryAfterSeconds };
}

P26-E33 · TypedEmitter: אירועים עם טיפוסים 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

החתימה שעושה את כל העבודה: on<K extends keyof Events>(event: K, listener: (payload: Events[K]) => void). ‏K הוא שם אירוע מסוים, ו־Events[K] הוא ה־payload שלו. אותו דבר ב־emit. האחסון: #listeners = new Map<keyof Events, Set<(payload: any) => void>>().

💡 רמז 2

once: עוטפים את המאזין בפונקציה שקודם קוראת ל־this.off(event, wrapper) ורק אז ל־listener, ורושמים את העטיפה. ב־emit עוברים על עותק: [...set]. מחיקה מ־Set תוך כדי מעבר עליו עלולה לדלג על איבר.

✅ פתרון
// P26-E33 — TypedEmitter: אירועים עם טיפוסים
type Listener<T> = (payload: T) => void;

export class TypedEmitter<Events extends Record<string, unknown>> {
  #listeners = new Map<keyof Events, Set<Listener<any>>>();

  on<K extends keyof Events>(event: K, listener: Listener<Events[K]>): () => void {
    let set = this.#listeners.get(event);
    if (!set) {
      set = new Set();
      this.#listeners.set(event, set);
    }
    set.add(listener);
    return () => this.off(event, listener);
  }

  off<K extends keyof Events>(event: K, listener: Listener<Events[K]>): void {
    const set = this.#listeners.get(event);
    if (!set) return;
    set.delete(listener);
    if (set.size === 0) this.#listeners.delete(event);
  }

  once<K extends keyof Events>(event: K, listener: Listener<Events[K]>): () => void {
    const wrapper: Listener<Events[K]> = (payload) => {
      this.off(event, wrapper);
      listener(payload);
    };
    return this.on(event, wrapper);
  }

  emit<K extends keyof Events>(event: K, payload: Events[K]): number {
    const set = this.#listeners.get(event);
    if (!set) return 0;
    const listeners = [...set];
    for (const listener of listeners) listener(payload);
    return listeners.length;
  }

  listenerCount(event: keyof Events): number {
    return this.#listeners.get(event)?.size ?? 0;
  }
}

// P26-E69: middleware של הגבלת קצב, משותף לשני שרתים
import type express from "express";
import type { Redis } from "ioredis";

type Opts = { limit: number; windowSeconds: number; keyOf?: (req: express.Request) => string; now?: () => number };

export function rateLimit(redis: Redis, { limit, windowSeconds, keyOf = (req) => req.ip ?? "unknown", now = Date.now }: Opts): express.RequestHandler {
  return async (req, res, next) => {
    const t = now();
    const window = Math.floor(t / 1000 / windowSeconds);
    const key = `rl:${keyOf(req)}:${window}`;
    const r = await redis.multi().incr(key).expire(key, windowSeconds, "NX").exec();
    const count = Number(r![0][1]);
    res.set("X-RateLimit-Limit", String(limit));
    res.set("X-RateLimit-Remaining", String(Math.max(0, limit - count)));
    if (count > limit) {
      const end = (window + 1) * windowSeconds * 1000;
      res.set("Retry-After", String(Math.ceil((end - t) / 1000)));
      return res.status(429).json({ error: "יותר מדי בקשות" });
    }
    next();
  };
}

‏now כפרמטר הוא אותו "שעון מוזרק" מפרק 24: בבדיקה הזמן קבוע, ואין סיכוי שהבדיקה תיפול כי עברה בדיוק בגבול של דקה.

⚠️ טעויות נפוצות
  • Retry-After = ‏windowSeconds קבוע — לקוח שנחסם שנייה לפני סוף החלון מחכה דקה שלמה.
  • Math.floor ב־Retry-After — יוצא 0 בשנייה האחרונה, והלקוח מנסה מיד.

export async function withLockRetry<T>(redis: Redis, name: string, ttlMs: number, fn: () => Promise<T>, opts: { retries?: number; delayMs?: number } = {}): Promise<T> {
  const { retries = 10, delayMs = 50 } = opts;
  const key = `lock:${name}`;
  const token = randomUUID();
  for (let attempt = 0; attempt <= retries; attempt++) {
    if ((await redis.set(key, token, "PX", ttlMs, "NX")) === "OK") {
      try {
        return await fn();
      } finally {
        await redis.eval(RELEASE, 1, key, token);
      }
    }
    if (attempt < retries) await sleep(delayMs);
  }
  throw new Error("LOCKED");
}

‏return await fn() בתוך try, ולא return fn(): בלי await ה־finally רץ מיד — לפני ש־fn סיים — והמנעול משתחרר באמצע העבודה.

⚠️ טעויות נפוצות
  • return fn() בלי await — המנעול משתחרר לפני שהעבודה נגמרת, והבודק רואה שתי עבודות במקביל.
  • לולאה בלי sleep — מאות פקודות בשנייה ל־Redis מכל מחכה.
