P26-E04 · בתור או עכשיו? 🧠 הבנה רמה 1

💡 רמז 1

שאלה: האם התשובה ללקוח תלויה בתוצאה?

💡 רמז 2

worker שסיים את העבודה ונפל רגע לפני שדיווח "סיימתי" — מה התור יעשה?

✅ פתרון
  1. עכשיו. התשובה ("הוזמן" / "אזל") תלויה בזה, וזה חלק מהטרנזקציה.
  2. תור. הלקוח לא צריך לחכות ל־SMTP, ו־SMTP שלא זמין לרגע לא צריך להכשיל הזמנה. נכשל ← retry עם backoff.
  3. תור. מחזירים מיד "בהכנה", וכשמוכן — מודיעים (או הלקוח בודק).
  4. תלוי. בפרויקט — עכשיו: הלקוח מחכה לתשובה "שולם / נדחה". במערכות גדולות — הספק עונה מאוחר יותר ב־webhook, וזה כבר אסינכרוני.
  5. תור עם delay (BullMQ: delay). לא cron שסורק כל דקה את כל ההזמנות.
  6. תור. עקביות "בסופו של דבר" מספיקה: חיפוש שמתעדכן אחרי שנייה זה בסדר.

לא נכון. תורים מבטיחים "לפחות פעם אחת" (at-least-once). worker שנפל אחרי העבודה ולפני ה־ack ← העבודה תרוץ שוב. לכן כל צרכן חייב להיות idempotent: jobId קבוע להוספה, ובצד הביצוע — "כבר טופל?" (E18, ו־UNIQUE (kind, order_id) בפרויקט).

⚠️ טעויות נפוצות
  • לשלוח מייל מתוך הטרנזקציה — ואז הטרנזקציה נכשלת (ROLLBACK), והמייל "ההזמנה התקבלה" כבר יצא.

P26-E71 · ‏backoff: מתי כל ניסיון? 🧠 הבנה רמה 2

💡 רמז 1

1, 2, 4, 8 שניות.

💡 רמז 2

סכום ההמתנות: 1+2+4+…

✅ פתרון
  1. ניסיון 2 ב־t=1s, ‏3 ב־t=3s (עוד 2), ‏4 ב־t=7s (עוד 4), ‏5 ב־t=15s (עוד 8).
  2. מיד אחרי שהחמישי נכשל — t≈15s.
  3. ב־1, 2, 3, 4 שניות; ‏failed ב־t≈4s.
  4. אף אחת — שתיהן מוותרות אחרי פחות מ־20 שניות. עם exponential של שנייה, סכום ההמתנות אחרי n ניסיונות חוזרים הוא 2^n−1 שניות. כדי לעבור 600 שניות צריך 2^n−1 ≥ 600 ← ‏n=10, כלומר attempts: 11 (הניסיון האחרון אחרי ~17 דקות). זה הכוח של exponential: מעט ניסיונות, טווח זמן גדול.
⚠️ טעויות נפוצות
  • לספור את הניסיון הראשון כ"ניסיון חוזר" — attempts הוא סך הכול, כולל הראשון.

P26-E72 · ‏worker קרס — איפה בדיוק? 🧠 הבנה רמה 2

💡 רמז 1

BullMQ מזהה worker שנעלם (stalled) ומחזיר את העבודה לתור.

💡 רמז 2

מה גרוע יותר ללקוח: שני מיילים, או אף אחד?

✅ פתרון
  1. העבודה stalled ← חוזרת לתור ← worker אחר שולח. הלקוח מקבל מייל אחד.
  2. המייל נשלח, אבל העבודה לא סומנה ← חוזרת ← נשלח שוב. שני מיילים.
  3. סומן הושלם ולא נשלח ← אף אחד לא ינסה שוב. אפס מיילים, בלי שום סימן.

(א)(ב)(ג) הוא at-least-once, ו־(א)(ג)(ב) הוא at-most-once. תורים בוחרים at-least-once כי את הכפילות אפשר לנטרל בצרכן (idempotent — ‏UNIQUE, ‏SET NX), ואת ההיעלמות אי אפשר לגלות.

⚠️ טעויות נפוצות
  • "נבחר exactly-once" — אין דבר כזה מקצה לקצה עם מערכת חיצונית (שרת מייל). יש at-least-once + צרכן idempotent, שנראה מבחוץ כמו "פעם אחת".

P26-E73 · איזה ‏jobId? 🧠 הבנה רמה 1

💡 רמז 1

ה־jobId צריך לתאר "מה העבודה", לא "מתי ביקשו אותה".

💡 רמז 2

אצל BullMQ אי אפשר להשתמש בנקודתיים בתוך jobId מותאם — משתמשים במקף.

✅ פתרון
  1. confirm-<orderId>.
  2. resize-<uploadId> — כל העלאה מקבלת מזהה; העלאה חוזרת של אותו קובץ היא העלאה חדשה.
  3. daily-report-2026-11-08 — התאריך הוא חלק מהזהות.
  4. remind-<userId>-2026-11-08.
  5. webhook-<orderId>-<status> — שינוי ל־shipped ושינוי ל־paid הם שני אירועים; אותו שינוי פעמיים — אחד.

וזכור: jobId מונע כפילות רק כל עוד העבודה הקודמת עדיין קיימת בתור (כולל completed שלא נמחקה). הוא לא תחליף לצרכן idempotent.

⚠️ טעויות נפוצות
  • jobId: randomUUID() — זהה לבלי jobId.
  • jobId: String(Date.now()) — שתי לחיצות באותה מילישנייה ייחשבו אחת, ושתיים שונות ייחשבו שתיים.

P26-E74 · לבטל את העבודה, או לבדוק כשהיא רצה? 🧠 הבנה רמה 2

💡 רמז 1

מה אם remove נכשל? ומה אם העבודה כבר active בדיוק ברגע התשלום?

💡 רמז 2

UPDATE … WHERE status = 'pending_payment'.

✅ פתרון
  1. (א) ה־remove נכשל (Redis לא זמין לרגע, השרת קרס אחרי ה־UPDATE) — העבודה רצה ומבטלת. (ב) העבודה כבר רצה (active) כשהתשלום הגיע — אי אפשר למחוק עבודה פעילה, והיא מבטלת. ועוד: retry של עבודה שנכשלה באמצע.
  2. היא מבטלת בתנאי: UPDATE עם AND status = 'pending_payment' בתוך ה־WHERE. שולם? אפס שורות ← skipped. התנאי נבדק במסד, ברגע הביצוע — לא משנה מתי או כמה פעמים.
  3. חיסכון: פחות עבודות מיותרות בתור. אופטימיזציה — בתנאי שהנכונות עדיין בבדיקה בזמן הריצה.
⚠️ טעויות נפוצות
  • "נבדוק את הסטטוס ב־SELECT, ואז UPDATE" — בין השניים התשלום יכול להיכנס. התנאי בתוך ה־UPDATE (פרק 18).

P26-E75 · תור עם delay, או cron? 🧠 הבנה רמה 1

💡 רמז 1

אירוע לכל ישות מול סריקה תקופתית.

💡 רמז 2

"תור לזמן אמת, cron כרשת ביטחון".

✅ פתרון
  1. שניהם: תור — מדויק לשנייה ולא סורק טבלה; cron כל כמה דקות — "בטל כל מה שב־pending_payment יותר מ־30 דקות" — תופס את מה שהתור איבד.
  2. cron (או repeatable job של BullMQ, שהוא cron בתוך התור) — זה זמן ביום, לא "X אחרי אירוע".
  3. cron — ניקוי תקופתי, אין אירוע לכל session.
  4. תור עם delay, ו־jobId לכל משתמש. העבודה בודקת כשהיא רצה: "האם העגלה עדיין לא נקנתה?".

Redis התאפס ← כל העבודות המתוזמנות נעלמו. לכן כל דבר חשוב שתלוי בהן צריך רשת ביטחון שמבוססת על המסד (cron שסורק לפי סטטוס וזמן).

⚠️ טעויות נפוצות
  • להחזיק setTimeout של 30 דקות בתהליך — כל deploy מוחק את כולם.

P26-E16 · תור מיילים 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

queue.add(name, data, { jobId, attempts, backoff: { type: "exponential", delay } }).

💡 רמז 2

new Worker(name, async (job) => …, { connection, prefix }) — אותו name ואותו prefix כמו ה־Queue.

✅ פתרון
// P26-E16
import { Queue, Worker, type ConnectionOptions } from "bullmq";

export interface Email {
  to: string;
  subject: string;
}

// יצרן: מוסיף עבודה. jobId מהעסק (לא אקראי): אותו מייל פעמיים = עבודה אחת
export function createEmailQueue(connection: ConnectionOptions, prefix: string) {
  const queue = new Queue<Email>("emails", { connection, prefix });
  return {
    queue,
    send: (id: string, email: Email) =>
      queue.add("email", email, { jobId: id, attempts: 4, backoff: { type: "exponential", delay: 50 }, removeOnComplete: 100 }),
    close: () => queue.close(),
  };
}

// צרכן: מריץ את deliver; זריקה ← BullMQ ינסה שוב (attempts), עם backoff
export function startEmailWorker(connection: ConnectionOptions, prefix: string, deliver: (email: Email) => Promise<void>) {
  return new Worker<Email>("emails", async (job) => deliver(job.data), { connection, prefix, concurrency: 5 });
}

הבודק: מייל אחד שנכשל פעמיים ומצליח בשלישית, אותו מייל שנשלח פעמיים, וכתובת שתמיד נכשלת — שמגיעה בסוף ל־failed ולא מנסה לנצח.

⚠️ טעויות נפוצות
  • Worker בלי maxRetriesPerRequest: null בחיבור — BullMQ מזהיר, וחיבור שנקטע מפיל את ה־worker.

P26-E17 · עבודה מתוזמנת וביטול 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

queue.getJob(id), job.isDelayed(), job.remove().

💡 רמז 2

בפרויקט אין cancel — ה־worker פשוט בודק את המצב כשהעבודה רצה ("עדיין לא שולמה?"). שתי גישות; מה היתרון של כל אחת?

✅ פתרון
// P26-E17
import { Queue, Worker, type ConnectionOptions } from "bullmq";

// תזכורת מתוזמנת: עבודה עם delay. jobId לפי ההזמנה — כדי שאפשר יהיה לבטל אותה כשהלקוח שילם
export function createReminders(connection: ConnectionOptions, prefix: string) {
  const queue = new Queue<{ orderId: number }>("reminders", { connection, prefix });
  return {
    queue,
    schedule: (orderId: number, delayMs: number) => queue.add("remind", { orderId }, { jobId: `remind-${orderId}`, delay: delayMs }),
    // שולם לפני הזמן — מבטלים. מחזיר true אם הייתה עבודה ממתינה שבוטלה
    async cancel(orderId: number) {
      const job = await queue.getJob(`remind-${orderId}`);
      if (!job || !(await job.isDelayed())) return false;
      await job.remove();
      return true;
    },
    close: () => queue.close(),
  };
}

export function startReminderWorker(connection: ConnectionOptions, prefix: string, remind: (orderId: number) => Promise<void>) {
  return new Worker<{ orderId: number }>("reminders", (job) => remind(job.data.orderId), { connection, prefix });
}

בפרויקט בחרנו "לבדוק כשמגיע הזמן" ולא "לבטל כששולם": אם הביטול נכשל (Redis לא זמין לרגע) — העבודה תרוץ, ותבטל הזמנה ששולמה. בדיקה בזמן הריצה נכונה תמיד; ביטול הוא רק חיסכון.

⚠️ טעויות נפוצות
  • cron כל דקה שסורק את כל ההזמנות "האם עברו 30 דקות" — עובד, אבל עמוס ולא מדויק.

P26-E18 · צרכן idempotent 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

redis.set(key, "1", "EX", ttl, "NX") מחזיר "OK" רק לראשון.

💡 רמז 2

למה TTL? כדי שהסימונים לא יצטברו לנצח. (כמה זמן? יותר מהזמן שבו הודעה יכולה להגיע שוב.)

✅ פתרון
// P26-E18
import type { Redis } from "ioredis";

// "צרכן idempotent": תורים מבטיחים "לפחות פעם אחת" — לא "בדיוק פעם אחת". retry, worker שנפל אחרי העבודה ולפני ack…
// לכן כל הודעה מסומנת כ"טופלה". SET NX: רק הראשון מצליח לסמן. נכשל באמצע? מוחקים את הסימון — שינסו שוב
export async function processOnce<T>(redis: Redis, messageId: string, ttlSeconds: number, handler: () => Promise<T>): Promise<{ processed: boolean; result?: T }> {
  const key = `processed:${messageId}`;
  if ((await redis.set(key, "1", "EX", ttlSeconds, "NX")) !== "OK") return { processed: false };
  try {
    return { processed: true, result: await handler() };
  } catch (err) {
    await redis.del(key);
    throw err;
  }
}

יש עדינות: אם ה־handler הצליח, אבל התהליך מת לפני שהחזיר — הסימון קיים, וההודעה לא תטופל שוב. מצוין לחיוב; פחות למשהו שבאמת לא קרה. הפתרון החזק יותר — כמו בפרויקט: הייחודיות בתוך אותה פעולה (UNIQUE בטבלת המיילים), כך ש"טופל" ו"קרה" הם אותו דבר.

⚠️ טעויות נפוצות
  • לסמן "טופל" רק אחרי ה־handler — שתי העתקות שמגיעות יחד יריצו שתיהן.

P26-E23 · תור עם שלוש תקלות 🤖 💻 כתיבת קוד 🤖 רמה 4

💡 רמז 1

מה עושה ה־try/catch ב־worker מבחינת BullMQ?

💡 רמז 2

jobId: randomUUID() — מה זה עושה לכפילויות?

✅ פתרון
// P26-E23
import { Queue, Worker, type ConnectionOptions } from "bullmq";

export function createConfirmations(connection: ConnectionOptions, prefix: string, deliver: (orderId: number) => Promise<void>) {
  const queue = new Queue<{ orderId: number }>("confirmations", { connection, prefix });
  // תקלה 1: try/catch שבולע את השגיאה — מבחינת BullMQ העבודה "הצליחה", ואין retry. נותנים לשגיאה לעלות
  const worker = new Worker<{ orderId: number }>("confirmations", (job) => deliver(job.data.orderId), { connection, prefix });
  return {
    // תקלה 2: jobId אקראי — כל קריאה היא עבודה חדשה (תשלום שנשלח פעמיים ← שני מיילים). מזהה עסקי
    // תקלה 3: בלי attempts — ניסיון אחד בלבד
    send: (orderId: number) => queue.add("confirm", { orderId }, { jobId: `confirm-${orderId}`, attempts: 5, backoff: { type: "exponential", delay: 50 } }),
    close: async () => {
      await worker.close();
      await queue.close();
    },
  };
}
⚠️ טעויות נפוצות
  • try/catch שבולע — "שקט" בלוגים, ומיילים שנעלמים בלי זכר. עדיף שעבודה תיכשל בקול ותגיע ל־failed.

P26-E76 · לוח זמנים של backoff 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

‏Array.from({ length: attempts - 1 }, (_, i) => …) — ‏i מתחיל מ־0, אז 2 ** i.

💡 רמז 2

‏reduce((s, x) => s + x, 0).

✅ פתרון
// P26-E76: לוח זמנים של backoff
type Kind = "fixed" | "exponential";

export function backoffDelays(attempts: number, delay: number, type: Kind): number[] {
  if (!Number.isInteger(attempts) || attempts < 1) throw new RangeError("attempts חייב להיות שלם חיובי");
  if (!(delay >= 0)) throw new RangeError("delay לא יכול להיות שלילי");
  return Array.from({ length: attempts - 1 }, (_, i) => (type === "fixed" ? delay : delay * 2 ** i));
}

export function giveUpAfter(attempts: number, delay: number, type: Kind): number {
  return backoffDelays(attempts, delay, type).reduce((s, x) => s + x, 0);
}

כדאי לחשב את זה לפני שבוחרים מספרים: giveUpAfter(5, 200, "exponential") הוא 3 שניות — מעט מדי לשרת מייל שנופל לדקה.

⚠️ טעויות נפוצות
  • attempts מספרים במקום attempts − 1 — הניסיון הראשון לא מחכה.
  • delay * 2 ** (i + 1) — ההמתנה הראשונה כפולה.

💡 רמז 2

✅ פתרון
// P26-E77: worker עם התקדמות
import { Worker, type ConnectionOptions } from "bullmq";

export function startImportWorker(connection: ConnectionOptions, prefix: string, handleItem: (item: string) => Promise<void>) {
  return new Worker(
    "imports",
    async (job) => {
      const items: string[] = job.data.items;
      if (items.length === 0) {
        await job.updateProgress(100);
        return { processed: 0 };
      }
      for (let i = 0; i < items.length; i++) {
        await handleItem(items[i]);
        await job.updateProgress(Math.round(((i + 1) / items.length) * 100));
      }
      return { processed: items.length };
    },
    { connection, prefix },
  );
}

ההתקדמות נשמרת ב־Redis (בתוך העבודה) ומתפרסמת כאירוע progress ב־QueueEvents. ה־API יכול להחזיר אותה ב־GET /imports/:id, או להעביר אותה ב־SSE (שיעור 6).

⚠️ טעויות נפוצות
  • Promise.all(items.map(handleItem)) — לא לפי הסדר, וההתקדמות קופצת מ־0 ל־100.
  • job.updateProgress בלי await — העבודה עלולה להסתיים לפני שהעדכון האחרון נכתב.

P26-E78 · לוח בקרה: מצב התור והרצה מחדש 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

מחזיר אובייקט עם המפתחות האלה:

await queue.getJobCounts("waiting", "active", "delayed", "completed", "failed")
💡 רמז 2

‏queue.getFailed(0, -1) — כל ה־failed (בלי הטווח, ברירת המחדל מחזירה רק חלק). לכל אחת: await job.retry().

✅ פתרון
// P26-E78: לוח בקרה — מצב התור והרצה מחדש
import type { Queue } from "bullmq";

export async function queueStats(queue: Queue) {
  const c = await queue.getJobCounts("waiting", "active", "delayed", "completed", "failed");
  return { waiting: c.waiting ?? 0, active: c.active ?? 0, delayed: c.delayed ?? 0, completed: c.completed ?? 0, failed: c.failed ?? 0 };
}

export async function retryAllFailed(queue: Queue) {
  const jobs = await queue.getFailed(0, -1);
  for (const job of jobs) await job.retry();
  return jobs.length;
}

זה בדיוק מה ש־bull-board עושה בכפתור "Retry all". ההרצה מחדש בטוחה רק כי הצרכן idempotent: אם חלק מהמיילים נשלחו לפני שהעבודה נכשלה — הם לא יישלחו שוב.

⚠️ טעויות נפוצות
  • queue.getFailed() בלי טווח — רק העמוד הראשון.
  • להוסיף עבודות חדשות עם אותם נתונים במקום retry — העבודה הישנה נשארת ב־failed, ו־jobId קבוע ימנע את החדשה.

P26-E79 · תור פשוט מ־list 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

‏RPUSH לסוף, ‏LPOP מהראש. ‏LPOP על list ריקה ← null.

💡 רמז 2

‏LPOP אטומי — שני workers לא יקבלו אותה עבודה.

✅ פתרון
// P26-E79: תור פשוט מ־list
import type { Redis } from "ioredis";

export async function enqueue(redis: Redis, queue: string, job: unknown) {
  return redis.rpush(`q:${queue}`, JSON.stringify(job));
}

export async function drain(redis: Redis, queue: string, handler: (job: any) => Promise<void>) {
  let done = 0, failed = 0;
  for (let raw = await redis.lpop(`q:${queue}`); raw !== null; raw = await redis.lpop(`q:${queue}`)) {
    const job = JSON.parse(raw);
    try {
      await handler(job);
      done++;
    } catch (e) {
      failed++;
      await redis.rpush(`q:${queue}:failed`, JSON.stringify({ job, error: (e as Error).message }));
    }
  }
  return { done, failed };
}

מה חסר כאן לעומת BullMQ? worker שקרס אחרי LPOP ולפני הסוף — העבודה אבדה (at-most-once). אין ניסיונות חוזרים, אין עיכוב, אין התקדמות. לכן בפרויקט — BullMQ, שעושה את כל זה עם סקריפטי Lua מעל אותם מבנים.

⚠️ טעויות נפוצות
  • LPUSH ו־LPOP — מחסנית (LIFO), לא תור: העבודה הישנה ביותר מחכה הכי הרבה.
  • LRANGE ואז DEL — שני workers קוראים את אותה רשימה.

‏jobId מונע כפילות רק כל עוד העבודה הקודמת קיימת בתור.

P26-E81 · ‏SIGTERM ל־worker באמצע עבודה 🧠 הבנה רמה 2

💡 רמז 1

‏close() מפסיק לקחת עבודות חדשות ומחכה לפעילות.

💡 רמז 2

stalled.

✅ פתרון
  1. מפסיק לקחת עבודות חדשות, ומחכה שהעבודה הפעילה תסתיים (ותסומן). אז מתנתק.
  2. קודם מפסיקים לקבל עבודה חדשה: שרת HTTP (‏server.close) ו־worker.close() — במקביל. אחר כך מה שהם השתמשו בו: Queue (שה־API מוסיף אליו), ואז Redis ו־Prisma. סוגרים מסד אחרון — עבודה שבאמצע עוד כותבת אליו.
  3. SIGKILL הורג אותה באמצע. BullMQ יזהה אותה כ־stalled ויחזיר לתור, ו־worker אחר יריץ מההתחלה. לכן זה לא אסון — כי הצרכן idempotent. מה שכדאי: עבודות קצרות, או לחלק עבודה ארוכה לצעדים.
⚠️ טעויות נפוצות
  • לסגור את Prisma ב־hook לפני שה־worker סיים — העבודה האחרונה נכשלת על "client closed" (בדיוק הניסוי מפרק 24).

P26-E83 · ‏outbox relay: מ־PostgreSQL לתור 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1
SELECT id, kind, payload FROM outbox WHERE sent_at IS NULL ORDER BY id LIMIT $1
💡 רמז 2

‏payload מגיע מ־pg כבר כאובייקט (jsonb). סימון: UPDATE outbox SET sent_at = now() WHERE id = $1.

✅ פתרון
// P26-E83: outbox relay — מ־PostgreSQL לתור
import type pg from "pg";
import type { Queue } from "bullmq";

export async function relayOutbox(db: pg.Client, queue: Queue, limit = 100) {
  const { rows } = await db.query("SELECT id, kind, payload FROM outbox WHERE sent_at IS NULL ORDER BY id LIMIT $1", [limit]);
  for (const r of rows) {
    await queue.add(r.kind, r.payload, { jobId: `outbox-${r.id}` });
    await db.query("UPDATE outbox SET sent_at = now() WHERE id = $1", [r.id]);
  }
  return rows.length;
}

הסדר — קודם add, אחר כך סימון — הוא בחירה ב־at-least-once: קריסה ביניהם = הוספה כפולה (ש־jobId מנטרל). ההפך (קודם סימון) = שורה מסומנת שאף פעם לא נשלחה.

עם כמה relays במקביל, שניים יקראו את אותן שורות. התיקון מפרק 18: FOR UPDATE SKIP LOCKED בתוך טרנזקציה — כל relay לוקח שורות אחרות.

⚠️ טעויות נפוצות
  • לסמן את כל השורות ב־UPDATE אחד לפני הלולאה — קריסה באמצע הלולאה משאירה שורות מסומנות שלא נשלחו.
  • ‏jobId בלי קידומת (String(id)) — BullMQ לא מקבל jobId שהוא מספר שלם.

✅ פתרון
// P26-E84: POST /pay שעונה מיד ושולח לתור
import express from "express";
import type { Queue } from "bullmq";

export function payApp({ queue, markPaid }: { queue: Queue; markPaid: (orderId: number) => Promise<boolean> }) {
  const app = express();
  app.post("/orders/:id/pay", async (req, res) => {
    if (!/^[1-9]\d*$/.test(req.params.id)) return res.status(400).json({ error: "id לא תקין" });
    const orderId = Number(req.params.id);
    if (!(await markPaid(orderId))) return res.status(404).json({ error: "אין הזמנה שממתינה לתשלום" });
    await queue.add("order-confirmation", { orderId }, { jobId: `confirm-${orderId}`, attempts: 3, backoff: { type: "exponential", delay: 1000 } });
    res.status(202).json({ status: "paid" });
  });
  return app;
}

הבקשה עושה שני דברים מהירים: עדכון במסד ו־queue.add (כתיבה אחת ל־Redis). שרת המייל יכול להיות למטה שעה — הלקוח לא יודע.

⚠️ טעויות נפוצות
  • להוסיף לתור לפני markPaid — מייל על הזמנה שלא קיימת.
  • ‏200 במקום 202 — עובד, אבל 202 אומר במפורש שחלק מהעבודה עוד לא נעשה.

P26-E85 · ‏timeout בתוך worker 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1
let timer: NodeJS.Timeout | undefined;
const timeout = new Promise((_, reject) => { timer = setTimeout(() => reject(new Error("TIMEOUT")), timeoutMs); });
💡 רמז 2
try {
  return await Promise.race([handler(job.data), timeout]);
} finally {
  clearTimeout(timer);
}
✅ פתרון
// P26-E85: timeout בתוך worker
import { Worker, type ConnectionOptions } from "bullmq";

export function startWorkerWithTimeout(connection: ConnectionOptions, prefix: string, queueName: string, handler: (data: any) => Promise<unknown>, timeoutMs: number) {
  return new Worker(
    queueName,
    async (job) => {
      let timer: NodeJS.Timeout | undefined;
      const timeout = new Promise<never>((_, reject) => {
        timer = setTimeout(() => reject(new Error("TIMEOUT")), timeoutMs);
      });
      try {
        return await Promise.race([handler(job.data), timeout]);
      } finally {
        clearTimeout(timer);
      }
    },
    { connection, prefix },
  );
}

שים לב מה Promise.race לא עושה: הוא לא עוצר את ה־handler. הבקשה ל־SMTP ממשיכה ברקע, ואם היא בכל זאת תצליח — והניסיון החוזר גם — יישלחו שני מיילים. עוד סיבה לצרכן idempotent (ואם הספרייה תומכת — AbortSignal, שבאמת מבטל).

⚠️ טעויות נפוצות
  • בלי clearTimeout — כל עבודה שהצליחה משאירה timer, והתהליך לא נסגר עד שכולם פגים.
  • timeout שמחזיר ערך (resolve) במקום לזרוק — BullMQ חושב שהעבודה הצליחה.
