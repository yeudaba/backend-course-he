שיעור 3 — מצב משותף: הגבלת קצב, מנעולים ו־Lua

⏱ ~45 דקות

🎯 בשיעור הזה
  • למה "קרא, שנה, כתוב" שבור כשיש כמה שרתים — וראייה בקוד.
  • הגבלת קצב משותפת: fixed window עם INCR, וחלון נע עם sorted set.
  • מנעול מבוזר: SET NX PX, token, ושחרור בטוח.
  • Lua: כמה פקודות כפקודה אחת. ו־pub/sub.

1. שלושה שרתים, מונה אחד

בפרק 24 כתבנו הגבלת קצב עם Map בזיכרון. עם שלושה עותקים של השרת מאחורי load balancer — כל אחד סופר לבד, והמגבלה האמיתית פי 3. הפתרון: המונה ב־Redis, שכל השרתים רואים. אבל צריך לעדכן אותו נכון:

import { Redis } from "ioredis";
const redis = new Redis(process.env.REDIS_URL ?? "redis://localhost:6379", { keyPrefix: "lesson26:" });
await redis.del("a", "b");

// "קרא, הוסף 1, כתוב" — 100 בקשות במקביל
await Promise.all(Array.from({ length: 100 }, async () => {
  const n = Number((await redis.get("a")) ?? 0);
  await redis.set("a", n + 1);
}));
// INCR — הקריאה והכתיבה הן פקודה אחת בתוך Redis
await Promise.all(Array.from({ length: 100 }, () => redis.incr("b")));

console.log("GET+SET:", await redis.get("a"), "· INCR:", await redis.get("b"));
await redis.del("a", "b");
await redis.quit();
GET+SET: 1 · INCR: 100

כל 100 ה־GET יצאו לפני שה־SET הראשון הגיע — כולם קראו 0, כולם כתבו 1. זה אותו מרוץ ממכירת המלאי בפרויקט 3 (12 הזמנות על 3 יחידות), רק ב־Redis. והתיקון באותה רוח: לא "קרא ואז החלט", אלא פעולה אחת שהשרת עושה בבת אחת — INCR, SET NX, או סקריפט Lua.

2. הגבלת קצב

Fixed window — מונה לכל (לקוח, חלון), שמת לבד בסוף החלון:

P26-E09.ts 
const window = Math.floor(now / 1000 / windowSeconds);
const key = `rl:${clientId}:${window}`;
const [[, count]] = await redis.multi()
  .incr(key)
  .expire(key, windowSeconds, "NX")   // NX: תוקף רק בפעם הראשונה (Redis 7+)
  .exec();
return { allowed: count <= limit, remaining: Math.max(0, limit - count), … };

בלי NX, כל בקשה מאריכה את התוקף — ומי שממשיך לשלוח אף פעם לא משתחרר (E21). והחיסרון של fixed window, שראינו בפרק 24: בסוף חלון אחד ובתחילת הבא אפשר לשלוח כמעט פי 2. חלון נע — sorted set שבו ה־score הוא הזמן: ZREMRANGEBYSCORE מוחק מה שיצא מהחלון, ZCARD סופר, ZADD מוסיף (E15). ו־token bucket — דורש לקרוא את המצב, לחשב ולכתוב: שם צריך Lua (סעיף 4, E25).

בפועל, בפרויקט Nest לא כותבים את זה מאפס: ל־@nestjs/throttler יש storage של Redis, ו־nginx או ה־API gateway של ספק הענן עושים את זה לפני שהבקשה מגיעה אליך. אבל להבין מה הם עושים — זו שאלת ראיון קלאסית ("תכנן rate limiter").

3. מנעול מבוזר

"הדוח הלילי צריך לרוץ פעם אחת, לא שלוש" · "רק שרת אחד מרענן את ה־cache" (E13). מנעול ב־Redis:

P26-E12.ts 
const RELEASE = `if redis.call("GET", KEYS[1]) == ARGV[1] then return redis.call("DEL", KEYS[1]) else return 0 end`;

const token = randomUUID();
const ok = await redis.set(`lock:${name}`, token, "PX", ttlMs, "NX"); // "OK" או null
…
await redis.eval(RELEASE, 1, `lock:${name}`, token);                  // מוחק רק אם עדיין שלי

כל פרט כאן תיקון של באג אמיתי (E22):

  • NX ו־PX באותה פקודה. SETNX ואז EXPIRE — תהליך שקרס ביניהן משאיר מנעול לנצח.
  • תוקף. שרת שמחזיק את המנעול ומת — המנעול משתחרר לבד.
  • token ייחודי, ושחרור רק אם הוא שלך. A לקח מנעול ל־10 שניות, עבד 12. בשנייה 10 המנעול פג ו־B לקח אותו. בשנייה 12 A "משחרר" — וDEL פשוט מוחק את המנעול של B. לכן בודקים את ה־token — ובפקודה אחת (Lua), אחרת אותו מרוץ בדיוק בין ה־GET ל־DEL.
⚠️ מנעול עם תוקף — לא לנכונות

גם עם כל התיקונים, A שנתקע (GC ארוך, רשת איטית) ממשיך לעבוד אחרי שהמנעול שלו פג — ושניהם עובדים במקביל. לכן מנעול Redis טוב ל"לחסוך עבודה כפולה", לא ל"אסור שזה יקרה פעמיים". מלאי, כסף, ייחודיות — המסד אוכף: UPDATE … WHERE stock >= qty, UNIQUE, טרנזקציות (פרקים 18–19, פרויקט 3). ואם באמת צריך מנעול נכון — SELECT … FOR UPDATE או advisory lock של PostgreSQL.

4. Lua: סקריפט שרץ כפקודה אחת

MULTI שולח כמה פקודות יחד, אבל אי אפשר להחליט באמצע לפי ערך. סקריפט Lua רץ בתוך Redis, ועד שהוא מסתיים שום פקודה אחרת לא רצה:

import { Redis } from "ioredis";
const redis = new Redis(process.env.REDIS_URL ?? "redis://localhost:6379", { keyPrefix: "lesson26:" });

// "קח עד N יחידות, אם יש" — קריאה, החלטה וכתיבה, בלי מרוץ
const TAKE = `
local left = tonumber(redis.call("GET", KEYS[1]) or "0")
local want = tonumber(ARGV[1])
if left < want then return -1 end
return redis.call("DECRBY", KEYS[1], want)
`;
await redis.set("seats", 3);
const results = await Promise.all(Array.from({ length: 5 }, () => redis.eval(TAKE, 1, "seats", 1)));
console.log(results, "נשאר:", await redis.get("seats"));
await redis.del("seats");
await redis.quit();
[ 2, 1, 0, -1, -1 ] נשאר: 0

KEYS[1] עובר דרך ioredis ולכן מקבל את ה־keyPrefix — עוד סיבה להעביר מפתחות כ־KEYS ולא לכתוב אותם בתוך הסקריפט. שני כללים: סקריפט קצר (בזמן שהוא רץ, כל Redis מחכה), ורק מפתחות שקיבל ב־KEYS. כך עובד BullMQ מבפנים: רוב הלוגיקה שלו — "קח עבודה מהתור והעבר ל־active" — היא סקריפטי Lua.

5. pub/sub

PUBLISH channel message — כל מי שמחובר ומנוי (SUBSCRIBE) מקבל, באותו רגע. בלי שמירה: מי שלא היה מחובר — פספס. שימושים: "בטל את ה־cache המקומי שלך" לכל השרתים (E19), התראות בזמן אמת שמועברות ל־WebSocket. ובגלל שאין שמירה — לא לעבודות שחייבות לקרות. לזה יש תורים, בשיעור הבא.

פרט טכני שתפגוש: חיבור שעשה SUBSCRIBE נכנס למצב מיוחד ולא יכול להריץ GET — לכן מחזיקים חיבור נפרד למנויים (redis.duplicate()).
