שיעור 6 — זמן אמת: SSE, WebSocket ו־fan-out

⏱ ~50 דקות

🎯 בשיעור הזה
  • איך השרת שולח עדכון בלי שהלקוח ביקש: polling, SSE ו־WebSocket — ומתי כל אחד.
  • Server-Sent Events ב־Express: הפורמט, התחברות מחדש ו־Last-Event-ID.

  • המלכודות: חיבורים שלא נסגרים, proxies, ו־heartbeat.

1. השרת רוצה לדבר ראשון

HTTP הוא "הלקוח שואל, השרת עונה". אבל בחנות הקפה (פרויקט 3), דנה מסתכלת על דף ההזמנה שלה, והסטטוס משתנה מ"בהכנה" ל"נשלחה" — איך הדף יודע? שלוש דרכים:

הכלל: אם רק השרת מדבר — SSE. הוא HTTP רגיל: עובר דרך proxies, עובד עם ה־cookies וה־CORS שכבר יש, והדפדפן מתחבר מחדש לבד. WebSocket — כשגם הלקוח שולח הרבה הודעות קטנות (E26).

2. Server-Sent Events

הפורמט פשוט: Content-Type: text/event-stream, ואז הודעות טקסט. כל הודעה היא שורות שדה: ערך, ושורה ריקה מסיימת אותה. נריץ שרת וקורא באותו קובץ:

import express from "express";

const app = express();
app.get("/orders/7/events", (req, res) => {
  res.writeHead(200, { "Content-Type": "text/event-stream", "Cache-Control": "no-cache" });
  const steps = ["received", "preparing", "shipped"];
  let id = 0;
  const timer = setInterval(() => {
    id++;
    res.write(`id: ${id}\nevent: status\ndata: ${JSON.stringify({ order: 7, status: steps[id - 1] })}\n\n`);
    if (id === steps.length) { clearInterval(timer); res.end(); }
  }, 20);
  req.on("close", () => clearInterval(timer)); // הלקוח עזב — מפסיקים לכתוב
});

const server = app.listen(0);
const res = await fetch(`http://localhost:${server.address().port}/orders/7/events`);
console.log(res.headers.get("content-type"));
const decoder = new TextDecoder();
for await (const chunk of res.body) process.stdout.write(decoder.decode(chunk)); // מה שעובר על החוט
server.close();

בדפדפן לא קוראים את הזרם ביד:

בדפדפן 
const es = new EventSource("/orders/7/events");
es.addEventListener("status", (e) => render(JSON.parse(e.data)));

שלושה שדות שכדאי להכיר:

  • id — אם החיבור נפל (Wi‑Fi ברכבת, deploy של השרת), EventSource מתחבר מחדש לבד ושולח Last-Event-ID: 2. שרת ששומר את האירועים האחרונים שולח רק את מה שפוספס (E28).
  • event — שם הסוג, ל־addEventListener. בלעדיו — message.
  • retry — כמה מילישניות הדפדפן מחכה לפני שהוא מתחבר מחדש.

ושורה שמתחילה בנקודתיים (: ping) היא הערה — הדפדפן מתעלם ממנה. שולחים אותה כל 15–30 שניות כ־heartbeat: load balancers ו־proxies סוגרים חיבור ששקט יותר מדי זמן.

3. WebSocket

WebSocket מתחיל כבקשת HTTP עם Upgrade: websocket. השרת עונה 101 Switching Protocols, ומאותו רגע זה כבר לא HTTP: שני הצדדים שולחים הודעות (frames) מתי שהם רוצים, על אותו חיבור TCP. ב־Node, השרת הוא החבילה ws, והלקוח — WebSocket גלובלי (מובנה מ־Node 22, כמו בדפדפן):

import http from "node:http";
import { WebSocketServer } from "ws";

const server = http.createServer();
const wss = new WebSocketServer({ server }); // מחובר לאותו שרת HTTP — אותו פורט
wss.on("connection", (ws, req) => {
  console.log("server: connected", req.url);
  ws.on("message", (raw) => {
    const msg = JSON.parse(String(raw));
    ws.send(JSON.stringify({ type: "echo", text: msg.text.toUpperCase() }));
  });
});
await new Promise<void>((r) => server.listen(0, r));

const ws = new WebSocket(`ws://localhost:${(server.address() as any).port}/live?room=7`);
ws.addEventListener("open", () => ws.send(JSON.stringify({ type: "say", text: "hello" })));
ws.addEventListener("message", (e) => {
  console.log("client got:", e.data);
  ws.close();
  wss.close();
  server.close();
});
server: connected /live?room=7
client got: {"type":"echo","text":"HELLO"}

מה שצריך לבנות בעצמך (ו־SSE נתן חינם): התחברות מחדש אחרי ניתוק, ו־heartbeat — ws.ping() כל 30 שניות, ומי שלא ענה ב־pong — ws.terminate(). בלי זה, לקוח שהטלפון שלו נכבה נשאר "מחובר" בזיכרון לנצח.

⚠️ אימות — לפני שהחיבור נפתח

בדפדפן אי אפשר להוסיף header של Authorization ל־new WebSocket(). האפשרויות: cookie של session, או token קצר־מועד בכתובת (?token=, שהשרת מנפיק לחיבור אחד). את הבדיקה עושים באירוע upgrade של שרת ה־HTTP — ואם לא תקין, מחזירים 401 וסוגרים, לפני שנפתח חיבור (E29). ובכל הודעה: מי שלח נקבע לפי החיבור, אף פעם לא לפי שדה בהודעה. ו־token בכתובת נכתב ללוגים של proxies — לכן קצר־מועד.

4. כמה שרתים: fan-out דרך Redis

חיבור SSE או WebSocket מחובר לתהליך אחד. עם שלושה שרתים מאחורי load balancer, אירוע שקרה בשרת A צריך להגיע גם ללקוחות של B ו־C. זה בדיוק pub/sub משיעור 3: כל שרת עושה SUBSCRIBE פעם אחת (בחיבור נפרד), ומפיץ כל הודעה ללקוחות המקומיים שלו (E30). ומה ש־pub/sub לא נותן: שמירה. שרת שהיה למטה ברגע ה־publish — פספס. ל־SSE זה בסדר (Last-Event-ID, או טעינה מחדש); למה שאסור לפספס — תור (שיעור 4).

5. מלכודות בפרודקשן

  • חיבורים פתוחים הם משאב. כל לקוח מחזיק socket וזיכרון. ניקוי ב־req.on("close") (SSE) וב־ws.on("close"), ו־heartbeat שמזהה חיבורים מתים.
  • proxies ודחיסה. nginx מחזיק תשובות בזיכרון לפני שהוא שולח (buffering) — האירועים מגיעים בבת אחת, באיחור. X-Accel-Buffering: no, ובלי middleware של compression על נתיב ה־SSE.
  • timeouts. load balancers סוגרים חיבור "שקט" אחרי 60 שניות בערך. heartbeat מתחת לזה.
  • HTTP/1.1: עד 6 חיבורים לדומיין בדפדפן. שבע לשוניות עם SSE — השביעית נתקעת. ב־HTTP/2 (שה־reverse proxy מפרק 25 נותן) הבעיה נעלמת.
  • deploy. כיבוי מסודר (פרק 24) מחכה שבקשות יסתיימו — וחיבור SSE לא מסתיים לעולם. ב־SIGTERM סוגרים את חיבורי ה־SSE והלקוחות מתחברים מחדש לשרת אחר.

בפרויקט 3 (רשות): GET /orders/:id/events ב־SSE — רק לבעל ההזמנה (אותו בדיקת בעלות כמו ב־GET /orders/:id) — שמודיע על כל שינוי סטטוס. ה־worker של התשלומים (שיעור 5) מפרסם ב־Redis, וכל שרת מפיץ ללקוחות שלו.

💼 בעולם העבודה

"תכנן מערכת התראות" ו"איך היית בונה צ'אט?" הן שאלות system design קלאסיות. תשובה טובה מתחילה בשאלה "מי מדבר?" (SSE מול WebSocket), ממשיכה ב"איך זה עובד עם כמה שרתים?" (pub/sub, ולמה לא sticky sessions בלבד), ונגמרת במלכודות: אימות לפני ה־upgrade, heartbeat, ומה קורה ללקוח שהתנתק (Last-Event-ID). בפרק 28 תשתמש בזה בשאלת תכנון שלמה.
