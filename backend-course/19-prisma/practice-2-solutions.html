P19-E48 · מה Prisma ייצר במסד? 🧠 הבנה רמה 2

💡 רמז 1

הטבלה בשיעור: ‏String? ← nullable; ‏enum ← CREATE TYPE.

💡 רמז 2

מה חסר ב־createdAt? ומה חסר בסוף המודל?

✅ פתרון

זה מה שהפקודה הזו מייצרת מהמודל (הרצה אמיתית):

% npx prisma migrate diff --from-empty --to-schema schema.prisma --script
-- CreateEnum
CREATE TYPE "Plan" AS ENUM ('free', 'pro');

-- CreateTable
CREATE TABLE "Account" (
    "id" SERIAL NOT NULL,
    "email" TEXT NOT NULL,
    "nickname" TEXT,
    "balance" DECIMAL(10,2) NOT NULL,
    "plan" "Plan" NOT NULL DEFAULT 'free',
    "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT "Account_pkey" PRIMARY KEY ("id")
);

-- CreateIndex
CREATE UNIQUE INDEX "Account_email_key" ON "Account"("email");

שתי הבעיות: (1) createdAt הוא TIMESTAMP(3) — בלי אזור זמן; חסר @db.Timestamptz(3). (2) בלי @@map/@map — הטבלה "Account" והעמודה "createdAt", עם אותיות גדולות, וב־psql צריך מירכאות בכל שאילתה (SELECT "createdAt" FROM "Account"). שאר הדברים כצפוי: nickname בלי NOT NULL, ‏@unique הפך ל־UNIQUE INDEX, ה־enum לטיפוס.

⚠️ טעויות נפוצות
  • "נשנה אחר כך" — שינוי טבלה עם נתונים הוא migration שצריך לתכנן. כדאי להחליט על שמות וטיפוסי זמן מההתחלה.

P19-E49 · ‏"missing an opposite relation field" 🧠 הבנה רמה 2

💡 רמז 1

בשיעור: "בצד ה'אחד' — מערך".

💡 רמז 2

שדות קשר הם "בשביל ה־client". מה ה־client של Author לא יידע לעשות בלי השדה הזה?

✅ פתרון

השגיאה (הרצה אמיתית של migrate diff):

error: Error validating field `author` in model `Book`: The relation field `author` on model `Book` is missing an opposite relation field on the model `Author`. Either run `prisma format` or add it manually.

חסר ב־Author: books Book[]. במסד הוא לא קיים (ה־FK רק ב־books), אבל Prisma דורש ששני הצדדים של קשר יוגדרו, כדי שה־client יתמוך בשני הכיוונים: include: { books: true } על מחבר, ו־where: { books: { some: ... } }. ‏npx prisma format מוסיף אותו לבד.

⚠️ טעויות נפוצות
  • להוסיף bookId ל־Author "כדי להשלים" — זו עמודה אמיתית במסד, וקשר שונה לגמרי (לכל מחבר ספר אחד).

P19-E51 · ‏migrate dev, ‏deploy או reset? 🧠 הבנה רמה 1

💡 רמז 1

מה יוצר migration חדש? מה רק מריץ קיימים? מה מוחק?

💡 רמז 2

בייצור — רק מה שלא שואל ולא מוחק.

✅ פתרון
  1. dev — יוצר migration חדש מההבדל, ומריץ.
  2. dev (מריץ את החדשים; אם אין שינוי בסכמה — לא יוצר כלום). ‏deploy גם יעבוד.
  3. deploy — רק מריץ את מה שלא רץ. בלי ליצור, בלי לשאול, בלי לאפס.
  4. reset — מוחק הכול ומריץ מחדש (ואז seed).
  5. deploy — אותו דבר כמו בייצור, ולכן גם בודק שה־migrations רצים נקי מאפס.
  6. status.
⚠️ טעויות נפוצות
  • migrate dev מול ייצור — אם הוא מזהה "drift" הוא מציע לאפס את המסד. זה הסוף של הנתונים.

P19-E52 · עמודת חובה חדשה בטבלה מלאה 🧠 הבנה רמה 2

💡 רמז 1

לשורות הקיימות — מה הערך של העמודה החדשה?

💡 רמז 2

P16-E19: שלושה שלבים.

✅ פתרון
ALTER TABLE customers ADD COLUMN phone text NOT NULL;
ALTER TABLE customers ADD COLUMN phone text NOT NULL DEFAULT '';
SELECT COUNT(*) AS customers, COUNT(*) FILTER (WHERE phone = '') AS empty_phone FROM customers;
ERROR:  column "phone" of relation "customers" contains null values
ALTER TABLE
 customers | empty_phone
-----------+-------------
         8 |           8
(1 row)

בלי default — השורות הקיימות היו מקבלות NULL, וה־NOT NULL אוסר: הפקודה נכשלת (‏migrate dev מזהיר מראש שהשינוי לא יעבור על טבלה עם נתונים). עם default ריק — עובר, אבל עכשיו 8 לקוחות עם "טלפון" ריק, שאף בדיקה לא תתפוס. האפשרויות: (א) String? — אם באמת לא לכולם יש טלפון; (ב) שלושה שלבים: עמודה nullable ← מילוי (script או UPDATE) ← NOT NULL — עם npx prisma migrate dev --create-only, שמאפשר לערוך את ה־SQL לפני שהוא רץ.

⚠️ טעויות נפוצות
  • @default("") רק כדי שה־migration יעבור — ערך "חובה" שאין לו משמעות.

P19-E19 · seed שאפשר להריץ שוב 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

upsert לכל דבר שיש לו שדה ייחודי (קטגוריה לפי name, לקוח לפי email).

💡 רמז 2

למוצר אין שדה ייחודי חוץ מ־id. findFirst לפי שם וקטגוריה, ו־create רק אם אין.

✅ פתרון
// P19-E19
import type { PrismaClient } from "../files/generated/prisma/client.ts";

const PRODUCTS = [
  { name: "Cold Brew Bottle 1L", price: 59.9, stock: 20 },
  { name: "Cold Brew Filter Bags", price: 34.9, stock: 100 },
];

export async function seedDemoData(prisma: PrismaClient) {
  const category = await prisma.category.upsert({ where: { name: "cold brew" }, create: { name: "cold brew" }, update: {} });
  for (const p of PRODUCTS) {
    const existing = await prisma.product.findFirst({ where: { name: p.name, categoryId: category.id } });
    if (!existing) await prisma.product.create({ data: { ...p, categoryId: category.id } });
  }
  const customer = await prisma.customer.upsert({
    where: { email: "demo@example.com" },
    create: { email: "demo@example.com", fullName: "Demo User", city: "Tel Aviv", joinedOn: new Date("2026-01-01") },
    update: {},
  });
  return { categoryId: category.id, customerId: customer.id };
}

seed שאפשר להריץ שוב ("idempotent") חוסך המון כאב: אפשר להריץ אותו בכל הפעלה של סביבת פיתוח, בלי "קודם תמחק".

⚠️ טעויות נפוצות
  • create לכל דבר — הרצה שנייה נכשלת על unique (או יוצרת מוצרים כפולים).

P19-E26 · הספרייה כ־schema של Prisma 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

העתק את המבנה מ־files/prisma/schema.prisma: ‏Product/Category הם דוגמה לקשר "רבים לאחד", ו־ProductTag היא בדיוק טבלת קישור כמו BookAuthor. שדה לא חובה: Int?. תאריך עם ברירת מחדל: DateTime @default(now()) @map("loaned_on") @db.Date.

💡 רמז 2

לכל קשר יש שני צדדים. ב־Loan: ‏bookId Int @map("book_id") ו־book Book @relation(fields: [bookId], references: [id]). ב־Book: ‏loans Loan[]. אם תשכח את הצד של המערך, Prisma יגיד בדיוק מה חסר.

✅ פתרון
// P19-E26: הספרייה (P17-E26) כ־schema של Prisma
datasource db {
  provider = "postgresql"
}

model Author {
  id       Int          @id @default(autoincrement())
  fullName String       @map("full_name")
  books    BookAuthor[]

  @@map("authors")
}

model Book {
  id            Int          @id @default(autoincrement())
  title         String
  isbn          String       @unique
  publishedYear Int?         @map("published_year")
  authors       BookAuthor[]
  loans         Loan[]

  @@map("books")
}

model BookAuthor {
  bookId   Int    @map("book_id")
  book     Book   @relation(fields: [bookId], references: [id], onDelete: Cascade)
  authorId Int    @map("author_id")
  author   Author @relation(fields: [authorId], references: [id])

  @@id([bookId, authorId])
  @@map("book_authors")
}

model Member {
  id       Int    @id @default(autoincrement())
  fullName String @map("full_name")
  email    String @unique
  loans    Loan[]

  @@map("members")
}

model Loan {
  id         Int       @id @default(autoincrement())
  bookId     Int       @map("book_id")
  book       Book      @relation(fields: [bookId], references: [id])
  memberId   Int       @map("member_id")
  member     Member    @relation(fields: [memberId], references: [id])
  loanedOn   DateTime  @default(now()) @map("loaned_on") @db.Date
  returnedOn DateTime? @map("returned_on") @db.Date

  @@index([memberId])
  @@map("loans")
}

שלוש שורות ב־schema שוות כאן הרבה SQL: ‏@relation הופך ל־FOREIGN KEY, ‏@unique ל־UNIQUE INDEX, ו־@@id ל־PRIMARY KEY על שתי עמודות. בלי onDelete, Prisma כותב ON DELETE RESTRICT, ולכן היסטוריית ההשאלות מוגנת כמו ב־P17-E26.

השדות books BookAuthor[] ו־loans Loan[] לא יוצרים עמודות. הם קיימים רק ב־Prisma Client, כדי שתוכל לכתוב include: { loans: true }. העמודה עצמה (book_id) נמצאת תמיד בצד ה"רבים".

מה לא עבר מ־P17-E26? ה־CHECK (returned_on >= loaned_on). ב־schema של Prisma אין דרך לכתוב CHECK. בפרויקט אמיתי יוצרים migration עם --create-only, ומוסיפים את ה־CHECK ביד לקובץ ה־SQL (שיעור 2). עוד הבדל: Prisma יוצר SERIAL ולא GENERATED ALWAYS AS IDENTITY.

ה־@@index([memberId]) לא חובה כאן, אבל הוא הרגל טוב. PostgreSQL לא יוצר index על foreign key לבד (‏P18-E16), ו"כל ההשאלות של חבר" היא שאילתה נפוצה.

⚠️ טעויות נפוצות
  • לשכוח @@map("books") — הטבלה נקראת "Book" (באות גדולה ובמירכאות), וכל SQL שכתבת עד עכשיו לא מוצא אותה.
  • onDelete: Cascade גם ב־Loan — מחיקת ספר מוחקת בשקט את ההיסטוריה שלו.
  • DateTime בלי @db.Date — העמודה היא timestamp(3), ו"השאלות של היום" צריכות טווח שעות.
  • id נוסף ב־BookAuthor בלי @@id([bookId, authorId]) — אותו קישור יכול להופיע פעמיים.

P19-E53 · פוסטים ותגובות 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

אחד־לרבים: בצד התגובה — postId, ושדה הקשר:

post Post @relation(fields: [postId], references: [id], onDelete: Cascade)

ובצד הפוסט — comments Comment[].

💡 רמז 2

זמן לא חובה: DateTime? @map("published_at") @db.Timestamptz(3). ‏index: @@index([postId]).

✅ פתרון
datasource db {
  provider = "postgresql"
}

model Post {
  id          Int       @id @default(autoincrement())
  title       String
  body        String
  publishedAt DateTime? @map("published_at") @db.Timestamptz(3)
  comments    Comment[]

  @@map("posts")
}

model Comment {
  id        Int      @id @default(autoincrement())
  postId    Int      @map("post_id")
  post      Post     @relation(fields: [postId], references: [id], onDelete: Cascade)
  author    String
  text      String
  createdAt DateTime @default(now()) @map("created_at") @db.Timestamptz(3)

  @@index([postId])
  @@map("comments")
}

ה־index על postId — כי "התגובות של פוסט" היא השאילתה הנפוצה, ו־PostgreSQL לא יוצר index ל־FK לבד (פרק 18).

⚠️ טעויות נפוצות
  • DateTime בלי @db.Timestamptz(3) — timestamp בלי אזור זמן (P19-E48).

P19-E54 · צוותים וחברות בצוות 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

כמו ProductTag בסכמה של הפרק: מודל קישור עם @@id([userId, teamId]), ושני @relation עם onDelete: Cascade.

💡 רמז 2

שדה מסוג enum עם ברירת מחדל: role Role @default(member). ובשני המודלים האחרים — memberships Membership[].

✅ פתרון
datasource db {
  provider = "postgresql"
}

enum Role {
  member
  admin
  owner
}

model User {
  id          Int          @id @default(autoincrement())
  email       String       @unique
  memberships Membership[]

  @@map("users")
}

model Team {
  id          Int          @id @default(autoincrement())
  name        String       @unique
  memberships Membership[]

  @@map("teams")
}

model Membership {
  userId   Int      @map("user_id")
  user     User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  teamId   Int      @map("team_id")
  team     Team     @relation(fields: [teamId], references: [id], onDelete: Cascade)
  role     Role     @default(member)
  joinedAt DateTime @default(now()) @map("joined_at") @db.Timestamptz(3)

  @@id([userId, teamId])
  @@index([teamId])
  @@map("memberships")
}

‏role הוא הסיבה לקשר מפורש (ולא "מובלע"): לקשר עצמו יש מידע. ‏@@index([teamId]) — כי המפתח הראשי מתחיל ב־userId, ו"חברי צוות X" צריך index משלו (P18-E57).

⚠️ טעויות נפוצות
  • id נפרד בלי @@id/@@unique על הזוג — אותו משתמש פעמיים באותו צוות, עם שני תפקידים.

P19-E55 · משימה בלי אחראי 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

שני סימני שאלה: assigneeId Int? ו־assignee Employee?.

💡 רמז 2
@relation(fields: [assigneeId], references: [id], onDelete: SetNull)
✅ פתרון
datasource db {
  provider = "postgresql"
}

model Employee {
  id    Int    @id @default(autoincrement())
  name  String
  tasks Task[]

  @@map("employees")
}

model Task {
  id         Int       @id @default(autoincrement())
  title      String
  assigneeId Int?      @map("assignee_id")
  assignee   Employee? @relation(fields: [assigneeId], references: [id], onDelete: SetNull)

  @@index([assigneeId])
  @@map("tasks")
}

‏Int? הופך את העמודה ל־nullable, ו־Employee? אומר ל־client ש־task.assignee יכול להיות null — ו־TypeScript יכריח לבדוק (P17-E53).

⚠️ טעויות נפוצות
  • רק assignee Employee? בלי Int? — Prisma דוחה: שדה הקשר אופציונלי אבל העמודה חובה.

P19-E56 · חשבוניות: תאריך, כסף וזמן עדכון 🤖 💻 כתיבת קוד 🤖 רמה 2

💡 רמז 1

תאריך בלבד: DateTime @db.Date. מתעדכן אוטומטית: @updatedAt.

💡 רמז 2
updatedAt DateTime @updatedAt @map("updated_at") @db.Timestamptz(3)
✅ פתרון
datasource db {
  provider = "postgresql"
}

model Invoice {
  id        Int      @id @default(autoincrement())
  number    String   @unique
  issuedOn  DateTime @map("issued_on") @db.Date
  total     Decimal  @db.Decimal(12, 2)
  note      String?
  createdAt DateTime @default(now()) @map("created_at") @db.Timestamptz(3)
  updatedAt DateTime @updatedAt @map("updated_at") @db.Timestamptz(3)

  @@map("invoices")
}

שים לב: ל־updated_at אין DEFAULT במסד — Prisma ממלא אותו בעצמו בכל create/update. ‏INSERT ישיר ב־SQL (בלי Prisma) חייב לתת לו ערך.

⚠️ טעויות נפוצות
  • DateTime בלי @db.Date לתאריך הנפקה — עכשיו יש לו גם שעה, ו"חשבוניות מ־1 במרץ" תלוי באזור זמן.

P19-E57 · ממסד קיים לסכמה: חדר כושר 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

timestamptz(3) ← @db.Timestamptz(3). ‏DEFAULT now() ← @default(now()).

💡 רמז 2

Booking הוא מודל קישור עם @@id([memberId, classId]) ושני קשרים עם onDelete: Cascade.

✅ פתרון
datasource db {
  provider = "postgresql"
}

model Member {
  id       Int       @id @default(autoincrement())
  fullName String    @map("full_name")
  email    String    @unique
  bookings Booking[]

  @@map("members")

  customer   Customer @relation(fields: [customerId], references: [id])

‏String? @unique — ייחודי רק בין הערכים שקיימים: הרבה מוצרים יכולים להיות בלי sku (NULL), כי ב־UNIQUE שני NULLים לא נחשבים שווים. ו־@@unique של הזוג יוצר index שמתחיל ב־productId, אז "הביקורות של לקוח" צריך @@index([customerId]).

P19-E59 · ‏enum במסד ו־union ב־TypeScript 🧠 הבנה רמה 2

💡 רמז 1

Prisma מייצר מ־enum OrderStatus טיפוס "pending" | "paid" | "shipped" | "cancelled".

💡 רמז 2

"ב־enum של PostgreSQL הסדר הוא סדר ההגדרה בסכמה" (שיעור 4).

✅ פתרון
  1. שגיאת TypeScript: "shiped" לא יכול להיות שווה לאף ערך ב־union — שגיאת כתיב נתפסת לפני הרצה (עם string רגיל — הייתה עוברת בשקט).

⚠️ טעויות נפוצות

P19-E60 · אילו indexes Prisma יצר? 🧠 הבנה רמה 2

💡 רמז 1

@unique ← UNIQUE INDEX. ‏@@index([...]) ← INDEX.

💡 רמז 2

המפתח הראשי של order_items הוא (order_id, product_id).

✅ פתרון
  1. ‏UNIQUE — מ־@unique על Category.name, ‏Customer.email, ‏Tag.name. השאר — מ־@@index: ‏Product (‏[categoryId]), ‏Order (‏[customerId, createdAt]), ‏OrderItem (‏[productId]), ‏ProductTag (‏[tagId]).
  2. המפתח הראשי (order_id, product_id) כבר מתחיל ב־order_id — הוא משמש גם כ־index עליו. בדיוק כמו ב־P18-E57. (וכך גם product_tags: ‏product_id ראשון במפתח, ו־tag_id צריך index משלו.)
  3. "ההזמנות של לקוח X, מהחדשה לישנה" — WHERE customer_id = $1 ORDER BY created_at DESC: שוויון ואז מיון, כמו ב־P18-E59.

⚠️ טעויות נפוצות
  • להוסיף @@index([orderId]) ל־OrderItem — כפילות של תחילת המפתח הראשי, עוד עלות על כל INSERT.

P19-E61 · ‏Decimal — לא number 🧠 הבנה רמה 2

💡 רמז 1

‏numeric(10,2) במסד מדויק. ‏number ב־JS — לא תמיד.

💡 רמז 2

שורה 3: כמה ספרות מדויקות יש ל־number?

✅ פתרון
console.log(0.1 + 0.2, 89.9 * 3);
console.log(Math.round(0.1 * 100) + Math.round(0.2 * 100), Math.round(89.9 * 100) * 3 / 100);
console.log(Number("12345678901234567.89"), Number.MAX_SAFE_INTEGER);
0.30000000000000004 269.70000000000005
30 269.7
12345678901234568 9007199254740991

number הוא float: חשבון עשרוני לא מדויק, ומעל ~15–16 ספרות הוא מאבד ספרות. ‏Decimal שומר את הערך בדיוק כמו המסד — ומשאיר לך את ההחלטה: Number(price) להצגה ולחישובים קטנים (עם אגורות, כמו בשורה 2), או חשבון עם Decimal עצמו (price.mul(3)) בכספים גדולים.

⚠️ טעויות נפוצות
  • price + 10 על Decimal — מחרוזת משורשרת ("89.910") או שגיאת טיפוס, לא חיבור.

P19-E62 · ‏"migrate diff" בזיכרון 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

Map של טבלה ← Map של עמודה ← Column, לכל אחד מהצדדים. ‏[...new Set([...a.keys(), ...b.keys()])].sort() — כל השמות משני הצדדים.

💡 רמז 2

מיון מחרוזות "לפי א״ב" כאן: sort() בלי פונקציה (סדר תווים) מספיק — שמות טבלאות ועמודות באנגלית.

✅ פתרון
// P19-E62: "migrate diff" בזיכרון
export type Column = { table: string; name: string; type: string; nullable: boolean };

function byTable(cols: Column[]) {
  const m = new Map<string, Map<string, Column>>();
  for (const c of cols) {
    if (!m.has(c.table)) m.set(c.table, new Map());
    m.get(c.table)!.set(c.name, c);
  }
  return m;
}
const union = (a: Iterable<string>, b: Iterable<string>) => [...new Set([...a, ...b])].sort();

export function diffColumns(before: Column[], after: Column[]) {
  const b = byTable(before);
  const a = byTable(after);
  const steps: string[] = [];
  let destructive = false;
  for (const t of union(b.keys(), a.keys())) {
    const old = b.get(t);
    const cur = a.get(t);
    if (!old) { steps.push(`CREATE TABLE ${t}`); continue; }
    if (!cur) { steps.push(`DROP TABLE ${t}`); destructive = true; continue; }
    for (const name of union(old.keys(), cur.keys())) {
      const o = old.get(name);
      const c = cur.get(name);
      if (!o) steps.push(`ADD COLUMN ${t}.${name} ${c!.type}${c!.nullable ? "" : " NOT NULL"}`);
      else if (!c) { steps.push(`DROP COLUMN ${t}.${name}`); destructive = true; }
      else {
        if (o.type !== c.type) { steps.push(`ALTER COLUMN ${t}.${name} TYPE ${c.type}`); destructive = true; }
        if (o.nullable && !c.nullable) { steps.push(`ALTER COLUMN ${t}.${name} SET NOT NULL`); destructive = true; }
        if (!o.nullable && c.nullable) steps.push(`ALTER COLUMN ${t}.${name} DROP NOT NULL`);
      }
    }
  }
  return { steps, destructive };
}

‏DROP NOT NULL לא הורס (רק מרשה יותר). ‏ADD COLUMN ... NOT NULL — גם הוא יכול להיכשל על טבלה מלאה (P19-E52); Prisma בודק את זה מול המסד האמיתי — כאן אין לנו את הנתונים.

⚠️ טעויות נפוצות
  • לעבור רק על העמודות של after — עמודות שנמחקו לא מתגלות.

P19-E63 · ‏@db.Date: מ־Date למחרוזת ובחזרה 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

‏d.toISOString().slice(0, 10) — תמיד UTC. ‏d.getDate() — לפי השעון המקומי.

💡 רמז 2

בדיקת תאריך: /^\d{4}-\d{2}-\d{2}$/, ואז new Date(s + "T00:00:00Z") — ובחזרה: אם toISOString().slice(0, 10) !== s, התאריך "גלש" (30 בפברואר ← 2 במרץ).

✅ פתרון
// P19-E63: @db.Date — מ־Date למחרוזת ובחזרה
export type ApiCustomer = { id: number; fullName: string; email: string; city: string | null; joinedOn: string };

export function toApiCustomer(c: { id: number; fullName: string; email: string; city: string | null; joinedOn: Date }): ApiCustomer {
  return { id: c.id, fullName: c.fullName, email: c.email, city: c.city, joinedOn: c.joinedOn.toISOString().slice(0, 10) };
}

export function toCustomerData(body: { fullName: string; email: string; city?: string | null; joinedOn: string }) {
  const d = new Date(`${body.joinedOn}T00:00:00Z`);
  if (!/^\d{4}-\d{2}-\d{2}$/.test(body.joinedOn) || Number.isNaN(d.getTime()) || d.toISOString().slice(0, 10) !== body.joinedOn) {
    throw new Error("תאריך לא תקין");
  }
  return { fullName: body.fullName, email: body.email.trim().toLowerCase(), city: body.city ?? null, joinedOn: d };
}

שתי פונקציות, אחת לכל כיוון, ובכל אחת — כל ההמרות. כשהן במקום אחד, הבאג של "התאריך זז ביום בשרת בחו״ל" נפתר פעם אחת.

⚠️ טעויות נפוצות
  • new Date("2025-11-02") בלי Z — זה דווקא UTC (פורמט תאריך בלבד), אבל new Date("2025-11-02T00:00") הוא שעון מקומי. הכי בטוח: לכתוב את ה־Z במפורש.
  • ${d.getFullYear()}-${d.getMonth() + 1}-... — שעון מקומי, ובלי אפסים מובילים.
