1. מה בודקים

בשאלת קוד ל־Junior, המראיין ממלא בסוף טופס עם שאלות כמו: האם הבין את הבעיה? האם תקשר בזמן העבודה? האם הגיע לפתרון עובד? האם ידע להגיד מה הסיבוכיות? האם בדק את הקוד שלו? "הגיע לפתרון אופטימלי" הוא רק אחד מהם. מועמד שכתב פתרון O(n²) נכון, אמר "זה O(n²), ואפשר לשפר עם Map — רוצה שאשפר?", ובדק מקרה קצה — עדיף על מי שכתב בשקט פתרון O(n) עם באג.

2. שישה צעדים

צעדמה עושיםכמה זמן (מתוך 40 דק׳)

3. דוגמה מלאה

"יש לך רשימת הזמנות עם userId וסכום. החזר את המשתמשים שהוציאו הכי הרבה."

  1. להבין: "כמה להחזיר — k? גם את הסכום? הזמנות מבוטלות נספרות? בתיקו — לפי מה? כמה הזמנות, בסדר גודל?" ← נניח: k משתמשים, עם הסכום, בלי מבוטלות, בתיקו לפי userId, עד מיליון הזמנות.
  2. דוגמאות: [{u:1, 50}, {u:2, 30}, {u:1, 20}], k=1 ← [{userId: 1, total: 70}]. ריק ← [].
  3. ראשון: "לכל משתמש — לעבור על כל ההזמנות ולסכום: O(u·n)."
  4. לשפר: "Map של userId ← סכום, במעבר אחד: O(n). ואז למיין את המשתמשים: O(u log u)."
  5. לכתוב:
type Order = { userId: number; amountCents: number; status: "paid" | "cancelled" };

function topSpenders(orders: Order[], k: number) {
  const totals = new Map<number, number>();
  for (const o of orders) {
    if (o.status === "cancelled") continue;
    totals.set(o.userId, (totals.get(o.userId) ?? 0) + o.amountCents);
  }
  return [...totals]
    .map(([userId, total]) => ({ userId, total }))
    .sort((a, b) => b.total - a.total || a.userId - b.userId)
    .slice(0, k);
}

// 6. לבדוק — הדוגמה, ומקרי קצה
console.log(topSpenders([{ userId: 1, amountCents: 5000, status: "paid" }, { userId: 2, amountCents: 3000, status: "paid" }, { userId: 1, amountCents: 2000, status: "paid" }], 1));
console.log(topSpenders([], 3));
console.log(topSpenders([{ userId: 9, amountCents: 100, status: "cancelled" }], 3));
console.log(topSpenders([{ userId: 2, amountCents: 10, status: "paid" }, { userId: 1, amountCents: 10, status: "paid" }], 5));
[ { userId: 1, total: 7000 } ]
[]
[]
[ { userId: 1, total: 10 }, { userId: 2, total: 10 } ]

וסיום: "זמן O(n + u log u), זיכרון O(u). שימו לב שסכמתי באגורות — לא בשברים. ואם ההזמנות במסד, הייתי עושה את זה ב־SQL: GROUP BY user_id ORDER BY SUM(…) DESC LIMIT k — המסד עושה בדיוק את זה, בלי להעביר מיליון שורות לשרת." המשפט האחרון הוא מה שמבדיל מועמד Backend.

4. לחשוב בקול — באנגלית

ראיונות טכניים מתקיימים לעיתים קרובות באנגלית, גם בחברות ישראליות. לא צריך אנגלית מושלמת — צריך כמה משפטים מוכנים:

מתימשפט
להבהיר"Just to make sure I understand — the input is…, and I should return…?" · "What should happen if the list is empty?"
פתרון ראשון"The brute-force approach would be…, which is O(n²). Let me see if I can do better."
לשפר"Since I keep looking up values, I can use a hash map to get O(1) lookups."
תקוע"I'm thinking about whether sorting helps here…" — שתיקה ארוכה גרועה יותר מחשיבה בקול
לבדוק"Let me walk through my example." · "Edge cases: empty input, a single element, duplicates."
סיבוכיות"This runs in O(n) time and O(n) extra space."

5. שאלות SQL

בראיון Backend כמעט תמיד יש גם SQL. שלוש שחוזרות שוב ושוב, על 27-algorithms/files/interview.sql:

"המשכורת השנייה בגובהה" — DISTINCT (שניים שחולקים את המקום הראשון) ו־OFFSET. והמלכודת: אם אין שנייה — שאילתה רגילה מחזירה אפס שורות; העטיפה ב־SELECT ( … ) מחזירה NULL (E12).

"Top-N לכל קבוצה" — העובד המרוויח ביותר בכל מחלקה, המוצר הנמכר ביותר בכל קטגוריה. window function (פרק 17):

SELECT department, name, salary
FROM (
  SELECT *, RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS r
  FROM employees
) ranked
WHERE r = 1
ORDER BY department, name;
 department  | name  | salary
-------------+-------+--------
 engineering | Dana  |  42000
 sales       | Maya  |  28000
 support     | Eli   |  16000
 support     | Shira |  16000
(4 rows)

RANK נותן לשווים את אותו מקום — לכן ב־support חוזרים שניים. ROW_NUMBER היה בוחר אחד "שרירותית" (אלא אם מוסיפים קריטריון שני ל־ORDER BY, כמו ב־E18). בראיון — לשאול: "בתיקו, להחזיר את כולם או אחד?"

"מי שאין לו…" — לקוחות בלי הזמנה ששולמה. הניסיון הראשון של כמעט כולם:

SELECT c.id, c.name, o.status
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE c.id IN (1, 3)
ORDER BY c.id, o.id;
 id |   name    |  status
----+-----------+-----------
  1 | Dana Levi | paid
  1 | Dana Levi | cancelled
  1 | Dana Levi | paid
  3 | Dana L.   |
(4 rows)

לקוח 3 לא הזמין: ה־LEFT JOIN נותן לו שורה עם status ריק — NULL. ועכשיו WHERE o.status <> 'paid': NULL <> 'paid' הוא לא TRUE (הוא NULL), אז לקוח 3 נעלם — בדיוק מי שחיפשנו. ולקוח 1 נכנס בגלל ההזמנה שבוטלה, למרות ששילם על שתיים אחרות. NOT EXISTS שואל את השאלה הנכונה: "אין אף הזמנה ששולמה" (E23).
