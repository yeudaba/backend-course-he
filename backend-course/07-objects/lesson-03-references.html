מספרים, מחרוזות ובוליאנים מועתקים. אובייקטים ומערכים — לא: המשתנה מחזיק הפניה (כמו כתובת), ו־user2 = user1 מעתיק רק את הכתובת. שתי מדבקות — קופסה אחת.

הבאג הקלאסי: פונקציה שמשנה את מה שקיבלה

function applyDiscount(product, percent) {
  product.price = product.price * (1 - percent / 100);
  return product;
}

const keyboard = { name: "מקלדת", price: 200 };
const sale = applyDiscount(keyboard, 10);
console.log(sale.price, keyboard.price);
180 180

רצינו "מחיר במבצע" — וקיבלנו גם שינוי של המוצר המקורי. הפרמטר product הוא עוד חץ לאותו אובייקט, ולכן product.price = ... שינה את keyboard. בשרת זה יכול להיות מחירון שכל הבקשות משתמשות בו: לקוח אחד קיבל הנחה — וכל הלקוחות אחריו משלמים פחות.

2. העתקה: spread

const original = { name: "מקלדת", price: 200 };
const copy = { ...original };
copy.price = 180;
console.log(original.price, copy.price);

const updated = { ...original, price: 150, onSale: true };
console.log(updated);
200 180
{ name: 'מקלדת', price: 150, onSale: true }

{ ...original } יוצר אובייקט חדש עם אותם שדות. ו־{ ...original, price: 150 } — "הכול כמו במקור, חוץ מ...". זו הדרך המקובלת לעדכן בלי לשנות את המקור. הפונקציה מלמעלה, נכון:

function applyDiscount(product, percent) {
  return { ...product, price: product.price * (1 - percent / 100) };
}
const keyboard = { name: "מקלדת", price: 200 };
const sale = applyDiscount(keyboard, 10);
console.log(sale.price, keyboard.price);
180 200

spread מעתיק רק את הרמה הראשונה. address הוא אובייקט — אז ה"עותק" מחזיק הפניה לאותה כתובת. structuredClone יוצר עותק עמוק מלא. ברוב הקוד מספיק spread, ומעדכנים גם את הרמה הפנימית במפורש: { ...user, address: { ...user.address, city: "אילת" } }.

5. JSON — הפורמט שבו שרתים מדברים

כשהשרת שולח אובייקט לדפדפן, הוא לא יכול לשלוח "אובייקט" — רק טקסט. JSON הוא הדרך לכתוב אובייקט כטקסט:

const order = { id: 7, items: ["עט", "מחברת"], paid: true, coupon: null };
const text = JSON.stringify(order);
console.log(text);
console.log(typeof text);

const back = JSON.parse(text);
console.log(back.items[1], back === order);

6. תאריכים: Date

בטבלה למעלה כתוב "תאריכים הופכים למחרוזת". כדי להבין למה, צריך לראות מה זה תאריך ב־JavaScript. כמעט כל שרת עובד עם זמן: מתי נוצרה הזמנה, מתי פג תוקף של קוד, כמה ימים נשארו עד מועד היעד.

const created = new Date("2026-11-19T08:30:00Z");
console.log(created.toISOString());
console.log(created.getTime());
console.log(typeof created);
2026-11-19T08:30:00.000Z
1795077000000
object

שלוש שורות, שלושה דברים חשובים:

  • new Date("...") יוצר תאריך מטקסט. הפורמט הוא ISO: שנה־חודש־יום, T, שעה, ובסוף Z. ה־Z אומר "השעה הזו ב־UTC", השעון העולמי שלא משתנה בקיץ ובחורף.
  • getTime() מחזיר את מה שבאמת שמור בתוך התאריך: מספר אחד. כמה אלפיות שנייה (milliseconds) עברו מ־1 בינואר 1970, חצות UTC.
  • typeof מחזיר "object". תאריך הוא אובייקט, ולכן כל מה שלמדת בשיעור הזה על הפניות נכון גם לו.

חישובים: עובדים עם המספר

const DAY = 24 * 60 * 60 * 1000;

console.log(ms / DAY);

console.log(nextWeek.toISOString());

console.log(due > created);
console.log(due === new Date("2026-11-19T10:00:00Z"));
console.log(due.getTime() === new Date("2026-11-19T10:00:00Z").getTime());

מחסרים, מחברים ומשווים את המספרים. new Date(מספר) הופך מספר בחזרה לתאריך. < ו־> עובדים על תאריכים (JavaScript משווה את המספרים), אבל === משווה הפניות, בדיוק כמו { name: "x" } === { name: "x" } בתחילת השיעור. לכן "האם זה אותו רגע?" בודקים עם getTime(). ו־Date.now() מחזיר את הרגע הנוכחי ישר כמספר, בלי ליצור אובייקט.

  • getUTCMonth() מחזיר 2 למרץ: החודשים נספרים מ־0 (ינואר = 0, דצמבר = 11). שאר החלקים נספרים רגיל. זו אחת הטעויות הנפוצות ביותר ב־JavaScript.
  • Date.UTC(שנה, חודש, יום) בונה רגע מחלקים (גם כאן חודש מ־0), ו־new Date(...) עוטף אותו.
  • 30 בפברואר לא קיים, ו־JavaScript לא מתלונן: הוא "גולש" ל־2 במרץ. אם הקלט מגיע ממשתמש, בודקים אותו לפני כן.
  • toISOString().slice(0, 10) נותן את התאריך בלבד, "2026-03-05". תראה את זה הרבה.

ולמה דווקא getUTC...? יש גם getDate(), getHours() וכו׳ בלי UTC. הם מחזירים את החלקים לפי אזור הזמן של המחשב שמריץ את הקוד. אותו d במחשב בישראל: getDate() מחזיר 6, כי 22:15 ב־UTC זה כבר 00:15 בלילה של 6 במרץ בישראל. ב־getUTCDate() מתקבל 5 בכל מחשב. בשרת משתמשים בגרסאות ה־UTC, כדי שהתוצאה לא תשתנה לפי המקום שבו השרת רץ. את "איזו שעה זו אצל המשתמש" נלמד בפרק 24 (שיעור 2).

תאריך ב־JSON: יוצא מחרוזת, נשאר מחרוזת

const order = { id: 7, createdAt: new Date("2026-11-19T08:30:00Z") };
const text = JSON.stringify(order);
console.log(text);

const back = JSON.parse(text);
console.log(typeof back.createdAt);
const createdAt = new Date(back.createdAt);
console.log(createdAt.getTime() === order.createdAt.getTime());
{"id":7,"createdAt":"2026-11-19T08:30:00.000Z"}
string
true

JSON.stringify כותב תאריך כמחרוזת ISO. JSON.parse לא יודע שזו הייתה פעם תאריך, ומחזיר מחרוזת. מי שמקבל את ה־JSON (שרת, דפדפן) ממיר בחזרה עם new Date(...). זה המצב בכל API: תאריכים עוברים ברשת כמחרוזות ISO.

⚠️ טעויות נפוצות עם Date
  • תאריך לא תקין לא זורק שגיאה מיד. new Date("31/12/2026") מחזיר תאריך "שבור": getTime() מחזיר NaN, ו־String(...) מחזיר "Invalid Date". השגיאה מגיעה רק אחר כך, כשקוראים ל־toISOString() (הדוגמה למטה). לכן קלט של תאריך בודקים עם Number.isNaN(d.getTime()).
  • בלי Z בסוף. new Date("2026-11-19T10:00:00") (בלי Z) מתפרש לפי השעון של המחשב. בשרת ב־UTC יוצא 10:00 UTC, ובמק בישראל יוצא 08:00 UTC. אותו קוד, תוצאה שונה. כותבים Z תמיד.
  • חודש מ־0: Date.UTC(2026, 3, 1) הוא 1 באפריל.
  • === בין תאריכים כמעט תמיד false. משווים getTime().
const bad = new Date("31/12/2026");
console.log(bad.getTime(), String(bad));
console.log(bad.toISOString());

הפלט: NaN Invalid Date, ואז Node קורס עם RangeError: Invalid time value. השגיאה מצביעה על השורה של toISOString, לא על השורה שבה נוצר התאריך השבור. בגלל זה הבאג הזה קשה למצוא.
