P16-E01 · איזה טיפוס? 🧠 הבנה רמה 1

💡 רמז 1

טלפון הוא מספר? האם עושים עליו חשבון?

💡 רמז 2

"מתי נוצרה" = רגע בזמן. "תאריך משלוח" = יום.

✅ פתרון
  1. integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY (או bigint אם מצפים למיליארדים)
  2. numeric(10, 2) NOT NULL CHECK (total >= 0) — לא float
  3. integer NOT NULL CHECK (quantity > 0)

  8. boolean NOT NULL DEFAULT false

💡 רמז 2

✅ פתרון
  1. ⚠️ מאפס את המלאי של כל המוצרים — אין WHERE.
  2. מאפס מלאי של מוצר 7 בלבד.

P16-E72 · מה RETURNING מחזיר? 🧠 הבנה רמה 2

💡 רמז 1

הדרך להוסיף עמודת חובה לטבלה קיימת היא בשלבים: (1) להוסיף כ־nullable (או עם DEFAULT); (2) למלא ערכים (UPDATE); (3) רק אז SET NOT NULL. זה בדיוק מה שתעשה ב־migrations בפרק 19 — על טבלה עם מיליון שורות, בלי להשבית את השרת.

P16-E26 · יומן אימונים — טבלה, נתונים ושאילתה 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

תזכורת לתחביר: integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY, ‏CHECK (kind IN ('run', 'bike', 'swim')), ‏CHECK (minutes BETWEEN 1 AND 600), ‏DEFAULT CURRENT_DATE. עמודה בלי NOT NULL היא לא חובה.

💡 רמז 2

ב־INSERT רושמים את העמודות במפורש, ובמקום ריק כותבים NULL: ('swim', 45, NULL, '2026-11-02', 'pool'). בשאילתה: WHERE distance_km IS NOT NULL, ו־ROUND(minutes / distance_km, 2) AS min_per_km.

✅ פתרון
CREATE TABLE workouts (
  id           integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  kind         text NOT NULL CHECK (kind IN ('run', 'bike', 'swim')),
  minutes      integer NOT NULL CHECK (minutes BETWEEN 1 AND 600),
  distance_km  numeric(6, 2) CHECK (distance_km > 0),
  done_on      date NOT NULL DEFAULT CURRENT_DATE,
  note         text
);

CHECK (distance_km > 0) בלי NOT NULL: כשהערך הוא NULL, התנאי לא "נכשל" (הוא "לא ידוע"), ולכן השורה מתקבלת. זה בדיוק מה שרצינו: מרחק לא חובה, אבל אם יש — חיובי. זה אותו כלל כמו uses <= max_uses ב־P16-E24.

minutes / distance_km: מספר שלם חלקי numeric נותן numeric, ולכן אין כאן בעיה של חלוקת שלמים. אילו שתי העמודות היו integer, ‏30 / 4 היה נותן 7 ולא 7.5.

ה־WHERE distance_km IS NOT NULL לא רק מסנן את השחייה. בלעדיו השורה של השחייה הייתה מופיעה עם min_per_km ריק.

⚠️ טעויות נפוצות
  • distance_km numeric(6, 2) NOT NULL CHECK (...) — אימון השחייה נדחה.
  • WHERE distance_km != NULL — שום שורה לא חוזרת. עם NULL משווים רק עם IS / IS NOT.
  • id serial — עובד, אבל מאפשר להכניס id ידני. הבודק מצפה ש"רק המסד ממספר" (GENERATED ALWAYS).
  • לשכוח DEFAULT CURRENT_DATE — ‏INSERT בלי תאריך נכשל, במקום לקבל את היום.

✅ פתרון
  1. Date — "חצות ב־20.11 לפי השעון של המחשב". בישראל זה 22:00Z של ה־19, ולכן ה־ISO "זז" יום אחורה (התצוגה המקומית עדיין 20.11).
  2. "due":"2026-11-19T22:00:00.000Z" — לקוח בכל מקום אחר בעולם יראה את ה־19. "יום יעד" הפך לרגע בזמן, ושגוי.
  3. timestamptz הוא באמת רגע בזמן, עם אזור זמן — ההמרה ל־Date מדויקת.
  4. (א) לבקש מחרוזת מהמסד: SELECT due::text ← "2026-11-20". (ב) להגדיר ל־pg להחזיר date כמחרוזת (types.setTypeParser(1082, (v) => v) — פרק 18). בשני המקרים, ה־API מחזיר "2026-11-20".
⚠️ טעויות נפוצות
  • לבדוק רק במחשב שעובד ב־UTC (שרת, CI) — שם הבאג לא מופיע, ובמחשב של המפתח בישראל כן (או להפך).

P16-E79 · DELETE או "מחיקה רכה"? 🧠 הבנה רמה 1

💡 רמז 1

אחרי DELETE השורה לא קיימת. אחרי (ב) היא קיימת, רק "מוסתרת".

💡 רמז 2

"שכחתי לסנן is_active" — באיזה מקום זה יקרה?

✅ פתרון
  1. המסד יסרב (אם יש מפתח זר, פרק 17), או — בלי מפתח זר — ההזמנות יצביעו על מוצר שלא קיים. היסטוריה נשברת.
  2. כל שאילתה ל"מוצרים זמינים" צריכה WHERE is_active — ומספיק מקום אחד ששכח, והמוצר "חוזר".
  3. בשתיהן 204. אחר כך GET ← 404 בשתיהן (ב־(ב) — כי ה־route מסנן is_active). ללקוח זה נראה אותו דבר.
  4. מחיקה אמיתית (או "אנונימיזציה" — דריסה של השם, האימייל והטלפון). מחיקה רכה לא מוחקת את המידע — רק מסתירה.

כלל אצבע: נתונים עסקיים שיש להם היסטוריה (מוצרים, הזמנות) — רכה. מידע אישי לבקשת המשתמש, ונתונים זמניים (sessions, טוקנים) — מחיקה אמיתית.

⚠️ טעויות נפוצות
  • לבחור מחיקה רכה "ליתר ביטחון" לכל טבלה — הטבלאות מתמלאות בשורות מתות, וכל שאילתה צריכה לזכור לסנן.

P16-E24 · אתגר: טבלת קופונים 🤖 💻 כתיבת קוד 🤖 רמה 5

💡 רמז 1

תבנית: CHECK (code ~ '^[A-Z0-9]{4,20}$') (~ = התאמה ל־regex).

💡 רמז 2

"בדיוק אחד": CHECK (num_nonnulls(percent_off, amount_off) = 1). ו־uses <= max_uses כשהוא NULL — CHECK עם NULL עובר.

✅ פתרון
CREATE TABLE coupons (
  id           integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  code         text NOT NULL UNIQUE CHECK (code ~ '^[A-Z0-9]{4,20}$'),
  percent_off  smallint CHECK (percent_off BETWEEN 1 AND 90),
  amount_off   numeric(10, 2) CHECK (amount_off > 0),
  valid_from   date NOT NULL,
  valid_until  date NOT NULL,
  max_uses     integer CHECK (max_uses > 0),
  uses         integer NOT NULL DEFAULT 0 CHECK (uses >= 0),
  CHECK (num_nonnulls(percent_off, amount_off) = 1),
  CHECK (valid_until > valid_from),
  CHECK (uses <= max_uses)
);
CREATE TABLE

שים לב לאילוצים בסוף הטבלה — אילוץ שמערב כמה עמודות כותבים כך. ומה יקרה כש־uses יגיע ל־max_uses ושני לקוחות ינסו לממש את הקופון האחרון באותו רגע? ה־CHECK יציל אחד מהם — נראה איך בפרק 18.

⚠️ טעויות נפוצות
  • CHECK (percent_off IS NOT NULL OR amount_off IS NOT NULL) — "לפחות אחד", לא "בדיוק אחד".

P16-E25 · אתגר: מחירון עם תוויות 🤖 💻 כתיבת קוד 🤖 רמה 5

P16-E80 · יצירת מוצר — Zod ואז INSERT 🤖 💻 כתיבת קוד 🤖 רמה 3

💡 רמז 1

INSERT INTO products (name, category, price, stock, added_on) VALUES ($1, $2, $3, $4, CURRENT_DATE) RETURNING id, name, category, price, stock, is_active

💡 רמז 2

אחרי ה־parse, השתמש ב־data (עם ה־trim וה־default) — לא ב־input.

✅ פתרון
// P16-E80: יצירת מוצר — Zod ואז INSERT
import { z } from "zod";

export type Db = { query(text: string, values?: unknown[]): Promise<{ rows: any[] }> };

export const productInput = z.object({
  name: z.string().trim().min(2).max(100),
  category: z.enum(["beans", "grinders", "brewing", "accessories"]),
  price: z.number().positive().max(100000).multipleOf(0.01),
  stock: z.number().int().min(0).default(0),
});

export async function createProduct(client: Db, input: unknown) {
  const data = productInput.parse(input);
  const { rows } = await client.query(
    `INSERT INTO products (name, category, price, stock, added_on)
     VALUES ($1, $2, $3, $4, CURRENT_DATE)
     RETURNING id, name, category, price, stock, is_active`,
    [data.name, data.category, data.price, data.stock],
  );
  const r = rows[0];
  return { id: r.id, name: r.name, category: r.category, price: Number(r.price), stock: r.stock, isActive: r.is_active };
}

שלושה גבולות, שלושה תפקידים: Zod — "האם הקלט הגיוני" (עם הודעה למשתמש); המסד — "האם הנתונים עקביים" (CHECK, NOT NULL — גם אם מישהו עקף את הקוד); ו־RETURNING + המרה — "מה הלקוח מקבל". בפרק 19 Prisma יחליף את ה־SQL ואת ההמרה — אבל הגבולות יישארו.

⚠️ טעויות נפוצות
  • לשלוח ל־INSERT את input.name — בלי ה־trim, ועם stock חסר שהופך ל־undefined (ונכשל ב־NOT NULL, כי pg שולח null).
  • לתפוס את ה־ZodError בפונקציה ולהחזיר null — מי שקרא לא יודע מה היה לא תקין.
